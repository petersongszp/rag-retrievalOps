# 智能检索优化（混合召回 + 动态 TopK + Token 预算）- 7 个最容易踩的坑与避坑指南

---

## 前言

混合检索这事儿听起来就是「Dense 一路、Sparse 一路、加权融合」三件套，看代码也就几百行。但真做过才知道，**几乎每个参数、每条降级路径都埋着坑**——很多坑不是上线第一天能发现的，而是流量结构变了、新租户进来、词典更新了之后才暴露。

下面这 7 个坑，按踩中概率从高到低排序，配合主文档 [06-智能检索优化-面试题和参考答案.md](./06-智能检索优化-面试题和参考答案.md) 一起看。

---

## 🕳️ 坑 1：Dense/Sparse 权重一刀切 → acronym query 救不回来

### 问题描述
按教科书设了 dense=0.7 / sparse=0.3 的"经验值"，结果像 `JVM GC`、`K8s HPA` 这类字面量很重的 query，sparse 路虽然命中了，但被 dense 的高分压住，Top1 仍然是个语义相近的"内存管理通用文章"。

### 踩坑过程
最开始的普遍心态是"**dense 是先进技术，权重就该高一些**"。我们一开始抄了不少业界 RAG 项目的默认值，dense 权重直接给 0.8。

跑了一周看着指标都还行，nDCG@5 在 0.71 左右。直到一个用户来反馈："我搜 `etcd raft`，怎么前几条全是分布式一致性的科普文，**真正讲 etcd 实现的反而排到第 6**？"

我们去翻 debug trace，发现 sparse 路明明把 `etcd-raft.md` 排在了 sparse 第 1 名（BM25=8.4），但融合后被 dense 的"分布式系统设计"压成了第 6——dense 路那篇文章 raw 分数 0.85，归一化后 1.0×0.8=0.8；而 sparse 第 1 归一化后 1.0×0.2=0.2，差太多。

### 后果
- acronym/专有名词类 query 的 Recall@5 比纯 BM25 还低（约 -8 个百分点）
- 用户感觉"搜不到字面命中"，对系统信任度下降
- **更隐蔽的影响**：rerank 拿到的候选池就已经偏 dense 了，rerank 模型再准也没用——garbage in, garbage out

### 避坑方案
1. **权重要做 runtime override，别写死配置**：[config.go#L1103-1108](../../backend/internal/config/config.go) 已经把 `hybrid_dense_weight` 接到 runtime override，运营调权重不重启
2. **0.7/0.3 是甜点位但不是真理**：跑过 grid search，dense 在 0.6-0.8 区间 nDCG 几乎持平；超过 0.8 sparse 救不回 acronym；低于 0.6 dense 优势被稀释
3. **按 query 类型分桶评测**，别看总 nDCG：把 acronym query、长描述 query、混合 query 分开跑评测，**至少保证每一类都不退化**才能上线
4. **极端场景手动切到 RRF**：minmax 在「一路 max 也很低」时会放大噪声；BM25 候选明显异常时切 `fusion_strategy: rrf_v1` 至少排名不会被劣质 raw 分数污染
5. **配评测兜底**：每次改权重都要跑 phase2 baseline 评测集，对比 [baseline_snapshot.json](../../backend/docs/baseline/phase2/baseline_snapshot.json)

### 📚 延伸知识点
- **Hybrid Search 的常见融合方法**：CombSUM、CombMNZ、Reciprocal Rank Fusion（RRF）、Borda Count；本项目用的是带权 minmax 和 RRF 两种
- **Score normalization 的陷阱**：min-max、z-score、softmax 各有适用场景，min-max 对异常值敏感、z-score 假设近似正态，业内通病
- **Late Interaction 模型**：ColBERT 这类把 dense 检索做成 token-level，部分弥补了语义模型在字面命中上的短板，未来可考虑

### 面试时怎么说
> "在融合权重上我们踩过一个挺典型的坑。最开始权重抄业界默认值，dense 给到 0.8，觉得'dense 是新东西、权重就该高'。
>
> 上线一周看指标都还行，但有用户反馈搜 `etcd raft` 找不到真讲 etcd 的那篇。我们查 debug trace 才发现，sparse 路其实命中得很准，但 0.2 的权重在融合时根本压不过 dense 的 0.8，**字面命中被语义近似给"碾"过去了**。
>
> 后来我们就把权重调成 0.7/0.3，并且做了分类型评测——acronym 类、长描述类、混合类各跑一遍，保证每一类都不退化才上线。
>
> 这件事让我意识到，**RAG 检索里没有"先进的就是对的"，dense 和 sparse 是互补不是替代关系，谁的权重大要看 query 分布，不能拍脑袋**。"

## 🕳️ 坑 2：BM25 用候选级 IDF → 通用词被错误地当成"重要词"

### 问题描述
我们的 BM25 不是全库倒排，是先用 `like` 拉一批候选再在内存里建索引。这导致 IDF 的分母 N 是候选池大小（几十到几百），不是全库——**像 "the"、"how"、"what" 这种通用词，因为在小池子里出现频率不均匀，反而拿到了高 IDF 分**。

### 踩坑过程
最开始设计时觉得"反正候选已经过了停用词过滤，词频分布应该差不多"，没多想。

直到有一天评测集一个 case 翻车了：query 是 `how does redis persistence work`，结果 Top1 是一篇讲"how to debug Java"的文章——它在候选池里 `how` 出现 5 次，而其他候选只出现 1 次，BM25 把这条文档分数拉得特别高。

排查代码时看 [sparse_inverted_index.go#L162-164](../../backend/internal/milvus/retrieval/sparse_inverted_index.go#L162-L164) 的 IDF 公式：`log(1 + (N-df+0.5)/(df+0.5))`，这里 N = `idx.totalDocs` 就是候选池大小。**小 N 的 IDF 信号本来就不稳**，再叠加候选池里 term 频率的随机抖动，结论就跑偏了。

### 后果
- 含通用词的长 query（"how/what/why"打头那种）BM25 排序失真
- 评测里 nDCG 看不出明显问题（因为 fusion + rerank 还能救一部分），但**单跑 sparse 路 P@1 比预期低 5-8 个百分点**
- 排查时间长，因为没人会一开始就怀疑「教科书 BM25 公式」本身

### 避坑方案
1. **加强停用词过滤**：[sparse_search.go#L426-429](../../backend/internal/milvus/retrieval/sparse_search.go#L426-L429) 已经过滤了 the/a/of/how/why 等，但**业务相关的高频通用词要持续补**（比如中文的"如何"、"怎么"、"什么"——目前是已知短板）
2. **Term 长度兜底**：< 2 字符的 term 直接 drop，避免单字符在小池子里被放大
3. **未来上 corpus IDF**：离线跑一次全库的 `df` 表注入，用全局 IDF 替代候选级 IDF，**工程量不大**，已写进 phase4 backlog
4. **评测要覆盖 query 句式**：`how/what/why/...` 打头的 query 单独建一个评测子集，回归时单独看
5. **拿融合 + rerank 兜底**：好在 sparse 只是粗排，融合后 rerank 模型还能纠回来——所以**「sparse 不准但 rerank 准」也是一种正常状态**，不要把 sparse 单路指标看得太重

### 📚 延伸知识点
- **BM25 的全局 vs 局部 IDF**：业内通病，Lucene/ES 默认用 segment 级 IDF（也是局部），分布式场景下需要跨 shard 聚合 df 才能拿到准确的全局值
- **BM25F**：BM25 的多字段加权变种，不同字段（标题/正文/标签）用不同权重，可以缓解通用词主导的问题
- **TF-IDF 的 cardinality 信号**：通用词的低区分度本质是信息论里的「低熵」，可以用熵或互信息做更精细的 term weighting

### 面试时怎么说
> "BM25 我们踩过一个候选级 IDF 的坑。我们的 sparse 是「先用 like 拉候选，再内存里建倒排」的设计，最开始没意识到这个 N 不是全库，是候选池大小。
>
> 出问题的 case 是一个用户搜 `how does redis persistence work`，Top1 居然是一篇讲调试 Java 的，因为 `how` 这词在那篇文档里出现了 5 次，候选池 N 又小，IDF 给得很高，BM25 把它顶到第一。
>
> 后来我们一边补停用词、加强 term 过滤，一边规划上离线 corpus IDF——把全库的 df 算好注入索引，绕开候选池统计噪声。
>
> 这件事让我意识到，**「教科书公式」用在简化版数据结构上，第一反应要怀疑它的统计前提还成不成立**。BM25 假设了大语料 + 稳定 df，我们这种候选级实现就违反了前提，结果自然不对。"

## 🕳️ 坑 3：两路并发但忘了 ctx 透传 → Sparse 路成超时元凶

### 问题描述
Dense + Sparse 两路用 goroutine 并发跑，看起来很爽。但有一段时间线上整体 P95 飙升到 5s+，单看 dense_ms 才 200ms，全是 sparse_ms 在拖——而且 sparse 自己内部的超时配置明明是 800ms。

### 踩坑过程
最开始这块的设计很朴素：两个 goroutine 各跑一边，[hybrid_search.go#L264-302](../../backend/internal/milvus/retrieval/hybrid_search.go#L264-L302) 用 `sync.WaitGroup` 等齐两路。当时心态是"**两路都用一个父 ctx 就行了，主流程超时自然两边都会停**"。

线上跑了几个月没问题。直到有天 Milvus 集群 metadata 抖动，`like` query 的响应变慢，sparse 路单 term 查询变成 1-2s。我们配的 `SparseRetrieverConfig.TimeoutMS=800` 本以为能止血，结果 sparse 路 6 个 term 串行下来，**累计 5-6 秒**，而父 ctx 超时根本没管它——因为 sparse 内部 6 次 query 之间没检查 ctx done。

排查时差点漏掉这个，因为日志里 sparse 路返回了"成功"——它确实最后给了结果，只是花了 5 秒。

### 后果
- 整体 P95 从 1.2s 涨到 5.4s，告警炸群
- 用户侧大量请求被前端 client timeout 提前断掉
- **dense 路明明已经返回，但 `wg.Wait()` 还在等 sparse**，白白浪费了并发的好处

### 避坑方案
1. **每个 IO 调用前都要 `select { case <-ctx.Done() }` 检查**：sparse 路 6 个 term 的循环里，每次 query 之前先看主 ctx 是不是已经超时了
2. **sparse 内部超时要比父 ctx 严格**：[sparse_search.go#L193-197](../../backend/internal/milvus/retrieval/sparse_search.go#L193-L197) 用 `context.WithTimeout` 包了一层，但**这个超时是覆盖整个 sparse 流程的，不是每个 term 的**——要算好 `TimeoutMS / MaxTerms` 才安全
3. **降级到「单 term 失败也返回」**：与其卡死等所有 term，不如失败一个就 break 出来用已有候选，再标 `fallback_reason=timeout`
4. **加路由级 P99 监控**：[rag_metrics.go#L81-87](../../backend/internal/observability/metrics/rag_metrics.go#L81-L87) 的 `rag_retrieve_route_duration_seconds` 要按 route 拆分告警阈值，**dense 和 sparse 各自的 P99 应该独立设阈值**
5. **混沌测试**：定期主动注入 Milvus 慢查询，验证 sparse 真的会在父 ctx 超时时停下来

### 📚 延伸知识点
- **Go Context 取消传播**：是 cooperative 的，被调方不主动检查就感知不到——业内通病，初学者经常忽略
- **Hedged Requests**：Google 著名的"对冲请求"模式，并发发同样请求给多个副本，谁先返回用谁，能很好压制长尾延迟
- **Errgroup with Context**：`golang.org/x/sync/errgroup` 比裸 `sync.WaitGroup` 更优雅，一路出错可以让另一路也提前停，避免无效等待

### 面试时怎么说
> "两路并发我们踩过一个 ctx 超时不生效的坑。最开始觉得 `sync.WaitGroup` 加父 ctx 就够了，goroutine 自己会感知超时。
>
> 结果有次 Milvus metadata 抖动，sparse 路单 term 查询从 50ms 变成 1-2 秒，6 个 term 串起来要 5 秒以上。整体 P95 直接炸了。回头看代码才发现 sparse 内部那个 for 循环根本没 `select ctx.Done()`，父 ctx 取消了它也不管。
>
> 后来我们做了三件事：每次 query 前 check ctx；sparse 整体用 `context.WithTimeout` 包一层；按 route 拆 P99 告警，dense 和 sparse 各自独立。
>
> 这事让我学到一句话：**Go 的 context 取消是「礼貌请求」不是「强制中断」，被调方不主动检查就等于没设超时**。看着是并发，其实是串行慢调用 + 假超时。"

## 🕳️ 坑 4：动态 TopK 决策只看 query 长度 → rerank 后才发现没意义

### 问题描述
最早只有规则版 `DecideDynamicTopK`，按 query 长度决定 finalTopK。结果上线后发现：很多短 query 实际证据很多（应该多给几条），很多长 query 反而只有 1-2 条强证据（多的全是噪声）。

### 踩坑过程
规则版的设计逻辑很直观：query 短 → 用户问得精确 → minTopK；query 长 → 描述复杂 → maxTopK。这个心智模型符合直觉，所以大家都没多想。

直到有一次评测发现：`What is JVM GC?` 这种短 query，规则版给 minTopK=3，但 BM25 + Dense 召回了 12 条强相关证据；而 `请帮我详细分析一下分布式系统中的一致性算法和它们各自的应用场景以及优劣势` 这种长 query，规则版给 maxTopK=8，但 rerank 完只有 top2 是真正强的，下面 6 条都是擦边。

**规则版的根本问题是：它在 rerank 之前决策，根本不知道实际证据强不强**。短 query 也可能命中很多强证据，长 query 也可能命中一堆弱噪声。

### 后果
- 短 query 类的 nDCG@5 比 nDCG@maxTopK 反而更高——说明规则版砍多了
- 长 query 给到 LLM 的 context 里 60% 是弱证据，token 浪费 + 答案噪声
- 评测整体看不出明显问题（互相抵消），**只有按 query 类型分桶才能暴露**

### 避坑方案
1. **加策略版做二次决策**：[topk_policy.go#L107-201](../../backend/internal/milvus/retrieval/topk_policy.go#L107-L201) 实现的 `DecideStrategicTopK` 在 rerank 后跑，看真实分数分布、rerank gap、evidence density 调整
2. **必须有 fallback**：策略版 panic 了直接退回规则版，[topk_policy.go#L114-123](../../backend/internal/milvus/retrieval/topk_policy.go#L114-L123) 用 defer recover 兜住，policy_version 标 `phase2-rule-v1`、reason 加 `strategic_fallback:xxx`，**永远不会比规则版更糟**
3. **决策路径要可观测**：`DecisionReason` 字符串拼了所有触发的规则名（`broad_query+score_cliff+token_budget_cap`），`[RAG:L2]` 日志里能直接看
4. **关键阈值不要拍脑袋**：cliff 判定的 0.15、flat 的 0.08、evidence_density 的 0.34/0.7 都是对着 baseline 数据集人工拉曲线调出来的，不是经验值
5. **规则版和策略版的 bound 要分开配**：[topk_policy.go#L125-128](../../backend/internal/milvus/retrieval/topk_policy.go#L125-L128) 用 `StrategicMinTopK/StrategicMaxTopK` 而不是复用规则版的 min/max，**给运营留出空间分别调**

### 📚 延伸知识点
- **Score-based Truncation / Adaptive Cutoff**：IR 领域专门研究"什么时候截断"的子方向，有基于 entropy、score gap、cumulative gain 多种方法
- **Predictive vs Reactive 决策**：规则版是 predictive（事前猜），策略版是 reactive（事后看），二者结合是工程界对纯模型决策的常见妥协
- **rerank gap 作为置信度信号**：业内做 evidence-based refusal 时也常用同样的信号，gap 大说明 top1 可信，gap 小要谨慎

### 面试时怎么说
> "动态 TopK 我们踩过一个'只看 query 表面特征'的坑。一开始想当然地觉得 query 长就要多给点，短就少给点。
>
> 后来发现这个规则在评测上抵消，按类型分桶看才暴露问题：短 query 也可能命中一堆强证据被砍掉，长 query 也可能只有两条强证据但被塞了 8 条噪声。
>
> 现在的做法是双层决策：规则版按 query 表面特征出基线，rerank 完之后**再用真实分数分布、rerank gap、parent diversity 这些信号做策略版二次调整**。策略版 panic 了直接 defer recover 退回规则版，永远不会更糟。
>
> 这件事教我一个道理：**任何一个「在数据真正出现之前做决策」的规则，都需要一个事后修正层兜底**。不然你只能保证决策"看起来合理"，没法保证"事后回看仍然合理"。"

## 🕳️ 坑 5：Token 预算用 tokenizer → 多了一个外部依赖

### 问题描述
最初有人提议接 OpenAI tiktoken 算精确 token 数，避免 `rune/4` 这种粗暴估算。我们差点接了，**幸亏没接**——tokenizer 调用失败的时候整个守卫流程要么挂、要么降级，反而把简单问题搞复杂。

### 踩坑过程
讨论 token 预算时，最开始的心态是"**既然要算 token，那就要算准**"。有同学已经在调研 tiktoken-go、@dqbd/tiktoken 这些库了。

后来我们做了一个反向论证：**算这么准有什么用？** Token budget 本质上是个软上限，目的是不让 context 撑爆 LLM 上下文窗口；预算给到 4000，实际用 3950 还是 3990 没区别。但接 tokenizer 引入的问题立刻就出来：

- tokenizer 库要么是 native 库（cgo，跨平台编译麻烦），要么走 HTTP 调 OpenAI API（**多一个网络依赖 + RTT**）
- tokenizer 失败了怎么办？预算守卫直接挂？还是 fallback 到估算？两套代码维护成本翻倍
- 不同 LLM 用不同 tokenizer，要不要每个都接？

最后选了 [topk_policy.go#L497-514](../../backend/internal/milvus/retrieval/topk_policy.go#L497-L514) 里的 `rune/4` 简单估算。**这个坑是「差点踩进去」的坑**——记下来给后人看。

### 后果（如果踩了的话）
- 多一个外部依赖，多一个故障点
- 中英文混合场景误差只是从 ~25% 降到 ~5%，**用 buffer 能完全吸收**，工程收益接近零
- tokenizer 库版本升级和 LLM 换型号要同步维护
- 业内通病：很多 RAG 项目都接了 tokenizer，结果 latency 多了 5-20ms，得不偿失

### 避坑方案
1. **预算本来就是软上限，估算够用**：`rune/4` 中文偏高估、英文偏低估，但**预算本身留 30% buffer 就能吸收**
2. **真要算准，离线算**：评测期可以接 tokenizer 跑一次离线分析，对比估算误差，有数据驱动地调 buffer
3. **MinAnswerChunks 兜底比预算精确更重要**：[topk_policy.go#L221-223](../../backend/internal/milvus/retrieval/topk_policy.go#L221-L223) 强制保留前 N 条不看预算，**保答案完整比省 token 更重要**
4. **预算扣空时要有保底**：[topk_policy.go#L255-258](../../backend/internal/milvus/retrieval/topk_policy.go#L255-L258) 强制塞 1 条，宁可超预算也不能空返回——空返回会让上层 evidence_gate 误判成"没找到"
5. **预算开关要可控**：默认 `token_budget=0`（关闭），等高负载租户场景再启用，**不要默认就开一个会改变行为的开关**

### 📚 延伸知识点
- **BPE / WordPiece / SentencePiece**：主流 LLM tokenizer 算法，不同模型分词粒度差异大，"精确 token 数"本身是个伪命题
- **依赖最小化原则**：YAGNI（You Aren't Gonna Need It），引入外部依赖前先问「不引入会怎样」
- **Estimation vs Measurement**：监控领域同样适用，`rune/4` 是 estimation，tiktoken 是 measurement，根据用途选

### 面试时怎么说
> "token 预算这块我们差点踩进一个坑——精确化陷阱。最开始有人说'要算 token 那就要算准'，差点把 tiktoken 接进来。
>
> 后来停下来想了一下：我们这个预算本来就是软上限，给 4000 用到 3950 和 3990 没区别，**为了 5% 的精度引入一个外部库 + 网络依赖，性价比太差**。
>
> 现在用的是 `rune/4` 这种最朴素的估算，配合 30% buffer，配合 `min_answer_chunks=2` 强制保底，效果完全够用。tokenizer 那条路留给离线评测。
>
> 这事让我记住：**很多看起来"应该做"的优化，本质是「精度焦虑」而不是真实需求**。工程上反而是「**够用就好，把复杂度让位给可观测性和降级**」更有价值。"

## 🕳️ 坑 6：去重只看 document_id → 父子拆分场景下漏召回

### 问题描述
融合后用 `document_id + chunk_id` 做去重，看着没问题。但接入 parent-child 检索之后，发现一个怪现象：明明 dense 和 sparse 都召回了同一篇文档的不同 chunk，去重之后只剩一个 chunk 被保留，**另一个本来高分的 chunk 就这么被吞了**。

### 踩坑过程
最开始的去重逻辑很朴素，[dedupe.go#L9-10](../../backend/internal/milvus/retrieval/dedupe.go#L9-L10) 注释写得清清楚楚："按 document_id + chunk_id 去重"。在没有父子拆分之前这是对的——同一个 chunk 出现两次只保留一个。

接入 parent-child 后，事情变了。一篇大文档会被拆成多个 chunk（child），还会有 parent 块。dense 命中 chunk-A、sparse 命中 chunk-B，本来应该都保留，做后续 parent fill。但因为 fusion 后两条 FusedDocument 实际上 [fusion.go#L357-373](../../backend/internal/milvus/retrieval/fusion.go#L357-L373) 用的是 `document_id:chunk_id` 拼接 key，理论上应该不会撞——

**真正的坑在这里**：当某个文档的 metadata 漏写了 `chunk_id`（早期入库的 legacy 数据），buildDedupeKey 退化成只用 `document_id`，于是同文档不同 chunk 全部被合并成一条。我们排查时发现某些 KB 的 legacy 文档完全没 chunk_id 字段。

### 后果
- 受影响的 KB（约占 15% 历史数据）召回数比预期少 30-40%
- rerank 拿到的候选多样性下降，nDCG@5 看起来没变（因为头部还在），但 nDCG@8 明显退化
- 排查时间长——融合分布式日志看起来「都正常」，只有去重前后的 count 对比能暴露

### 避坑方案
1. **去重 key 要 fail-closed 而不是 fail-open**：[fusion.go#L357-373](../../backend/internal/milvus/retrieval/fusion.go#L357-L373) 当前是退化到 `document_id`，应该改为「缺 chunk_id 直接 fallback 到 `buildPseudoDocID`（content hash）」，至少保证不同 chunk 拿到不同 key
2. **入库时强制要求 chunk_id**：在 indexer 层加 schema 校验，没 chunk_id 直接拒绝写入，杜绝源头
3. **legacy 数据补迁移**：写一次性脚本扫历史文档，按 content 切片补 chunk_id
4. **加去重前后的 count 对比指标**：debug_trace 里已有 `dedupe.before_count`、`after_count`、`removed`，**比例异常（>50% 被去掉）触发告警**
5. **单测覆盖 metadata 缺失场景**：[fusion_test.go](../../backend/internal/milvus/retrieval/fusion_test.go) 要有「文档缺 chunk_id」「文档缺 document_id」「ID 全缺」三个 case

### 📚 延伸知识点
- **Fail-open vs Fail-closed**：安全/可靠性领域通用原则，元数据缺失时是宽容（按 ID 合并）还是严格（视为不同文档），决策要有意识
- **Idempotent Key Design**：去重 key 的设计本质是「等价类」定义，不同业务等价类不一样，要写 spec 而不是隐式
- **数据漂移（Schema Drift）**：长生命周期系统里 legacy 数据和新数据 schema 不一致是常态，业内通病，早期就要做 schema 校验

### 面试时怎么说
> "去重逻辑我们踩过一个 fail-open 的坑。最开始 dedupe key 是 `document_id + chunk_id`，看着挺合理。
>
> 接入 parent-child 拆分后发现一个怪现象：某些 KB 召回数比预期少 30%，但日志看不出问题。查了几天才发现是历史数据有些文档没 chunk_id 字段，去重 key 就退化成纯 document_id，**同文档不同 chunk 被错误地合并成一条**。
>
> 后来我们做了三件事：dedupe key 缺字段时 fallback 到 content hash 而不是去掉字段；入库 schema 加强校验；加了去重前后的 count 对比告警。
>
> 这件事让我意识到：**当一个 fallback 路径让"两个本应不同的东西看起来一样"时，它就不是 fallback 了，是 bug**。Fail-closed 是默认正确的工程姿势——宁可拒绝也别合并错。"

## 🕳️ 坑 7：策略版 TopK 阈值反复调 → 评测和监控割裂

### 问题描述
策略版 `DecideStrategicTopK` 里有一堆魔法数：cliff 判定 0.15、flat 0.08、evidence_density 0.34/0.7、parent_share 0.7/0.75。每个都改过几次，**但每次只改代码不改评测，最终代码和评测预期完全对不上**。

### 踩坑过程
策略版上线初期心态是"**这些阈值都是先验值，跑跑看再调**"。第一版上线后，运营反馈"长 query 召回还是少"，于是把 evidence_density 阈值从 0.4 调成 0.34；又过两周，反馈"短 query 噪声多"，把 cliff gap 从 0.12 调到 0.15；又过几周，把 parent_share 阈值挪了一次。

每次调代码 PR 都过了 review，单测也都更新了。但**评测集 baseline 一直没动**，还是用最早那一版阈值跑出来的。结果：

- 评测脚本跑出来的 nDCG@5 = 0.78
- 线上实测 nDCG@5 ≈ 0.74（按抽样人工标注）
- 没人能解释 4 个百分点的 gap，怀疑过 rerank、怀疑过 embedding 模型升级，**就是没怀疑评测基线**

最后排查时发现：评测脚本 [phase2/baseline_snapshot.json](../../backend/docs/baseline/phase2/baseline_snapshot.json) 里用的阈值版本是 `phase3-strategic-v1` 的 v1.0 版，代码里实际跑的是 v1.3 版。**评测和代码一直在割裂演进**。

### 后果
- 4 个百分点的 nDCG gap 找不到根因，团队对评测信任度下降
- 多次"看起来上线了优化但评测没涨"，PM 开始怀疑技术团队的能力
- **最大的损失是「评测失去权威性」**——后面再做调优大家都不信评测数据了

### 避坑方案
1. **策略版本号绑定阈值版本**：[topk_policy.go#L17-19](../../backend/internal/milvus/retrieval/topk_policy.go#L17-L19) 定义了 `TopKPolicyVersionStrategic = "phase3-strategic-v1"`，**任何阈值改动都要 bump 版本号**，比如改成 `phase3-strategic-v1.4`
2. **评测脚本固定版本**：baseline_snapshot.json 里要存 `policy_version`，跑评测时校验当前代码版本是否匹配，不匹配直接拒绝跑
3. **阈值改动走双轨**：新版本 shadow 上线一周，对比新旧两版的指标差异，确认改善再切流量；不要直接覆盖
4. **评测自动化跑 CI**：每次 PR 触及 [topk_policy.go](../../backend/internal/milvus/retrieval/topk_policy.go)，CI 自动跑一次 phase2 baseline，对比 baseline 偏差
5. **阈值放配置而不是代码**：当前阈值是硬编码，理想状态是放 config + runtime override，**但风险是运营乱调、所以要配 freeze 流程**

### 📚 延伸知识点
- **A/B 测试 vs 影子流量**：策略变更的两种验证模式，A/B 直接分流量、影子是新策略只跑不生效。本项目策略版迭代时更适合影子模式
- **Configuration as Code**：阈值放配置 + Git 版本管理，每次改阈值就是一次 commit，可追溯
- **Reproducibility Crisis**：ML 评测的可复现性危机——同一份代码在不同时间跑出不同结果，业内通病，根源就是各种隐式版本依赖

### 面试时怎么说
> "策略版 TopK 我们踩过一个评测和代码割裂的坑。策略版里有一堆阈值——cliff 0.15、evidence_density 0.34、parent_share 0.7 之类的。
>
> 上线后运营每次反馈我们就调一下，每次代码 PR 都过 review，单测也都更新了。但**评测基线一直没人 bump 版本**，跑出来的 nDCG 比线上抽样测高了 4 个百分点，找了好久找不到原因，最后才发现评测用的阈值快递公司是几个月前的版本。
>
> 后来我们做了几件事：策略版本号和阈值绑定，改阈值必须 bump 版本；评测脚本启动时校验版本匹配；阈值改动先走 shadow 一周，确认有效再切流量。
>
> 这事让我意识到：**所有"小改动"积累起来都会变成"大漂移"，工程上必须有强制的版本对齐机制，不能靠人记得**。评测一旦失去权威性，后面所有优化都白做。"

## 📋 避坑口诀总结

| 坑 | 一句话避坑口诀 |
|----|---------------|
| 1. Dense/Sparse 权重一刀切 | **权重做 runtime override，按 query 类型分桶评测，禁止只看总 nDCG** |
| 2. 候选级 IDF 失真 | **小 N 的 BM25 公式失效，停用词要持续补，长期上 corpus IDF** |
| 3. 并发 ctx 不传 | **Go context 是「请求」不是「命令」，每个 IO 前都要 `select ctx.Done()`** |
| 4. 动态 TopK 只看 query 长度 | **任何「事前决策」都要配「事后修正」，rerank 后再调 TopK 才靠谱** |
| 5. Token 预算精确化陷阱 | **软上限不需要精确，buffer 比 tokenizer 便宜得多** |
| 6. 去重 fail-open | **fallback 让两个不同的东西看起来一样，就不是 fallback 是 bug，要 fail-closed** |
| 7. 策略阈值漂移 | **阈值改动必须 bump 版本号，评测脚本启动时校验，CI 强制对齐** |

## 💡 面试时主动升华

讲完任意一个具体的坑后，可以顺势补一句体现深度思考：

> "其实做混合检索这件事，很多人觉得就是『多写个 BM25、加个融合公式』就完了。但真做过才知道，**70% 的坑不在算法本身，在「数据假设漂移」和「降级路径有没有真的兜底」**。
>
> dense 权重 0.7、BM25 K1=1.2、TopK 阈值 0.15，这些数字单独看都对，但**它们都依赖一个隐式假设：query 分布、corpus 分布、metadata 完整性都和当初设计时一样**。一旦任何一个前提变了——新租户进来、新词典上线、legacy 数据接入——这套数字就不对了。
>
> 所以混合检索真正的工程能力，**不是怎么把算法调到最优，是怎么让降级路径覆盖每一种「假设被打破」的场景，并且这些路径都被单测和评测覆盖**。算法是 20%，治理是 80%。"
