## 二、这个项目相比开源 RAG 系统的优势是什么

### 推荐回答

如果和开源 RAG 系统比，我觉得这个项目的差异主要有五点。

#### 1. 不是只有检索，还有完整的治理闭环
开源 RAG 系统通常只是“上传文档 + 检索回答”就结束了，但这个项目已经把评测、灰度、回滚、成本、审计、告警和后台管理平台补齐了。

#### 2. 不是只关注召回，还关注回答是否可信
项目里不仅有 `citation` 字段，还有 `citation consistency` 校验和 `evidence gate`。也就是说，不只是“给引用”，而是会判断“这些引用到底能不能支撑当前问题”，证据不足时会明确拒答。

#### 3. 检索策略不是固定参数，而是可调、可解释的
比如 `TopK` 不是写死的，而是动态 `TopK` + 策略版 `TopK`；`rewrite` 也不是让模型随便改，而是受控 rewrite，支持规则、领域词、route-specific 和模型辅助灰度。

#### 4. 它有明显的平台化特征
项目对外暴露统一检索 API，已有 Go SDK，同时已经支持面向 Agent / 企业系统的接入方式：
- 直接 HTTP API
- Go SDK
- MCP / Tool 化接入
- 其他语言 SDK 的扩展路线

这意味着它不是只能被人手动点后台使用，而是可以作为标准能力层被上游 Agent、业务服务和企业应用接入。

#### 5. 它更贴近真实企业使用场景
- 多租户
- API Key
- RBAC
- 成本治理
- 引用一致性
- 证据不足拒答

这些恰恰是企业在意，而很多开源 RAG 系统根本没做深的部分。

### 如果面试官继续追问“那你和 Dify / FastGPT / RAGFlow 比呢？”

你可以这样答：

- 和 Dify 比，我们的优势不在 workflow，而在**检索治理深度**，比如 Parent-Child、citation consistency、evidence gate、A/B 实验、策略管理和成本追踪。
- 和 FastGPT 比，我们的优势不在流程编排，而在**RAG 中台能力更完整**。
- 和 RAGFlow 比，我们在深度文档理解上未必更强，但我们在**策略治理、灰度回滚、实验评测、成本与审计**上更像一个中台，而不只是一个检索引擎。

## 三、面试官高频核心问题：你要怎么答

## 0. 面试里这些英文到底是什么意思

### `dense retrieval`
- 全称：**Dense Retrieval**
- 中文：**稠密检索 / 语义检索**
- 含义：把 query 和文档都编码成向量，再按向量相似度检索
- 优点：擅长理解语义相近、说法不同的问题
- 缺点：对精确术语、缩写、代码标识符不够稳定

### `sparse retrieval`
- 全称：**Sparse Retrieval**
- 中文：**稀疏检索 / 关键词检索**
- 含义：更依赖倒排索引、BM25、关键词匹配
- 优点：擅长精确词命中，比如缩写、版本号、函数名、字段名
- 缺点：对语义改写不敏感

### `dense + sparse hybrid retrieval`
- 全称：**Dense + Sparse Hybrid Retrieval**
- 中文：**语义检索 + 关键词检索的混合检索**
- 含义：同时跑 dense 和 sparse 两套路召回，再做融合
- 面试里最好这样讲：
  - dense 负责“懂意思”
  - sparse 负责“抓关键词”
  - hybrid 负责“两条腿走路”

### `citation`
- 中文：**引用 / 引证**
- 含义：答案里这句话具体来自哪个知识库、文档、chunk

### `citation consistency`
- 中文：**引用一致性校验 / 引用支撑一致性校验**
- 含义：不是只看“有没有 citation”，而是判断 citation 是否真的支撑当前 query

### `evidence`
- 中文：**证据**
- 含义：能够支撑回答成立的检索结果

### `evidence gate`
- 中文：**证据门禁 / 证据闸门**
- 含义：在生成答案之前，先判断当前证据是否足够支持系统回答

### `rerank`
- 全称：**Re-ranking**
- 中文：**重排序 / 精排**
- 含义：召回后再重新排序，把最相关的结果排到前面

### `token budget`
- 中文：**Token 预算**
- 含义：一次回答最多允许塞多少上下文 token，避免上下文过长、成本过高

### `route-specific rewrite`
- 中文：**按检索路线定制的 query 改写**
- 含义：dense route 和 sparse route 使用不同的 rewrite 结果

### `parent-child retrieval`
- 中文：**父子块检索 / 子块检索父块补全**
- 含义：先用小块提高命中精度，再用大块补全上下文

### `MCP`
- 全称：**Model Context Protocol**
- 中文：**模型上下文协议**
- 含义：把 RAG 能力标准化暴露给 Agent / 工具生态，便于其他系统以统一协议接入
- 面试里可以简单说：
  - SDK 更像语言绑定
  - API 更像协议接口
  - MCP 更像面向 Agent 生态的标准接入层

## 1. 什么是 dense + sparse 混合检索？为什么你们项目要这么做？

### 推荐回答

dense + sparse 混合检索，本质上就是把“语义理解能力”和“关键词精确命中能力”结合起来。

- `dense retrieval` 负责理解语义，适合“换一种说法但意思一样”的问题。
- `sparse retrieval` 负责命中关键词，适合缩写、术语、版本号、字段名、代码符号这种必须精确命中的场景。

所以我们做 hybrid retrieval，不是因为单一路线不能用，而是因为企业知识库里的 query 类型非常复杂，只靠 dense 或 sparse 单独一条路线都不稳。

### 结合项目怎么讲

你可以这样说：

在我们项目里，dense 和 sparse 不是互斥路线，而是并行召回路线。先分别召回候选结果，再做融合、rerank 和 parent-child 补全。

所以这套链路不是“向量检索 + 一个关键词兜底”，而是正式的 **hybrid retrieval pipeline**。

### 面试官可能怎么追问

#### 追问 1：为什么企业场景更需要 hybrid retrieval？

**推荐回答：**
因为企业 query 往往不是纯自然语言，它会混入：
- 产品名
- 缩写
- 版本号
- 代码符号
- 专有名词
- 中英文混合表达

这种情况下，dense 能保证语义覆盖，sparse 能保证精确命中，混合起来更稳。

#### 追问 2：dense 和 sparse 召回后怎么合并？

**推荐回答：**
核心思路是先并行召回，再做 fusion，也就是融合排序。融合时不是简单拼接，而是要综合 rank 和 score，最后再进入 rerank。

#### 追问 3：为什么混合检索之后还要 rerank？

**推荐回答：**
因为 hybrid 解决的是“召回尽量别漏”，rerank 解决的是“把最该进上下文的排到最前面”。一个偏 recall，一个偏 precision，两者职责不同。

### 一句高级表达

**我们做 dense + sparse，不是为了堆技术名词，而是为了同时覆盖语义理解和精确命中，把召回稳定性做高。**

## 2. 什么是 TopK？你们项目里的 TopK 有什么不一样？

### 推荐回答

如果只讲定义，TopK 就是一次检索准备拿多少条候选结果进入后续链路。

但在我们项目里，TopK 不是固定参数，而是一套正式的检索策略能力。

我们做了两层决策：
- 第一层是规则版动态 TopK：先根据 query 本身判断，比如它是宽泛查询、长查询还是短而精确的查询。
- 第二层是策略版 TopK：在 rerank 之后，再根据证据分布去调，比如分数是不是断崖式下降、结果是不是过于集中在同一个 parent、当前 evidence density 是否足够，以及 token budget 还能不能装下更多上下文。

所以我会把 TopK 理解成一个平衡问题：

**它不是“多拿几条还是少拿几条”，而是在覆盖度、噪声和上下文成本之间找平衡。**

### 结合项目实现怎么讲

你可以明确提到项目里有两层实现：
- `DecideDynamicTopK`
- `DecideStrategicTopK`

位置在：
[backend/internal/milvus/retrieval/topk_policy.go](file:///Users/wangzhongyang/go/code/rag-retrievalOps/backend/internal/milvus/retrieval/topk_policy.go)

里面的 `DynamicTopKConfig` 直接体现了这个设计：
- `MinTopK`
- `MaxTopK`
- `TokenBudget`
- `StrategicMinTopK`
- `StrategicMaxTopK`
- `StrategicBudgetRatio`

而且结果不是只给一个数字，还会产出 `TopKDecision`：
- `FinalTopK`
- `PolicyVersion`
- `ScoreDistribution`
- `RerankGap`
- `EvidenceDensity`
- `DecisionReason`

这就意味着 TopK 决策是**可解释、可观测、可回放**的。

### 面试官可能怎么追问

#### 追问 1：为什么不直接固定 `TopK=5`？

**推荐回答：**
固定值最大的问题是一刀切。
- 简单问题取太多，会增加噪声和 token 成本。
- 复杂问题取太少，会导致证据不足。

所以我们做动态 TopK，本质上是在避免“所有 query 都走同一套召回规模”。

#### 追问 2：为什么策略版 TopK 要放在 rerank 之后？

**推荐回答：**
因为 rerank 之后的候选排序更稳定，这时才更适合判断：
- 前几条是不是有明显断崖
- 结果是不是都来自同一个 parent
- 当前证据密度够不够
- 如果再加条数，会不会只加噪声不加价值

#### 追问 3：怎么防止 TopK 放大以后把噪声带进来？

**推荐回答：**
我们有三层约束：
- rerank 后再判断
- evidence density 参与决策
- token budget guard 最后兜底

所以不是无限扩 K，而是受控放宽。

### 一句高级表达

**在我们项目里，TopK 已经不是一个静态参数，而是和 query 特征、证据分布、parent 覆盖和 token budget 联动的检索策略。**

## 3. 什么是 rewrite？你们为什么不直接让大模型来改写 query？

### 推荐回答

rewrite 本质上是查询改写，但在我们项目里，它不是“让模型随便改一句话”，而是一套受控的召回增强能力。

它的目标是解决这些问题：
- 用户口语化表达
- 术语缩写
- 拼写错误
- 别名不统一
- dense 和 sparse 路线对 query 的需求不同

所以我们做的不是自由改写，而是**Controlled Query Rewrite**。

### 面试官可能怎么追问

#### 追问 1：为什么不直接让 LLM 重写 query？

**推荐回答：**
因为这样风险太大。主要有四个问题：
- 不可控
- 不可解释
- 不方便回放和审计
- 成本和时延不可控

所以我们采用分层设计：
- 先做规则 rewrite
- 再做领域词增强
- 最后才是模型辅助 rewrite，而且它是灰度、shadow、结构化建议，不是直接替换原 query

#### 追问 2：什么是 route-specific rewrite？

**推荐回答：**
因为 dense 和 sparse 的工作原理不同。
- dense 更看整体语义，所以 rewrite 要保守一点
- sparse 更吃关键词覆盖，所以可以更积极做术语扩展、别名扩展和缩写展开

所以项目里一个 query 最后不是只有一个 final query，而是可以针对 dense 和 sparse 生成不同 route query。

#### 追问 3：rewrite 最大的风险是什么？

**推荐回答：**
最大的风险就是偏离用户原始意图。所以项目里一定保留：
- `OriginalQuery`
- `FinalQuery`
- `RewriteStrategy`

这样无论审计、评测还是日志排查，都能看出这次到底改了什么。

### 一句高级表达

**rewrite 在我们项目里不是一个 NLP 小功能，而是一个受控的召回增强模块，重点是提升召回稳定性，同时保证可解释、可灰度、可回退。**

## 4. 什么是 citation？为什么你们项目里的 citation 更有价值？

### 推荐回答

如果只从表面看，citation 就是引用来源，告诉用户答案来自哪个知识库、哪篇文档、哪个 chunk。

但在我们项目里，citation 不只是展示信息，而是已经和“可信回答”绑定起来了。

因为真正的问题不是“有没有 citation”，而是：

**当前 citation 到底能不能支撑用户问的这个问题。**

### `citation consistency` 到底是什么意思

你可以这样解释给面试官听：

- `citation` 是引用
- `consistency` 是一致性

也就是说，它不是只检查“有没有出处”，而是在检查：

**这个出处是不是和当前 query 真正对得上。**

### 面试官可能怎么追问

#### 追问 1：citation 和 source 有什么区别？

**推荐回答：**
- `source` 更偏链路来源信息，比如 route、collection、retriever version、parent fill strategy
- `citation` 更偏证据定位和证据支撑能力

也就是说，source 回答“这条结果从哪条路线来的”，citation 回答“这条结果到底能不能作为当前问题的证据”。

#### 追问 2：你们怎么判断 citation 能不能支撑问题？

**推荐回答：**
当前实现不是直接上大模型 judge，而是先用一套启发式且可解释的方式：
- 抽 claim
- 做词面覆盖
- 做实体覆盖
- 做字符级覆盖
- 汇总成 `support_score`

这样做的优点是：
- 成本低
- 延迟低
- 可解释
- 适合先做线上工程落地

#### 追问 3：如果 citation 不支撑怎么办？

**推荐回答：**
项目不是“依然硬答”，而是会把这套结果继续交给 evidence gate。轻则降级或 refine，重则触发标准拒答。

### 一句高级表达

**在我们项目里，citation 已经从“结果展示字段”升级成了“可信回答的质量信号”。**

## 5. 什么是 evidence gate？为什么这个能力很重要？

### 推荐回答

`evidence gate` 可以理解成“证据门禁”。

- `evidence` 是证据
- `gate` 是闸门 / 门禁
- `evidence gate` 合起来，就是“先过证据门，再决定答不答”

它的职责不是生成答案，而是在生成答案之前先判断：

**当前检索出来的证据，到底够不够支撑系统继续回答。**

如果不够，系统就不该强答，而应该拒答、降级或者引导用户补充材料。

项目里这套能力已经做成独立模块，而且配置和测试都比较完整：
[backend/internal/milvus/retrieval/evidence_gate.go](file:///Users/wangzhongyang/go/code/rag-retrievalOps/backend/internal/milvus/retrieval/evidence_gate.go)
[backend/internal/milvus/retrieval/evidence_gate_test.go](file:///Users/wangzhongyang/go/code/rag-retrievalOps/backend/internal/milvus/retrieval/evidence_gate_test.go)

- `MinCitationCoverage = 0.5`

这三个阈值很适合在面试里讲，因为它们体现了 evidence gate 不是一句概念，而是有实际策略边界的：
- rerank 太低，说明相关性本身不够
- evidence density 太低，说明证据太稀
- citation coverage 太低，说明证据不可追溯

此外，项目里还定义了明确的拒答原因：
- `No-Retrieval-Hit`
- `Low-Rerank-Confidence`
- `Insufficient-Citation-Coverage`
- `Contradictory-Evidence`
- `Out-Of-KB-Scope`

这就意味着拒答不是一条模糊文案，而是**结构化、可统计、可回放的策略结果**。

### 面试官可能怎么追问

#### 追问 1：为什么 evidence gate 不放在 handler 层？

**推荐回答：**
因为 handler 看不到完整检索中间态，比如：
- rerank score 分布
- evidence density
- citation consistency 结果

而 evidence gate 恰恰要用这些信息做判断，所以它更适合放在检索层，handler 只负责把结果翻译成外部协议和拒答模板。

#### 追问 2：evidence gate 和 citation consistency 的关系是什么？

**推荐回答：**
我会把它理解成上下游关系：
- citation consistency 负责判断“证据是否支撑问题”
- evidence gate 负责利用这些信号决定“系统应不应该回答”

也就是说，citation consistency 更偏质量打分，evidence gate 更偏最终决策。

#### 追问 3：如果 evidence gate 误伤怎么办？

**推荐回答：**
项目在工程上预留了几个兜底手段：
- 阈值可调
- 开关可关
- 策略异常不阻断主链路
- 能通过日志和评测集持续回放和调参

所以 evidence gate 不是一刀切死规则，而是一个可治理的门禁层。

### 一句高级表达

**evidence gate 的本质不是“多返回一个 refusal 字段”，而是把“什么时候系统必须克制不回答”做成了可配置、可审计、可回放的工程能力。**

## 6. 什么是拒答机制？拒答阈值怎么讲才像真实做过项目？

### 推荐回答

拒答机制不是为了让系统显得保守，而是为了避免在证据不足时产生高风险幻觉。

在面试里，我不会把拒答讲成“搜不到就不答”，而会讲成：

**我们把拒答做成了 evidence gate 的结果，而不是一个拍脑袋的后处理判断。**

### 怎么回答“阈值怎么定”最稳

你可以这样答：

我们项目当前的门禁阈值不是凭感觉定的，而是先给一组稳定默认值，再通过评测集和日志回放去调：
- `MinRerankScore` 先用 `0.55` 作为第一版门槛
- `MinEvidenceDensity` 先用 `0.2` 控制证据稀疏度
- `MinCitationCoverage` 先用 `0.5` 控制可追溯性
- citation consistency 默认阈值是 `0.7`

这样设计的好处是：
- 相关性不过线就不答
- 有内容但证据太稀也不答
- 有结果但引用支撑不够也不答

同时，这些阈值不是拍死的，它们本质上是 Phase 3 检索治理参数，可以结合：
- 拒答误伤率
- 强答率
- unsupported claims 分布
- 线上 query 类型

持续调优。

### 如果面试官继续追问“你为什么不是 0.8 / 0.9？”

**推荐回答：**
如果阈值一开始设得太高，拒答误伤会很严重，很多本来可答的问题也会被挡掉。

所以第一版更合理的做法不是追求极致严格，而是：
- 先用中等偏稳的阈值上线
- 保证能拦住明显弱证据
- 再基于评测和线上日志调优

这比一开始就把阈值拉得特别高更符合工程实践。

### 一句高级表达

**拒答阈值不是“一个神奇数字”，而是一组围绕相关性、证据密度、引用支撑度建立的可调策略边界。**

## 7. 为什么你这个项目要把入库做成 MQ 异步，而不是同步处理？

### 推荐回答

这个问题我会从“耗时”上升到“系统设计”。

如果只是做 Demo，同步上传后直接切分、向量化、写库也能跑通；但在企业场景下，这样做的问题很大：
- 请求链路太长
- 用户等待时间不可控
- 失败无法优雅重试
- 批量导入会把在线接口拖垮

所以我们项目把入库拆成：
- 元数据先落库
- 再发 MQ 消息
- 由消费者异步完成解析、切分、向量化和索引写入

这样做的价值不只是“更快”，而是：
- 可以做重试补偿
- 可以做暂停/恢复
- 可以做失败回放
- 可以做任务状态跟踪
- 可以把在线请求和重处理任务解耦

### 结合项目怎么讲

文档里已经明确写到：
- 上传后不是同步入库
- 而是先落库再发消息
- 再由消费者异步处理

见：
[后台-06-RAG与后台管理平台学习指南](file:///Users/wangzhongyang/go/code/rag-retrievalOps/docs/后台-06-RAG与后台管理平台学习指南.md#L43)

### 面试官可能怎么追问

#### 追问 1：异步后怎么保证状态可见？

**推荐回答：**
通过任务表和状态流转管理，让后台可以看到文档当前是在待处理、处理中、成功还是失败。这样异步不等于黑盒。

#### 追问 2：异步后失败怎么办？

**推荐回答：**
失败不能只是打一条日志，而是要有重试、补偿和人工恢复入口。否则异步只是把问题藏起来。

#### 追问 3：为什么这件事能体现工程能力？

**推荐回答：**
因为它体现的是“把重链路拆出在线请求”的能力，本质上是吞吐、稳定性和运维友好性的优化，不是单点功能优化。

## 8. 为什么 RAG 平台需要策略中心、灰度发布和回滚？

### 推荐回答

因为 RAG 的很多关键能力，其实都不是纯代码逻辑，而是“线上策略配置”：
- TopK
- rewrite
- rerank
- fusion 权重
- evidence gate
- citation threshold

如果没有灰度和回滚，任何一个策略变动都有可能影响线上回答质量。

所以我会把策略中心理解成：

**把检索算法配置，像业务代码一样做版本化治理。**

### 结合项目怎么讲

你们项目文档里已经把这些能力列得很清楚：
- 策略版本控制
- 灰度发布
- 回滚
- A/B 实验

见：
[规划-01-RAG平台战略规划与未来路线图](file:///Users/wangzhongyang/go/code/rag-retrievalOps/docs/规划-01-RAG平台战略规划与未来路线图.md#L18)

### 面试官可能怎么追问

#### 追问 1：为什么 RAG 特别需要灰度？

**推荐回答：**
因为 RAG 的问题很多不是功能错误，而是质量波动。比如召回率变差、误拒答增加、引用支撑下降，这些都不是单测能完全兜住的，所以需要线上灰度和对照实验。

#### 追问 2：如果灰度后效果变差，怎么判断是 rewrite、TopK 还是 rerank 的问题？

**推荐回答：**
这就是为什么我们要把这些信号都结构化记录下来，比如：
- `topk_policy_version`
- `rewrite_strategy`
- `evidence_gate_result`
- `citation_support_score`

只有日志里有这些策略上下文，线上回放才有意义。

## 9. 为什么要做成本追踪和可观测性？

### 推荐回答

因为企业买的不是“一个能回答问题的玩具”，而是一套要长期运行的系统。

只要系统持续运行，企业就一定会问三个问题：
- 效果怎么样
- 成本高不高
- 出问题能不能定位

所以成本追踪和可观测性不是附属能力，而是 RAG 中台化的核心能力。

### 更高级的回答方式

在这个项目里，我会把可观测性拆成三层：
- 指标：延迟、召回数、TopK 分布、拒答率、citation 覆盖率、缓存命中率、单请求成本
- 日志：query、final query、rewrite strategy、TopK 决策原因、evidence gate、citation check
- trace：链路耗时和阶段分布

而成本追踪则不仅仅看 LLM，还要看：
- embedding
- rerank
- 检索调用
- 缓存命中情况
- 不同 KB / App / 策略的成本差异

### 一句高级表达

**企业不会只问“准不准”，还会问“值不值、稳不稳、出了问题能不能查”，这就是可观测性和成本治理的意义。**

## 10. 为什么这个项目更像 RAG 中台，而不是单体 AI 应用？

### 推荐回答

我会把“中台”和“单体应用”的差异讲成四个层次。

#### 第一，它不只提供一个问答结果，而是提供统一的检索能力
对外有统一 API、SDK 和面向 Agent 的标准化接入能力，能服务多个上游系统。

#### 第二，它不只做检索，还做知识库管理和策略治理
这说明它已经从“功能组件”变成了“平台服务”。

#### 第三，它有完整的后台管理体系
包括：
- 知识库管理
- 检索实验室
- 策略中心
- 审计日志
- 质量监控
- 成本运营

#### 第四，它天然面向多方接入和长期运营
项目已经明确在往：
- 多租户
- RBAC
- API Key
- 多语言 SDK
- MCP / Agent 接入

这些方向演进。

### 最有杀伤力的一句话

**单体 AI 应用是在解决一个业务场景，中台是在为多个业务场景提供统一能力、统一治理和统一运维。这个项目显然属于后者。**

**企业级 RAG 的关键不是多堆几个算法模块，而是把“效果、风险和治理”统一成一条工程闭环。**
