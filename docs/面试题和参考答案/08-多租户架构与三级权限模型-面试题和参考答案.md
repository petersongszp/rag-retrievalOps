# 08-多租户架构与三级权限模型-面试题和参考答案

> 面向场景：**租户 → 知识库 → API Key 三级权限模型**，以 `tenant_id` 做行级数据隔离，依托 JWT + API Key（OAuth2 暂未落地，Phase 5 预留）实现权限分级管控；按业务域拆分 `auth / repository / service / quota / ragplatform` 等模块，支撑多团队并行迭代。

## Q1：你们这个多租户的三级权限模型是怎么设计的？

**我的回答：**

核心结论：**租户 → 知识库 → API Key 三级，每一级解决一类问题**，不是为了三级而三级。

我们的三张核心表分别是 [rag_tenant.go](../../backend/internal/model/rag_tenant.go#L6-L18)、[rag_tenant_kb_permission.go](../../backend/internal/model/rag_tenant_kb_permission.go#L11-L17)、[rag_api_key.go](../../backend/internal/model/rag_api_key.go#L6-L24)。租户表是组织维度，挂套餐和配额（`max_kb_count=5`、`max_doc_count=100`、`max_storage_mb=1024`、`max_api_calls_per_day=10000`，全是默认值）；`rag_tenant_kb_permission` 是租户-知识库的多对多授权，权限粒度三档 `read / write / admin`（[rag_tenant_kb_permission.go#L5-L9](../../backend/internal/model/rag_tenant_kb_permission.go#L5-L9)）；API Key 表则是 Agent 维度的凭证，自带 `permissions` JSON 字段做更细的能力控制。

**为什么必须三级**：租户级解决"你属于哪个组织"，知识库级解决"你这个组织能访问哪几个 KB"，API Key 级解决"这个 Agent 实例只能干什么"。**三级是逐层收窄的过滤器**——一个租户可能有 10 个 KB 但某个 Agent 只能读其中 2 个，这种诉求两级表达不了。

校验链路看 `/v1/retrieve` 的 [authorizeRetrieveKBIDs](../../backend/api/handler/rag/retrieve.go#L137-L175)：先 `kbTenantRepo.GetByIDForTenant(tenantID, kbID)` 卡租户归属，再 `kbPermService.CheckPermission(tenantID, kbID, "read")` 卡知识库权限，**任何一个失败整个请求 403**，不做部分成功。

> 相关代码：[model/rag_tenant.go](../../backend/internal/model/rag_tenant.go)、[service/kb_permission_service.go#L74-L103](../../backend/internal/service/kb_permission_service.go#L74-L103)、[api/handler/rag/retrieve.go#L137-L175](../../backend/api/handler/rag/retrieve.go#L137-L175)

### 🔍 深挖追问兜底

> **Q：API Key 的 `permissions` 字段和 `rag_tenant_kb_permission` 表是不是重复了？**
> 不重复。`rag_tenant_kb_permission` 是租户对 KB 的"能不能访问"，是组织级的；API Key 的 `permissions` JSON 是"这个 Agent 能在已授权 KB 里做什么"，是凭证级的。Phase 3 合约写得很清楚：**两者求交集**——请求的 `kb_ids` 必须同时通过两道校验。

> **Q：为什么权限粒度只到 `read/write/admin` 三档？**
> RBAC 的常见做法是细粒度 ACL，但我们看实际场景：知识库就两件大事——读检索、写入库；admin 多一个删库权限。再细分成 8 个动作没有真实业务承载，反而推高 UI 复杂度。看 [normalizeKBPermission](../../backend/internal/service/kb_permission_service.go#L150-L158) 用 `kbPermissionRank` 做包含关系：admin > write > read，**校验时按 rank 比较**，简单粗暴。

> **Q：用户和租户是 1:1 还是 N:1？换租户怎么办？**
> 当前是 N:1，[rag_user](../../backend/internal/model/rag_user.go) 表里 `tenant_id` 字段写死归属。换租户目前没做，因为 Phase 1-4 不涉及成员邀请和跨租户调动，**目前没做，未来思考是 Phase 5 加 `rag_tenant_member` 中间表**。

## Q2：`tenant_id` 是怎么从 HTTP 入口一路注入到 SQL 的？中间不会丢吗？

**我的回答：**

核心结论：**全链路只信 `auth.Identity` 一个数据源**，请求体里的 `tenant_id` 一律忽略。

链路是这样的：HTTP 请求进来 → [JWTAuth](../../backend/internal/middleware/auth.go#L15-L64) 或 [APIKeyAuth](../../backend/internal/middleware/auth.go#L139-L221) 中间件解析出 token → 构造 `*auth.Identity{TenantID, UserID, Role, ...}`（[context.go#L17-L26](../../backend/internal/auth/context.go#L17-L26)）→ `auth.WithIdentity(ctx, identity)` 注入到 `context.Context` → handler 里通过 `getCurrentTenantID(c)`（[handler.go#L2118-L2147](../../backend/api/handler/kb/handler.go#L2118-L2147)）拿出来 → Repository 层强制带 `Where("tenant_id = ?", tenantID)`。

**关键决策：tenant_id 不接受请求体覆盖**。看 `/v1/retrieve` 的 [retrieve.go#L242-L286](../../backend/api/handler/rag/retrieve.go#L242-L286) switch-case，无论是 API Key、JWT 还是 legacy app_id 路径，最终的 `identity.TenantID` 都是从凭证反查出来的。Phase 3 隔离合约里专门冻结了这条规则（[phase3-l0-isolation-contract.md#L10-L17](../../backend/docs/zhuhu/phase3-l0-isolation-contract.md#L10-L17)）。

为什么这么强势：**只要给前端留一个 `tenant_id` 参数，越权就是时间问题**。攻击者改一个数字就能跨租户读数据。所以我们 handler 层只读 ctx，Repository 层方法签名直接要求 `tenantID uint64` 必传，比如 [GetByIDForTenant](../../backend/internal/repository/kb_tenant_repo.go#L29-L33)、[CountByTenant](../../backend/internal/repository/kb_tenant_repo.go#L62-L66)，**类型系统层面就不允许少传**。

中间还有一道兜底：[applyActorIsolationScope](../../backend/api/handler/kb/handler.go#L2159-L2169)，对 `tenant_id=0` 的 legacy 老数据自动 fallback 到 `user_id` 维度，**新数据走租户隔离，老数据走用户隔离**，灰度迁移期不破坏存量。

> 相关代码：[middleware/auth.go](../../backend/internal/middleware/auth.go)、[auth/context.go](../../backend/internal/auth/context.go)、[handler.go#L2079-L2169](../../backend/api/handler/kb/handler.go#L2079-L2169)

### 🔍 深挖追问兜底

> **Q：context 里塞 tenant_id 不就行了？为什么还要包一层 Identity？**
> 因为 tenant_id 不是孤立的，下游经常还要 `auth_type`（区分 JWT/API Key 走不同审计）、`api_key_id`（落 `kb_retrieve_log`）、`is_legacy`（埋点）。包成 [Identity](../../backend/internal/auth/context.go#L17-L26) 结构体 GetIdentity 一次拿全，避免散在 context 各处。

> **Q：API Key 中间件里每次都要查 `tenantRepo.GetByID` 检查 tenant 状态，性能怎么样？**
> [APIKeyAuth](../../backend/internal/middleware/auth.go#L189-L195) 这一查是单行 PK 命中，MySQL 0.5ms 内。Phase 3 没加缓存因为租户表写极少。**目前没做缓存，未来思考是给 tenant 状态加 30s LRU**，现在不是瓶颈。

> **Q：legacy app_id 路径下没有真实租户，怎么办？**
> [retrieve.go#L269-L276](../../backend/api/handler/rag/retrieve.go#L269-L276) 把 legacy 调用映射到 `systemTenantID = 1`、`systemUserID = 1`，并标 `IsLegacy=true`。这样 Repository 层照样能用 `tenant_id=1` 过滤，不打破隔离链路。

## Q3：行级隔离具体怎么落？历史数据没 `tenant_id` 字段怎么处理？

**我的回答：**

核心结论：**先加列再迁移，全程默认值 0 兜底**，不停服。

行级隔离落地分三步走：第一步 schema 扩字段，[004_add_tenant_id_to_kb_tables.up.sql](../../backend/migrations/004_add_tenant_id_to_kb_tables.up.sql) 给 `kb_knowledge_base / kb_document / kb_ingest_job / kb_job_operation_log / kb_audit_event` 5 张核心表加 `tenant_id BIGINT UNSIGNED DEFAULT 0` + 普通索引；第二步在 Repository 层强制过滤；第三步在 handler 层做 actor 兼容。

**关键决策：`DEFAULT 0` + `applyActorIsolationScope` 双轨**。看 [handler.go#L2159-L2169](../../backend/api/handler/kb/handler.go#L2159-L2169)：

```go
if tenantID > 0 {
    return query.Where(
        "(tenant_id = ? OR (tenant_id = 0 AND user_id = ?))",
        tenantID, userID,
    )
}
```

**`tenant_id > 0` 的新数据走租户隔离，`tenant_id = 0` 的老数据 fallback 到 `user_id`**。这样老用户登录时，新接口能继续看到自己以前的库；新建的库自动有 `tenant_id`。

迁移脚本是配套写的，把存量 `kb_knowledge_base` 按 `user_id` 反查 `rag_user.tenant_id` 回填——这是 Phase 3 L1 的工作，已经跑完。隔离测试有专门的单测 [isolation_test.go](../../backend/api/handler/kb/isolation_test.go#L9-L66)，4 个场景：租户匹配、租户不匹配、legacy 用户回退命中、legacy 回退不匹配，**4/4 都过才允许合代码**。

配额也是按 `tenant_id` 切的：[quota.go#L40-L42](../../backend/internal/quota/quota.go#L40-L42) 数 KB 用 `Where("tenant_id = ?", tenantID).Count`，[counter.go#L70-L72](../../backend/internal/quota/counter.go#L70-L72) Redis Key 是 `quota:api_calls:{tenantID}:{date}`，**租户 A 刷爆配额完全不影响租户 B**。

> 相关代码：[migrations/004](../../backend/migrations/004_add_tenant_id_to_kb_tables.up.sql)、[quota/quota.go](../../backend/internal/quota/quota.go)、[isolation_test.go](../../backend/api/handler/kb/isolation_test.go)

### 🔍 深挖追问兜底

> **Q：为什么不一刀切把 `tenant_id` 设成 NOT NULL？**
> 老数据迁移期间不能停服。`DEFAULT 0` 让加列操作秒级完成（MySQL 8 INSTANT ALGORITHM），后续异步回填。等回填脚本跑完、隔离回归通过，**未来思考是改成 NOT NULL + 删 fallback 分支**，目前还没做。

> **Q：所有表都加 `tenant_id` 索引，写入会不会变慢？**
> 加的是单列普通索引，写入开销可忽略。读路径反而更快——`Where tenant_id = ?` 命中索引后扫描行数从全表降到该租户的几十行。Milvus 那边也是类似思路，chunk metadata 写 `tenant_id`，检索 expr 强制拼 `metadata["tenant_id"] == ?`。

> **Q：跨租户聚合查询怎么办？比如平台总用量？**
> 平台运营接口走单独的 admin handler，**不复用普通 Repository**，并且必须显式声明 `tenantID = 0` + `IsAdmin(ctx)` 才放行。普通业务路径**永远不允许 `tenant_id = 0` 跨租户查询**，Phase 3 通过标准第 8 条明确禁止。

## Q4：API Key 这一级到底怎么用？跟 JWT 的关系是什么？

**我的回答：**

核心结论：**JWT 给人用（Admin UI），API Key 给机器用（Agent / SDK）**，两套并行不冲突。

身份分两类，看 [context.go#L8-L14](../../backend/internal/auth/context.go#L8-L14)：`AuthTypeJWT` 是用户登录后拿到的 access token，TTL 默认 [短期](../../backend/internal/auth/jwt.go#L42-L49)，带 `user_id / tenant_id / role`；`AuthTypeAPIKey` 是用户在管理后台创建的长期凭证，存的是 SHA256 哈希（[apikey.go#L30-L32](../../backend/internal/auth/apikey.go#L30-L32)），库里**只有哈希值，明文 Key 创建时返回一次**。

**关键差异**：JWT 验签是纯内存 HMAC（[jwt.go#L70-L88](../../backend/internal/auth/jwt.go#L70-L88)），不查库，吊销靠 TTL 过期；API Key 必须查库（[middleware/auth.go#L168](../../backend/internal/middleware/auth.go#L168)），但可以**实时吊销**——把 `status` 改成 `revoked` 立即生效。两套机制各自的 trade-off 都很清晰：JWT 快但吊销有延迟，API Key 慢一点但可控。

角色权限走 RBAC，[rbac.go#L27-L55](../../backend/internal/auth/rbac.go#L27-L55) 写死了 4 个角色 `owner / admin / member / viewer` 对应 9 个权限点（`tenant:read/write`、`kb:read/write`、`api_key:read/write` 等）。**API Key 默认是 `member` 角色**（[middleware/auth.go#L205](../../backend/internal/middleware/auth.go#L205)），但 `permissions` JSON 字段可以再收窄，比如某个 Agent 只允许 `kb_id IN [12, 34]`。

为什么不让 Agent 也走 JWT：**Agent 是长期运行的服务，不能每 1 小时跑一次 refresh token**。API Key 一次发放、长期使用、随时吊销，对机器更友好。

> 相关代码：[auth/jwt.go](../../backend/internal/auth/jwt.go)、[auth/apikey.go](../../backend/internal/auth/apikey.go)、[auth/rbac.go](../../backend/internal/auth/rbac.go)

### 🔍 深挖追问兜底

> **Q：API Key 校验每次都查库，QPS 高了顶得住吗？**
> `key_hash` 字段是 unique index，单次查询 PK-like 性能。Phase 3 还没加 Redis 缓存，**目前没做，未来思考是热 Key 进 Redis，TTL 60s + 吊销时主动 DEL**，但要解决吊销延迟问题。

> **Q：JWT 吊销延迟怎么办？万一员工离职 access token 还有效？**
> 现在的兜底是 [RequireTenantActive](../../backend/internal/middleware/auth.go#L109-L136)：每次请求查租户状态，租户被 suspend 立刻 403。用户级别的实时吊销目前没做，**未来思考是引入 token 黑名单（Redis Set）**，但 Phase 3 没列入范围。

> **Q：你们说支持 OAuth2，是真接了三方登录吗？**
> 老实讲，**没有**。Phase 1-4 范围明确写"不做 OAuth/SSO"（[phase3 路线图#L47](../../backend/docs/zhuhu/phase3-multi-tenant-isolation-quota-detailed-roadmap.md#L47)）。go.mod 里有 `golang.org/x/oauth2 v0.35.0` 是间接依赖，[config.go](../../backend/internal/config/config.go#L41-L92) 里也有 `GitHub / Google OAuth` 的配置结构体，但只是占位预留。**Phase 5 才计划真接飞书/GitHub/Google**（[multi-tenant-roadmap.md#L1138](../../backend/docs/zhuhu/multi-tenant-roadmap.md#L1138)）。

## Q5：为什么 `max_api_calls_per_day = 10000`？这些配额数字怎么定的？

**我的回答：**

核心结论：**默认值是 free 套餐的保守起步值，不是瓶颈值**，按真实用户使用形态调出来的。

看 [rag_tenant.go#L12-L15](../../backend/internal/model/rag_tenant.go#L12-L15) 的 4 个默认值：`MaxKBCount=5`、`MaxDocCount=100`、`MaxStorageMB=1024`、`MaxAPICallsPerDay=10000`。这是 free 套餐的硬编码默认，付费套餐通过 admin 接口改 `rag_tenant` 表覆盖。

**为什么是这些数字**：

`MaxKBCount=5`：实测一个团队建库的形态——通常按业务域分 KB（产品、客服、技术、销售、HR），5 个够 80% 团队首月使用。

`MaxDocCount=100` / `MaxStorageMB=1024`（1GB）：单 KB 平均 20 个文档、单文档 ~10MB，这是我们看到的中位数。1GB 也是阿里云 OSS / 本地存储一个比较舒服的免费阈值。

`MaxAPICallsPerDay=10000`：折算下来是 **0.12 QPS**，按一个团队 5-10 个 Agent 实例并发跑，每个每天调几百次完全够。压不到这个量证明用户还在试用阶段，付费才是真需求。

**关键参数的反直觉点**：很多人会把 free 默认值定到"勉强能用"，逼用户付费。我们反过来——**默认值给到一个真实小团队 1-2 个月够用**。理由是 RAG 还在早期教育市场，用户先把链路跑通才会评估付费，前 1 个月卡死等于把人赶走。

配额拦截在 [quota.go](../../backend/internal/quota/quota.go) 里，命中就返回 `429 quota_exceeded`：[CheckKBLimit](../../backend/internal/quota/quota.go#L29-L53) 用 `Count` 比对、[CheckAPICallLimit](../../backend/internal/quota/quota.go#L116-L134) 走 Redis 计数器。每日 API 调用数走 [counter.go](../../backend/internal/quota/counter.go#L14-L44) 的 Lua 脚本 `INCR + EXPIRE` 原子化，**Key 按 UTC 日期切**，自动过期。

> 相关代码：[model/rag_tenant.go#L7-L18](../../backend/internal/model/rag_tenant.go#L7-L18)、[quota/quota.go](../../backend/internal/quota/quota.go)、[quota/counter.go](../../backend/internal/quota/counter.go)

### 🔍 深挖追问兜底

> **Q：为什么 API 调用数用 Redis 计数器，存储用 SQL `SUM`？**
> 调用数是高频写（每次请求 +1），SQL `UPDATE` 顶不住，必须 Redis。存储是低频写（上传时才变），且 `kb_document.file_size` 字段已存在，[CheckStorageLimit](../../backend/internal/quota/quota.go#L84-L114) 一条 SUM 查询就行，不用引新组件。

> **Q：Redis 挂了配额会失效吗？**
> 会。看 [counter.go#L31-L33](../../backend/internal/quota/counter.go#L31-L33)：Redis client 为空就 `return 0` 放行，**故意不阻塞业务**。配额本质是软约束不是安全边界，Redis 抖动期间宁可漏放也不能让所有租户全部 429。监控告警单独在 Prometheus 配。

> **Q：`MaxAPICallsPerDay` 是按 UTC 还是本地时区切？**
> UTC，看 [counter.go#L35](../../backend/internal/quota/counter.go#L35) 是 `time.Now().UTC()`。**反直觉但故意的**：本地时区切会导致跨时区团队配额重置时间不一致，UTC 是统一基准。坏处是中国用户在北京时间早上 8 点会突然重置，体验略奇怪。

## Q6：线上突然有用户投诉自己看到了别租户的知识库列表，你怎么排？

**我的回答：**

核心结论：**第一反应不是改代码，是定位是哪一层漏的**——Repository 层、handler 层、还是前端展示层。

排障步骤我会这么走：

**第一步，拿 request_id 反查日志**。让用户提供出错时刻的 request_id，去 `kb_retrieve_log` 表（[kb_retrieve_log.go](../../backend/internal/model/kb_retrieve_log.go)）反查这次请求落库的 `tenant_id` 和返回的 `kb_id` 列表。如果落库的 tenant_id 是对的、返回的 kb_id 也都属于这个租户，那就是前端展示问题；如果落库 tenant_id 错了，那是身份注入链路漏了。

**第二步，按层定位**。我们的隔离链路有三层：中间件注入 Identity（[middleware/auth.go](../../backend/internal/middleware/auth.go)）→ handler 取 `getCurrentTenantID(c)`（[handler.go#L2118](../../backend/api/handler/kb/handler.go#L2118)）→ Repository 强制过滤（[kb_tenant_repo.go](../../backend/internal/repository/kb_tenant_repo.go)）。每层都有日志埋点，**对照 `[Auth] auth_type=... tenant_id=...` 这种结构化日志逐层看**。

**第三步，最大嫌疑是哪里**：根据我的经验，**最容易漏的是新加接口忘了带 `tenant_id` 过滤**。我们有过一次 review 漏的——新加的统计接口直接 `db.Find(&list)` 没带 `Where`。所以第三步直接 `Grep "Find\|First" | grep -v "tenant_id"` 找可疑 Repository。

**第四步，紧急止血**。如果确认越权，先改 `rag_tenant.status = 'suspended'` 把出问题的租户挂起（[middleware/auth.go#L125-L131](../../backend/internal/middleware/auth.go#L125-L131) 的 `RequireTenantActive` 会立刻拦截），然后赶紧上修复 patch。**先止血再复盘**。

事后必做：把出问题的接口加进 [isolation_test.go](../../backend/api/handler/kb/isolation_test.go) 这种隔离回归测试，构造租户 A/B 跨读场景，**写死单测防止再犯**。

> 相关代码：[isolation_test.go](../../backend/api/handler/kb/isolation_test.go)、[middleware/auth.go#L109-L136](../../backend/internal/middleware/auth.go#L109-L136)

### 🔍 深挖追问兜底

> **Q：你怎么保证下次 Code Review 不漏？**
> 两道闸：第一，Repository 强制要求方法签名带 `tenantID` 参数（[kb_tenant_repo.go](../../backend/internal/repository/kb_tenant_repo.go)），漏传编译不过；第二，Phase 3 隔离回归脚本是 CI 必跑项，构造租户 A/B 跨读、跨删、跨检索，**任一失败 PR 不让合**。

> **Q：用户 token 是有效的，但他怎么会拿到别租户的 kb_id？**
> 通常是前端缓存问题——A 用户登录后切 B 用户没清前端缓存，导致 B 看到 A 的列表。这种情况后端日志完全干净，要去看前端 [services/auth/session.ts](../../admin/src/services/auth/session.ts) 的 token 刷新和清理逻辑。这种"看似越权实际是前端 bug"的占比挺高。

> **Q：万一 Milvus 那边漏了过滤呢？**
> Milvus 的隔离靠 chunk metadata 里的 `tenant_id` 字段 + 检索 expr 强制拼 `metadata["tenant_id"] == ?`（Phase 3 L5 的工作）。如果 SQL 层的 `kb_id` 校验先过了那道（[authorizeRetrieveKBIDs](../../backend/api/handler/rag/retrieve.go#L137-L175)），到 Milvus 时 `kb_ids` 就已经是合法集合，**双保险，单点漏掉另一个能兜住**。

## Q7：为什么不用 schema-per-tenant 或 database-per-tenant？这种行级隔离不是最弱的吗？

**我的回答：**

核心结论：**单库行级隔离不是"最弱"，是 SaaS 场景下成本/隔离强度比最高的**。

三种主流方案的取舍我们当时讨论过：

**database-per-tenant**：每个租户一个 MySQL database。强隔离，但 **1000 个租户 = 1000 个库**，连接池、迁移脚本、备份策略全要按租户跑一遍，运维爆炸。适合金融、医疗这种合规要求极强的场景。

**schema-per-tenant**：同库不同 schema。比 database 轻一些，但一样要给每个租户单独跑 DDL，加字段时很痛苦。MySQL 还不像 PostgreSQL 那样原生 schema 概念，落地反而更别扭。

**row-level（我们选的）**：所有租户共享同一张表，靠 `tenant_id` 字段做行级过滤。**改一次表所有租户立刻生效**，连接池统一管，备份/监控/扩容都按一套打法。代价是隔离强度依赖代码纪律——一旦某个 query 漏写 `WHERE tenant_id`，就跨租户了。

**关键决策：用工程纪律换运维成本**。我们的对策是把"漏写 `WHERE tenant_id`"这件事系统性消灭：Repository 方法签名硬编码 `tenantID uint64` 参数（[kb_tenant_repo.go#L29](../../backend/internal/repository/kb_tenant_repo.go#L29)），handler 必须从 ctx 拿 [getCurrentTenantID](../../backend/api/handler/kb/handler.go#L2118)，CI 跑 [isolation_test.go](../../backend/api/handler/kb/isolation_test.go) 跨租户测试。

为什么这个 trade-off 在我们这成立：**RAG 是 PaaS 不是金融**——租户最坏情况下泄露的是知识库内容，不是钱。隔离强度要求没那么极端。等真有金融客户进来，可以单独给他们用 database-per-tenant，**这是 Phase 5 企业版的预案，不是 Phase 1-4 的事**。

Milvus 这一侧也是同样思路：所有租户共用 collection，靠 chunk metadata 里的 `tenant_id` 字段做检索 expr 过滤，**没有为每个租户开 collection**。collection 数量上去 Milvus 自己也吃不消。

> 相关代码：[multi-tenant-roadmap.md](../../backend/docs/zhuhu/multi-tenant-roadmap.md)、[phase3-multi-tenant-isolation-quota-detailed-roadmap.md](../../backend/docs/zhuhu/phase3-multi-tenant-isolation-quota-detailed-roadmap.md)

### 🔍 深挖追问兜底

> **Q：行级隔离的索引膨胀问题怎么处理？所有 KB 都在一张表，`kb_knowledge_base` 表会不会爆？**
> 估算一下：10000 个租户 × 平均 5 个 KB = 5 万行，离 MySQL 单表瓶颈（千万级）还远。真到瓶颈再考虑按 `tenant_id` hash 分表，**目前没做，未来思考是引入 ShardingSphere**，Phase 1-4 完全用不上。

> **Q：你们 ragplatform 这层为啥又抽象出 domain/application/repository 三层？是不是过度设计？**
> 看 [ragplatform/domain/retrieve_contract.go](../../backend/internal/ragplatform/domain/retrieve_contract.go#L11-L14) 是个 interface，[application/retrieve_service.go](../../backend/internal/ragplatform/application/retrieve_service.go) 是默认实现。这层是为了**让 MCP / SDK / OpenAPI 三种入口共享同一份业务契约**，将来检索实现要从单机 Milvus 换成远程服务，只换 application 层，domain 不动。Phase 4 之后这层会持续承重。

> **Q：业务域怎么拆的？为什么 auth、quota、ragplatform 是独立 package？**
> 按职责切：`auth` 只管身份（JWT/API Key/RBAC），`quota` 只管配额计数和拦截，`ragplatform` 是检索业务核心，`repository` 是数据访问，`middleware` 是 HTTP 切面。**每个包对外只暴露很薄的接口**，多团队并行开发时改 quota 不会动到 auth。代价是初期建包成本高，但 Phase 3 之后改一处影响一处的次数明显下降。
