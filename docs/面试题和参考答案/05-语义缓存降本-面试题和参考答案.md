## 1. 基础题：语义缓存的核心概念

**Q：你们做语义缓存是为了解决什么问题？简单说说核心思路。**

**我的回答：**

最核心的诉求就是 **降本**。RAG 链路里成本最重的两块：一个是向量检索（embedding + Milvus 召回 + rerank），另一个是 LLM 生成。用户问的问题里有相当比例是重复或近似的，每次都走完整链路太浪费。

我们的语义缓存做了**两层**，但要说清楚：**这两层不是「embedding + LLM 答案」，而是「进程内 query embedding LRU」+「Redis 检索结果缓存」**。

- 第一层是**进程内的 query embedding 缓存**：同一个进程里短时间内重复的 query，直接复用上次算好的向量，配 singleflight 还能合并并发请求。这层省的是 embedding 模型调用的钱。
- 第二层是**Redis 里的检索结果缓存**：把整个 retrieve 阶段（召回 + 融合 + rerank）的结果按 scope 缓存起来，命中后直接跳过整个检索链路。这层省的是检索计算和 rerank 的成本。

我们**当前阶段明确不缓存 LLM 最终回答**，因为 LLM 回答涉及 prompt 拼装、temperature、用户上下文这些变量，命中条件复杂、风险高，宁愿少省一点也不在这一层冒险。

整体下来综合成本下降 **22%**，缓存命中率稳定在 **35%** 左右——这两个数字是**基于灰度试运行 2 周的真实账单和 Prometheus 指标测算出来的**，不是拍脑袋。每 3 个请求就有 1 个不用花钱，量上去之后效益很可观。

### 🔍 深挖追问兜底

**Q：为什么不缓存 LLM 最终回答？业界很多公司都在做啊。**
> 我们评估过，但风险收益比不划算。LLM 回答的"等价条件"很难定义——同一段 prompt 拼装可能因为用户上下文不同而需要给出不同回答；而且一旦命中错了答案，用户感知是直接的"答非所问"。我们选择**用短 TTL（15 分钟）的检索结果缓存换稳定性**，把 LLM 留给实时生成。如果未来要做，必须先把"答案等价性判定"和"过期回填"补齐。

**Q：进程内 LRU 和 Redis 不会重复缓存吗？**
> 不重复，**它们缓存的不是同一个东西**。进程内 LRU 缓存的是 query → embedding 向量；Redis 缓存的是 scope → retrieve 结果。一个 query 可能两层都命中，也可能只命中第一层，是互补关系。

**Q：进程内缓存多实例之间不一致怎么办？**
> 不需要一致。进程内缓存只保证"同进程同 query 不重复算 embedding"，跨实例不共享是预期行为；真正需要跨实例共享的检索结果放在 Redis。这是**故意的**——内存缓存追求极速（μs 级），Redis 缓存追求覆盖（ms 级 + 跨实例），分工明确。

**Q：35% 的命中率是怎么算出来的？怎么验证这个方案真的省钱了？**

**我的回答：**

命中率有真实的 Prometheus 指标可以查，不是估算的。我们埋了 `rag_semantic_cache_requests_total{enabled, hit, reason}` 这个 counter，命中率就是 `hit="true"` 的占比，按 5 分钟滚动窗口算。Grafana 上能直接看到曲线。

但光看命中率没意义，关键是看 **ROI**。我们埋了两个累计 counter：`rag_semantic_cache_saved_retrieval_cost` 和 `rag_semantic_cache_saved_rerank_cost`，每命中一次就把"如果走完整链路本来要花的钱"加进去。

每天的对账逻辑是：
- **成本侧**：Redis 存储 + 网络 IO + 节点 CPU（cosine 计算）
- **收益侧**：上面两个 saved counter 的累计值

22% 这个降本数字是灰度试运行 2 周的对账结果——把 saved_cost 减掉 Redis 自身的 infra 成本，再除以本来要花的总成本。**最开始我们也担心缓存自己的开销超过省下来的钱**，跑了几天数据出来才放心：净收益是正的，而且随着 QPS 提升，单位成本会进一步下降。

> 相关指标：[rag_metrics.go#L140-173](../../backend/internal/observability/metrics/rag_metrics.go#L140-173)、Admin 接口 [/api/admin/kb/semantic-cache/gate](../../backend/api/handler/kb/semantic_cache_l5.go)

### 🔍 深挖追问兜底

**Q：35% 的命中率算法分母是什么？是所有 RAG 请求还是命中了 retrieve 阶段的请求？**
> 分母是**所有走到检索缓存查询入口的请求**，也就是 enabled=true 的总数。被 feature flag 关掉的请求不进分母。这样能精确反映"开启缓存后的真实命中表现"，避免被关掉的流量稀释指标。

**Q：怎么避免命中率指标被恶意刷高？**
> 我们不刻意防，重复问题命中缓存就是它该干的活。但我们会监控 **scope 维度的命中率分布**，某个 scope 命中率异常高（比如某 tenant 占 80%）会触发告警，让运营看是不是有刷接口行为再决定要不要加限流。

**Q：22% 这个数字将来还会变吗？**
> 会，且会变好。一是规模效应让固定成本占比下降；二是阈值和 TTL 还在调，每次小优化能挤出 1-2 个点。**这个数字是「保守起点」，不是「天花板」。**

## 2. 进阶题：技术选型与权衡

**Q：为什么用 Redis 而不是直接用向量数据库做相似查询？数据结构是怎么设计的？**

**我的回答：**

最开始我们也考虑过直接接 Milvus 做语义缓存，毕竟它就是干这个的。但仔细想了想，**杀鸡用牛刀**——我们这个场景的特点决定了 Redis 是更合适的选型：

- **数据量小**：缓存条目几十万级别，Milvus 的优势在百万千万以上才显现
- **延迟敏感**：缓存判断要求 <10ms，向量库一次 query 怎么也要几十毫秒
- **天然 TTL**：缓存 15 分钟就过期，不需要长期存储和复杂索引
- **运维成本**：项目本来就有 Redis，多用一个 keyspace 几乎零成本

具体的数据结构设计，我们用了 **String + ZSet + Set** 三种组合，每种各司其职：

1. **String 存 entry payload**：key 是 `rag:semantic_cache:entry:<sha1(scope+query+top_k)>`，value 是 JSON（包含 query embedding、retrieve 结果、命中次数、过期时间）。读写都是 O(1)。
2. **ZSet 维护 scope 内候选列表**：key 是 `rag:semantic_cache:scope:<scope_hash>`，member 是 entry_id，score 是写入时间戳。**新查询过来时，用 `ZRevRange 0 N` 拿最近 N 个候选**（默认 max_candidates=20），然后在应用层算 cosine 找最相似的。
3. **Set 做 KB → scope 反向索引**：key 是 `rag:semantic_cache:kb:<kb_id>:scope_index`，member 是受影响的 scope key 列表。知识库内容更新时，通过这个索引按 KB 批量清理相关缓存。

为什么用 scope 隔离而不用全局相似度搜索？因为我们的 query 天然带了 `tenant_id + kb_ids + strategy_version + query_type` 这些维度，**不同 scope 之间的 query 即使字面相似，召回结果也不该相同**（不同租户看不到对方的知识库）。先用 scope 把候选集劈成小集合（每个 scope 默认上限 200 条），再算相似度，比全局检索快得多。

cosine 相似度也是在**应用层**算的，不放在 Redis Lua 里——Redis 单线程，重计算放在 Lua 里会拖垮整个实例。**让 Redis 干 Redis 擅长的（KV + ZSet 排序），让应用层干计算**。

这件事给我的教训：**技术选型不是越牛越好，而是要匹配场景，够用就好。**

### 🔍 深挖追问兜底

**Q：ZSet 的 score 用时间戳，那不就只能拿到「最近的」候选，不一定是「最相似的」吗？**
> 对，这是有意为之。我们假设**相同 scope 下最近的请求最有可能相似**（业务流量有局部聚集性），加上每个 scope 上限 200 条，最近 20 条作为候选已经能覆盖绝大部分命中场景。如果未来要更精确，可以引入 LSH 把 score 改成哈希桶号，但目前的方案足够用。

**Q：为什么是 max_candidates=20？怎么定的？**
> 这是性能和命中率的平衡点。20 条候选每个算一次 cosine 大概 200μs，整体延迟控制在 <5ms；再多收益递减。配置项是 `rag.semantic_cache.max_candidates`，可以按场景调。

**Q：scope_hash 是怎么算的？为什么要再哈希一层？**
> 直接用 `tenant=1|kb=2,3|strategy=v1.2|query_type=hybrid` 这种字符串当 key 太长，而且暴露租户信息。我们用 sha1 哈希后取前 16 位作为 scope_hash，**既保证了 key 紧凑，又是确定性的**——同样的 scope 字段总是哈希成同样的值，不会出现"明明是同一个 scope 却查不到缓存"的 bug。

---

**Q：相似度阈值你们是怎么定的？为什么是 0.92？**

**我的回答：**

我们当前用的是**单一阈值 0.92**，没有做分层。这个数字是踩了几次坑迭代出来的。

最开始定的是 **0.95**，想着"要足够相似才能复用"。结果跑了一周命中率只有 10% 多一点，老板说"这降本效果还不如我们的开发投入"。我们就开始往下降。

降到 **0.85** 的时候命中率冲到 45%，没高兴两天就有用户反馈"答非所问"——比如问"怎么退款"返回了"怎么开发票"的答案。虽然都是售后类问题，但语义距离比想象的远。

最后我们停在了 **0.92**，理由：
- 在 0.88-0.95 之间跑了多组 A/B 测试，0.92 是命中率（35%）和误匹配率（< 0.3%）的拐点
- 误匹配率会被检索结果的多样性"冲淡"——即使 query 不完全等价，召回的 top_k 文档有重叠，对最终 LLM 输出影响有限

阈值统一存在配置里 `rag.semantic_cache.similarity_threshold`，热更新生效，不用重启。

**这件事给我的教训：阈值是命中率和质量的权衡，不要追求极致。** 我们也讨论过未来是否做分层（敏感领域 0.95、闲聊 0.88），但现阶段单档 0.92 + 短 TTL（15 分钟）的组合已经够用，复杂分层会带来配置维护负担，**够用就先不上**。

### 🔍 深挖追问兜底

**Q：A/B 测试怎么做的？怎么算「误匹配率」？**
> 我们灰度时把 5% 流量打到不同阈值的 bucket，然后对每个命中样本做**离线对比**——把缓存返回的 retrieve 结果和"如果不命中重跑一次"的结果做 Jaccard 相似度，<0.7 就标记为"误匹配"。每个阈值跑 3 天，挑误匹配率 < 0.3% 里命中率最高的。

**Q：阈值热更新会不会出现"切阈值瞬间命中率波动"？**
> 会有短时波动，但影响有限：旧缓存条目还是用新阈值判断，所以提阈值会让一部分原本能命中的失效（命中率短暂下降），降阈值反之。**我们的运维规范是阈值变更走灰度发布**——同步改 phase 配置，避免大流量瞬间切换。

**Q：你们想过用动态阈值吗？比如按 query 长度自适应？**
> 想过没做。query 越短越容易"碰巧相似"，按长度调阈值理论上有道理。但实测发现长度分布并不极端（90% 的 query 在 5-30 字之间），加这个复杂度收益太小。**做过收益评估，发现不值就不做**，是我们对待"看起来很聪明的优化"的一贯态度。

**Q：如果缓存里的答案过时了怎么办？比如知识库更新了，旧缓存还在返回老结果，你们怎么处理？**

**我的回答：**

这是缓存最头疼的问题，但我们的解法非常**朴素**——**用短 TTL 兜底 + scope 隔离 + 主动失效接口**三层防御，没有走"复杂的一致性协议"那条路。

**第一层：短 TTL 自动过期**。默认 15 分钟，对应配置项 `rag.semantic_cache.ttl_seconds=900`。这个值定得很短，是有意为之——我们用"快速失效"规避了大多数一致性问题。即使其他机制都失效了，最坏 15 分钟后旧缓存自动消失。

**第二层：scope 隔离 + strategy_version 嵌入**。每条缓存的 key 里都带了 `strategy_version`（检索策略版本），策略一发版，scope_hash 就变，旧缓存自动作废、新缓存重新攒。这是"**用 key 设计绕开失效问题**"——旧缓存不会被读到，自然就废了。

**第三层：主动失效接口 `DeleteByKnowledgeBase`**。当某个 KB 的内容更新（文档新增/删除/修改）时，我们调这个接口按 KB 批量清理相关 scope 的所有缓存。它通过前面说的"Set 反向索引"找到所有受影响的 scope，逐个清掉。这个调用是 KB 更新流程的一部分，已经接到了知识库管理后台。

**为什么不做版本号机制 / 5% 抽样校验 / 用户负反馈清理？** 我们评估过：
- 版本号机制和 strategy_version 嵌入 key 的效果重叠，多此一举
- 5% 抽样校验会把"命中"变成"半命中"，削弱降本效果
- 用户反馈链路太长，等用户反馈到我们清缓存，TTL 已经自然过期了

**朴素是力量**——我们用 15 分钟 TTL + 主动失效接口换来了最小的工程复杂度，迄今没出过严重的一致性事故。

### 🔍 深挖追问兜底

**Q：15 分钟 TTL 会不会太短？降本效果会不会变差？**
> 不会。我们的请求局部性其实很强——同一个用户在同一个会话里反复问相似问题，15 分钟内能复用就够了。跨会话/跨用户的"相似 query"虽然存在，但占比低。**我们用数据验证过：把 TTL 从 15 分钟拉到 1 小时，命中率只多 2-3 个点，但一致性风险翻倍**，不划算。

**Q：DeleteByKnowledgeBase 是同步还是异步？KB 更新后多久能清干净？**
> 异步，写到一个 goroutine 队列里串行执行，超时 3 秒。一般几百个 scope 几十毫秒就清完了。如果 KB 体量特别大（上万个 scope），最坏几秒内能完成；这段时间内的查询可能拿到旧缓存，但 15 分钟 TTL 是兜底。

**Q：如果 DeleteByKnowledgeBase 调用失败了怎么办？**
> 不阻塞 KB 更新主流程，只打 error 日志和告警。**因为 TTL 兜底兜得住**——最坏情况就是有 15 分钟的旧缓存被读到，可以接受。这就是短 TTL 设计的另一个隐含价值：让所有"主动失效"都变成 best-effort。

---

**Q：两层缓存（进程内 embedding + Redis 检索结果）是怎么协同的？为什么不直接做 LLM 答案缓存？**

**我的回答：**

两层缓存的协同有两个关键点：**入口顺序** 和 **写回策略**。

**入口顺序**：一个 query 进来，先查进程内 embedding 缓存（用 `cachedQueryEmbedder` 的 LRU + singleflight），命中就拿到向量；不命中就调 embedding 服务算一次再写入。**拿到向量后**才去 Redis 查检索结果缓存——用刚才的 embedding 在 ZSet 候选集里找最相似的 entry，相似度 ≥ 0.92 就直接返回缓存的检索结果。

**写回策略**：检索结果缓存是**异步回填**的——本次请求即使没命中，也会让正常的检索链路完成、然后异步把结果写入 Redis（`scheduleSemanticCacheBackfill`），不阻塞主链路。这样既不增加首次请求延迟，又能让后续相似请求受益。

为什么这两层都要，缺一不可？
- **只做 Redis 不做进程内**：embedding 模型调用还是会重复算，浪费 embedding 服务的钱
- **只做进程内不做 Redis**：跨实例无法共享检索结果，多 pod 部署下 100 个 pod 要各自暖缓存，整体命中率被稀释

至于**为什么不做 LLM 答案缓存**，前面也提过——LLM 输出的等价性很难判断，prompt 一变（加了用户偏好、上下文记忆）答案就该不同，缓存住一个错答案的代价是用户感知到的"答非所问"，比缓存检索结果错误严重得多。**我们的原则是：缓存层级越靠近用户、收益越大但风险也越大，要在能稳定控制风险的最深层级停下**。我们停在了"检索结果缓存"，再往上不做。

### 🔍 深挖追问兜底

**Q：进程内 LRU 的容量是怎么定的？满了之后淘汰策略？**
> 默认 1000 条，对应配置 `rag.embedding_cache.size`，按 LRU 淘汰，每条带 5 分钟 TTL。1000 条 × 1024 维 × 4 bytes = 4MB 左右，单实例完全扛得住。容量是按"覆盖最近 5-10 分钟所有活跃用户"反推的。

**Q：singleflight 是干嘛的？**
> 防止同一个 query 在并发场景下被多次同时调 embedding 服务。比如 100 个并发请求同时来同一个 query，没有 singleflight 就要调 100 次 embedding；有了之后，只有第一个请求真正调用，其他 99 个都等结果，然后共享。**这是 Go 里的"防抖"**。

**Q：异步回填会不会出现"刚回填完就被 KB 更新清掉了"？**
> 会，但概率低。我们的 backfill 用了 `scheduleSemanticCacheInvalidation` 做时序保护——如果发现写入时刻晚于最近一次 KB 更新事件，会跳过这次写入。**用时间戳比较来避免"写入旧值"**，比分布式锁轻量得多。

## 3. 场景排障题

**Q：线上告警说缓存命中率突然从平时的 35% 掉到了 5%，用户还没反馈，但你要马上排查，你会怎么处理？**

**我的回答：**

按照**止损优先，排查其次**的原则，我会分三步走：

**第一步：先定范围，30 秒内搞清楚影响面。**
- 拉 Prometheus `rag_semantic_cache_requests_total` 的时间序列，按 `tenant`、`kb_id`、`strategy_version` 分组，看是全量掉了还是某个维度掉了
- 看命中率掉的同时，有没有伴随其他指标异常：`rag_semantic_cache_lookup_duration_seconds` 飙升？错误率高？最近有没有发布？
- 如果是某次发布之后掉的，先**一键关闭语义缓存** feature flag（`rag.feature_flags.enable_semantic_cache=false`），让流量走完整链路。命中率不是核心链路，关掉用户感知不到，但能立刻止血

**第二步：下钻分析，2 分钟内缩小嫌疑范围。**
- 如果不是发布导致，看 Redis 健康：是不是连接超时？INFO MEMORY 看内存有没有打满？keyspace 里 `rag:semantic_cache:entry:*` 数量是不是异常少？
- 看 `strategy_version` 配置：策略一改 scope_hash 就变，旧缓存全失效是预期行为，等几分钟新缓存暖起来命中率会自然恢复
- 看 `embedding_cache` 的命中率：如果第一层 embedding 缓存也大幅下降，说明 query 分布变了（比如来了一波新用户/新业务线），缓存冷启动需要时间

**第三步：定位根因。**
- 如果是 strategy_version 切换：等缓存暖起来就好，下次发布前可以预热
- 如果是 query 分布变了：业务侧确认是不是有运营活动引入新流量，是的话不用处理；不是的话查是不是接口被异常调用
- 如果是 Redis 出问题：联系 SRE 看 Redis 实例是否扩容/升级过，检查最近的 Redis 配置变更

**核心原则：命中率下降不影响用户体验，不用慌，但要尽快定位防止成本失控。**

> 相关指标：`rag_semantic_cache_requests_total`、`rag_semantic_cache_lookup_duration_seconds`、Feature Flag [config.go FeatureFlags](../../backend/internal/config/config.go)

### 🔍 深挖追问兜底

**Q：为什么不直接看 Redis evicted_keys？**
> 因为我们目前**没有给 Redis 配 redis_exporter 抓取**，也没有 evicted 的监控告警，这是一个待补的运维债。所以排障时第一时间能看到的还是业务侧的 Prometheus 指标，Redis 内部状态需要 SRE 同学手动 `INFO MEMORY` 查。这事我们已经在 backlog 里。

**Q：如果是 Embedding 模型升级导致的命中率掉，你怎么发现？**
> 模型升级是高危操作，**我们的发布流程里要求 embedding 模型变更必须主动调 `DeleteByKnowledgeBase` 全量清缓存**。如果有人没按规范操作，会出现"新 query 算出新向量，但 Redis 里全是旧向量算出来的 entry，cosine 全部低于阈值"的现象——表现就是命中率断崖跌到接近 0。这种情况只能事后清缓存重新暖。

**Q：feature flag 关掉后，进程内 embedding 缓存还工作吗？**
> 工作。两个 flag 是独立的——`enable_semantic_cache` 控制 Redis 那一层，进程内 LRU 永远开着（这层风险极低，无脑省钱）。

---

**Q：用户反馈同一个问题，上午问的答案是对的，下午再问就错了，而且连续好几次都是这样，你怎么排查？**

**我的回答：**

这个问题很典型，得一步步来：

**第一步：先止损，把影响控制住。**
- 先确认用户具体问的什么、命中的是哪条缓存（结合 trace_id 在结构化日志里查 `semantic_cache_lookup` 的命中记录）
- 把这个用户提到的具体问题对应的 scope 调用 `DeleteByKnowledgeBase` 清掉
- 紧急情况下可以全局关闭语义缓存 feature flag，先保证答案正确，成本的事后面再说

**第二步：定范围。**
- 看是个案还是普遍：抽样最近的命中样本，对每个做"如果不命中重跑一次"的对比，看 Jaccard 相似度有没有大批量下降
- 看最近有没有 KB 更新、产品规则变更——如果有，但 `DeleteByKnowledgeBase` 没被调用，那就是失效流程漏了

**第三步：定位根因。**
- 如果是 KB 更新没清缓存：检查 KB 管理后台到 `DeleteByKnowledgeBase` 的调用链路是不是断了，是不是某个环节失败被静默吞掉
- 如果是阈值偏低导致的"语义相似但答案该不同"：把这一类 query 的领域单独挑出来，提阈值或加 hard rule（比如包含"价格""退款"等敏感词的强制走完整链路）
- 如果是 strategy_version 没变但召回逻辑变了：这是流程 bug，strategy_version 必须在任何召回逻辑变更时同步递增

我们之前真遇到过类似的：用户问"苹果手机保修多久"，缓存里存的是"苹果电脑保修多久"，相似度刚好踩在 0.93。后来我们的应对是**对涉及具体产品名/规则的 query 做硬规则前置**——直接 bypass 缓存走完整链路，宁可这一类不省钱也要保正确。

**这件事给我的教训：语义相似不等于答案相同，越是敏感领域，缓存越要谨慎。**

### 🔍 深挖追问兜底

**Q：为什么不用 Embedding 直接做精确匹配，而要用阈值匹配？**
> 因为 embedding 是语义层面的，"完全相同的 query"其实很少（用户会带不同语气词、错别字），用精确匹配命中率会非常低，回到 10% 那个尴尬区间。**阈值匹配是 trade-off 的产物，不是技术不到位。**

**Q：硬规则前置 bypass 缓存，会不会被绕过？**
> 我们的硬规则是基于**关键词正则 + 领域分类器**两层。关键词命中就 bypass，分类器判定为敏感领域也 bypass，两层任一命中就走完整链路。绕过的成本远大于收益。

**Q：为什么不做"被动校验"——命中后异步重跑一次对比？**
> 评估过，弃了。被动校验等于"把命中率为 X 的缓存变成了命中率为 X 但成本只省一半"，因为后台仍要跑一遍完整链路。**与其做半成品，不如把准入阈值定准。**

## 4. 加分题：深度思考

**Q：你觉得语义缓存这个技术的本质是什么？未来在 RAG 系统里会怎么演进？**

**我的回答：**

基于我们当前这个**朴素但够用**的实现，我对语义缓存的本质有个理解：它的本质是 **"把计算结果按语义空间做索引"**。

传统缓存按精确匹配做索引，Key 完全一致才命中。语义缓存按向量空间距离做索引，两个 Key 不需要一样，只要语义距离足够近就命中。这相当于把缓存的匹配范围从"一个点"扩大到了"一个区域"。

从这个本质出发，未来的演进方向有三个：

**第一，从"缓存结果"到"缓存计算过程"。** 我们现在缓存的是 retrieve 结果，未来可能会缓存中间产物——比如召回阶段的文档集、重排前的 score 矩阵。这样部分相似的请求可以复用部分计算，颗粒度更细、命中率更高。

**第二，从"被动缓存"到"主动预测"。** 现在是有人问了才缓存，未来可以根据用户行为预测——比如用户停留在退款页面，提前把退款常见问题缓存好，用户真问的时候零延迟。

**第三，从"单层 TTL"到"分层一致性模型"。** 我们现在是统一 15 分钟 TTL，未来可以按数据稳定性分层——产品文档类 1 小时（很少变），运营活动类 5 分钟（频繁变），FAQ 类 1 天（几乎不变）。**这本质上是把"一致性预算"按数据类别分配**。

最根本的变化我觉得是：**现在的 RAG 系统是"请求驱动"的，每次都从头算；未来的 RAG 系统会是"记忆驱动"的，系统记得之前做过什么，能复用就复用。** 语义缓存是这个演进方向的第一步，目前我们走的是最朴素的形式，但这条路是对的。
