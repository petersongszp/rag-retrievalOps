# 全链路可观测体系 - 7 个最容易踩的坑与避坑指南

---

## 前言

可观测系统看起来就是"打点、打日志、配告警"三件事，但实际上处处是坑。很多坑不是技术问题，而是认知问题——做的时候觉得没问题，线上跑几个月才发现坑了。

下面这 7 个坑，按踩中的概率从高到低排序。

---

## 🕳️ 坑 1：告警太灵敏 → 狼来了效应

### 问题描述
告警一有风吹草动就炸群，结果大家麻木了，真出问题反而没人看。

### 踩坑过程
最开始做告警的普遍心态是"宁可误报，不可漏报"。于是：
- 窗口设 1 分钟，持续时间 0 分钟，瞬间异常就告警
- 错误率 > 1% 就告警，根本不考虑 QPS 低的时候 1 个错误就 100% 错误率
- 什么指标都想告警，P50 波动、缓存命中率轻微下降都告警

结果误报频繁发生，团队成员逐渐对告警失去信任。当真正的故障发生时，大家以为又是误报，导致故障处理延迟了几十分钟。

### 后果
- 告警信噪比 < 10%，10 条告警里 9 条是假的
- 团队成员直接把告警群静音，或者干脆屏蔽
- 真故障发生时响应时间反而变长了

### 避坑方案
1. **宁晚勿滥**：5 分钟窗口 + 5 分钟持续时间，异常必须持续才告警
2. **分级处理**：P1 才 @所有人，P2 就发个消息，P3 甚至可以不发
3. **告警聚合**：同类型告警攒 1 分钟再发，别一个问题十几台机器各报一条
4. **定期复盘**：每周一上午复盘上周的告警，把没用的删掉或者调松阈值
5. **信噪比指标**：把告警信噪比作为可观测系统的核心 KPI 之一，目标 > 50%

### 📚 延伸知识点
- **告警分级方法论**：Google SRE 提的 **USE / RED / Golden Signals** 三套指标体系，可以参考用于划分 P1/P2/P3
- **error budget**：把每月允许的故障时间作为预算，超支了就停发版回归质量，是 SRE 的核心治理手段
- **告警 SLO**：把"信噪比 > 50%"、"P1 平均响应时间 < 5min"作为告警系统自身的 SLO 来运营

### 面试时怎么说
> "在告警治理方面我们踩过一个挺典型的坑。最开始觉得告警嘛肯定灵敏点好，宁早勿漏，所以就设了 1 分钟窗口，一有波动就报。
>
> 结果就是误报太多了，大家慢慢就麻木了，真出问题的时候反而没当回事，耽误了处理时间。
>
> 后来我们就调整思路了：告警这东西，**准比早重要**。宁可贵个几分钟，也不能狼来了。就改成 5 分钟窗口再加 5 分钟持续时间，而且做了分级——P1 级别的才 @所有人，P2 就普通消息发一发。现在告警质量高多了，出来一条大家都会认真看。"

## 🕳️ 坑 2：Histogram 分桶太粗 → P95 严重失真

### 问题描述
用 Prometheus 默认分桶，结果算出来的 P95 和真实延迟差了一倍，监控显示正常，实际上用户已经卡得不行了。

### 踩坑过程
最开始用 Histogram 的时候，普遍觉得"不就是统计个分布嘛，默认分桶应该够用"。

Prometheus 默认分桶是：
```
[0.005, 0.01, 0.025, 0.05, 0.1, 0.25, 0.5, 1, 2.5, 5, 10]
```

问题在于 1s - 2.5s 这个区间太宽，大量请求落在这个区间，但 `histogram_quantile` **是基于"桶内样本均匀分布"的假设做线性插值**估算的——一旦桶很宽且桶内分布不均匀（实际样本都堆在桶的某一侧），估算误差就会被放大。

线上实际延迟大部分在 1.5s - 2.2s，用户已经感知到卡顿，但监控显示 P95 = 2.5s，看起来还在 SLA 以内。这个问题排查了很久才定位到是分桶设计不合理。

### 后果
- P95 误差能到 50% 以上，监控完全不可信
- 性能退化了都不知道，等用户投诉才发现
- 优化效果也没法量化，改了代码不知道延迟到底降了多少

### 避坑方案
1. **自定义分桶**：在预期的 SLA 阈值附近加密分桶
   ```go
   Buckets: []float64{0.01, 0.025, 0.05, 0.1, 0.2, 0.35, 0.5, 0.75, 1, 1.5, 2, 3, 5, 8}
   ```
   注意 1-3s 之间有 1.5、2、3 三个桶，而不是原来的一个 2.5 桶

2. **分桶对齐业务场景**：
   - API 延迟：在 100ms、500ms、1s、2s、3s、5s 附近加密
   - 消息队列耗时：在 1s、5s、30s、1min 附近加密
   - 嵌入向量耗时：在 50ms、100ms、200ms 附近加密

3. **定期校准**：用真实日志算一下 P95，和监控值对比，误差超过 10% 就要调分桶了

### 📚 延伸知识点
- **Histogram vs Summary**：两者都能算分位数。Summary 在客户端算好分位数，准但不能跨实例聚合；Histogram 上报 bucket 计数，支持聚合但有插值误差。多 pod 场景下选 Histogram
- **t-digest / DDSketch**：业界专门解决"分位数估算"的数据结构，比传统 Histogram 精度高得多，不少 APM 产品已经用了
- **VictoriaMetrics / Mimir**：Prometheus 兼容的存储后端，支持更高效的高基数存储

### 面试时怎么说
> "关于 Metrics 指标设计我们踩过一个坑，就是 Histogram 分桶设计。最开始图省事，直接用 Prometheus 默认分桶，结果上线后发现问题了。

> 线上用户反馈卡顿，但看板上 P95 显示 2.5s，看起来还在 SLA 以内。查了一天才发现问题：默认分桶 1s 之后直接跳到 2.5s，中间是空的，大量 1.5s-2s 的请求都被粗暴地算到 2.5s 那个桶里，再加上 `histogram_quantile` 是基于"桶内均匀分布"的假设做插值的，桶宽 + 分布不均一叠加，误差就特别大。

> 之后我们就专门做了自定义分桶，在 SLA 阈值附近加密，比如 1s、1.5s、2s、3s 都设了桶，把误差控制在 5% 以内。这件事给我的教训就是：**数据准确是可观测的基础，数据不准的话，看板再漂亮也没用**。"

## 🕳️ 坑 3：标签基数爆炸 → Prometheus 直接 OOM

### 问题描述
给指标加了个看似普通的标签，结果 Prometheus 内存爆了直接挂。

### 踩坑过程
为了做细粒度的 QPS 统计，给请求量指标加了 user_id 标签，当时觉得很合理。

上线初期用户量小，没什么问题。但随着用户量增长到几十万，Prometheus 突然 OOM 挂掉了。

原因是 Prometheus 里每个标签的每个值组合，都是一个独立的时间序列：
- status 有 3 个值，error_code 有 10 个值，user_id 有 10 万个值
- 3 × 10 × 100,000 = **300 万个时间序列**

每个时间序列在内存里占 1-2KB，300 万个就是 3-6GB，查询时还要遍历这么多序列，自然就 OOM 了。

这个坑的特点是温水煮青蛙，内存随着用户量慢慢增长，很难提前发现。

### 后果
- Prometheus OOM 挂掉，整个监控体系瘫痪
- 恢复要很久，因为重启的时候要加载几百万时间序列
- 还在不断写入的话，起来又挂，陷入死循环

### 避坑方案
1. **标签三原则**：
   - ✅ 标签值必须是**可枚举**的（status、error_code、strategy 这种）
   - ❌ 标签值绝对不能是**无限的**（user_id、request_id、order_id 这种）
   - ❌ 标签值的种类预估不能超过 100 个

2. **基数检查**：加新标签之前先算一下：`标签1基数 × 标签2基数 × ...`，超过 1 万就要谨慎

3. **PromQL 排查工具**（线上日常巡检必备）：
   ```promql
   # 找出基数最高的 Top10 指标，第一时间定位嫌疑指标
   topk(10, count by (__name__)({__name__=~".+"}))

   # 排查某个指标的高基数标签是哪一个
   count(count by (label_name) (metric_name))

   # 监控时间序列总数的增长趋势（这是 Prometheus 自身指标）
   prometheus_tsdb_head_series
   ```
   建议把第三条配成告警，超过阈值（比如 100 万）就提前介入

4. **监控指标本身**：给 Prometheus 自己加监控，`prometheus_tsdb_head_series` 这个指标就是时间序列总数，超过阈值要告警

5. **高基数数据放日志**：真要按 user_id 查，去结构化日志里查，不要放 Prometheus 里

### 📚 延伸知识点
- **Cardinality Bomb**（基数炸弹）：高基数标签是 Prometheus 的"经典反模式"，社区文档专门把它列为头号陷阱
- **VictoriaMetrics / Cortex / Mimir**：原生支持高基数和水平扩展的 Prometheus 兼容方案，日均序列数百万级别可以考虑
- **指标分层**：Metrics 看趋势、Logs 查明细、Traces 看链路——**三者职责不要混**，是 OpenTelemetry 三大支柱的核心思想

### 面试时怎么说
> "关于标签设计我们踩过一个 Prometheus 经典坑。当时想做细粒度统计，能看到每个用户的请求量，就给请求量指标加了个 user_id 标签。

> 上线初期用户量小没事，后来涨到几十万，Prometheus 直接 OOM 挂了。原因就是每个标签值组合都是一个独立的时间序列，status、error_code 加上 user_id，乘起来一下跑出 300 万个序列，直接把内存撑爆了。

> 现在我们加标签之前都会先算一下基数，而且也会监控时间序列总数的增长。这件事也让我想明白了一个边界：**Metrics 是用来统计宏观趋势的，想查单条记录那是 Logs 该干的事，别混了**。"

## 🕳️ 坑 4：Debug Trace 性能开销没控制 → 拖慢请求

### 问题描述
为了方便排查问题，Debug Trace 里塞了太多东西，结果正常请求的延迟涨了 30%。

### 踩坑过程
Debug Trace 的初衷是线上出问题时，能看到每个阶段的详情，方便快速排查。

为了排查方便，Trace 里加入了越来越多的信息：各阶段的完整文档列表、分数变化、过滤原因等，导致一个 Debug Trace 的 JSON 达到几十 KB。

最开始是默认关闭的，只有传特定 header 才开启，性能没问题。

后来为了排查方便，默认开了 1% 采样。结果一周后发现整体 P95 涨了 30%，定位了很久才发现是 Debug Trace 的问题。

性能开销来自几方面：
- 序列化几十 KB 的 JSON 需要几十毫秒
- 写入 MySQL 又要几十毫秒
- 即使是 1% 采样，所有请求都要做"要不要采样"的判断，也有开销

这个坑的特点是性能退化是累积的，每次加一点点，很难察觉。

### 后果
- 正常请求延迟涨了 20%-30%
- 为了"排查问题方便"，把所有用户的体验都搞差了
- 性能回退了都找不到根因，因为每次加一点点，看不出来

### 避坑方案
1. **默认全关，按需开启**：不要搞什么默认采样，排查问题的时候针对特定 request_id 或者特定 tenant 开启

2. **开销上限**：Debug Trace 总大小不能超过 4KB，超过就截断，只保留最关键的信息

3. **只存统计值，不存完整列表**：
   - ✅ 存"命中 150 个文档，去重后 80 个"
   - ❌ 不要把 150 个文档的 ID 全存进去

4. **性能回归测试**：每次改 Debug Trace，都要压测一下对延迟的影响

5. **分级采样**：正常请求完全不开，错误请求 100% 开，慢请求 100% 开

### 📚 延伸知识点
- **Sampling 策略**：头采样（Head-based，请求开始就决定）vs 尾采样（Tail-based，请求结束后根据结果决定）。错误/慢请求 100% 采样属于尾采样，更精准但实现成本高
- **Observability Overhead 黄金法则**：业内共识——可观测带来的性能开销**不能超过 5%**，超过就要重新审视采样策略
- **eBPF**：新一代低开销的可观测技术，在内核态采集数据几乎无侵入，代表项目 Pixie、Cilium Tetragon

### 面试时怎么说
> "Debug Trace 这东西真的是双刃剑，我们在性能开销上踩过坑。最开始为了排查方便，往里面塞了特别多东西，每个阶段的完整文档列表都存了，一个 Trace 几十 KB。

> 后来为了方便就默认开了 1% 采样，结果线上 P95 直接涨了 30%，查了半天才发现是这个问题。

> 现在我们就很明确了：**可观测绝对不能影响业务本身的性能**。Debug Trace 默认全关，按需开启，而且只存统计值，不存完整列表，大小控制在 4KB 以内。毕竟，监控系统把业务给拖垮了，那不是本末倒置嘛。"

## 🕳️ 坑 5：TraceID 透传漏了 → 链路断了查不到

### 问题描述
跨服务调用的时候 TraceID 没传过去，结果一个请求到了第三个服务，链路就断了，根本不知道哪慢。

### 踩坑过程
单服务场景下 TraceID 就是 request_id，没什么问题。

随着服务拆分增加了 embedding、rerank 等多个服务，跨服务调用需要透传 TraceID。

HTTP 和 gRPC 调用都做了透传，但问题出在各种边缘场景：
- 异步消息队列（Redis Stream）发消息时，忘了把 TraceID 塞进消息体
- Go 协程池提交任务时，context 不会自动跨协程传输，TraceID 丢了
- 第三方 SDK 调用时，没有传递 TraceID

只要有一处没传，整个链路就断了，前面的投入就白费了。排查问题时链路图是碎的，根本不知道瓶颈在哪。

### 后果
- 跨服务调用的链路图是碎的，只能看到半截
- 排查问题的时候，慢到底是发生在哪个服务，根本不知道
- 白瞎了链路追踪的投入，钱花了，效果没看到

### 避坑方案
1. **公共工具类强制透传**（核心思路：**工具层封死，不靠人自觉**）：
   - 封装统一的 HTTP Client（自动注入 `X-Trace-Id` 请求头）、gRPC Client（自动塞 metadata）
   - 封装统一的 MQ Producer/Consumer，自动把 TraceID 塞进消息体的 metadata 字段
   - 封装统一的协程池，提交任务时自动从父 ctx 把 TraceID 拷到子 ctx（Go 的 `context` 不会跨 goroutine 自动传，必须手动携带）
   - 不让大家直接用原生的，必须用封装好的

   > 我们用的是**自研 TraceID 透传**，没接 OpenTelemetry。原因是早期项目轻量、链路不复杂，自研一套就够用；如果未来要跟外部系统打通或者上分布式追踪平台，再考虑迁到 OTel。

2. **UT 覆盖**：写个单元测试，调一下各个公共方法，看 TraceID 有没有传过去

3. **漏传告警**：日志里如果 TraceID 是空的，打个 error 日志，累计到一定量就告警

4. **链路完整性监控**：定期统计一下，有多少 Trace 是完整的，多少是断的

### 📚 延伸知识点
- **W3C Trace Context**：跨语言、跨厂商的链路追踪标准，定义了 `traceparent`、`tracestate` 两个 header，未来对接外部系统时大概率要遵循
- **OpenTelemetry**：CNCF 毕业项目，事实上的可观测标准，统一了 Metrics/Logs/Traces 三大支柱的 SDK 和协议
- **Context Propagation**：Go 里跨 goroutine 必须显式传 ctx 是设计哲学，类似 Java 的 ThreadLocal 跨线程也会丢，是所有语言通病

### 面试时怎么说
> "TraceID 透传真的是说着简单做着难，我们在这上面踩过好几次坑。你根本不知道代码里藏了多少种跨边界的调用方式，HTTP、gRPC、MQ、协程池，甚至第三方 SDK，只要有一个地方漏传了，整个链路就断了。

> 我们最开始是消息队列发消息忘了传，后来又发现协程池里提交任务时 TraceID 丢了。

> 现在我们的做法就是**所有跨边界调用都必须用封装好的公共工具类，自动透传 TraceID，不让业务同学自己写**。而且还加了漏传告警，日志里一出现空 TraceID 就报警。这件事给我的感受是：可观测的基础设施，一定要做到防错，不能靠人自觉。人总是会忘的，工具层面封死才是王道。"

## 🕳️ 坑 6：结构化日志字段膨胀 → 写入性能拖垮

### 问题描述
日志字段越加越多，最后一条日志几个 KB，写入 MySQL 拖慢了整个检索请求。

### 踩坑过程
结构化日志最开始只有二十多个基础字段，很清爽。

随着业务发展，各角色都有自己的诉求：
- 策略同学需要 strategy_version 做 AB 实验对比
- 产品同学需要 query_type 看不同查询类型的分布
- 运维同学需要 host_ip 方便问题定位
- 检索同学需要各阶段召回量统计

字段越加越多，很快达到八十多个，一条日志就有几 KB。

业务量不大时 MySQL 能扛住，当一天日志量达到几百万条时，问题就爆发了：
- 写入 QPS 上不去，MySQL 主库 CPU 飙到 80%
- 日志写入超时，反过来影响检索接口的响应时间
- 单表几个月就几十 GB，备份恢复都慢
- 查询时因为行太宽，IO 性能也很差

本来是用来排查问题的工具，结果本身成了性能瓶颈。

### 后果
- 数据库写入瓶颈，反过来拖慢业务接口
- 存储成本快速上涨，几个月就要删历史数据
- 查询性能下降，排查问题反而更慢了

### 避坑方案
1. **字段准入机制**：加新字段要评审，真的需要吗？能不能放 Debug Trace 里而不是主表？

2. **冷热分离**：
   - 热数据（最近 7 天）：存在 MySQL，字段全，查询快
   - 冷数据（7 天以上）：归档到对象存储，要用的时候再捞

3. **字段类型优化**：
   - 能用 int 就不用 varchar，能用 tinyint 就不用 int
   - 状态码用数字存，不要存字符串
   - JSON 字段尽量小，只放必要的

4. **分库分表/按时间分表**：按月建表，上个月的表改成只读

5. **预留方案**：日志写入的时候同时写一份到 Kafka，未来量真的大了直接接 ClickHouse，不用改业务代码

### 📚 延伸知识点
- **冷热分离**：业内通用方案，热数据用 OLTP（MySQL）/搜索引擎（ES），冷数据归档到对象存储（S3/OSS）+ 列存（ClickHouse / Parquet）
- **写放大**：宽表的每一次写入都会带上所有字段，字段越多 IO 越多。这就是"字段膨胀"导致写入瓶颈的根本机制
- **ClickHouse / Doris**：日志/指标场景常见的列式存储选型，单机就能扛日均亿级写入

### 面试时怎么说
> "结构化日志我们踩过一个字段膨胀的坑。最开始也就二十个字段，大家你加一个我加一个，都觉得'多个字段也没啥事'，不知不觉就八十多个了，一条日志好几 KB。

> 业务量上来之后问题就来了，一天几百万条，MySQL 写入直接成瓶颈，反而把检索接口拖慢了。

> 现在我们加新字段要走评审，而且做了冷热分离，最近 7 天的存在 MySQL 方便查，超过 7 天的归档到对象存储。这件事让我意识到：**可观测也是有成本的，每个字段加进去之前都得想想，这个信息值不值得花这么多存储和性能成本去存**。"

---

## 🕳️ 坑 7：可观测本身成了故障点 → 监控系统先挂

### 问题描述
出问题了想去看监控，结果 Grafana 打不开，Prometheus 挂了，雪上加霜。

### 踩坑过程
这个坑最讽刺：做监控是为了发现故障，结果故障发生时，监控系统先挂了。

有一次线上 Milvus 出问题，检索请求全超时。大家想去看 Grafana，结果 Grafana 502——因为错误日志量暴涨几十倍，把 MySQL 打挂了，而 Grafana 的数据源正是同一个 MySQL。

更糟的是，告警也没发出来，因为 Prometheus 时间序列太多 OOM 了，正在重启。

结果就是业务、监控、告警全挂了，团队只能黑盒排查，故障时间大大延长。

这个问题的根源是监控系统和业务系统没有物理隔离，共享数据库和资源，一荣俱荣一损俱损。

### 后果
- 故障的时候失去了所有排查工具
- 故障时间成倍延长
- 团队信心严重受挫

### 避坑方案
1. **物理隔离**：监控系统和业务系统完全分开，用独立的数据库、独立的服务器、独立的网络
   - 业务用的 MySQL 和可观测用的 MySQL 绝对不能是同一个
   - Prometheus、Grafana 部署在独立的 K8s 集群或者独立的机器上

2. **监控的监控**：
   - 搞个最简单的健康检查脚本，定时 ping 一下 Prometheus 和 Grafana 能不能访问
   - 这个脚本绝对不能用你正在监控的告警系统发，要用独立的通道
   - 真挂了直接打电话给运维

3. **降级预案**：
   - Prometheus 挂了怎么办？至少能查结构化日志
   - MySQL 挂了怎么办？至少能看实时日志
   - 不能所有鸡蛋都放在一个篮子里

4. **容量规划**：Prometheus 的存储、内存、CPU 要提前规划好，不要等满了再扩容

### 📚 延伸知识点
- **Meta-monitoring（监控的监控）**：SRE 经典原则，监控系统自身必须有独立监控通道，且不依赖被监控对象
- **Dogfooding 反模式**：监控系统用自己监控自己，看似自洽实际是单点故障的伪装
- **混沌工程（Chaos Engineering）**：主动注入故障验证可观测系统能不能扛得住，Netflix Chaos Monkey 是这个领域的鼻祖
- **黄金信号 Golden Signals**：Google SRE 总结的 4 大核心指标——延迟、流量、错误率、饱和度，监控系统自身也应该用这套标准衡量

### 面试时怎么说
> "关于监控系统本身的可用性，我们踩过一个特别讽刺的坑。有次底层存储出问题，我们想去看监控，结果 Grafana 打不开，告警也没发出来。

> 原因是业务 MySQL 被暴涨的错误日志打挂了，而 Grafana 用的就是同一个库。同时 Prometheus 刚好因为时间序列太多 OOM 重启了。那半个小时我们完全是黑盒排查，特别痛苦。

> 之后我们就把监控系统和业务系统彻底物理隔离了，各用各的数据库、各用各的服务器，而且加了'监控的监控'——用一个独立的脚本去检查监控系统本身的健康。

> 这个教训我记得特别清楚：**监控系统的可用性，必须比业务系统的可用性还要高**。这本质上是 SRE 里的 **meta-monitoring 原则**——监控系统的可靠性必须独立于被监控对象，否则就是 dogfooding 反模式。不然真出问题了，你连排查的工具都没有。"

## 📋 总结：7 个坑的避坑口诀

| 坑 | 避坑口诀 |
|---|---------|
| 告警太灵敏 | 宁晚勿滥，信噪比优先 |
| Histogram 分桶太粗 | SLA 附近加密分桶，定期校准误差 |
| 标签基数爆炸 | 标签只加可枚举的，高基数放日志 |
| Debug Trace 拖性能 | 默认全关按需开，只存统计值不存列表 |
| TraceID 透传漏了 | 公共工具类强制透传，不准用原生 |
| 日志字段膨胀 | 加字段要评审，冷热分离降成本 |
| 监控本身挂了 | 物理隔离，监控的监控，降级预案 |
