## 1. 整体架构题：你们这个混合检索是怎么设计的？

**Q：你们做混合检索是为了解决什么？整体架构怎么分层？**

**我的回答：**

最核心的痛点是**纯向量召回对缩写、专有名词、代码标识符这类字面量很弱**。比如 query 里写「JVM GC」，向量模型可能把它泛化成"内存管理"，把真正命中 `JVM` 字面的文档排到后面。我们线上观察到，靠纯 dense 检索时这类 query 的 Recall@5 长期在 60% 出头。

整体设计是**双路并行召回 + 加权融合 + 双层动态 TopK + Token 预算守卫**，分四层：

- **召回层**：Dense 走 Milvus 向量检索，Sparse 走 BM25 倒排，两路用 `sync.WaitGroup` **并发跑**，互不阻塞，单边挂了另一边照常出结果。
- **融合层**：默认 `minmax_v1` 归一化加权（dense 0.7 / sparse 0.3），可切到 `rrf_v1`（RRFK=60）。融合后做去重。
- **TopK 决策层**：先走规则版 `DecideDynamicTopK`（按 query 长度/类型出 finalTopK），rerank 之后再走策略版 `DecideStrategicTopK`（看分数分布、rerank gap、证据密度二次调整）。
- **预算守卫**：`ApplyTokenBudgetGuard` 按 token 估算逐条加入，超预算就截断，但**至少保留 `min_answer_chunks=2` 条**，避免饿死答案。

**这个架构的关键不是堆模块，而是「每一层都能单点降级」**。Sparse 挂了走 dense，rerank 挂了用融合分，token 预算为 0 就退化成纯 finalTopK 截断。

> 相关代码：[hybrid_search.go#L264-302](../../backend/internal/milvus/retrieval/hybrid_search.go#L264-302)、[topk_policy.go](../../backend/internal/milvus/retrieval/topk_policy.go)、[fusion.go](../../backend/internal/milvus/retrieval/fusion.go)

### 🔍 深挖追问兜底

**Q：为什么不直接用 Milvus 自带的 hybrid search？非要自己拼？**
> Milvus 的 hybrid 强依赖它的 sparse 字段类型，我们的集合最初是纯 dense 建的，迁移成本高；而且我们要在融合前后插自己的 rewrite/rerank/parent-child fill，自己拼调度链路控制力更强。**说白了是为了把每一步的可观测性和降级开关握在自己手里**。

**Q：两路并发会不会有 goroutine 泄漏风险？**
> 不会。`sync.WaitGroup` 等齐两路，channel buffer=2 双方都写进去就关，主流程 `range` 完才继续。即便其中一路 panic 也是 goroutine 内部 recover 不了直接挂主进程，但实际两边都用 ctx 透传超时，超时返回 err 不返回 nil。

**Q：那如果 query 里既有自然语言又有专有名词呢？**
> 就是混合检索发力的场景。Dense 命中语义近似，Sparse 命中字面，融合后两边都强的文档分数最高。我们对照过纯 dense vs 混合，**在 acronym + 长描述类 query 上 Recall@5 能从 ~62% 提到 ~78%**（基于 phase2 baseline 评测）。

## 2. 数据结构题：BM25 倒排索引怎么搭的？

**Q：你们的 Sparse 索引为什么自己写 BM25，不用 ES 或 Milvus 自带稀疏？数据结构怎么设计？**

**我的回答：**

我们做的是**「候选级 BM25」**，不是全库倒排。流程分两步：

第一步，`MilvusLikeCandidateProvider` 用 `content like "%term%"` 给每个 query term 拉一批候选（`per_term_limit = candidate_topk * 4`，最少 20 条），多 term 结果按 docID 去重合并。

第二步，`BuildSparseInvertedIndex` **只对这批召回的候选**在内存里建倒排索引：`postings map[term][]sparsePosting{docID, tf}`、`docLengths map[docID]int`、`avgDocLength`，然后 `Search()` 跑 BM25 公式 `IDF * tf*(K1+1) / (tf + K1*(1-B+B*docLen/avgDocLen))`，K1=1.2、B=0.75 是经典默认。

为什么这么设计？

- **不维护全库倒排**：项目本来就跑 Milvus，再搭一个 ES 集群运维成本太高。我们的语料体量不到百万级，候选级 BM25 完全够用。
- **`like` 拉粗排不做精排**：`like` 走全表扫描其实贵，但限制了 per_term_limit 之后单 term 几十毫秒能搞定，且能享受 Milvus 的 expr filter（KB scope、tenant 隔离）。
- **BM25 在内存里跑**：候选只有 100-200 条量级，建索引 + 打分整体亚毫秒级，**比起 ES 的网络往返反而更快**。

最关键的取舍是「**接受一定的召回上限，换运维零成本**」——`like` 召不出来的 term 就是打不到。这点我们用 `term_dict` 词典扩展 + query rewrite 来补。

> 相关代码：[sparse_search.go#L258-339](../../backend/internal/milvus/retrieval/sparse_search.go#L258-339)、[sparse_inverted_index.go#L136-225](../../backend/internal/milvus/retrieval/sparse_inverted_index.go#L136-225)

### 🔍 深挖追问兜底

**Q：`content like "%term%"` 不是会全表扫吗？性能怎么保证？**
> 单 term 上限拉到 `candidate_topk*4`（默认 40 条）就停，且和 `kb_scope`、`tenant` 的 expr 拼成 `(base_expr) && (content like ...)`，Milvus 会先用元数据过滤再做内容匹配。我们埋了 `sparse_ms` 单路指标，**线上 P95 在 30-50ms 区间**，没成为瓶颈。

**Q：BM25 里 IDF 的 N 是什么？是全库还是候选池？**
> 是**候选池**，`idx.totalDocs = len(documents)`，也就是这一批拉回来的文档数。这和教科书的全库 IDF 不一样——好处是不用维护 corpus stats，坏处是 IDF 区分度比真全库 BM25 弱一些。**对我们的场景影响不大**，因为最终还要走融合 + rerank，BM25 只负责把候选粗排。

**Q：Term 提取怎么做？只是 split 吗？**
> `extractSparseTermsDetailed` 用 `unicode.IsLetter/IsNumber` 切词，过滤停用词（the/a/of 等）和 <2 字符词，最多 6 个 term（rewrite 命中时上调到 10）。识别 acronym 用「全大写或全小写且长度 2-8」简单启发式。**没做中文分词**，中文字面靠 query 里直接出现的 token 命中——这是已知短板，未来上 jieba 或 ik 能再涨一点。

## 3. 关键参数题：minmax 和 RRF 怎么选？为什么权重 0.7/0.3？

**Q：你们融合默认用 minmax_v1，权重 dense=0.7 sparse=0.3，这俩数字怎么来的？为什么不全用 RRF？**

**我的回答：**

先说 0.7/0.3。我们做过 grid search 评测，dense 权重在 0.6-0.8 区间 nDCG 几乎持平，超过 0.8 sparse 影响太弱（acronym query 救不回来），低于 0.6 dense 优势被稀释。**0.7 是甜点位**，再者它和 sparse 0.3 加起来正好 1.0，归一化语义清晰。

minmax vs RRF 我们都实现了，用 `fusion_strategy` 配置切：

- **`minmax_v1` 是默认**：把每路的 raw score 按 `(score - min) / (max - min)` 归一到 [0,1]，再乘权重。优点是分数有物理含义、可解释；缺点是当一路结果质量差（max 也低）时容易把噪声放大。
- **`rrf_v1` 备选**：直接用排名 `weight / (RRFK + rank)`（RRFK=60），不看具体分数。优点是抗噪、对异常分数鲁棒；缺点是丢失了 dense/sparse 的「绝对置信度」信息，rerank 阶段就拿不到这个信号。

**我们最终选 minmax 做默认，因为 rerank 模型需要喂融合分作为先验**。RRF 的纯排名信号会让 rerank 退化成「重新洗牌」。但只要 dense 路质量明显异常（比如 embedding 服务降级），我们可以用 runtime override 切到 RRF 兜底。

> 相关代码：[fusion.go#L60-143](../../backend/internal/milvus/retrieval/fusion.go#L60-143)、[config.example.yaml#L103-110](../../backend/config.example.yaml#L103-110)

### 🔍 深挖追问兜底

**Q：minmax 归一化遇到 max==min 怎么办？**
> 看 `normalizeRouteScore`：max<=min 时，score>0 一律返回 1，否则返回 0。**这是故意的「无差别处理」**——所有候选并列后让另一路的差异说话，避免归一除零。

**Q：RRFK=60 这个值哪来的？**
> 是 IR 领域 Cormack 2009 那篇论文里的经典推荐值，工业界包括 Elasticsearch 的 RRF 实现也用 60。我们实测 30/60/120 差异在 1% 以内，没动力调。

**Q：那 dense 权重做成动态的能不能更准？**
> 能，但代价大。理论上 query 越短越像关键词，越该提高 sparse 权重；越长越像自然语言，越该提高 dense。我们目前没做，**因为权重动态会让评测和回归成本翻倍**——每次改阈值都要重跑 baseline。算性价比，**先把配置做成 runtime override 让运营能切，比上自适应更稳**。

## 4. 算法题：双层动态 TopK 是怎么决策的？

**Q：你们说有规则版 + 策略版双层 TopK，分别看什么信号？为什么要两层？**

**我的回答：**

两层的核心区别是**「rerank 之前还是之后」**。

**规则版 `DecideDynamicTopK`** 在 rerank 前跑，**纯靠 query 表面特征**：

- broad query（含「区别/对比/原理/best practice」等关键词）→ maxTopK=8
- 长 query（>=48 rune 或 >=8 term）→ maxTopK=8
- 中等（>=24 rune 或 >=5 term）→ 中间偏上
- 短精确（<=12 rune 且 <=3 term）→ minTopK=3
- 默认 → 区间中位

**策略版 `DecideStrategicTopK`** 在 rerank 后跑，看**真实结果分布**做二次调整：

- **score distribution**：rerank 后分数「悬崖型」（gap>=0.15）→ 减 1-2 条，砍掉断崖下面的弱证据；「平坦型」（spread<=0.08）→ 加 2 条，多给一点上下文
- **parent diversity**：来源 parent 多样且无主导 → +1；75% 都来自同一 parent → -1（避免上下文重复）
- **evidence density**：strong hits 占比 <34% 不允许扩；>=70% 且 gap<0.08 → +1
- **token budget cap**：策略版还要二次过 token 预算（用 `strategic_topk_budget_ratio=0.6` 切一份预算），超了直接砍

**为什么两层？**因为 rerank 之前我们只能猜「这个 query 要多少证据」，rerank 之后才知道「**实际拿到的证据有多少是强证据**」。规则版给基线，策略版按事实修正，**两层 reason 字符串都拼进 metrics 日志**，线上能直接看到决策路径。

> 相关代码：[topk_policy.go#L48-201](../../backend/internal/milvus/retrieval/topk_policy.go#L48-201)、版本号 `phase2-rule-v1` / `phase3-strategic-v1`

### 🔍 深挖追问兜底

**Q：策略版要是判断错了把好结果减没了怎么办？**
> 有 fallback：`DecideStrategicTopK` 用 defer recover 兜底，任何 panic 直接退回规则版的 `base` 决策，policy_version 标 `phase2-rule-v1`、reason 加 `strategic_fallback:xxx`。**永远不会比规则版更糟**。

**Q：「悬崖型」「平坦型」是怎么判定的？**
> `classifyScoreDistribution`：归一化后 spread<=0.08 → flat；rerank gap>=0.15 或 (spread>0.12 且 top1-top2 归一化差>=0.22) → cliff；相邻平均差<=0.08 也归 flat；其余 balanced。这套阈值是我们对着 baseline 数据集人工调出来的，不是拍的。

**Q：rerank gap 是什么？**
> 就是 rerank 后 top1 和 top2 的分数差。**这是一个非常关键的"置信度"信号**——gap 大说明模型很笃定 top1 是对的，下面的可以砍；gap 小说明几条都差不多，应该多保留几条让用户/LLM 自己看。

## 5. 选型对比题：为什么不用 Elasticsearch？

**Q：BM25 业界标配就是 ES，你们为什么死磕在内存里手搓？是不是过度工程？**

**我的回答：**

我直接说结论：**不是不能用 ES，是性价比不划算**。

**第一，运维成本**。ES 集群至少 3 节点起，加上 logstash/kibana 全套，服务器、监控、告警、版本升级都要专人。我们整个 RAG 链路就 1-2 个后端在维护，多一个 stateful 中间件就是多一份事故面。**Milvus 已经够重了**。

**第二，数据双写一致性**。文档入库要同时写 Milvus 和 ES，任何一边写失败都要补偿，回滚链路复杂。我们目前是 Milvus 单写，sparse 候选通过 `like` 实时拉，**写路径少一个一致性问题**。

**第三，召回量级**。我们的 KB 是租户隔离的，单租户内文档量级 10K-100K 文本块，候选级 BM25 在 100-200 条候选上跑就够。ES 的优势在百万千万级全库倒排，**杀鸡用牛刀**。

**第四，延迟**。ES 查询要走 HTTP/gRPC，单次 RTT 几十毫秒；我们内存 BM25 是亚毫秒级。融合、rerank、parent-child fill 后面还有好几层，**每一层都得抠 ms**。

代价是什么？**召回上限确实低于 ES**。如果未来语料涨到千万级，或者要支持复杂的中文分词、同义词扩展、edit distance 模糊匹配，会重新评估接 ES 或 Tantivy。**当前阶段「能用 + 零运维」比「最优但重」更重要**。

> 相关代码：[sparse_search.go#L80-153](../../backend/internal/milvus/retrieval/sparse_search.go#L80-153)

### 🔍 深挖追问兜底

**Q：那如果 sparse 召回上限低，难道不会损害 recall 吗？**
> 会，但有 query rewrite 和 term 词典扩展兜底。Rewrite 在 sparse 路上会注入同义词和缩写展开（比如 `JVM` 自动加 `Java Virtual Machine`），从 query 端补。我们埋了 `sparse_terms`、`term_sources` 两个 metric 字段，**线上看 rewrite 命中能多带 30%+ 的有效 term**。

**Q：Tantivy 这种嵌入式倒排引擎为啥不用？**
> 评估过。Tantivy 是 Rust 写的，Go 项目要走 cgo 或 IPC，工程复杂度上来了；而且它仍然要落盘维护索引，写入侧的双写问题没解。**候选级 BM25 是「无状态」的**，每次请求重建，零持久化负担——这个简单性是它最大的护城河。

**Q：你这个 N 不全（候选级 IDF）会不会导致 BM25 失真？**
> 会有偏差。具体表现是高频通用词（"how"、"what"）的 IDF 在小池里偏高。我们用停用词表先过滤了一批，剩下的 term 在候选池里出现频率本来就不会差太多，**实测 nDCG 影响 <2%**。后续如果要更准，可以离线算 corpus IDF 表注入，工程量也不大。

## 6. 故障实战题：线上 Sparse 路全挂了怎么办？

**Q：假设有一天 Sparse 路全部 timeout 或者拿到空结果，你怎么排？怎么止血？**

**我的回答：**

先讲我们的**降级是默认就有的**，不需要现场操作。`hybrid_search.go` 里两路并发跑，最后只有 `denseErr != nil && sparseErr != nil` 同时失败才整体失败，**任何单边挂了另一边的结果直接走融合**——融合层 `fuseMinMaxCandidates` 输入空 slice 不会爆炸，结果就退化成纯 dense。`debugTrace.Degradation` 会记录 `reason="route_error"`、`fallback_strategy="continue_with_available_routes"`。

排查路径：

1. **先看 Prometheus**：`rag_retrieve_route_requests_total{route="sparse",status="error"}` 错误率，对比 dense 路是否同步异常。如果只是 sparse 异常，定位到是 Milvus 的 `Query` 调用还是 BM25 内存计算。
2. **拉日志**：`[RAG:L1]/[RAG:L2]` 行里有 `sparse_ms`、`sparse_error`、`empty_reason`，请求级别能直接看哪个 term 拉不出候选。
3. **本地复现**：拿一个失败的 query 走 retrieval-debug 接口，看 `debug_trace.route_hits[sparse]` 的 fallback_reason——`provider_error`（Milvus query 失败）还是 `ranker_error`（BM25 panic）还是 term 提取后为空。

止血手段：

- **临时切 RRF**：`fusion_strategy` 切到 `rrf_v1` 后 sparse 路即使分数全 0，至少排名还有意义；不过 sparse 直接挂 0 命中时 RRF/minmax 没区别。
- **Runtime override** 把 `hybrid_dense_weight` 拉到 1.0，sparse_weight 设 0，等同于关掉 sparse 路融合贡献，**避免 sparse 残留的少量低质命中污染结果**。
- 极端情况关掉 `enable_hybrid_retrieval` flag，整个降级为纯 dense + rerank。

**重点是这套降级路径都是事先写好的代码路径，不是临场写补丁**——线上敢动这些开关的前提是它们已经在 phase2 验收里跑过几百次。

> 相关代码：[hybrid_search.go#L360-375](../../backend/internal/milvus/retrieval/hybrid_search.go#L360-375)（双路同时挂的判断）、[hybrid_search.go#L912-920](../../backend/internal/milvus/retrieval/hybrid_search.go#L912-920)（route metric 埋点）

### 🔍 深挖追问兜底

**Q：两路并发的 ctx 超时是怎么传的？**
> 主 ctx 透到两个 goroutine，sparse 路自己再用 `SparseRetrieverConfig.TimeoutMS` 包一层 `context.WithTimeout`。**两层超时取严的那个生效**。Dense 路超时是 retriever 内部的 Milvus 调用控制，没加额外 wrap。

**Q：如果 dense 也只剩 5 条，sparse 全挂，token 预算和 minTopK 怎么协调？**
> `ApplyTokenBudgetGuard` 里有兜底：`if cfg.MinAnswerChunks > len(docs) { cfg.MinAnswerChunks = len(docs) }`，**永远不会要求超过实际数量的最小值**。最少返回 1 条（`if len(budgeted)==0 budgeted = truncated[:1]`）。

**Q：你说降级路径是预写的，怎么验证它真的有效？**
> 我们在 `search_l4_test.go`、`fusion_test.go`、`topk_policy_test.go` 里有针对性的 case：sparse 返回 nil、empty、err 三种情况的融合行为；TokenBudget=0 时不截断；策略版 panic 退回规则版。**单测覆盖了所有的「单边挂掉」组合**，每次 PR 跑一遍。

## 7. 边界场景题：Token 预算守卫的细节怎么处理的？

**Q：Token 预算守卫是怎么算 token 的？预算扣完了怎么办？保底逻辑是什么？**

**我的回答：**

token 估算用的是**最简朴的方法**：`tokens = ceil(rune_count / 4)`，最少 1 个 token。**不调 tokenizer**，因为我们的预算是个软上限，不需要精确到个位数；走 OpenAI tokenizer 反而引入网络/库依赖。

守卫流程在 `ApplyTokenBudgetGuard`：

1. 先按 `decision.FinalTopK` 截断到候选池前 N 条
2. 如果 `TokenBudget=0`（关闭预算），直接返回，只看 finalTopK
3. 否则逐条遍历，累加 token 数，一旦 `total + doc_tokens > budget` 立即停，并标 `truncate_reason="token_budget"`
4. **`min_answer_chunks=2` 的强保护**：前 2 条无视预算硬塞进去，避免高 token 文档把答案饿死

返回结果里带 `EstimatedContextTokens`（实际用了多少）和 `TokenBudgetRemaining`（还剩多少），**这两个数字会进 metrics 也会进日志**，运营调预算的时候直接看。

策略版还多一层：`strategic_topk_budget_ratio=0.6` 表示**策略版只能用总预算的 60%**——剩下的 40% 留给后面的 LLM prompt 拼装、citation 标注、system message。这个比例是我们和 prompt 团队对齐之后定的。

最隐蔽的一个细节：**如果连 `min_answer_chunks` 都装不下预算，会强制塞 1 条**（`if len(budgeted)==0 budgeted = truncated[:1]`），保底返回；而不是宁缺毋滥，因为返回空在我们的 evidence_gate 那层有专门的 refusal 处理，分得清"没找到"和"被截断了"。

> 相关代码：[topk_policy.go#L203-267](../../backend/internal/milvus/retrieval/topk_policy.go#L203-267)、[topk_policy.go#L497-514](../../backend/internal/milvus/retrieval/topk_policy.go#L497-514)（token 估算）

### 🔍 深挖追问兜底

**Q：rune/4 这个估算误差大吗？中英文混合呢？**
> 中文 rune 1 个 ≈ 1.5-2 个 GPT token，英文 1 个 rune ≈ 0.25 token。我们的 4 是个折中值——**纯中文场景会高估 token，纯英文会低估**。但我们的预算本来设的就保守（默认 0=不限制，开启时一般留 30% buffer），**误差被 buffer 吸收了**。要追求精确得接 tiktoken-go，性价比不高。

**Q：min_answer_chunks=2 这个 2 怎么定的？**
> 来自评测：单条上下文 LLM 能答的 query 占比不到 30%，2 条覆盖到 ~75%，3 条提升到 ~85% 但 token 翻倍。**2 是性价比平衡点**。它和 `min_topk=3` 不矛盾——前者保答案完整、后者保候选多样性。

**Q：策略版 budget_ratio=0.6 留 40% 给 prompt 是怎么算的？**
> 我们 prompt 模板（system + few-shot + citation 标注）平均吃 ~800 token。如果预算是 4000，留 1600 给上下文之外的部分确实有点紧。这个比例是 phase3 阶段定的，**当前实际用的预算 token_budget=0（关闭）**，开启场景预计在 phase4 的高负载租户里上线。
