## 三、需要先理解的术语

### 1. 向量检索

向量检索，英文常叫 `dense retrieval`，意思是先把查询和文档都变成向量，再在向量空间里找“语义相近”的内容。

可以把它理解成：

1. 关键词检索是在看“字面上像不像”。
2. 向量检索是在看“意思上像不像”。

举个例子：

1. 用户问“JVM 调优”
2. 文档里写的是“Java virtual machine performance tuning”

即使字面上不完全一样，向量检索也可能把它们找出来。

在我们这套代码里，向量检索对应的是 `dense` 路由。

### 2. 关键词检索

关键词检索，英文常叫 `sparse retrieval`，意思是按词项匹配来找文档。

它更擅长处理下面这些情况：

1. 专有名词非常明确
2. 缩写很多
3. 必须精确命中某个字面词

在我们这套代码里，关键词检索对应的是 `sparse` 路由。

### 3. BM25

BM25 是一种经典的关键词排序算法。

不要把它理解成“数据库自己带的搜索引擎”。更准确地说，它是一套打分公式，用来给候选文档排序。

它会考虑：

1. 查询词在文档里出现了几次
2. 这个词是不是太常见
3. 文档是不是太长

在我们这里，BM25 不是数据库原生执行的，而是在候选文档取出来以后，在应用进程里自己算的。

### 4. Fusion

`fusion` 可以翻成“融合”。

它的作用是：把 `dense` 路由召回的结果和 `sparse` 路由召回的结果放到一起，按一套规则重新打统一分数。

### 5. Dedupe

`dedupe` 就是“去重”。

因为同一个文档块可能同时被 `dense` 和 `sparse` 两条路命中，所以需要在融合后把重复项合并。

### 6. Rerank

`rerank` 就是“重排序”。

可以把它理解成：

1. 前面几步先尽量多找候选
2. 最后再用更精细的规则，把候选重新排一遍

在我们当前实现里，默认使用的是一个基于 Jaccard 相似度的轻量重排器。

### 7. Contribution

这里要特别小心。

在当前代码里，日志里的 `dense_contribution` 和 `sparse_contribution`，并不表示“这一条路有没有参与过”，而更接近“最终保留下来的结果，主路由是谁”。

这件事正是这次误解的根源之一。

## 四、先说结论

先把最重要的结论讲在前面，开会时也建议先这样讲。

### 结论 1：当前系统不是“只走 LIKE，不走向量”

这个说法不准确。

按照当前默认配置和代码路径，线上请求会走 `phase2` 混合检索，也就是 `dense + sparse` 两条路一起跑。

### 结论 2：当前关键词检索这条路，确实是 `LIKE` 候选召回，再在应用内做 BM25

这个说法是成立的。

但要注意两点：

1. 它查的不是 MySQL，而是 Milvus collection。
2. 它不是整条检索链路的全部，而只是 `sparse` 路由的实现方式。

### 结论 3：从真实日志看，向量检索是当前成功请求的主力

截至 `2026-06-04 16:34:12`，本地这套环境里的 `kb_retrieve_log` 一共有 `7` 条记录，时间范围是：

1. 最早：`2026-06-02 03:52:54.702`
2. 最晚：`2026-06-04 16:34:12.581`

聚合结果如下：

1. 总请求数：`7`
2. 成功请求数：`6`
3. 有 `dense_hits > 0` 的请求数：`6`
4. 有 `sparse_hits > 0` 的请求数：`6`
5. 有 `dense_contribution > 0` 的请求数：`6`
6. 有 `sparse_contribution > 0` 的请求数：`0`

10. `total_sparse_contribution = 0`

这说明三件事：

1. `dense` 确实执行了，而且每次成功请求都有命中。
2. `sparse` 也确实执行了，而且每次成功请求也都有命中。
3. 但当前样本里，最终保留下来的结果，主导路由几乎全是 `dense`。

### 结论 4：当前真正的问题不是“有没有跑向量”，而是“关键词路由虽然跑了，但产出价值很弱”

## 六、整体流程

如果要在会议上用一句话讲清楚当前架构，可以这样说：

> 现在的检索是一个以向量检索为主、关键词检索为辅、两路并发召回、再融合去重重排的混合检索管线。

把请求链路按顺序展开，是下面这样：

1. 请求进入 `kb.Retrieve` API
2. 根据配置和 release 策略，决定走 `phase1` 纯 dense，还是 `phase2` hybrid
3. 当前默认配置会走 `phase2`
4. `phase2` 里会并发跑两条路：
   1. `dense`：向量化查询，再去 Milvus 做 ANN 搜索
   2. `sparse`：提取关键词，按 `content like "%term%"` 去 Milvus 拉候选，再在应用内做 BM25
5. 两路结果拿回来以后做融合
6. 融合后做去重
7. 去重后做 rerank
8. 再做 parent-child 补全文、token budget 截断、evidence gate、citation check
9. 最终把结果写回响应，并把整条链路的可观测数据落到 `kb_retrieve_log`

这套设计不是简单的“检索一下返回”，而是一个完整的检索流水线。

## 八、第一步：API 是怎么决定走混合检索的

### 目标

先把“请求入口到底决定走哪条路”讲清楚。

### 文件

1. [backend/api/handler/kb/handler.go](/abs/path/d:/Bear/rag-retrievalOps/backend/api/handler/kb/handler.go)
2. [backend/internal/rag/release/controller.go](/abs/path/d:/Bear/rag-retrievalOps/backend/internal/rag/release/controller.go)
3. [backend/config.yaml](/abs/path/d:/Bear/rag-retrievalOps/backend/config.yaml)

### 这一步在做什么

在 `handler.go` 里，代码会先判断：

1. Hybrid 功能开没开
2. Hybrid Retriever 有没有初始化成功
3. 当前 release 策略是否允许走 Phase2

关键判断点在这些位置：

1. `phase2Available := config.Global.RAG.FeatureFlags.EnableHybridRetrieval && manager.GetHybridRetriever() != nil`
2. `releaseDecision := release.Decide(...)`
3. `useHybrid := releaseDecision.UsePhase2 && manager.GetHybridRetriever() != nil`

也就是说，是否走混合检索，不是前端传个参数就能决定，而是服务端统一控制。

### 为什么要这样设计

这样做的好处是，检索策略可以统一灰度、统一回滚、统一观测。

如果用最简单的方案，让每个调用方自己传 `use_hybrid=true/false`，会有两个问题：

1. 策略分裂，线上到底谁走了哪套逻辑很难统一追踪
2. 出问题时没法快速整批回滚

### 当前默认行为

在 [backend/config.yaml](/abs/path/d:/Bear/rag-retrievalOps/backend/config.yaml) 里，我们当前配置是：

```yaml
rag:
  feature_flags:
    enable_hybrid_retrieval: true
  release:
    enabled: false
    stage: full
  phase2:
    hybrid_dense_weight: 0.7
    hybrid_sparse_weight: 0.3
```

而在 [backend/internal/rag/release/controller.go](/abs/path/d:/Bear/rag-retrievalOps/backend/internal/rag/release/controller.go) 里，`release.enabled = false` 时会直接返回 Phase2：

```go
if !ragCfg.Release.Enabled {
	return Decision{
		Strategy:  StrategyPhase2,
		Stage:     StageFull,
		Reason:    "legacy_flags",
		UsePhase2: true,
	}
}
```

这意味着当前默认流量是会走 hybrid 的。

### 这一步建立了什么

这一步建立的是“总开关和流量分配规则”。

简单理解就是：检索要不要走混合，不是猜的，也不是文档里写写而已，而是服务端有明确代码控制。

## 九、第二步：请求真正落到哪套检索实现

### 目标

看清楚当 `useHybrid = true` 时，后面到底调用了谁。

### 文件

1. [backend/api/handler/kb/knowledge_base_binding.go](/abs/path/d:/Bear/rag-retrievalOps/backend/api/handler/kb/knowledge_base_binding.go)

### 完整代码

文件：`backend/api/handler/kb/knowledge_base_binding.go`

```go
func searchKnowledgeBaseTarget(
	ctx context.Context,
	manager *milvus.MilvusManager,
	retrieverService *retrieval.RetrieverService,
	useHybrid bool,
	query string,
	topK int,
	target kbRetrieveTarget,
	requestID string,
	queryType string,
	experimentDecision experiment.Decision,
) (*retrieval.SearchResult, error) {
	expr := buildKBFilterExpr(target.KBIDs)
	activeKBID := uint64(0)
	if len(target.KBIDs) == 1 {
		activeKBID = target.KBIDs[0]
	}

	if useHybrid {
		searchOpts := &retrieval.RetrieveOptions{
			TopK:             topK,
			Collection:       target.Collection,
			Expr:             expr,
			KBScope:          "global",
			ActiveGlobalKBID: activeKBID,
			RequestID:        requestID,
			OriginalQuery:    query,
			QueryType:        queryType,
			ExperimentID:     experimentDecision.ExperimentID,
			StrategyVersion:  experimentDecision.CandidateVersion,
			ReleaseID:        experimentDecision.ExperimentID,
		}
		if experimentDecision.Matched {
			searchOpts.ForceRewriteOff = experimentDecision.Override.ForceRewriteOff
			if experimentDecision.Override.CandidateTopK > 0 {
				searchOpts.CandidateTopK = experimentDecision.Override.CandidateTopK
			}
		}
		return manager.GetHybridRetriever().SearchWithMetrics(ctx, query, searchOpts)
	}

	searchOpts := &retrieval.RetrieveOptions{
		TopK:             topK,
		Collection:       target.Collection,
		Expr:             expr,
		KBScope:          "global",
		ActiveGlobalKBID: activeKBID,
	}
	return retrieverService.RetrieveWithOptionsAndMetrics(ctx, query, searchOpts)
}
```

### 这段代码在做什么

这段代码非常关键，因为它把“策略判断”真正变成了“实现调用”。

它的逻辑很直接：

1. 如果 `useHybrid = true`
   1. 就调用 `manager.GetHybridRetriever().SearchWithMetrics(...)`
2. 如果 `useHybrid = false`
   1. 就调用 `retrieverService.RetrieveWithOptionsAndMetrics(...)`

所以“是不是走混合检索”不是抽象概念，而是已经落到了不同函数分支上。

### 为什么要这样写

这样写的好处是：

1. 入口统一
2. 策略切换清晰
3. 纯 dense 和 hybrid 可以共用上层 API

如果这里没有这层封装，而是上层到处自己拼 different search path，会导致后续维护成本非常高。

### 这一段跟后面怎么衔接

这一步结束以后，如果当前是默认配置，那么请求就会进入 `HybridRetriever.SearchWithMetrics(...)`，也就是我们下面要讲的核心混合检索管线。

## 十、第三步：Hybrid 检索是如何并发跑两条路的

### 目标

看清楚系统为什么能同时有 `dense_hits` 和 `sparse_hits`。

### 文件

1. [backend/internal/milvus/retrieval/hybrid_search.go](/abs/path/d:/Bear/rag-retrievalOps/backend/internal/milvus/retrieval/hybrid_search.go)

### 这一步在做什么

`HybridRetriever.SearchWithRequestAndMetrics(...)` 是整个 Phase2 检索的核心函数。

它会做这些事：

1. 处理 query rewrite
2. 决定 candidate topK 和 final topK
3. 并发启动 dense 路由
4. 并发启动 sparse 路由
5. 收集两路结果
6. 做融合、去重、重排、过滤
7. 产出结果和 metrics

里面最关键的一段是并发执行：

1. 一个 goroutine 跑 `h.searchDenseWithMetrics(...)`
2. 一个 goroutine 跑 `h.sparseRetriever.Search(...)`

这就是为什么日志里能同时出现 `dense_hits` 和 `sparse_hits`。

### 为什么这里要并发

因为 dense 和 sparse 本质上是两条独立召回路。

如果串行执行，会有两个明显问题：

1. 总延迟更高
2. 某一路慢时会拖累整条链路

并发执行的好处是：

1. 可以把两路召回时间重叠起来
2. 其中一路失败时，还可以考虑用另一路兜底

### 这里已经埋下了什么伏笔

这一步已经说明：

1. 混合检索不是“先 like，再向量”
2. 也不是“先向量，再 like”
3. 而是两条路并行跑，各自产生候选

这对后面理解“为什么 sparse 有 hits 但没有 contribution”非常重要，因为问题不是出在“有没有执行”，而是出在后面的融合和保留逻辑。

## 十一、第四步：Dense 路由，也就是向量检索，是怎么做的

### 目标

用代码把“向量检索确实在跑”这件事讲死。

### 文件

1. [backend/internal/milvus/retrieval/search.go](/abs/path/d:/Bear/rag-retrievalOps/backend/internal/milvus/retrieval/search.go)

### 这段逻辑在做什么

`dense` 路由的核心过程是：

1. 先把查询文本做 embedding
2. 得到一个浮点向量
3. 再把这个向量传给 Milvus 的 `client.Search(...)`
4. 使用向量字段 `vector` 做近似最近邻搜索

最关键的两个动作是：

1. `embedder.EmbedStrings(ctx, []string{query})`
2. `client.Search(... []entity.Vector{entity.FloatVector(queryVector)} ...)`

这已经足够证明当前系统确实在跑向量检索。

### 为什么这一点很关键

因为会议上很可能有人会把“sparse 路由里出现了 LIKE”误解成“整条检索链路根本没用向量库”。

而 dense 路由这里的代码说明：

1. 查询被转成向量了
2. 向量被送给 Milvus 搜索了
3. 搜索字段就是 `vector`

所以“没用向量检索”这个判断，不符合当前代码事实。

### 当前 dense 路由的优点

1. 有语义召回能力
2. 对同义词、改写词更友好
3. 对中英文混杂、缩写扩展更有弹性
4. 已经和 query rewrite、rerank、debug trace 接通了

### 当前 dense 路由的局限

1. 会依赖 embedding 模型质量
2. 对特别短、特别精确的字面词不一定最强
3. 如果 query rewrite 做得不好，dense 也可能被带偏

```go
func (s *SparseRetriever) Search(ctx context.Context, req *HybridSearchRequest) ([]*schema.Document, error) {
	if req == nil {
		return nil, fmt.Errorf("hybrid search request is nil")
	}
	query := strings.TrimSpace(req.SparseQuery)
	if query == "" {
		query = strings.TrimSpace(req.FinalQuery)
	}
	if query == "" {
		query = strings.TrimSpace(req.Query)
	}
	if query == "" {
		return nil, fmt.Errorf("query is empty")
	}

	topK := req.CandidateTopK
	if topK <= 0 {
		topK = s.config.DefaultTopK
	}
	termLimit := s.config.MaxTerms
	if strings.TrimSpace(req.SparseQuery) != "" && !strings.EqualFold(strings.TrimSpace(req.SparseQuery), strings.TrimSpace(req.OriginalQuery)) && termLimit < 10 {
		termLimit = 10
	}
	terms := extractSparseTerms(query, termLimit)
	if len(terms) == 0 {
		return []*schema.Document{}, nil
	}

	baseExpr := strings.TrimSpace(req.Expr)
	if baseExpr == "" && (strings.TrimSpace(req.KBScope) != "" || req.KBID > 0) {
		baseExpr = BuildFilterExpr(&RetrieveOptions{
			KBScope:          req.KBScope,
			ActiveGlobalKBID: req.KBID,
		})
	}

	collection := strings.TrimSpace(req.Collection)
	if collection == "" {
		collection = s.collection
	}

	perTermLimit := topK * s.config.PerTermFactor
	if perTermLimit < s.config.MinPerTermK {
		perTermLimit = s.config.MinPerTermK
	}

	merged := make(map[string]*schema.Document, perTermLimit)
	for _, term := range terms {
		likeExpr := fmt.Sprintf("content like \"%%%s%%\"", escapeLikeValue(term))
		expr := likeExpr
		if baseExpr != "" {
			expr = fmt.Sprintf("(%s) && (%s)", baseExpr, likeExpr)
		}

		resultSet, err := s.client.Query(
			ctx,
			collection,
			nil,
			expr,
			[]string{"id", "content", "metadata"},
			milvusClient.WithLimit(int64(perTermLimit)),
		)
		if err != nil {
			return nil, fmt.Errorf("sparse query failed, term=%q expr=%q: %w", term, expr, err)
		}

		for _, doc := range parseQueryResultSet(resultSet) {
			docID := strings.TrimSpace(doc.ID)
			if docID == "" {
				docID = buildPseudoDocID(doc)
			}
			if docID == "" {
				continue
			}

			if _, exists := merged[docID]; exists {
				continue
			}
			if doc.MetaData == nil {
				doc.MetaData = make(map[string]interface{})
			}
			doc.MetaData["route"] = "sparse"
			doc.MetaData["retriever_version"] = hybridRetrieverVersion
			if collection != "" {
				doc.MetaData["collection"] = collection
			}
			source := ensureSourceMetadata(doc)
			source["route"] = routeSparse
			source["retriever_version"] = hybridRetrieverVersion
			if collection != "" {
				source["collection"] = collection
			}
			doc.MetaData["source"] = source
			annotateParentChildSource(doc)
			merged[docID] = doc
		}
	}

	if len(merged) == 0 {
		return []*schema.Document{}, nil
	}

	candidates := make([]*schema.Document, 0, len(merged))
	for _, doc := range merged {
		candidates = append(candidates, doc)
	}
	index := BuildSparseInvertedIndex(candidates, nil)
	hits := index.Search(terms, topK)
	if len(hits) == 0 {
		return []*schema.Document{}, nil
	}

	results := make([]*schema.Document, 0, len(hits))
	for _, hit := range hits {
		doc := hit.Document
		if doc == nil {
			continue
		}
		if doc.MetaData == nil {
			doc.MetaData = make(map[string]interface{})
		}
		doc.MetaData["route"] = routeSparse
		doc.MetaData["sparse_score"] = hit.Score
		doc.MetaData["score"] = hit.Score
		doc.MetaData["retriever_version"] = hybridRetrieverVersion
		if collection != "" {
			doc.MetaData["collection"] = collection
		}
		source := ensureSourceMetadata(doc)
		source["route"] = routeSparse
		source["retriever_version"] = hybridRetrieverVersion
		if collection != "" {
			source["collection"] = collection
		}
		doc.MetaData["source"] = source
		annotateParentChildSource(doc)
		attachRewriteMetadata(doc, req, routeSparse)
		results = append(results, doc)
	}

	return results, nil
}
```

### 这段代码在做什么

这段代码完整体现了当前 sparse 路由的实现方式。

它大致分四步：

1. 从查询里提取关键词 `terms`
2. 对每个 term 生成 `content like "%term%"`
3. 调 Milvus `Query(...)` 把候选文档拉回来
4. 在应用进程内用 `BuildSparseInvertedIndex(...).Search(...)` 做 BM25 排序

### 先讲最重要的事实

如果会议里有人说：

> 现在的 sparse 检索就是 `LIKE` 拼接再 BM25

这个说法基本是对的。

但是要补全成更准确的版本：

> 现在的 sparse 路由会对 Milvus collection 做 `content like "%term%"` 候选召回，然后在应用内用显式倒排索引做 BM25 排序。

### 为什么这个设计不是“完全错误”

它不是一个完全乱来的实现，它有一些现实考虑：

1. 实现快
2. 不需要单独再接一套 ES
3. 能在现有 Milvus 存储结构上先把 hybrid pipeline 跑起来
4. 对小规模数据集和早期验证阶段是能工作的

也就是说，这个设计更像一个“可运行的 Phase2 sparse baseline”，而不是一个成熟的生产级关键词检索方案。

### 它的好处

1. 开发成本低
2. 不需要额外部署独立倒排搜索引擎
3. 容易和现有 debug trace、metadata、KB 过滤条件对齐
4. 能和 dense 路由共用下游融合、去重、重排、日志体系

### 它的弊端

这是本次分享最值得展开讲的部分。

#### 弊端 1：关键词召回依赖 `LIKE`

`LIKE` 的本质是字面匹配，不是专业搜索引擎级别的倒排检索。

这会带来几个问题：

1. 对词形变化不友好
2. 对中文分词不友好
3. 对长文本大库扩展性差
4. 候选召回过程可能越来越像扫描

#### 弊端 2：BM25 不是在索引层做的，而是在应用层对候选集做的

这意味着：

1. BM25 的排序质量上限受候选集质量限制
2. 如果 `LIKE` 一开始没把真正该来的文档拉出来，后面的 BM25 再好也没用

这是一个很重要的工程现实：

> BM25 只能排“已经被拉回来的候选”，它不能凭空把漏掉的好文档救回来。

#### 弊端 3：性能成本会随数据量增大而上升

当前实现是：

1. 每个 term 都要做一次 `Query`
2. 每次 `Query` 再拉一批文档回来
3. 再在应用内建临时倒排索引
4. 再做 BM25 排序

这条路的成本会随着：

1. term 数量
2. 每个 term 的命中文档数
3. collection 大小

一起放大。

#### 弊端 4：当前 term 提取比较轻量

`extractSparseTerms(...)` 用的是比较简单的规则：

1. 小写化
2. 按非字母数字切词
3. 去掉停用词
4. 限制最大 term 数

这对于专业术语、中文、缩写、混合文本来说，未必足够强。

### 这一步建立了什么

这一步建立的是一个非常重要的共识：

1. 当前确实有关键词检索
2. 但它不是一个成熟倒排引擎式的关键词检索
3. 它更像“基于 Milvus scalar query 的候选召回 + 应用内 BM25 重排”

## 十三、第六步：BM25 是怎么在应用内算的

### 目标

说明 BM25 和 `LIKE` 的关系，避免大家把这两个阶段混成一件事。

### 文件

1. [backend/internal/milvus/retrieval/sparse_inverted_index.go](/abs/path/d:/Bear/rag-retrievalOps/backend/internal/milvus/retrieval/sparse_inverted_index.go)

### 这一步在做什么

`BuildSparseInvertedIndex(...)` 会对已经拿回来的候选文档临时建一个显式倒排索引，然后 `Search(...)` 用 BM25 算分。

这里要强调一个容易被误会的点：

1. `LIKE` 负责“拉候选”
2. BM25 负责“排候选”

它们不是一回事。

### 这个设计的好处

好处是实现简单，而且比较灵活：

1. 候选来源可以先简单一点
2. 排序逻辑可以自己控制
3. 后面如果要换 BM25 参数或者换排序公式，改动相对集中

### 这个设计的限制

限制也非常明显：

1. 候选太差，BM25 也救不回来
2. 候选太大，应用层重排成本会上升
3. 不能享受成熟倒排系统在召回阶段的索引优势

## 十四、第七步：为什么 sparse 明明命中了，最后却没有贡献

### 目标

这是这次分享最核心的解释点。

### 文件

1. [backend/internal/milvus/retrieval/fusion.go](/abs/path/d:/Bear/rag-retrievalOps/backend/internal/milvus/retrieval/fusion.go)

### 这一步在做什么

融合阶段会对 `dense` 和 `sparse` 两条路各自的分数做归一化，然后乘权重。

当前默认权重是：

1. `dense = 0.7`
2. `sparse = 0.3`

最关键的函数是 `normalizeRouteScore(...)`：

文件：`backend/internal/milvus/retrieval/fusion.go`

```go
func normalizeRouteScore(score float64, stats scoreStats) float64 {
	if stats.max <= stats.min {
		if score <= 0 {
			return 0
		}
		return 1
	}
	normalized := (score - stats.min) / (stats.max - stats.min)
	if normalized < 0 {
		return 0
	}
	if normalized > 1 {
		return 1
	}
	return normalized
}
```

### 这段代码在做什么

这是标准的 min-max 归一化。

意思是：

1. 本路最高分会被映射到 `1`
2. 本路最低分会被映射到 `0`
3. 中间按比例落在 `0` 到 `1` 之间

然后再乘路由权重。

### 为什么这会压死 sparse

当 sparse 路由命中数很少时，比如只有 2 条：

1. 高分那条可能变成 `1 * 0.3 = 0.3`
2. 低分那条可能直接变成 `0 * 0.3 = 0`

如果同时 dense 路由有 10 条候选，而且前几名语义分很高，那么 sparse 的候选很容易：

1. 要么被压成很小的分
2. 要么直接压成 0

这正是我们在真实 trace 里看到的现象。

某条真实 sparse 候选里：

1. `sparse_score = 0.430143...`
2. 但 `fusion_score = 0`

这说明它不是“没有 sparse_score”，而是“归一化加权之后掉到 0 了”。

### 这套融合的好处

1. 实现简单
2. 好解释
3. Dense 和 sparse 可以用统一方式落到一个分数空间里

### 这套融合的弊端

1. 对小样本路由不友好
2. 对极少命中的 sparse 结果不友好
3. 最低分会被直接打成 0，过于激进
4. 很容易让弱路由“参与了但看起来毫无存在感”

### 更直白一点怎么讲

如果要在会议里用一句更容易懂的话来解释，可以这样说：

> 现在 sparse 的问题，不只是召回弱，还包括融合规则本身对 sparse 太苛刻，特别是命中数少的时候，很容易一上来就被归零。

```go
func annotateDedupedDocument(doc *schema.Document, score float64, primaryRoute string, contrib, rawScores map[string]float64) {
	if doc == nil {
		return
	}
	if doc.MetaData == nil {
		doc.MetaData = make(map[string]interface{})
	}

	doc.MetaData["score"] = score
	doc.MetaData["fusion_score"] = score
	doc.MetaData["route"] = primaryRoute
	doc.MetaData["route_contrib"] = floatMapToInterfaceMap(contrib)
	doc.MetaData["route_raw_scores"] = floatMapToInterfaceMap(rawScores)

	source := make(map[string]interface{})
	if existing, ok := doc.MetaData["source"].(map[string]interface{}); ok && existing != nil {
		for key, value := range existing {
			source[key] = value
		}
	}
	source["route"] = primaryRoute
	source["route_contrib"] = floatMapToInterfaceMap(contrib)
	if collection := readCollectionFromDoc(doc); collection != "" {
		source["collection"] = collection
	}
	if version := readMetadataString(doc, "retriever_version"); version != "" {
		source["retriever_version"] = version
	} else if _, exists := source["retriever_version"]; !exists {
		source["retriever_version"] = hybridRetrieverVersion
	}
	doc.MetaData["source"] = source
	annotateParentChildSource(doc)
}
```

### 这段代码在做什么

这里有两个非常重要的事实。

第一个事实：

1. 去重后文档会被写一个主路由 `route = primaryRoute`

第二个事实：

1. 后续统计 `dense_contribution` / `sparse_contribution`
2. 看的就是这个 `route`

也就是说，当前日志字段更像是在统计：

1. “最后留下来的文档，主标签是 dense 还是 sparse”

而不是在统计：

1. “dense 有没有参与过”
2. “sparse 有没有参与过”

### 为什么这会让人误会

因为字段名叫 `sparse_contribution`，大家很容易自然地把它理解成：

> sparse 到底有没有贡献

但从当前实现看，它更像：

> 最终入选结果里，有多少条的主路由是 sparse

如果一个文档：

1. 同时被 dense 和 sparse 命中
2. 但去重后主路由被标成 dense

那么：

1. `route_contrib` 里可能还有 sparse 信息
2. 但 `sparse_contribution` 统计仍然会是 0

### 这一步为什么很重要

因为它解释了本次排查中最容易被误解的一点：

> `sparse_contribution=0` 不等于 `sparse` 没执行，也不等于 `sparse` 没参与。

它只说明：

> 当前最终结果里，没有文档的主路由被记成 sparse。

## 十六、第九步：重排序会不会进一步放大 dense 优势

### 目标

说明 rerank 对当前结果结构的影响。

### 文件

1. [backend/internal/milvus/retrieval/reranker.go](/abs/path/d:/Bear/rag-retrievalOps/backend/internal/milvus/retrieval/reranker.go)

### 这一步在做什么

当前默认用的是 Jaccard reranker。

它的思路是：

1. 计算 query token 和文档 token 的 Jaccard 相似度
2. 再和原始分数按比例混合

默认权重大致是：

1. 原始分数占 `0.7`
2. Jaccard 相似度占 `0.3`

### 为什么这对 sparse 不一定有利

表面上看，关键词路由应该更受词面匹配型重排器欢迎。

但在我们现在这条链路里，前面融合后 sparse 的分数已经可能被压到很低，甚至变成 0。到了 rerank 阶段：

1. 原始分数已经弱了
2. Jaccard 再补一点也未必能翻盘

所以 rerank 更多是在“已有候选上微调顺序”，而不是替 sparse 路由翻盘。

### 这一步告诉我们什么

不要把问题归咎到某一个单点。

当前 sparse 弱，不是单一原因，而是几个环节叠加：

1. 候选召回方式偏弱
2. term 提取偏轻
3. 融合规则对小样本 sparse 不友好
4. rerank 不是专门为 sparse 翻盘设计的

## 十八、当前设计的主要问题

这一部分是会议里真正要推动决策的重点。

### 1. 关键词检索的召回方式偏弱

当前 sparse 路由的核心候选召回方式是：

1. 关键词提取
2. `content like "%term%"`
3. Milvus `Query`

这不是一个强倒排召回方案。

#### 风险

1. 数据量增大时性能压力会明显上升
2. 中文、缩写、变体词处理能力有限
3. 查出来的候选质量不稳定

### 2. BM25 只是在候选集上工作，不是在全量索引上工作

这导致 BM25 的效果上限被前面的 `LIKE` 候选上限限制住了。

简单说就是：

1. 候选没拉对，BM25 再强也没用

### 3. 融合规则对 sparse 太不友好

当前的 min-max 归一化会把低分 sparse 候选直接打到 0。

当 sparse 命中很少时，这个现象尤其严重。

#### 结果

1. sparse 参与了
2. 但在融合阶段已经几乎被判死刑

### 4. 当前贡献指标语义容易误导

`sparse_contribution=0` 很容易让人误会成：

1. sparse 没执行
2. sparse 没价值

但实际语义更接近：

1. 最终保留结果的主路由不是 sparse

这是一个“指标命名和统计口径不够直观”的问题。

### 5. Route-specific rewrite 能力没有真正发挥

虽然代码已经有 route-specific rewrite 的框架，但当前配置里：

1. `enable_route_specific_rewrite: false`

这意味着 dense 和 sparse 目前大体上还是共享同一个改写方向。

问题在于：

1. dense 更适合语义扩展
2. sparse 更适合保留字面锚点

如果两条路吃同一套改写结果，可能对 sparse 不是最优。

### 6. 当前样本量还小

截至 `2026-06-04`，本地库里只有 `7` 条检索日志。

这意味着：

1. 当前结论足够说明“系统怎么跑”
2. 但还不足够说明“最终线上稳定收益”

这不是结论不成立，而是说明后面还需要更大样本验证。

## 二十二、取舍与后续优化

这一版实现，优化的是“先把混合检索链路跑起来并可观测”，不是“把关键词检索做到生产级最优”。

这是它的合理性，也是它现在的边界。

### 当前版本优化了什么

1. 快速具备混合检索主链路
2. 能上线验证
3. 能产生日志和 debug trace
4. 能做灰度和回滚

### 当前版本刻意没有解决好的问题

1. 稳健的关键词召回索引体系
2. 强中文分词和术语词典
3. 更鲁棒的多路融合策略
4. 更直观的路由贡献指标

### 后续最自然的优化方向

#### 方向 1：先把日志口径补清楚

优先级很高，而且改动最小。

建议补充两类指标：

1. `sparse_participation_count`
   含义是 sparse 是否参与了最终候选融合
2. `dual_route_final_count`
   含义是最终结果里有多少条同时带 dense 和 sparse route_contrib

这样团队以后就不会把 `sparse_contribution=0` 误读成“sparse 没执行”。

#### 方向 2：改 sparse 融合策略

这是当前最可能直接提升 sparse 可见价值的点。

可以考虑：

1. 不再用会直接归零的 min-max
2. 改成 rank-based fusion
3. 改成 RRF
4. 或者至少给 sparse 一个非零保底分

#### 方向 3：升级 sparse 召回

这是中长期更本质的方向。

可选思路包括：

1. 使用真正的倒排索引引擎
2. 使用更强的全文检索能力
3. 强化 term extraction、词典、缩写展开、中文分词

#### 方向 4：启用 route-specific rewrite

让 dense 和 sparse 分别吃不同风格的改写：

1. dense 偏语义扩展
2. sparse 偏字面锚点保留

#### 方向 5：做更大样本评估

当前只有 7 条日志，足够解释“怎么跑”，但不够评估“策略收益”。

后面建议：

1. 扩大真实 query 样本
2. 拉评测集
3. 对比 sparse 参与前后收益

## 二十三、最后的会议版总结

如果会议最后只留 1 分钟总结，我建议直接用下面这段话：

> 这次排查的最终结论是：当前系统不是没用向量检索，而是确实在跑混合检索，`dense` 和 `sparse` 两条路都执行了。只是 `sparse` 这条路当前实现方式是 `content like` 候选召回，再在应用内做 BM25，它更像一个早期 baseline，不是成熟的关键词检索方案。再加上当前融合和贡献统计口径的设计，导致 sparse 虽然参与了，但在日志上看起来像“没有贡献”。所以我们现在真正该讨论的，不是“有没有向量检索”，而是“怎么把 sparse 做强、把融合做公平、把指标口径说清楚”。
