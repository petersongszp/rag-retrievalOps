## 第 3 页：背景与目标

### 🎯 我们要解决的痛点

| 痛点 | 业务影响 |
|---|---|
| **「格式不统一」** | 客户知识来源多样：PDF 产品手册、Word 方案、HTML 网页、扫描件、纯文本… 每种格式解析质量参差不齐 |
| **「表格解析烂」** | PDF 里的报价单、参数表、费用清单解析成"纯文本一坨"，检索根本问不出准确答案 |
| **「切分无策略」** | 不管什么文档都按固定字符数一刀切，标题层级、表格结构全被切碎 |
| **「出错排障难」** | 文档入库后检索答非所问，不知道是"解析错了"还是"切分错了"还是"向量错了" |
| **「多租户不放心」** | 客户担心自己的文档会不会被其他租户检索到 |

### ✅ 我们的目标

> **让任意格式的业务文档，都能高质量、可追溯、安全地接入 RAG 知识库**

## 第 5 页：核心交付成果（中）—— 质量与可追溯

### 📊 成果 2：智能切分，保留结构，不再"一刀切"

| 文档特征 | 之前的切分 | 现在的切分策略 |
|---|---|---|
| **含表格的 PDF** | 按字符数切 → 表格被切碎 | ✅ **table-aware**：整块识别表格，单独切块 + 保留上下文 |
| **OCR 扫描件** | 当普通文本切 | ✅ **ocr-aware**：标记低置信度区域，检索时自动降级权重 |
| **有结构的文档** | 忽略标题层级 | ✅ **structure-aware**：按 PDF 内部标题层级切分 |
| **Markdown/纯文本** | 一刀切 | ✅ **markdown-aware**：按 `#` 标题切分，保留章节上下文 |

> **业务价值**：同一份文档，检索准确率提升「XX%」（建议你找一份典型客户文档测一下，填个实际数字）

## 第 6 页：核心交付成果（下）—— 可审计 + 安全

### 📊 成果 3：全程可追溯，排障效率提升 10 倍

| 能力 | 说明 |
|---|---|
| ✅ **双版本存储** | 原始解析结果 + 规范化结果，同时保留两份 |
| ✅ **sidecar 审计文件** | 每篇文档入库后生成 `*.normalized.json`，记录：<br>- 用了什么解析器<br>- 执行了哪些规范化规则<br>- 切分了多少块、每块的元数据<br>- 原始 hash / 规范化后 hash |
| ✅ **错误不丢信息** | 解析失败生成 `*.normalized.error.json`，记录错误码、发生在哪一步、是否可重试 |

> **业务价值**：
> - 客户问"为什么这个问题答不对"时，5 分钟内就能定位是"文档本身有问题"还是"解析问题"还是"切分问题"
> - 合规审计友好，每篇文档的处理过程全程可追溯

## 第 8 页：技术架构亮点（简化版 —— 给有技术背景的客户听）

### 🏗️ 整体架构：三层解耦，可替换、可扩展

```
┌─────────────────────────────────────────────┐
│   客户业务系统 / Admin 管理后台                │
└──────────────┬──────────────────────────────┘
               │ 上传 / 检索
┌──────────────▼──────────────────────────────┐
│   RAG Server（原有系统，不用改）              │  ← 第一层：业务层
└──────────────┬──────────────────────────────┘
               │ 统一解析接口
┌──────────────▼──────────────────────────────┐
│   Parser Provider Adapter（我们新增）          │  ← 第二层：适配层
│   - 协议转换                                 │
│   - 质量补丁（表格延展、HTML lead-in 修复）  │
│   - 错误分类与重试                            │
└──────────────┬──────────────────────────────┘
               │ 标准 Docling API
┌──────────────▼──────────────────────────────┐
│   Docling Serve（开源工业级解析引擎）          │  ← 第三层：引擎层
│   - PDF / DOCX / HTML 原生支持               │
│   - 内置 OCR / 表格识别                      │
└─────────────────────────────────────────────┘
```

### 💡 为什么这么设计？

1. **不碰主架构**：RAG Server 基本不用改，风险极低
2. **引擎可替换**：未来想换 MinerU / Unstructured / 自研，只换第三层
3. **就近做补丁**：HTML lead-in 缺失、PDF 表格截断这类"脏活"，在适配层就近修好，不污染业务层
4. **按需伸缩**：解析服务可以独立扩缩容，不影响检索性能

## 第 10 页：上线计划与风险

### 📅 建议上线节奏

| 阶段 | 时间 | 内容 |
|---|---|---|
| **灰度期** | 第 1 周 | 只给 1~2 个试点客户开启新解析器，旧解析器保留作为 fallback |
| **全量期** | 第 2 周 | 灰度无问题后，所有新上传文档默认走新解析器 |
| **存量迁移** | 第 3~4 周 | 对存量文档评估是否需要重新解析（建议：只迁移客户反馈"答不准"的文档） |

### ⚠️ 已知风险与应对

| 风险 | 概率 | 影响 | 应对措施 |
|---|---|---|---|
| Docling 解析某些特殊 PDF 超时 | 中 | 单篇文档入库慢 | 已配置 60s 超时，失败后自动降级回本地解析器 |
| OCR 扫描件质量差，识别不准 | 高 | 检索答案不准 | 已实现 ocr-aware 切分，低置信度区域自动降级权重；建议客户尽量提供文本型 PDF |
| 新切分策略导致 chunk 数变多 | 中 | Milvus 存储空间增加 | 已做父子 chunk 优化，实际存储增量约 10~20%，在可接受范围内 |

## 附录 A：技术细节（可选 —— 给深度技术客户）

### A.1 核心技术栈
- **Go 1.25.1**：后端主语言
- **Docling**（IBM 开源）：工业级文档解析引擎
- **goldmark**：Markdown AST 解析，用于按标题切分
- **Unicode Normalization**：NFC 归一化，解决乱码问题
- **Docker Compose**：解析服务独立部署，`--profile parser` 按需启动

### A.2 关键文件清单（用于技术对接）
- `backend/internal/documentparser/`：统一解析接口与本地实现
- `backend/internal/documentparser/canonical/`：归一化规则引擎
- `backend/internal/parserprovider/`：Docling HTTP 适配器
- `backend/internal/milvus/chunking/`：智能切分路由与策略
- `backend/cmd/parser-provider/`：独立解析服务入口
- `backend/scripts/start-docling-parser-stack.sh`：一键启动脚本

### A.3 配置项说明
- `DOCUMENT_PARSER_ENDPOINT`：解析服务地址
- `DOCUMENT_PARSER_TIMEOUT_MS`：超时时间（默认 60s）
- `DOCUMENT_PARSER_STRICT_MODE`：严格模式（失败即报错）
- `OCR_ENDPOINT`：OCR 服务地址（可选）
