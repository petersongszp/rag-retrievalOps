# wubo 分支文档清洗功能验证计划

## 一、验证目标

本验证计划用于系统性验证 `wubo` 分支实现的“文档解析归一化 / 文档清洗”能力是否满足知识库入库链路要求。

验证重点不是单独验证一个上传前工具，而是验证以下完整链路：

1. 知识库上传接口是否正确支持多格式文件。
2. 上传接口是否完成文件类型、大小、空文件、重复文件等基础校验。
3. `txt`、`md`、`markdown` 是否能由后端本地归一化为 `NormalizedDocument`。
4. `pdf`、`docx`、`html`、`htm` 是否能通过 parser-provider 调用 Docling Serve 解析为 Markdown。
5. 解析结果是否经过 canonical normalizer 二次清洗。
6. 成功和失败场景是否生成 sidecar 文件。
7. 归一化结果是否进入后续 chunking router，并按文档结构选择正确切片策略。
8. 入库任务状态、文档状态、向量写入和检索结果是否符合预期。
9. 异常场景是否能被定位、记录和重试。

## 二、验证范围

### 1. 需要验证的核心模块

| 模块 | 验证目的 |
| --- | --- |
| `backend/api/handler/kb/handler.go` | 验证上传入口、文件校验、去重、任务创建、MQ 发布 |
| `backend/internal/documentparser` | 验证标准文档模型、本地归一化、表格清洗、sidecar 输出 |
| `backend/internal/documentparser/canonical` | 验证 parser 输出后的确定性二次清洗 |
| `backend/internal/parserprovider` | 验证 `/parse` 接口、Docling Serve 适配、错误返回 |
| `backend/cmd/parser-provider` | 验证 parser-provider 可独立启动 |
| `backend/internal/ragqueue/consumer.go` | 验证异步入库消费者是否调用解析归一化并写 sidecar |
| `backend/internal/milvus/chunking` | 验证切片策略路由和 chunk metadata |
| `docker-compose.yml` | 验证 Docling Serve 与 parser-provider 服务编排 |
| `backend/scripts/start-docling-parser-stack.sh` | 验证一键启动 Docling 解析栈 |

### 2. 不在本次验证范围内的内容

1. MCP Server 相关功能不纳入文档清洗主线验收。
2. 前端“上传前预览清洗结果”不纳入通过标准，因为当前实现是上传后、切片前异步清洗。
3. Docling 本身的解析算法准确率不作为代码通过或失败的唯一依据，只验证项目是否正确调用、适配、记录和降级处理。
4. 大规模性能压测不作为本轮必要验收项，但会给出基础稳定性验证建议。

## 五、第一阶段：静态代码验证

### 1. 上传入口检查

检查上传接口是否具备以下逻辑：

| 检查项 | 预期 |
| --- | --- |
| 上传接口路由 | `POST /api/admin/kb/documents/upload` |
| 表单字段 | `kb_id` 和 `file` |
| 支持后缀 | `pdf/txt/md/markdown/docx/html/htm` |
| 大小限制 | 20MB |
| 空文件处理 | 返回错误 `uploaded file is empty` |
| 不支持类型处理 | 返回错误 `only pdf/txt/md/markdown/docx/html/htm files are supported` |
| 文件 hash | 按内容计算 SHA256 |
| 去重范围 | 同一知识库内按文件 hash 去重 |
| 新文件入库 | 创建 `KBDocument` 和 `KBIngestJob` |
| 消息发布 | 发布 `knowledge_ingest` 消息 |

重点核对：

1. `validateKnowledgeFile` 是否只按后缀判断类型。
2. `readKnowledgeFile` 是否读取内容、限制 20MB、拒绝空文件、计算 SHA256。
3. `UploadDocument` 是否在去重命中时返回 `reused=true`。
4. `UploadDocument` 是否在新文件时创建文档和任务，并发布 `knowledge_ingest`。

### 2. 异步消费者检查

检查 `extractNormalizedKnowledgeDocument` 逻辑：

| 文件类型 | 预期处理方式 |
| --- | --- |
| `txt/md/markdown` | 调用 `documentparser.NormalizeLocal` |
| `pdf/docx/html/htm` | 创建 HTTP provider 并调用 parser-provider `/parse` |
| 不支持类型 | 返回 `unsupported file type` |
| provider 配置错误 | 写入 `.normalized.error.json` |
| parser 返回错误 | 写入 `.normalized.error.json` |
| canonical 失败 | 写入 `.normalized.error.json` |
| 成功 | 写入 `.normalized.json` |

重点核对：

1. 是否读取源文件内容。
2. 是否使用 `documentparser.NormalizeFileType` 统一文件类型。
3. 是否根据 `IsLocalType` / `IsProviderType` 分支处理。
4. 是否将 `engine`、`strict_mode`、OCR 配置传给 provider。
5. PDF 是否额外传入 `pdf_backend=pypdfium2`。
6. 成功路径是否总是调用 canonical normalizer。
7. 成功路径是否写入 normalized sidecar。
8. 失败路径是否写入 error sidecar。

### 3. parser-provider 检查

检查 parser-provider `/parse` 接口：

| 检查项 | 预期 |
| --- | --- |
| 方法限制 | 只允许 POST |
| multipart 字段 | `file` 必填 |
| 文件大小 | parser-provider 限制 50MB |
| `file_type` | 支持显式传入，也可从文件名后缀推断 |
| `options` | JSON 字符串，非法时返回 `invalid_options` |
| Docling 字段 | 向 Docling 发送 `files`、`to_formats=md/json`、`image_export_mode=placeholder` |
| 成功返回 | `NormalizedDocument` JSON |
| 失败返回 | `ProviderError` JSON |

重点核对：

1. parser-provider 的上传字段是 `file`。
2. 转发到 Docling Serve 时字段名变为 `files`。
3. Docling 默认地址是否为 `http://localhost:5001`。
4. Docling 默认路径是否为 `/v1/convert/file`。
5. Docling markdown 为空时是否使用 text fallback。
6. Docling 输出是否被转换为项目内部 `NormalizedDocument`。
7. HTML 是否调用 `RestoreHTMLLeadInBeforeFirstHeading` 保留首段说明。
8. Markdown 表格是否调用 `NormalizeMarkdownPipeTables`。

### 4. 切片路由检查

检查 `chunking` 路由策略：

| 条件 | 预期路由 |
| --- | --- |
| `doc.Tables` 非空 | `table-aware` |
| PDF 且 warning 或 block confidence 中出现 OCR 信号 | `ocr-aware` |
| `doc.Blocks` 非空且类型为 docx/pdf/html/htm | `structure-aware` |
| 其他情况 | `markdown` |

重点核对：

1. table-aware 优先级是否高于 OCR-aware 和 structure-aware。
2. 每个 chunk metadata 是否写入 `chunking_route`。
3. chunk metadata 是否包含 `normalized_path`、来源文件等可追溯字段。

```powershell
curl -X POST "$env:RAG_BASE_URL/api/admin/kb/documents/upload" -H "Authorization: Bearer $env:TOKEN" -F "kb_id=$env:KB_ID" -F "file=@h:\GYT-CODE\rag-retrievalOps\testdata\wubo-parser\unsupported.xlsx"
```

预期：

1. 返回 400。
2. 错误信息包含 `only pdf/txt/md/markdown/docx/html/htm files are supported`。
3. 不入库、不入队。

### 4. 重复上传

先上传 `table.md`，再上传内容完全相同的 `duplicate.md` 或再次上传 `table.md`。

预期：

1. 第二次上传返回成功。
2. 响应中 `reused=true`。
3. 返回已有 `document_id`。
4. 返回已有或最近一次 `job_id`。
5. 不创建新的文档记录。
6. 不重复发布新的入库任务。
7. 不重复写入向量。

### 5. 同内容不同知识库上传

将相同文件上传到另一个测试知识库。

预期：

1. 不应复用第一个知识库的文档。
2. 应创建新的 `KBDocument` 和 `KBIngestJob`。
3. 去重范围应限定在同一个 `kb_id` 内。

## 十、第六阶段：sidecar 文件验证

### 1. 成功 sidecar

成功解析后，检查源文件旁是否存在：

```text
原始文件路径.normalized.json
```

重点检查字段：

| 字段 | 预期 |
| --- | --- |
| `content_markdown` | 非空，最终用于切片 |
| `content_markdown_raw` | provider 原始 Markdown 输出，若本地解析可为空 |
| `source.file_name` | 原始文件名正确 |
| `source.file_type` | 文件类型正确 |
| `source.source_path` | 源文件路径可追溯 |
| `tables` | 表格文档应非空 |
| `blocks` | 如 parser 有结构块则保留 |
| `omitted_images` | 被忽略图片可记录 |
| `quality.status` | 成功时为 `ok` 或可接受状态 |
| `quality.warnings` | 有警告时不应丢失 |
| `extractor` | 能看出解析器来源 |
| `canonicalization` | 记录清洗规则和 hash 信息 |

### 2. 失败 sidecar

故意上传损坏 PDF，或关闭 parser-provider 后上传 docx/pdf/html。

预期源文件旁生成：

```text
原始文件路径.normalized.error.json
```

重点检查字段：

| 字段 | 预期 |
| --- | --- |
| `error_code` | 默认为 `parse_error` 或 provider 返回 code |
| `message` | 包含可定位错误原因 |
| `stage` | 建议为 `parse` |
| `quality` | 如有解析质量信息应保留 |

### 3. `DOCUMENT_PARSER_SAVE_SIDECAR=false` 行为确认

将配置改为：

```env
DOCUMENT_PARSER_SAVE_SIDECAR=false
```

上传一个新文件。

需要确认实际行为：

1. 如果仍生成 `.normalized.json`，说明当前代码没有使用该配置控制 sidecar 写入。
2. 如果不生成 `.normalized.json`，说明配置已生效。

验收结论需要明确记录这一点。根据当前代码观察，消费者成功路径会直接调用 `SaveNormalizedSidecar`，失败路径会直接调用 `SaveErrorSidecar`，因此很可能配置为 false 仍会写 sidecar。这应作为待修复或待确认项。

## 十一、第七阶段：任务状态和重试验证

### 1. 查询任务状态

上传成功后，使用返回的 `job_id` 查询：

```powershell
curl -X GET "$env:RAG_BASE_URL/api/admin/kb/jobs/$env:JOB_ID" -H "Authorization: Bearer $env:TOKEN"
```

预期状态流转：

```text
pending -> processing -> completed
```

失败场景：

```text
pending -> processing -> failed
```

### 2. 查询任务列表

```powershell
curl -X GET "$env:RAG_BASE_URL/api/admin/kb/jobs?kb_id=$env:KB_ID" -H "Authorization: Bearer $env:TOKEN"
```

预期：

1. 能看到当前知识库的入库任务。
2. 状态、错误信息、重试次数等字段可用于排查。

### 3. 失败重试

制造失败：关闭 parser-provider，然后上传 docx/pdf/html。

预期：

1. 任务进入 `failed`。
2. 生成 `.normalized.error.json`。

恢复 parser-provider 后执行：

```powershell
curl -X POST "$env:RAG_BASE_URL/api/admin/kb/jobs/$env:JOB_ID/retry" -H "Authorization: Bearer $env:TOKEN"
```

预期：

1. 任务可被重试。
2. 重试后最终 `completed`。
3. 成功后生成 `.normalized.json`。
4. 文档状态从 failed 恢复为 completed，或按代码设计正确更新。

### 4. 任务取消

对尚未完成的任务执行：

```powershell
curl -X POST "$env:RAG_BASE_URL/api/admin/kb/jobs/$env:JOB_ID/cancel" -H "Authorization: Bearer $env:TOKEN"
```

预期：

1. 未完成任务可取消。
2. 已完成任务不可取消。
3. 取消后任务状态为 `canceled`。
4. 关联文档状态按代码设计更新。

## 十二、第八阶段：向量写入和检索验证

### 1. 验证 chunk metadata

对已完成入库的样例文档，检查 Milvus 中写入的 metadata，重点字段：

| 字段 | 预期 |
| --- | --- |
| `document_id` | 与上传返回一致 |
| `kb_id` | 与测试知识库一致 |
| `file_name` | 与上传文件一致 |
| `file_type` | 与解析文件类型一致 |
| `normalized_path` | 指向 `.normalized.json` |
| `chunking_route` | 符合路由规则 |
| `table_id` | 表格切片时应尽量存在 |
| `page` | PDF 如能识别页码则保留 |

### 2. 检索普通文本

上传 `plain.txt` 后，查询其中一个明确短句：

```powershell
curl -X POST "$env:RAG_BASE_URL/api/admin/kb/retrieve" -H "Authorization: Bearer $env:TOKEN" -H "Content-Type: application/json" -d "{\"kb_ids\":[$env:KB_ID],\"query\":\"这里填写 plain.txt 中的关键句\",\"top_k\":5}"
```

预期：

1. 能返回 `plain.txt` 对应 chunk。
2. metadata 中 `chunking_route=markdown`。
3. 分数和内容可解释。

### 3. 检索表格内容

上传 `table.md` 或 `table.pdf` 后，查询表格中的某个字段和值。

预期：

1. 能命中对应文档。
2. 返回内容应包含表格上下文。
3. metadata 中 `chunking_route=table-aware`。
4. 如果有 `table_id`，应能对应 sidecar 中的 table。

### 4. 检索 DOCX / HTML 标题结构

上传 `simple.docx` 或 `simple.html` 后，查询二级标题或列表项。

预期：

1. 能命中对应文档。
2. chunk 内容保留标题上下文。
3. metadata 中路由为 `structure-aware` 或 `markdown`，取决于 blocks 是否生成。

## 十三、第九阶段：异常和降级验证

### 1. parser-provider 未启动

停止 parser-provider，上传 `simple.docx`。

预期：

1. 上传接口本身仍可能返回 pending，因为解析是异步执行。
2. 异步任务最终 failed。
3. 错误 sidecar 生成。
4. 错误信息应包含连接失败或 provider 不可用信息。
5. 不应导致消费者进程崩溃。

### 2. Docling Serve 未启动，但 parser-provider 启动

停止 Docling Serve，保留 parser-provider，上传 `simple.pdf`。

预期：

1. parser-provider 返回调用 Docling 失败。
2. 入库任务 failed。
3. error sidecar message 可定位为 Docling 调用失败。

### 3. parser-provider 返回空 Markdown

可通过 mock 或构造特殊文件触发。

预期：

1. 返回 `empty_docling_result` 或等价错误。
2. 入库任务 failed。
3. error sidecar 可定位。

### 4. 本地文本为空白

上传只包含空格、换行的 txt 或 md 文件。

预期：

1. 上传入口不一定会拒绝，因为文件不是 0 字节。
2. 本地 NormalizeLocal 会返回 `empty text content`。
3. 入库任务 failed。
4. 生成 `.normalized.error.json`。

## 十四、第十阶段：验收判定标准

### 1. 必须通过项

以下全部通过，才能认为文档清洗主链路通过验收：

1. 单元测试 `documentparser`、`canonical`、`parserprovider`、`ragqueue` 全部通过。
2. 上传入口支持 `pdf/txt/md/markdown/docx/html/htm`。
3. 空文件、超 20MB、不支持类型均能被拒绝。
4. 同一知识库内重复文件能返回 `reused=true`。
5. `txt/md/markdown` 可本地生成 `NormalizedDocument`。
6. `md/markdown` 中的 pipe table 可生成 `tables`。
7. `pdf/docx/html/htm` 可经 parser-provider + Docling Serve 生成 Markdown。
8. 成功解析生成 `.normalized.json`。
9. 失败解析生成 `.normalized.error.json`。
10. canonical 清洗信息能写入 sidecar。
11. 有表格文档优先走 `table-aware`。
12. 普通文档走 `markdown` 兜底策略。
13. 入库任务能从 pending/processing 变为 completed 或 failed。
14. 成功入库文档能被检索命中。
15. parser-provider 或 Docling 不可用时，不应导致后端或消费者崩溃。

### 2. 可接受但需要记录的问题

以下问题不一定阻塞主链路验收，但需要记录：

1. 扫描 PDF OCR 效果不稳定。
2. DOCX/HTML/PDF 的 `blocks` 不完整，导致无法走 `structure-aware`。
3. Docling 对复杂表格识别不完整。
4. `DOCUMENT_PARSER_SAVE_SIDECAR=false` 仍然写 sidecar。
5. 大文件解析耗时较长或偶发超时。
6. provider 错误信息可读性不足。
7. parser-provider 50MB 限制与业务上传入口 20MB 限制不一致，但业务入口以 20MB 为准。

### 3. 阻塞问题

出现以下任意问题，应判定为不通过：

1. 上传合法文件后不能创建 `KBDocument` 或 `KBIngestJob`。
2. MQ 消息没有发布，异步消费者无法处理任务。
3. `txt/md/markdown` 本地归一化失败。
4. parser-provider 无法启动或 `/parse` 基本不可用。
5. Docling 成功返回后无法适配为 `NormalizedDocument`。
6. 成功解析不生成 sidecar，且无其他可审计结果。
7. 解析失败不生成错误 sidecar，也无法从任务错误中定位原因。
8. 有表格的 Markdown 无法生成 `tables`。
9. chunking router 不写入 `chunking_route`。
10. 入库任务状态长时间停留在 `pending` 或 `processing`，且无错误信息。
11. 成功任务未写入向量库，检索完全无法命中。
12. 异常文件导致服务 panic 或进程退出。

## 十六、推荐最终验证顺序

建议按以下顺序执行，避免一开始就做复杂联调导致问题难定位：

1. 跑单元测试：确认核心代码没有基础失败。
2. 静态检查上传入口和消费者逻辑：确认实现路径符合预期。
3. 单独启动 parser-provider + Docling：确认外部解析链路可用。
4. 直接调用 parser-provider `/parse`：排除后端入库链路干扰。
5. 上传 `plain.txt`：验证本地解析最小闭环。
6. 上传 `table.md`：验证本地 Markdown 表格和 table-aware。
7. 上传 `simple.docx`：验证 provider 链路。
8. 上传 `simple.html` / `simple.htm`：验证 HTML 特殊处理。
9. 上传 `table.pdf`：验证 PDF 和表格。
10. 上传 `scan.pdf`：验证 OCR 或失败可观测性。
11. 验证空文件、超限文件、不支持类型、重复文件。
12. 验证任务查询、失败重试、取消。
13. 验证 Milvus metadata 和检索命中。
14. 汇总阻塞问题、可接受问题和最终验收结论。
