# RAG 平台总路线图

## 1. 文档定位

本文档是项目总路线图，作为当前 RAG 平台的统一推进入口。
它覆盖以下内容，并按固定顺序组织：

1. 项目现状
2. 目标
3. 能力分层
4. Phase 0 - Phase 4
5. 每阶段任务
6. Gate
7. 测试方案
8. 协作分工
9. 首批任务

本文档的作用有两个：

1. 作为团队对齐项目全貌、阶段边界和优先级的总控文档。
2. 作为后续各 Phase 详细路线文档的上位索引，避免局部优化失去整体方向。

统一口径说明：

1. `统一检索结果契约` 固定指：`content/score/citation/source`。
2. `标准检索流水线` 固定指：`dense + sparse -> fusion -> dedupe -> rerank -> filter/truncate`。
3. `平台能力` 固定指：不仅包含检索本身，也包含知识库、评测、监控、治理、权限和运维。
4. `阶段 Gate` 固定指：只有上一阶段的功能、测试、回滚路径都满足要求，才进入下一阶段。

---

## 2. 项目现状

## 2.1 当前已经具备的能力

从现有代码和文档看，项目已经不是一个“RAG Demo”，而是一套已经具备平台雏形的 RAG 系统。

当前已经落地的核心能力包括：

1. Go 后端服务，负责知识库、检索、评测、策略、审计和治理能力。
2. Next.js 管理后台，负责运营和管理视角的可视化入口。
3. Milvus 向量检索链路，支持文档入库、向量检索和混合检索。
4. Dense + Sparse 的混合检索主链路，已经具备 fusion、dedupe、rerank、filter/truncate 的结构。
5. Query Rewrite、动态 TopK、Parent-Child、Evidence Gate、Citation Consistency 等高级检索能力基础。
6. 多租户、JWT、API Key、知识库权限控制等平台访问控制能力。
7. 评测数据集、评测运行、实验、策略版本、回滚和治理相关模块。
8. 监控、告警、周报、成本、审计、向量运维等平台治理能力。

## 2.2 当前还存在的主要问题

虽然能力很多，但从“平台成熟度”角度看，当前仍有几个核心问题：

1. 总路线分散在多份文档里，阶段目标和依赖关系不够集中。
2. 高级检索能力很多，但缺少统一的总优先级和交付顺序视图。
3. 某些能力已经有实现基础，但还没有形成稳定的产品化闭环。
4. 平台治理、检索策略、成本控制、运维工具之间的衔接还需要继续收敛。
5. 首批高价值任务需要从“功能很多”切换到“持续按 Gate 推进”。

## 2.3 当前项目定位

当前项目最准确的定位是：

`面向企业知识场景的 RAG 平台`。

它的目标不是只提供一个 `/retrieve` 接口，而是提供：

1. 可管理的知识库能力
2. 可解释的检索能力
3. 可评测的策略能力
4. 可治理的生产能力
5. 可扩展的平台能力

---

## 3. 项目目标

项目总目标分三层：

1. 先把平台做成“可稳定使用”的 RAG 产品，而不是实验代码。
2. 再把平台做成“可持续优化”的检索工程系统，而不是一次性交付。
3. 最后把平台做成“可规模化治理”的企业级基础设施，而不是单团队内部工具。

具体来说，目标可归纳为：

1. 检索效果要持续可优化。
2. 文档入库和知识管理要可运维。
3. 鉴权、隔离、审计、告警要可上线。
4. 策略实验、灰度、回滚要可治理。
5. 成本、性能、容量、风险要可观测。
6. 前后端、后端、算法、QA、SRE 能按阶段稳定协作。

## 5. Phase 0 - 4 总览

项目按 5 个阶段推进，每个阶段只解决一类核心问题。

## 5.1 Phase 0：RAG 基线打通

目标：

把最小知识库闭环跑通，确保“文档可上传、可入库、可检索、可删除、可追踪”。

关键词：

1. 基线可用
2. 异步入库
3. 最小检索契约
4. 最小前后台闭环

## 5.2 Phase 1：生产可用

目标：

把 Phase 0 的最小闭环升级成生产链路，解决重试、告警、审计、限流、隔离和回滚问题。

关键词：

1. 生产稳定
2. 安全隔离
3. 可观测
4. 可回滚

## 5.3 Phase 2：混合检索与质量提升

目标：

把单路检索升级成标准混合检索流水线，提升召回质量和结果可解释性。

关键词：

1. Dense + Sparse
2. Fusion
3. Dedupe
4. Rerank
5. Query Rewrite

## 5.4 Phase 3：高级检索能力

目标：

在 Phase 2 的基础上继续提升复杂问题、长文档、多段证据和弱证据场景的质量。

关键词：

1. Parent-Child
2. Strategic TopK
3. Evidence Refusal
4. Citation Consistency
5. Advanced Rewrite

## 5.5 Phase 4：企业治理与规模化

目标：

把检索平台升级成真正可治理、可实验、可规模化运维的企业级系统。

关键词：

1. 实验平台
2. 索引生命周期
3. 成本治理
4. 审计合规
5. 自动化周报
6. 运维工具化

## 6. 每阶段任务

这里只保留总视角任务，详细实现继续下钻到各自 Phase 文档。

## 6.1 Phase 0 任务

1. 打通知识库、文档、任务三张核心表。
2. 打通上传 -> 异步入库 -> 检索 -> 删除闭环。
3. 固定最小检索结果契约：`content/score/citation/source`。
4. 打通最小管理后台页面和最小调试能力。
5. 建立基线冒烟测试和最小回滚方案。

## 6.2 Phase 1 任务

1. 建立入库重试与补偿机制。
2. 建立任务状态机和人工干预入口。
3. 建立监控、告警、审计和 request_id 追踪。
4. 建立权限隔离、限流和配额控制。
5. 完成压测、灰度和回滚演练。

## 6.3 Phase 2 任务

1. 引入 Dense + Sparse 混合检索。
2. 固化 `fusion -> dedupe -> rerank` 标准流水线。
3. 引入统一分数协议和可解释调试链路。
4. 引入 Query Rewrite 和 Dynamic TopK。
5. 建立离线评测、策略对比和回归基线。

## 6.4 Phase 3 任务

1. 引入 Parent-Child 检索与回填。
2. 引入战略版 Dynamic TopK 和 token budget 联动。
3. 引入 Evidence Gate 和标准拒答模板。
4. 引入 Citation Consistency 校验。
5. 引入高级 Rewrite：领域术语、route-specific、模型辅助灰度。
6. 完善高级检索 debug view 和高级评测门禁。

## 6.5 Phase 4 任务

1. 平台化 AB 实验和灰度发布。
2. 建立索引 / Collection 生命周期管理。
3. 建立成本采集、归因和成本看板。
4. 建立审计合规和保留策略。
5. 建立自动化周报和运营复盘机制。
6. 建立 Milvus / 向量库运维工具体系。

## 7. Gate

阶段 Gate 是这个项目最重要的推进约束。
规则是：`功能完成` 不等于 `阶段完成`，只有功能、测试、观测、回滚都满足才算通过。

## 7.1 Phase 0 Gate

1. 上传文档后可成功入库并被检索命中。
2. 删除文档后不再命中相关 chunk。
3. 任务状态完整可追踪。
4. 检索结果稳定包含 `content/score/citation/source`。
5. 冒烟测试通过，且不影响已有主流程。

## 7.2 Phase 1 Gate

1. 临时故障可自动重试并恢复。
2. 检索链路可通过 `request_id` 完整追踪。
3. 告警面板可发现核心异常。
4. 越权和限流测试通过。
5. 灰度和回滚演练通过。

## 7.3 Phase 2 Gate

1. Hybrid 相比 Dense Baseline 有明确质量收益。
2. Fusion、Dedupe、Rerank 流水线稳定。
3. 调试链路能解释召回来源、分数和路由贡献。
4. 离线评测和线上日志口径一致。
5. 关闭 Hybrid 开关后可回到稳定基线。

## 7.4 Phase 3 Gate

1. 长文档和多段证据场景相对 Phase 2 有显著收益。
2. 拒答策略降低强答风险，且误伤可控。
3. Citation 一致性能力可发现 unsupported claims。
4. 高级 rewrite 收益、风险、延迟都可量化。
5. 任一高级策略都可独立关闭并快速回滚。

## 7.5 Phase 4 Gate

1. 任意策略变更都可灰度、可实验、可回滚。
2. Collection 切换、重建、回滚可审计、可演练。
3. 成本、审计、运维、周报能力形成治理闭环。
4. 治理链路异常时不会拖垮查询主链路。
5. 项目进入“指标驱动 + 周期运营”状态。

## 8. 测试方案

测试方案按“阶段递进 + 层次递进”设计。

## 8.1 测试层次

1. 单元测试
   - 面向 fusion、dedupe、rerank、rewrite、topk、evidence gate 等策略函数
2. 集成测试
   - 面向 API、DB、Redis、Milvus、Consumer、配置初始化
3. 冒烟测试
   - 面向上传、入库、检索、删除、任务状态、页面操作
4. 回归测试
   - 面向已有主流程、旧策略、旧配置兼容性
5. 离线评测
   - 面向 Recall@K、MRR、nDCG、Citation Precision、Rewrite Gain
6. 发布演练
   - 面向灰度、告警、回滚、Collection 切换

## 8.2 按阶段测试重点

Phase 0：

1. 上传、入库、检索、删除闭环
2. 非法文件、重复文件、超大文件
3. Collection 配错和启动 fail-fast

Phase 1：

1. 重试和补偿
2. request_id 链路追踪
3. 鉴权、越权、限流、配额
4. 压测和回滚演练

Phase 2：

1. Dense vs Hybrid 对比
2. Fusion / Dedupe / Rerank 行为验证
3. Rewrite 和 Dynamic TopK 回归验证

Phase 3：

1. 长文档和多证据评测
2. 拒答误伤 / 漏拦评测
3. Citation consistency 评测
4. 高级 rewrite 收益和风险评测

Phase 4：

1. 实验分流正确性
2. Collection 生命周期演练
3. 成本归因正确性
4. 审计覆盖率和脱敏验证
5. 周报自动生成和门禁联动

## 8.3 测试产物要求

每个阶段至少应产出：

1. 通过 / 失败清单
2. 指标快照
3. 风险清单
4. 回滚说明
5. 验收结论

## 9. 协作分工

建议团队分工按能力层来拆，而不是按文件目录机械拆。

## 9.1 角色建议

1. 架构 / 主负责人
   - 负责总路线、阶段 Gate、配置口径、回滚口径
2. 后端工程
   - 负责 API、模型、任务、检索链路、治理链路
3. 算法 / 检索工程
   - 负责 fusion、rerank、rewrite、topk、citation、评测
4. 前端工程
   - 负责 admin 页面、调试页面、策略和治理可视化
5. QA
   - 负责冒烟、回归、验收、用例沉淀
6. SRE / 平台
   - 负责监控、告警、压测、发布、回滚、运维工具

## 9.2 协作原则

1. 先冻结契约，再并行开发。
2. 先冻结评测口径，再讨论策略收益。
3. 先冻结 Gate，再推进灰度。
4. 任意新能力都必须附带：
   - 测试方案
   - 可观测性
   - 回滚路径

## 9.3 阶段协作重点

Phase 0：

1. 后端与前端先冻结最小接口契约。
2. 后端与 QA 先冻结冒烟清单。

Phase 1：

1. 后端与 SRE 先冻结指标和告警口径。
2. 后端与 QA 先冻结错误码和状态机。

Phase 2：

1. 检索工程与后端先冻结分数字段和 debug 字段。
2. QA 介入 Hybrid 回归集和基线集。

Phase 3：

1. 检索工程、后端、QA 先冻结高级评测集和收益口径。
2. 高级策略必须按可独立开关原则落地。

Phase 4：

1. 架构、后端、SRE 先冻结实验、发布、Collection 生命周期协议。
2. 成本、审计、周报能力必须形成联动，而不是孤立页面。

## 10. 首批任务

首批任务不是“把所有能力都做完”，而是先把总控节奏建立起来。

建议第一批任务按优先级如下：

## 10.1 P0：路线与阶段对齐

1. 冻结本总路线图，作为后续详细实现的总入口。
2. 梳理并补齐各 Phase 文档之间的引用关系。
3. 确认当前项目处于哪个实际阶段，以及哪些 Gate 已满足、哪些未满足。

## 10.2 P0：当前主链路收敛

1. 盘点当前检索主链路的真实默认路径。
2. 盘点当前 feature flag、实验开关和回滚入口。
3. 盘点当前评测数据集、测试脚本和监控口径是否一致。

## 10.3 P1：短期高价值交付

1. 收敛一项明确的检索策略升级任务，例如 RRF、Fusion 改造或评测门禁完善。
2. 为这项升级任务补一份独立的大纲文档。
3. 按 `L0 -> L1 -> ... -> Gate` 节奏推进，并要求每层都可验证、可提交。

## 10.4 P1：治理闭环补强

1. 确认调试视图、结构化日志、评测报告三者字段是否一致。
2. 确认策略变更是否真正具备灰度和回滚路径。
3. 确认成本、审计、告警是否能支撑后续规模化治理。

## 10.5 P2：文档化与交接

1. 为每个阶段建立验收模板。
2. 为高风险链路建立运行手册。
3. 为首批核心策略建立“设计 -> 实现 -> 测试 -> 发布 -> 回滚”闭环模板。

---

## 11. 推荐推进顺序

如果从今天开始往前推进，建议总顺序如下：

1. 先冻结总路线图。
2. 再确认当前实际阶段状态。
3. 再选择一个高价值、低分叉的策略任务做样板。
4. 用样板任务跑通：
   - 大纲
   - 分层实施
   - 验证
   - 中文提交
   - Gate 验收
5. 跑通一次后，再把同样的方法复制到后续策略和治理任务上。

---

## 12. 总结

这个项目当前最重要的事，不是再堆一个新功能，而是把“已有很多能力”收敛成“按阶段稳定演进的平台路线”。

总方向可以概括成一句话：

`先把基线做稳，再把检索做强，最后把治理做深。`

对当前项目来说，正确的推进原则是：

1. 不追求一次性全做完。
2. 每一阶段都必须有明确 Gate。
3. 每一项策略能力都必须有测试、日志和回滚。
4. 每一次演进都要能沉淀成下一次复用的工程模板。

本文档之后，所有新增路线、详细方案和具体实现，原则上都应以上述阶段和能力分层为总参照。
