# 语义缓存降本 - 踩坑与避坑指南

---

## 前言

语义缓存看起来就是"算 embedding、找相似、返回结果"三件事，但实际上处处是坑。它跨越了"缓存"和"机器学习"两个领域，每个领域单独看都有自己的经典坑，叠在一起更是放大效应——既要面对缓存一致性、内存淘汰、单点故障这些传统缓存问题，又要面对模型升级、向量空间不兼容、阈值难定这些 ML 系统的特有问题。

下面这 7 个坑按踩中概率从高到低排序，覆盖了我们项目从立项到稳定运行的整个生命周期。每个坑都附了"业内通病"还是"项目实战"标记，以及当前项目的真实应对方案。

---

## 🕳️ 坑 1：相似度阈值拍脑袋，命中率和质量两头不讨好

> **类型**：项目实战 + 业内通病
> **排查难度**：★★★☆☆
> **当前应对**：单档 0.92 + 配置项热更新

### 问题描述
相似度阈值设置不合理，要么太高导致命中率低省不了钱，要么太低导致误匹配率高用户体验下降。

### 踩坑过程
大部分人都是这么踩的：
- 一开始拍脑袋定个 0.95，觉得"要足够像才能复用"，结果命中率只有 10%，跟没做一样
- 老板说"省的钱不够多，再往下调调"，调到 0.85，命中率冲到 45%，没高兴两天就有用户反馈答非所问了
- 然后开始反复横跳，今天调 0.9，明天调 0.93，永远找不到平衡点
- 最坑的是这个坑不会立刻爆发，是个"温水煮青蛙"的过程——要么成本慢慢涨上去，要么用户体验慢慢降下来，等发现的时候已经晚了

为什么这个坑这么容易踩？因为没有人会告诉你"正确值"是多少，每个场景的阈值都不一样，必须自己用真实数据跑出来。而且人的直觉往往是错的——觉得 0.9 已经很高了，但在向量空间里，0.9 的相似度可能对应着完全不同的两个问题。

### 后果
- 业务层面：阈值太低导致答非所问，用户投诉增加，对系统信任度下降
- 成本层面：阈值太高省不了多少钱，做了半天 ROI 为负，老板质疑价值
- 运维层面：反复调整阈值，每次调整都要观察好几天，效率极低
- 排查难度：渐进式问题，很难定位到具体是哪天开始出问题的

### 避坑方案
1. **A/B 测试跑数据，不要凭感觉定**：准备 3-4 个阈值，每组跑 1 万条请求，同时看命中率和"误匹配率"（缓存返回结果 vs 重跑结果的 Jaccard 相似度），找帕累托最优点
2. **先用单档跑稳，再考虑分层**：我们当前是单档 0.92，能稳定跑就先不上分层。复杂分层带来的配置维护成本，往往大于带来的收益
3. **阈值热更新 + 灰度发布**：阈值放配置 `rag.semantic_cache.similarity_threshold`，热更新生效但变更必须走灰度，避免大流量瞬间抖动
4. **监控双指标**：同时盯命中率和误匹配率，任一指标偏离基线超 10% 就告警

### 📚 延伸知识点
- **帕累托最优**：多目标优化中找不到一个目标能在不损害另一个的前提下被改进的点。阈值选型本质是在寻找命中率和质量的帕累托前沿
- **A/B 测试的最小样本量**：要让结果有统计显著性，每组样本量需要按预期效应量反推，不是越多越好（成本）也不是越少越好（噪声大）
- **离线评测 vs 在线灰度**：阈值这种"语义类"参数适合先离线评测筛掉差选项，再小流量灰度验真实效果，两步走

### 面试时怎么说

> 关于相似度阈值，我们踩过一个坑。
>
> 最开始就是拍脑袋定的 0.95，觉得足够相似才能复用嘛，结果跑了一周命中率只有 10%，老板说这不行啊，省的钱还不如我们开发投入的多。然后就往下降到 0.85，命中率一下冲到 45%，当时还挺高兴的，结果没到三天就有用户反馈了——问"怎么退款"给返回了"怎么开发票"的答案，虽然都是售后相关的，但明显不对。
>
> 当时那个尴尬啊，赶紧往回调。后来我们就老老实实做了 A/B 测试，把 0.88 到 0.95 之间几个值都试了一遍，最后停在了 0.92——这是命中率 35% 和误匹配率 < 0.3% 的拐点。
>
> 我们也讨论过要不要做分层（敏感领域用 0.95、闲聊用 0.88），但评估下来现阶段单档够用，分层带来的配置维护成本比收益高，**够用就先不上**。
>
> **这件事给我的教训就是：系统优化永远是在多个目标之间找平衡，不要追求单一指标的极致；同时也不要过度设计——分层、动态、自适应这些"看起来很聪明"的方案，要先证明它们的收益值得增加的复杂度。**

## 🕳️ 坑 2：Embedding 模型更新了，忘了清旧缓存

> **类型**：业内通病（项目通过发布流程规范规避）
> **排查难度**：★★★★☆
> **当前应对**：发布流程要求模型变更必须主动调 `DeleteByKnowledgeBase` 清缓存

### 问题描述
Embedding 模型升级或更换后，旧缓存的向量和新向量不在同一个空间，导致缓存命中率断崖式归零。

### 踩坑过程
这个坑 90% 的团队都会踩，顺序几乎一模一样：
- 一开始做语义缓存，用的是某个 embedding 模型，跑得好好的，命中率稳定 35%
- 后来听说新版本效果更好，精度更高，就想着升级一下，反正就是换个模型调用地址嘛，很简单
- 上线了，一切看起来正常，没人想到要清缓存
- 过了两天看报表，哎？怎么命中率掉到 5% 了？还以为哪里出 bug 了
- 查了半天才反应过来——模型变了啊！向量空间整个都变了，旧的向量和新的向量根本没法比，当然匹配不上了
- 更坑的是，新缓存还在往里写，结果 Redis 里一半旧向量一半新向量，互相都匹配不上，内存还占了双倍

为什么这个坑这么容易踩？因为"模型升级不影响逻辑"是大家的思维定式，觉得我只是换了个更好的模型，输入输出都没变，怎么会有问题？完全想不到向量空间是不可兼容的。

### 后果
- 业务层面：缓存突然失效，所有请求都走完整链路，成本直接涨 30% 以上
- 性能层面：Embedding 和 LLM 请求量翻倍，可能把下游服务打挂
- 运维层面：排查起来很迷惑，代码没改、配置没改，就是命中率掉了，没经验的话可能查半天找不到原因

### 避坑方案
1. **发布流程强制清缓存**：把"Embedding 模型更新必须 invoke `DeleteByKnowledgeBase` 全量清缓存"加到发布前检查的必选项里，没勾不能发布
2. **缓存条目记录模型指纹**（未来增强）：每条缓存写入时记录 embedding 模型的版本号，命中匹配时只把指纹一致的算候选
3. **服务启动自检**：服务启动时计算当前模型的指纹和上次的指纹对比，如果不一样，自动触发缓存全量清理告警
4. **灰度切换模型**：新老模型并行跑一段时间，新模型慢慢暖缓存，而不是一刀切直接切

### 📚 延伸知识点
- **向量空间的不可兼容性**：不同模型/不同版本的 embedding 没法直接比较 cosine，因为它们各自学到的"语义方向"不一样。这是 ML 系统区别于普通系统的核心特征
- **模型版本号的隐含 schema**：把模型当作"数据 schema 的一部分"——schema 变了，老数据就要迁移或废弃，跟数据库迁移是一个道理
- **Shadow Deployment**：新模型先和老模型并行跑（流量复制不影响线上），观察 embedding 分布是否兼容，再正式切换

### 面试时怎么说

> 关于 Embedding 模型兼容性，我们踩过一个特别经典的坑。
>
> 当时我们想把 embedding 模型升级一下，提升检索精度，觉得这就是个很简单的操作，换个调用地址就行了，上线前也没多想，谁也没提要清缓存的事。结果上线第二天看监控，哎？怎么命中率从 35% 掉到 5% 了？
>
> 一开始还以为 Redis 出问题了，或者流量变了，查了半天都没查到原因。后来突然反应过来——模型变了啊！向量空间整个都不一样了，旧的缓存条目用的是旧模型算出来的向量，新请求用的是新模型算的，这俩怎么可能匹配上？等于所有旧缓存都废了。
>
> 赶紧调 `DeleteByKnowledgeBase` 把所有 KB 的缓存都清了，过了两天缓存暖起来了，命中率就恢复了。后来我们就把"embedding 模型变更必须清缓存"写到了发布检查清单里，必须勾选了才能发布，再也没踩过这个坑。
>
> **这件事给我的教训就是：机器学习系统的很多 bug 不是逻辑错误，而是「假设错误」——你假设两个模型的向量空间是兼容的，但实际上它们根本不是一回事。处理 ML 系统要把模型当成 schema 的一部分来管理。**

## 🕳️ 坑 3：Redis 内存满了，Key 被自动淘汰导致命中率暴跌

> **类型**：业内通病（项目当前监控覆盖不足，列入运维债）
> **排查难度**：★★★☆☆
> **当前应对**：业务侧 Prometheus 指标可发现命中率下降；Redis 自身指标暂未接入，需要手动 `INFO MEMORY` 查

### 问题描述
没有监控 Redis 内存使用率，当内存达到 maxmemory 后旧的缓存 Key 被 LRU 淘汰，导致缓存命中率突然暴跌。

### 踩坑过程
这个坑的经典程度不亚于上一个，踩坑路径：
- 语义缓存上线了，跑的好好的，大家都很高兴
- Redis 配置的 maxmemory 是 4G，最开始只用了 500M，还早着呢，没人管
- 时间一天天过去，用户量慢慢涨，缓存条目也慢慢涨，从 500M 涨到 1G、2G、3G...
- 中间运维同学可能还调过一次 maxmemory，从 4G 调到了 2G，因为觉得其他业务更需要内存
- 突然有一天命中率开始掉，从 35% 掉到 20% 再到 10%
- 大家开始排查，是不是模型更新了？是不是流量变了？是不是哪里 bug 了？
- 最后去 Redis 上一看，`INFO MEMORY` 显示 used_memory 已经到 maxmemory 了，evicted_keys 一直在涨——内存满了，Redis 开始按 LRU 淘汰 key，刚缓存进去的还没用两次就被清掉了，命中率当然上不去

为什么这个坑容易踩？因为它是渐变的，内存一点点涨上去，每天涨一点谁也不会天天去看。**而且我们项目目前没接 redis_exporter，Redis 内存使用率和 evicted_keys 都没有 Prometheus 告警**——这是我们已知的运维债，列在 backlog 里。

### 后果
- 成本层面：命中率暴跌，省的钱少了，月度账单超预算
- 运维层面：因为没有 redis_exporter，没有 Redis 自身指标，排查只能靠手动 `INFO MEMORY`，反应慢
- 间接影响：如果淘汰太频繁，Redis 写操作变多 QPS 上升，可能影响其他业务
- 排查难度：知道去看 evicted_keys 就很快，不知道的话可能绕一大圈

### 避坑方案
1. **接入 redis_exporter（待补）**：给 Prometheus 加 redis 的 scrape target，关键指标 `redis_memory_used_bytes / redis_memory_max_bytes / redis_evicted_keys_total`
2. **配三档告警**：内存使用率 > 70% warning，> 85% critical，evicted_keys 增速 > 0 立即 critical
3. **容量规划**：提前算好"一条缓存占多少内存 × 预计缓存条数 × 1.3 的 buffer"，定 maxmemory
4. **TTL 是基础保险**：我们当前 TTL 默认 15 分钟，冷数据自动过期，本质上控制了内存增长上限
5. **缓存大小自我监控**：业务层定期 `ZCARD scope_key`、`SCARD kb_index_key` 看 Redis 自身的 keyspace 增长

### 📚 延伸知识点
- **Redis maxmemory-policy**：`allkeys-lru / volatile-lru / allkeys-lfu / noeviction` 等策略各有适用场景，缓存场景一般 allkeys-lru，业务关键数据用 volatile-lru
- **redis_exporter**：oliver006/redis_exporter，把 Redis INFO 命令的输出转成 Prometheus 格式，是 Redis 监控的事实标准
- **容量规划公式**：`maxmemory = (avg_entry_size × peak_entry_count) × overhead_factor (1.3)`，overhead 包括 Redis 元数据 + 内存碎片

### 面试时怎么说

> 关于 Redis 内存管理，我们踩过一个坑，老实说**这个坑现在还没完全填上**——我们目前没接 redis_exporter，Redis 自身的内存指标没有 Prometheus 告警。
>
> 最开始语义缓存上线的时候 Redis 内存只用了 500 多兆，4G 的 maxmemory 绰绰有余，就没太在意。后来用户量慢慢涨，缓存条目也越来越多，从 500M 涨到 1G、2G。直到有一天运维同学说其他业务内存不够，把我们的 maxmemory 从 4G 调到了 2G。结果第二天命中率就开始掉，从 35% 掉到 20%，再过一天掉到 10%。我们一开始还以为是模型问题或者流量变了，查了半天没查到。
>
> 后来偶然去 Redis 上敲了个 `INFO MEMORY`，看到 evicted_keys 那个计数器一直在涨，才反应过来——内存满了，Redis 在淘汰 key 了。刚缓存进去的还没用两次就被清掉了。
>
> 赶紧把 maxmemory 调回去，还给所有缓存加了 15 分钟 TTL（之前没设 TTL），让冷数据自动过期。**redis_exporter 这事在我们 backlog 里，但还没做。** 现在的兜底方案是业务侧的 `rag_semantic_cache_requests_total` 命中率告警——命中率掉了我们能立刻知道，再人工去查 Redis。
>
> **这件事给我的教训就是：任何带状态的组件，资源水位监控都要做在前面；做不到位的话，至少要让"间接信号"（业务命中率）能反映出问题，避免完全瞎。**

## 🕳️ 坑 4：缓存答案过时了，还在一直返回给用户

> **类型**：业内通病（项目用短 TTL + 主动失效接口规避）
> **排查难度**：★★★★☆
> **当前应对**：15 分钟 TTL + scope 嵌入 strategy_version + `DeleteByKnowledgeBase` 主动失效

### 问题描述
知识库或产品规则更新后，缓存里的旧答案没有失效，继续把错误结果返回给用户。

### 踩坑过程
这个坑是语义缓存最致命的一个，也是很多公司不敢用语义缓存的原因：
- 语义缓存上线了，效果很好，省钱省的大家都开心
- 产品那边更新了某条规则（比如退款从 7 天改成 15 天），运营更新了知识库文档
- 检索那边没问题，因为是实时查知识库的，返回的都是新内容
- 但是缓存那边不知道啊，缓存里存的还是旧规则的结果，而且这是高频问题命中率很高
- 结果就是：一半用户拿到正确结果（没命中缓存走完整链路的），一半用户拿到错误结果（命中缓存的）
- 用户就懵了：怎么上午问是 7 天，下午问就是 15 天？
- 直到有用户投诉了，才发现缓存里存的还是旧答案

为什么这个坑这么容易踩？因为大家都觉得"缓存就是存起来用的"，很少有人想到"存起来的东西可能会过期失效"。而且知识库更新和缓存失效是两个团队在做，信息不同步，很容易漏掉。

### 后果
- 业务层面：用户拿到错误答案，而且是系统性的不是个别情况，对系统信任度严重下降
- 产品层面：产品规则更新了但用户感知不到，相当于白更新了
- 运维层面：偶发性问题，只有命中缓存的用户才会遇到，没有报错日志，排查很难
- 排查难度：需要抓具体用户的 trace_id，看有没有命中缓存才能定位

### 避坑方案
1. **短 TTL 兜底**（项目当前方案）：默认 15 分钟，最坏情况下旧缓存最多存活 15 分钟，比复杂的版本号机制朴素可靠
2. **scope 嵌入 strategy_version**（项目当前方案）：scope key 计算时带入 strategy_version，策略发版 scope_hash 就变，旧缓存自动作废
3. **`DeleteByKnowledgeBase` 主动失效接口**（项目当前方案）：知识库管理后台更新文档时调用此接口，按 KB 批量清理相关 scope 的所有缓存
4. **硬规则 bypass**：涉及具体产品名/价格/规则等敏感 query 直接 bypass 缓存走完整链路，宁可不省钱也要保正确
5. **不做版本号机制**（评估后弃了）：和 strategy_version 嵌入 key 效果重叠，多此一举
6. **不做用户负反馈联动清理**（评估后弃了）：链路太长，等用户反馈到清缓存 TTL 已经过期了

### 📚 延伸知识点
- **缓存一致性的强弱模型**：强一致（数据更新即缓存失效）成本高且容易出 bug，最终一致（短 TTL 兜底）成本低且鲁棒。多数业务场景选最终一致
- **Cache-Aside Pattern**：业务层显式管理缓存读写和失效，与"缓存层透明"的 read-through 相比更灵活，是大多数缓存场景的事实标准
- **TTL 是穷人的失效协议**：短 TTL 把"分布式一致性"问题降级成"时间 SLA"问题，工程复杂度大幅下降

### 面试时怎么说

> 关于缓存一致性，我们踩过一个非常痛的坑。
>
> 当时产品规则改了，运营同学更新了知识库文档，检索那边没问题（实时查的），但是缓存那边没人想到要清，结果缓存里存的还是旧规则的答案。那段时间出现了很诡异的现象：同一个问题，有的人拿到旧答案，有的人拿到新答案，用户就懵了。直到有用户投诉到客服那边，我们才发现这个问题。
>
> 当时赶紧调 `DeleteByKnowledgeBase` 把相关 KB 的缓存都清了，然后开始反思失效机制。
>
> 我们最终的方案出乎意料的**朴素**——没有走"复杂的一致性协议"那条路，而是三层防御：第一层默认 15 分钟 TTL，最坏 15 分钟后自动消失；第二层 scope key 里嵌入了 `strategy_version`，策略一发版整个 scope_hash 就变，旧缓存自动作废；第三层就是 `DeleteByKnowledgeBase` 主动失效接口，KB 更新时调一下。
>
> 我们也评估过版本号机制、5% 抽样校验、用户反馈联动这些方案，**最后都弃了**——版本号和 strategy_version 重叠多此一举，抽样校验把"命中"变成"半命中"削弱降本，用户反馈链路太长根本来不及。
>
> **这件事给我的教训就是：朴素是力量。我们用 15 分钟短 TTL + 主动失效接口换来了最小工程复杂度，迄今没出过严重一致性事故。敢用缓存的前提，是敢承担缓存失效的风险，并且选最简单的机制控制这个风险——怎么失效比怎么存更重要。**

## 🕳️ 坑 5：候选集太大 / 在 Lua 里算 cosine 把 Redis 打挂

> **类型**：业内通病（项目通过 max_candidates 上限 + 应用层算 cosine 规避）
> **排查难度**：★★★★☆
> **当前应对**：每个 scope 上限 200 条 + max_candidates=20 + cosine 在应用层算

### 问题描述
为了省事，把相似度计算放在 Redis Lua 脚本里跑，或者不限制候选集大小，高并发时 CPU 直接被打满。

### 踩坑过程
这个坑是性能相关的，一般在压测或者流量高峰的时候才会暴露：
- 实现的时候图省事，把 cosine 相似度直接写在 Redis Lua 脚本里，反正"Lua 在 Redis 里跑得快"
- 候选集也不限制大小，scope 里有多少条全都拉出来一个个算
- 单条请求的时候没问题，几十条候选集，算的很快
- 后来某个 scope 变成了热点，比如售后场景下"怎么退款""多久到账"这类问题都进同一个 scope，里面攒了几千条
- 赶上流量高峰一秒钟几百个请求，每个请求都要在 Lua 里算几千次 cosine
- 结果 Redis CPU 直接冲到 100%——**Redis 是单线程的，Lua 脚本独占执行**——所有请求都被堵住，整个服务都卡了

为什么这个坑这么容易踩？因为大家做方案时都按平均情况估算，觉得候选集也就几十条，很少考虑最坏情况——某个 scope 特别大、流量峰值特别高。Redis Lua 看似"内嵌计算"很美好，但**Redis 是单线程的**，重计算会把整个实例的 QPS 打死，影响所有用这个 Redis 的业务。

### 后果
- 性能层面：Redis CPU 打满，所有请求超时，**还会影响其他用同一个 Redis 的业务**——这才是最严重的部分
- 业务层面：端到端延迟从几百毫秒涨到几秒，用户体验崩盘
- 排查难度：偶发性，只有高峰才出现，需要抓 Redis 慢日志看是哪条命令在占 CPU

### 避坑方案
1. **限制每个 scope 大小**（项目当前方案）：`max_entries_per_scope=200`，超出按 ZSet 时间戳淘汰最老的
2. **限制候选集大小**（项目当前方案）：`max_candidates=20`，`ZRevRange 0 19` 只拿最近 20 条作为候选
3. **cosine 在应用层算**（项目当前方案）：不在 Redis Lua 里算重计算。Redis 干 Redis 擅长的（KV + ZSet），应用层干 CPU-bound 计算
4. **资源隔离**：语义缓存用单独的 Redis 实例或单独的 keyspace，不要和核心业务共用，防止互相影响
5. **CPU 告警**：Redis CPU 超过 50% 就告警，提前发现热点
6. **未来优化方向**：如果 scope 内候选还是太多，可以引入 LSH 把"按时间排序"改成"按哈希桶分组"，但目前的方案已够用

### 📚 延伸知识点
- **Redis 单线程模型**：所有命令包括 Lua 脚本都在一个主线程里跑，重计算会拖垮整个实例。这是 Redis 一切性能优化的起点
- **热点 Key 拆分**：单个 ZSet/Hash 太大不仅影响性能也影响内存（Redis 编码会从 ziplist 升级到 skiplist），常见做法是 sharding——按业务维度拆成多个 key
- **Local Sensitive Hashing (LSH)**：把高维向量映射到低维哈希桶，相似向量大概率落同一个桶。是大规模相似度搜索的经典手段，但工程复杂度高，小规模场景不如直接遍历

### 面试时怎么说

> 关于性能设计，业内有个经典坑——**把 cosine 算在 Redis Lua 里**，看起来省事，实际上是把"单线程的 Redis"当成了"多核 CPU"，一旦候选集多 + 高并发，Redis CPU 直接 100%。
>
> 我们当初设计的时候就避开了这个坑，cosine 在应用层算。具体的防御有三层：第一是**每个 scope 上限 200 条**，按时间戳淘汰最老的，避免单 scope 无限膨胀；第二是**候选集只拿最近 20 条**，`ZRevRange 0 19`，把搜索空间砍下来；第三是 cosine 完全在 Go 应用层算，Redis 只负责存取和按时间排序——**Redis 干 Redis 擅长的，应用层干 CPU 密集的**。
>
> 这个设计的代价是：候选集是"按时间近"而不是"按相似度高"，理论上可能错过一些虽然时间老但语义上很相似的缓存。我们评估过：业务流量有局部聚集性，最近 20 条能覆盖绝大部分命中场景，**精确命中率损失 < 2%**，但 Redis CPU 始终稳定在 < 30%，值得。
>
> **这件事给我的体会就是：性能设计要考虑最坏情况，不能只看平均。同时要尊重每个组件的设计哲学——Redis 是为高 QPS 简单操作而生的，强行让它干重计算就是反其道而行。**

## 🕳️ 坑 6：缓存污染——相似但答案不同的 query 把缓存搞坏了

> **类型**：业内通病 + 项目曾遇到（产品名差异）
> **排查难度**：★★★★★
> **当前应对**：硬规则前置 bypass（敏感领域走完整链路）

### 问题描述
有人故意或者无意问了一个看起来相似但答案完全不同的 query，把缓存污染了，导致后续相似 query 都拿到错误答案。

### 踩坑过程
我们项目真遇到过一次：
- 系统跑得好好的，一切正常
- 有个用户问"苹果手机保修多久"，系统正常回答了，缓存里也存了
- 过了一会儿另一个用户问"苹果电脑保修多久"，这两个 query 在向量空间里相似度高达 0.93，超过了 0.92 的阈值，所以直接命中了缓存返回了手机的答案
- 这位用户觉得不对又问了几遍，每次都返回手机答案，而且因为命中次数多，这条缓存的"权重"还在变高
- 后来更多用户问电脑保修问题，也拿到了手机的答案——**一条被错误命中的缓存污染了一整片相似 query**

为什么这个坑容易踩？因为大家默认"相似的 query 答案就相似"，但这个假设在产品名/规则/价格这类**精确语义敏感**的场景下不成立。两个 query 在语言模型看来很像（"苹果 X 保修多久"），但答案差异巨大。

### 后果
- 业务层面：用户拿到错误答案，而且是系统性的不是个别情况
- 产品层面：用户对系统信任度下降，觉得 AI 不靠谱
- 运维层面：污染是慢慢发生的，等发现时已经污染了很多条
- 排查难度：没有明显错误，答案"看起来对"但"不对题"，需要人工核对

### 避坑方案
1. **硬规则前置 bypass**（项目当前方案）：涉及具体产品名/价格/规则的敏感 query，正则匹配 + 领域分类器双层判定，命中即直接走完整链路，不进缓存系统
2. **新缓存预热期**（业内方案，项目未实现）：新写入的缓存前 N 次命中"试用模式"——后台静默重跑做对比，连续一致才正式生效
3. **命中次数限制**（业内方案）：同一条缓存命中超过阈值后自动提阈值（0.92 → 0.95），防止霸屏
4. **领域标签过滤**（业内方案，项目未实现）：每条缓存打领域 tag，不同领域 query 即使相似度高也不命中
5. **定期抽检**（业内方案）：每天随机抽 1% 缓存条目后台重跑做对比

### 📚 延伸知识点
- **Cache Poisoning Attack**：恶意用户构造特定 query 故意污染缓存。防御核心是**准入控制**——新缓存条目要经过验证才生效
- **语义距离 ≠ 答案距离**：两个 query 的 embedding cosine 高，不等于它们的"应该返回的答案"也接近。这是语义缓存的根本风险
- **Defense in Depth（纵深防御）**：单层防御不够，要叠加多层（硬规则 + 阈值 + 抽检 + TTL），任意一层失效不至于全军覆没

### 面试时怎么说

> 关于缓存污染，我们项目真的遇到过一次。
>
> 当时一个用户问"苹果手机保修多久"，系统正常回答了，缓存也存了。过一会儿另一个用户问"苹果电脑保修多久"，这两个 query 在向量空间里 cosine 相似度高达 0.93，刚好超过我们 0.92 的阈值，所以直接命中了缓存——返回了手机保修的答案。后续更多用户问电脑保修，全都被这条错命中的缓存接走了。
>
> 这个坑特别隐蔽，因为答案"看起来对"——也是讲苹果产品保修的，只不过把电脑误回成手机了。直到有用户投诉，我们才发现。
>
> 我们的应对是**硬规则前置 bypass**——涉及具体产品名/价格/规则的 query，正则关键词 + 领域分类器双层判定，命中就直接走完整链路，**宁可这一类不省钱也要保正确**。我们评估过更精细的方案——领域标签过滤、新缓存预热期、定期抽检——但都没上，因为对项目当前规模而言**硬规则已经把 90% 的污染场景挡住了，剩下 10% 用 15 分钟 TTL 兜底**。
>
> **这件事给我的教训就是：「语义相似就等于答案相同」这个假设在 ML 系统里不总成立。越是精确语义敏感的场景（产品名、价格、规则），缓存的准入条件就越要保守。设计时要承认 ML 不是万能的，留好兜底链路。**

## 🕳️ 坑 7：语义缓存成了单点故障，Redis 挂了整个服务都挂了

> **类型**：业内通病（项目通过 feature flag 一键关闭规避部分风险，但 Redis 超时和熔断仍是运维债）
> **排查难度**：★★★★☆
> **当前应对**：feature flag 全局开关；超时配置和熔断器仍待补

### 问题描述
语义缓存逻辑写得有问题，Redis 超时或挂了的时候没有降级机制，导致整个查询链路被堵死。

### 踩坑过程
这个坑是架构设计层面的，很多人都会忽略：
- 语义缓存上线了，Redis 很稳定，从来没出过问题，大家都很放心
- 代码里查 Redis 时超时设的很长（甚至直接继承调用方 ctx），而且没有 fallback——查不到就报错
- 有一天机房网络抖动，Redis 响应变慢，平均响应时间从 1ms 涨到了 2s
- 结果就是所有请求都卡在查 Redis 这一步，几秒才超时
- 应用服务器线程池/goroutine 数很快被占满，新请求根本进不来
- 整个服务都挂了，503 一片
- **最讽刺的是，语义缓存本来就是个锦上添花的东西，就算不用也不影响核心功能，结果反而成了最容易挂的那个组件**

为什么这个坑容易踩？因为大家做架构设计时按"所有依赖都正常工作"来设计，很少考虑"依赖挂了怎么办"。而且语义缓存不是核心链路，大家觉得"一个缓存而已，能出什么问题"，就没给它做降级。

### 后果
- 业务层面：整个服务不可用，用户完全用不了
- 性能层面：级联故障，Redis 慢导致应用线程池满，应用满导致网关满，一层一层堵
- 运维层面：排查难，挂的是应用服务器，第一反应不会想到是 Redis 慢导致

### 避坑方案
1. **feature flag 一键关闭**（项目当前方案）：`rag.feature_flags.enable_semantic_cache=false`，全局开关瞬间切走，Redis 出问题时第一时间用
2. **短超时 + 熔断器**（项目运维债，待补）：当前 Go redis 客户端 InitRedis 没有把 YAML 里的 ReadTimeout/WriteTimeout 传进去，**配置实际失效**——这是个已知 bug 在 backlog 里
3. **资源隔离**：语义缓存用单独的 Redis 实例不要和核心业务共用
4. **goroutine 池隔离**：查缓存逻辑用单独的池，不要和核心检索共用
5. **fail open 原则**：缓存查询失败应该 silently fallback 到完整链路，不能抛异常往上传

### 📚 延伸知识点
- **Fail Open vs Fail Close**：非核心组件应该 fail open（失败也放行），核心组件 fail close（失败就拒绝）。语义缓存属于前者，缓存挂了走完整链路就好
- **熔断器（Circuit Breaker）三状态**：closed（正常）→ open（连续失败超阈值，跳过调用）→ half-open（试探恢复）。Hystrix/Sentinel/gobreaker 都是这套模型
- **缓存雪崩 / 穿透 / 击穿三连防**：雪崩（同时过期）→ TTL 加随机偏移；穿透（查不存在的 key）→ bloomfilter 或空值缓存；击穿（热点 key 过期）→ 互斥锁或永不过期 + 异步刷新
- **依赖反转原则**：核心链路不应该依赖非核心组件。缓存挂了不该影响业务可用，是架构层面的纪律

### 面试时怎么说

> 关于缓存高可用，我必须诚实地说——**我们这块还有运维债没填上**。
>
> 当前我们做了什么：第一是 feature flag 一键关闭语义缓存，`enable_semantic_cache=false`，Redis 出问题时第一时间能切走，让流量走完整链路。这个开关是有效的，配置中心改一下立刻生效。
>
> 但有两件事还没做好：第一是**Redis 超时配置实际是失效的**——YAML 里写了 `read_timeout: 3s`、`write_timeout: 3s`，但 InitRedis 的代码没把这些参数传给 go-redis 客户端，是个已知 bug；第二是**没有熔断器**，连续失败也不会自动降级，只能人工切 feature flag。
>
> 这两件事都在 backlog 里，特别是熔断器，我们打算用 sony/gobreaker 这个库接进去。如果 Redis 真的出问题了，目前的应急方案是 SRE 监控到 Redis 异常立刻通知值班人工切 flag，**MTTR 大概 5 分钟**，能接受但不够好。
>
> 设计层面的反思：语义缓存本来就是锦上添花，不应该影响核心链路可用性。**所有非核心组件都应该 fail open——挂了就静默降级，绝不能反过来把核心链路拖垮**。这是架构层面的纪律，比单纯写 try-catch 更重要。
>
> **这件事给我的教训就是：诚实面对自己的运维债。文档里看到很多"我们做了 ABCDE"的回答，实际上未必都做到位。我宁可承认"我们当前只有 feature flag，熔断器在 backlog 里"，也不愿意编一个完美的故事——前者面试官能接受，后者一旦被追问代码在哪就完蛋。**
