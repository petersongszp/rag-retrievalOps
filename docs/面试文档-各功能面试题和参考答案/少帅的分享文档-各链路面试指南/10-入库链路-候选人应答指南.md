## 入门叙事：入库链路看起来简单，实际有哪些坑？

入库这件事，外行听到的版本是："上传文件 → 切片 → embedding → 存进向量库"。短短一句话。
但真正做过的人都知道，这条链路上有 6 个看似无关、其实都会让你"看似跑通了但效果烂得离谱"的坑：

**坑 1：解析这一步，就足够把单测 Demo 和企业级系统拉开两个数量级。**
本地 Markdown 看着特别美好，丢一个扫描版合同 PDF 进去，立刻发现 80% 的内容根本读不出来；OCR 出来一堆乱码、表格解析成一行一行散文。所以项目把解析单独抽成 `parser-provider` 进程跑 Docling，前面挂一层 `documentparser.Provider` 抽象，PDF/DOCX/HTML 走 HTTP，本地 md/txt 走 in-process。这是适配器模式的真实落地。

**坑 2：切分一刀切，效果一定差。**
Markdown 文档要按标题切，含表格的文档表格必须独立成 chunk，扫描版 PDF 要按 OCR 置信度做降权，含版面 block 的 docx/html 要按 block 窗口聚合。所以项目设计了 `StrategyRouter`，按文档特征选 4 种策略中的一种，再叠 OCR-Aware / Table-Aware 装饰器。

**坑 3：检索粒度和 LLM 输入粒度天然冲突。**
Embedding 喜欢 200~500 字的小块（语义集中），但 LLM 拼 prompt 时最好给它一段 1500~3000 字的完整上下文。所以项目用父子块——子块进 Milvus 做向量召回，父块通过 `parent_id / parent_start_offset / parent_end_offset` 关联，检索完再用父块拼 prompt。

**坑 4：Embedding 缓存放错地方比不放还糟。**
入库时缓存 embedding 是浪费内存（每段 chunk 都不一样），查询时缓存才有意义（用户 query 高频重复）。项目里 `EmbeddingService` 暴露 `embedder` 和 `queryEmbedder` 两个出口，写入用前者、查询用后者，后者挂了一层带 singleflight 的 TTL+LRU 缓存。

**坑 5：异步消费的可靠性，不在 Stream 上，而在业务表上。**
Redis Stream 的 PEL 重投机制运维成本高、粒度粗。项目里 Stream 只承担"分发"，业务表 `kb_ingest_job` 才是真相之源——7 状态状态机 + 错误码分类 + 指数退避补偿器，一切重试逻辑都跑在 MySQL 这边。

**坑 6：失败要"区分而不是合并"。**
"不可重试错误（解析失败、payload 不合法）" 必须和 "可重试错误（embedding 超时、网络抖动）" 严格分流。前者直接进 `failed`，后者进 `retrying`；超过最大重试次数再进 `dead`，由人工 review。

把这 6 个坑讲清楚，面试官基本就知道你做过真东西。

## Q1 ⭐：完整入库链路

### 基础回答（先把版本控制在 90 秒内）

"用户上传 PDF 之后，整条链路分三段。

**第一段是上传同步段**：rag-server 收到请求，把文件落盘，写一条 `kb_document` 和一条 `kb_ingest_job`，状态都是 pending；然后向 Redis Stream `interview:stream:knowledge_ingest` 投递一条入库消息，包含 `job_id / document_id / kb_id / file_path / file_type`，HTTP 接口立刻返回。

**第二段是异步消费段**：消费者从 Stream 读到消息后做这几步——
1. `ClaimForProcessing` 把 job 从 pending 翻到 processing，避免并发认领；
2. 根据文件类型分流解析：md/txt 走本地 `NormalizeLocal`，pdf/docx/html 走 HTTP `Provider` 调 parser-provider；
3. `canonical.Normalize` 做 Unicode 清洗、噪声去除、标题修复、表格 span 重锚，写 `*.normalized.json` sidecar 留痕；
4. `StrategyRouter` 把规范化后的 NormalizedDocument 路由到 4 种切分策略之一；
5. `finalizeChunks` 给每个 chunk 补上父子块、blockIDs、tableIDs 等溯源元数据。

**第三段是 Milvus 落库段**：`IndexerService.Store` 调 EmbeddingService 出向量，再把 `(id, content, vector, metadata)` 写 Milvus；写入成功后 job 切到 completed、document 切到 completed。

任何一步失败都会被分类为 `payload / parse / embedding / milvus / unknown` 五类错误码，可重试的进 retrying，超过 3 次进 dead。"

### 亮点细节（追问时的加分项）

- **同步异步边界为什么放在投递 Stream 那里**：放更前 HTTP 会被 LB 超时切；放更后 CPU 密集型工作还是堵在同步链路。当前边界只做"轻量元数据 + 一条消息"，HTTP 亚秒级返回。
- **为什么要 KBIngestJob 这张表**：document 表的 status 是粗粒度展示态，job 表是细粒度任务态——`retry_count / next_retry_at / last_error_code` 这些字段是补偿和审计的基础；任务表还能支撑"同一个文档多次入库"的历史留痕。
- **代码定位**（被追问时直接 cite 文件路径）：消费总入口在 `consumer.go:HandleKnowledgeIngest`，编排在 `ingestKnowledgeDocument`，解析在 `extractNormalizedKnowledgeDocument`。

## Q2 ⭐：为什么要异步

### 基础回答

"主要 4 个理由：

1. **解析耗时不可控**：Docling 解扫描 PDF 几十秒到几分钟，HTTP 同步等不起；
2. **资源隔离**：解析、Embedding 是 CPU/IO 密集型，混在 web worker 会拖垮检索接口的 P99；
3. **可重试 / 可补偿**：异步任务天然可以失败重投，重试逻辑独立于 HTTP；
4. **削峰填谷**：批量上传 100 个文档同步处理会瞬间打爆 Embedding 限流；进 Stream 后由 ants 1000 并发池匀速消费。

实现上：Stream key 是 `interview:stream:knowledge_ingest`，`MaxLen=10000 + Approx=true` 防止无限增长；消费者用 `panjf2000/ants` 池子限制最大并发；处理成功才 XAck，失败仅打日志（让业务表层补偿器接管重试）。"

### 亮点细节

- **为什么用 Redis Stream 不用 Kafka**：项目本身就在用 Redis 做缓存，零运维成本引入 Stream；消息量级（每天百万级）远没到需要 Kafka 的水平；MySQL 轮询会有惊群和锁竞争，Stream 消费组天然解决。
- **池子开 1000 并不意味着真的同时 1000 并发**：实际上下游 Embedding API 的限流（DashScope 默认 batch=10）和 Milvus 写入吞吐才是瓶颈，开太大反而 P95 飙升。
- **失败不 ack 是有意为之**：让业务表 + 补偿器控制重试节奏，而不是依赖 Stream 自己的 redelivery，这样可以做差异化退避（5xx 用指数退避，业务错误直接 fail）。

## Q3 ⭐：parser-provider 适配器模式

### 基础回答

"PDF/DOCX 的高质量解析（带表格识别、OCR、版面分析）目前最强的是 Python 生态——Docling、PaddleOCR、unstructured，Go 这边没有同级别替代品。在 Go 里 cgo 调 Python 又是 GIL、依赖打包的雷区，所以项目把解析进程化、HTTP 化。

整个适配器模式分三层：

- 主进程定义 `documentparser.Provider` 抽象接口，只暴露 `Parse(ctx, ProviderRequest) (*NormalizedDocument, error)`；
- 默认实现 `HTTPProvider` 用 multipart 把 file + file_type + options POST 给 parser-provider 的 `/parse`；
- parser-provider 是独立 Go 二进制（`cmd/parser-provider/main.go`），内部 `DoclingClient` 把请求翻译成 Docling Serve 协议（`to_formats=md,json` + `image_export_mode=placeholder` + 一堆 `pdf_backend / table_mode / ocr_*` 选项），把响应翻成项目自己的 `NormalizedDocument`。

好处有 4 个：可替换（明天换 unstructured 只写新 Parser 实现）、进程隔离（解析崩了不拖垮主服务）、横向扩展（无状态 HTTP 服务）、协议清晰（multipart 契约便于多语言混搭）。"

### 亮点细节

- **`NormalizedDocument` 是格式无关的中间表示**：包含 `ContentMarkdown`（下游切分只认这个字段）、`Blocks/Tables`（带偏移量的结构信息）、`Quality/Extractor/Canonicalization`（审计版本和指纹）。所有格式在 parser 这一层就被对齐到同一数据结构——这是适配器的精髓。
- **multipart vs base64 JSON**：大 PDF 走 base64 内存膨胀 33%，对 GC 不友好；multipart 是流式的。这是行业惯例（OpenAI / Docling 都这么做）。
- **超时分层**：HTTPProvider 默认 60s，Docling 一层默认 120s——分层设计是为了让外层先超时返回，避免内层卡死撑爆 goroutine。
- **错误体设计**：`ProviderError` 带 `Code/Message/Stage/Page/Retryable`，retryable 字段决定上层是否进入重试链路，比裸 string 错误更容易做策略路由。

## Q4 ⭐：canonical.Normalize 在做什么

### 基础回答

"`canonical.Normalize` 是把"解析器输出"再做一次确定性归一化——让所有来源（不同 PDF backend、不同 Docling 版本、本地 Markdown）汇聚到同一种 Markdown 形态再进切分。具体做 5 件事：

1. Unicode + 行尾清洗（CRLF → LF、全角空格 → 半角、不可见字符过滤）；
2. 解析噪声去除（水印行、页眉页脚残留、`[image]` 占位）；
3. 标题修复（破碎标题合并、伪标题识别）；
4. 空行收敛（≥3 个换行 → 2 个）；
5. 表格 span 重锚（重新渲染表格 + 重算 MarkdownStart/End）。

输出包含 `ContentMarkdownRaw`（原始）+ `ContentMarkdown`（清洗后）+ `Canonicalization.RawSHA1/CanonicalSHA1`（双指纹）。

不能跳过的原因：切分策略和检索阶段都假设"标题层级干净、表格 span 准确"，跳过这一步会让 Markdown 结构切分把伪标题切成一堆小块，表格 chunk 偏移错位、父子块定位失败。"

### 亮点细节

- **NormalizerVersion 和 canonical.Version 分开**：前者标识整个 normalize 流程版本，后者标识具体规范化器版本——事后排查"为什么这份文档现在切出来的 chunk 数和上个月不一样"时，这两个字段是关键证据。
- **AppliedRules 字段**：记录真正命中的规则名（`unicode-whitespace / parser-noise / heading-cleanup / heading-continuation-merge / table-span-rebase`），可以批量统计哪些规则使用率高、哪些从未触发，给规则集演进提供数据依据。
- **RawSHA1 + CanonicalSHA1 双指纹**：前者用于检测"同一份文件不同时间解析结果是否漂移"，后者用于检测"规范化逻辑是否变更"。两个指纹同时变化大概率是规范化版本升级，只 RawSHA1 变就是解析器输出漂移。

## Q5 ⭐：4 种切分策略 + 路由

### 基础回答

"路由器 `StrategyRouter` 持有 default 和一组 `RoutedStrategy{Name, Match, Strategy}`，按顺序匹配 Match，第一个匹配的策略接管切分，所有 chunk 打上 `chunking_route` 元数据标签。

4 种 Match：
- **OCR-Aware**：file_type=pdf 且 quality.warnings 含 `ocr` 或 block 有 confidence；
- **Table-Aware**：`len(doc.Tables) > 0`；
- **Structure-Aware**：有 blocks 且类型是 docx/pdf/html；
- **默认 Markdown**：其他。

为什么不用单一策略：
- 扫描合同要按 block 窗口切并标低置信度，Markdown 技术文档要按 `##` 标题切；
- 表格按字符长度切会把表头表体分到两个 chunk，必须按表为单位独立切；
- 单一策略要么粒度过粗要么把表格/标题切碎，检索质量直接崩。

具体切法：
- **MarkdownStrategy**：goldmark AST 找标题切 sections，section 太长按 1000B 二次切，无标题时回落到 eino recursive splitter；
- **StructureAwareStrategy**：以 NormalizedBlock 为最小单元做窗口聚合，超过 1000B 就 flush；
- **TableAwareStrategy**：装饰器——先委托默认策略切普通文本，再为每张表生成专用 chunk（含 Markdown 表格 + `headers: values` 行格式）；
- **OCRAwareStrategy**：装饰器——委托后给每个 chunk 算 span 内 block 平均 confidence，低于 0.8 打 `weak_evidence=true`。"

### 亮点细节

- **Match 顺序很重要**：OCR-Aware 必须在 Table-Aware 前面，否则一份"扫描版+含表格"的 PDF 错过 OCR 标注链路。这是个真实的策略耦合问题。
- **装饰器组合**：TableAware 内部如果检测到 OCR 信号也会主动调 `annotateOCRQuality`，保证表格 chunk 不会因为路由没选 OCR-Aware 就丢掉置信度信息——这是策略编排的鲁棒性设计。
- **finalizeChunks 是统一兜底层**：所有策略切完后再跑一遍 finalizeChunks，给 chunk 补 chunk_index、parent_id、normalized_path、hierarchy_path 等元数据，确保下游看到的 chunk 字段是齐的、不依赖某个具体策略。

## Q6 ⭐：父子块切分

### 基础回答

"父子块解决的是 Embedding 检索粒度（200~500 字最佳）和 LLM 上下文粒度（1500~3000 字最佳）冲突的问题。

设计思路：真正进 Milvus、参与向量检索的是子块（粒度小、Embedding 精准）；同时给每个子块挂一个父块的指针，父块是更大的语义单元（heading_section / heading_section_window / paragraph_window / table），用于检索后拼 prompt 时"以父代子"补充上下文。

项目里有两套实现：
1. **eino splitter 内部** 的 `annotateSplitChunks`：当 Markdown 策略 fallback 到 eino recursive splitter 时，按"包含子块的最小父块"原则挂父；
2. **chunking 层的 finalizeChunks**：所有策略切完后再跑一遍，根据 chunk 的 child_start/end_offset 找到对应的 heading section，构造 parent_id / parent_start_offset / parent_end_offset / hierarchy_path 写入元数据，版本号 `phase3-parent-child-v1`。

关键元数据：`chunk_id / child_id / child_start_offset / child_end_offset / parent_id / parent_start_offset / parent_end_offset / parent_build_strategy / parent_truncated / hierarchy_path / section_title`。"

### 亮点细节

- **父块 ID 生成是幂等的**：`{documentKey}-parent-{shortHash(hierarchyPath:start:end)}-{idx}`，documentKey 优先用 document_id（业务键），其次 file_name + content shortHash。同一份文档反复入库 ID 稳定，方便增量更新。
- **检索阶段的用法**：召回拿到 child 后按 `metadata.parent_id` 反查 / 或者直接用 `parent_start_offset/end_offset` 截原 Markdown，把同父子块聚合 + 上下文补全。
- **退化场景**：当 chunking_unit=table 时父块直接等于子块（表格本身是独立语义单元，没有更大的父）；当文档完全没标题时，父块退化成 paragraph_window 切出的较大段。
- **parent_truncated 字段**：标记父块是否超过 defaultStructuredChunkBytes（1000B）阈值——评测时可以用这个字段过滤"父块被强切过"的低质样本。

## Q7 ⭐：Embedding 服务封装

### 基础回答

"`EmbeddingService` 是个薄壳，叠了 3 层增强：

1. **Provider 抽象 + 多家适配**：配置 `provider=ark/openai/mock` 选底层 embedder。ark 支持火山引擎 text/multi-modal；openai 是兼容协议（DashScope/智谱/千帆都走这条路）；mock 是确定性 hash 向量，给单测和离线评测用。
2. **batchingEmbedder 自动分批**：DashScope 这类有"单次最多 10 条"限制的 API，自动按 BatchSize 拆。`provider=openai && BaseURL 含 dashscope.aliyuncs.com` 时强制 10。返回向量数和入参数不一致直接报错（避免静默错位）。
3. **双 embedder 出口**：`embedder` 给写入用（无缓存）、`queryEmbedder` 给检索用（可选挂内存缓存）。

为什么写入不缓存：写入文本是 chunk 内容，每段都不一样，缓存命中率近乎 0；写入是一次性消费——同一份文档不会反复 embed。真正能复用的是用户 query 在短窗口重复，那是查询链路的事。"

### 亮点细节

- **mock embedder 的真实价值**：CI 单测稳定性（不依赖外部 API）、离线评测加速（只想测 chunk 召回结构时不用真 embedding）。`buildMockEmbedding` 用 FNV hash + sin/cos 生成确定性向量，结果可复现。
- **批量失败的处理策略**：单批失败 → 整 EmbedBatch 失败 → 错误码归类为 embedding_error → 进重试链路。没做"批内部分失败"的精细化补偿——大模型 API 通常是整批 429/5xx，不会真的"成功一半"。
- **数据类型转换的隐藏点**：底层 embedding 库返回 `[][]float64`，写入 Milvus 时在 `FloatVectorDocumentConverter` 里转成 `[]float32` 节省 50% 存储。这种"只在最后一步降精度"的设计避免了中间精度丢失。

## Q8 ⭐：Embedding 缓存设计

### 基础回答

"`cachedQueryEmbedder` 是包在底层 embedder 上的进程内缓存层，4 个关键设计：

1. **缓存键 = 单条 query 的 trim 结果**：只对 `len(texts)==1` 走缓存（对应'一条 query → 一个向量'）；多文本 batch 直接绕过（batch_bypass）；key 是 `strings.TrimSpace(texts[0])`，保留大小写和中间空格。隐含约束：缓存语义和模型版本绑定，切模型必须新建 embedder 实例。
2. **TTL + LRU 双重淘汰**：每 entry 有 expiresAt + lastAccess；get 时过期直接删；put 后 pruneLocked 先删过期再按 lastAccess LRU。
3. **singleflight 收敛并发**：同一 normalized query 同一时刻只调一次底层 embedder，其余并发请求等同一个结果，trace 标 `singleflight_shared`。
4. **trace 钩子**：`WithEmbeddingCacheTrace(ctx)` + `ConsumeEmbeddingCacheTrace(ctx)` 拿到 `{Enabled, Hit, LookupMs, Reason}`，Reason 枚举包含 hit/miss/singleflight_shared/batch_bypass 等，检索链路可以把这个 trace 写到检索日志，事后能解释每次 embedding 是怎么来的。"

### 亮点细节

- **get 用写锁不用读锁是个被改过的 bug**：之前 RLock 读 + Lock 写两步式更新 lastAccess，两步之间另一个 goroutine 的 put 可能让旧 entry 覆盖新 entry，下次命中拿到陈旧向量。改成全程写锁是 TOCTOU 修复。代码注释也明确写了。
- **向量返回前必须复制**：`append([]float64(nil), entry.vector...)`——如果直接返回 slice，调用方原地修改会污染缓存。768/1024 维向量复制成本几个微秒，可接受。
- **为什么不用 Redis 共享缓存**：进程内零网络开销、零序列化、亚毫秒命中；当前 query 重复率已经很高，命中率上去了，多副本缓存不命中的边际损失不大。Redis 共享缓存方案的真正价值是"模型版本+文本 hash"持久化，但当前还没到那个临界点。

## Q9：Milvus schema + Sparse 写入

### 基础回答

"写入 schema 4 个字段：`id (VARCHAR, primary)`、`vector (FloatVector, 动态 dim)`、`content (VARCHAR, max 4096)`、`metadata (JSON)`，度量类型 COSINE。

用 FloatVector 而不是 SDK 默认 BinaryVector，是因为现代 sentence-embedding 都是浮点向量（768/1024/1536/3072 维），二值化损失精度；HNSW/IVF_FLAT 等高效索引也是为浮点设计。`FloatVectorDocumentConverter` 把 `[]float64` 转 `[]float32` 节省 50% 存储，metadata 用 sonic.Marshal 成 JSON 字节，里面装 kb_id / document_id / chunk_id / parent_id / hierarchy_path / chunking_strategy / block_ids / table_ids 等所有过滤和上下文恢复需要的字段。

Sparse 向量在写入侧没有显式字段——content 字段就是原始可读文本。Sparse 检索是查询侧基于倒排索引/BM25 实时计算的（`SparseRetriever`），不需要写入时构建。代价是 sparse 检索路径需要先用 dense 召回粗筛 candidates 再 BM25 精排。"

### 亮点细节

- **metadata 用 JSON 不展开成 typed 字段的取舍**：Milvus 2.x 支持对 JSON 做 `metadata["kb_id"] == 123` 的表达式过滤；展开成 typed 字段每加一个元数据都要改 collection schema 迁数据，演进成本高。JSON 的反序列化开销在读侧本来就要做，整体可控。
- **多租户隔离 = 一 KB 一 collection**：`resolveKnowledgeBaseCollectionForIngest` 决定 collection 名，优先用 `kb.vector_collection`，没有就用 `DefaultKnowledgeBaseCollectionName(kbID)`。删 KB 直接 drop collection。`manager.NewIndexerServiceForCollection(ctx, collection)` 按 collection 动态建 indexer。
- **Sparse 写入侧不存的代价是查询侧的复杂度**：得先做 dense 召回再倒排精排，候选集质量影响最终分数。这是个有意识的 trade-off——简化 schema 演进，把复杂度推到查询侧。

## Q10 ⭐：状态机

### 基础回答

"状态机定义在 `kb_ingest_job.go` 的 `kbIngestJobTransitions` 表里，7 个状态、转换关系是：

- pending → processing | failed | canceled
- processing → completed | failed | retrying | canceled
- failed → retrying | dead | canceled
- retrying → processing | failed | dead | canceled
- dead → retrying（人工干预）
- completed / canceled 是终态

各状态语义：pending = 已投递等待认领；processing = 消费者已 claim；completed = 全成功可被检索；failed = 暂时失败但还没决定要不要重试；retrying = 失败可重试，等补偿器重投；dead = 重试用尽人工 review；canceled = 用户主动取消。

关键转换实现：
- `ClaimForProcessing`：pending|retrying → processing，乐观并发（`UPDATE WHERE id=? AND status IN (...)`）保证不重复消费；
- `UpdateFailureState`：写错误信息 + 可选 retry_count+1；
- `MarkPendingForRetry`：补偿器从 retrying 集合捞到期任务时使用；
- 任何非法转换返回 `ErrInvalidKBIngestJobTransition`。"

### 亮点细节

- **failed 和 dead 分开是有意义的**：failed 是中间态——发生失败后下一轮才决定进 retrying 还是 dead；dead 是终态——补偿器不会再扫，避免反复浪费重试预算。监控告警也能区分"自动重试用尽"和"人工放弃"。
- **乐观锁比分布式锁更合适**：多副本消费者并发认领同一 job 时，只有一个 UPDATE 改到行（RowsAffected==1），其他 RowsAffected==0 自动放弃。比 Redis SETNX 更朴素可靠，零额外依赖。
- **document 和 job 状态同步规则**：document 只有 4 状态（pending/processing/completed/failed），job 7 状态映射到 document 的简化态——retrying/dead 都映射到 failed（管理后台用户不需要区分）。最终一致性，不强求事务。

## Q11 ⭐：失败重试链路

### 基础回答

"错误分 5 类：
- `invalid_payload`（消息格式错）→ 不可重试；
- `parse_error`（PDF 损坏/格式不支持）→ 不可重试；
- `embedding_error`（Embedding 服务异常）→ 仅瞬时信号才重试；
- `milvus_write_error`（Milvus 写入失败）→ 仅瞬时信号才重试；
- `unknown_error` → 仅瞬时信号才重试。

瞬时信号判断：错误消息命中 `timeout / deadline exceeded / temporarily unavailable / connection reset / connection refused / broken pipe / eof / i/o timeout / network` 才算可重试——白名单匹配比黑名单安全。

退避公式：`delay = base * 2^(retry_count-1) * jitter`，base 默认 500ms，jitter 是 0.8~1.2 之间随机，上限 5 分钟，最低 1 秒。指数退避 + 抖动避免雷暴。

补偿器是独立 goroutine，每 5~30s 扫一次 `status=retrying AND next_retry_at <= now`，`MarkPendingForRetry` claim 任务，再 `PublishKnowledgeIngest` 重投。投递失败时刻意保持 retrying 状态而不是切到 failed——避免任务卡死无人重试，注释里明确说了这是数据丢失级 bug 修复。"

### 亮点细节

- **关键字匹配虽然 hack 但务实**：底层错误来自 Go HTTP / Milvus SDK / Embedding SDK 多个库，没有统一的 `errors.Is(ErrTransient)` 接口。白名单匹配的最坏情况是"应该重试的没重试"，比"不该重试的反复重试"安全。长期改进方向是各 SDK 适配层包装自定义错误类型再用 `errors.As`。
- **Stream redelivery vs 业务表重试**：Stream 的 redelivery 依赖消费者存活和 PEL 扫描，运维成本高、粒度粗（不能按错误类型差异化退避）。当前设计 Stream 只管分发，业务表才是真相之源——便于监控大盘、人工干预、审计。
- **dead 后的运维路径**：管理后台 dead 列表 → 看 last_error_code/detail → 改数据/代码后 `MarkRetrying` 拉回，或者 `MarkCanceled` 永久放弃。

## Q12：Redis Stream 消费者

### 基础回答

"消费循环用 `XReadGroup(group, consumer, streams=">", count=10, block=1s, NoAck=false)`：`>` 表示只读未投递的新消息，block=1s 单次阻塞既不空转也能定期检查 ctx.Done，count=10 防止单次拉太多。

每条消息按 type/payload 解析后分发，handler 不是同步阻塞而是 `pool.Submit(func{...})` 提交到 ants 池——这是避免单消费者阻塞的核心。handler 处理成功才 XAck，失败仅日志（业务表层补偿器接管）。

backlog 监控独立 goroutine 每 10s 调 `XInfoGroups(stream)` 取 Pending + Lag，通过 `metrics.SetConsumerBacklog` 暴露给 Prometheus。MaxLen=10000 + Approx=true 防止 Stream 无限增长（近似裁剪比精确裁剪快一个数量级）。"

### 亮点细节

- **PEL 超时不自动回流**：Redis Stream 的 PEL 不会自动让消息超时返回 New 队列，要用 XCLAIM 偷消息。当前实现没有 XCLAIM，但补偿器从业务表层兜底——即使 Stream PEL 有遗留也不影响实际处理。trade-off 是 Pending 数会虚高。
- **暂停开关**：`IsKnowledgeIngestPaused()` 在 handler 第一行检查，运维触发暂停后新消息直接被忽略（仍然 ack），用于紧急情况下临时关闭入库。

## Q13：Provenance 溯源

### 基础回答

"`AnnotateChunksWithProvenance` 在切分完成后给每个 chunk 补溯源元数据：

- 根据 chunk 的 child_start_offset/child_end_offset，在 NormalizedDocument.Blocks 找区间相交的 blocks，写 block_ids；
- 同时计算这些 blocks 跨越的 page_start/page_end 和平均 OCR confidence；
- 对 Tables 做同样的相交检测，写 table_ids；
- 写 normalized_path（sidecar 路径）方便事后回溯。

检索阶段用法：按页码定位（PDF 第几页第几块）、OCR 置信度兜底（低置信加'低质证据'标记）、表格特殊渲染（table_ids 命中时直接展示原表）、重切分（chunking_route 标了非预期策略时离线重切）。"

### 亮点细节

- **rangesOverlap 的简洁实现**：`leftStart <= rightEnd && rightStart <= leftEnd` 一行搞定区间相交。比想象中简单——经典算法面试题。
- **confidence 的统计方式**：是"该 span 内所有相交 blocks 的平均"，不是所有 blocks 的全局平均——这样能反映 chunk 局部的真实质量。

## 应答的几个心法

1. **先讲全景再讲细节**：开口 30 秒内一定要让面试官听到"上传同步段 → 异步消费段 → Milvus 落库段"这种结构化表达，再展开细节。结构化是基本功。

2. **每个细节带"为什么"**：说"我们用了 Redis Stream"不够，要说"我们没用 Kafka 而用 Redis Stream，因为消息量级不到、Redis 已经在用、运维成本低"。

3. **主动暴露 trade-off**：比如 Sparse 写入侧不存的代价是查询侧复杂度高、metadata JSON 反序列化有成本但 schema 演进自由——展示你看得到取舍，比一味鼓吹某个方案更打动人。

4. **代码位置是加分项**：被追问时如果能说出"在 `consumer.go` 的 `extractNormalizedKnowledgeDocument` 里，大概第 600 行附近"会让面试官立刻意识到你真读过代码。

5. **遇到不会的题别硬掰**：可以坦然说"这部分我接触不多，但根据上下游的设计我推测可能是这样……"——展示推理过程比硬背强。
