┌────────────────────────────────────────────────────────────┐

│   ① ClaimForProcessing（pending → processing）                │

│        └─ pdf/docx/html → HTTP Provider ──► parser-provider  │
│                                                  ↓            │
│                                            Docling 引擎       │

## Q1 ⭐：用 5 分钟把"用户上传一个 PDF"到"Milvus 里出现可检索向量"的完整链路讲一遍。

### 基础答案

完整链路分三段：**上传同步段 → 队列异步段 → Milvus 落库段**。

**1. 上传同步段（Web 层）**

- 管理后台调用文档上传接口，服务端把文件落到本地存储，写一条 `kb_document`（status=pending）和一条 `kb_ingest_job`（status=pending）。
- 然后向 Redis Stream `interview:stream:knowledge_ingest` 发一条入库消息（含 `job_id / document_id / kb_id / file_path / file_type`）。
- 接口立即返回，用户看到"处理中"。

**2. 队列异步段（消费者）**

- 消费者从 Stream 读到消息，先 `ClaimForProcessing` 把 job 从 `pending` 翻到 `processing`，把 document 状态翻到 `processing`。
- **解析**：根据文件类型分流——`md/txt` 走本地 normalizer，`pdf/docx/html` 走 HTTP parser-provider（背后是 Docling）。返回一份 `NormalizedDocument`（包含 Markdown 内容、blocks、tables、quality 信息等）。
- **规范化**：交给 `canonical.Normalize` 做 Unicode 清洗、解析噪声去除、标题修复、表格 span 重锚，并记录 `RawSHA1 / CanonicalSHA1` 用于审计。
- **留痕**：把 `NormalizedDocument` 写到 `*.normalized.json` sidecar 文件，方便事后排查。
- **切分**：交给 `StrategyRouter` 路由到 4 种策略之一（Markdown / Structure-Aware / Table-Aware / OCR-Aware），生成一组 `*schema.Document`。
- **父子块补全**：`finalizeChunks` 给每个 chunk 补上 `parent_id / parent_start_offset / parent_end_offset / hierarchy_path / block_ids / table_ids` 等元数据。

**3. Milvus 落库段（Indexer）**

- `IndexerService.Store` 内部调 Embedding 服务（火山 Ark / OpenAI 兼容）批量出 Float 向量，再把 `(id, content, vector, metadata)` 写入对应知识库的 Milvus collection。
- 写入成功后，状态机 `processing → completed`，`kb_document.chunk_count` 更新。

**失败路径**：任何一步出错都会被分类为 `payload / parse / embedding / milvus / unknown` 五种错误码，可重试错误进入 `retrying`，超过 `max_retry_count` 进 `dead`。

### 深入追问

**Q：上传段和异步段的边界为什么放在"投递 Redis Stream"那里？放更前或更后会怎样？**

- 放在更前（比如直接在 HTTP handler 里解析 PDF）：解析一个 100 页 PDF 可能要 30 秒，HTTP 长连接很容易被 LB / 反向代理超时切断；高并发下还会把进程的工作 goroutine 占满。
- 放在更后（比如先在 server 里把 chunk 切完再投递）：等于把 CPU 密集型的切分跑在了同步链路里，依然解决不了用户等待的问题。
- 当前的边界恰好是"轻量元数据写入 + 一条消息"，HTTP 接口可以做到亚秒级返回，CPU 密集型工作全部留给消费者池。

**Q：为什么需要 KBIngestJob 这张表？只用 KBDocument 的 status 字段不行吗？**

- KBDocument 是"文档"维度，状态只是个粗粒度的展示状态（pending / processing / completed / failed）。
- KBIngestJob 是"任务"维度，有 `retry_count / next_retry_at / last_error_code / last_error_detail / operator_id / operation`，承担补偿、审计、重试调度。
- 两张表分开后还能支持"同一个文档多次入库（重新切分）"——历史 job 留痕，文档当前状态不被破坏。

## Q2 ⭐：为什么入库链路要做成异步消费？同步处理（上传完直接解析+入库）有什么问题？

### 基础答案

**核心理由有 4 个**：

1. **解析耗时不可控**：Docling 解一个扫描版 PDF 几十秒甚至几分钟很正常，HTTP 同步等不起。
2. **资源隔离**：解析、Embedding 都是 CPU/IO 密集型操作，混在 web worker 里会和正常 API 抢 goroutine，影响检索接口 P99。
3. **可重试 / 可补偿**：异步任务天然可以失败重投——把"重试"这件事单独拎出来比在 HTTP 里做更干净。
4. **削峰填谷**：批量上传 100 个文档时，同步处理会瞬间打爆 Embedding 服务的限流；进 Stream 后由消费者按池大小（`ants.NewPool(1000)`）匀速消费。

**实现方式**：

- 队列：Redis Stream（`XADD` + `XReadGroup` 消费组），key 为 `interview:stream:knowledge_ingest`，`MaxLen=10000` + `Approx=true` 防止 Stream 无限增长。
- 工作池：`panjf2000/ants` goroutine 池，限制最大 1000 并发。
- 确认机制：处理成功才 `XAck`；失败仅写 log 不 ack，让 PEL（Pending Entries List）保留消息（项目里更倾向用业务表 + 重试补偿器自己控制重试节奏）。

### 深入追问

**Q：为什么用 Redis Stream，不用 Kafka / RabbitMQ / MySQL 轮询？**

- 项目本身就在用 Redis（缓存、限流），引入 Stream 零基础设施成本。
- 消息量级（每天千万级以下）远没到需要 Kafka 的水平；上 Kafka 反而增加运维复杂度。
- MySQL 轮询能实现，但存在惊群和锁竞争问题；Stream 的消费组天然避免了重复消费。
- 真正需要"严格顺序、跨业务流式"才考虑 Kafka，本项目用不上。

**Q：消费者并发度怎么定？池子开太大会怎样？**

- 真正卡住吞吐的是下游：parser-provider 的解析能力、Embedding API 的 RPS 配额、Milvus 写入吞吐。
- 池子开到 1000 是一个上限，实际并发被 Embedding 服务的限流"自然"压住（DashScope 默认 batch=10）。
- 池子开太大会导致 Embedding 调用的 P95 飙升、Milvus 写入排队，最终吞吐反而下降；这种链路是"流量适配"问题，不是"并发越大越好"。

## Q3 ⭐：项目把 PDF/DOCX/HTML 的解析单独抽成了一个 `parser-provider` 进程，为什么不直接在 Go 里调库？这种"适配器+独立进程"模式带来什么好处？

### 基础答案

**为什么不直接在 Go 里调库？**

- PDF/DOCX 的高质量解析（带表格识别、OCR、版面分析）目前最强的是 Python 生态（Docling、PaddleOCR、unstructured 等），Go 这边没有同级别替代品。
- 在 Go 里 `cgo` 调 Python 极其反人类——内存模型、GIL、依赖打包都是雷。
- 解析过程是 CPU/内存密集型，单独跑一个进程可以独立扩缩容、独立 OOM 重启，不影响主服务。

**适配器模式的设计**：

- 主进程定义抽象接口 `documentparser.Provider`（[provider.go](file:///h:/GYT-CODE/rag-retrievalOps/backend/internal/documentparser/provider.go#L11-L13)），只暴露 `Parse(ctx, ProviderRequest) (*NormalizedDocument, error)`。
- 默认实现是 `HTTPProvider`（[http_provider.go](file:///h:/GYT-CODE/rag-retrievalOps/backend/internal/documentparser/http_provider.go#L47-L118)），用 multipart 把 file + file_type + options 发给 `parser-provider` 的 `/parse` 端点。
- `parser-provider` 是一个独立 Go 二进制（[cmd/parser-provider/main.go](file:///h:/GYT-CODE/rag-retrievalOps/backend/cmd/parser-provider/main.go#L18-L62)），它内部再用 `DoclingClient` 把请求转换成 Docling Serve 协议（multipart `to_formats=md,json` + `image_export_mode=placeholder` + 一堆 `pdf_backend / table_mode / ocr_*` 选项）。
- Docling 返回的 JSON 在适配器里被翻译成项目自己的 `NormalizedDocument` 结构。

**好处**：

1. **可替换性**：明天换 unstructured / textract，只需要写一个新的 Parser 实现，不动主服务。
2. **进程隔离**：解析进程崩了不会拖垮 rag-server。
3. **横向扩展**：parser-provider 是无状态 HTTP 服务，可以独立加副本。
4. **协议清晰**：主服务和解析服务之间只有一份 multipart 协议契约，便于多语言混搭（Docling 那一层换成 Python 服务也照样跑）。

### 深入追问

**Q：抽象接口的形状（`NormalizedDocument`）是怎么设计的？为什么不让上游自己适配每种格式？**

`NormalizedDocument` 是"格式无关"的中间表示（[types.go](file:///h:/GYT-CODE/rag-retrievalOps/backend/internal/documentparser/types.go#L11-L21)），关键字段：

- `ContentMarkdown`：规范化后的 Markdown，下游切分只认这个字段。
- `Blocks` + `Tables`：带 `MarkdownStart/MarkdownEnd` 偏移量的结构信息，用于切分阶段决定切分策略和后续 provenance 标注。
- `Quality` + `Extractor` + `Canonicalization`：审计信息（解析器版本、规范化版本、SHA1）。

设计思想是：**所有格式在 parser 这一层就被对齐到同一个数据结构**，下游切分、Embedding、Milvus 写入完全不需要关心源文件是 PDF 还是 Word；这就是适配器模式的核心价值。

**Q：multipart 传文件 vs base64 传 JSON，为什么选前者？**

- 大文件（几十 MB 的 PDF）走 base64 内存膨胀 33%，对 GC 不友好。
- multipart 是流式的，Go 的 `http.Request.Body` 可以边读边写。
- 错误码用 JSON 返回，文件用 multipart 上传是行业惯例（OpenAI / Docling 都这么做）。

**Q：HTTP 调用本身有哪些必须考虑的细节？**

- 超时：`HTTPProvider` 默认 60s，配置里通过 `RAG.DocumentParser.TimeoutMS` 注入；Docling 一层默认 120s（[DoclingClient](file:///h:/GYT-CODE/rag-retrievalOps/backend/internal/parserprovider/docling.go#L52-L74)）。
- 错误体：上游 4xx/5xx 时尝试解析成 `ProviderError`（带 `Code/Message/Stage/Page/Retryable`），retryable 字段决定上层是否进入重试。
- 校验：`Parse` 返回前会调 `doc.Validate()`，确保 Markdown 非空、文件类型支持、Extractor 信息齐全。

## Q4 ⭐：解析完成后还要走一步 `canonical.Normalize`，这一步在做什么？为什么不能跳过？

### 基础答案

`canonical.Normalize`（[normalizer.go](file:///h:/GYT-CODE/rag-retrievalOps/backend/internal/documentparser/canonical/normalizer.go#L29-L64)）是把"解析器输出"再做一次确定性归一化，让所有来源（不同 PDF backend、不同 Docling 版本、本地 Markdown）汇聚到同一种 Markdown 形态再进入切分。它做了 5 件事：

1. **Unicode + 行尾清洗**：CRLF → LF、全角空格 → 半角、各类不可见字符过滤。
2. **解析噪声去除**：Docling 输出里常见的水印行、页眉页脚残留、`[image]` 占位符等清理。
3. **标题修复**：把"破碎的标题"（比如 "1.2 INTRO" 被拆成两行）合并；处理数字+全大写英文的伪标题。
4. **空行收敛**：连续 3 个以上换行收敛成 2 个。
5. **表格 span 重锚**：调用 `NormalizeMarkdownPipeTables` 重新渲染表格 + 重算 `MarkdownStart/MarkdownEnd`，并和 parser 输出的表格元数据合并。

**输出**：

- `ContentMarkdownRaw`：保留原始解析输出（用于事后审计/回溯）。
- `ContentMarkdown`：清洗后的标准 Markdown。
- `Canonicalization.RawSHA1 / CanonicalSHA1`：两份内容的指纹，用于检测"同一份文件不同时间解析结果是否漂移"。

**为什么不能跳过**：

- 切分策略和检索阶段都假设"标题层级是干净的、表格 span 是准确的"，跳过这一步会导致：
  - Markdown 结构切分把伪标题当成真标题，切出一堆没语义的小块。
  - 表格 chunk 的 `MarkdownStart/End` 偏移和实际不一致，父子块定位错位。
- 无法做"内容指纹"，文档解析的可重复性失去基线。

### 深入追问

**Q：`NormalizerVersion` 和 `canonical.Version` 各自代表什么？为什么要分开？**

- `documentparser.NormalizerVersion = "document-normalizer-v1"`：父概念，标识整个 normalize 流程的版本。
- `canonical.Version = "canonical-normalizer-v1"`：具体规范化器的版本，写到 `Canonicalization.Version` 里。
- 分开是为了 schema 演进——`Extractor.Version` 标识"是谁解出来的"（local / docling-v1），`Canonicalization.Version` 标识"是谁清洗的"，事后排查"为什么一份文档现在切出来的 chunk 数和上个月不一样"时这两个字段是关键证据。

**Q：`AppliedRules` 字段有什么用？**

- 规范化过程中真正命中的规则名（`unicode-whitespace / parser-noise / heading-cleanup / heading-continuation-merge / table-span-rebase`）会写进这个数组。
- 用途：批量统计哪些规则使用率高、哪些规则其实从未触发，给"规范化规则集是否需要更新"提供数据依据。

## Q5 ⭐：项目内置了 4 种切分策略（Markdown / Structure / Table / OCR），它们是怎么被路由的？为什么不能用单一策略？

### 基础答案

**路由机制**（[StrategyRouter](file:///h:/GYT-CODE/rag-retrievalOps/backend/internal/milvus/chunking/router.go#L28-L62)）：

- `StrategyRouter` 持有一个 `defaultStrategy` 和一组 `RoutedStrategy{Name, Match, Strategy}`。
- 收到 `Request` 后按顺序匹配 `Match`，第一个匹配的策略接管切分；都不匹配走默认。
- 切分完所有 chunks 都会被打上 `chunking_route` 元数据标签，方便事后统计每种策略的占比。

**4 种 Match 函数**：

| 策略 | Match 条件 | 适用场景 |
| --- | --- | --- |
| `MatchOCRAware` | `file_type == pdf` 且（quality.warnings 含 "ocr" 或任意 block 有 confidence） | 扫描版 PDF / 低质量 OCR 文档 |
| `MatchHasTables` | `len(doc.Tables) > 0` | 含表格的文档（财报、API 文档等） |
| `MatchHasStructure` | 有 blocks 且类型是 docx/pdf/html | 有版面结构的解析输出 |
| 默认（StrategyMarkdown） | 其它 | md / txt / 无结构信息的文档 |

**为什么不能单一策略**：

- 一份扫描合同（OCR 置信度低）和一份 Markdown 技术文档的"自然切分单元"完全不同：前者要按 block 窗口切并标低置信度，后者要按 `##` 标题切。
- 表格如果按字符长度切会被切碎（比如把表头和表体分到两个 chunk），必须按表为单位独立切。
- 单一策略的极端结果：要么粒度过粗（整段切不开）、要么把表格/标题切碎，检索质量直接崩。

### 深入追问

**Q：Match 顺序为什么重要？**

- 注册顺序决定优先级。OCR-Aware 必须排在 Table-Aware 前面，否则一份"扫描版 + 含表格"的 PDF 会先被路由到 Table-Aware，错过 OCR 标注链路。
- 同理 `MatchHasTables` 通常排在 `MatchHasStructure` 前面，因为表格走专用策略后 chunk 元数据更精准。

**Q：每种策略具体怎么切？**

- **MarkdownStrategy**（[markdown_strategy.go](file:///h:/GYT-CODE/rag-retrievalOps/backend/internal/milvus/chunking/markdown_strategy.go#L43-L137)）：先用 goldmark 解析 AST 找到所有标题，按标题层级切成 sections；section 太长则按字节限制（默认 1000B）二次切；切不出标题就回落到 eino 的 `recursive` 切分器。
- **StructureAwareStrategy**（[structure_strategy.go](file:///h:/GYT-CODE/rag-retrievalOps/backend/internal/milvus/chunking/structure_strategy.go#L25-L94)）：以 `NormalizedBlock` 为最小单元，做"窗口聚合"——逐块累加，超过 1000B 就 flush 一个 chunk；保证 chunk 边界落在 block 边界上。
- **TableAwareStrategy**（[table_strategy.go](file:///h:/GYT-CODE/rag-retrievalOps/backend/internal/milvus/chunking/table_strategy.go#L21-L79)）：装饰器模式——先委托默认策略切普通文本，再为每张表单独生成一个 chunk（既包含 Markdown 表格又包含 `headers: values` 的可检索行），用 `chunking_unit=table` 和 `table_ids` 标注。
- **OCRAwareStrategy**（[ocr_strategy.go](file:///h:/GYT-CODE/rag-retrievalOps/backend/internal/milvus/chunking/ocr_strategy.go#L29-L70)）：装饰器——委托执行后给每个 chunk 算"该 span 内 block 平均 confidence"，低于阈值（默认 0.8）打上 `weak_evidence=true`，下游检索可以用这个标志降权。

**Q：策略路由 + 装饰器叠加的边界？**

- TableAware 和 OCRAware 都是装饰器（包另一个策略），可以组合使用。
- 路由器一次只选一种"主策略"，但 TableAware 内部如果检测到 OCR 信号也会顺带调用 `annotateOCRQuality`（[table_strategy.go:74](file:///h:/GYT-CODE/rag-retrievalOps/backend/internal/milvus/chunking/table_strategy.go#L74-L76)），保证表格 chunk 不会因为路由没选 OCR-Aware 就丢掉置信度信息。

## Q6 ⭐：解释一下父子块（Parent-Child）切分。这套设计要解决什么问题？元数据具体是怎么挂上去的？

### 基础答案

**问题**：Embedding 检索的最佳粒度（200~500 字）和给 LLM 看的最佳上下文粒度（1500~3000 字）不一致。
- 切得太粗：召回精度低，Embedding 容易漂移。
- 切得太细：检索回来的小段缺乏上下文，LLM 接不住。

**父子块方案**：

- 真正参与向量检索的是「子块」（child），粒度小、Embedding 精准。
- 同时给每个子块挂一个「父块」（parent）的指针——父块是一段更大的语义单元（小节级、段落窗口级），用于在 LLM 拼 prompt 的时候"以父代子"补充上下文。
- 子父之间通过 `parent_id / parent_start_offset / parent_end_offset` 关联，检索阶段只需要拿到 child，再用 parent 信息回 Markdown 里截一段大文本即可。

**两套实现共存**：

1. **eino splitter 内部**（[parent_child.go](file:///h:/GYT-CODE/rag-retrievalOps/backend/internal/milvus/splitter/parent_child.go#L46-L123)）：当 Markdown 策略 fallback 到 eino recursive splitter 时，在 `annotateSplitChunks` 里给 child 找"包含它的最小父块"。父块通过解析标题层级 + 段落窗口生成（`heading_section / heading_section_window / paragraph_window` 三种 strategy）。
2. **chunking 层 finalizeChunks**（[helpers.go](file:///h:/GYT-CODE/rag-retrievalOps/backend/internal/milvus/chunking/helpers.go#L160-L226)）：统一在所有策略切完之后再跑一遍，根据 chunk 已经写入的 `child_start_offset / child_end_offset` 找到对应的 heading section，构造 `parent_id / parent_start_offset / parent_end_offset / hierarchy_path`，写到元数据里；版本号 `phase3-parent-child-v1`。

**关键元数据字段**：

```
chunk_id                 child 的 ID
child_id                 同上（兼容字段）
child_start_offset       child 在原 Markdown 中的起始字节偏移
child_end_offset         child 在原 Markdown 中的结束字节偏移
parent_id                父块 ID（hash 自 hierarchyPath:start:end）
parent_start_offset      父块起始偏移
parent_end_offset        父块结束偏移
parent_build_version     phase3-parent-child-v1
parent_build_strategy    heading_section / paragraph_window / table
parent_token_count       近似 token 数
parent_truncated         父块大小是否超过默认上限
parent_child_available   是否成功挂到了一个父块
hierarchy_path           "Chapter 1 > Section 1.2 > Subsection 1.2.3"
section_title            最近一级标题
```

### 深入追问

**Q：父块怎么避免和子块完全相等（这样就退化成普通切分了）？**

- 父块的最小粒度是 heading section 或 paragraph window，不是 chunk。
- 当文档没有任何标题时（极端情况），父块退化成 `chunking_unit=table` 时直接等于子块（表格本身就是一个独立单元，没有更大的语义父）。
- 一般情况父子比例在 1:3 ~ 1:5 左右。

**Q：父块 ID 怎么生成？怎么保证幂等？**

- 通过 `documentKey-parent-{shortHash(hierarchyPath:start:end)}-{idx}` 生成（[helpers.go:289](file:///h:/GYT-CODE/rag-retrievalOps/backend/internal/milvus/chunking/helpers.go#L289)）。
- `documentKey` 优先取 `document_id`，其次取 `file_name + content shortHash`，保证同一份文档反复入库 ID 稳定。
- `shortHash(hierarchyPath:start:end)` 让"同一段父块"在重切后能拿到相同 ID（前提是规范化后的 Markdown 没变），便于增量索引。

**Q：检索阶段怎么用父子关系？**

- 检索时返回 child；去 Milvus 里按 `metadata.parent_id` 反查一次，把同父的 child 聚合或者直接用 `parent_start_offset/end_offset` 截原 Markdown 拼上下文。
- 评测时也会用 `parent_truncated` 做样本筛选，避免把"父块被强切过"的样本算进高质量集。

## Q7 ⭐：Embedding 服务这一层是怎么封装的？它做了哪几件不显眼但关键的事？

### 基础答案

`EmbeddingService`（[embedding.go](file:///h:/GYT-CODE/rag-retrievalOps/backend/internal/milvus/storage/embedding.go#L19-L81)）是个薄壳，但里面叠了 3 层增强：

- `ark` → 火山引擎，支持 text/multi-modal API type。
- `openai` → OpenAI 兼容协议（DashScope / 智谱 / 千帆都走这条路，只换 BaseURL+APIKey）。
- `mock` → 本地确定性向量（hash 生成），用于单元测试和无网络调试。

**2. batchingEmbedder 自动分批**

- 对 DashScope 这类有"单次最多 10 条"限制的 API，自动按 `BatchSize` 把大批文本拆成多次调用（[batchingEmbedder.EmbedStrings](file:///h:/GYT-CODE/rag-retrievalOps/backend/internal/milvus/storage/embedding.go#L247-L271)）。
- 默认 batch 自动识别：`provider=openai` 且 `BaseURL` 含 `dashscope.aliyuncs.com` 时强制 10。
- 防御性校验：返回向量数和入参文本数不一致时直接报错（避免静默错位）。

**3. 双 embedder 出口**

- `embedder`：写入链路用（无缓存，直接打底层 API）。
- `queryEmbedder`：检索链路用（可选挂内存缓存）。
- 两个出口分开：写入是大批量、低复用，缓存了反而是无效内存占用；查询是高频重复短文本，缓存命中收益大。

### 深入追问

**Q：为什么写入不缓存 Embedding？**

- 写入的文本是 chunk 内容，几乎每段都不一样，缓存命中率近乎 0。
- 写入是一次性消费——同一份文档不会反复被 embed。
- 真正能复用的是"用户 query 在短时间窗口内重复"的场景，那是查询链路的事。

**Q：mock embedder 不是开发时玩具，它在线上有用吗？**

- 单元测试稳定性：CI 跑切分/索引器测试时不能依赖外部 API。
- 离线评测：跑 `evaluation` 模块时如果只想测 chunk 召回结构，可以用 mock 替换真 embedding，加速实验。
- 注意：mock 是确定性的（FNV hash + sin/cos 生成），结果可复现。

**Q：批量调用失败时怎么处理？**

- 当前实现：单批失败 → 整个 EmbedBatch 失败 → 抛回上层 → 错误码归类为 `embedding_error` → 进入重试链路。
- 没有做"批内部分失败"的精细化补偿，因为大模型 API 通常是整批 429 / 5xx，不会真的"成功一半"。

## Q8 ⭐：Embedding 缓存只对 query 链路开启，缓存键和淘汰策略具体是怎么做的？还做了什么并发优化？

### 基础答案

`cachedQueryEmbedder`（[embedding_cache.go](file:///h:/GYT-CODE/rag-retrievalOps/backend/internal/milvus/storage/embedding_cache.go)）是包在底层 embedder 上的进程内缓存层，3 个关键设计：

**1. 缓存键 = 单条 query 的 trim 结果**

- 只对 `len(texts)==1` 的请求走缓存——对应 query 链路的"一条用户 query → 一个向量"。
- 多文本批量请求直接绕过缓存（`batch_bypass`），不污染语义。
- key 是 `strings.TrimSpace(texts[0])`，保留大小写和中间空格（语义敏感）。
- **隐含约束**：缓存语义和模型版本绑定——切换模型时必须重启进程或新建 embedder 实例（不同模型不能复用同一进程内 cache）。

**2. TTL + LRU 双重淘汰**

- 每个 entry 有 `expiresAt = now + ttl`、`lastAccess`。
- `get()` 时若过期直接 delete + 返回 miss。
- `put()` 后调 `pruneLocked`：先删过期项，再按 `lastAccess` 找最早访问的 entry 淘汰（保证总数 ≤ `maxEntries`）。

**3. singleflight 收敛并发**

- 用 `golang.org/x/sync/singleflight`：同一个 normalized query 在同一时刻只会真正调一次底层 embedder，其余并发请求等同一个结果。
- 通过 `shared` 标志识别这是不是借用了别人的请求结果，trace 中标 `singleflight_shared`。

**4. trace 钩子**

- `WithEmbeddingCacheTrace(ctx)` 注入 trace collector，调用结束 `ConsumeEmbeddingCacheTrace(ctx)` 拿到 `{Enabled, Hit, LookupMs, Reason}`。
- Reason 枚举：`hit / miss / singleflight_shared / batch_bypass / empty_query / embed_failed / dependency_unavailable / unexpected_type`。
- 检索链路侧可以把这个 trace 一起写到检索日志，事后能解释"这次检索的 embedding 究竟是怎么来的"。

### 深入追问

**Q：`get` 里用写锁而不是读锁，为什么？**

- 这是被刻意修过的（注释里也说了）：之前用 RLock 读 + Lock 写的两步式更新 `lastAccess`，在两步之间可能被另一个 goroutine 通过 `put` 写入新 entry，回写时旧 entry 覆盖新 entry，导致下次命中拿到陈旧向量。
- 现在统一在写锁里完成"读 entry → 续命 lastAccess → 写回"，规避 TOCTOU 竞态。
- 代价是这是个写锁，但 query 缓存命中频率不高到要纠结这点性能（实际场景每秒几十次）。

**Q：为什么向量返回前要 `append([]float64(nil), entry.vector...)` 复制一份？**

- 如果直接返回内部 slice，调用方原地修改会污染缓存数据，下次命中拿到错的向量。
- 复制成本对 768/1536 维向量是几个微秒级别，可接受。
- 同样的策略用在 `cloneVectors`（[embedding_cache.go:268](file:///h:/GYT-CODE/rag-retrievalOps/backend/internal/milvus/storage/embedding_cache.go#L268-L277)）保护 batch_bypass 路径。

**Q：进程内缓存够用吗？要不要 Redis 共享缓存？**

- 当前是单进程缓存，`maxEntries` 限制（默认上千条）。
- Pros：零网络开销、零序列化开销、内存命中亚毫秒级。
- Cons：多副本之间不共享、进程重启缓存清空。
- 真正的"模型版本+文本 hash"持久缓存可以叠在 Redis 上，但当前项目场景下进程内缓存命中率已经很高（query 高度重复），还没到需要持久化的临界点。

## Q9：Milvus 写入侧的 schema 是什么？为什么用 FloatVector 而不是 BinaryVector？Sparse 向量怎么参与？

### 基础答案

**写入 schema**（[indexer.go](file:///h:/GYT-CODE/rag-retrievalOps/backend/internal/milvus/storage/indexer.go#L21-L82)）：

```
id        VARCHAR  primary_key  max_length=255
vector    FloatVector dim=动态注入
content   VARCHAR  max_length=4096
metadata  JSON
```

度量类型 `COSINE`，对应余弦相似度（适合 sentence-embedding 这类做归一化的向量）。

**FloatVector vs BinaryVector**：

- 项目使用 `entity.FieldTypeFloatVector` 而不是 SDK 默认的 BinaryVector，原因是：现代 sentence-embedding 都是浮点向量（768 / 1024 / 1536 / 3072 维），二值化会损失精度；HNSW / IVF_FLAT 等高效索引也是为浮点设计的。
- `FloatVectorDocumentConverter`（[converter.go](file:///h:/GYT-CODE/rag-retrievalOps/backend/internal/milvus/storage/converter.go)）负责把 `*schema.Document` + `[][]float64` 转换成 Milvus 写入需要的 `FloatVectorSchema{ID, Content, Vector []float32, Metadata []byte}` 行结构（注意：内部从 float64 转成 float32 节省 50% 存储）。
- `metadata` 字段是 `sonic.Marshal` 后的 JSON 字节，里面装着 `kb_id / document_id / chunk_id / parent_id / child_start_offset / hierarchy_path / chunking_strategy / block_ids / table_ids` 等所有用于检索过滤和上下文恢复的元数据。

**Sparse 向量怎么参与**：

- 写入侧没有显式落 sparse 向量字段——`content` 字段就保存了原始可读文本。
- Sparse 检索是在查询侧通过 `SparseRetriever` 在内存里基于倒排索引/BM25 实时计算的（见 `internal/milvus/retrieval/sparse_*.go`），不需要在写入时构建 sparse vector。
- 这种"写入只存 dense + content，sparse 在查询侧基于 content 重建"的设计简化了 schema，代价是 sparse 检索路径需要先用 dense 召回粗筛 candidates 再 BM25 精排。

### 深入追问

**Q：metadata 用 JSON 字段而不是展开成多个 typed 字段，会不会丢失过滤能力？**

- Milvus 2.x 支持对 JSON 字段做 `metadata["kb_id"] == 123` 这种表达式过滤，性能已经够用。
- 展开成 typed 字段会让 schema 演进非常痛苦——每加一个元数据都要改 collection schema 和迁移历史数据。
- JSON 字段的代价是反序列化开销，但读侧拿回来本来就要解析 metadata，整体成本可控。

**Q：Collection 是怎么命名的？多租户隔离怎么做？**

- 每个知识库（KB）有自己独立的 collection，命名规则：优先用 `kb.vector_collection` 字段，没有就用 `DefaultKnowledgeBaseCollectionName(kbID)` 自动生成（[consumer.go:656-679](file:///h:/GYT-CODE/rag-retrievalOps/backend/internal/ragqueue/consumer.go#L656-L679)）。
- 这种"一 KB 一 collection"模式天然实现了租户隔离，删除一个知识库直接 drop collection，不用清扫。
- 索引器是按 collection 动态创建的：`manager.NewIndexerServiceForCollection(ctx, collection)`，不同 KB 不共享 indexer 实例。

## Q10 ⭐：解释入库的状态机。`pending / processing / completed / failed / retrying / dead / canceled` 各自代表什么？哪些转换是允许的？

### 基础答案

状态机定义在 [kb_ingest_job.go](file:///h:/GYT-CODE/rag-retrievalOps/backend/internal/model/kb_ingest_job.go#L38-L64) 的 `kbIngestJobTransitions` 表里：

```
pending     → processing | failed | canceled
processing  → completed | failed | retrying | canceled
failed      → retrying | dead | canceled
retrying    → processing | failed | dead | canceled
dead        → retrying（人工干预重试）
completed   → 终态
canceled    → 终态
```

**各状态语义**：

| 状态 | 含义 |
| --- | --- |
| `pending` | 已投递到 Stream，等待消费者认领 |
| `processing` | 消费者已 claim，正在解析/切分/Embedding/写入 |
| `completed` | 全部步骤成功，文档可被检索 |
| `failed` | 失败但不再重试（不可重试错误，或重试次数耗尽前的中间态） |
| `retrying` | 失败但属于可重试错误，等待补偿器重投 |
| `dead` | 重试次数超过上限，进入死信，需要人工干预 |
| `canceled` | 用户主动取消 |

**关键转换实现**：

- `ClaimForProcessing`：`pending|retrying → processing`，用 `UPDATE ... WHERE id=? AND status IN (...)` 的乐观并发，保证同一 job 不会被两个 worker 同时认领。
- `UpdateFailureState`：写入失败信息（`last_error_code / last_error_detail / next_retry_at`），并可选 `retry_count + 1`。
- `MarkPendingForRetry`：补偿器从 retrying 集合里捞到期任务时使用（实际上写的是 retrying → retrying，只清空 next_retry_at 和 started_at）。
- `MarkRetrying`：人工触发的"从 failed/dead 拉回 retrying"，记录 operator_id 和原因。
- 任何非法转换（比如试图从 completed → processing）都会返回 `ErrInvalidKBIngestJobTransition`。

### 深入追问

**Q：为什么把 `failed` 和 `dead` 分成两个状态？合并成一个不行吗？**

- `failed` 是"暂时失败但还没决定要不要重试"的中间态——比如 Embedding 服务报 5xx，先记下错误，下一轮才决定是进 `retrying` 还是 `dead`。
- `dead` 是"永久失败、需要人工 review"，进了 dead 的任务不会被自动补偿器再扫到，避免反复浪费重试预算。
- 合并的话就丢失了"自动重试用尽 vs 人工放弃"的语义边界，监控告警也没法区分。

**Q：状态转换都用 `UPDATE ... WHERE id=? AND status IN (?)` 而不是先 SELECT 再 UPDATE，为什么？**

- 这是经典的"乐观并发 + 幂等保护"模式。
- 多副本消费者并发认领同一条消息时，只有一个 UPDATE 会真正改到行（RowsAffected==1），其他的 RowsAffected==0 → 自动放弃，不会出现重复处理。
- 比起分布式锁（Redis SETNX 等），这种纯 SQL 的乐观锁更朴素、更可靠。

**Q：`document` 表的 status 和 `ingest_job` 表的 status 怎么同步？**

- 文档 status 只有 4 个值：`pending / processing / completed / failed`（见 [kb_document.go](file:///h:/GYT-CODE/rag-retrievalOps/backend/internal/model/kb_document.go#L11-L15)）。
- 任务 status 是 7 个值，但同步规则简单：任务进 processing → 文档 processing；任务 completed → 文档 completed；任务 failed/retrying/dead → 文档 failed（管理后台不需要让用户区分这三种）。
- 同步发生在消费者每次状态变更后（[consumer.go](file:///h:/GYT-CODE/rag-retrievalOps/backend/internal/ragqueue/consumer.go#L73-L101)），不强求事务，因为最终一致性即可。

## Q11 ⭐：失败重试链路是怎么设计的？错误怎么分类？退避策略是什么？

### 基础答案

**错误分类**（[consumer.go](file:///h:/GYT-CODE/rag-retrievalOps/backend/internal/ragqueue/consumer.go#L24-L32)）：

| 错误码 | 来源 | 是否可重试 |
| --- | --- | --- |
| `invalid_payload` | 消息格式错误、字段缺失 | ❌ 永久失败（重试也是错） |
| `parse_error` | 解析阶段失败（PDF 损坏、格式不支持） | ❌ 永久失败 |
| `embedding_error` | Embedding 服务异常 | ✅ 仅当带瞬时信号才重试 |
| `milvus_write_error` | Milvus 写入失败 | ✅ 仅当带瞬时信号才重试 |
| `unknown_error` | 其他 | ✅ 仅当带瞬时信号才重试 |

**瞬时失败信号**（[hasTransientFailureSignal](file:///h:/GYT-CODE/rag-retrievalOps/backend/internal/ragqueue/consumer.go#L495-L520)）：错误消息里命中 `timeout / deadline exceeded / temporarily unavailable / connection reset / connection refused / broken pipe / eof / i/o timeout / network` 才算可重试。这个判断很关键——避免"语义错误"被无限重试。

**退避策略**（[calculateKnowledgeRetryBackoff](file:///h:/GYT-CODE/rag-retrievalOps/backend/internal/ragqueue/consumer.go#L549-L567)）：

- 基础间隔 `RetryBackoffMS`（默认 500ms）。
- 指数退避：`delay = base * 2^(retry_count-1)`。
- 加抖动：`jitter = 0.8 + rand.Float64()*0.4`（80% ~ 120% 之间），避免雷暴。
- 上限 `maxKnowledgeRetryBackoff = 5 * time.Minute`。
- 最低 1 秒（避免 base 太小导致风暴）。

**补偿器**（[startKnowledgeRetryCompensator](file:///h:/GYT-CODE/rag-retrievalOps/backend/internal/ragqueue/consumer.go#L323-L413)）：

- 独立 goroutine，按 5~30 秒间隔扫表。
- `ListRetryDueJobs`：查 `status=retrying AND next_retry_at <= now`。
- `MarkPendingForRetry`：claim 任务（防止并发扫描）。
- 重新 `PublishKnowledgeIngest` 把消息重投到 Stream。
- 投递失败时刻意保持 `retrying` 状态而不是切到 `failed`——避免任务卡死无人重试（注释里明确说了这是"数据丢失级"的 bug 修复）。

### 深入追问

**Q：为什么用关键字匹配判断瞬时失败？不是很 hack 吗？**

- 是有点 hack，但务实。底层错误来自不同库（Go HTTP、Milvus SDK、Embedding SDK），并没有统一的 `errors.Is(err, ErrTransient)` 接口。
- 关键字虽然有漏判风险，但白名单式匹配（命中才重试）比黑名单更安全——最坏情况是"应该重试的没重试"，不会变成"不该重试的反复重试"。
- 长期改进方向：让各 SDK 适配层把瞬时错误包装成自定义类型，再用 `errors.As` 判断。

**Q：Stream 自身也有"消息没 ack 就重发"的能力，为什么还要业务表层做重试？**

- Stream 的 redelivery 机制依赖 Consumer 实例存活和 PEL 扫描，运维成本高且粒度粗（不能按错误类型差异化退避）。
- 当前设计是"Stream 只管投递，业务表才是真相之源"——任务状态、重试次数、错误码都在 MySQL，可以做监控大盘、可以人工干预、可以审计。
- Stream 实际上承担的是"低成本的消息分发"，不承担可靠性保证。

**Q：什么情况下任务会进 `dead`？运维怎么处理？**

- 重试次数累计超过 `RAG.Thresholds.MaxRetryCount`（默认 3），下一次失败时直接进 dead。
- 运维侧：管理后台有 dead 任务列表 → 查看 `last_error_code/detail` → 决定是改数据/改代码后 `MarkRetrying`，还是 `MarkCanceled` 永久放弃。

## Q12：Redis Stream 消费者具体怎么读消息？怎么避免单消费者阻塞、怎么做 backlog 监控？

### 基础答案

**消费循环**（[readMessages](file:///h:/GYT-CODE/rag-retrievalOps/backend/internal/ragqueue/redis_stream.go#L110-L197)）：

- 用 `XReadGroup(group, consumer, streams=">", count=10, block=1s, NoAck=false)` 阻塞读取。
- `>` 表示"只读未投递给这个消费者的新消息"。
- `Block=1s` 是单次阻塞时间，超时后再循环；这样既不空转也能定期检查 ctx.Done。
- `Count=10` 一次最多拉 10 条，防止单次拉太多无法及时反应取消信号。

**消息分发**（同函数）：

- 每条消息按 `type / payload` 解析，再根据注册的 handlers 分发。
- 关键：handler 的执行不是同步阻塞，而是 `pool.Submit(func{...})` 提交到 ants goroutine 池——这就是"避免单消费者阻塞"的核心。
- handler 处理成功才 `XAck`，失败仅写日志（不 ack 让 Stream 端记入 PEL，但实际重试由业务表层补偿器驱动）。
- 提交到池失败时直接 ack（兜底，避免消息卡死）。

**backlog 监控**（[reportBacklogMetrics](file:///h:/GYT-CODE/rag-retrievalOps/backend/internal/ragqueue/redis_stream.go#L216-L244)）：

- 单独 goroutine，每 10s 调一次 `XInfoGroups(stream)`。
- 取出 `Pending`（已投递未 ack）+ `Lag`（未投递的积压数），合计为 `backlog`。
- 通过 `metrics.SetConsumerBacklog` 暴露给 Prometheus，告警系统可以基于"backlog > 阈值持续 5 分钟"触发。

### 深入追问

**Q：消息的可见性超时怎么处理？卡死的消费者会让消息永远不可见吗？**

- Redis Stream 的 PEL 不会自动让消息超时返回 New 队列，需要靠 `XCLAIM` 把超时消息从一个消费者偷到另一个消费者。
- 当前实现没有显式 XCLAIM 逻辑，但补偿器从业务表层兜底——即便 Stream PEL 有遗留，业务侧仍然能把 retrying 任务推回处理。
- 这是个 trade-off：Stream PEL 长期堆积会让 Pending 数虚高，但不影响实际处理。

**Q：MaxLen=10000 + Approx=true 是为了什么？**

- 防止 Stream 无限增长——批量上传 10 万文档场景下，Stream 长度爆炸会让 Redis OOM。
- Approx=true 表示"近似裁剪"，性能比精确裁剪高一个数量级（背后用 RDB radix tree 的节点级裁剪）。
- 代价是裁剪粒度不严格——可能短时间超过 10000 一点点，但收敛后会回到上限。

**Q：消费者有暂停开关吗？**

- 有：`IsKnowledgeIngestPaused()` 在 handler 第一行就检查（[consumer.go:45-48](file:///h:/GYT-CODE/rag-retrievalOps/backend/internal/ragqueue/consumer.go#L44-L48)）。运维触发暂停后新消息进来直接被忽略（不影响 ack），用于紧急情况下临时关闭入库链路。

## Q13：Provenance（溯源）信息是怎么挂到每个 chunk 的？检索阶段怎么用？

### 基础答案

`AnnotateChunksWithProvenance`（[provenance.go](file:///h:/GYT-CODE/rag-retrievalOps/backend/internal/documentparser/provenance.go#L9-L45)）在切分完成后给每个 chunk 补充溯源元数据：

- 根据 chunk 的 `child_start_offset / child_end_offset`，在 `NormalizedDocument.Blocks` 中找出"区间相交的 blocks"，把它们的 `block_ids` 写到 chunk metadata。
- 同时计算这些 blocks 跨越的 `page_start / page_end` 和平均 OCR `confidence`。
- 对 `NormalizedDocument.Tables` 也做同样的相交检测，写入 `table_ids`。
- 写入 `normalized_path`（本 sidecar 文件路径），用于事后回到 NormalizedDocument 重建上下文。

### 深入追问

**Q：检索阶段拿到这些 provenance 字段能做什么？**

- **按页码定位**：管理后台预览答案时直接定位到 PDF 第几页第几块。
- **OCR 置信度兜底**：低 confidence chunk 可以在结果页上加"低质证据"标记，提醒人工核对。
- **表格特殊渲染**：`table_ids` 命中时检索结果可以直接展示原表，而不是切碎的文本。
- **重切分**：若 `chunking_route` 标了"非预期策略"（比如本应该走 OCR-Aware 却走了默认），可以离线触发重切。
