## 使用说明

### 给面试官

- 本阶段题目密度大，建议挑选 4-6 道题深入问，而不是把 10 道题平铺。
- 全链路追踪的"看点"在于**分层与权衡**——要听候选人能否说清"为什么不用一套方案搞定"。
- 标注 ⭐ 的题是核心题，必须能答出来；标注 ⭐⭐ 的题是亮点题，能答好就是加分项。
- 追问到第 2 层答不上来很正常，关键看候选人是否理解"分层设计"的内在逻辑。

### 给新人

- 全链路追踪的最大坑是"知道有 Trace ID 但说不清楚为什么要这么多 ID"——务必用本文档把每个 ID 的职责、串联关系想透。
- 答题时要主动画出"三层追踪 + 一张矩阵"的心智模型，避免变成"我们用了 Prometheus、CozeLoop、Trace ID"的流水账。
- 代码位置一定要看，面试官会问"这个结构体在哪个文件、长什么样"。

## 三层追踪心智模型（看题前先建立）

```
┌─────────────────────────────────────────────────────────────┐
│ 第三层：横向治理串联（Trace ID 矩阵）                          │
│  request_id ↔ experiment_id ↔ cost_trace_id                  │
│             ↔ audit_trace_id ↔ release_id                    │
│  作用：把"检索 / 实验 / 成本 / 审计 / 发布"五条业务链路打通    │
└─────────────────────────────────────────────────────────────┘
              ▲                                  ▲
              │                                  │
┌─────────────┴─────────────┐    ┌──────────────┴──────────────┐
│ 第一层：检索引擎内部追踪    │    │ 第二层：跨系统可观测性         │
│ DebugTrace（数据流转模型）  │    │ CozeLoop Span（调用链模型）  │
│ 7 阶段 before/after 快照    │    │ Service / User / Thread 维度 │
│ 用于"为什么这条召回了"        │    │ 用于"谁慢了、谁挂了"         │
└────────────────────────────┘    └─────────────────────────────┘
```

**一句话区分**：
- **第一层（DebugTrace）** 关心**数据**——每个文档在哪一阶段进、哪一阶段出、Score 怎么变；
- **第二层（CozeLoop）** 关心**调用**——每个 Span 的耗时、状态、上下游关系；
- **第三层（Trace ID 矩阵）** 关心**业务**——一次请求在 5 张业务表中的横向打通。

## Q1 ⭐：这个项目的全链路追踪是怎么做的？为什么不直接用 OpenTelemetry 一套搞定？

### 基础答案

项目里追踪并不是一个"模块"，而是**三层叠加**：

| 层级 | 解决的问题 | 模型 | 技术实现 |
|------|------------|------|----------|
| 第一层：检索引擎内部追踪 | "为什么这条召回了 / 这条没召回" | **数据流转模型**：每个阶段都打 before/after 快照 | `DebugTrace` 结构体 + 7 阶段填充 |
| 第二层：跨系统可观测性 | "谁慢了 / 谁挂了" | **调用链模型**：Span 嵌套 + 时间轴 | CozeLoop SDK（封装在 looptrace 包） |
| 第三层：横向治理串联 | "一次检索关联了哪个实验 / 花了多少钱 / 谁审批的" | **ID 矩阵**：N 个 trace_id 横向 join | `kb_retrieve_log` 里挂 5 个 ID 字段 |

**为什么不全用 OpenTelemetry？** OpenTelemetry 擅长第二层"调用链"，但**不擅长第一层"数据流转"**。原因有两点：

1. **数据语义重**：检索每一步要快照的不是"耗时和 status"，而是**整个文档列表**——`DebugTrace.RouteHits` 里要带文档内容、Score、RerankScore、Metadata，再用 OpenTelemetry 的 Attribute 塞进去会爆 Span 大小限制，而且不利于结构化查询。
2. **业务语义化**：DebugTrace 的字段是检索领域专属的（`SparseTerms`、`PerTermCandidateCounts`、`ParentFillReason`、`DropReasons`），用通用 Span 表达会丢失业务含义；前端"检索调试实验室"需要直接对这些结构化字段渲染图表，而不是在 Span 树里翻 Attribute。

所以选择是：**OpenTelemetry 风格的 Span（CozeLoop）只承担调用链，DebugTrace 承担数据流转**，两者通过 `request_id` 在最外层挂钩。

### 深入追问

**Q：那为什么不把 DebugTrace 也改成 Span？比如每个阶段一个 Span，把文档塞 Attribute？**

可以，但代价大：
- **存储成本**：CozeLoop / 一般 APM 都是按 Span 数量和大小计费，每次检索写 7 个 Span × 平均 30 个文档 × 每个文档若干 KB，量级直接放大几十倍；
- **查询语义错位**：APM 的查询是"按 service / endpoint 看 P99"，DebugTrace 的查询是"给我 request_id=xxx 的完整数据流转"——后者其实就是按主键查，存关系库即可；
- **关闭代价不同**：CozeLoop 通过环境变量开关，关掉就是真不写；DebugTrace 是检索逻辑里就近构造的内存对象，开销是常量级的，可以始终开启。

所以这两层是**互补**关系，而不是"OpenTelemetry 能不能取代 DebugTrace"的取代关系。

**Q：三层追踪有没有共用的"骨架"？**

有，骨架是 **`request_id`**。它在请求入口生成，会同时被：
- 写进 DebugTrace 的日志和 `kb_retrieve_log.request_id` 主键；
- 设置成 CozeLoop 当前 Span 的 Tag；
- 透传到 cost_trace、audit_event 表里作为外键。

可以理解为 `request_id` 是"穿过三层追踪的那根线"。

## Q2 ⭐：DebugTrace 里有哪 7 个阶段？每个阶段都记录了什么？

### 基础答案

DebugTrace 的核心结构体在 [debug_trace.go#L92-L102](file:///h:/GYT-CODE/rag-retrievalOps/backend/internal/milvus/retrieval/debug_trace.go)：

```go
type DebugTrace struct {
    RouteHits      []RouteDebugHit       // 1. 多路召回
    Fusion         FusionDebugInfo       // 2. 融合
    Dedupe         DedupeDebugInfo       // 3. 去重
    Rerank         RerankDebugInfo       // 4. 重排
    Filter         FilterDebugInfo       // 5. 过滤/截断
    ParentChild    ParentChildDebugInfo  // 6. 父子补全
    FinalResults   []DebugDocument       // 7. 最终结果
    StageDurations map[string]int64
    Degradation    DegradationDebugInfo
}
```

每个阶段记录的核心字段：

| 阶段 | 关键记录 | 解决的问题 |
|------|----------|------------|
| ① RouteHits（多路召回） | 每路 query、命中文档、`SparseTerms`、`TermSources`、`PerTermCandidateCounts`、`CandidateCountBefore/After`、路由耗时 | "Dense 召了几个、Sparse 召了几个、稀疏 query 切成了什么 term" |
| ② Fusion（融合） | `Before / After`、`DenseParticipationCount / SparseParticipationCount`、`PrimaryRouteDistribution` | "RRF 之后哪条文档来自哪一路、谁主导了最终排序" |
| ③ Dedupe（去重） | `BeforeCount / AfterCount / Removed` | "去掉的几个是什么、是不是误杀了" |
| ④ Rerank（重排） | `Before / After`、`RerankModel / RerankVersion`、`Fallback / Reason` | "重排前后 Score 怎么变、是否触发了降级" |
| ⑤ Filter（过滤截断） | `BeforeCount / AfterCount / Removed / DropReasons / TruncateReason` | "Token 预算砍掉了几个、Score Cliff 砍掉了几个、各占比" |
| ⑥ ParentChild（父子补全） | `ChildHits / ParentContexts / FallbackReason` | "子块命中后是否回填了父块、回填失败原因是什么" |
| ⑦ FinalResults（最终结果） | 完整 `DebugDocument` 列表 | "最终交给大模型的就是这些" |

每个阶段填充的关键代码在 [hybrid_search.go#L330-L580](file:///h:/GYT-CODE/rag-retrievalOps/backend/internal/milvus/retrieval/hybrid_search.go)，按数据流顺序依次为：

```go
debugTrace.RouteHits   = ...   // L331
debugTrace.Fusion      = ...   // L454
debugTrace.Dedupe      = ...   // L469
debugTrace.Rerank      = ...   // L505
debugTrace.ParentChild = ...   // L528
debugTrace.Filter      = ...   // L555
debugTrace.FinalResults = ...  // L564
```

### 深入追问

**Q：为什么 ParentChild 在 Filter 前？常理感觉应该先过滤再补父块？**

这是设计权衡：
- **先父子补全**：父子文本会被纳入 Token 预算的计算，过滤阶段才能基于"补完父块后的真实 Token 占用"做截断决策；
- **先过滤**：会出现"过滤完只剩 5 个，再补父块又把 Token 顶爆，最后还要二次截断"的反复修剪。

代码里这两步紧挨着（L528 → L541 ApplyTokenBudgetGuard → L555 写 Filter 快照），ParentChild 是"补"，Filter 才是"截"，顺序不能颠倒。

**Q：Dedupe 为什么用 `RemovedFusedSnapshots` 而其他阶段用 `RemovedSnapshots`？**

两者都在 [debug_trace.go#L135-L202](file:///h:/GYT-CODE/rag-retrievalOps/backend/internal/milvus/retrieval/debug_trace.go)：
- `RemovedSnapshots(before, after []*schema.Document)`：用 `*schema.Document` 直接比对；
- `RemovedFusedSnapshots(before []*FusedDocument, after []*schema.Document)`：处理融合后的 `FusedDocument`，因为 Dedupe 阶段输入是带融合分的 `FusedDocument`。

差异本质是"融合后的对象多了 Score 和 PrimaryRoute 字段"，需要单独的 Snapshot 路径来保留这些信息。

**Q：StageDurations 既有 `dense_ms / sparse_ms` 又有 `embedding_ms / search_ms`，会不会重复？**

不会，分工不同：
- `dense_ms / sparse_ms` 是**路由级**耗时（在 hybrid_search 里赋值，[hybrid_search.go#L355-L358](file:///h:/GYT-CODE/rag-retrievalOps/backend/internal/milvus/retrieval/hybrid_search.go)）；
- `embedding_ms / search_ms / postprocess_ms / rerank_ms` 是**阶段级**耗时（在 SearchMetrics 里），最后通过 [retrieval_debug_trace_v2.go#L466-L480](file:///h:/GYT-CODE/rag-retrievalOps/backend/api/handler/kb/retrieval_debug_trace_v2.go) 的 `buildDebugStageDurations` 合并展示。

前端拿到的是合并后的 map，可以同时画"路由对比图"和"阶段瀑布图"。

## Q3 ⭐⭐：你说"DebugTrace 是数据流转模型，不是调用链模型"，能展开讲讲两者的差异吗？

### 基础答案

这是项目里最有差异化的设计点，也是和市面上 RAG Demo 拉开差距的地方。

**调用链模型（OpenTelemetry / CozeLoop 走的路线）**：
- 核心抽象：`Span`（一次调用）
- 关心的事：父子调用关系、耗时、状态码、错误
- 典型问法："这次请求在哪个 Span 卡住了？"
- 典型可视化：火焰图、瀑布图

**数据流转模型（DebugTrace 走的路线）**：
- 核心抽象：`Stage`（一次数据变换）
- 关心的事：每个阶段输入了什么、输出了什么、丢弃了什么、为什么丢弃
- 典型问法："这条文档在哪一阶段被淘汰的？"
- 典型可视化：阶段对比表、文档生死图

**举个具体例子**：用户说"我搜'阿里云负载均衡 SLB 配置'，召回结果里没有最权威的那篇文档"。

- 用调用链模型：能告诉你 dense_ms = 80ms，sparse_ms = 120ms，rerank_ms = 200ms，**但回答不了"为什么没召回"**。
- 用数据流转模型：能定位到 `RouteHits[sparse]` 里 SparseTerms = ["阿里云", "负载", "SLB", "配置"]，`DroppedTerms = {"均衡": "stopword"}`，原来"均衡"被当成停用词丢了，导致最关键的 term 漏掉，所以那篇含"负载均衡"全词的权威文档没召回。

这是调用链模型给不出来的诊断深度。

### 深入追问

**Q：那 DebugTrace 里能不能也加上 Span 风格的"父子关系"？**

理论上可以，但项目刻意没做。原因是：DebugTrace 的 7 个阶段是**线性的、强绑定的**——多路召回必然在融合前、重排必然在过滤前——这种线性流水线用"数组"表达比"树"清晰。强行套 Span 树反而要给每个阶段编 SpanID、ParentSpanID，徒增冗余。

**Q：那不同请求之间的 DebugTrace 怎么对齐？比如要分析"昨天 1 万条请求中有多少在 Filter 阶段被砍超过 50%"？**

这是项目最有意思的地方——DebugTrace 写到 [kb_retrieve_log.DebugTrace](file:///h:/GYT-CODE/rag-retrievalOps/backend/internal/model/kb_retrieve_log.go#L121) 这个 longtext 字段里，**同时**关键聚合字段（DenseHits / SparseHits / TruncatedCount / DropReasons 计数）也被打平到独立列上。这样：
- 想看单条详情：`SELECT debug_trace FROM kb_retrieve_log WHERE request_id = ?`
- 想做批量统计：`SELECT count(*) FROM kb_retrieve_log WHERE truncated_count > final_count * 0.5`

这就是"明细看 JSON、聚合看列"的混合模型。OpenTelemetry 系的方案要做这种聚合分析就很笨拙，要么打回数据仓库，要么走指标系统，链路就拉长了。

**Q：DebugTrace 不可避免地体积大（带原文），怎么控制存储成本？**

代码里有几个细节：
1. [cloneDebugMetadata](file:///h:/GYT-CODE/rag-retrievalOps/backend/internal/milvus/retrieval/debug_trace.go#L238-L250) 主动 **过滤 `source` 字段**，因为 source 通常嵌套整个文档原文；
2. `DebugTrace` 字段在数据库 ORM 标签里写的是 `gorm:"type:longtext"` 但 `json:"-"`，**列表查询不返回**，只在 V2 详情接口按 request_id 单独取；
3. 配合"按租户 / 按时间"的归档策略（实际上线时通过定时清理 / 冷归档解决，不在本模块代码内）。

## Q4 ⭐：检索日志 kb_retrieve_log 里挂了哪些 Trace ID？这个 ID 矩阵是怎么设计的？

### 基础答案

`kb_retrieve_log` 表里有 **5 个核心 Trace ID 字段**：

```go
RequestID     string  // 唯一索引：请求级主键
ExperimentID  string  // 索引：A/B 实验组
CostTraceID   string  // 索引：成本追踪
AuditTraceID  string  // 索引：审计追踪
ReleaseID     string  // 索引：策略发布版本
```

详见 [kb_retrieve_log.go#L40-L50](file:///h:/GYT-CODE/rag-retrievalOps/backend/internal/model/kb_retrieve_log.go)。

每个 ID 对应一张业务表：

| ID 字段 | 关联表 | 业务含义 |
|---------|--------|----------|
| `request_id` | 自身（唯一索引） | 一次检索请求的全局唯一 ID |
| `experiment_id` | 实验组管理表 | 这次请求被分到哪个 A/B 实验组 |
| `cost_trace_id` | [kb_cost_trace](file:///h:/GYT-CODE/rag-retrievalOps/backend/internal/model/kb_cost_trace.go) | Embedding / Retrieval / Rerank / LLM 各阶段花了多少钱 |
| `audit_trace_id` | [kb_audit_event](file:///h:/GYT-CODE/rag-retrievalOps/backend/internal/model/kb_audit_event.go) | 这次请求触发了哪些审计事件（敏感操作、权限变更） |
| `release_id` | 策略发布表 | 这次请求生效的是哪个策略版本（灰度阶段） |

**矩阵的本质**：这是一个"以 request_id 为中心的横向 join 网络"。任意一个 ID 都可以反向追到 request_id，再从 request_id 拉出完整上下文。

### 深入追问

**Q：为什么不直接用一个 `trace_id` 串到底？**

因为这 5 个 ID **生命周期和粒度完全不同**：
- `request_id`：1 次检索 = 1 个，毫秒级
- `experiment_id`：1 个实验可能持续几周，覆盖几百万次检索
- `cost_trace_id`：1 次检索 = 1 个成本流水（成本可能涉及多个 token 调用聚合）
- `audit_trace_id`：1 次审计事件 = 1 个，但 1 次检索可能触发 0 个或多个审计
- `release_id`：1 个策略版本 = 1 个，覆盖该版本生效期间所有请求

如果强行合一，要么粒度太细（实验组每天换 ID）、要么粒度太粗（成本对不上）。**分而治之**才能各自维护清晰的语义，再用 join 串联。

**Q：5 个 ID 之间的关系是 1:1 还是 N:1？**

看从哪头看：
- 从 `request_id` 看：1 个 request → 1 个 experiment / 1 个 cost / 0..N 个 audit / 1 个 release；
- 从 `experiment_id` 看：1 个 experiment → N 个 request；
- 从 `release_id` 看：1 个 release → N 个 request。

`kb_retrieve_log` 表的索引设计正是为这种 join 优化的：`experiment_id`、`cost_trace_id`、`audit_trace_id`、`release_id` 都建了普通索引，`request_id` 是唯一索引。

**Q：审计事件用 `audit_trace_id` 而不是 `request_id` 关联，为什么？**

## Q5 ⭐⭐：CozeLoop 这一层是怎么集成的？为什么用环境变量做开关而不是配置中心？

### 基础答案

封装在 [looptrace/client.go](file:///h:/GYT-CODE/rag-retrievalOps/backend/internal/observability/looptrace/client.go)，关键设计：

**1. 三个环境变量驱动**：
```go
const (
    envEnabled       = "COZELOOP_ENABLED"
    envServiceName   = "COZELOOP_SERVICE_NAME"
    envDeploymentEnv = "COZELOOP_DEPLOYMENT_ENV"
)
```
另外 SDK 自身读 `COZELOOP_API_BASE_URL / WORKSPACE_ID / API_TOKEN`，封装层只关心"开关 + 公共维度"。

**2. 单例 + sync.Once 懒加载**（[client.go#L34-L66](file:///h:/GYT-CODE/rag-retrievalOps/backend/internal/observability/looptrace/client.go)）：
```go
func InitFromEnv() error {
    initOnce.Do(func() { ... })
    return initErr
}
```
保证多次调用只初始化一次，且失败可见。

**3. 三个对外 API**：
- `StartSpan(ctx, name, spanType)` 返回 `(ctx, span, ok)`，**ok=false 时调用方走旁路**；
- `GetSpanFromContext(ctx)` 从上下文里取当前 Span；
- `TraceHeaders(ctx)` 把 Span 序列化成 HTTP header，方便跨服务透传；
- `ApplyCommonFields` 给 Span 补齐 service / env / userID / threadID / tags 五个公共字段。

**4. 关闭即彻底关闭**：所有公开 API 第一步都是 `if !Enabled() { return... }`，确保关闭时**零开销**——这一点对生产很重要。

**为什么用环境变量而不是配置中心？**

| 维度 | 环境变量 | 配置中心 |
|------|----------|----------|
| 启动时机 | 进程启动前就确定 | 启动后异步拉取 |
| 失败处理 | 启动失败立刻能发现 | 拉取失败可能静默退化 |
| 部署一致性 | 跟容器编排绑定，K8s 友好 | 多了个外部依赖 |
| 灰度需求 | 全量开关足够 | 不需要按用户灰度 |

可观测性是"基础设施级"开关，**不需要也不应该按业务规则动态切换**——它要么全开要么全关。环境变量是最朴素也最稳定的选择。

### 深入追问

**Q：CozeLoop 关掉之后，DebugTrace 还能跑吗？**

能。DebugTrace 完全不依赖 CozeLoop。looptrace 包里所有公开 API 都在 `!Enabled()` 时直接返回 nil/false，调用方判一下就走过去。这正是"两层互补"的好处——任意一层挂了，另一层还在。

**Q：为什么 `ApplyCommonFields` 把 userID / threadID 拎出来当一等公民？**

因为这两个维度**贯穿很多业务场景**：用户级问题排障要按 userID 过滤、Agent 多轮对话要按 threadID 串联。把它们从 tags 里抽出来变成方法签名，避免每个调用方都自己 `SetTags(map[...]interface{}{"user_id": ...})`，减少样板代码也防止字段名拼错。

**Q：Span 是怎么关联到我们前面说的 `request_id` 的？**

通过 tag 注入。在请求入口拿到 `request_id` 之后，会调用 `ApplyCommonFields(ctx, span, userID, threadID, map[string]interface{}{"request_id": rid, ...})`，这样在 CozeLoop 上按 `request_id` tag 一搜就能拉出整条 Span 链路。这是第二层和第三层的接合点。

## Q6 ⭐：除了三层追踪，metrics 体系是怎么搭的？和追踪是什么关系？

### 基础答案

metrics 在 [rag_metrics.go](file:///h:/GYT-CODE/rag-retrievalOps/backend/internal/observability/metrics/rag_metrics.go)，使用 Prometheus client_golang 实现。核心指标分 4 大类：

**① 检索请求级**
- `rag_retrieve_requests_total{status, error_code}` Counter
- `rag_retrieve_duration_seconds{status}` Histogram（桶：10ms ~ 8s）
- `rag_retrieve_result_count` Histogram

**② 路由级**
- `rag_retrieve_route_requests_total{route, status, error_code}`
- `rag_retrieve_route_duration_seconds{route, status}`
- `rag_retrieve_route_hits{route}`
- `rag_retrieve_route_contribution_total{route, strategy, release_stage}`

**③ 策略 / 治理级**
- `rag_retrieve_strategy_total{strategy, release_stage, reason, status}`
- `rag_retrieve_empty_reason_total{strategy, release_stage, empty_reason}`
- `rag_retrieve_rewrite_total{strategy, release_stage, applied}`
- `rag_retrieve_rerank_duration_seconds{release_stage, strategy, model, status}`
- `rag_release_rollback_total{action, target_stage}`

**④ 缓存 / 入库 / 错误 / 队列**
- `rag_semantic_cache_*`、`rag_ingest_*`、`rag_errors_total{scope, error_code}`、`rag_consumer_backlog/pending/lag`

**Metrics 和追踪的关系**：

| 维度 | Metrics | 追踪（Trace） |
|------|---------|---------------|
| 数据形态 | 时间序列、聚合、定长 | 单条记录、原始、变长 |
| 适合问题 | "P99 是多少 / 错误率多少" | "request_id=xxx 详情" |
| 存储 | Prometheus / VM | MySQL（kb_retrieve_log）+ APM |
| 排障姿势 | 先看 metrics 大盘 → 发现异常 → 取异常时段的 request_id → 按 ID 拉 trace | |

**典型协作流程**：监控大盘报警 `rag_retrieve_duration_seconds{status="success"}` P99 飙到 3s → 拉异常时段的 request_id 列表 → 按 request_id 调 V2 Debug Trace 接口 → DebugTrace.StageDurations 里看到 rerank_ms 占了 2.5s → 定位到 Rerank 慢。

metrics 是"鹰眼"，trace 是"显微镜"，缺一不可。

### 深入追问

**Q：标签维度（label cardinality）爆炸是怎么控制的？**

代码里有几个细节：
1. **`sanitizeLabel`** 函数（[rag_metrics.go#L423-L444](file:///h:/GYT-CODE/rag-retrievalOps/backend/internal/observability/metrics/rag_metrics.go)）：把所有 label 转小写、非字母数字一律替换成下划线、空值给 fallback；防止"用户传脏数据导致 Prometheus 序列爆炸"；

## Q7 ⭐：用户反馈"刚才那条搜索结果不对"，你按 request_id 怎么排障？

### 基础答案

**标准排障流程（三步走）**：

**第 1 步：拿 request_id 定位检索日志**
```sql
SELECT * FROM kb_retrieve_log WHERE request_id = ?
```
对应代码：[KBRetrieveLog.GetByRequestID](file:///h:/GYT-CODE/rag-retrievalOps/backend/internal/model/kb_retrieve_log.go#L144-L154)

先看 `result_status / error_code / error_msg / empty_reason / refusal_reason` 几个字段，定位**结果是怎么样的**：

- `result_status = error` → 看 `error_code`，是否 timeout / route_error / rerank_failed
- `result_status = no_result + empty_reason = empty-after-retrieve` → 召回空，下一步看 RouteHits
- `result_status = no_result + empty_reason = empty-after-fusion` → 融合后没东西
- `result_status = filtered_out` → 看 truncate_reason / refusal_reason
- `result_status = success` 但用户说不对 → 进第 2 步看 DebugTrace

**第 2 步：拉 DebugTrace 详情**

调 V2 Debug Trace API（[retrieval_debug_trace_v2.go](file:///h:/GYT-CODE/rag-retrievalOps/backend/api/handler/kb/retrieval_debug_trace_v2.go)），按 7 个阶段一层层看：
1. **改写**：original_query → rewritten_query 是否合理
2. **RouteHits**：dense / sparse 各召回几条，sparse 的 SparseTerms / DroppedTerms 有没有问题
3. **Fusion**：融合后是否还包含期望文档
4. **Rerank**：fallback 字段是否 true（重排没生效）
5. **Filter**：DropReasons 计数，是不是被截断丢了
6. **ParentChild**：父块补全是否成功

**第 3 步：横向 join 治理表**

如果上面没看出问题，按 ID 矩阵横向 join：
- `release_id` → 查策略版本表，看是不是刚好踩到一个有 bug 的灰度版本
- `experiment_id` → 看是不是命中了实验组的 B 组（新策略）
- `cost_trace_id` → 看 Embedding / Retrieval 阶段是否异常昂贵（暗示某步反复重试）
- `audit_trace_id` → 看是不是触发了权限拒绝（permission_result 字段）

**Q：如果用户给的不是 request_id，而是"我大概 11:30 搜的"，怎么办？**

## Q8 ⭐：StageDurations 这个 map 是怎么设计的？为什么不用结构体？

### 基础答案

`StageDurations map[string]int64` 在 [debug_trace.go#L100](file:///h:/GYT-CODE/rag-retrievalOps/backend/internal/milvus/retrieval/debug_trace.go) 的设计是**有意为之的弱类型**，原因是：

**1. 阶段集合不闭合**
不同检索路径触发的阶段不一样：
- 单路检索没有 `dense_ms / sparse_ms`
- 不开父子补全时没有 `parent_fill_ms`
- 不开 Rerank 时没有 `rerank_ms`

如果用结构体，要么写一堆指针字段（很丑），要么每次加新阶段就改结构体（破坏性变更）。map 做"开放集合"更灵活。

**2. 上下游能"叠加"**
[buildDebugStageDurations](file:///h:/GYT-CODE/rag-retrievalOps/backend/api/handler/kb/retrieval_debug_trace_v2.go#L466-L480) 这个函数把：
- SearchMetrics 里的 `embedding_ms / search_ms / postprocess_ms / rerank_ms`（结构化字段）
- DebugTrace 里的 `dense_ms / sparse_ms / total_ms / ...`（map）

合并到一个 `map[string]int64` 输出给前端：

```go
func buildDebugStageDurations(metrics retrieval.SearchMetrics, debugTrace *retrieval.DebugTrace) map[string]int64 {
    result := map[string]int64{
        "embedding_ms":   metrics.EmbeddingMs,
        "search_ms":      metrics.SearchMs,
        "postprocess_ms": metrics.PostprocessMs,
        "rerank_ms":      metrics.RerankMs,
    }
    if debugTrace == nil || len(debugTrace.StageDurations) == 0 {
        return result
    }
    for key, value := range debugTrace.StageDurations {
        result[key] = value
    }
    return result
}
```

DebugTrace 的 map 优先级更高（因为更细粒度）。这种"基础结构 + 扩展 map"的合并模式让前端只面对一个统一的 key-value 列表。

**3. 前端按需画图**

前端拿到 map 之后，可以按 key 关键字（包含 "_ms"）自动渲染瀑布图，不用维护"已知阶段名单"。增加新阶段时，前端自动支持。

### 深入追问

**Q：那用 map 类型安全怎么保证？比如 key 拼错了怎么办？**

通过 **常量集中定义**（在写入侧就把所有 key 名字管控起来）。代码里各处写 map 的位置都是字面量（`"dense_ms"`, `"sparse_ms"`, `"rerank_ms"`, `"total_ms"`），其实存在改进空间——可以提取常量。这一题是面试时如果候选人指出来，会是个加分点（说明真的看了代码且有自己的判断）。

**Q：这个设计和 Prometheus Histogram 有什么区别？**

完全不同维度的东西：
- StageDurations 是**单条请求**内的"阶段-耗时"映射，是 trace 维度的"快照"
- Prometheus Histogram 是**多条请求**的"耗时-频次"分布，是 metrics 维度的"分布"

举例：StageDurations 告诉你"这条请求 rerank 花了 200ms"，Histogram 告诉你"过去 1 小时 rerank P99 是 500ms"。

## Q9 ⭐⭐：Degradation（降级追踪）是怎么做的？哪些场景会触发？

### 基础答案

`DegradationDebugInfo` 在 [debug_trace.go#L85-L90](file:///h:/GYT-CODE/rag-retrievalOps/backend/internal/milvus/retrieval/debug_trace.go) 定义：

```go
type DegradationDebugInfo struct {
    Enabled          bool   `json:"enabled"`
    Reason           string `json:"reason,omitempty"`
    FallbackStrategy string `json:"fallback_strategy,omitempty"`
    ErrorCode        string `json:"error_code,omitempty"`
}
```

**它要回答 4 个问题**：是否降级、为什么降级、降到了哪个备份策略、对应的错误码是什么。这 4 个字段对应一个完整的"降级故事"。

**已经在代码里实现的降级触发场景**（[hybrid_search.go](file:///h:/GYT-CODE/rag-retrievalOps/backend/internal/milvus/retrieval/hybrid_search.go)）：

| 触发位置 | Reason | FallbackStrategy | 业务含义 |
|----------|--------|------------------|----------|
| L361 双路召回任一失败 | `route_error` | `continue_with_available_routes` | Dense 或 Sparse 单路挂了，继续用另一路 |
| L568 Rerank 失败 / 跳过 | rerank 自带 reason 或 `rerank_fallback` | `use_pre_rerank_order` | 重排没生效，使用融合后的原始顺序 |
| L575 Evidence Gate 降级通过 | `evidence_gate_degraded` | `return_results_without_strict_evidence_gate` | 证据门禁因异常无法严格判定，先返回结果 |
| 接口层 V2 兜底 | `legacy_debug_trace_missing` | `basic_trace_fallback` | 旧版日志没有 DebugTrace 字段，用 SearchMetrics 兜底渲染 |

**为什么降级也要追踪？** 因为"系统看起来工作正常但实际上走了备份策略"是最危险的状态——SLO 表面达标，但用户体验已经降级。把降级事件显式刻在 trace 里，能保证：
1. 排障时第一时间看到"这次响应其实是降级的"，不会被假象误导；
2. 监控可以基于 `Degradation.Enabled = true` 做单独的告警，区分"真正的健康"和"带病工作"。

### 深入追问

**Q：降级 Reason 字段为什么是字符串而不是枚举？**

字符串保留扩展性。不同检索路径会引入不同的降级原因，强枚举会导致每加一个新场景都要改全局代码。但同时项目对常用 reason 用了**驼峰风格的语义化字符串**（`route_error / rerank_fallback / evidence_gate_degraded`），事实上的"软枚举"——既保持灵活，又便于后续梳理统计。

**Q：多次降级怎么处理？比如 Rerank 失败 + Evidence Gate 降级同时发生？**

代码里目前是**最后写入者覆盖**——L568 写 rerank 降级，L575 又会被 evidence_gate 覆盖。这是一个简化处理，因为：
1. 业务上能同时触发的降级场景较少；
2. 真正排障时通过 RouteHits / Rerank.Fallback / FilterDropReasons 等结构化字段能交叉印证。

如果要做严格的"多降级叠加追踪"，可以把 Degradation 改成 `[]DegradationDebugInfo`，但目前还没有强需求。

**Q：降级追踪如何和 metrics 联动？**

通过 `release_rollback_total` Counter 这个指标：[ObserveReleaseRollback](file:///h:/GYT-CODE/rag-retrievalOps/backend/internal/observability/metrics/rag_metrics.go#L329-L335)。当上层判断进入降级路径时主动调一次，metrics 上看降级率，trace 上看降级原因，两层都齐。

## Q10 ⭐⭐：V2 Debug Trace API 是怎么组织响应的？为什么要做 ContractGaps 这个字段？

### 基础答案

V2 接口的入口在 [buildRetrievalDebugTraceResponse](file:///h:/GYT-CODE/rag-retrievalOps/backend/api/handler/kb/retrieval_debug_trace_v2.go#L165-L409)。它做了两件事：

**1. 数据汇聚**：把三个数据来源（`KBRetrieveLog` 落库字段、内存 `SearchMetrics`、内存 `DebugTrace`）合并成一个**对前端友好的扁平响应结构** `retrievalDebugTraceResponse`。这里的核心是**优先级**——内存里的 SearchMetrics > DebugTrace > 落库 logEntry，因为：
- SearchMetrics 是"刚算完最准确"
- DebugTrace 是"快照可能略晚"
- logEntry 是"持久化兜底"

具体代码细节体现在大量 `firstNonEmptyString(searchMetrics.X, logEntry.X)` 这种"主备取值"模式上。

**2. 契约缺口标注**：当部分阶段数据缺失时，**主动告诉调用方"哪些字段我没填"**——通过 `ContractGaps []string` 字段：

```go
response.ContractGaps = []string{
    "route_hits",
    "fusion_results",
    "dedupe_results",
    "rerank_results",
    "filter_results",
    "parent_child.child_hits",
    "parent_child.parent_contexts",
}
```

这是非常重要的设计——**让缺失变得显式**。前端拿到 `ContractGaps` 时能：
- 在 UI 上展示"这部分数据未采集，可能是旧版本日志"的提示；
- 跳过该阶段的图表渲染；
- 反馈给后端做"日志合规性"统计。

### 深入追问

**Q：为什么要重新定义一份 `retrievalDebugTraceResponse` 结构体？直接返回 DebugTrace 不行吗？**

不行，三个原因：
1. **聚合维度多源**：响应需要混合 logEntry / metrics / DebugTrace，单一结构体表达不了；
2. **前端语义优先**：响应字段名（`fusion_results / rerank_results / parent_child / topk_decision`）是按前端"检索调试实验室"页面的卡片划分的，不是按后端内存模型；
3. **版本兼容**：内部 DebugTrace 升级时不要影响外部契约，加一层映射就能稳住接口。

**Q：`firstNonEmptyString(searchMetrics.X, logEntry.X)` 这种模式重复很多，没考虑提取吗？**

考虑过。但每个字段的"主备取值规则"略有差异（有时只看 metrics 不看 log，有时反过来；有时还要带 trim 处理），统一抽象后反而不如显式更清晰。这是"代码重复 vs 抽象代价"的经典权衡——选择保留少量重复换取可读性。这其实也是 Go 风格的一种体现。

**Q：UnsupportedClaims 的特殊处理是干什么的？**

[retrieval_debug_trace_v2.go#L397-L399](file:///h:/GYT-CODE/rag-retrievalOps/backend/api/handler/kb/retrieval_debug_trace_v2.go) 里有这一段：
```go
if len(response.CitationCheck.UnsupportedClaims) == 0 && logEntry != nil && logEntry.UnsupportedClaimCount > 0 {
    response.ContractGaps = append(response.ContractGaps, "citation_check.unsupported_claims")
}
```

含义：日志里说有 N 条不支持的引用，但内存 SearchMetrics 没保留具体 claims 文本——这种"统计数 vs 详情"的不一致也要标注成契约缺口，提示前端"这块没法展开看明细"。这是契约缺口检测的精细化案例。
