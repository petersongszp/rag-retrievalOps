## 写在前面：为什么这个模块值得讲

简历里写"做过 RAG"的人遍地都是。**真正能在面试里把一个项目讲出"运维感"和"工程感"的人极少**。"全链路追踪"恰好就是这种话题——它不是一个具体算法、不是一个具体 API 的封装，而是**一套贯穿系统全身的"看得见"的能力**。

讲得好，会让面试官觉得你"真的把项目运营过、不是只跑通过一遍 demo"。讲得不好，会变成"我们用了 Prometheus、CozeLoop、写了个 trace_id"这种听上去人人都做过的流水账。

**这套话术的目标**：让你在面试官追问 3 层之内都能稳住，并且能反过来引导 ta 关注你设计的"亮点"。

## 第一部分：30 秒电梯介绍（追踪模块版）

**场景**：你在自我介绍里把"全链路追踪"作为重点提了一嘴，面试官接话："哦你们追踪是怎么做的？"

**模板**：

> "我们的追踪不是一套'方案'，而是**三层叠加的能力**——
>
> 第一层是**检索引擎内部的数据流转追踪**，叫 DebugTrace，把一次检索拆成多路召回、融合、去重、重排、过滤、父子补全 7 个阶段，每个阶段都打 before/after 文档快照；
>
> 第二层是**跨系统的调用链追踪**，基于字节的 CozeLoop 做 Span 级追踪，通过环境变量开关；
>
> 第三层是 **Trace ID 矩阵**，检索日志里挂 5 个 ID——request_id、experiment_id、cost_trace_id、audit_trace_id、release_id，把检索、实验、成本、审计、发布五条业务链路横向打通。
>
> 这三层不是冗余，**是各管一类问题**——DebugTrace 答'为什么这条没召回'，CozeLoop 答'谁慢了'，Trace ID 矩阵答'这次请求关联了哪些治理动作'。"

### 这段话的设计意图

- **"三层叠加"** 这个说法马上区别于"一套追踪"——面试官 80% 没听过这种说法，会被钩住。
- **每层一句话定位**——避免泥潭式描述，让面试官能记住三个标签。
- **三层各管一类问题** 这句话最关键，它把"为什么需要三层"的合理性讲清楚了，避免被追问"为什么不用一套搞定"时崩盘。

### 风险点

- 不要在 30 秒里就掏 7 个阶段细节——那是 3 分钟版本的内容。
- 不要说"我们参考了 OpenTelemetry"——很容易被追问"那为什么不直接用"，给自己挖坑。要说"用 CozeLoop"或者"OpenTelemetry 风格的 Span"。

## 第二部分：3 分钟深入介绍（追踪模块版）

**场景**：面试官说"展开讲讲那个 DebugTrace"。

**模板**：

> "好，我具体讲下。
>
> **先讲背景**：一开始我们排障特别痛。用户说'刚搜的那条结果不对'，我们后端只能拿到一个 request_id 和最后的文档列表——但**中间发生了什么完全是黑盒**。是改写改坏了？是 Sparse 没召回？是 Rerank 翻了？是 Filter 砍多了？只能本地复现，效率极低。
>
> **DebugTrace 就是为了解决这个'数据流转黑盒'**。
>
> 我们把一次检索的完整数据流定义成 7 个阶段：
>
> 1. **RouteHits**——每路召回的 query、命中文档、Sparse 切词、停用词过滤情况
> 2. **Fusion**——RRF 融合前后的文档列表，每条文档来自哪一路
> 3. **Dedupe**——去重前后计数、被去掉的是哪些
> 4. **Rerank**——重排前后 Score 变化、是否触发降级
> 5. **ParentChild**——子块命中后是否补全父块、补全失败原因
> 6. **Filter**——Token 预算 / Score Cliff 砍掉了几个、各占比
> 7. **FinalResults**——最终交给大模型的列表
>
> 每个阶段都打 before/after 文档级快照，所以**任何文档在任何一阶段被淘汰都能追溯**。
>
> **设计上有个有意思的地方**：DebugTrace 不是 OpenTelemetry 风格的 Span 树，而是'数据流转模型'。Span 关心的是'调用关系和耗时'，DebugTrace 关心的是'数据怎么变'。一次检索的 7 个阶段是线性的、强绑定的，用数组而不是树表达。同时检索体积大（带原文），如果走 Span 会爆 APM 的存储和查询；放进 MySQL longtext 字段反而便宜——按 request_id 主键查就够了。
>
> **再讲第二、第三层**：CozeLoop 那一层我们用得比较克制——只在跨服务调用、外部模型调用这些点打 Span，**关键是关闭时零开销**，封装层第一行就是 `if !Enabled() return`。Trace ID 矩阵那一层是把 5 个业务 ID 都挂在 kb_retrieve_log 上，索引设计就是为了横向 join——任何一条检索都能反查对应的实验、成本、审计、发布版本。
>
> **我重点做的工作**是 [xxx]——比如把 7 阶段的 before/after 字段定义清楚、把 ContractGaps 这种'让缺失显式'的契约设计落地、配合前端搭检索调试实验室页面等等。"

### 节奏把控

- **0:00-0:30**：背景"排障痛点"（建立共情）
- **0:30-1:30**：DebugTrace 7 阶段（打硬货）
- **1:30-2:00**：数据流转 vs 调用链（拉差异化）
- **2:00-2:30**：第二三层概述（建全景）
- **2:30-3:00**：你做了什么（落到自身）

## 第三部分：高频追问应对话术

下面是面试官最爱问的题，每题给"基础回答 + 一个亮点细节"。

### Q1：你们这套追踪和 OpenTelemetry 是什么关系？为什么不直接用？

**基础回答**：

> "OpenTelemetry 解决的是'调用链追踪'，本质是 Span 树——它擅长'谁调谁、谁慢了、谁挂了'。我们项目里第二层 CozeLoop 走的就是这条路线。
>
> 但**第一层 DebugTrace 走的是'数据流转模型'**——它要快照的不是耗时，而是每个阶段的整个文档列表。如果硬塞进 OpenTelemetry 的 Attribute，会爆 Span 大小限制；而且 APM 系统的查询语义是'按服务 / 接口看 P99'，不是'按 request_id 翻明细'，根本不适合。
>
> 所以两者是**互补关系**——OpenTelemetry / CozeLoop 处理调用层，DebugTrace 处理数据层，通过 request_id 对齐。"

**亮点细节**：

> "其实我们做这个决策的时候做过一次试算——按平均 30 个文档、7 个阶段算，每条请求要写大约 200 个 Span，每个 Span 平均 2KB Attribute，加起来一条请求 400KB。一天 100 万次检索就是 400GB Span 数据，按市面 APM 的计费就是上千美金/天。用 MySQL longtext 一行存，加上字段裁剪（[cloneDebugMetadata](file:///h:/GYT-CODE/rag-retrievalOps/backend/internal/milvus/retrieval/debug_trace.go#L238-L250) 主动过滤 source 字段），单条压缩到 几 KB - 几十 KB，整体存储成本能降一两个数量级。这是一个**实打实的工程权衡**。"

### Q2：DebugTrace 7 个阶段顺序是怎么定的？为什么 ParentChild 在 Filter 前？

**基础回答**：

> "7 个阶段顺序就是检索流水线的实际执行顺序：先多路召回、再 RRF 融合、再去重、再重排、再补父块、再过滤截断、最后输出。
>
> ParentChild 在 Filter 前是个有意思的设计点——直觉上觉得'先过滤干净再补父块'更省事，但实际**反过来**。原因是父子块会显著增加 Token 占用，如果先过滤再补父块，会出现'好不容易砍到 5 条，一补又顶爆 Token 预算'，再砍一次的反复修剪。所以**先补全再统一截断**才能让 Filter 一次性拿到真实的 Token 占用做决策**。"

**亮点细节**：

> "代码里这两步紧挨着——先 [parentChild.Fill](file:///h:/GYT-CODE/rag-retrievalOps/backend/internal/milvus/retrieval/hybrid_search.go#L525-L527)，紧跟着 [ApplyTokenBudgetGuard](file:///h:/GYT-CODE/rag-retrievalOps/backend/internal/milvus/retrieval/hybrid_search.go#L541)。Filter 阶段的 DebugDocument 快照是在 budget guard 之后才打的（[hybrid_search.go#L555](file:///h:/GYT-CODE/rag-retrievalOps/backend/internal/milvus/retrieval/hybrid_search.go)），所以 Filter 的 BeforeCount 就是'已补完父块的文档数'——这种细节是新人接手时容易踩的坑，我们加了注释和测试覆盖。"

### Q3：你说"数据流转模型"，能举个例子说说它和调用链相比的诊断深度差异吗？

**基础回答**：

> "举个真实场景。用户搜'阿里云负载均衡 SLB 配置'，召回结果里没有那篇最权威的文档。
>
> 用调用链模型，我能告诉你 dense_ms = 80ms，sparse_ms = 120ms，rerank_ms = 200ms，**但回答不了'为什么没召回'**。
>
> 用 DebugTrace 的数据流转模型，我能定位到 RouteHits[sparse] 里 SparseTerms = ['阿里云', '负载', 'SLB', '配置']，DroppedTerms = {'均衡': 'stopword'}——原来'均衡'被当成停用词丢了，导致最关键的 term 漏掉，含'负载均衡'全词的权威文档自然没召回。
>
> **这是调用链模型给不出来的诊断深度**。"

**亮点细节**：

> "其实这种场景用 OpenTelemetry 的 Attribute 也能记录（把 SparseTerms 塞进 Span Attribute），但**前端要做'检索调试实验室'页面，按阶段画对比表**——这种结构化展示需要的是 SQL/JSON 查询，不是 Span 树查询。所以 DebugTrace 的字段定义就是为前端 UI 卡片量身打造的，比如 RouteHits 里的 PerTermCandidateCounts、DropReasons 计数 map、PrimaryRouteDistribution——每个字段背后都对应一个图表组件。"

### Q4：5 个 Trace ID 看起来挺多，能简化成一个吗？

**基础回答**：

> "不能。这 5 个 ID 生命周期和粒度完全不同：
>
> - request_id：1 次检索 = 1 个，毫秒级
> - experiment_id：1 个实验持续几周，覆盖几百万次请求
> - cost_trace_id：1 次检索 = 1 个成本流水，但成本可能聚合多个 token 调用
> - audit_trace_id：1 次审计 = 1 个，1 次检索可能触发 0~N 个审计
> - release_id：1 个策略版本覆盖该版本生效期所有请求
>
> 强行合一要么粒度太细（实验组每天换 ID）、要么粒度太粗（成本对不上）。**分而治之** 才能各自维护清晰语义，再用 join 串联——这就是 [kb_retrieve_log](file:///h:/GYT-CODE/rag-retrievalOps/backend/internal/model/kb_retrieve_log.go#L40-L50) 里 5 个 ID 字段都建索引的原因。"

**亮点细节**：

> "其中 audit_trace_id 这个 ID 设计有个细节——审计事件的主键不是 request_id，因为审计动作可能由非检索操作触发（管理员批准权限、删除文档等）。所以 [kb_audit_event](file:///h:/GYT-CODE/rag-retrievalOps/backend/internal/model/kb_audit_event.go#L29-L30) 表里 AuditTraceID 是必填、RequestID 是可选——这是把'审计追踪'和'检索追踪'解耦的关键设计。如果用一个 trace_id 串到底，这种 0..N 关系就表达不了。"

### Q5：CozeLoop 怎么集成的？为什么用环境变量做开关？

**基础回答**：

> "封装在 [looptrace/client.go](file:///h:/GYT-CODE/rag-retrievalOps/backend/internal/observability/looptrace/client.go)，三个要点：
>
> 1. **三个环境变量驱动**：COZELOOP_ENABLED / SERVICE_NAME / DEPLOYMENT_ENV，配合 SDK 自身读 BASE_URL / WORKSPACE_ID / TOKEN；
>
> 2. **sync.Once 单例懒加载**：保证多次调用只初始化一次，失败可见；
>
> 3. **关闭即彻底关闭**：所有公开 API 第一行都判 `if !Enabled() return`，关闭时**零开销**——这对生产很重要。
>
> 用环境变量而不是配置中心，是因为可观测性是基础设施级开关，不需要按业务规则动态切换；环境变量启动前就确定，K8s 友好，失败立刻能发现。"

**亮点细节**：

> "代码里 [ApplyCommonFields](file:///h:/GYT-CODE/rag-retrievalOps/backend/internal/observability/looptrace/client.go#L103-L122) 这个函数把 service / env / userID / threadID / tags 五个字段拎成一等公民——尤其 userID 和 threadID 单独参数化。这是因为这两个维度贯穿很多业务排障场景：用户级问题按 userID 过滤、Agent 多轮对话按 threadID 串联。把它们从 tags map 里抽出来变方法签名，**减少样板代码也防止字段名拼错**——这种小细节是工程化项目和 demo 项目的差别所在。"

### Q6：metrics 和追踪是什么关系？

**基础回答**：

> "metrics 和 trace 是'鹰眼'和'显微镜'的关系——
>
> - metrics 是**时间序列、聚合、定长**，回答'P99 是多少 / 错误率多少'；
> - trace 是**单条记录、原始、变长**，回答'request_id=xxx 详情'。
>
> **典型协作**：监控大盘报警 P99 飙到 3s → 拉异常时段 request_id 列表 → 按 ID 调 V2 Debug Trace → StageDurations 里看到 rerank_ms 占了 2.5s → 定位到 Rerank 慢。**先看 metrics 找异常时间窗口，再用 trace 钻明细**，这是标准排障姿势。"

**亮点细节**：

> "项目里 metrics 有个细节叫 [sanitizeLabel](file:///h:/GYT-CODE/rag-retrievalOps/backend/internal/observability/metrics/rag_metrics.go#L423-L444)——所有 label 值进入 Prometheus 前先转小写、非字母数字替换成下划线、空值给 fallback。这是为了**防止 label cardinality 爆炸**——比如某天上游传了个带空格 / 中文 / 特殊字符的 strategy 名进来，会导致 Prometheus 序列空间爆炸。同时我们刻意**不把高基数字段做 label**——user_id / kb_id / request_id 都不在 label 里，这些属于 trace 域；route ∈ {dense, sparse}、status ∈ 已知枚举——这是 metrics 标签设计的基本功。"

### Q7：用户给你一个 request_id，你怎么排障？

**基础回答**：

> "三步走：
>
> 第一步：[KBRetrieveLog.GetByRequestID](file:///h:/GYT-CODE/rag-retrievalOps/backend/internal/model/kb_retrieve_log.go#L144-L154) 查检索日志，先看 result_status / error_code / empty_reason / refusal_reason 几个字段，定位结果是'错了'、'空了'还是'拒了'；
>
> 第二步：调 V2 Debug Trace API，按 7 阶段一层层看——改写、RouteHits（特别是 SparseTerms 和 DroppedTerms）、Fusion、Rerank（看 fallback）、Filter（看 DropReasons）、ParentChild；
>
> 第三步：横向 join——release_id 看是不是踩了 bug 灰度版本、experiment_id 看是不是命中了 B 组新策略、cost_trace_id 看是不是某步反复重试了。"

**亮点细节**：

> "有个细节是处理'旧日志没 DebugTrace 字段'的情况。代码里在 [retrieval_debug_trace_v2.go#L384-L407](file:///h:/GYT-CODE/rag-retrievalOps/backend/api/handler/kb/retrieval_debug_trace_v2.go) 里加了**契约缺口标注**——当 debugTrace == nil 时，会用 SearchMetrics 兜底构造 RouteHits（虽然没有原文级细节，但路由级数字还在），同时把缺失的字段名写进 ContractGaps 数组，告诉前端'这部分没数据'。这是'不可观测'和'假装可观测'的关键区别——**缺数据要明确告诉调用方哪里缺**，而不是默默返回空数组让前端误以为'没数据 = 没问题'。"

### Q8：StageDurations 为什么用 map 不用结构体？

**基础回答**：

> "**阶段集合不闭合**——单路检索没有 dense_ms / sparse_ms，不开父子补全没有 parent_fill_ms，不开 Rerank 没有 rerank_ms。用结构体要么写一堆指针字段、要么每加一个新阶段就改结构体（破坏性变更）。
>
> map 做'开放集合'更灵活，**前端可以按 key 关键字（包含 _ms）自动渲染瀑布图**，新加阶段不用改前端代码。"

**亮点细节**：

> "在 V2 接口层有个 [buildDebugStageDurations](file:///h:/GYT-CODE/rag-retrievalOps/backend/api/handler/kb/retrieval_debug_trace_v2.go#L466-L480) 函数——它把 SearchMetrics 里的结构化字段（embedding_ms / search_ms / postprocess_ms / rerank_ms）和 DebugTrace 里的 map（dense_ms / sparse_ms / total_ms）合并到一起输出。这种'结构化基础 + 扩展 map'的模式让前端只面对一个统一的 key-value 列表。**取舍**：缺点是没有强类型，key 拼错就静默丢失；改进方向是提取一组常量集中管理。这一点在面试时如果你主动说出来，是个加分点——说明你不是只看了代码、还有自己的判断。"

### Q9：Degradation 这个降级追踪具体追什么？

**基础回答**：

> "DegradationDebugInfo 4 个字段——Enabled / Reason / FallbackStrategy / ErrorCode，对应一个完整的降级故事：是否降级、为什么、降到哪个备份策略、错误码是什么。
>
> 实际触发场景有 4 个：
>
> 1. 双路召回任一失败 → 走 'continue_with_available_routes'
> 2. Rerank 失败 → 'use_pre_rerank_order'（用融合后的原始顺序）
> 3. Evidence Gate 异常 → 'return_results_without_strict_evidence_gate'
> 4. 旧日志缺 DebugTrace → 'basic_trace_fallback'
>
> **为什么降级也要追踪**？因为'看似工作正常但走了备份策略'是最危险的状态——SLO 表面达标，用户体验已经退化。把降级显式刻在 trace 里，监控可以基于 Degradation.Enabled 单独告警。"

**亮点细节**：

> "代码里有个**潜在改进点**：当前 Degradation 是单一对象，多次降级会被覆盖（[hybrid_search.go#L568](file:///h:/GYT-CODE/rag-retrievalOps/backend/internal/milvus/retrieval/hybrid_search.go) 写 rerank 降级，[L575](file:///h:/GYT-CODE/rag-retrievalOps/backend/internal/milvus/retrieval/hybrid_search.go) 又会被 evidence_gate 覆盖）。当前简化处理是因为同时多降级场景较少，且 RouteHits / Rerank.Fallback / DropReasons 等结构化字段能交叉印证。如果未来要严格追踪'多降级叠加'，可以改成 `[]DegradationDebugInfo`——这是面试官如果想深挖时一个不错的话题点。"

### Q10：ContractGaps 这个字段是干嘛的？

**基础回答**：

> "它是**让数据缺失变得显式**的契约设计。
>
> V2 接口构造响应时，如果发现某些阶段数据没采集（比如旧版本 DebugTrace 缺失），就把缺失字段名写进 `ContractGaps []string` 返回给前端。前端拿到后能：
>
> 1. UI 展示'此部分数据未采集，可能是旧版本日志'；
> 2. 跳过该阶段图表渲染；
> 3. 反馈给后端做'日志合规性'统计。
>
> 这是'不可观测'和'假装可观测'的关键区别——**缺数据要主动告知，而不是默默返回空数组**。"

**亮点细节**：

> "代码里有个精细案例：[retrieval_debug_trace_v2.go#L397-L399](file:///h:/GYT-CODE/rag-retrievalOps/backend/api/handler/kb/retrieval_debug_trace_v2.go) 单独处理 UnsupportedClaims——如果日志里 UnsupportedClaimCount > 0 但 SearchMetrics 没保留具体 claims 文本，就追加一条 'citation_check.unsupported_claims' 到 ContractGaps。**统计数和详情的不一致也算契约缺口**——这种细致的'缺什么明说什么'是把追踪体系做成'可信'的关键。"

## 第四部分：我设计这套追踪体系的故事

> 这一段是给你"自我介绍 / 项目深挖"环节用的故事化叙事——比生硬的功能清单更有说服力。

**【背景】**

> "做这套追踪是被'排障痛点'倒逼出来的。
>
> 项目早期，用户反馈'刚才那条搜索结果不对'，我们手里只有一个 request_id 和最终的文档列表——但中间发生了什么，对我们来说是黑盒。是改写改坏了？是 Sparse 没召回？是 Rerank 翻了？还是 Filter 砍多了？只能本地复现，每次定位一个问题要花半天。"

**【转折】**

> "我后来意识到——**这个问题用 OpenTelemetry / 普通 APM 是解不了的**。APM 强项是调用链：谁调谁、谁慢、谁挂；但我们要的是'数据怎么变'——这个文档进来了什么 score、出去什么 score、被谁淘汰、为什么淘汰。这是另一个维度。
>
> 所以我提出了 DebugTrace 的'数据流转模型'：把检索拆成 7 个阶段，每个阶段打 before/after 文档级快照。这个模型和 Span 树并不冲突——它们是互补的：APM 管调用层，DebugTrace 管数据层。"

**【落地的取舍】**

> "落地过程有几个非常具体的取舍：
>
> **取舍 1**：DebugTrace 体积大（带原文），存哪里？最后选了 MySQL longtext + JSON。理由是检索的查询模式就是'按 request_id 主键查'，关系库够用；APM 系统按服务/接口聚合的查询模式根本不匹配。
>
> **取舍 2**：阶段耗时用 map 还是结构体？最后选了 map。理由是阶段集合不闭合（单路 / 双路 / 开父子 / 不开父子各不一样），map 做开放集合更灵活，前端按 key 关键字自动渲染。
>
> **取舍 3**：Trace ID 要不要合一？最后保留了 5 个独立 ID（request / experiment / cost / audit / release）。理由是它们生命周期完全不同，强行合一会扭曲业务语义。"

**【后续演进】**

> "DebugTrace 上线后，排障效率有了**质变**——以前拍脑袋猜 + 复现要半天，现在按 request_id 查 → 看 7 阶段 → 30 秒定位到根因。但我们没停在这里，又往上加了两层：
>
> 1. **CozeLoop Span 层**：补上调用链可观测性，跨服务慢调用一眼可见；
> 2. **Trace ID 矩阵层**：在 kb_retrieve_log 里挂 5 个业务 ID，把检索和实验、成本、审计、发布五条业务链路打通。任意一个 ID 都能反查 request_id，再从 request_id 拉出完整上下文。
>
> 这就形成了**三层叠加**的追踪体系——每层都有自己擅长的问题域，三层加起来，'看得见'的能力就完整了。"

**【收尾自我评价】**

> "我觉得这个模块最有价值的不是任何一个具体技术点，而是**把'追踪'当成产品来设计**——不是堆 SDK，而是先想清楚'要解决什么问题'，再选择对应的数据模型。这是从'写代码'到'做工程'的一道坎，我感觉这个项目让我把这道坎跨过去了。"

## 第六部分：避坑提醒

| 坑 | 表现 | 正确姿势 |
|----|------|----------|
| **死磕术语** | 把 OpenTelemetry / Jaeger / Tempo 等名词堆出来 | 用"调用链模型 vs 数据流转模型"这种自定义说法，更显思考深度 |
| **吹牛 7 阶段** | 说"我设计了 7 个阶段" | 7 个阶段是检索流水线本来的结构，你的贡献是"把它们结构化追踪起来"，不要把流水线设计揽到自己头上 |
| **混淆 ID 用法** | 把 request_id 当 trace_id、把 experiment_id 当 user_id | 一定要按业务语义说："5 个 ID 各自有不同的生命周期和粒度" |
| **CozeLoop = OpenTelemetry** | 直接说"我们用了 OpenTelemetry" | 准确说："我们用 CozeLoop SDK，是 OpenTelemetry 风格的调用链追踪" |
| **混淆 metrics 和 trace 的角色** | 说"metrics 用来排障" | 应该说："metrics 用来发现异常时间窗口，trace 用来钻明细，两者协作" |

## 第七部分：一页纸速查表

> 面试前 5 分钟扫一遍，建立瞬时记忆。

### 三层追踪 心智模型

| 层 | 名称 | 模型 | 关键技术 | 解决问题 |
|----|------|------|----------|----------|
| L1 | DebugTrace | 数据流转 | 7 阶段 before/after 快照 | "为什么这条没召回" |
| L2 | CozeLoop Span | 调用链 | OpenTelemetry 风格 Span | "谁慢了 / 谁挂了" |
| L3 | Trace ID 矩阵 | 横向治理 | 5 个 ID + 索引 join | "关联了哪些业务动作" |

### DebugTrace 7 阶段（按数据流顺序）

```
RouteHits → Fusion → Dedupe → Rerank → ParentChild → Filter → FinalResults
   ↓          ↓        ↓        ↓          ↓           ↓          ↓
多路召回    RRF融合   去重    重排序    补父块      过滤截断    最终结果
```

每阶段必记字段：
- RouteHits：SparseTerms / DroppedTerms / PerTermCandidateCounts
- Fusion：Before / After / PrimaryRouteDistribution
- Rerank：Fallback / Reason / RerankModel
- Filter：DropReasons / TruncateReason
- ParentChild：ChildHits / ParentContexts / FallbackReason

### Trace ID 矩阵 5 兄弟

| ID | 生命周期 | 关联表 |
|----|----------|--------|
| request_id | 1 次检索 = 1 个 | kb_retrieve_log（自身唯一索引） |
| experiment_id | 1 个实验 = 1 个 | 实验组管理表 |
| cost_trace_id | 1 次检索 = 1 个流水 | kb_cost_trace |
| audit_trace_id | 1 个审计动作 = 1 个 | kb_audit_event |
| release_id | 1 个策略版本 = 1 个 | 策略发布表 |

### CozeLoop 三个要点

1. 三个环境变量（ENABLED / SERVICE_NAME / DEPLOYMENT_ENV）
2. sync.Once 单例懒加载
3. 关闭时所有 API 立刻 short-circuit，零开销

### Metrics 4 大类

1. 检索请求级（rag_retrieve_*）
2. 路由级（rag_retrieve_route_*）
3. 策略治理级（rag_retrieve_strategy_* / rewrite_* / rerank_*）
4. 缓存 / 入库 / 错误 / 队列

### 排障三步走

```
1. GetByRequestID → 看 result_status / error_code / empty_reason
2. V2 Debug Trace → 按 7 阶段一层层看
3. 横向 join → release_id / experiment_id / cost_trace_id / audit_trace_id
```

### Degradation 4 大触发点

```
1. route_error                  → continue_with_available_routes
2. rerank_fallback              → use_pre_rerank_order
3. evidence_gate_degraded       → return_results_without_strict_evidence_gate
4. legacy_debug_trace_missing   → basic_trace_fallback
```

### 几个高频亮点关键词

- **数据流转模型 vs 调用链模型** ←—— 最大的差异化
- **ContractGaps（让缺失变显式）** ←—— 体现工程审美
- **三层互补（任意一层挂了其他还能用）** ←—— 体现可靠性思维
- **sanitizeLabel 防 cardinality 爆炸** ←—— 体现监控基本功
- **5 个 ID 分而治之** ←—— 体现领域建模能力
- **rerank_ms 既出现在 SearchMetrics 又出现在 StageDurations 的合并模式** ←—— 体现 API 设计能力
