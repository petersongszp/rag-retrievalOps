## 写在前面：怎么把检索引擎讲漂亮

这一段代码涉及面广（改写 / 召回 / 融合 / 重排 / 父子 / 门禁），最容易踩两个坑：

1. **平铺直叙**：从改写一路报到门禁，讲完面试官只记住"做得挺多"，没记住你强在哪。
2. **细节崩盘**：在某个不熟的点上被追问到第 3 层，答崩。

对策是**主线 + 钩子 + 防守**：
- **主线**：用"为什么是混合检索 + 多策略治理"作为统一叙事，所有模块都是为了"对抗单一信号失效"而存在。
- **钩子**：在自我介绍时主动埋"双路并发 / 两次 TopK / 拒答门禁 / Title Boost"等关键词，引面试官追问你最熟的那个。
- **防守**：不熟的题先承认"这块我了解到 xxx 层级，再深的设计是 yyy 同事负责的"——比硬编强。

## 第一部分：电梯介绍（30 秒）

**模板**：

> "我在项目里负责的是**检索引擎核心**，也就是从'用户输入 query'到'交给 LLM 生成'之间的整条流水线。它不是一个简单的'调一下 Milvus'，而是一套**多策略融合 + 多重门禁**的链路：双路并发召回（Dense + Sparse）、可切换的融合策略（MinMax / RRF）、两次动态 TopK 决策、可超时降级的重排、父子检索补上下文，再到证据门禁做拒答兜底。
>
> 整条链路的核心理念是**对抗单一信号失效**——不靠任何一路把命运压死，每一步都给降级路径。"

### 这段话的钩子

- "**双路并发**"：勾出"为什么不是顺序"的追问 → 你回答 P95 延迟取最长那一路 + sync.WaitGroup 收口。
- "**MinMax / RRF**"：勾出"两种融合的取舍"的追问 → 你回答 minmax 区分度高但敏感、RRF 抗噪。
- "**两次 TopK**"：勾出"为什么不是一次"的追问 → 你回答召回前没有真实分数，召回后才能看 cliff/flat。
- "**证据门禁**"：勾出"什么时候拒答"的追问 → 你回答 5 个拒答理由 + 阈值按 query 复杂度缩放。

### 注意

- 不要在 30 秒里把 12 个阶段全念一遍，**只点 3-4 个钩子**就够。
- 把"对抗单一信号失效"这句话作为统一旗帜，反复呼应，让面试官记住你的设计哲学。

## 第二部分：3 分钟深入介绍

**模板**：

> "好，具体讲下检索引擎。
>
> **第一层：要解决什么问题。**
>
> 普通 RAG 通常只有一路向量检索，但生产环境有 3 个明确的痛点：
> 1. 单路召回有死角——向量擅长语义但对专有名词、缩写漂；BM25 擅长字面但对同义改写丢；
> 2. 没有兜底——某个外部依赖（reranker / embedding API）抖一下就影响主链路；
> 3. 没有可观测性——出问题不知道是改写、召回、融合、重排还是过滤哪一步丢掉的。
>
> 我们这套引擎围绕这三个痛点做：**双路混合 + 多重降级 + 全链路 metadata 落盘**。
>
> **第二层：核心设计。**
>
> - 改写阶段做了 5 类策略组合，dense 走保守、sparse 走激进，模型改写只跑 10% shadow 流量做 A/B；
> - 召回阶段 dense 和 sparse 用 sync.WaitGroup 并发，单路失败仍能降级运行；
> - 融合默认 MinMax + 0.7/0.3 权重，RRF 作为可切策略保留，把每路 contribution 都写进 metadata；
> - 重排接的是 ConfigurableReranker，主用 bge-reranker，超时降级到本地 Jaccard，挂 fallback reason；
> - 父子检索支持 4 种填充策略，默认 section_window，在保留命中精度的同时补全上下文；
> - 两次动态 TopK：召回前看 query 特征定先验 K，重排后再看分数分布做战略调整；
> - 最后是证据门禁，6 种 outcome / 5 种拒答理由，阈值按 query 复杂度缩放。
>
> **第三层：我具体做了什么。**
>
> 我重点参与了 [xxx]——比如我修过一个 Bug：ScoreCliff Guard 在重排后误用旧融合分截断，导致相关结果被静默丢弃。修法是把分数读取改成 `rerank_score → fusion_score → score` 的 fallback 链。这是 [topk_policy.go#readScoreCliffScore](file:///h:/GYT-CODE/rag-retrievalOps/backend/internal/milvus/retrieval/topk_policy.go#L313-L328) 里的真实注释。"

### 第三层的"我做了什么"怎么编

如果是**真做过**：直接讲你做过的具体一段（如修 bug、加策略、调阈值），强调"为什么这么改 / 改完前后指标对比"。

如果是**学过没做过**：选一个**很具体的小点**讲，例如：
- "我跑通了 fusion_test.go 里 RRF 和 MinMax 的对比，验证了短查询下 RRF 更稳定，长查询下 MinMax 区分度更好"；
- "我用 mock 跑了证据门禁的 5 个拒答路径，画了状态机图"；
- 切忌说"整个引擎都是我做的"——一追问就崩。

## 第三部分：12 道核心题的双层应答

下面每题都给两层：**基础回答**（保命线，2 句话讲清楚）和**亮点细节**（拉分项，给 1-2 个能展示深度的具体细节）。

---

### Q1 ⭐ 整个流水线长什么样？

**基础回答**：

> "12 个阶段：改写 → 第一次 TopK → 双路并发召回（dense + sparse）→ 融合 → 去重 → Title Boost → 重排 → 第二次 TopK + ScoreCliff → 父子填充 → Token Budget Guard → 引用一致性 → 证据门禁。每个阶段都把产物挂到文档 metadata 上，方便 Debug Trace 还原。"

**亮点细节**：

> "整条链路的关键设计是'阶段间靠 metadata 通信'——比如重排会写 `pre_rerank_rank / post_rerank_rank / score_delta`，门禁会读 `rerank_score / evidence_density / citation_support_score`，前端 Debug 面板能逐阶段还原决策过程。日志按 L1（双路召回）/ L2（融合到门禁聚合）/ L5（子阶段错误）分层，便于按链路定位问题。"

**主动埋的钩子**：metadata 接力、Debug Trace、L1/L2/L5 日志分层。

---

### Q2 ⭐ 为什么要做混合检索？

**基础回答**：

> "单路一定有盲区。Dense 擅长语义改写但对专有名词、缩写、版本号漂；BM25 擅长字面但对同义改写直接 0 命中。两者捕捉的相关性信号不重合，所以做 Hybrid 让 dense 兜召回、sparse 锚精确。"

**亮点细节**：

> "我们没用 Milvus 内置 sparse 索引，自己写了一套 BM25：一是因为按 term 拆分召回更可控，每个 term 的 candidate 数能单独埋点（PerTermCandidateCount），方便归因哪个词召回多 / 哪个被 drop 了；二是 BM25 的 K1/B/MinScore 想自己调，不受 Milvus 内置打分曲线绑死。"

**容易翻车的点**：

- 被问"BM25 的 K1 / B 物理含义是什么"——K1 控制词频饱和度（越大越线性），B 控制文档长度归一化（默认 0.75）。不熟就直接说"工程上用经验值 1.2 / 0.75，没自己推过公式"。
- 被问"sparse 路 timeout 怎么设"——默认不设（TimeoutMS=0），靠上层 ctx 控制。

---

### Q3 ⭐ MinMax 和 RRF 怎么选？

**基础回答**：

> "MinMax 是把每路分数归一化到 0-1 后加权求和，区分度高，但对 dense 和 sparse 量级不一致敏感；RRF 只看 rank 不看分数本身，rrf_score = w / (60 + rank)，抗噪强、对量级不敏感。我们默认 MinMax + 0.7/0.3 权重，RRF 作为可切策略放在策略中心。"

**亮点细节**：

> "RRFK=60 是 Cormack 2009 论文实验出来的经典值——大到能压平 rank 之间的细微差，小到不会完全抹掉 rank 信号。MinMax 的坑是当 max == min 时会 NaN，代码里专门做了 `score <= 0 ? 0 : 1` 的 fallback。还有一个隐藏的 trick：dense 0.7 / sparse 0.3 的权重本质是给 dense 一个'信任度溢价'，因为 dense 的离群值更稳定，sparse 的 BM25 容易被某个长文档的 IDF 拉飞。"

**主动埋的钩子**：RRFK=60 的来由、MinMax 的 NaN 防御、dense 信任度溢价。

---

### Q4 ⭐ 查询改写有几种策略？

**基础回答**：

> "5 类，按优先级串：黑名单（直接拦） → rule_based（缩写/别名/typo） → domain_terms（领域词典） → route_specific（dense 保守 / sparse 激进） → model_assisted_shadow（模型改写 10% shadow 采样）。最终输出 dense_query 和 sparse_query 可以分路。"

**亮点细节**：

> "**route-specific 是这套改写最有意思的设计**：dense 是语义匹配，扩同义词反而会稀释主语义，所以只加首选扩展，保守；sparse 是字面匹配，召回靠 term 数量，所以把所有别名都加，激进。代码里 `addExpansion(term, includeDense)` 的 includeDense 参数就是控制这个的。
>
> 模型改写为什么 10% shadow？三个考虑：延迟（模型 100-300ms 直接拖 P95）、漂移（模型可能改飞）、成本（每次都掉钱）。所以哈希采样 10%，用 sha1(query+kb+collection) 分桶保证同 query 命中稳定，方便回放复现。"

**容易翻车的点**：

- 被问"模型改写具体接的什么模型"——如果你不知道接的是什么，就说"接口是 ModelRewriteAssistant，目前线上是 heuristic 兜底实现，生产可换 Qwen / GPT-4"。
- 被问"10% 这个比例怎么定的"——A/B 实验拍的，没有理论根据；高了影响 P95，低了样本不够。

---

### Q5 重排为什么是 Jaccard？

**基础回答**：

> "Jaccard 是 fallback 默认实现，零依赖、几毫秒跑完。生产 reranker 通常对接 bge-reranker / Cohere，用 ConfigurableReranker 包装：主 reranker 加 timeout，超时或报错就降级到 Jaccard，并把 fallback reason（timeout / canceled / error）写进 metrics。"

**亮点细节**：

> "Jaccard 公式是 `final_score = original * 0.7 + lexical * 0.3`，lexical 取 Jaccard(query, content) 和 query_coverage 的最大值——coverage 对短查询更友好。
>
> 一个细节：fallback 跑 Jaccard 时**不能用已 cancel 的 timeout ctx**，会立即退出。所以 ConfigurableReranker 用**原始 ctx**重跑 fallback。这是从一个 P0 故障里学到的——本来 primary 超时已经是降级场景，再因为 ctx 串错变成两次失败就太冤了。"

**主动埋的钩子**：fallback 用原始 ctx、coverage vs Jaccard 取最大、pre/post rank 用于事后审计。

---

### Q6 ⭐ 父子检索为什么需要？4 种策略怎么选？

**基础回答**：

> "父子检索解决的是'切得越小召回越准、但生成上下文越碎'的矛盾——索引时切 child chunk 做向量化，召回命中后用父块或邻居块补上下文再喂给 LLM。我们支持 4 种策略：parent_only / sibling_window / section_window（默认）/ child_first_with_parent_summary。"

**亮点细节**：

> "默认选 section_window 是因为它**对切分不规则更鲁棒**——只要在同一 hierarchy_path 下就算邻居，不像 sibling_window 严格依赖 chunk_index。而且 section_window 里还**叠加了 parent_id 的 fallback expr**：先查 hierarchy_path，再补查 parent_id，提高召回成功率。
>
> 还有一个工程细节：填充失败必须可降级。如果 chunk 缺 parent_id（老数据），代码不会报错，而是挂 `parent_fill_strategy=child_only, parent_fill_reason=parent_child_unavailable` 跳过填充。这种'可观察的降级'比硬抛异常友好得多。
>
> 第二次去重也是设计点：多个 child 命中同一 parent 时，按 `document_id:parent:parent_id` 二次去重，只留 score 最高的，避免上下文重复污染。"

**容易翻车的点**：

- 被问"为什么不用 GraphRAG 那种结构化 retrieval"——回答"GraphRAG 适合实体关系强的场景，我们文档是非结构化技术文档，section_window 已经够用，且实现成本低 1 个数量级"。
- 被问"buildWindowedContent 的 token 估算靠谱吗"——按 utf-8 rune / 4 估算，对英文 OK，对中文偏低（实际 1 个汉字 ≈ 1-2 token）。这是已知的偏差，靠 MaxTokens 留了 buffer。

### Q7 ⭐ 动态 TopK 为什么要两次？

**基础回答**：

> "第一次发生在召回前，只能基于 query 特征（短/长/广/精确）猜个先验 K，否则 candidate_topk 都没法定。第二次发生在重排后，能看到真实分数分布（cliff / flat / balanced）和 evidence_density / parent_diversity 等信号，做战略调整。如果只做一次，要么决策太早（无真实分数），要么太晚（召回阶段已经按错误的 K 拉数据）。"

**亮点细节**：

> "战略 TopK 看 5 个信号：**score_distribution**（cliff/flat/balanced）、**rerank_gap**（top1-top2）、**evidence_density**（强结果占比）、**parent_diversity**（不同父块数）、**dominant_parent_share**（最大父块占比）。每个信号对应一个调整规则，比如 cliff + gap≥0.18 就 K-2，flat 就 K+2，单父块占比≥75% 就 K-1（避免上下文同质化）。
>
> 还有一个真实修过的 Bug：ApplyScoreCliffGuard 早期直接读 `score`，但重排后 `score` 字段没更新（保留的是融合分），导致 cliff guard 用错误的 top 值截断，**静默丢失相关文档**。修法是改成 `rerank_score → fusion_score → score` 的 fallback 链，[topk_policy.go#readScoreCliffScore](file:///h:/GYT-CODE/rag-retrievalOps/backend/internal/milvus/retrieval/topk_policy.go#L313-L328) 里有完整中文注释。"

**主动埋的钩子**：5 个分布信号、修过的 ScoreCliff Bug、MinAnswerChunks 兜底（保至少 N 篇进 prompt）。

### Q8 ⭐ 证据门禁如何工作？

**基础回答**：

> "门禁是流水线最后一关，输出 4 种 outcome：pass / refused / degraded_pass / disabled。拒答理由有 5 种：No-Retrieval-Hit（空召回）、Contradictory-Evidence（top1/top2 一肯一否）、Out-Of-KB-Scope（query token 覆盖率<20%）、Low-Rerank-Confidence（分数或密度低）、Insufficient-Citation-Coverage（引用一致性不达标）。"

**亮点细节**：

> "**阈值不是固定的**，会按 query 特征做'敏感度倍率'——broad_query +12%、短查询 +5%、含 how/why/区别/对比 +5%，上限 1.25x。**阈值越高越容易拒答**——这是反直觉的设计，但符合工程逻辑：广/短/比较类 query 召回风险高，与其勉强答个含混答案，不如拒答让用户细化问题。
>
> Contradictory-Evidence 的判定也有意思：取 top2，要求都 docTouchesQuery（query token 出现在 content），且其中一个含否定语（no/never/不能/无…）另一个不含。能拦住像'Java GC 默认开启吗'召回到一个说开一个说不开的场景，但又不会误杀正常多观点共存的内容。
>
> 拒答必须可观测——`EvidenceGateResult / RefusalReason / CitationSupportScore / EvidenceGateError` 全部回写 metrics，前端能按拒答理由筛流量做 review。"

**主动埋的钩子**：阈值按复杂度缩放、Contradictory 判定逻辑、保守拒答理念。

---

### Q9 引用一致性怎么打分？

**基础回答**：

> "对每个 query 抽 claim（按标点切 + 复合句拆），每个 claim 对每个 doc 打分，公式是 `0.5*lexical_coverage + 0.2*entity_coverage + 0.3*char_3gram_coverage`，字面 substring 命中直接给 0.98。聚合得到 SupportScore，任一 claim < threshold（默认 0.7）就计为 unsupported。"

**亮点细节**：

> "我特别想强调的是 **tryRefineUnsupportedCitations** 这个'反向修复'设计：当 SupportScore 不达标时，**只保留** `citation_supported=true` 的子集重新打分；如果新分数提高了就采纳，否则保留原集合。这是'宁可少而精，不可滥而虚'的工程权衡，比直接拒答更友好。
>
> 还有 entity 提取的设计：含数字、含大写、含 `_-/#+.` 这些 hint 才认为是 entity term——专门为代码标识符（k8s_v1.28 / pre-stop-hook）和版本号设计的。"

**容易翻车的点**：

- 被问"为什么 substring 给 0.98 不给 1.0"——是为了和'多 claim 都完美命中'的边界留区别，避免分数互相覆盖。
- 被问"中文 3-gram 会不会虚抬分数"——会，所以权重只给 0.3，由 lexical_coverage(0.5) 主导。

### Q10 Title Boost 为什么只对短精确查询？

**基础回答**：

> "短精确查询命中标题的信号强度极高——比如用户输 'PreStop hook'，命中 section_title 几乎一定是想找的；但长查询命中标题的信号被稀释，可能是'标题命中但内容浅'。所以只对 runeCount≤12 && termCount≤3 触发，加 +0.30 ~ +0.40 的 boost。"

**亮点细节**：

> "boost 这么重（最高 0.4）会不会破坏分数体系？做了三层防护：1）仅短精确触发；2）score clamp 到 1.0；3）后面还会被 reranker 重新评估。Title Boost 实际上是为了**确保标题命中能进 reranker 的输入 top**，不直接决定最终顺序。
>
> 命中类型有 4 档：section_title 完全相等 / hierarchy_path 完全相等 / hierarchy_path 包含 / section_title 包含。每档对应不同 boost 值，写到 `title_match_boost_reason` 让评测能按命中类型做归因。"

**主动埋的钩子**：三层防护、4 档命中类型、版本号 title-match-boost-v1 留 A/B 余地。

### Q11 去重还做了 ID 之外的什么事？

**基础回答**：

> "三件事：1）按 dedupe key（document_id:chunk_id）合并同条目，保留最高分但合并所有路由的 contrib；2）table-section 抑制——同 document_id 下，table chunk 和包含它的 section chunk 重叠时去掉 section；3）写回融合 / 路由贡献的全套 metadata 供下游使用。"

**亮点细节**：

> "table-section 抑制是入库阶段同时跑了 paragraph 切分和 table-aware 切分的副产品——两种切分都保留能让'找表头'和'找上下文'两类查询都能召回，但喂给模型时如果都进 prompt 就重复了。判定条件叠加：要么 child_offset 完全包含且更长，要么内容包含 4 个 token + 至少 1 个长（≥8 字符）匹配。
>
> 路由贡献合并的细节：`mergeFloatMaps` 取 max（贡献越大越能代表这一路的最佳贡献），`mergeIntMaps` 取 min（rank 越小越好）。这是个看起来不起眼但很容易写反的点。"

**主动埋的钩子**：table 切分双路设计、max vs min 取值、key 4 层 fallback。

### Q12 Filter Expr 的多租户安全怎么做的？

**基础回答**：

> "BuildFilterExpr 把 TenantID / AllowedKBIDs / KBScope / ActiveGlobalKBID / Language / Category 拼成 Milvus 表达式，用 && 串起来。AllowedKBIDs 和 ActiveGlobalKBID 同时存在时是双重收紧，必须既在白名单又是激活 KB——这是租户安全的关键。"

**亮点细节**：

> "**自定义 Expr 的注入风险靠'调用边界'防御**：opts.Expr 只能由可信内部调用方设置，前端可控字段只有 KBScope / Language / Category 这些枚举。这比 SQL 那种'参数化查询'保护要弱，但对内部 API 来说够用——再加防御就是 over-engineering。
>
> 还有个细节：sparse 路在 candidate provider 里也会读 base expr，再拼上 `content like "%term%"`。所以 filter 是**两路都生效**的，不会出现'dense 过滤了，sparse 漏出来'的越权 bug。"

**容易翻车的点**：

- 被问"为什么 metadata key 用引号风格混用"——历史遗留 + Milvus 不同版本对引号容错有差异，统一可以重构但风险大。
- 被问"为什么不做 OR 关系"——业务上目前没有 OR 需求，全是 AND 收紧。

## 第四部分：项目难点叙事（讲故事用）

下面 3 个故事，挑一个你最熟的版本背下来——面试官常问"项目里最有挑战的事"。

### 故事 1：ScoreCliff 的静默丢结果 Bug（强烈推荐）

> "我们 ScoreCliff Guard 之前有个 P1 级 Bug——重排后用错误的 top 值做悬崖截断，**导致相关文档被静默丢弃**。
>
> 触发场景：用户搜'PreStop hook'，本来重排后 top1 是相关文档（rerank_score=0.85），top2-3 也都是相关 chunk（rerank_score=0.7+）。但 cliff guard 读的是 `score` 字段，那是融合后的分数（top1=0.6, top2=0.55），所以 cutoff 算出来是 0.4，正常情况下不该截断。
>
> 但偶发情况下融合分数差距大，guard 就会把 top2-3 截掉——**而被截掉的恰恰是 rerank_score 排名前几的相关文档**。最坑的是这个 bug **不报错、不打日志**，用户只感觉'有时检索结果数比预期少'。
>
> 我定位是先看 Debug Trace，发现 'before-cliff vs after-cliff' 的 doc 列表对不上 metadata 上的 rerank_score 排序，才意识到 guard 用错了分数。修法是把分数读取改成 `rerank_score → fusion_score → score` 的 fallback 链。代码里这段中文注释就是当时 RCA 后留下的：[topk_policy.go#L317-L319](file:///h:/GYT-CODE/rag-retrievalOps/backend/internal/milvus/retrieval/topk_policy.go#L317-L319)。
>
> 教训是：**重排会改变 metadata 的'真实分数'，但融合分数不会自动同步**——任何依赖分数做截断的逻辑都必须明确读哪个字段，并优先读重排后的。"

### 故事 2：Sparse 路超时引发 dense 路雪崩

> "线上某次 Milvus 元数据变更后 sparse 的 like 查询变得很慢（200ms+），但因为 dense / sparse 是 sync.WaitGroup 并发的，dense 跑得快也得等 sparse 跑完——P95 直接从 200ms 飙到 800ms。
>
> 排查发现 SparseRetrieverConfig.TimeoutMS 默认是 0（不超时），完全靠上层 ctx 控制。我们最终的修法是给 sparse 配独立 TimeoutMS=300ms，超时就走降级（标记 fallback_reason=provider_error），让 dense 路结果至少能用。
>
> 这个故事讲两件事：1）混合检索的'木桶效应'是真实存在的，最慢的那一路决定 P95；2）独立超时配置必须给到每一路，不能完全依赖外层 ctx。"

### 故事 3：模型改写 shadow 灰度的 A/B 拉胯

> "上线模型改写时我们一开始想直接 100% 流量切，被压力测试拦住——P95 拉了 200ms。改成 shadow 模式：10% 流量进模型改写但**不替换原 query**，只把扩展词加进 sparse 路，并用 sha1 哈希做稳定分桶。
>
> 一开始用 rand.Float64() 随机采样，回放时同一 query 命中比例不稳定，复现 bug 很麻烦。改成哈希分桶后，**同 query 在不同请求里命中是恒定的**，A/B 数据可信度上来了。
>
> 这套机制后来又复用到了其他实验场景。讲这个故事是想体现：**实验性功能的灰度方案要从'可重复' 而不是'随机'出发**。"

## 第五部分：可主动埋的"亮点钩子"

按面试官追问意图分类，下次自我介绍可以提前抛一个：

| 钩子词 | 可能引出的追问 | 你需要准备的回答 |
|--------|---------------|-----------------|

## 第六部分：容易被追问到崩溃的点（重点防守）

下面这些点是面试官最爱深挖的，**不熟就提前承认 +  借力打力**——比硬编强。

### 1. BM25 公式细节

- 完整公式：`score = Σ IDF(qi) * (f(qi,D) * (k1+1)) / (f(qi,D) + k1*(1-b+b*|D|/avgdl))`
- 不熟就说："我用的是标准 BM25 实现，K1=1.2 / B=0.75 是经验值。具体公式细节是同事写的 SparseInvertedIndex 里实现的，我主要负责调用层。"

### 2. Embedding 模型细节

- 不熟就说："我们用的是 BGE-M3 / OpenAI text-embedding 之类，dim 1024 / 1536，Embedding 缓存层（Redis）我没深入做。"
- 不要硬编"我训练了 embedding"——一追问就死。

### 3. Reranker 模型架构

- 不熟就说："Cross-Encoder 类，输入 [CLS] query [SEP] doc [SEP]，输出 0-1 相关度。具体 BGE-Reranker-v2-m3 的训练细节我没看过，工程上当作黑盒接入。"

### 4. RRF 论文具体内容

- 不熟就说："Cormack 2009，我看过摘要和 K=60 的实验数据，没读完整论文。但 RRF 的核心思想我理解：用 rank 替代 raw score 来抗噪声 / 抗量级差。"

### 5. Milvus 索引类型选择

- 不熟就说："我们用的是 AUTOINDEX，由 Milvus 根据数据规模自动选 IVF_FLAT / HNSW。具体索引参数（nlist / efConstruction）是 SRE 同事调的，我能讲 search 阶段的 ef 参数对召回影响。"

### 6. 评测指标

- 必须熟：Recall@K（前 K 召回的相关比例）、nDCG@K（带位置衰减的相关性）、MRR（首个相关结果的 1/rank 平均）。
- 不熟就说："业务侧主看 Recall@5 和拒答率，工程侧主看 P95 延迟。NDCG 我们离线看，不直接驱动决策。"

### 7. "你最近的优化数据"

- 真做过：直接报数（"P95 从 800ms 降到 250ms / Recall@5 从 0.62 升到 0.71"）。
- 没做过：说"我加入时这部分基线已比较稳定，最近做的更多是策略治理（A/B 实验、灰度）和 bug 修复，没拿到端到端可量化的指标改进"。**诚实比吹牛分高**。
