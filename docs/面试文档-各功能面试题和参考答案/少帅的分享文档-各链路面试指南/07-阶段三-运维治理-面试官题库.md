## Q1 ⭐：什么叫"评测驱动上线"？为什么不能直接灰度上线？

### 基础答案

**评测驱动上线**指的是：任何一次策略/索引/模型的变更，**先在离线评测集上跑出量化指标**，并通过质量门禁（Gate），才允许进入下一步的灰度发布。否则即使灰度，也只是"小范围翻车"而不是"避免翻车"。

我们项目里这条流水线长这样：

```
代码/参数变更
      │
      ▼
组装 StrategyProfile（baseline + candidate）
      │
      ▼
Runner 跑离线评测集 ─── 计算 Recall@K / MRR / nDCG / Citation / 拒答 / P95 延迟
      │
      ▼
EvaluateGate(comparison, thresholds) ── 8 项门禁
      │
      ├─ Passed=true  → 允许进入灰度（internal → 5% → 20% → 50% → 100%）
      └─ Passed=false → 阻塞上线，回到优化迭代
```

核心方法：`Runner.Run` 把 baseline 与 candidate 跑同一份数据集，再调 `EvaluateGate` 出门禁结果。

### 深入追问

**Q：为什么不能"先灰度再看效果"？**

灰度的代价是**真实用户流量**。如果 candidate 的 Recall 实际比 baseline 低 10%，就算只灰度 5%，那 5% 用户体验到的就是"项目变烂了"。而离线评测用的是 ground-truth 数据集，可以在没有用户的环境提前发现这种回归。

**Q：那评测集本身的质量怎么保证？**

评测集是带标注的（`DatasetCase` 里有 `RelevantIDs`、`CitationTargets`、`ExpectedPrimaryRoute`、`MustContainTerms`、`Tags` 等字段），覆盖不同 query 类型与 refusal 场景。`expectsRefusal` 还会专门识别 `out_of_scope`、`insufficient_evidence` 这类 tag，验证拒答是否触发正确。

**Q：评测集怎么避免"过拟合"？**

定期补充用户真实 query 进评测集；对 candidate 同时跑 `RewriteApplied` 子集统计 `RewriteGainDelta`，确保增益不是数据集偏置带来的。

## Q2 ⭐：Gate 门禁具体卡哪些指标？阈值是怎么定的？

### 基础答案

Gate 是一个"多维度联合门禁"，**只要有一项不过就整体 fail**。当前实现卡了 8 个核心维度：

| 维度 | 阈值默认值 | 含义 |
|------|------------|------|
| `recall_at_k_delta` | ≥ 0.08 | candidate 召回必须比 baseline 提升至少 8 个百分点 |
| `mrr_delta` | ≥ 0 | MRR 不能回归 |
| `ndcg_delta` | ≥ 0 | nDCG 不能回归 |
| `citation_accuracy_delta` | ≥ 0 | 引用命中率不能回归 |
| `citation_precision_delta` | ≥ 0 | 引用精确率不能回归 |
| `citation_recall_delta` | ≥ 0 | 引用召回率不能回归 |
| `p95_latency_regression_ratio` | ≤ 0.20 | P95 延迟劣化不能超过 20% |
| `refusal_false_positive_rate` | ≤ 0.05 | 误拒答率不能超过 5% |

另外两条**条件门禁**：

- `rewrite_gain_delta`：当 candidate 启用模型改写或阈值 > 0 时才追加，确保改写带来的实际增益非负。
- `p95_latency_regression_ms`：当配置了绝对 ms 阈值时追加，防止"比例小但绝对值大"的回归。

### 深入追问

**Q：阈值 0.08 / 0.20 / 0.05 是怎么定的？**

经验值，不是拍脑袋：
- Recall +8% 是评测集上"用户能感知到差异"的最小变化幅度——再小就可能是噪声。
- P95 +20% 是延迟容忍上限——超过这个用户能明显感觉到"卡了"。
- 误拒答率 5% 是"宁可漏拒，不能错拒"——错拒会直接被用户骂"为什么我问的好好的不答"。

阈值不是写死，`DefaultGateThresholds` 提供默认值，调用方可以按业务严苛度覆盖（比如金融场景把 P95 阈值降到 5%）。

**Q：为什么 Recall 设了正向门槛（必须 +0.08），而其他指标只是"不回归"（≥ 0）？**

因为这套 candidate 是"带改进诉求上来的"——你升级一个策略不就是为了提升召回吗？没提升 8% 就别上线，免得做无用功。MRR/nDCG 是"伴随指标"，主指标提升时它们顺带保住即可。

**Q：8 项门禁串行 short-circuit，会不会漏掉报错？**

不会。`EvaluateGate` 里 `checks` 数组**全部 8 项都计算完再统一遍历**，只是返回时碰到第一个失败就标记 fail（见循环 `for _, check := range checks`）。这样即使整体 fail，前端依然能看到所有指标的 actual/expected 对比。

## Q3 ⭐：灰度发布是怎么分阶段的？用户被分到哪个阶段是随机的吗？

### 基础答案

灰度发布有 **5 个 Stage**：

```
phase1（兜底）→ internal → small_flow → batch → full
   纯老策略    内部全量   公网 5%   公网 20%~50%  全量
```

对应在 [controller.go](file:///h:/GYT-CODE/rag-retrievalOps/backend/internal/rag/release/controller.go) 里有常量定义：`StagePhase1 / StageInternal / StageSmall / StageBatch / StageFull`。

**用户分桶不是随机的**，是基于 `userID` 的稳定哈希：

```go
func matchesStableBucket(userID uint, percent int) bool {
    if percent <= 0 { return false }
    if percent >= 100 { return true }
    hasher := fnv.New32a()
    _, _ = hasher.Write([]byte(fmt.Sprintf("%d", userID)))
    return int(hasher.Sum32()%100) < percent
}
```

同一个 userID 多次访问，哈希值固定，分桶结果固定——这叫**稳定分桶**。

`Decide` 决策顺序：
1. 如果 phase2 不可用 → 强制 phase1。
2. 如果有运行时 override（紧急回滚或临时强切）→ 优先生效。
3. 否则按配置 `releaseCfg.Stage` 进入 `evaluateStage`。
4. 内部 allowlist / 内部角色 → 直接用 phase2。
5. 普通用户按 stage 命中分桶逻辑。

### 深入追问

**Q：为什么不能用随机分桶？**

随机分桶会出现"同一个用户这次走 phase2 下次走 phase1"，对比效果时数据是噪声，用户体验也割裂。**稳定分桶保证"用户级别一致性"**——一个用户在小流量阶段进了 candidate 桶，他后续所有请求都在 candidate 桶里，便于横向对比。

**Q：Stage 之间怎么切换？谁触发的？**

两条路：
1. **配置切换**（计划内）：改 `cfg.RAG.Release.Stage` 配置项，重新加载。
2. **运行时 override**（紧急）：通过 `SetRuntimeOverride(stage, reason, updatedBy)` 直接覆写内存里的 `runtimeOverride`，**不需要重启服务**。

运行时 override 优先级最高，主要用于灰度过程中发现问题立即回退，或 PM 临时把某个阶段往前推。

**Q：internal 阶段的"内部用户"怎么识别？**

两种方式叠加：
- `UserAllowlist`（白名单 ID 列表，运营手工维护）
- `InternalRoles`（默认 `["admin"]`，可配置扩展）

只要命中其中之一，无论当前 stage 是什么，都强制走 phase2。这就是为什么"内部测试"可以在公网用户还是 phase1 时就能用上新策略。

**Q：为什么用 FNV 哈希不用 MD5/SHA？**

灰度判定每次请求都要算，FNV 是非加密哈希，速度比 MD5 快一个数量级，而且分桶用的"打散均匀性"对加密强度无要求。

## Q4 ⭐⭐：A/B 实验和灰度发布有什么区别？

### 基础答案

灰度和 A/B 实验长得像，但目的不同：

| 维度 | 灰度发布（Release） | A/B 实验（Experiment） |
|------|---------------------|------------------------|
| 目的 | 把"已经验证好"的新策略**安全推全** | 在真实流量上**对比两个策略哪个更好** |
| 持续时间 | 短（几小时到几天，目标是推到 100%） | 长（多天甚至数周，需要统计显著性） |
| 决策依据 | 看"有没有翻车"（错误率/延迟/空结果） | 看"哪边指标更好"（效果对比 delta） |
| 是否要跑评测 | 上线前必须过 Gate | 实验过程持续累计 baseline / candidate 样本 |
| 流量分配 | 按 stage 比例（5%/20%/50%/100%） | 按 `traffic_ratio` 分桶（一般 50/50） |
| 影子模式 | 无 | 有（`ShadowMode=true` 不影响真实结果） |

A/B 实验的实现见 [state.go](file:///h:/GYT-CODE/rag-retrievalOps/backend/internal/rag/experiment/state.go)：

- `ConfigRecord` 是实验配置：strategy_type、baseline_version、candidate_version、traffic_ratio、target_kb_ids、target_query_types、target_environment、shadow_mode、status。
- `Decide` 走匹配链：feature flag → 状态（必须 running）→ 时间窗 → 环境 → KB → query type → 流量分桶。匹配后分到 baseline / candidate / shadow 三组之一。
- `BuildSummary` 从 retrieve_log 表里聚合 baseline / candidate 各自的样本量、平均延迟差、context_tokens 差、错误率差。

### 深入追问

**Q：什么是 Shadow Mode？为什么需要它？**

Shadow Mode 指**candidate 跑但结果不影响用户**。把 candidate 的检索结果记录下来，与 baseline 对比，但**最终返回给用户的还是 baseline 的结果**。

它的价值：
1. 模型改写、新 reranker 这类高风险变更，先在影子里跑一段时间看稳定性。
2. 不需要真实流量"被白鼠"，但能拿到真实流量的指标。

代码里 `ShadowMode=true` 时直接走 `GroupShadow` 分支，不参与真实排名（见 `decideOne`）。

**Q：怎么判断"哪个版本胜出"？**

`summarizeRecord` 会输出三个关键 delta：
- `AvgDurationDeltaMS`：candidate 平均延迟相比 baseline 的差。
- `AvgContextTokensDelta`：上下文 token 数差（影响 LLM 成本）。
- `ErrorRateDelta`：错误率差。

这三个差值都是负向越好（candidate 比 baseline 更快、更省、更稳）。最终决定是否推全还要结合业务侧的 LLM 质量评分。

**Q：A/B 实验里的 candidate 一定要先过 Gate 吗？**

是的。Gate 是"上场前的体检"，A/B 实验是"上场后的对比"。如果连 Gate 都没过就上 A/B，相当于让一个明确知道生病的运动员上场，对比结果毫无意义。

**Q：如果实验中途发现 candidate 严重回归怎么办？**

`Rollback(ctx, cfg, experimentID, reason)` 可以一键停实验：把 status 改成 stopped，traffic_ratio 强制改成 0，并把这次回滚事件 `EnqueueCompensation` 到补偿队列里，触发后续清理。

## Q5 ⭐：策略热加载是什么？为什么不能"改配置重启服务"？

### 基础答案

**策略热加载**指的是：通过管理后台改一条 Feature Flag（比如 `RAG_ENABLE_MODEL_ASSISTED_REWRITE`），后端不重启就能让新策略立即生效。

实现看 [phase3admin/state.go:UpdateFlag](file:///h:/GYT-CODE/rag-retrievalOps/backend/internal/rag/phase3admin/state.go#L122-L165)：

```go
snapshot := *cfg                                              // 1. 先拍快照
if !cfg.RAG.FeatureFlags.SetPhase3StrategyFlag(flagKey, ...) { // 2. 改 flag
    return ...
}
applyRolloutSideEffects(cfg, flagKey, status, rolloutPercentage) // 3. 改连带的影子比例等副作用
if err := reconfigureManager(ctx, cfg); err != nil {           // 4. 重新装载 milvus 检索器
    *cfg = snapshot                                            // 5. 失败则回滚
    return ..., err
}
```

核心要点：
1. **快照 + 失败回滚**：改 flag 前拍快照，reconfigure 失败就把 cfg 整体还原。
2. **写入审计**：成功后调 `recordOperationLocked` 记录 from→to 的变化，调 `appendVersionLocked` 生成新版本快照。
3. **高风险 flag 强约束**：`isHighRiskFlag` 标记的 flag（比如模型改写）首次启用必须先走 shadow 或 canary，不能直接 enabled。

### 深入追问

**Q：为什么不能重启服务？**

1. **服务有状态**：长连接、缓存预热都会丢。
2. **回滚太慢**：发现新策略翻车要重启回滚，再花几分钟才能恢复。
3. **多实例不一致**：同一个集群多个实例重启不同步，会出现"流量打到老实例还是新策略"的诡异 bug。

**Q：rolloutPercentage 怎么生效？比如设 30 是什么意思？**

视 flag 而定。看 `applyRolloutSideEffects`：

- 普通 flag：rolloutPercentage 实际上不直接影响 candidate 比例，由灰度阶段决定。
- `model_assisted_rewrite` 这种特殊 flag：`status=shadow/canary` 时把 rolloutPercentage 转成 `cfg.RAG.Phase3.ModelRewriteShadowRatio = rolloutPercentage / 100`，让影子流量按这个比例触发模型改写。

**Q：为什么要支持 ConfigVersion？**

`ensureStateLocked` 会比较 `cfg.ConfigVersion` 和 `lastConfigVersion`，发现不一致才重新初始化 flag 状态。这避免了"配置外部刷新后内部状态滞后"的问题，也是热加载的一致性保证。

**Q：高风险 flag 的"shadow → canary → enabled"路径是写死的吗？**

是写死的安全规则。看代码：

```go
if isHighRiskFlag(flagKey) && !current.Enabled && enabled &&
   status != phase3.StatusShadow && status != phase3.StatusCanary {
    return FlagState{}, fmt.Errorf("high-risk flag %s must be enabled through shadow or canary first", flagKey)
}
```

这是一道"防止运维误操作"的护栏——你不能从 disabled 直接拉到 enabled，必须先 shadow 或 canary。

## Q6 ⭐⭐：如果线上发现新策略翻车，怎么"一键回滚"？

### 基础答案

项目有**三层回滚能力**，针对不同场景：

| 层级 | 触发方式 | 影响范围 | 时延 |
|------|----------|----------|------|
| 灰度 Stage 回滚 | `release.SetRuntimeOverride("phase1", reason, userID)` | 整个 phase2 流量回到 phase1 | < 1 秒 |
| 单 Flag 回滚 | `phase3admin.Rollback(target_version, flag_keys, reason)` | 指定 flag 回到指定版本或 disabled | < 1 秒 |
| 实验回滚 | `experiment.Rollback(experimentID, reason)` | 单个实验停掉，traffic 清零 | < 1 秒 |

**Stage 级回滚**（最暴力）：

```go
func RollbackPlan() []string {
    return []string{
        "Set runtime release stage to phase1 via /api/admin/kb/release/rollback",
        "Disable RAG_ENABLE_HYBRID_RETRIEVAL in persistent config after emergency rollback",
        ...
        "Confirm retrieve P95, empty-after-filter, and error rate return to Phase 1 baseline",
    }
}
```

不仅是改一个开关，还附带一份"回滚后必须做的事情清单"——同步关闭高风险 flag、确认指标已恢复 baseline。

**Flag 级回滚**（精确）：

`phase3admin.Rollback` 支持两种 target：
1. `target_version = "phase2_baseline"`：把所有 flag（或指定的几个 flag）回到 disabled。
2. `target_version = "p3-xxx-vN"`：把指定 flag 回到历史某个版本（从 `versionByID` 里查出 metadata 还原）。

整个过程同样有快照保护：`snapshot := *cfg`，失败则 `*cfg = snapshot`。

### 深入追问

**Q：怎么定义"回滚成功"？**

不是"配置改完了"就算成功，而是看指标：
- 错误率 / P95 / Empty-After-Filter ratio 回到 baseline。
- 治理 Gate 重新通过（`/api/admin/kb/governance/gate`）。
- `RollbackSuccessRate` 治理指标 ≥ 90%。

[handler_governance_gate.go:GetGovernanceGate](file:///h:/GYT-CODE/rag-retrievalOps/backend/api/handler/kb/handler_governance_gate.go#L39-L152) 会综合判断回滚后系统是否恢复健康。

**Q：回滚的版本能恢复到任意历史版本吗？**

理论上可以——`appendVersionLocked` 每次更新都会把 metadata 写进 `versionByID`，包括 enabled / status / rollout_percentage / strategy_version 四个关键字段。回滚时通过 `stateFromVersionRecord` 反序列化即可。

但实际中限制在"上一个稳定版本"或"phase2_baseline"，避免误回滚到一个更早的也有问题的版本。

**Q：回滚操作会留下审计吗？**

会。`RollbackStrategy` handler 在调完 `phase3admin.Rollback` 之后会调 `persistAuditEvent` 写入 `KBAuditEvent` 表，Action=`strategy_rollback`，记录操作人、目标版本、原因。同时 `recordOperationLocked` 在内存层面也留了一条 `OperationRecord`。

**Q：如果回滚本身失败了怎么办？**

代码里 `Rollback` 函数对失败情况显式返回 `Status="failed"` 和 `ErrorMsg`。配置 cfg 已经被 snapshot 还原，不会留下脏状态。运维侧应该立即 page on-call，走更暴力的方式（重启实例 / 全量切到 phase1）。

## Q7 ⭐：治理 Gate（governance gate）和评测 Gate 有什么区别？

### 基础答案

两个 Gate 不是一回事，分别守在"上线前"和"运营中"：

| 维度 | 评测 Gate（evaluation/gate.go） | 治理 Gate（governance gate） |
|------|--------------------------------|-----------------------------|
| 守在哪 | candidate 上线前 | 系统持续运行中 |
| 数据源 | 离线评测集 | 最近 24h 的 retrieve_log / cost_trace / index_registry / audit_event |
| 维度 | 8 项检索质量 + 延迟 + 拒答 | 5 项治理域：cost / audit / index / experiment / release |
| 输出 | candidate 能否进入灰度 | 系统是否健康，是否需要回滚 |

**治理 Gate**（[handler_governance_gate.go:GetGovernanceGate](file:///h:/GYT-CODE/rag-retrievalOps/backend/api/handler/kb/handler_governance_gate.go#L39-L152)）的 5 项：

```go
costGuardPassed       := latestCostPer1K < 25 || latestCostPer1K == 0
auditGuardPassed      := auditCoverageRate >= 0.6
indexGuardPassed      := collectionHealthScore >= 0.5
experimentGuardPassed := !任何实验 ErrorRateDelta > 0.2
releaseGuardPassed    := !releaseSummary.RollbackRecommended
```

只要有一项不通过，整体 `Passed=false`，并把不通过的原因（中文）追加到 `Risks` 列表里返回前端。

### 深入追问

**Q：审计覆盖率 60% 意味着什么？**

`auditCoverageRate = len(auditEvents) / len(retrieveLogs)`。理论上每次检索都该有相应的审计事件，但实际可能因为审计中心降级、或某些操作被豁免审计而低于 1.0。设 0.6 是经验下限——低于这个说明审计中心可能有大面积漏写或宕机。

**Q：CollectionHealthScore 是怎么算的？**

```go
healthy := 0
for _, item := range indexRegistry {
    if item.BuildStatus == IndexBuildStatusReady ||
       item.BuildStatus == IndexBuildStatusSwitched {
        healthy++
    }
}
collectionHealthScore = float64(healthy) / float64(len(indexRegistry))
```

注册表里 ready 或 switched（已切换为 active）的 index 占比。低于 50% 说明大量 index 处于 building / failed / rolled_back 状态，不该再做新的索引切换。

**Q：cost_per_1k_queries < 25 这个 25 是怎么来的？**

经验阈值，按"业务可承受成本上限"反推：单次问答平均成本 ¥0.025，1000 次问答 ¥25 是预算红线。超出立即报警。这个阈值显然要按 LLM 模型选型变化（用 GPT-4 vs DeepSeek 完全不一样），生产环境会做成可配置。

**Q：为什么 experimentGuardPassed 卡的是 `ErrorRateDelta > 0.2`？**

candidate 错误率比 baseline 高 20% 是非常严重的回归，几乎一定是 bug 或配置问题。卡这个阈值是为了**自动触发实验告警**，让运维不需要时刻盯着实验 dashboard。

## Q8 ⭐⭐：成本归因是怎么实现的？怎么知道一笔成本花在了"哪个 KB / 哪个策略 / 哪个模型"？

### 基础答案

成本归因的核心是**每次检索都落一条 `kb_cost_trace` 记录**，记录里挂上了所有维度的 ID。

[kb_cost_trace.go:KBCostTrace](file:///h:/GYT-CODE/rag-retrievalOps/backend/internal/model/kb_cost_trace.go#L9-L34) 字段：

```go
RequestID               string    // 串联全链路
CostTraceID             string    // 本次成本追踪 ID
KBID                    uint64    // 哪个知识库（带 index）
UserID                  uint      // 哪个用户（带 index）
ExperimentID            string    // 哪个实验（带 index）
StrategyVersion         string    // 哪个策略版本（带 index）
QueryType               string    // 哪类 query（带 index）
LLMModel                string    // 哪个模型
EmbeddingTokens / ContextTokens / CompletionTokens  // 三段 token 用量
EmbeddingCost / RetrievalCost / RerankCost / LLMCost / VectorStorageCost  // 五段成本拆分
CacheSavedRetrievalCost / CacheSavedRerankCost      // 缓存节省的成本
TotalCost               // 合计
```

**关键设计**：
1. 维度全部带 GORM index，按任何一个维度 group by 都能秒级聚合。
2. 成本拆 5 段而不是只记 total——能看清"贵在 LLM 还是 Embedding"。
3. 单独记 `CacheSaved*`——能量化缓存命中节省了多少。

聚合时（见 `handler_cost.go:getCostBreakdown`），传入一个 `resolveKey func(*model.KBCostTrace) (string, string)` 闭包，按需切片：
- 按 KB：`return fmt.Sprint(t.KBID), kbNameMap[t.KBID]`
- 按策略：`return t.StrategyVersion, strategyLabel`
- 按模型：`return t.LLMModel, modelLabel`
- 按租户、按 query type 同理。

### 深入追问

**Q：为什么不只记 TotalCost？**

因为优化方向不一样：
- LLMCost 太高 → 换更便宜的模型 / 缩短 context。
- RetrievalCost 太高 → 加 Embedding 缓存 / 降低 candidate 数。
- RerankCost 太高 → 跳过重排或换轻量 reranker。

**只记 total 等于知道"花了 100 块"，但不知道往哪砍**。

**Q：CacheSavedRetrievalCost 是怎么算的？**

走缓存命中时，把"如果没命中本来要花的钱"算出来记到 saved 里。这样运营 dashboard 可以呈现"缓存今天帮我们省了 X 元"，**让缓存的价值可量化**。

**Q：如果一个请求跨 KB 检索，成本怎么归？**

如果业务允许多 KB 检索，会落多条 cost_trace，每条 KBID 不同，TotalCost 按比例分摊。RequestID 和 CostTraceID 一致，方便后续按 request 维度合计。

**Q：聚合查询的性能怎么保证？**

1. 字段级 index：KBID / UserID / ExperimentID / StrategyVersion / QueryType / CreatedAt 全部带 index。
2. 时间窗收敛：`ListByCreatedAt` 强制传 `startTime / endTime`，永远走时间索引。
3. 大时间范围用预聚合（每小时落一份小时级聚合表）——24h 窗口直接查明细，30 天窗口查聚合。

## Q9 ⭐：审计追踪和普通日志有什么区别？

### 基础答案

普通日志是给开发看的，审计是给**合规、安全、运营**看的。两者最关键的区别：

| 维度 | 普通日志 | 审计追踪（audit event） |
|------|---------|------------------------|
| 谁看 | 开发 / SRE | 合规 / 安全 / 审计员 |
| 落地 | stdout / 日志文件 | MySQL 持久化（kb_audit_event） |
| 保留 | 7-30 天滚动 | 长期（一般 1 年起）不可删 |
| 字段 | 自由文本 | 结构化（before/after/result/reason） |
| 索引 | 全文搜索 | 按 actor / kb / action / request_id 精确查 |

[kb_audit_event.go:KBAuditEvent](file:///h:/GYT-CODE/rag-retrievalOps/backend/internal/model/kb_audit_event.go#L25-L49) 字段拆解：

```
AuditTraceID / RequestID  → 串联同一动作的所有审计事件
TenantID / OperatorID / UserID  → 谁干的
KBID / DocumentID / ResourceType / ResourceID  → 操作了什么
Action  → 做了什么（kb_create / strategy_flag_update / strategy_rollback / experiment_rollback / ...）
BeforeData / AfterData  → 状态变化（差异审计）
Result / Reason  → 成功/失败 + 原因
ActorName / IP / UserAgent  → 操作者环境
SensitiveFieldsMasked  → 哪些字段被脱敏
```

**关键 Action** 在 [governance.go](file:///h:/GYT-CODE/rag-retrievalOps/backend/internal/rag/governance/governance.go#L36-L55) 集中定义：`ActionStrategyFlagUpdate`、`ActionStrategyRollback`、`ActionExperimentRollback`、`ActionCollectionSwitch`、`ActionPermissionChange`...

### 深入追问

**Q：为什么 before / after 都要存？**

合规要求"可追溯"——审计员要能回答"3 天前谁把这个 flag 从 disabled 改成 canary 的，原值是什么"。**only after 等于无差异审计**，等于没审计。

**Q：审计写入和主流程是同步还是异步？**

代码里 `persistAuditEvent` 是同步调用，但在 handler 里调用时即使失败也不影响主流程（被 `_=` 或独立 goroutine 包裹）。**审计可以丢，但主流程不能因为审计写失败而 fail**——这是审计设计的基本原则。

**Q：SensitiveFieldsMasked 字段干嘛用？**

记录"本条审计里哪些字段做了脱敏"。比如用户 query 里包含手机号被掩成 `139****1234`，就把 "query.phone" 写到这个字段。这样审计员看到 after_data 时知道"这里被掩过，原文需要走更高权限走另一条流程拿"。

**Q：审计能不能删？**

代码层面 DAO 没提供 Delete 方法（只有 Create / List / GetByID）。物理上可以靠 DBA 删，但流程上必须走"双人审批 + 审计员复核"。审计本身**不能被审计的人删**——这是合规底线。

**Q：审计能撑多大量？**

`kb_audit_event.created_at` 有 index，配合分库分表 / 冷热分离，单租户日均百万条没问题。我们项目目前是单库单表，QPS 上来后会加 partition by month。

## Q10 ⭐：多租户隔离是怎么做的？同一份代码怎么避免租户 A 看到租户 B 的数据？

### 基础答案

项目走"**共享存储 + tenant_id 强制过滤 + 配额隔离**"路线：

1. **数据隔离**：所有业务表（KBKnowledgeBase / KBDocument / KBAuditEvent / KBCostTrace 等）都带 `tenant_id` 字段，所有查询强制 where tenant_id = ?。
2. **配额隔离**：每个租户在 `RAGTenant` 表里有配额上限——`MaxKBCount / MaxDocCount / MaxStorageMB / MaxAPICallsPerDay`，由 [quota.QuotaChecker](file:///h:/GYT-CODE/rag-retrievalOps/backend/internal/quota/quota.go#L14-L27) 在写操作前强校验。
3. **向量隔离**：Milvus collection 共享，但 chunk 元数据带 tenant_id，检索时 `expr=tenant_id == X` 过滤。
4. **审计隔离**：审计事件表自带 `TenantID` 字段，租户 A 的审计员只能看自己租户。

### 深入追问

**Q：QuotaChecker 是在哪个层级生效的？**

在"业务写操作前"。看 [quota.go](file:///h:/GYT-CODE/rag-retrievalOps/backend/internal/quota/quota.go) 提供的 4 个方法：

- `CheckKBLimit(tenantID)`：建知识库前调，超额返回 `TooManyRequestsError`。
- `CheckDocLimit(tenantID, count)`：上传文档前调，count 是这次想加几个。
- `CheckStorageLimit(tenantID, sizeMB)`：上传前算累计存储，超 limit 拒绝。
- `CheckAPICallLimit(tenantID)`：每次 API 调用前查当日计数（Redis 计数器 GetAPICallCount），超 daily quota 拒绝。

**Q：API 调用计数怎么实现？**

`GetAPICallCount(tenantID)` 走 Redis，key 类似 `quota:api:{tenantID}:{YYYYMMDD}`，每次调用 `INCR + EXPIRE 86400`，第二天自然滚动。这样不需要清理任务。

**Q：如果租户 A 的恶意流量打爆 Milvus，租户 B 怎么办？**

API 配额是第一道防线（限到天级别上限），但秒级流量爆冲不了天级别配额。所以再加：
- **租户级 QPS 限流**（项目里在 middleware 层做了 token bucket，按 tenantID 划分桶）。
- **Milvus 资源组隔离**（高级功能，把不同租户分到不同 query node 池）。

**Q：如果一个租户被删了，数据怎么清？**

逻辑删除（`deleted=1`）+ 异步任务清理 Milvus 向量。审计与成本数据**不删**，按合规保留期保留。

**Q：tenant_id 来自哪里？JWT 里？**

是的。鉴权 middleware 解 JWT 拿到 `userID + tenantID`，放进 `requestContext`，下层 service 取出来透传到 GORM where 条件。**永远不能信前端传的 tenantID**——这是水平越权的最大入口。

## Q11 ⭐⭐：索引生命周期是怎么管理的？换 Embedding 模型怎么不出事？

### 基础答案

换 Embedding 模型本质是**整个向量空间换了一套**——老向量和新向量不能在同一个 collection 里混着用，否则内积根本不可比。

项目用 [indexlifecycle/service.go](file:///h:/GYT-CODE/rag-retrievalOps/backend/internal/rag/indexlifecycle/service.go) 走"双 collection 蓝绿切换"：

```
[旧 collection: active]  ←── 在线流量
       │
       ▼
1. BuildCandidate    新建 candidate collection，全量重灌新模型向量
       │
       ▼
2. HealthCheck       校验维度匹配、metric 匹配、loaded、smoke 查询通过
       │
       ▼
3. SwitchActive      原子切换 active 标记 + reconfigure 全局 manager
       │
       ▼
[新 collection: active]   ←── 在线流量
[旧 collection: rollback] ←── 保留 24~72h 作为回滚兜底
```

`KBIndexRegistry` 表记录每个 index 的元信息：embedding_model、dimension、metric_type、index_type、build_status、collection_role（active/candidate/rollback）。`KBIndexOperationLog` 表记录所有操作动作，可审计、可回滚。

### 深入追问

**Q：HealthCheck 都查什么？**

```go
report.DimensionMatch  := record.EmbeddingDimension == cfg.Embedding.Dimensions
report.MetricTypeMatch := record.MetricType == cfg.Milvus.MetricType
// inspectCollection 内部还查：
//   - ListCollections 看是否真存在
//   - Load 状态是否健康
//   - Smoke query 是否能返回
```

四项缺一不可，少一项就拒绝切换。

**Q：SwitchActive 为什么必须配合 `EnableCollectionSwitchGuard` flag？**

```go
if !cfg.RAG.FeatureFlags.EnableCollectionSwitchGuard {
    return SwitchResult{}, fmt.Errorf("collection switch guard is disabled")
}
```

切换是高危操作，要求"防呆"：必须在配置里显式开启 guard，避免误操作（比如脚本批量执行时把测试环境的切换命令打到生产）。

**Q：切换后老 collection 直接删除？**

不删。看代码：旧 active 被设为 `CollectionRoleRollback`，BuildStatus 改成 `IndexBuildStatusRolledBack`，**保留在那里**。`RollbackActive` 直接复用这个 rollback collection 即可瞬间回退。

24~72h 后通过额外清理任务才物理删除，给运维留充分的"反悔窗口"。

**Q：reconfigure 期间会有流量打到错的 collection 吗？**

`milvus.ReconfigureGlobalManager(ctx, cfg)` 内部走"先建新连接，再原子替换"路线，类似 `atomic.SwapPointer`。瞬间切换，不存在中间状态。

## Q12 ⭐：补偿任务（Compensation Task）是干嘛用的？

### 基础答案

补偿任务是"治理操作的脏活清理队列"。当一个治理动作（比如实验回滚、collection 切换）发生时，可能会留下一些**需要异步清理**的副作用——比如：

- 实验回滚后，需要清理 candidate 版本占用的临时缓存。
- collection 切换后，需要异步释放老 collection 的资源。
- 配置变更后，需要通知下游服务刷新本地缓存。

这些副作用不能阻塞主流程（主流程要立即返回"回滚成功"），所以入队后台异步执行。

[governance.go:EnqueueCompensation](file:///h:/GYT-CODE/rag-retrievalOps/backend/internal/rag/governance/governance.go#L127-L146)：

```go
task := CompensationTask{
    ID:        fmt.Sprintf("governance-comp-%d", compensationCounter),
    Scope:     scope,        // 比如 "experiment_rollback"
    TraceID:   traceID,
    RequestID: requestID,
    Reason:    reason,
    Payload:   clonePayload(payload),
    CreatedAt: time.Now().UTC(),
}
compensationTasks = append([]CompensationTask{task}, compensationTasks...)
if len(compensationTasks) > 256 {
    compensationTasks = compensationTasks[:256]
}
```

队列容量 256，超出 FIFO 淘汰最早的——这是个**有界队列**，防止无人消费时无限膨胀。

### 深入追问

**Q：为什么补偿队列要在治理层而不是业务层？**

业务层只关心"主流程是否成功"，补偿是治理面的统一兜底机制。把它放在 `governance` package 里，业务侧只需要 `EnqueueCompensation(...)` 一行代码就能挂入队列，不必各自实现重试/淘汰逻辑。

**Q：为什么用内存队列而不是 Redis Stream / MQ？**

权衡之下的简化：
- 治理动作 QPS 极低（一天可能就几十次），不需要分布式队列。
- 内存队列实现简单，重启丢了也无所谓——补偿是"尽力而为"，主流程已经保证了原子性。
- 如果未来确实需要持久化，再切到 Redis Stream 即可（项目其他地方已经有 stream 基础设施）。

**Q：补偿如果失败了会重试吗？**

当前实现没做自动重试。`SnapshotCompensationTasks` 提供给运营页查看 pending 任务，运营可以手动触发重试。这种"半自动化"的补偿更适合治理场景——错了不能盲重，得人工判断。

## Q13：TraceContext 把哪些 ID 串起来了？为什么需要这么多 ID？

### 基础答案

[governance.go:TraceContext](file:///h:/GYT-CODE/rag-retrievalOps/backend/internal/rag/governance/governance.go#L84-L92) 定义了 7 个 ID：

```go
type TraceContext struct {
    ExperimentID      string  // 命中了哪个 A/B 实验
    StrategyVersion   string  // 当前策略版本
    IndexVersion      string  // 当前索引版本
    CollectionVersion string  // 当前 collection 版本
    CostTraceID       string  // 关联到成本记录
    AuditTraceID      string  // 关联到审计记录
    ReleaseID         string  // 关联到灰度阶段
}
```

每次请求都把这 7 个 ID 注入到 RetrieveLog / CostTrace / AuditEvent 三张表里，**任何一个 ID 都能反查到完整的"7 维全息上下文"**。

### 深入追问

**Q：为什么需要这么多维度 ID？少几个不行吗？**

每个 ID 解决一类问题：
- 用户反馈"今天检索质量不行" → 用 ExperimentID + StrategyVersion 看是不是新策略上的。
- 财务问"昨天 LLM 钱怎么涨了" → 用 CostTraceID 反查每条记录的 strategy / model 维度。
- 审计员问"这条违规检索是谁触发的" → 用 AuditTraceID 串到操作者。
- 运维问"上周五 14:00 的回滚有没有副作用" → 用 ReleaseID + IndexVersion 看那个时间点的快照。

**单一 RequestID 串不起这些维度**——RequestID 只代表"这次请求"，不代表"这次请求所处的版本上下文"。

**Q：这 7 个 ID 是怎么注入的？**

请求进入时由 middleware 根据当前 cfg / experiment.Decide / release.Decide 等组装好 TraceContext，挂在 ctx 上。下层落库时统一从 ctx 取，不需要业务代码自己拼。
