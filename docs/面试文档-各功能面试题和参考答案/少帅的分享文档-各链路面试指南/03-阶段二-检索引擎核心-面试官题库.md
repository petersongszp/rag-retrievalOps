## 整体流水线（先问 Q1 锁定全局认知）

混合检索的请求流转（一句话顺序）：

```
查询改写（rewrite） → 并发召回（dense + sparse） → 融合（minmax / rrf）
    → 去重（dedupe + table-section 抑制） → Title Boost（短查询命中标题加权）
    → 重排（Jaccard / 可插拔，带超时降级） → 战略 TopK（评估 cliff/flat 等信号）
    → ScoreCliff Guard（短精确查询的悬崖截断） → 父子填充（parent-child）
    → Token Budget Guard → 引用一致性检查 → 证据门禁（pass / refused / degraded_pass）
    → 写指标 + Debug Trace + 输出
```

## Q1 ⭐：白板画出"混合检索"的完整流水线，标出关键阶段与对应日志层级

### 基础答案

混合检索由 `HybridRetriever.SearchWithRequestAndMetrics` 编排，主要阶段如下：

1. **改写**：`applyControlledRewrite` 调用 `QueryRewriter`，产出 `final_query / dense_query / sparse_query` 与多策略组合（rule_based / domain_terms / route_specific / model_assisted_shadow）。
2. **动态 TopK 决策（第一次）**：`DecideDynamicTopK` 仅基于查询特征给出 `RuleBased` 版本的 `TopKDecision`。
3. **并发双路召回**：用 `sync.WaitGroup` 并发跑 dense（走 Embedding + Milvus 向量检索）和 sparse（走 BM25 倒排）。任一路失败时降级（`route_error`）。
4. **空路检查**：`rawCandidateCount == 0` 直接进证据门禁（拒答）+ 打 `EmptyReasonAfterRetrieve`。
5. **融合**：`FuseRouteCandidates` 按 `FusionStrategy` 走 minmax_v1 或 rrf_v1，给每个候选打 `fusion_score`。
6. **去重 + Title Boost**：`DeduplicateFusedDocuments` 按 `document_id+chunk_id` 合并；`applyTitleMatchBoost` 对短精确查询命中 `section_title / hierarchy_path` 时加权。
7. **重排**：`Reranker.Rerank`，带超时降级（`ConfigurableReranker` 的 primary/fallback）。
8. **战略 TopK + ScoreCliff**：`DecideStrategicTopK` 基于分布信号（cliff/flat）调整 K，`ApplyScoreCliffGuard` 对短精确查询做悬崖截断。
9. **父子填充**：`parentChildPostProcessor.Fill` 按 `section_window / parent_only / sibling_window / child_first_with_parent_summary` 填充上下文。
10. **Token Budget**：`ApplyTokenBudgetGuard` 在保留 `MinAnswerChunks` 的前提下削减 K。
11. **引用一致性**：`CitationConsistencyChecker.Check` 对每个 claim 计算 token/entity/n-gram 覆盖度。
12. **证据门禁**：`EvaluateEvidenceGate` 综合 `rerank_score / evidence_density / citation_support_score` 决定 pass / refused / degraded_pass。

各阶段写日志的 tag：
- L1：双路召回结束、双路全失败时打印；
- L2：融合 / 去重 / 重排 / 父子 / 截断 / 证据门禁 / 最终结果都聚合在 L2 一行；
- L5：重排失败、引用检查异常等子阶段错误。

### 深入追问

**Q：为什么要把 dense / sparse 跑成并发，不直接顺序？**

dense 受限于 Embedding API（容易 50-200ms），sparse 受限于 Milvus 多次 like 查询（每个 term 一次）。两者完全无依赖，串行会把 P95 拉到两者之和；并发后取最长那一路。代码里通过 `sync.WaitGroup + chan routeResult` 实现，最终在 `for routeRes := range resultCh` 收口，并由 `observeRouteMetric` 单独埋点。

**Q：为什么 TopK 决策要做两次（DecideDynamicTopK + DecideStrategicTopK）？**

第一次发生在召回前，**只能基于 query 特征**（短/长/广）给一个先验 K，否则 sparse / dense 的 candidate_topk 都没法定。第二次发生在重排后，**可以利用真实分数分布**（cliff / flat / balanced）和 `evidence_density / parent_diversity` 修正 K，并叠加 token budget 与 ScoreCliff Guard。

**Q：为什么空候选时也要走证据门禁，而不是直接 return？**

为了保证"拒答理由可观测"。空候选会被打 `EvidenceGateResult=refused, RefusalReason=No-Retrieval-Hit`，后续生成层据此走拒答 prompt 而不是"硬编一个答案"。门禁的存在让"召回为空"不再是无声失败。

## Q2 ⭐：Dense 召回和 Sparse 召回为什么要"做混合"？两路各自的强弱在哪？

### 基础答案

**单路的局限：**
- **Dense 向量检索（语义匹配）**：召回基于 embedding 相似度，能 cover 同义改写、跨语言、模糊问法；但对**专有名词、缩写、版本号、新词**容易漂——比如 "K8s 1.28 PreStop" 这种 query，向量匹配会被相似但无关的章节淹没。
- **Sparse / BM25（字面匹配）**：对专有名词、代码标识符、长 token 命中精准；但**同义词、自然语言改写**全都丢——用户问"如何停掉 Pod"，文档写的是"PreStop hook"，BM25 直接 0 命中。

两者**各自捕捉不同的相关性信号**，所以工程上几乎所有生产 RAG 都做 Hybrid：dense 提供召回保底，sparse 提供精确锚定。

**本项目实现：**
- Dense 走 Milvus AUTOINDEX 向量检索（`retriever.Retrieve`），结果挂 `route=dense, dense_score`；
- Sparse 走 `MilvusLikeCandidateProvider`：先对每个 term 用 `content like "%term%"` 拉候选，再交给 `CandidateBM25Ranker` 做显式 BM25 打分（`SparseInvertedIndex`）。结果挂 `route=sparse, sparse_score`。

### 深入追问

**Q：为什么不直接用 Milvus 自带的 sparse 索引（SPARSE_INVERTED_INDEX），而要自己再做一遍 BM25？**

两个原因：
1. **改写后的 sparse_query 对每个 term 拆分召回更可控**：每个 term 有 `per_term_limit`，可以按 term 分别埋点（`PerTermCandidateCount`），便于事后归因"哪个词召回多 / 哪个词被 drop"。
2. **打分公式自主**：`CandidateBM25Ranker` 用本项目自己的 `SparseIndexConfig（K1/B/MinScore）`，可以独立调参；而 Milvus 内置 sparse 的打分曲线对短文本/中文友好性较弱，不利于和 dense 做归一化融合。

**Q：sparse 路有没有"会爆炸"的风险？term 太多怎么办？**

有。所以：
- `SparseRetrieverConfig.MaxTerms` 默认 6，改写过的 query 才会放宽到 10（[sparse_search.go#L174-L177](file:///h:/GYT-CODE/rag-retrievalOps/backend/internal/milvus/retrieval/sparse_search.go#L174-L177)）。
- term 抽取阶段会用 stop_words 表（the / a / how / why 等）+ 长度 < 2 + 重复去重过滤。被丢弃的 term 写入 `DroppedTerms map[string]string`，原因可能是 `too_short / stopword / duplicate`，全部进 metrics。
- per_term 拉取上限 `perTermLimit = candidateTopK * PerTermFactor`，下限 `MinPerTermK = 20`。

**Q：dense 失败 / sparse 失败如何降级？**

`SearchWithRequestAndMetrics` 收口处看 `denseErr / sparseErr`：
- 一路失败：仍走融合（融合代码对 `nil docs` 友好），日志打 `Degradation.Reason=route_error`。
- 两路全失败：直接 return error，并补一行 L1 日志，标记 `empty_reason=empty-after-retrieve`。

## Q3 ⭐：融合环节支持 MinMax 和 RRF 两种策略，这两种策略各自的取舍是什么？项目默认用哪个？

### 基础答案

`FuseRouteCandidates` 有两种策略，由 `FusionStrategy` 字段切换：

**1. minmax_v1（默认）**

按 route 分别做 min-max 归一化，再用 `DenseWeight / SparseWeight` 加权：
```
normalized = (raw - min) / (max - min)
weighted   = normalized * route_weight
```
权重默认 0.7 / 0.3（dense 占大头），归一化前会自动归并到合 1。

**2. rrf_v1（Reciprocal Rank Fusion）**

按 route 排序后，每个文档的分数只看**排名**：
```
rrf_score = route_weight * 1 / (RRFK + rank)
```
`RRFK` 默认 60（Cormack 论文的经典值）。

| 维度 | minmax_v1 | rrf_v1 |
|------|-----------|--------|
| 输入信号 | 原始分数本身（有大小） | 排名（仅顺序） |
| 对分数尺度敏感度 | 高（dense / sparse 分布不同会导致权重失真） | 低（只看 rank） |
| 区分度 | 高（同 rank 的 doc 也能拉开差距） | 低（同 rank 完全一样） |
| 抗噪声 | 弱（单点离群值会拉飞 max） | 强 |
| 适用场景 | 同质打分体系、需要细粒度排序 | 异质打分体系（dense vs sparse 量级差异大） |

**默认是 minmax_v1**，但代码里给 RRF 留了完整通路，可通过策略中心一键切换。

### 深入追问

**Q：为什么 RRF 取 K=60？这个数字怎么来的？**

是 Cormack 等人 2009 年 RRF 论文里实验出来的"较优常数"——对绝大多数 IR 任务都比较稳。具体作用是：当 K 远大于排名差时，1/(K+rank) 之间的差距被压平，让 RRF 对"是不是 top1"不那么敏感；当 K 很小，1/(K+rank) 接近 1/rank，强调 top 排名。60 是一个"既不至于压死 rank 信号、又能容忍噪声"的折中值。

**Q：MinMax 归一化的坑在哪里？项目里怎么防？**

经典坑：当一路只有 1 个候选 / 所有候选分数相同时，max == min，公式会 NaN。代码里这样处理：

```go
if stats.max <= stats.min {
    if score <= 0 { return 0 }
    return 1
}
```
（[fusion.go#normalizeRouteScore](file:///h:/GYT-CODE/rag-retrievalOps/backend/internal/milvus/retrieval/fusion.go#L300-L315)）

第二个坑是 dense / sparse 量级不同——例如 dense 的 cosine 在 0.6-0.95，sparse 的 BM25 在 0.5-15。直接 minmax 后还是 0-1，看似公平；但**离群值**容易打飞 max。所以默认 dense 0.7 / sparse 0.3 的权重，本质是给 dense "信任度溢价"。

**Q：融合后每个 doc 上挂了哪些 metadata，下游怎么用？**

minmax 路径会挂：`fusion_strategy / fusion_score / score / route / route_score`；rrf 路径还会额外挂：`rrf_score / route_rank / route_rrf_contrib`。去重阶段（[dedupe.go#annotateDedupedDocument](file:///h:/GYT-CODE/rag-retrievalOps/backend/internal/milvus/retrieval/dedupe.go#L252-L292)）会把多路贡献合并成 `route_contrib / route_raw_scores / route_rank / route_rrf_contrib`，写到 `metadata.source` 里供 Debug Trace 使用，前端可视化能看到"这个文档 dense 贡献多少 / sparse 贡献多少"。

## Q4 ⭐：查询改写有几种策略？project 怎么把"规则改写"和"模型改写"组合起来？

### 基础答案

`ControlledQueryRewriter.Rewrite` 内部串了 5 类策略，最终 `Strategy` 字段是几种策略的拼接：

| 策略 | 触发条件 | 行为 |
|------|----------|------|
| `RewriteStrategyBlacklist` | query 命中黑名单（SQL 关键字、注入提示词、URL 等） | 立即 skip，标记 `BlockedByPolicy=true` |
| `RewriteStrategyTimeout` | ctx.Done | skip，回退到 original |
| `RewriteStrategyRuleBased` | 缩写表 / 别名表 / typo 修正命中 | 加上同义词 / 修正后的词 |
| `RewriteStrategyDomainTerms` | `EnableDomainTerms=true` 且 `DomainTermProvider.Resolve` 命中 | 注入领域词典扩展，记录 scope/version/term_hits |
| `RewriteStrategyRouteSpecific` | `EnableRouteSpecificRewrite=true` 且 dense / sparse 词集不同 | dense 保守 / sparse 激进，dense 只加首选扩展 |
| `RewriteStrategyModelAssistedShadow` | `EnableModelAssistedRewrite=true` + 哈希采样（默认 10% shadow）+ 非高风险 query | 调大模型补充扩展词，仅作影子（不替换原 query），记录 risk_level |

输出的关键字段：
- `OriginalQuery / RewriteQuery / FinalQuery`
- `DenseQuery / SparseQuery`（可分路）
- `RouteStrategies` map：`{dense: rule_based+route_specific:conservative, sparse: rule_based+route_specific:aggressive+domain_terms}`
- `TermDictScope / TermDictVersion / TermHits`：领域词典命中
- `ModelRewriteApplied / ModelRewriteShadow / ModelRewriteRiskLevel / ModelRewriteTerms`：模型改写命中

最终在 `formatRewriteStrategy` 拼成 `rule_based+domain_terms;routes=dense:...|sparse:...;term_scope=kb_global;term_version=v1;...` 这种"可读但可机解析"的字符串塞进日志和 metrics。

### 深入追问

**Q：route-specific（dense 保守 / sparse 激进）这个设计的动机是什么？**

匹配机制差异决定的：
- **dense** 是语义匹配，多塞同义词反而稀释主语义 → 只加"首选扩展"，保守。
- **sparse** 是字面匹配，召回靠 term 数量 → 把所有别名 / 缩写 / 修正词全加上，激进。

实现细节：`addExpansion(term, includeDense)` 的第二个参数控制是否加到 dense 集合（[rewrite.go#L286-L299](file:///h:/GYT-CODE/rag-retrievalOps/backend/internal/milvus/retrieval/rewrite.go#L286-L299)）；只有当 `EnableRouteSpecificRewrite && index == 0` 才把首选项也塞 dense。

**Q：模型改写为什么是"shadow"？为什么默认只采样 10%？**

模型改写有 3 个风险：
1. **延迟**：模型调用 100-300ms，串在改写路径上会拖垮 P95；
2. **漂移**：模型可能改写出无关词，导致召回从准变垃圾；
3. **代价**：每次都调用大模型贵。

所以采取**影子模式**：
- 只对 10% 流量采（`sampleModelRewriteShadow` 用 sha1(query+kb+collection) 哈希分桶，**保证同 query 命中是稳定的**，便于复现）；
- 改写结果被加入扩展词，但 `ModelRewriteShadow=true` 标记，便于 A/B 对比"加了模型词的那 10% 召回 vs 没加的 90%"；
- 高风险词（含 SQL / URL / token 数 > 12）直接跳过，不让模型扩词。

**Q：黑名单为什么不放在 API 层做，而要塞进改写器？**

两层兜底：API 层做粗过滤，改写层做语义级二次拦截。改写器拿到的是已经分词后的 query，能识别"ignore previous instructions"这种 prompt injection；这是字面正则黑名单覆盖不到的。代码里黑名单包含 `ignore previous`、`system prompt`、`select / delete / drop` 等。

## Q5：重排为什么用 Jaccard？对接外部模型时怎么做超时降级？

### 基础答案

**为什么 Jaccard 是 fallback 默认实现？**

线上 reranker 通常对接 bge-reranker / Cohere 这类外部 API，受限于网络与 quota，不可能没兜底。本项目用 `JaccardReranker` 作为零依赖的本地 fallback：

- **打分公式**：`final = original_score * α + lexical_score * (1 - α)`，默认 α=0.7。
- **lexical_score**：取 `Jaccard(query_tokens, content_tokens)` 与 `query_coverage` 的最大值。
  - Jaccard 关注集合重叠率；
  - coverage 关注"query 中多少 token 在内容里出现"，对查询很短的情况更友好。
- **tokenize**：英文按 letter+digit 切，中文 unicode.Han 单字 + bigram（前后两个汉字组合）。

**怎么超时降级？**

`ConfigurableReranker` 包了 primary（如 bge-reranker）和 fallback（Jaccard）两个 reranker，外加 `timeout`。流程：
1. `WithTimeout` 包 ctx；
2. `primary.Rerank` 失败 / 超时；
3. 用**原始 ctx**（不带 timeout）跑 fallback；
4. 设置 `Fallback=true, Reason=timeout/canceled/error`；
5. 上层 metrics 写 `rerank_fallback=true / rerank_reason=timeout`，并在 Debug Trace 的 `Degradation` 段记录。

### 深入追问

**Q：为什么 fallback 跑 Jaccard 时**用原始 ctx**而不是 timeout ctx？**

Jaccard 是本地纯计算，几毫秒就跑完，不需要再做超时。如果继续用已经 cancel 的 timeout ctx，`ctx.Err()` 直接返回，等于"primary 超时 + fallback 也立刻退出 = 两次都失败"，体验最差。

**Q：rerank 失败但不报错时（reranked.Documents 为空）怎么处理？**

代码在 [hybrid_search.go#L500-L502](file:///h:/GYT-CODE/rag-retrievalOps/backend/internal/milvus/retrieval/hybrid_search.go#L500-L502)：
```go
if len(reranked.Documents) > 0 {
    merged = reranked.Documents
}
```
只有重排返回非空才覆盖，否则保留融合后的顺序。这是为了防御"reranker 静默返回 0 条"的边界。

**Q：reranker 给文档挂的 metadata 都有哪些？为什么要存 pre/post rank？**

`annotateRerankMetadata`（[reranker.go#L240-L270](file:///h:/GYT-CODE/rag-retrievalOps/backend/internal/milvus/retrieval/reranker.go#L240-L270)）会写入：`rerank_score / rerank_version / rerank_latency_ms / pre_rerank_rank / post_rerank_rank / original_score / score_delta`，并镜像到 `source`。

存 pre/post rank 是为了**事后审计**：定位"重排是不是把对的拉下去了"。前端的 Debug 面板会展示"重排前 top3 vs 重排后 top3"的差异表，依赖这两个字段。

## Q6 ⭐：父子检索（Parent-Child）解决什么问题？项目支持哪几种填充策略？

### 基础答案

**问题来源**：

切分时 chunk 越小，**召回越准**（语义聚焦）；但 chunk 越小，**生成时上下文越碎**（缺少前后语境，模型容易胡编）。父子检索是为了同时享受两者：

- 索引时切**子块（child chunk）**，做向量化、做召回；
- 召回命中后再用 **父块（parent）/兄弟块/同节块** 把上下文补齐再喂给模型。

**项目实现的 4 种填充策略**（`ParentChildConfig.FillStrategy`）：

| 策略 | 行为 | 适用场景 |
|------|------|----------|
| `parent_only` | 取整段父块（同 parent_id 的所有 child） | 章节短、父块本身可塞 |
| `sibling_window` | 同 parent 下、按 chunk_index 取 ±N 个邻居 | 父块过大但局部够用 |
| `section_window`（默认） | 同 hierarchy_path 下取窗口邻居 + 同 parent 兜底 | 跨小节但同章节，兼顾结构 |
| `child_first_with_parent_summary` | 把命中 child 放在最前，父块作为 "Parent context:" 后缀 | 强调命中证据，减少模型分心 |

**关键参数**：
- `WindowSize`：邻居窗口大小；
- `MaxTokens`：填充后的总 token 上限（默认 1200）；
- 填充失败的兜底：直接挂 `parent_fill_strategy=child_only, parent_fill_reason=parent_child_unavailable / query_failed`。

### 深入追问

**Q：父块是从哪里来的？是入库时就建好的吗？**

是。入库切分时，每个 child chunk 的 metadata 必有：`parent_id / child_id / hierarchy_path / chunk_index / parent_start_offset / parent_end_offset / parent_build_strategy / parent_build_version`。检索时就根据这些字段，拿当前 chunk 的 `parent_id` 或 `hierarchy_path` 反查 Milvus（用 `client.Query`，不是向量检索）。

但**填充失败必须可降级**：如果检索 chunk 的 metadata 里没有 `parent_id`（例如老数据），代码会直接挂 `parent_child_unavailable` 跳过填充，绝不报错（[parent_child.go#L213-L217](file:///h:/GYT-CODE/rag-retrievalOps/backend/internal/milvus/retrieval/parent_child.go#L213-L217)）。

**Q：`section_window` 和 `sibling_window` 的区别是什么？哪个更稳？**

- `sibling_window`：必须 `parent_id` 相同 + `chunk_index` 在 ±WindowSize 以内。粒度细，容错差——如果父块切得不规则，windows 太窄会拿不到内容。
- `section_window`：要求 `hierarchy_path` 相同（即在同一个文档章节内），叠加 `WindowSize > 0` 时再加 chunk_index 窗口。粒度粗一点，对切分不规则更鲁棒。

代码里 `buildCandidateExprs`（[parent_child.go#L304-L320](file:///h:/GYT-CODE/rag-retrievalOps/backend/internal/milvus/retrieval/parent_child.go#L304-L320)）里 `section_window` 还会**叠加 parent_id 的 fallback expr**，先查 hierarchy_path 再补查 parent_id，提高召回成功率。所以 section_window 是默认。

**Q：填充会不会把 token 撑爆？**

`buildWindowedContent` 用 `selectDocsAroundChild` 做以 child 为中心的"左右轮流取"贪心：每加一篇就累加 `estimateDocumentTokens`（按 utf-8 rune / 4 估算），超过 `MaxTokens` 就 break，并把 reason 标为 `budget_limited`。最终结果还会经过 `ApplyTokenBudgetGuard` 二次卡。

**Q：填充后会有重复怎么办？**

`deduplicateFilledParentResults`（[parent_child.go#L161-L185](file:///h:/GYT-CODE/rag-retrievalOps/backend/internal/milvus/retrieval/parent_child.go#L161-L185)）按 `document_id:parent:parent_id` 做二次去重——多个 child 命中同一个 parent 时，只保留 score 最高的那条，避免上下文重复污染。

## Q7 ⭐：动态 TopK 的两次决策都看了哪些信号？为什么要分两次？

### 基础答案

第一次：`DecideDynamicTopK`（PolicyVersion = `phase2-rule-v1`）
- 输入：query 字符 / 词数、是否 broad / short-precise；
- 决策表：
  - `isBroadQuery` → maxTopK（"区别 / 对比 / 总结 / overview" 等关键词）；
  - 长 query（runeCount ≥ 48 || termCount ≥ 8）→ maxTopK；
  - 中 query（runeCount ≥ 24 || termCount ≥ 5）→ 中位数；
  - 短精确（runeCount ≤ 12 && termCount ≤ 3）→ minTopK；
  - 其他 → 中位数；
- 输出 `DecisionReason`：`broad_query` / `long_query` / `medium_query` / `short_precise_query` / `default_mid_range`。

第二次：`DecideStrategicTopK`（PolicyVersion = `phase3-strategic-v1`）
- 输入：第一次决策 + 重排后的 docs；
- 提取信号：
  - **score_distribution**：cliff / flat / balanced / single；
  - **rerank_gap**：top1 - top2；
  - **evidence_density**：score ≥ top*0.82 的 doc 占比；
  - **parent_diversity**：不同 parent_id 数量；
  - **dominant_parent_share**：某一 parent 占比；
- 决策规则：
  - `cliff` 且 gap≥0.18 → K-2，否则 K-1；
  - `flat` → K+2；
  - `parent_diversity ≥ min(len, 3) && dominant_parent_share < 0.7` → K+1；
  - `dominant_parent_share ≥ 0.75` → K-1（避免单父块占满）；
  - `evidence_density < 0.34` → 不扩张；
  - `evidence_density ≥ 0.7 && rerank_gap < 0.08` → K+1。
- 叠加 `requested_cap`、`token_budget_cap`，最后 clamp 到 `[StrategicMinTopK, StrategicMaxTopK]`。

外加 `ApplyScoreCliffGuard`（针对 short_precise_query 的悬崖截断）和 `ApplyTokenBudgetGuard`（保 `MinAnswerChunks` 的前提下卡 token 预算）。

### 深入追问

**Q：为什么两次决策不能合并？**

第一次发生在召回前，**没有真实分数**——只能基于查询特征猜个 K 给召回 / 融合用。第二次必须看到重排后的真实分数，才能识别 cliff / flat。如果只做一次，要么"召回前没法定 K"，要么"决策晚了，召回阶段已经按错误的 K 去 milvus 拉数据"。

**Q：cliff 截断为什么只在 short_precise_query 触发？**

`ApplyScoreCliffGuard` 的限制（[topk_policy.go#ApplyScoreCliffGuard](file:///h:/GYT-CODE/rag-retrievalOps/backend/internal/milvus/retrieval/topk_policy.go#L270-L307)）：
1. `isShortPreciseQuery(query)`，否则直接 return；
2. top1 必须包含**精确字面命中**（content / section_title / hierarchy_path 经过 `normalizeTitleMatchText` 后包含 query）；
3. top1 的实际分数必须 ≥ 0.55；
4. cutoff = max(top * 0.72, top - 0.18)；
5. 一遇到分数 < cutoff 的就 break，截掉后面。

为什么这么严？因为 cliff 截断本质是"我对 top1 高度确信"——一旦判断错就会丢掉相关结果。短精确查询 + 字面命中 + 高分三重锁，才允许做这种激进截断。

**Q：`readScoreCliffScore` 为什么按 `rerank_score / fusion_score / score` 顺序读？**

代码里有一段中文注释：

> 与 readStrategicScore 保持一致的优先级：重排后应优先读取 rerank_score，否则会读到重排前的旧融合分数（score 字段在 rerank 后未更新），导致 ApplyScoreCliffGuard 基于错误的 topScore 截断，静默丢弃相关文档。

这是一个真实修过的 bug：rerank 完之后 metadata 里 `score` 字段没更新（保留的是融合后的 score），如果直接读 `score`，cliff guard 用的是错误的 top 值。修复方式是用 fallback 链，先读 `rerank_score`，再 fusion，再 score。

**Q：MinAnswerChunks 的存在是什么动机？**

`ApplyTokenBudgetGuard` 在 token 预算很紧时，仍然保证至少 `MinAnswerChunks` 个文档进入 prompt——避免出现"算法砍到 0 chunk 但还想让模型答题"的尴尬。前 `MinAnswerChunks` 个文档**不参与**预算扣除（[topk_policy.go#L243-L246](file:///h:/GYT-CODE/rag-retrievalOps/backend/internal/milvus/retrieval/topk_policy.go#L243-L246)）。

## Q8 ⭐：证据门禁（Evidence Gate）的拒答机制怎么设计的？有哪些拒答理由？

### 基础答案

`EvaluateEvidenceGate` 在所有处理结束后做最后一关 gating，输出三种结果：

| 结果 | 含义 |
|------|------|
| `pass` | 通过，正常返回结果 |
| `refused` | 拒答，附带 RefusalReason，前端走拒答 prompt |
| `degraded_pass` | 配置异常等情况下的降级放行（带 Error） |
| `disabled` | 没开 gate |

**6 个拒答理由（Refusal Reason）**：

| 拒答理由 | 触发条件 |
|----------|----------|
| `No-Retrieval-Hit` | docs 为空 |
| `Contradictory-Evidence` | top1 / top2 都触及 query，但其中一个含否定语 (no/never/不能/无...) 而另一个不含 |
| `Out-Of-KB-Scope` | query token 在所有 doc 中覆盖率 < 20% + 分数 / 密度也低 |
| `Low-Rerank-Confidence` | maxRerankScore < 阈值 OR evidenceDensity < 阈值 |
| `Insufficient-Citation-Coverage` | citation 检查未通过、有 unsupported claim、或 citation_support_score < 阈值 |

**阈值不是固定的**，会按 query 特征做"敏感度倍率"：
- `isBroadQuery` → +12%
- short query (runeCount≤12 || termCount≤2) → +5%
- 含 how / why / compare / 区别 / 对比 / 怎么 / 如何 / 为什么 → +5%
- 倍率上限 1.25x

阈值越高 = 越容易拒答，所以广泛/比较类 query 会更严格。

### 深入追问

**Q：为什么"敏感度倍率"对广查询更严？反直觉吧？**

不反，恰恰是为了**保护用户体验**：

- 短/广查询本身召回风险高（容易拉来一堆"看起来相关其实无关"的内容）；
- 与其勉强拼一个含混的答案，不如直接拒答 + 引导用户细化问题；
- 这是一种**保守拒答**策略——宁可 refused 一部分能答的，也不要 hallucinate。

**Q：`Contradictory-Evidence` 怎么判定的？**

`hasContradictoryEvidence`（[evidence_gate.go#L223-L257](file:///h:/GYT-CODE/rag-retrievalOps/backend/internal/milvus/retrieval/evidence_gate.go#L223-L257)）：
1. 取 top2 候选（按分数）；
2. 都必须 `docTouchesQuery`（query token 出现在 content）；
3. 一个含 `containsNegationCue`（` not / no / never / 禁止 / 不能 / 不支持 / 无 / 未` 等否定语），一个不含；
4. 即认定矛盾。

这是个非常**保守的实现**——只看一组 hit；但已经能拦住很多明显冲突场景，比如"Java GC 默认开启吗"召回到一个说"开"一个说"不开"的章节。

**Q：`computeFallbackEvidenceDensity` 在什么时候用？**

当上游没传入 `EvidenceDensity` 时，gate 自己用 `score >= MinRerankScore` 的占比当作密度兜底（[evidence_gate.go#L203-L221](file:///h:/GYT-CODE/rag-retrievalOps/backend/internal/milvus/retrieval/evidence_gate.go#L203-L221)）。这个 fallback 让 gate 不依赖 `DecideStrategicTopK` 的输出，能独立工作。

**Q：拒答的产物在 metrics 里怎么暴露？**

`SearchMetrics.EvidenceGateResult / RefusalReason / CitationSupportScore / EvidenceGateError` 全部回写。Debug Trace 的 Degradation 段也会标记 `evidence_gate_degraded`。前端能直接根据这些字段渲染"已拒答 + 拒答原因"提示框，并在审计页可筛"refused"流量。

## Q9：引用一致性检查（Citation Consistency）怎么打分？跟证据门禁是什么关系？

### 基础答案

`CitationConsistencyChecker.Check` 在重排和父子填充之后执行，对每个候选文档打"它能不能支持 query 的 claim"分。

**打分流程**：
1. **claim 抽取**（`extractCitationClaims`）：把 query 按标点 / 换行切句，再按 `and / vs / versus / compare` 拆复合 claim，过滤无意义短句，最多取 4 个。
2. **每个 claim 对每个 doc 打分**（`scoreCitationClaimAgainstDocument`）：
   - 字面包含命中（normalize 后 claim 是 content 子串）→ 0.98；
   - 否则 = `lexical_coverage * 0.5 + entity_coverage * 0.2 + char_3gram_coverage * 0.3`；
   - 三类 coverage：token 覆盖、entity（含数字 / 大写 / 包含 `_-/#+` 的词）覆盖、字符 3-gram 覆盖；
   - boost 规则：lexical_coverage=1 → 至少 0.9；lexical+entity≥0.8 → 至少 0.85；entity_coverage=1 → 至少 0.82。
3. **聚合**：`SupportScore = avg(每个 claim 的 best_score)`；任一 claim 得分 < threshold（默认 0.7）则计入 `UnsupportedClaims`；`Supported = (UnsupportedClaims 为空)`。
4. **回写 metadata**：每个 doc 上挂 `citation_supported / citation_support_score / citation_check_version / low_support_citation`。

**与证据门禁的关系**：

```
citation 检查的输出（SupportScore / Supported / UnsupportedClaims）
    → 灌进 SearchMetrics
    → 证据门禁的 resolveCitationSupport 读这些字段
    → 决定是否触发 Insufficient-Citation-Coverage 拒答
```

引用检查是"信息提供方"，门禁是"决策者"。两者解耦的好处：未启用 citation 检查时（无 version），门禁会 fallback 用 doc id 是否完整推算 SupportScore（[evidence_gate.go#L154-L184](file:///h:/GYT-CODE/rag-retrievalOps/backend/internal/milvus/retrieval/evidence_gate.go#L154-L184)）。

### 深入追问

**Q：为什么字面 substring 匹配能得 0.98？这不是过于乐观吗？**

它依赖一个前提：**claim 已经过 normalize**——去标点、去空格、变小写、去 stop 前缀（`how does / what is / explain` 等）。所以"how does Java GC work"会被剥成"java gc work"再做 substring 命中。这种命中已经非常强了，给 0.98（不给 1.0 是为了和"完美命中"留点区别）。

**Q：如果 SupportScore 不达标，会不会反过来"修复"结果集？**

会！`tryRefineUnsupportedCitations`（[hybrid_search.go#L951-L977](file:///h:/GYT-CODE/rag-retrievalOps/backend/internal/milvus/retrieval/hybrid_search.go#L951-L977)）会在 `current.Supported=false` 时，**只保留** `citation_supported=true` 的子集，重新跑一次检查；如果 SupportScore 提升了就采纳，否则保留原集合。这是"愿意用更少但更可信的证据"的工程权衡。

**Q：char 3-gram 覆盖在中文场景下有什么坑？**

中文 3-gram 颗粒度比英文小（3 个汉字 ≈ 一个短语），命中率天然偏高，可能虚抬分数。代码里通过把权重调到 0.3、且与 lexical_coverage(0.5) / entity_coverage(0.2) 合用，避免 3-gram 主导。如果未来上专门的中文向量打分模型，这个公式可以替换。

## Q10：Title Boost 的设计动机是什么？为什么只对短精确查询生效？

### 基础答案

`applyTitleMatchBoost` 在去重之后、重排之前对每个候选评估"标题是否命中"：

- 命中条件按优先级匹配：
  1. `section_title == query`（normalize 后） → +0.40，reason `section_title_exact`
  2. `hierarchy_path == query` → +0.40，reason `hierarchy_path_exact`
  3. `hierarchy_path contains query` → +0.35，reason `hierarchy_path_contains`
  4. `section_title contains query` → +0.30，reason `section_title_contains`
- score 加 boost 后 clamp 到 [0, 1]；旧分数存到 `pre_title_match_score`。
- normalize 用 `normalizeTitleMatchText`（小写 + 去空白 + 去标点）。

**触发限制**：
- `len(docs) <= 1` 不做（没意义）；
- `normalizedQuery` 长度 < 3 不做；
- **必须 `isShortPreciseQuery`（runeCount ≤ 12 && termCount ≤ 3）**。

### 深入追问

**Q：为什么只对短精确查询做 boost？长查询命中标题不该加分吗？**

长查询命中标题的"信号强度"远不如短查询：

- 用户输入"PreStop hook"（短精确）→ 命中 section_title 几乎 100% 是想要的；
- 用户输入"K8s 的 PreStop 在 Pod 优雅终止流程里到底什么时候被调用"（长描述）→ 命中标题不能保证比正文段更相关，反而可能是"标题命中却内容浅薄"。

短精确查询的标题命中是个**强先验信号**——基本等价于"用户想点这个目录条目"，所以加 0.30-0.40 这么大的权重不算激进。

**Q：boost 加得这么重（0.4），不会把分数体系压坏吗？**

会有副作用，所以做了三层防护：
1. 仅短精确触发；
2. score 最终 clamp 到 1.0（不会超过 max）；
3. boost 后会被重排再次重排——bge-reranker 会基于 query+content 重打分，title boost 的影响会被部分抵消。Title boost 主要起到"在重排前确保标题命中能进 top"的作用。

**Q：如何验证 Title Boost 真的有效？**

代码挂的 `title_match_boost_applied / title_match_boost_reason / title_match_boost_version` metadata 会落到 Debug Trace。评测中心可以筛"应用了 boost 的 query"，对比 Recall@5 / nDCG。版本号 `title-match-boost-v1` 也方便后续做 A/B 实验切换不同 boost 公式。

## Q11：去重不是简单的"按 ID 去重"——还做了哪些事？

### 基础答案

`DeduplicateFusedDocuments` 做了 3 件事，远不只是 ID 去重：

1. **按 dedupe key 去重**：key = `document_id:chunk_id`（缺失则降级到 `document_id` 或 `doc.ID` 或伪 ID）；同 key 多次出现时**保留最高分**，但**合并所有路由的 contrib**（`mergeFloatMaps` 取每路最大值，`mergeIntMaps` 取最小 rank）。
2. **table-section 抑制**：`removeContainedSectionDuplicates` 处理一个特定的污染场景——当一个 chunk 是 table（chunking_unit=table）、另一个是包含此 table 的 section chunk 时，**去掉 section chunk**（保留 table），避免上下文重复。判定条件：
   - 同 document_id；
   - section 的 child_offset 完全包含 table 的 offset 且更长；
   - 或 section 内容包含 table 内容的至少 4 个 token，且至少 1 个长（≥8 字符）匹配。
3. **annotateDedupedDocument**：把合并后的 `score / fusion_score / route / primary_route / fusion_strategy / route_contrib / route_raw_scores / route_rank / route_rrf_contrib / collection / retriever_version` 全部写回 metadata 与 source。

### 深入追问

**Q：为什么 table 去重要单独做？普通 ID 去重不就行了吗？**

它们是**两个不同的 chunk**——chunk_id 不同，但内容大量重叠。原因是入库阶段同时跑了两种切分策略：通用 paragraph 切分（拿到 section chunk，含 table）和 table-aware 切分（专门把 table 作为独立 chunk）。两者并存能让"找表头"和"找上下文"两类查询都召回得到，但喂给模型时如果都进 prompt，会出现明显重复。所以在去重阶段抑制掉 section 的那一份。

**Q：mergeFloatMaps 取最大值，mergeIntMaps 取最小值，为什么不一样？**

- `route_contrib / route_raw_scores / rrf_contrib` 是分数 → 越大越能代表这个文档在这一路的"最佳贡献"；
- `route_rank` 是排名 → 越小越好（rank=1 比 rank=5 更好）。

所以一个取 max 一个取 min。

**Q：为什么 dedupe key 设计有 4 层 fallback（doc_id+chunk_id → document_id → doc.ID → buildPseudoDocID）？**

不同来源的数据 metadata 完整度不一致：
- 父子检索补回的 chunk 一定有 document_id+chunk_id；
- 但 sparse 路有可能 metadata 解析失败缺 chunk_id；
- buildPseudoDocID 兜底用 `document_id+chunk_id`（再不行就 content 前缀）当 key，避免键值冲突时"误合并不同 chunk"。

## Q12：过滤表达式（Filter Expr）是怎么拼接的？多租户 / 知识库范围怎么生效？

### 基础答案

`BuildFilterExpr` 把 `RetrieveOptions` 的几个字段拼成 Milvus 表达式：

| 选项字段 | 表达式片段 |
|----------|-----------|
| `TenantID` | `metadata['tenant_id'] == 123` |
| `AllowedKBIDs` | `metadata['kb_id'] in [1, 2, 3]`（去重 / 跳过 0） |
| `KBScope` | `metadata["kb_scope"] == 'global'` |
| `ActiveGlobalKBID` | `metadata["kb_id"] == 7` |
| `Language` | `metadata['language'] == 'zh-CN'` |
| `Category` | `metadata['category'] == 'doc'` |
| `Expr`（自定义） | 用户自带的表达式 |

最终拼接：`(条件1 && 条件2 && ...) && (用户自定义)`。

**触发位置**：
- 入口 `RetrieveWithOptionsAndMetrics` 调一次，把表达式塞进 dense 路；
- sparse 路在 `MilvusLikeCandidateProvider.SearchCandidates` 里也会读 `req.Expr`，再用 `(base_expr) && (content like "%term%")` 套；
- `RetrieveKnowledge` 把 `KBScope=global, ActiveGlobalKBID=...` 转换成 expr，用于知识库定向召回。

### 深入追问

**Q：为什么 `kb_scope` 用双引号、`tenant_id` 用单引号？**

Milvus expr 语法对字符串值都接受单/双引号，但 metadata key 的引号风格在 Milvus 不同版本对解析的容错有差异，代码里**故意混用**（kb_scope/kb_id 用双引号 key，其他用单引号 key）以保持向前兼容历史 schema。统一可以重构，但风险大。

**Q：`AllowedKBIDs` 和 `ActiveGlobalKBID` 同时存在时怎么办？**

两个条件都加进 conditions，**用 && 串起来**——必须既在 AllowedKBIDs 内，又是 ActiveGlobalKBID。这种"双重收紧"是租户安全的关键：即便 ActiveGlobalKBID 写错，AllowedKBIDs 仍能兜住越权访问。

**Q：自定义 Expr 会不会有 SQL 注入风险？**

会，所以 `opts.Expr` 仅服务端可信调用方设置（如 retrieve_service 的内部逻辑），不直接暴露给 API 入参。前端可控的字段只有 KBScope / Language / Category 等枚举值，不会让用户随便拼 expr。
