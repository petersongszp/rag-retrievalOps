## 写在前面：为什么治理比算法更难

在讲具体话术之前，先说一段叙事——这是你介绍这块模块时的"中心思想"，所有具体回答都围绕它展开。

> "做 RAG 这两年我有个观察：**算法侧的天花板不高**——同一个开源 Embedding，谁用都能跑出 70% 的 Recall@5；同一套 RRF 融合，谁实现都差不多。真正拉开差距的是上线之后的**治理能力**。
>
> 因为算法是单点优化，一个人专注一个月就能调到位。但治理是**系统工程**，要把评测、灰度、回滚、成本、审计、多租户这 6 件事串成一个闭环——每一件事单独做都不难，**难的是不漏一环**。
>
> 漏哪一环都会出事：
> - 漏评测：上线翻车，用户先告诉你 "不准了"。
> - 漏灰度：翻车面是 100%，回滚之前已经被骂上热搜。
> - 漏回滚：发现问题没有止血手段，只能熬通宵。
> - 漏成本：老板月底看账单，问 "这钱花在哪了" 你答不上。
> - 漏审计：监管来查，没有 before/after 记录就是合规事故。
> - 漏多租户：一次水平越权，整个 SaaS 业务直接 GG。
>
> 算法不行可以加班调，治理不行是**架构层面的硬伤**——补起来要拆模块。所以我们项目把"运维治理"当成 Phase 3/Phase 4 的核心攻坚方向，做了一整套'评测驱动上线 + 5 阶段灰度 + 三层回滚 + 多维成本归因 + 全维审计'的体系。"

这段话有 3 个钩子：
1. **算法天花板不高**——直接破除"做 RAG = 调模型"的偏见。
2. **6 件事的闭环**——让面试官 get 到你不只是写代码，而是在做系统设计。
3. **每件事都举了一个翻车场景**——让面试官认可"这事确实重要"。

讲完这段，**面试官 80% 会从这 6 件事里挑一件追问**。下面就是这 6 件事的应答话术。

## 第一部分：6 件事的核心话术

每个话题给"基础回答 + 亮点细节"双层应答。基础回答用来"讲清楚"，亮点细节用来"扛追问"。

### Q1：评测驱动上线是什么？为啥不能直接灰度？

**基础回答**：

> "评测驱动上线指的是：任何一次策略/索引/模型的变更，都要先在离线评测集上跑出量化指标，过 Gate 之后才能进灰度。
>
> 我们项目里有个 `evaluation.Runner`，输入是 baseline + candidate 两个 StrategyProfile，加上一个标注好的数据集（带 RelevantIDs / CitationTargets / Tags），跑完之后输出 Recall@K / MRR / nDCG / Citation 命中率 / P95 延迟 / 拒答误判率 等十几个指标。然后 `EvaluateGate` 比较 candidate 相对 baseline 的 delta，过门禁才放行灰度。"

**亮点细节**：

> "Gate 一共 8 项指标，我背几个核心阈值：
> - **Recall@K 必须比 baseline 提升 ≥ 8 个百分点**。这个 0.08 不是拍脑袋——评测集上低于 8% 的 delta 都在数据集噪声范围内，提升不显著就别上。
> - **P95 延迟劣化 ≤ 20%**。再大用户能感知到"卡了"。
> - **误拒答率 ≤ 5%**。"宁可漏拒不可错拒"——错拒会被骂"问的好好的不答"。
>
> 还有一个比较巧妙的设计：**Gate 是先把 8 项 check 全部计算完再统一遍历**，不会 short-circuit。这样即使整体 fail，前端依然能看到每一项 actual/expected 的对比，运维就能直接定位到底是哪个指标拖了后腿——而不是只告诉你 'failed'，让你自己去查。"

**🎯 留钩子**：讲完这段，面试官多半会问"你们评测集多大""怎么避免过拟合""阈值怎么调"——继续按下面 Q1.1 / Q1.2 应对。

#### Q1.1（追问）：评测集过拟合怎么办？

> "三个手段叠加：
> 1. **持续补样本**：每周从线上 retrieve_log 抽真实 query 进评测集（用脱敏 + 标注流程）。
> 2. **分子集统计**：candidate 在 RewriteApplied 子集上单独算 RewriteGainDelta，避免改写策略只在标注集合上'看起来好'。
> 3. **拒答场景独立**：评测集里专门标 `out_of_scope`/`insufficient_evidence` 这类 tag，`expectsRefusal` 函数会专门验证拒答触发是否正确。
>
> 本质上评测集是'体检报告'，定期更新、分项体检，比单一指标更可靠。"

#### Q1.2（追问）：阈值是写死的吗？

> "默认值由 `DefaultGateThresholds` 提供，但 EvaluateGate 接收 thresholds 参数，调用方完全可以按业务严苛度覆盖。比如金融场景把 P95 阈值降到 5%，娱乐场景可以放到 30%。这样**同一套 Gate 引擎跑不同业务**——这是我设计时刻意保留的扩展点。"

---

### Q2：灰度发布怎么分阶段？分桶为什么不能随机？

**基础回答**：

> "我们项目灰度走 5 个 stage：phase1（兜底） → internal（内部全量） → small_flow（公网 5%） → batch（20%~50%） → full（100%）。
>
> 关键是用户分桶**不随机**，是基于 userID 的 FNV 稳定哈希——同一个 userID 哈希结果固定，永远落在同一个桶里。这叫**稳定分桶**。
>
> 决策入口是 `release.Decide(ragCfg, phase2Available, userID, userRole)`，里面有三层优先级：phase2 不可用强制 phase1 → runtimeOverride 优先 → 内部用户白名单/角色优先 → 普通用户按 stage 分桶。"

**亮点细节**：

> "为什么必须稳定分桶？讲两点：
>
> 1. **用户体验不能割裂**。如果随机分桶，同一个用户问第一个问题走 phase2 拿到答案 A，刷新一下走 phase1 拿到答案 B，他会以为系统坏了。
>
> 2. **数据对比有意义**。A/B 对比的前提是 baseline 和 candidate 的样本分布稳定，随机分桶相当于在每次请求都重新分组，统计量都是噪声。
>
> 还有一个细节，我们用 **FNV-32a** 而不是 MD5/SHA。原因很实用——灰度判定每个请求都要算一次，FNV 是非加密哈希，比 MD5 快一个数量级。分桶不需要加密强度，只需要打散均匀，FNV 完全够用。
>
> 另外**运行时 override** 是个杀手锏——通过 `SetRuntimeOverride(stage, reason, userID)` 可以**不重启服务**直接把 stage 切到 phase1，秒级回滚。这是我们能做到'1 秒一键回滚'的关键。"

#### Q2.1（追问）：内部用户怎么识别？

> "两条路叠加：UserAllowlist（白名单 ID）+ InternalRoles（默认 ['admin']，可配置扩展）。命中其中之一就强制走 phase2，无论当前 stage 是什么。这是为什么我们做内部测试时，公网用户还是 phase1，但 admin 已经能用上新策略了。"

### Q3：A/B 实验和灰度发布有什么区别？

**基础回答**：

> "看着像，但目的完全不同：
> - **灰度的目的是'安全推全'**——candidate 已经过 Gate 了，灰度只是'验证不翻车'。看的是错误率、延迟、空结果率。
> - **A/B 的目的是'对比哪个更好'**——两个策略都能用，跑真实流量看哪个指标更优。看的是 baseline 与 candidate 的 delta。
>
> 我们项目两套机制是**串行**的：先评测 → 灰度 → 推全 → A/B → 推全胜出方。"

**亮点细节**：

> "A/B 实验有个别的 RAG 系统不一定做得好的特性——**Shadow Mode**。candidate 跑但不影响用户，只把检索结果埋点。这样高风险变更（比如模型改写、新 reranker）可以先在影子里跑一段时间，**有指标但没风险**。
>
> 决策匹配链是 7 层：feature flag → status=running → 时间窗 → 环境（all/internal/external）→ target_kb_ids → target_query_types → 流量分桶。命中后分到 baseline / candidate / shadow 三组之一。
>
> 还有一个值得讲的工程细节：实验的稳定分桶用的是 **requestID 优先，userID 兜底**——这意味着同一个用户不同请求可能落在不同组。看似破坏了'用户级一致性'，但实验场景里更看重'请求级独立性'，否则一个用户多次问相同问题会污染单边样本。这是和灰度发布相反的取舍——**一致性 vs 独立性**，按场景选。"

#### Q3.1（追问）：怎么判定 candidate 胜出？

> "代码里 `summarizeRecord` 输出三个 delta：AvgDurationDeltaMS / AvgContextTokensDelta / ErrorRateDelta。三个都是负向越好（更快、更省、更稳）。但这些只是**通过性指标**，最终决定推不推全还要结合业务质量评分（人工标注或者大模型评测）。技术 delta 决定能不能推，业务质量决定该不该推。"

### Q4：策略热加载怎么做的？为什么不能重启服务？

**基础回答**：

> "我们做策略热加载的核心思路是**配置快照 + 失败回滚**。改一条 Feature Flag 的流程是：
>
> 1. 先 `snapshot := *cfg` 拍快照。
> 2. 调 `SetPhase3StrategyFlag(flagKey, enabled)` 改 flag。
> 3. 调 `applyRolloutSideEffects` 改连带的影子比例等副作用。
> 4. 调 `reconfigureManager(ctx, cfg)` 让 Milvus 检索器重新装载。
> 5. 任何一步失败 → `*cfg = snapshot` 整体回滚。
>
> 整个过程不重启服务、秒级生效。"

**亮点细节**：

> "有几个细节比较考验工程功底：
>
> 1. **高风险 flag 的护栏**。`isHighRiskFlag` 标记的 flag（比如模型改写）首次启用必须先走 shadow 或 canary，不能直接 enabled。代码里直接 fail-fast：`high-risk flag must be enabled through shadow or canary first`。这是一道防止运维误操作的硬护栏。
>
> 2. **ConfigVersion 一致性保护**。`ensureStateLocked` 会比较 `cfg.ConfigVersion` 和 `lastConfigVersion`，发现不一致才重新初始化 flag 状态。这避免了'配置外部刷新但内部状态滞后'的问题——多实例集群里这个特别容易出 bug。
>
> 3. **审计 + 版本流双写**。每次 UpdateFlag 成功，会同时调 `recordOperationLocked`（记 from→to 操作）和 `appendVersionLocked`（生成可回滚的 VersionRecord，metadata 里带 enabled / status / rollout / strategy_version 四个关键字段）。后者的存在让我们能**回滚到任意历史版本**，而不是只能 disabled。"

#### Q4.1（追问）：rolloutPercentage 设 30 是什么意思？

> "视 flag 而定。普通 flag 这个字段是辅助信息，实际灰度比例由灰度阶段决定。但**模型改写**这种特殊 flag 不一样——`status=shadow/canary` 时把 rolloutPercentage 转成 `cfg.RAG.Phase3.ModelRewriteShadowRatio = rolloutPercentage / 100`，让影子流量按这个比例触发模型改写。这是单独 flag 才有的副作用，写在 `applyRolloutSideEffects` 里集中处理。"

### Q5：怎么"一键回滚"？回滚到哪一层？

**基础回答**：

> "我们有**三层回滚**，针对不同场景：
>
> 1. **Stage 级回滚**（最暴力）：调 `release.SetRuntimeOverride('phase1', reason, userID)`，整个 phase2 流量瞬间回到 phase1。秒级，不重启。
> 2. **Flag 级回滚**（精确）：`phase3admin.Rollback(target, flag_keys, reason)` 把指定 flag 回到 phase2_baseline 或某个历史版本。带快照保护，失败自动还原。
> 3. **实验级回滚**：`experiment.Rollback(experimentID, reason)` 把指定实验 status 改成 stopped、traffic 清零，并入队补偿任务清理副作用。
>
> 三层各管各的——日常调 Flag 级，大故障调 Stage 级。"

**亮点细节**：

> "讲一个我觉得很'工程化'的细节：**`RollbackPlan()` 不仅返回'怎么改配置'，还返回了一份'回滚后必须做的事情清单'**。代码里写得很直白：
>
> 1. Set runtime release stage to phase1
> 2. Disable RAG_ENABLE_HYBRID_RETRIEVAL in persistent config
> 3. Disable RAG_ENABLE_QUERY_REWRITE / RAG_ENABLE_DYNAMIC_TOPK if metrics still regress
> 4. Disable RAG_ENABLE_ADVANCED_RERANK when rerank latency keeps rising
> 5. Confirm retrieve P95, empty-after-filter, and error rate return to Phase 1 baseline
>
> 你看，**回滚不是改一个开关**——是一个分层的 playbook。先拉回 stage、再视情况关掉相关 flag、最后必须确认指标恢复 baseline 才算完成。这种'回滚清单内化在代码里'的做法，能大幅减少凌晨救火时的判断失误。"

#### Q5.1（追问）：怎么定义"回滚成功"？

> "不是配置改完就算成功，而是看治理 Gate 重新通过：
> - 错误率、P95、Empty-After-Filter ratio 回到 baseline 范围。
> - 治理 Gate 5 个 guard 全 pass。
> - RollbackSuccessRate 治理指标 ≥ 90%。
>
> 这是我们在 governance Gate handler 里专门做的'回滚效果验证'——`releaseGuardPassed = !RollbackRecommended`，如果系统还在建议回滚，就说明前一次回滚不够。"

#### Q5.2（追问）：回滚操作有审计吗？

> "必须有。`RollbackStrategy` handler 在调完回滚之后立即调 `persistAuditEvent` 写 KBAuditEvent，Action=`strategy_rollback`，记录操作人、target_version、原因。同时内存层面也通过 `recordOperationLocked` 记录一条 OperationRecord。**双写保证回滚动作不会丢审计**——这是合规底线。"

### Q6：成本归因怎么做？怎么知道一笔钱花在哪？

**基础回答**：

> "核心是**每次检索都落一条 kb_cost_trace 记录**，里面挂了 7 个维度 ID（KBID / UserID / ExperimentID / StrategyVersion / QueryType / LLMModel / RequestID）和 5 段成本拆分（EmbeddingCost / RetrievalCost / RerankCost / LLMCost / VectorStorageCost）。
>
> 7 维 ID 全部带 GORM index，按任何一个维度 group by 都能秒级聚合。聚合接口用一个 `resolveKey func(*KBCostTrace) (string, string)` 闭包，传进去就能切片到任意维度——按 KB / 按策略 / 按模型 / 按租户……都是同一套代码。"

**亮点细节**：

> "几个我觉得设计得比较细致的点：
>
> 1. **拆 5 段而不是只记 total**。LLM 太贵就换便宜模型；Embedding 太贵就上缓存；Rerank 太贵就跳过。**只记 total 等于知道'花了 100 块'，但不知道往哪砍**。
>
> 2. **CacheSavedRetrievalCost / CacheSavedRerankCost 单独记**。走缓存命中时把'本来要花的钱'算进 saved 字段。运营 dashboard 可以呈现'缓存今天帮你省了多少钱'——**让缓存的价值可量化**，而不是凭感觉说'缓存挺有用的'。
>
> 3. **CostTraceID 与 RequestID 解耦**。同一次请求如果跨 KB 检索，会落多条 cost_trace（KBID 不同），但 RequestID 相同，方便按 request 维度合计。这种拆分让我们能同时回答两个问题：'这一次请求花了多少钱'（按 RequestID 合计）'这个 KB 总共花了多少'（按 KBID 合计）。"

#### Q6.1（追问）：聚合性能怎么扛？

> "三招：
> 1. **维度全部带 index**，CreatedAt 也带 index。
> 2. **强制时间窗**，`ListByCreatedAt(start, end, kbID)` 永远走时间索引而不是全表扫。
> 3. **预聚合**：24h 窗口直接查明细，30 天以上窗口走小时级聚合表。
>
> 当前是单库单表，QPS 上来后会改成 partition by month 加按租户分库。"

### Q7：审计追踪和普通日志有什么区别？

**基础回答**：

> "普通日志给开发看的，stdout / 文件、滚动 7-30 天就清。审计是给合规、安全、运营看的，**MySQL 持久化、长期不可删、结构化字段**。
>
> 我们 KBAuditEvent 表的字段拆得很细：
> - 谁干的：TenantID / OperatorID / UserID / ActorName / IP / UserAgent。
> - 干了什么：Action / ResourceType / ResourceID。
> - 状态变化：BeforeData / AfterData。
> - 结果与原因：Result / Reason。
> - 串联：AuditTraceID / RequestID。
> - 合规：SensitiveFieldsMasked（记录哪些字段被脱敏）。
>
> 关键 Action 全在 `governance.go` 集中定义：strategy_flag_update / strategy_rollback / experiment_rollback / collection_switch / collection_rollback / permission_change …… 共 19 个。**集中定义避免了拼写不一致——审计字段一旦写进库就是历史记录，错一个字符就查不到了**。"

**亮点细节**：

> "我特别想讲一个'反直觉'的点：**审计写入失败，主流程不能 fail**。
>
> 看代码里 handler 的写法都是 `_ = persistAuditEvent(...)`，即使审计入库失败，也只是丢一条审计，不影响业务返回。这个设计是反直觉的——直觉上'审计这么重要怎么能丢'。但实际中**主流程稳定性 > 审计完整性**：
> - 主流程因为审计失败而 5xx → 业务大面积告警，损失大。
> - 偶尔丢一条审计 → 通过 audit_coverage_rate 指标兜底监控（治理 Gate 卡 ≥ 60%）。
>
> 这是个典型的'优先级权衡'——**写审计可以容错，但不能容错到看不见**。所以我们用 audit_coverage_rate 在治理 Gate 里持续监控，覆盖率掉了就告警。
>
> 还有 SensitiveFieldsMasked 字段挺有意思——它不是'掩了哪些字段的值'，而是'记录了'哪些字段被掩过'。这样审计员看 after_data 时知道'这里的 phone 是已脱敏的，原值需要走更高权限审批拿'。**审计本身也要满足'最小知情'原则**。"

### Q8：多租户隔离怎么做？怎么防水平越权？

**基础回答**：

> "四道防线：
> 1. **数据隔离**：所有业务表带 tenant_id，所有查询强制 where tenant_id = ?。
> 2. **配额隔离**：QuotaChecker 在写操作前校验 MaxKBCount / MaxDocCount / MaxStorageMB / MaxAPICallsPerDay。
> 3. **向量隔离**：Milvus collection 共享，chunk 元数据带 tenant_id，检索时 `expr=tenant_id == X` 过滤。
> 4. **审计隔离**：KBAuditEvent 带 TenantID，租户 A 审计员只能看自己租户。
>
> 关键的水平越权防线是：**tenant_id 从 JWT 解出来，绝不接受前端传值**。Middleware 解 JWT 拿到 userID + tenantID，挂在 ctx 上，下层 service 取出来透传到 GORM 条件。前端传的 tenantID 直接忽略——这条规则在 code review 是 P0 卡点。"

**亮点细节**：

> "QuotaChecker 设计有几个细节我比较满意：
>
> 1. **API 调用配额走 Redis 自增**。`GetAPICallCount(tenantID)` 走 Redis，key 是 `quota:api:{tenantID}:{YYYYMMDD}`，每次请求 INCR + EXPIRE 86400，第二天自然滚动。**不需要清理任务，靠 TTL 自然消亡**——这是分布式计数器最简洁的实现。
>
> 2. **存储配额按字节算**。`CheckStorageLimit` 内部用 `bytesPerMB = 1024 * 1024` 做单位换算，向上取整：`(totalBytes + bytesPerMB - 1) / bytesPerMB`。这种'不让用户因为浮点误差占便宜'的细节，是处理资源配额的基本素养。
>
> 3. **配额超限返回 429 而不是 403**。代码里用的是 `NewTooManyRequestsError`——`429` 语义是'请求被限流'，`403` 是'权限不足'。配额本质是限流不是权限。这种**HTTP 状态码语义化**对接入方友好，他们可以根据 429 自动 backoff，而不是误以为权限被吊销了。
>
> 至于'恶意流量打爆 Milvus' 这种秒级流量爆冲，API 配额（天级别）兜不住。我们额外做了**租户级 QPS 限流**（middleware 层 token bucket，按 tenantID 分桶），再加上 Milvus 资源组隔离（高级版本）。三道防线叠加。"

## 第二部分：场景化追问应对

### 场景 1：面试官问"线上真出过故障吗？怎么处理的？"

不要承认"翻过车"——但要讲一个**演练/灰度过程发现回归**的小故事，体现"治理体系起作用了"：

> "真翻车没有，但灰度过程发现过回归。有一次我们要上一个新的 reranker 模型，先在 internal stage 跑了一周指标都不错，切到 small_flow（5%）的时候发现 P95 延迟上涨了 28%。
>
> 处理流程：
> 1. 治理 Gate 自动告警（cost_per_1k_queries 还没破阈值，但 release summary 已经标了 RollbackRecommended）。
> 2. on-call 看了 cost_trace 拆分，发现 RerankCost 占比从 15% 涨到 40%——是新 reranker 的 batch_size 配错了。
> 3. 调 `release.SetRuntimeOverride('phase1', 'rerank latency regression', oncallID)` 秒级回滚到 phase1。
> 4. 写一条 audit_event 记录回滚原因。
> 5. 同时把对应的 strategy flag 也调回 disabled，避免下次配置刷新又把新 reranker 拉起来。
> 6. 改完 batch_size，重新跑评测、过 Gate，再灰度。
>
> 整个过程从告警到回滚到指标恢复 baseline 一共 12 分钟。**这就是为什么治理体系值得做——故障不可避免，但故障时长可控**。"

### 场景 2：面试官问"你们这套和 Argo Rollouts / Flagger 这种通用灰度工具有什么区别？"

> "Argo Rollouts / Flagger 解决的是**通用 Kubernetes 服务的灰度**，主要是按 HTTP / metric 切流量。我们的灰度是**业务感知的灰度**——
>
> - 我们要按 userID 稳定分桶，让同一个用户始终在同一组——通用工具按 IP / Cookie 做不到稳定。
> - 我们要按 KB / queryType / environment 多维度匹配——通用工具只关心 HTTP 维度。
> - 我们要把灰度结果反查到 cost_trace / audit_event——通用工具不知道你的业务模型。
>
> 所以是**应用层灰度**（业务感知）和**基础设施层灰度**（流量调度）两个层面的事。生产里我们其实可以两层都用——基础设施层先做副本灰度，应用层再做策略灰度，两层独立回滚互不影响。"

### 场景 3：面试官问"评测集自己造的吗？质量怎么保证？"

> "种子数据是人工标注的（产品 + 算法工程师一起标了 500 条），后来主要靠两条管道：
>
> 1. **线上回流**：每周从 retrieve_log 抽真实 query，做脱敏后由人工标注 RelevantIDs。
> 2. **大模型辅助标注**：用 GPT-4 / Claude 做'第二意见'，与人工标注 disagreement 的样本重点 review。
>
> 质量保证的关键是**多人独立标注 + Kappa 一致性检验**。同一条样本至少 2 人独立标，Kappa < 0.7 的就送复核组讨论。
>
> 评测集本身也有'gating'——加新样本要看 baseline 在新样本上的表现是否合理（比如 baseline 在新样本上的 Recall 不应该 < 30%，太低说明样本本身有问题，不该进评测集）。"

### 场景 4：面试官问"如果让你重做这套治理，你会改什么？"

这是经典开放题，**不要说"我会重新做一遍"**，要讲具体改进点：

> "我会重点改三个地方：
>
> 1. **补偿队列持久化**。现在是内存有界队列（容量 256），重启就丢。生产规模上来后我会切到 Redis Stream + 消费者组，做到 at-least-once。
>
> 2. **Gate 阈值多租户化**。现在 `DefaultGateThresholds` 是全局的，金融客户要严，娱乐客户可以松——做成 `GetThresholdsForTenant(tenantID)`，每个租户独立阈值，配置在 RAGTenant 表里。
>
> 3. **审计写入异步化**。现在 handler 里同步调 persistAuditEvent，虽然失败不阻塞主流程，但还是占用主流程的 latency。我会改成扔到 Redis Stream，由独立消费者落库——主流程只负责把审计事件丢队列，更轻量。"

## 第三部分：常见误区与"翻车点"

### 误区 1：把"灰度"和"A/B"混着讲

很多候选人讲这块时说"我们用灰度做 A/B 实验"——这是混淆。**灰度的目的是推全，A/B 的目的是对比**。讲的时候一定要分开，不然面试官追问到第二层就会发现你没分清。

### 误区 2：说"我们做了 Gate"，但讲不出阈值

Gate 的核心是阈值。讲 Gate 不讲阈值就是空谈。**至少记住三个核心阈值**：Recall +0.08 / P95 ratio 0.20 / 误拒答率 0.05，并知道为什么是这三个数。

### 误区 3：说"一键回滚"但答不出具体 API

"一键"听起来很厉害，面试官一定追问"具体怎么一键"。**记住三个 API**：
- `release.SetRuntimeOverride("phase1", reason, userID)`
- `phase3admin.Rollback(target, flagKeys, reason, operatorID)`
- `experiment.Rollback(experimentID, reason)`

讲清楚每个对应什么场景。

### 误区 4：说"多租户隔离"但说不出 tenant_id 来源

这道题面试官一定追问"tenant_id 哪来的"。**唯一正确答案：从 JWT 解出来，绝不接受前端传值**。这是水平越权防线的核心。

### 误区 5：把"成本归因"讲成"成本统计"

统计是"花了 100 块"，归因是"100 块花在 KB-A 的 reranker 上"。讲成本归因必须讲清楚**多维度 group by**，并能举出"按 KB / 按策略 / 按模型"三种切片的实际场景。

### 误区 6：审计与普通日志不分

面试官问"审计是不是日志记一下"——**坚决说不**。审计的核心特征：MySQL 持久化、结构化字段、before/after 双写、不可删、actor 可追溯。普通日志一项都不沾。

## 第四部分：高级问题应对

### Q：怎么防止 Gate 阈值被人偷偷调松？

> "两层防：
> 1. **配置变更走审计**——`DefaultGateThresholds` 如果改成可配置，配置变更必须落 audit_event，Action=`gate_threshold_update`。
> 2. **配置变更走双人审批**——治理动作的高权操作（包括 Gate 阈值调整、回滚到非 baseline 版本）走 4-eyes 审批。
>
> 这是从'代码层防御'升级到'流程层防御'。技术管不住人时，流程必须接管。"

### Q：评测和真实线上效果不一致怎么办？

> "经典问题——评测集 ≠ 线上分布。我们做了几件事：
>
> 1. **线上回流持续更新评测集**（前面讲过）。
> 2. **A/B 实验作为线上验证**——评测过 Gate 不等于上线，还要 A/B 跑一段时间确认线上指标。
> 3. **影子流量观察**——高风险变更先上 ShadowMode，看真实流量下的稳定性。
>
> 评测是必要不充分条件——**过 Gate 不代表能上线，但不过 Gate 一定不能上线**。"

### Q：灰度过程指标在抖动，怎么判断是真回归还是噪声？

> "三个手段：
>
> 1. **看观察窗口长度**——5% 灰度至少观察 1 个完整周期（一般 24h），覆盖业务高峰低谷。
> 2. **看样本量**——RetrieveLog 至少累计 N 条（比如 1000+）才有统计意义。
> 3. **看 delta 大小**——P95 delta 在 ±5% 以内大概率是噪声，> 10% 才值得 alarm。
>
> 我们 release_summary 里专门有 `RollbackRecommended` 字段就是综合这三个维度算出来的——不是单个指标超阈值就回滚，而是多维度联合判断。"

### Q：如果让你设计第 4 层回滚（更细粒度），你会怎么做？

> "我会做**单 query 级回滚**——给每条 query 加一个 `force_strategy_version` 头，强制走指定策略。这个能力主要用于：
>
> 1. **客诉定向 fix**——某个 VIP 客户报告某条 query 不准，运营临时给这条 query 强制走老策略，不影响其他用户。
> 2. **A/B 实验对照组锁定**——某些实验需要部分流量永远走 baseline 做永久对照。
>
> 实现上就是在 release.Decide 入口判断 ctx 里有没有 force flag，有就直接返回固定 Decision，跳过分桶逻辑。改动很小，但灵活度大幅提升。"

```
MRR / nDCG / Citation* delta ≥ 0

RefusalFalsePositiveRate ≤ 0.05

（条件触发）P95 latency ms ≤ threshold
```

```
release.SetRuntimeOverride("phase1", reason, userID)
```

```
feature flag → status=running → 时间窗 → environment → kb_ids → query_types → traffic 分桶
```

```
costGuardPassed       latestCostPer1K < 25
```
