## 1. 整体架构：策略治理 + 灰度发布是怎么分层的

**Q：你们这个策略治理与灰度发布模块整体是怎么设计的？**

**我的回答：**

我们把这块拆成了**三层解耦**：发布层（release）、策略 Flag 层（phase3admin）、实验/评测门禁层（experiment + evaluation）。

最底下的 `release` 控制器只决定**一件事**：当前请求走 phase1 还是 phase2。它读一个 `RAGReleaseConfig`，里面有 `stage`（phase1/internal/small_flow/batch/full）、`canary_percent`、`batch_percent`、`internal_roles`、`user_allowlist` 五个字段，每个请求进来调一次 `release.Decide()` 就能得到 `Decision{Strategy, Stage, Reason, UsePhase2}`，决策结果还会落到检索日志里方便回查。

中间是 `phase3admin`，它管的是 **7 个 Phase3 策略 Flag**（父子检索、策略式 TopK、证据拒答、引用一致性、领域词、路由改写、模型辅助改写）。每个 Flag 有自己的状态机：`disabled / shadow / canary / enabled / rolling_back`，每次改动都会落一条 `VersionRecord`（版本记录）+ `OperationRecord`（操作流水），相当于策略的 Git 历史。

最上层是 `experiment` 和 `evaluation`：实验平台支持 baseline/candidate/shadow 三组流量分桶，候选组在上线前必须跑过 `evaluation.Runner`，**通过 `GateThresholds` 八项门禁**才允许进入下一档灰度。

**这三层是单向依赖：release 不知道 Flag、Flag 不知道实验、实验不知道路由。** 这样回滚可以只动 release stage 一秒生效，调 Flag 不会污染发布状态机，做评测也不会误改线上流量。

> 相关代码：[controller.go](../../backend/internal/rag/release/controller.go)、[phase3admin/state.go](../../backend/internal/rag/phase3admin/state.go)、[experiment/state.go](../../backend/internal/rag/experiment/state.go)、[evaluation/gate.go](../../backend/internal/milvus/evaluation/gate.go)

### 🔍 深挖追问兜底

**Q：三层为什么不合成一个大的 Strategy Manager？**
> 三层关心的时间尺度完全不一样：release 是「秒级」的紧急开关，Flag 是「分钟到小时」的策略迭代，实验是「天到周」的 AB 验证。绑在一起会让回滚带上一堆历史包袱。**线上事故只想动 release stage，绝不希望顺手把别人的 Flag 也回滚了**，所以宁愿三套独立状态。

**Q：策略决策结果怎么贯穿全链路？**
> `release.Decide` 返回的 `Decision` 会写到 `KBRetrieveLog` 的 `strategy / release_stage / reason` 三列，加上 `experiment_id / experiment_group` 两列，做 release summary 时直接 SQL 聚合就能算出每个 stage 的错误率、Empty-After-Filter 率，不依赖额外埋点。

**Q：Flag 改了之后下游组件怎么感知？**
> 改完先 `cfg.RAG.FeatureFlags.SetPhase3StrategyFlag()` 改全局配置，然后调 `milvus.ReconfigureGlobalManager(ctx, cfg)` 重建一次 Manager 内部依赖；如果重建失败会回滚 `*cfg = snapshot`，保证「要么全成、要么不变」，不会出现一半组件读到新配置、一半读到旧配置的中间态。

## 2. Feature Flag 热加载与版本回滚

**Q：你们 Feature Flag 是怎么实现热加载的？版本怎么管理？**

**我的回答：**

热加载的核心是「**改内存全局配置 + 触发 Manager 重建 + 全程加锁**」，全程不需要重启服务。

入口在 [`phase3admin.UpdateFlag`](../../backend/internal/rag/phase3admin/state.go#L122-L165)：先 `sync.Mutex` 加大锁，然后做四件事——**校验**（Flag 是否在 7 个白名单里、`reason` 必填、`rollout_percentage` 在 0~100、status 是合法枚举）、**做配置快照** `snapshot := *cfg`、**应用变更** `cfg.RAG.FeatureFlags.SetPhase3StrategyFlag()` 并触发 `reconfigureManager(ctx, cfg)`、最后**追加版本记录**。

只要 `reconfigureManager` 返回错（比如新 Flag 触发了底层组件初始化失败），我们立刻 `*cfg = snapshot` 把配置整体回退，再把错误抛出去给前端，保证**配置变更原子**——要么全生效要么完全没变。

版本管理是**写时追加**：每次 `UpdateFlag` 都会 `appendVersionLocked` 生成一条 `VersionRecord{VersionID: flagKey:v{N}, Metadata: {status, enabled, rollout_percentage, strategy_version}}`，挂在 `versionRecords[flagKey]` 链表头部，同时存到 `versionByID` 索引。这个版本就是后续回滚的「目标快照」。

**回滚有两个口**：一个是回到 phase2 基线（`target_version=phase2_baseline`），按 [`rollbackOrder`](../../backend/internal/rag/phase3/contract.go#L36-L44) 倒序把高风险的模型改写、路由改写一个个关掉；另一个是回到具体某个历史版本号，按 metadata 里的 `enabled/status/rollout_percentage` 还原。回滚也会重新触发 reconfigure，失败同样回退快照。

> 相关代码：[phase3admin/state.go](../../backend/internal/rag/phase3admin/state.go#L122-L259)、[phase3/contract.go](../../backend/internal/rag/phase3/contract.go)

### 🔍 深挖追问兜底

**Q：高频读、低频写，为什么用 `sync.Mutex` 不用 `RWMutex`？**
> 读路径其实不在 phase3admin 上，而是直接读 `config.Global.RAG.FeatureFlags`（业务请求那边是无锁读全局变量）。phase3admin 只管理「状态机 + 版本表」这种管理面操作，写远比读多，且每次都要触发 reconfigure，没必要 RWMutex 增加复杂度。**简单锁能解决就别上花活**。

**Q：reconfigure 失败回滚 `*cfg = snapshot` 不是浅拷贝吗，map / slice 不会泄露？**
> `RAGFeatureFlags` 是纯 bool 字段结构体，没有 map/slice 字段，浅拷贝就是完整快照。要不是我们刻意把 Flag 设计成扁平 bool，这里就得 deep copy 了，**这其实是个隐性约束，新加 Flag 时必须守住**。

**Q：高风险 Flag（比如模型辅助改写）有没有额外约束？**
> 有硬约束：[`isHighRiskFlag`](../../backend/internal/rag/phase3admin/state.go#L493-L495) 标记的 Flag（目前是 `RAG_ENABLE_MODEL_ASSISTED_REWRITE`），从 disabled 切到 enabled 时必须先经过 `shadow` 或 `canary` 中间态，否则 `UpdateFlag` 直接返回 "must be enabled through shadow or canary first"。**这是代码层硬卡的，不是流程文档说说而已**。

## 3. 渐进式灰度的分桶与决策

**Q：你们 internal → 5% → 20% → 50% → 100% 这五档灰度是怎么落地分桶的？**

**我的回答：**

分桶用 **FNV-1a 哈希 + userID 取模 100**，整段逻辑在 [`matchesStableBucket`](../../backend/internal/rag/release/controller.go#L233-L243)，10 行代码搞定，关键是**稳定**——同一个用户在同一灰度档位永远落在同一组，不会因为请求时间不同被翻来覆去切策略。

决策顺序也是有讲究的，[`evaluateStage`](../../backend/internal/rag/release/controller.go#L166-L194) 里是：**先 allowlist → 再 internal role → 最后哈希分桶**。这就意味着指定的 QA 同学 ID 写进 `user_allowlist` 后，不管当前 stage 是 5% 还是 50%，他都拿得到 phase2；admin 角色直接全量 phase2；其余用户才走百分比哈希。

五个 stage 的语义：
- **`internal`**：只有 `internal_roles`（默认 `admin`）能拿到 phase2，做内部冒烟
- **`small_flow`**：按 `canary_percent`（默认 **5%**）哈希分桶
- **`batch`**：按 `batch_percent`（默认 **25%**）哈希分桶
- **`full`**：所有用户 phase2
- **`phase1`**：紧急回滚档，所有用户走旧策略

五档的 percent 不是写死，是 `RAGReleaseConfig` 配置项，运维想调成 5/20/50 可以直接改 YAML。配合 `RuntimeOverride` 还能不重启把 stage 切到任意值，stage 切换毫秒生效。

**所有决策都会把 `Reason` 字段（allowlist / internal_role / canary_bucket / outside_batch_bucket 等）写到检索日志**，做 release summary 时一查就知道某个用户为什么被分到这组，灰度可解释。

> 相关代码：[controller.go#L44-L76](../../backend/internal/rag/release/controller.go#L44-L76)、[config.rag.example.yaml](../../backend/config.rag.example.yaml#L112-L118)

### 🔍 深挖追问兜底

**Q：为什么用 FNV 不用 MurmurHash 或者 CRC32？**
> FNV-1a 是 Go 标准库 `hash/fnv` 自带的，零依赖、分布够均匀、计算只要纳秒级。这里用它不是为了密码学强度，只是要个**确定性的 userID→桶号** 映射，FNV 完全够。MurmurHash 要引第三方库不划算。

**Q：`userID=0`（匿名用户）怎么处理？**
> `matchesStableBucket` 第一行就是 `if userID == 0 || percent <= 0 { return false }`，匿名用户**永远走 phase1 基线**。这是有意为之——匿名用户量大但价值低，不让他们参与灰度可以保护核心指标。

**Q：灰度档位之间切换，老用户会不会突然被切策略，体验抖动？**
> 由于哈希是稳定的，**从 5% 涨到 20% 时，原本在 5% 桶里的用户全部还在，新增的是 5~20 这段新桶里的人**。同一用户不会反复横跳。但反方向缩流量（20%→5%）时会有用户被切回 phase1，所以我们约定**只前进不后退**，要缩流量直接走 rollback 回 phase1 全量。

## 4. 质量门禁：为什么是这 8 项指标和阈值

**Q：新策略发布前的质量门禁卡哪些指标？阈值是怎么定的？**

**我的回答：**

门禁定义在 [`evaluation.DefaultGateThresholds`](../../backend/internal/milvus/evaluation/gate.go#L5-L18)，**8 项指标**分三类：

第一类是**召回质量类**（4 项）：`MinRecallDelta ≥ 0.08`、`MinMRRDelta ≥ 0`、`MinNDCGDelta ≥ 0`、`MinCitationAccuracyDelta ≥ 0`。Recall 卡 +0.08 是因为我们 Phase2→Phase3 改造的核心目标是「至少提 8 个点召回」，没提就没意义；MRR/NDCG/引用准确率只要不回归就行，**「不退步」比「提升多少」更重要**。

第二类是**延迟类**（2 项）：`MaxP95LatencyRegressionRatio ≤ 0.20`、`MaxP95LatencyRegressionMS`（可选）。卡 P95 回退比例 20%，因为线上 P95 基线大约 800ms~1.2s，再涨 20% 就到 1.5s 边界，超过这个值用户就有感了。

第三类是**安全类**（2 项）：`MaxRefusalFalsePositiveRate ≤ 0.05`、`MinRewriteGainDelta ≥ 0`。证据拒答的假阳率（不该拒答的拒了）不能超过 **5%**，超过就是「过度保守」，用户看到一堆「无法回答」会跑。模型改写有正收益增量才允许大流量上。

**这套门禁是「一票否决制」**——`EvaluateGate` 里只要任一 check.Passed=false 就整体不通过，调 `g.Error()` 直接返回第一个失败的项。我们刻意不做加权投票，因为权重一旦引入就有人扯皮，**简单粗暴的硬门禁反而最公平**。

每个候选策略上线前先建 `EvalRun` 跑全量评测集，结果写到 `kb_eval_run` 表，附带 baseline 和 candidate 各项指标和 delta，过门禁的 run 才会被引用到 Flag 版本元数据里。

> 相关代码：[evaluation/gate.go](../../backend/internal/milvus/evaluation/gate.go)、[eval_execution.go](../../backend/internal/service/kb/eval_execution.go)、[handler_eval_run.go](../../backend/api/handler/kb/handler_eval_run.go)

### 🔍 深挖追问兜底

**Q：模型改写的门禁为什么是条件触发？**
> [`gate.go#L80`](../../backend/internal/milvus/evaluation/gate.go#L80) 写得很清楚，只有 `CandidateModelRewrite=true` 或者 `MinRewriteGainDelta>0` 才会插这条检查。**模型改写默认 shadow 跑**，shadow 阶段只采样不用结果，这时候卡 gain 没意义；只有要真正放量时才把门禁打开。

**Q：评测集会不会过拟合？**
> 会，所以评测集分**冻结基线集**（baseline freeze）和**滚动新增集**两部分。冻结集保证 KPI 可比，滚动集补充长尾 case 和近期 bad case。新策略必须两个集都过，详见 `phase3-baseline-freeze-strategy-switch-eval-dataset-implementation-tutorial.md`。

**Q：门禁失败的 EvalRun 怎么处理？**
> EvalRun 表会把 status 标为 succeeded（执行完成）但 report 里 `GateResult.Passed=false`，然后 phase3admin 这边读 report 时会拒绝把这个版本作为 `target_version` 应用，**前端策略中心会把它显示为「未通过门禁」状态**，需要重新评测或废弃。

## 5. 选型对比：为什么自己写而不是用 LaunchDarkly / Unleash

**Q：Feature Flag 这块业界有 LaunchDarkly、Unleash、OpenFeature 这些成熟方案，你们为什么自己写？**

**我的回答：**

主要三个原因：**强类型耦合、零延迟决策、合规可审计**。

第一，**我们的 Flag 不是通用业务开关，是和检索 pipeline 强耦合的策略开关**。比如 `RAG_ENABLE_MODEL_ASSISTED_REWRITE` 改了之后必须重建 retrieval Manager 里的改写器组件，这个钩子 LaunchDarkly 给不了，最后还得自己写 reconfigure 逻辑，外部 SDK 反而变成累赘。

第二，**决策频率太高**。一次检索请求要走 `release.Decide` + 多个 Flag 判断，QPS 几百的时候每秒上千次决策。用 LaunchDarkly 这种 SaaS 即使本地缓存也有同步延迟，我们直接读 `config.Global` 内存变量，**纳秒级**。

第三，**合规要求每次 Flag 变更必须有 reason、operator、版本号、可回滚**。`phase3admin` 里 [`UpdateFlag` 第 131 行](../../backend/internal/rag/phase3admin/state.go#L131) 硬卡 `reason` 必填、强制写 `OperationRecord` 和 `VersionRecord`、配合 `KBAuditEvent` 落审计表，外部 SDK 想做到这个程度要额外大量胶水代码。

**当然也有取舍**：我们没做用户级灰度规则的 DSL（LaunchDarkly 那种「userId in [...] AND country = US」），目前只支持 allowlist + role + 百分比哈希。后面如果业务场景复杂了再扩。**先解决 80% 场景，剩下 20% 不预先设计**。

### 🔍 深挖追问兜底

**Q：自己写不怕 bug 吗？测试覆盖怎么保证？**
> [`controller_test.go`](../../backend/internal/rag/release/controller_test.go) 和 [`phase3admin/state_test.go`](../../backend/internal/rag/phase3admin/state_test.go) 覆盖了决策矩阵、override、回滚、高风险 Flag 拦截等关键路径。核心逻辑就几百行，比集成 SDK 引入的复杂度低得多。

**Q：多实例部署时 Flag 状态怎么同步？**
> **目前没做跨实例同步，是已知缺陷**。Flag 状态存在每个进程的内存里，多副本场景下管理员调一次接口只生效在被路由到的那台。生产上靠的是「改完立刻调一次配置中心 reload」的约定，未来计划是把状态搬到 Redis 或 etcd 里做 watch。

**Q：和 OpenFeature 标准比怎么取舍？**
> OpenFeature 的好处是给业务方一个统一接口，未来好换底层。我们目前**业务方都是内部固定几个调用点**，统一接口收益不大；如果以后要给外部 SDK 用户暴露 Flag 控制，会考虑包一层 OpenFeature 兼容层。

## 6. 线上排障：灰度过程中指标突然劣化

**Q：你们灰度到 20% 的时候，突然发现 phase2 错误率涨到 8%，P95 也飙到 3 秒，你怎么排？**

**我的回答：**

整套流程我们演练过，叫 **「30 分钟止损」预案**，分四步：

**第一步：先止血（5 分钟内）**。值班看到飞书告警，先调 `GET /api/admin/kb/release/summary?minutes=15` 看一眼，确认 `RollbackRecommended=true`、错误率和 EAF 率确实超过 [`buildReleaseSummary`](../../backend/api/handler/kb/handler.go#L3922-L3933) 里 hardcode 的 3% / 15% 阈值，没问题就 `POST /api/admin/kb/release/rollback`，**全局 runtime override 切到 phase1，毫秒级生效**，所有新请求立刻走老策略。

**第二步：定位（10 分钟）**。回滚后从 `kb_retrieve_log` 拉故障窗口的日志，按 `strategy / release_stage / empty_reason / experiment_id` 几个维度分组，看到底是哪个 Flag 引起的——比如错误集中在 `empty_reason=empty_after_filter`，基本就是证据门禁过严；集中在 timeout，多半是模型改写延迟。

**第三步：精准修复（10 分钟）**。定位到具体 Flag 后，**不用全量回滚**，调 [`POST /api/admin/kb/strategy/flags/{flag_key}`](../../backend/api/handler/kb/handler_strategy.go#L53-L97) 只关那一个，比如把 `RAG_ENABLE_MODEL_ASSISTED_REWRITE` 切回 disabled。`phase3admin.UpdateFlag` 会走 reconfigure + 版本追加，留下完整操作记录。

**第四步：验证恢复（5 分钟）**。再调一次 release summary 确认 P95、错误率回到基线（[告警阈值](../../backend/deploy/monitoring/prometheus/rag-l8-alert-rules.yml) 里 P95 < 2s、错误率 < 3%、EAF < 15%）。指标稳定 5 分钟，飞书发故障恢复通告。

**关键设计**：release 回滚和 Flag 关闭是**两个独立路径**，可以先粗后细——先 release 把流量切回 phase1 把火灭了，再慢慢调 Flag 找根因，**避免一上来就在故障状态下做精细操作**。

> 相关代码：release summary 阈值在 [handler.go#L3920-L3940](../../backend/api/handler/kb/handler.go#L3920-L3940)，告警规则在 [rag-l8-alert-rules.yml](../../backend/deploy/monitoring/prometheus/rag-l8-alert-rules.yml)

### 🔍 深挖追问兜底

**Q：为什么不做自动回滚？**
> 回滚本身也是一次变更，深夜被自动回滚搞出二次事故的成本更高；告警规则虽然有 5~10 分钟窗口，但仍可能因依赖抖动、流量突刺误报。**目标是 30 分钟止损，不是 30 秒止损**，留 1-2 分钟给人确认很值得。

**Q：runtime override 多实例怎么生效？**
> 这是已知短板，目前 override 也只在被调用的实例内存里。生产上靠负载均衡的 hash 一致性 + 值班手动确保几个实例都调到。**未来打算把 override 也搬 Redis**，做一次写多实例 watch。

**Q：回滚后 `experiment_id` 还会继续标记吗？**
> 会，因为 release 回滚只动 strategy，不动实验状态机。所以排障完后还要手动调 [`experiment.Rollback`](../../backend/internal/rag/experiment/state.go#L172-L196) 把出问题的实验 status 改 stopped，否则 `BuildSummary` 还会在统计里把它当 running。

## 7. 关键参数：为什么 EAF 卡 15%、错误率卡 3%

**Q：你们 release summary 里 EAF（Empty-After-Filter）卡 15%、错误率卡 3%、P95 卡 2 秒，这几个数字怎么定的？**

**我的回答：**

都是**基线 + 业务忍受度**两步算出来的，不是拍脑袋。

**错误率 3%**：phase1 基线在 0.5%~1% 之间波动，phase2 引入了更多策略（改写、重排、证据门禁）后链路变长，正常波动也会到 1.5%~2%。**3% 留了大约 1.5 倍的 buffer**，超过这条线基本就是有真实回归，不是噪声。这个值写死在 [handler.go#L3925](../../backend/api/handler/kb/handler.go#L3925)。

**EAF 15%**：基线 EAF 大约 5%~8%，主要是用户问了知识库里真没有的问题。15% 意味着 EAF 至少翻倍——一定是新策略（证据门禁过严、改写跑偏导致检索不到原内容）的问题。15% 还有一层考虑是**用户体验拐点**：用户看到「找不到答案」的概率超过 1/6 就会觉得这个工具不好用。

**P95 2 秒**：来自用户调研——RAG 问答场景用户能忍受的最长等待是 3 秒，留 1 秒给 LLM 生成，检索环节就只能给 2 秒。Phase1 P95 基线在 800ms~1.2s 之间，2 秒等于 1.6~2.5 倍 buffer。重排再加 P95 800ms 是因为重排本身就是最耗时的环节，单独监控。

**这三个数字之间是 OR 关系**——任一超阈值就 `RollbackRecommended=true`，再加上 P95 rerank > 800ms 是 warning（不触发回滚建议但记 risk）。我们刻意不做组合规则，**单一指标超阈值就告警，规则越简单值班越能快速判断**。

> 相关代码：[buildReleaseSummary](../../backend/api/handler/kb/handler.go#L3834-L3946) 第 3925、3930、3934、3938 行四个阈值

### 🔍 深挖追问兜底

**Q：阈值写死在代码里不灵活，为什么不放配置？**
> 是个**有意的设计取舍**。阈值放配置会有人随手改，故障时改阈值「假装恢复」是真实风险。写死在代码里要改必须 PR review，多一层保护。如果将来真的需要按租户区分阈值，会按租户加配置覆盖层，但默认值依然在代码里 hardcode。

**Q：为什么用 P95 不用 P99？**
> P99 受单点慢请求影响太大，灰度只占 5%~20% 流量时样本量小、P99 波动剧烈不可读。**P95 在 1000 个样本里就能稳定**，更适合灰度场景。线上常规监控 P95/P99 都看，但灰度门禁只用 P95。

**Q：5 分钟窗口够稳定吗？会不会瞬时突刺误判？**
> 告警规则里错误率是 5 分钟窗口 + `for: 5m`，P95 是 10 分钟窗口 + `for: 10m`，**等于真正触发要持续 5/10 分钟以上**，瞬时突刺会被自动吃掉。release summary 默认窗口在 [`defaultReleaseSummaryMinutes`](../../backend/api/handler/kb/handler.go) 里更长，看的是趋势而不是点。
