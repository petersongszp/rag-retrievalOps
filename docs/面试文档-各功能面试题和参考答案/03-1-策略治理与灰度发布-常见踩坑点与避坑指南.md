# 策略治理与灰度发布 - 7 个最容易踩的坑与避坑指南

> 配套主文档：[03-策略治理与灰度发布-面试题和参考答案.md](./03-策略治理与灰度发布-面试题和参考答案.md)

---

## 前言

策略治理和灰度发布看着是「开个 Feature Flag、按比例放量」三件事，实际上每一步都能踩坑。最痛的是这些坑很多不会在测试环境出现——只有真正灰度到 20%、跑了几天之后才暴雷，而那时候已经影响了几万用户。

下面这 7 个坑，按踩中概率从高到低排序，全都来自本项目 `release / phase3admin / experiment / evaluation` 这几个模块的真实代码与设计取舍。

---

## 🕳️ 坑 1：随机数分桶导致用户策略反复横跳 → 用户骂街

### 问题描述
灰度档位从 5% 涨到 20% 期间，用户群里收到大量反馈：「同一个问题，刷新一下答案就不一样了」「答案质量像抽奖」。

### 踩坑过程
最开始做灰度分桶的普遍心态是「按比例放就行」，最直觉的实现就是 `if rand.Intn(100) < percent`，每次请求重新掷骰子。

技术决策上想着「反正用户量大，长期来看比例就是准的」，所以没特意考虑稳定性。本地测试也没问题，因为本地很少有人会反复刷同一个问题。

灰度到 5% 的时候没人发现，因为 95% 的请求都走 phase1，偶尔抽中 phase2 用户也不在意。**真正出问题是涨到 20% 的时候**——用户开始频繁遇到「这次给我引了 3 篇，下次又只有 1 篇」的体验抖动，QA 同学复现 bug 时也抓不住稳定状态。

最后是支持同学拿着一份用户反馈截图来追问「为什么这个用户上午看到的功能下午就没了」，才意识到分桶必须**用户维度稳定**，不能按请求维度随机。

> 详见主文档 [Q3](./03-策略治理与灰度发布-面试题和参考答案.md#3-渐进式灰度的分桶与决策)

### 后果
- 用户体验剧烈抖动，A/B 实验的统计学结论全部失真（因为每个用户都是混合样本）
- 客诉量在灰度期间涨了 **40%**，支持团队一度怀疑是策略本身有问题
- QA 复现 bug 时无法稳定触发，排障效率断崖式下跌

### 避坑方案
1. **永远用确定性哈希，不用随机数**：本项目用 `hash/fnv` 标准库 + `userID % 100`，逻辑写在 [`matchesStableBucket`](../../backend/internal/rag/release/controller.go#L233-L243)，10 行代码搞定
   ```go
   hasher := fnv.New32a()
   _, _ = hasher.Write([]byte(fmt.Sprintf("%d", userID)))
   return int(hasher.Sum32()%100) < percent
   ```
2. **分桶 key 选择要稳定**：用 `userID` 而不是 `requestID`、不是 `sessionID`、不是 IP——这些会随时间变
3. **匿名用户单独处理**：`userID=0` 时直接返回 false 走基线，避免一群匿名用户被随机塞进灰度
4. **只前进不后退原则**：扩流量没问题，**缩流量会导致部分用户被切回旧策略**，所以缩流量要么走 rollback 整体切回 phase1，要么干脆不缩

### 📚 延伸知识点
- **Sticky Bucketing**：A/B 实验领域的标准术语，专门指「用户在一次实验中始终落在同一组」的设计
- **Consistent Hashing**：在多实例/分片场景下做稳定分桶的进阶方案，节点变化时只挪一小部分 key
- **CUPED**（Controlled-experiment Using Pre-Existing Data）：Microsoft 提出的方差缩减方法，在分桶不绝对均匀时能显著提升实验灵敏度

### 面试时怎么说
> "在灰度分桶这块我们踩过一个挺典型的坑。最开始觉得按比例放量嘛，`rand.Intn(100) < 5` 就完事了，本地测也没毛病。
>
> 灰度到 5% 的时候没人发现，等涨到 20% 用户就炸了——反馈说同一个问题刷一下答案就变了。我们查了半天才意识到，**每次请求重新掷骰子，等于让每个用户都在两种策略之间反复横跳**，体验抖到不行。
>
> 后来改成 FNV 哈希 userID 取模 100，同一个用户在同一档位永远落在同一组。这件事让我意识到，**灰度的核心不是「分了多少流量」，而是「这部分流量是不是同一拨人」**。统计学要稳定，用户体验更要稳定。"

## 🕳️ 坑 2：热加载没做配置原子回滚 → 半生效状态最致命

### 问题描述
管理员在策略中心点了一下「开启模型辅助改写」，前端提示成功，结果一半请求走新策略一半走旧策略，监控指标完全没法解释。

### 踩坑过程
做 Feature Flag 热加载最容易的实现就是「改个全局 bool 变量」——`config.Global.RAG.FeatureFlags.EnableModelRewrite = true` 一行搞定。

最开始我们就是这么写的，本地单元测试也都过。问题在于这个 Flag 不是孤立的，它改完之后**底层的 `RetrieverService`、`Rewriter` 这些组件需要重建**——比如要重新连模型 API、要装载新的 prompt 模板、要刷一遍缓存。

后来上线后某次操作发现：Flag 改完之后部分组件初始化失败（模型 API key 配置漏了），但 `EnableModelRewrite` 这个 bool 已经被改成 true 了，结果 reconfigure 失败但 Flag 已生效——**前置判断走新分支，后置组件还是旧的**，请求大面积 500。

发现这个问题是因为告警炸了，但日志里看不出来哪个 Flag 引起的，因为状态本身已经不一致了。

### 后果
- 一次失败的 Flag 切换直接导致 phase2 错误率瞬间从 1% 飙到 30%
- 排障花了 **20 分钟**，因为「Flag 是 true 但行为像 false」根本不在 troubleshooting 预案里
- 团队对热加载机制信任度下降，后续好几次 Flag 变更都坚持要走重启

### 避坑方案
1. **配置变更必须原子化**：[`phase3admin.UpdateFlag`](../../backend/internal/rag/phase3admin/state.go#L122-L165) 的标准模式——先做 `snapshot := *cfg`，应用变更后调 `reconfigureManager`，失败立刻 `*cfg = snapshot` 回退
   ```go
   snapshot := *cfg
   cfg.RAG.FeatureFlags.SetPhase3StrategyFlag(flagKey, enabled)
   if err := reconfigureManager(ctx, cfg); err != nil {
       *cfg = snapshot   // 失败整体回退
       return FlagState{}, err
   }
   ```
2. **配置结构必须是浅拷贝安全的**：`RAGFeatureFlags` 强制只用 bool 字段，没有 map / slice，这样 `*cfg = snapshot` 才真的能完整还原
3. **写时持锁**：用 `sync.Mutex` 包住整个「校验+快照+应用+重建+追加版本」流程，**禁止把锁拆成多段**
4. **失败一定要把错误透传给前端**：让管理员看到「失败了，没生效」而不是「成功了，但行为奇怪」

### 📚 延伸知识点
- **Two-Phase Commit**：分布式事务的经典模式，热加载本质上是 in-process 的 2PC（准备 → 提交/回滚）
- **Copy-on-Write**：Linux 内存管理的思想，借鉴到配置热加载就是「永远操作 snapshot，成功才替换原值」
- **Etcd Watch**：分布式配置中心标配，每次配置变更带 revision 号，订阅方按 revision 单调推进，天然原子

### 面试时怎么说
> "Feature Flag 热加载这块我们踩过一次教训。最开始想得很简单，就一个全局 bool 变量改一下嘛。
>
> 结果有一次 Flag 改完，底层组件重建失败了（模型 API key 没配对），但 bool 已经是 true 了。前置判断走新分支去调模型，后置的客户端还是空的，**Flag 是 true 但行为像 false**，错误率瞬间炸了 30%。最坑的是排障 20 分钟才反应过来——「半生效」这种状态根本不在我们的预案里。
>
> 后来重构成标准的 snapshot → apply → reconfigure → 失败回滚的原子流程，每次变更要么全成要么完全没变。这件事让我意识到，**热加载最大的风险不是慢，而是中间态——半生效比完全失败可怕一百倍，因为它会让你失去对系统状态的判断力**。"

## 🕳️ 坑 3：质量门禁阈值不绝对 → 候选策略蒙混过关

### 问题描述
某次新 rewrite 策略号称「ndcg 提升 0.005」通过了门禁，灰度上线后线上召回明显下降，回查才发现是评测集刚好有几条 case 对它友好，统计上根本不显著。

### 踩坑过程
最开始定门禁阈值的时候，大家的默认想法是「不退步就行」——`MinNDCGDelta = 0`、`MinMRRDelta = 0`，候选只要比基线不差就放过。

技术上看起来很合理：基线已经经过了上一轮门禁，新策略只要不回归就是「至少没变坏」。门禁里这条 check 长这样：
```go
{Name: "ndcg_delta", Expected: 0, Passed: comparison.NDCGDelta >= 0}
```

实际操作下，**只要候选 ndcg 比基线高 0.0001 都算 pass**。问题是评测集有几百个 case，单 case 波动本来就大，0.0001 这种差异完全可能是噪声。结果是连续几次候选策略「侥幸通过」，灰度上去之后线上指标反而不如基线。

后来回头看 EvalRun 报告才发现，这些 pass 掉的策略其实在某几个 query type 上是显著退步的，只是被另几个 type 的提升均摊掉了。

### 后果
- 至少有 3 次「门禁通过但线上回归」的事件，每次都要紧急回滚
- 评测集的公信力被质疑，团队开始重新评估门禁的有效性
- 业务方对「门禁通过」这个 signal 不再信任，每次上线都要求额外人工 review

### 避坑方案
1. **核心指标卡绝对提升，不卡「不退步」**：[`DefaultGateThresholds`](../../backend/internal/milvus/evaluation/gate.go#L5-L18) 里 `MinRecallDelta = 0.08`，意思是召回必须提 8 个点才算有意义
2. **一票否决，不做加权投票**：`EvaluateGate` 里只要任一 check.Passed=false 就整体 fail，**禁止「3 项过 5 项不过算 60 分」这种打分制**——会有人扯皮
3. **评测集分层**：冻结基线集（保 KPI 可比）+ 滚动 bad case 集（补长尾），新策略两个集都要过
4. **条件触发的门禁单独跑**：模型改写默认 shadow 模式，shadow 阶段 [`MinRewriteGainDelta`](../../backend/internal/milvus/evaluation/gate.go#L80) 这条 check 不开；只有要放量时才打开，避免「shadow 阶段反正不影响线上」就降低门禁
5. **样本量门槛**：候选评测集少于 100 条直接 fail，避免「30 条 case 算个 delta 就发车」

### 📚 延伸知识点
- **Statistical Significance Testing**：A/B 实验里的 p-value、置信区间，绝对值 delta 不显著时再大的提升也是噪声
- **Bonferroni Correction**：多重比较修正——同时跑 8 个门禁 check 时，单项的显著性阈值要按 8 倍收紧
- **Champion-Challenger**：信用风控领域的术语，新模型（challenger）必须显著优于旧模型（champion）才能上线
- **Online vs Offline Evaluation Gap**：经典话题，离线指标提升≠线上效果，门禁只是必要非充分条件

### 面试时怎么说
> "评测门禁这块我们也吃过亏。最开始定阈值的逻辑是「不退步就放过」，听起来很合理对吧——基线已经验过了，新策略不比它差就行。
>
> 结果连续踩雷三次：评测报告显示 ndcg 提了 0.0001，门禁过了，灰度上去线上召回反而掉。回头看才发现，**0.0001 这种 delta 在几百条评测集里就是噪声，等于在门禁阈值上裸奔**。
>
> 后来我们把核心指标 recall 直接卡 +0.08 的绝对提升，再加一票否决——任一项不过整体不过。这件事让我意识到，**门禁的价值不在「卡住坏的」，而在「逼策略证明自己真的好」。容忍 0 退步等于容忍噪声，门禁就形同虚设了。**"

## 🕳️ 坑 4：多实例部署 Flag/Override 状态不同步 → 灰度精度失控

### 问题描述
线上 3 个副本，管理员调一次回滚接口提示成功，结果监控显示只有 1/3 的请求切回了 phase1，剩下 2/3 还在跑新策略。

### 踩坑过程
最开始本地开发和测试环境都是单实例，`release.RuntimeOverride` 和 `phase3admin.flagStates` 都是 **进程内 sync 锁保护的全局变量**——`var runtimeOverride RuntimeOverride` 就这么放在 [controller.go](../../backend/internal/rag/release/controller.go#L39-L42)。

技术决策上没特别考虑跨实例，理由是「这是管理面操作，频率很低，先用最简单的方案」。本地、staging、单实例 demo 一切正常。

到了生产环境部署 3 个副本之后才暴露——管理员调 `POST /api/admin/kb/release/rollback`，负载均衡随机路由到一个 pod，那个 pod 内存里的 override 改了，**另外两个 pod 完全不知情**。前端调一次 `GET /release/status` 又随机命中另一台，看到的还是没回滚的状态，管理员一头雾水以为接口没生效。

更糟的是：灰度比例的精度也失控。理论上 5% 哈希应该精确分桶，但 3 个实例的 Flag 状态可能各自不一致，实际全局灰度比例变得像「薛定谔的灰度」。

### 后果
- 一次紧急回滚耗时多花了 **8 分钟**——发现状态不一致后只能轮询所有 pod 重试
- 灰度比例失真，无法证明「5% 灰度」就是真的 5%，业务方对监控失去信任
- 这个坑已经在文档里标注为「**已知缺陷，未来优化**」，目前靠运维「连续多次调接口直到所有 pod 都命中」绕过

### 避坑方案
1. **诚实承认现状，文档显著标注**：本项目主文档 Q5 和 Q6 都明确写了「目前没做跨实例同步」，不掩盖
2. **临时绕过：让接口幂等 + 客户端轮询**：管理后台连续调 N 次（N > 实例数 × 2），靠概率覆盖所有实例
3. **根治方案是把状态搬到外部 KV**：未来计划用 Redis + pub/sub 或 etcd watch，所有实例订阅同一个 channel，**Flag 变更走配置中心而不是进程内存**
4. **配置中心 watch 用 revision 单调推进**：避免「老版本配置覆盖新版本」的回滚冲突
5. **加 meta-monitoring**：监控各 pod 上报的 Flag 当前状态，如果 N 个 pod 上报的状态不一致就告警，**让不同步可见**

### 📚 延伸知识点
- **Configuration Drift**：业内对「多实例配置不一致」的标准命名，K8s ConfigMap 滚动更新也有这个问题
- **etcd Watch / Apollo / Nacos**：成熟的分布式配置中心，原生支持多实例订阅+原子推送
- **Raft / Paxos**：配置中心一致性的底层算法，关键是「写多数派成功才算成功」
- **Meta-monitoring**：监控监控系统本身的健康度，这里的延伸是「监控配置一致性」

### 面试时怎么说
> "这是我们项目目前还没完全解决的一个坑，我老实说——多实例部署下 Feature Flag 状态不同步。
>
> 最开始 override 和 Flag 状态都是进程内全局变量加 sync 锁，单实例跑得很好。上生产部署 3 个副本之后才发现，管理员调一次回滚接口，负载均衡随机路由到一台，另外两台压根不知情。最严重的一次紧急回滚多花了 8 分钟，因为得反复调接口确认全部生效。
>
> 我们的应对分三步：现在靠**客户端轮询调多次**绕过；中期把 override 状态搬到 Redis 做 pub/sub；终极方案是接 etcd 这种配置中心做 watch。这件事让我意识到，**单实例跑通的方案，在多实例下可能完全是另一个问题——分布式不是把单机功能复制 N 份，而是要重新设计状态边界**。"

## 🕳️ 坑 5：回滚链路漏挂实验状态 → 数据被持续污染

### 问题描述
线上紧急回滚到 phase1 之后，团队以为没事了，结果第二天发现实验报表里那个出问题的 candidate 组「样本数还在涨」——回滚根本没停掉实验。

### 踩坑过程
最开始设计回滚是「一键切 phase1」的极简思路：调 `release.SetRuntimeOverride(phase1)`，全局策略切回基线，搞定。

技术上看起来没问题，因为所有新请求都被 `release.Decide` 拦截走 phase1 了。监控也确实在 5 分钟内恢复正常。

**但被忽略的是 `experiment` 模块是独立状态机**——实验记录的 `Status = running` 完全独立于 release stage。`release.Decide` 决定的是 strategy（phase1/phase2），`experiment.Decide` 决定的是组（baseline/candidate/shadow），两者解耦的好处是互不影响，**坏处是回滚 release 不会顺便停实验**。

发现是因为周一早会复盘上周事故，团队 leader 问「那个 candidate 组的样本怎么还在增长」——原来 release 虽然回滚了，但 `experiment.Decide` 还会继续根据 `traffic_ratio` 给请求打 candidate 标签，写到 `KBRetrieveLog.experiment_id` 里，[`BuildSummary`](../../backend/internal/rag/experiment/state.go#L226-L239) 还在持续把它当 running 统计。

> 详见主文档 [Q1](./03-策略治理与灰度发布-面试题和参考答案.md#1-整体架构策略治理--灰度发布是怎么分层的) 关于三层解耦的设计取舍

### 后果
- 实验报表被污染：故障期间的脏数据混入了实验结论，后续策略决策都基于这份脏数据
- 排障复盘时需要额外手动清洗 `experiment_id` 字段，多花了 3-4 小时
- 业务方对「回滚」的定义产生分歧——「回滚到底回了什么、没回什么」需要重新写文档明确边界

### 避坑方案
1. **回滚走 checklist 而不是单接口**：明确「release rollback」只切策略，**实验、Flag、index switch 都要分别处理**
2. **实验有独立的 stop 接口**：[`experiment.Rollback`](../../backend/internal/rag/experiment/state.go#L172-L196) 单独提供，把 status 改 stopped 并把 traffic_ratio 清零
3. **告警关联回滚动作**：当 release rollback 触发后，自动给值班一个「相关实验是否需要停？」的二次确认弹窗
4. **`BuildSummary` 加状态过滤**：报表层默认排除已 stopped 实验，**避免 stop 不及时直接污染历史数据**
5. **解耦不等于断联**：架构上保持模块解耦，但**运维流程上要有 checklist 串起来**，工程纪律补设计妥协

### 📚 延伸知识点
- **Saga Pattern**：分布式事务的补偿模式，每个步骤都有对应的回滚动作，本质就是回滚 checklist
- **Idempotent Rollback**：回滚操作必须幂等，重复调用结果一致——避免「以为没回成功又调一次」反而出问题
- **Blast Radius**：事故影响半径，回滚做不彻底 = 半径未真正收敛 = 事故没真正结束

### 面试时怎么说
> "回滚这件事我们也踩过个坑，挺隐蔽的。
>
> 最开始我们设计回滚就是「一键切 phase1」，5 分钟内监控恢复正常，大家就散了。结果周一早会复盘，leader 问那个出问题的 candidate 组样本数怎么还在涨——原来 release 和 experiment 是两套状态机，**release 回滚了，实验还在跑，污染了一周报表**。
>
> 后来我们把回滚做成 checklist 形式：release stage、相关实验、相关 Flag、index switch 状态四件事必须挨个确认。这件事让我意识到，**「解耦」是给开发用的，「回滚」是给故障用的——架构可以解耦，但运维流程必须用 checklist 把它们串回来。**否则就是「每个模块都很干净，但整个系统在事故时一团糟」。"

## 🕳️ 坑 6：高风险 Flag 直接从 disabled 切 enabled → 跳过 shadow 验证

### 问题描述
有一次值班为了赶上线时间，把 `RAG_ENABLE_MODEL_ASSISTED_REWRITE` 从 disabled 直接切 enabled，结果模型改写的延迟问题瞬间冲击全量用户。

### 踩坑过程
模型辅助改写是我们风险最高的 Flag——会调外部 LLM，延迟和稳定性都是不可控因素。**标准流程应该是 disabled → shadow（影子流量，只采样不用结果） → canary（小流量真实生效） → enabled（全量）**。

最开始为了「灵活」，UI 上做了一个状态下拉框，让管理员可以自由切换 `enabled / disabled / shadow / canary`。规则文档写了「高风险 Flag 必须走 shadow→canary→enabled」，但没在代码里硬卡。

有一次某位同学晚上值班赶发车，看到「shadow 跑了一周稳定了」就觉得「直接 enabled 应该也没问题吧」，跳过 canary 直接切 enabled。模型 API 那天恰好抖动，P95 直接从 800ms 飙到 4 秒，整个 RAG 链路被拖垮。

事后追责的时候大家都很尴尬——文档明明写了流程，但**没人能 100% 时时刻刻记住所有 Flag 的特殊规则**，尤其是夜里赶上线的时候。

### 后果
- 一次跳过 canary 的切换直接导致 P95 翻 5 倍，影响范围覆盖全量用户
- 团队意识到「文档约束」在压力下完全靠不住
- 必须改成代码层硬约束才能根本解决

### 避坑方案
1. **代码层硬约束**：[`phase3admin.UpdateFlag` 第 143 行](../../backend/internal/rag/phase3admin/state.go#L143-L145) 显式拦截
   ```go
   if isHighRiskFlag(flagKey) && !current.Enabled && enabled && status != shadow && status != canary {
       return FlagState{}, fmt.Errorf("high-risk flag %s must be enabled through shadow or canary first", flagKey)
   }
   ```
2. **高风险 Flag 名单显式维护**：[`isHighRiskFlag`](../../backend/internal/rag/phase3admin/state.go#L493-L495) 函数里硬编码，添加新 Flag 时强制评审是否要进名单
3. **`reason` 必填**：每次 UpdateFlag 强制要 reason，防止「随手点」操作，事后审计能查到「为什么改」
4. **审计事件必须落库**：[`handler_strategy.go`](../../backend/api/handler/kb/handler_strategy.go#L84-L94) 写 `KBAuditEvent`，操作人、时间、reason、前后状态全部留痕
5. **UI 同步禁用违规选项**：disabled 状态下的高风险 Flag，前端直接灰掉 enabled 选项，从交互上断绝

### 📚 延伸知识点
- **Progressive Delivery**：业界对「渐进式发布」的标准命名，shadow → canary → blue-green → full 是标准链路
- **Shadow Traffic / Dark Launch**：影子流量做法的术语，Facebook、Netflix 都有大量实践
- **Policy as Code**：用代码实现治理规则（OPA、Sentinel），替代「文档约束」
- **Guardrail**：SRE 术语，指「让人无法做错事」的护栏机制，区别于「靠人做对事」的流程

### 面试时怎么说
> "有个挺血泪的事故跟 Flag 治理有关。
>
> 我们有个 Flag 是模型辅助改写，最高风险——会调外部 LLM。流程文档写得很清楚，必须 disabled → shadow → canary → enabled 一步一步走。某天晚上值班同学赶发车，shadow 跑了一周很稳，他就想「直接 enabled 也行吧」，跳过了 canary。结果那天模型 API 抖动，P95 从 800ms 飙到 4 秒，全量被拖垮。
>
> 后来我们做了一个最朴素也最有效的改动：在 `UpdateFlag` 函数里硬编码一行 `if isHighRiskFlag && 从 disabled 直跳 enabled，拒绝`。文档约束完全靠不住，**代码约束才靠得住**。
>
> 这件事让我意识到一个原则：**重要的规则一定要做成 Guardrail（护栏），而不是 Process（流程）**。流程靠人记，会出错；护栏靠代码，从设计上让人无法做错。"

## 🕳️ 坑 7：门禁阈值放配置 → 故障时被人「调阈值假装恢复」

### 问题描述
某次大促前压测，P95 阈值从配置里被偷偷调高了一档，结果上线后真出问题，监控以为还在 SLA 内，错过黄金处置时间。

### 踩坑过程
做 release summary 阈值的时候，团队对「阈值放配置还是写死在代码」吵了很久。

普遍的工程直觉是「放配置才灵活」——不同环境、不同租户、不同时段可能要用不同阈值，配置化听起来很专业。最开始的设计也确实是把 `errorRate=0.03`、`p95=2000ms`、`emptyAfterFilter=0.15` 都放进 `config.yaml`。

上线一段时间后逐渐发现一个隐性问题：**故障时有人会「修阈值代替修问题」**。最典型的一次是大促前压测发现 P95 超过 2s 持续触发告警，某位同学为了「让告警安静下来好继续压测」，把阈值临时调到 3s，**调完忘了改回来**。后来大促真出问题，监控显示一切正常，错过了 5 分钟的黄金处置窗口。

类似事件出现两次之后，团队决定**把阈值锁死在代码里**——[handler.go#L3925](../../backend/api/handler/kb/handler.go#L3925) 的 `0.03` 就是从那次事故之后 hardcode 的，要改必须发 PR 走 review。

### 后果
- 故障期间监控失真，黄金处置时间被浪费 5+ 分钟
- 后续每次 SRE 评审都要花时间检查「最近有没有人偷改阈值」
- 配置文件的可信度下降，团队对「配置项」整体变得疑神疑鬼

### 避坑方案
1. **核心阈值 hardcode 在代码**：本项目 [`buildReleaseSummary`](../../backend/api/handler/kb/handler.go#L3920-L3940) 里的 4 个核心阈值全部 hardcode，要改必须 PR
2. **PR review 是天然的 audit**：阈值变更走 git 记录，谁改、什么时候改、为什么改一目了然
3. **如果一定要配置化，加变更告警**：阈值变更事件单独发飞书告警 + 飞书审批，**让「偷偷调阈值」不可能**
4. **区分「调参」和「调阈值」**：业务参数可以配置化，**告警/门禁阈值属于元监控范畴，应该是「准代码」级别的稳定性**
5. **故障期间配置 freeze**：发生 P1 故障时，配置中心强制只读，避免有人在事故现场临时改东西

### 📚 延伸知识点
- **Configuration as Code**：配置也是代码的一部分，必须走版本控制、PR review、自动化测试
- **Goodhart's Law**：「当一个指标变成目标，它就不再是好指标」——可配置阈值容易被「优化」成「不报警的阈值」
- **Change Freeze Window**：大促/重要节点的变更冻结，配置变更也属于变更范畴
- **Meta-monitoring**：监控监控系统自己的健康度，阈值被偷改也算监控系统失效

### 面试时怎么说
> "我们在阈值配置化这件事上有个反直觉的决定。
>
> 最开始大家都觉得阈值应该放配置，理由很硬——不同环境、不同租户、不同时段都可能要调，写死在代码里多死板。所以一开始 release summary 的几个阈值都是配置化的。
>
> 结果出过两次事故都是同一个套路：故障前夕有人为了「让告警安静下来」临时调高阈值，调完忘了改回来。真出问题的时候监控显示一切正常，等到反应过来已经晚了。
>
> 后来我们就把核心阈值都写死在代码里，要改必须发 PR 走 review。听起来挺反工程直觉的，但**阈值这东西不属于「业务配置」，属于「监控系统的元配置」，应该和代码同等稳定性**。
>
> 这件事让我学到一个原则：**给系统一点「不灵活」的反而更安全——可配置的另一面是「可被误改」**。"
