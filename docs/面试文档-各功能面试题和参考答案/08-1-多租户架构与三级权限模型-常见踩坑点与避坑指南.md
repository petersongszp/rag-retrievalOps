# 多租户架构与三级权限模型 - 7 个最容易踩的坑与避坑指南

---

## 前言

"多租户嘛，加个 `tenant_id` 字段、查询时带上就行" —— 这是几乎所有第一次做多租户的人的心态。但只要你真把租户、知识库、API Key 三级权限串起来跑过一年，就会知道：行级隔离的每一处漏写、JWT 与 API Key 的语义混淆、配额计数的时区错位、模块边界的悄悄渗透，每一项都可能让你深夜被叫起来排障。

下面这 7 个坑按踩中概率从高到低排，配合主文档 [08-多租户架构与三级权限模型-面试题和参考答案.md](./08-多租户架构与三级权限模型-面试题和参考答案.md) 食用更佳。

---

## 🕳️ 坑 1：Repository 层漏带 `tenant_id` → 跨租户数据泄漏

### 问题描述
新加了一个统计接口或后台导出接口，handler 层校验都做了，但 Repository 直接 `db.Find(&list)`，结果一查就是全平台所有租户的数据。

### 踩坑过程
最开始我们的纪律是「每个 Repository 方法都要带 `tenantID` 参数」。前几个月写的 [kb_tenant_repo.go](../../backend/internal/repository/kb_tenant_repo.go) 也都老老实实这么干。

后来项目演进，新人接手加了一个「平台总用量统计」需求，他想着"反正只是给运营看的，先把数据查出来再说"，写了个 `db.Model(&KBKnowledgeBase{}).Find(&list)`，handler 那一层做了 `RequireRole("admin")` 卡角色，自以为没问题。

**问题在于**：这个接口被前端复用到了普通用户的"我的知识库"页面，前端发请求时角色判定走的是 JWT，但接口本身没强制 `tenant_id` 过滤。结果一个普通用户在某次接口联调中，意外看到了别租户的 KB 列表。

发现是用户在 QQ 群截图问"这些 KB 是干嘛的，怎么不是我建的"。我们当时心里咯噔一下。

### 后果
- 跨租户信息泄漏，**租户信任度直接清零**——一次泄漏比 100 次稳定运行更刻骨铭心
- 紧急回滚 + 全量审计 [kb_retrieve_log](../../backend/internal/model/kb_retrieve_log.go)，整整两天没干别的
- 团队 Code Review 流程被加进一道"必须搜 `Find\|First` 是否带 `tenant_id`"的硬规则

### 避坑方案
1. **类型签名硬约束**：Repository 方法签名直接要求 `tenantID uint64` 必传，参考 [GetByIDForTenant](../../backend/internal/repository/kb_tenant_repo.go#L29-L33)、[CountByTenant](../../backend/internal/repository/kb_tenant_repo.go#L62-L66)。**漏传编译都过不了**，比口头约束强 100 倍。

2. **CI 跑隔离回归**：[isolation_test.go](../../backend/api/handler/kb/isolation_test.go) 这种构造租户 A/B 跨读测试必须是 CI 必跑项，新接口加进来必须配套加用例。

3. **Grep 巡检脚本**：每周跑一次 `Grep "db\.(Find|First|Where).*&model\." | grep -v "tenant_id"`，把可疑代码拉出来人工 review。

4. **审计日志自检**：[kb_audit_event](../../backend/internal/model/kb_audit_event.go) 里 `tenant_id` 是必填，**埋点时如果 tenant_id 为 0 直接 panic**（dev 环境），强迫开发者在源头补全。

> 详见主文档 [Q6：线上突然有人投诉看到别租户知识库](./08-多租户架构与三级权限模型-面试题和参考答案.md#q6线上突然有用户投诉自己看到了别租户的知识库列表你怎么排)

### 📚 延伸知识点
- **Row-Level Security (RLS)**：PostgreSQL 原生支持，可以在数据库层面强制每行查询都带租户过滤，比应用层兜底更可靠。MySQL 没有，所以只能靠应用纪律
- **GORM Scopes**：可以注册全局 Scope 自动给所有查询加 `tenant_id`，但有反例——后台跨租户聚合时容易忘了 `Unscoped()`，反而出 Bug
- **Aspect-Oriented 拦截器**：Java 圈用 AOP 在 Mapper 层自动注入 `tenant_id`，Go 圈通常用 GORM 插件实现类似效果

### 面试时怎么说
> "在多租户隔离这块我们踩过一个特别典型的坑。最开始我们的纪律是 Repository 都带 `tenantID` 参数，前几个月写得挺好。
>
> 后来一个新人加了个统计接口，handler 层只卡了 admin 角色，Repository 那层直接 `db.Find` 全表查。结果接口被前端复用到普通用户页面，一个用户截图发群里问'这些 KB 是谁的'，我们才发现跨租户泄漏了。
>
> 后来我们做了几件事：Repository 方法签名硬要求 `tenantID` 必传，漏传编译就过不了；CI 加了一套租户 A/B 隔离回归用例；每周 Grep 巡检可疑 SQL。这件事让我意识到：**多租户隔离不是靠纪律，是靠工具把'漏写'这种可能性从源头消灭**。"

## 🕳️ 坑 2：JWT 里塞 `tenant_id` 但请求体也允许传 → 越权一行代码

### 问题描述
JWT 签发的时候 claims 里有 `tenant_id`，但 handler 为了"灵活性"也接受请求体里传 `tenant_id`，前端写错了一个字段直接跨租户。

### 踩坑过程
最开始普遍的心态是"既然 JWT 里有 `tenant_id`，请求体里再传一个也没什么坏处，前端不传就用 JWT 里的，传了就用传的"——这种"双保险"看起来挺稳。

我们最早一版 `/v1/retrieve` 就是这么写的。某次前端联调，把 `tenant_id` 这个字段写错了类型——本来该是 0（让后端从 JWT 取），但前端拿了一个 UI 上的下拉值塞进去。这个值恰好是别租户的真实 ID。

**线上跑了三天**，每天都有零星的"跨租户访问"请求，因为攻击者只要把请求体里的 `tenant_id` 改成任意数字就能绕过。我们是看 [kb_retrieve_log](../../backend/internal/model/kb_retrieve_log.go) 时发现一个 user_id 居然查了几十个不同租户，才意识到出大事了。

### 后果
- 三天的 `/v1/retrieve` 请求全部存在越权风险，需要逐条审计
- Phase 3 隔离合约被迫紧急冻结：**`tenant_id` 永远只从凭证反查，请求体禁止覆盖**（[phase3-l0-isolation-contract.md#L10-L17](../../backend/docs/zhuhu/phase3-l0-isolation-contract.md#L10-L17)）
- 老接口大量改造，赶在版本灰度前补完

### 避坑方案
1. **凭证是唯一信任源**：看 [retrieve.go#L242-L286](../../backend/api/handler/rag/retrieve.go#L242-L286) 的 switch-case，三种身份（API Key/JWT/legacy）的 `identity.TenantID` 全部从凭证反查，**请求体里有 `tenant_id` 字段也忽略**。

2. **结构体里干脆不放 `tenant_id`**：看 [RAGRetrieveRequest](../../backend/api/handler/rag/retrieve.go#L20-L28) 字段定义，根本没有 `tenant_id`——**字段不存在就没人能传**，这是最干净的封堵。

3. **统一从 ctx 取**：所有 handler 必须用 [getCurrentTenantID(c)](../../backend/api/handler/kb/handler.go#L2118-L2147)，禁止直接 `c.Query("tenant_id")` 或 `req.TenantID`。

4. **代码 Review 红线**：PR 里只要出现"`req.TenantID`""`c.Param("tenant_id")`"立即打回，不接受任何理由。

### 📚 延伸知识点
- **Confused Deputy 问题**：经典安全反模式——服务自身有权限，但被欺骗去为攻击者执行操作。多租户场景下，"信任客户端传的 `tenant_id`"就是这个反模式的典型
- **JWT 不可变 claims**：JWT 一旦签发就不可修改，把 `tenant_id` 放进 claims 等于让租户归属"绑定到凭证"，比放请求体安全得多
- **mTLS + SPIFFE**：服务间通信用证书带身份的方案，证书里嵌入 spiffe ID，调用方根本无法伪造身份

### 面试时怎么说
> "权限模型这块我们踩过一个挺隐蔽的坑。最开始我们的设计是 JWT 里有 `tenant_id`，请求体里也允许传——觉得双保险嘛，前端不传就用 JWT 的。
>
> 结果某次前端联调把字段写错了，传成了别租户的 ID。线上跑了三天才在 retrieve_log 里发现一个 user_id 跑了几十个租户的 KB，吓出冷汗。
>
> 后来我们把规则定死：**`tenant_id` 永远只从凭证反查，请求体里这个字段直接从结构体里删掉**。这件事让我明白：**安全设计的第一原则不是'多一道保险'，是'减少一种可能性'——能不让客户端传的东西，就根本不要在协议里暴露**。"

## 🕳️ 坑 3：API Key 明文存库 + 长期不轮换 → 一次拖库全军覆没

### 问题描述
为了调试方便，最早一版 API Key 是明文存进 `rag_api_key.key` 字段的，结果某次 DB 备份不小心外泄，所有租户被迫紧急轮换。

### 踩坑过程
最开始做 API Key 的时候，普遍心态是"这又不是密码，明文存有什么关系，调试方便"。库表里直接一个 `key VARCHAR(255)` 字段，admin 后台还能直接展示出来给用户看。

跑了几个月没事。直到某次开发同学把测试环境备份 `.sql` 文件传到了不该传的地方，被人扒了出来——**所有 API Key 明文一览无遗**。

更糟的是，没有轮换机制。客户接入 SDK 时把 Key 写死在配置文件里，让用户立即换 Key 等于让他们重新部署。最后我们花了一周时间一对一通知，分批吊销旧 Key、签发新 Key。

### 后果
- 全平台 API Key 紧急轮换，运维同学连续加了 3 天班
- 部分客户因为旧 Key 还在用、新 Key 没换上，Agent 服务出现间歇性 401
- 安全合规审计直接红线，被迫补一份完整的密钥管理流程

### 避坑方案
1. **只存哈希，明文一次性返回**：看 [GenerateAPIKey](../../backend/internal/auth/apikey.go#L20-L38)：明文 `key`、SHA256 `keyHash`、展示用 `keyPrefix` 三个值——库里只存 hash 和 prefix，**明文创建时返回一次给用户，之后任何人（包括 DBA）都看不到原文**。

2. **校验走哈希比对**：[APIKeyAuth](../../backend/internal/middleware/auth.go#L164-L173) 里先 `HashAPIKey(token)` 再查 `key_hash` 字段，**库里完全不知道明文长什么样**。

3. **支持轮换 + 双 Key 并存**：参考 [RotateAPIKeyResponse](../../backend/internal/auth/contract.go#L66-L71) 的 rotate 接口设计，旧 Key 标 `revoked` 但不立即生效，给用户 24 小时切换窗口。

4. **加过期机制**：`expires_at` 字段必填（[rag_api_key.go#L17](../../backend/internal/model/rag_api_key.go#L17)），强制用户每 90 天轮换一次，**业内通病是"长期 Key 永不过期"，等于把炸药埋家里**。

5. **last_used_at 巡检**：[UpdateLastUsed](../../backend/internal/middleware/auth.go#L198) 每次校验都更新，配合定期脚本扫"30 天没用过的 Key 自动 revoke"，减少存量风险。

### 📚 延伸知识点
- **HMAC-SHA256 vs Bcrypt**：API Key 校验是高频操作，用 SHA256 一次哈希就行；密码登录低频，要用 bcrypt/argon2 慢哈希抗暴力破解。**两者不能混用**
- **HashiCorp Vault / AWS Secrets Manager**：企业级密钥托管方案，支持自动轮换、动态租约，业界标准
- **Key Rolling**：双 Key 并存的轮换模式，避免发版瞬间所有客户端 401

### 面试时怎么说
> "API Key 这块我们踩过一个挺惨的坑。最早一版 Key 是明文存库的，admin 后台还能直接看——觉得调试方便嘛。
>
> 结果一次测试环境的 SQL 备份外泄了，所有 Key 一览无遗。客户那边 Key 写死在配置里，没法瞬间换，我们花了整整一周一对一通知客户轮换。
>
> 现在我们只存 SHA256 哈希，明文 Key 创建时只返回一次，之后任何人都看不到原文了；rotate 接口支持双 Key 并存 24 小时，给客户切换窗口。这件事让我明白：**安全设计的核心不是'防住 100% 的攻击'，是'攻破后让损失可控'——明文存就是把所有租户的命运绑在一个备份文件上**。"

## 🕳️ 坑 4：配额计数走 SQL 实时 COUNT → DB 被打爆

### 问题描述
最早 `MaxAPICallsPerDay` 配额校验是每次请求 `SELECT COUNT(*) FROM kb_retrieve_log WHERE tenant_id=? AND DATE(created_at)=CURDATE()`，结果 QPS 一上来 DB CPU 直接 100%。

### 踩坑过程
最开始做配额的时候，普遍心态是"现成有 `kb_retrieve_log` 表，每次 COUNT 一下就行，干嘛多搞个 Redis"。代码上线时 QPS 几十，看着挺正常。

后来某个客户的 Agent 接入跑批量任务，瞬时 QPS 拉到 300。每个请求进来都 `COUNT(*)`——**这是个全表扫描配 `DATE()` 函数走不了索引的 SQL**。DB CPU 瞬间冲到 100%，所有租户的请求全部排队，配额没拦住反而把整个平台干瘫了。

发现是 DBA 在群里 @我："你们这个查询是不是写错了，慢查询日志全是它"。

### 后果
- DB CPU 100%，整个平台 API 全部慢成蜗牛
- 真正配额超限的租户没拦住——因为 COUNT 太慢，请求都打进检索链路了
- 紧急回滚配额检查，**线上裸奔了两天没有任何配额拦截**

### 避坑方案
1. **Redis 计数器 + Lua 原子化**：现在的实现是 [counter.go#L14-L44](../../backend/internal/quota/counter.go#L14-L44)，`INCR + EXPIRE` 一条 Lua 脚本搞定，单次 0.1ms 内：
   ```lua
   local k = KEYS[1]
   local ttl = tonumber(ARGV[1])
   local c = redis.call('INCR', k)
   if c == 1 and ttl > 0 then
     redis.call('EXPIRE', k, ttl)
   end
   return c
   ```

2. **Key 按 UTC 日期切**：看 [apiCallCounterKey](../../backend/internal/quota/counter.go#L70-L72) 是 `quota:api_calls:{tenantID}:{date}`，第二天自然过期，不需要任何清理任务。

3. **降级策略写死**：[counter.go#L31-L33](../../backend/internal/quota/counter.go#L31-L33) Redis client 为空就 `return 0` 放行——**配额是软约束，Redis 抖动时宁可漏放也不能阻塞业务**。

4. **静态查询的配额走 SQL，动态计数走 Redis**：KB 数量、文档数量这种低频写、需要精确计数的，[quota.go](../../backend/internal/quota/quota.go) 用 SQL Count；调用次数这种高频累加用 Redis。**两套机制各司其职**。

### 📚 延伸知识点
- **Redis Cluster 与原子性**：Lua 脚本里多个 Key 要在同一 slot，否则在 Cluster 模式下报 CROSSSLOT。我们这里只有一个 Key，天然安全
- **Sliding Window Log**：滑动窗口限流的精确算法，但内存开销大；我们用的是固定窗口 INCR，简单粗暴但够用
- **Token Bucket / Leaky Bucket**：更平滑的限流算法，适合做秒级限流；日级配额用 INCR + EXPIRE 就够

### 面试时怎么说
> "配额这块我们踩过一个性能坑。最开始觉得 `kb_retrieve_log` 表都有了，每次请求 `COUNT` 一下不就行了，省得多引一个组件。
>
> 结果某客户跑批量任务把 QPS 拉到 300，每次请求都触发一次 `COUNT(*)` 配上 `DATE()` 函数走不了索引，DB CPU 瞬间打满，整个平台全慢了——讽刺的是配额都没拦住，反而把自己玩坏了。
>
> 后来改成 Redis Lua 脚本 `INCR + EXPIRE`，Key 按 UTC 日期切自动过期，单次 0.1ms。Redis 挂了直接放行，因为配额是软约束不是安全边界。这件事让我意识到：**做计数类功能，永远要分清'高频小数'和'低频大数'，前者必须走 Redis，后者才能用 SQL**。"

## 🕳️ 坑 5：legacy `app_id` 路径没映射租户 → 隔离链路出现"无 tenant" 黑洞

### 问题描述
为了兼容老前端，留了一条 `app_id` 鉴权路径，但 handler 里 `tenantID = 0` 直接传给 Repository，结果这条路径下的查询完全跨租户。

### 踩坑过程
最开始做 Phase 1 多租户改造时，老前端 `mianshiba-web/admin/interview-agent` 三个还在用 `app_id` 鉴权。我们想着"先兼容着，等 Phase 5 全切 API Key 再下线"。

代码里写了一个简单的 `if isLegacyAppID(appID) { ... }` 分支，里面 `identity.TenantID = 0`——当时觉得"反正这条路径只给老前端用，前端代码受我们控制不会乱传"。

灰度跑了一段，**问题在 QA 阶段才暴露**：QA 同学测租户 A，但他构造请求时把 `app_id` 设成了 `interview-agent`（这是 legacy 白名单里的），后端走了 legacy 分支，`tenantID = 0` 传进去——`applyActorIsolationScope` 在 `tenant_id = 0` 时根本不过滤。结果 QA 看到了所有租户的 KB。

### 后果
- legacy 路径下所有请求事实上跨租户，**整整一个 Sprint 的隔离测试白做**
- 紧急修复，把 `legacy app_id` 强制映射到 `systemTenantID = 1`
- Phase 3 验收推迟了一周

### 避坑方案
1. **legacy 必须映射到明确租户**：看 [retrieve.go#L269-L276](../../backend/api/handler/rag/retrieve.go#L269-L276) 的修复：

   ```go
   identity = &auth.Identity{
       AuthType: auth.AuthTypeLegacyAppID,
       TenantID: systemTenantID, // 1
       UserID:   systemUserID,   // 1
       AppID:    req.AppID,
       IsLegacy: true,
   }
   ```

   **`tenant_id` 永远不能是 0**，要么是真实租户，要么是 system 租户。

2. **`IsLegacy` 显式打标**：方便审计日志、Prometheus 指标按 `is_legacy` 切分，**主动观察老路径的衰减**——Phase 3 隔离合约第 9 条专门要求这个（[phase3-l0-isolation-contract.md](../../backend/docs/zhuhu/phase3-l0-isolation-contract.md)）。

3. **handler 入口 panic 兜底**（dev 环境）：`identity.TenantID == 0` 直接 panic，强迫所有路径都补全租户。生产环境降级为告警，不直接 panic。

4. **legacy 白名单动态化**：[allowedAppIDs](../../backend/api/handler/rag/retrieve.go#L179-L188) 现在是 hardcode，未来要把它挪到配置中心，**有客户切完 API Key 立刻从白名单删掉**，最终目标是清空。

### 📚 延伸知识点
- **Strangler Fig Pattern**：Martin Fowler 提的"绞杀者模式"——用新系统逐步包裹旧系统，最后老系统自然消亡。legacy 路径就是典型应用场景
- **Feature Flag 灰度下线**：用 LaunchDarkly / 自研 flag 控制 legacy 路径开关，可以按租户、按时间灰度关闭
- **Defense in Depth**：纵深防御。即使 legacy 路径有漏洞，Repository 层、Milvus 层还能兜住，**单点失效不致命**

### 面试时怎么说
> "兼容老路径这块我们踩过一个特别隐蔽的坑。Phase 1 的时候为了兼容老前端，留了 `app_id` 鉴权路径，当时图省事 `tenantID` 直接给了 0。
>
> 后来 Repository 层的隔离过滤是 `if tenantID > 0 then ...`，结果 legacy 路径走到这就完全不过滤——QA 同学测试时构造了一个 legacy app_id，看到了所有租户的数据，整整一个 Sprint 的隔离测试相当于白做。
>
> 现在的修复是 legacy 路径强制映射到 `systemTenantID = 1`，并且打 `IsLegacy=true` 标，方便观察老路径占比、推进切流。这件事让我意识到：**做兼容路径时，'临时凑合'的代价往往最贵——必须在第一天就把 legacy 当成一种正式的、有租户归属的身份来对待，而不是当成隔离链路的旁路**。"

## 🕳️ 坑 6：JWT 永不吊销 + 员工离职 → 长达 24 小时的"幽灵权限"

### 问题描述
JWT access token TTL 设了 24 小时，员工离职时 admin 后台禁用了账号，但他手里的 token 在 24 小时内仍然能正常调接口。

### 踩坑过程
最开始做 JWT 鉴权时的普遍心态是"JWT 不查库，签发后 TTL 内有效，TTL 一过自然就废了——这就是 JWT 设计的精髓"。我们把 access TTL 设成了 24 小时（图刷新次数少），refresh TTL 7 天。

某次某员工离职，HR 在 admin 后台把账号 `status` 改成 `disabled`。**问题在于** JWT 验签是纯内存 HMAC（[jwt.go#L70-L88](../../backend/internal/auth/jwt.go#L70-L88)），完全不查库——这个员工拿着没过期的 token 还能继续调接口、看数据，**整整 24 小时**。

是该员工的 leader 第二天发现"他都离职了怎么还在 GitLab 里有 commit 记录、admin 后台有访问日志"，才意识到问题。

### 后果
- 员工离职后仍有 24 小时窗口可以下载知识库内容
- 安全合规审计被记录在案，要求出整改方案
- 被迫紧急做了"租户级强制下线"功能补漏，本不在 Phase 3 范围内

### 避坑方案
1. **租户状态查库兜底**：看 [RequireTenantActive](../../backend/internal/middleware/auth.go#L109-L136) 中间件——每次请求查 `rag_tenant.status`，租户被 suspend 立刻 403。**这是当前唯一一道实时下线机制**。

2. **缩短 access TTL + 长 refresh TTL**：access 设 15 分钟，refresh 设 7 天，**禁用账号后最多 15 分钟生效**。代价是 refresh 调用频率上升，但比 24 小时窗口好多了。

3. **Token 黑名单（Redis Set）**：业内通病是"JWT 无状态所以无法吊销"，其实可以加 Redis 黑名单，校验时多查一次 `SISMEMBER`。**目前没做，未来思考是 Phase 5 加这块**。

4. **API Key 做反例**：[APIKeyAuth](../../backend/internal/middleware/auth.go#L168) 必须查库——`status="revoked"` 立刻生效。**Agent 用 API Key 反而比员工 JWT 更安全**，这是个反直觉但合理的设计。

5. **离职流程联动**：HR 系统调用 admin 接口时，自动触发"封禁该用户名下所有 API Key + 把用户加入 token 黑名单"两个动作，**人 + 凭证双关**。

### 📚 延伸知识点
- **JWT vs Session**：JWT 无状态、可水平扩展但难吊销；Session 有状态、易吊销但需要共享存储。**没有银弹，看场景**
- **JWT Blacklist 模式**：在 Redis 存 `jti` 黑名单，TTL 等于 token 剩余有效期，过期自动清理。代价是每次校验多一次 Redis 查询
- **Refresh Token Rotation**：每次刷新 refresh token 也换新，旧的立即失效，防止 refresh token 被盗后无限续期

### 面试时怎么说
> "JWT 这块我们踩过一个反直觉的坑。最开始我们觉得 JWT 的精髓就是无状态、不查库，所以 access TTL 设成了 24 小时图省事。
>
> 结果某员工离职那天，HR 把账号禁了，但他手里的 token 还能用 24 小时——leader 第二天看 GitLab 日志才发现这个'幽灵账号'。
>
> 后来我们做了三件事：access TTL 缩短到 15 分钟；加了 `RequireTenantActive` 中间件每次查一下租户状态；离职流程联动调 admin 接口封禁所有 API Key。这件事让我明白一个反直觉的事实：**JWT 的'无状态'只对'读多写少且容忍延迟'的场景有效，安全敏感的实时吊销，最终还是要落到查库这条路上**。"

## 🕳️ 坑 7：Milvus chunk metadata 没写 `tenant_id` → SQL 隔离过了，向量库照样跨租户

### 问题描述
SQL 层 `kb_id` 校验过了、Repository 也带 `tenant_id` 过滤了，但 Milvus 那边 chunk metadata 漏写 `tenant_id`，结果检索 expr 没法做租户过滤，跨租户向量泄漏。

### 踩坑过程
最开始做隔离时的注意力全在 SQL 层，反复 review `kb_tenant_repo` 各种 `Where`。Milvus 这边因为是单 collection 共用，大家想着"反正 `kb_id` 校验过了，进 Milvus 时 expr 拼了 `kb_id IN [合法集合]`，应该就够了"。

灰度过程中没问题。但 Phase 3 L5 做隔离回归时，安全同学构造了一个边界用例：**租户 A 通过 admin 接口创建了一个 KB，然后把这个 KB 通过 `rag_tenant_kb_permission` 共享给了租户 B 读**。后来租户 A 把这个 KB 删了（DB 层删），但 Milvus 里 chunk 数据还在（异步清理）。租户 B 此时再查 `kb_id`，按 `kb_id` expr 还能查到——**因为 Milvus 那边压根不知道这个 KB 是哪个租户的**。

更糟的是，如果有人构造请求绕过 SQL 层（比如用 `metadata_filter` 自定义 expr 覆盖了 `kb_id` 过滤），Milvus 里所有租户的 chunk 都会被检索到。**SQL 隔离过了不代表向量隔离过了**。

### 后果
- 两层隔离实际只有一层在生效，违反 Phase 3 通过标准第 5 条
- 推迟 Phase 3 验收，紧急补 chunk metadata 改造和重灌索引
- 索引重建期间检索质量回退，灰度策略不得不回滚

### 避坑方案
1. **chunk metadata 强制写 `tenant_id`**：入库时把 `tenant_id / kb_id / document_id` 三件套全写到 chunk metadata（Phase 3 L5 的核心工作），**这是物理层面的隔离基础**。

2. **检索 expr 强制拼租户过滤**：`metadata["tenant_id"] == <current_tenant>` 必须在 retrieval options 里硬编码，**禁止被 `metadata_filter` 覆盖**——这是 Phase 3 通过标准第 5 条。

3. **`metadata_filter` 字段做白名单**：用户只能在白名单字段里自定义过滤，`tenant_id / kb_id` 是系统保留字段，覆盖请求直接 400。

4. **双层校验**：SQL 层校验 `kb_id` 归属（[authorizeRetrieveKBIDs](../../backend/api/handler/rag/retrieve.go#L137-L175)）+ Milvus 层 expr 强制租户过滤，**两道闸门，单点漏掉另一个能兜住**。

5. **回归测试覆盖跨层**：构造租户 A 删除 KB 但 Milvus 数据未清理的场景，验证租户 B 拿到老 `kb_id` 也查不到结果。

### 📚 延伸知识点
- **Cell-based Architecture**：每个租户独占一个 Milvus collection 是终极隔离方案，但 collection 数量上千 Milvus 自己会扛不住，所以**隔离强度和资源成本永远是 trade-off**
- **Attribute-Based Access Control (ABAC)**：基于属性的访问控制，Milvus 的 metadata expr 本质是 ABAC 的一种实现
- **Soft Delete vs Hard Delete**：DB 层软删除 + 向量库异步清理是常见模式，但**清理延迟期间的隔离漏洞**是经典坑

### 面试时怎么说
> "向量库隔离这块我们踩过一个跨层的坑。最开始我们的注意力全在 SQL 层，反复 review `Where tenant_id`，Milvus 那边觉得'反正 `kb_id` 都校验过了，进去拼个 `kb_id IN [...]` 就行'。
>
> 安全同学测了一个边界场景：租户 A 删了一个 KB，但 Milvus 异步清理还没跑，这时候租户 B 拿着老 `kb_id` 还能查到 chunk——因为 Milvus 根本不知道这个 KB 属于谁。再加上如果有人用 `metadata_filter` 自定义 expr 覆盖 `kb_id`，所有租户的向量都漏了。
>
> 后来我们在 chunk metadata 里硬写 `tenant_id`，检索 expr 强制拼 `metadata["tenant_id"] == ?`，并且把 `tenant_id` 列为系统保留字段不允许用户覆盖。这件事让我意识到：**多租户隔离不是 SQL 层一处的事，是数据流经过的每一层都要兜一道——SQL、向量库、缓存、日志，每一层都是潜在的越权入口**。"

## 总结：避坑口诀表

| 坑 | 一句话避坑口诀 |
|---|---|
| 1. Repository 漏带 `tenant_id` | **类型签名硬约束 `tenantID uint64`，让漏传编译都过不了** |
| 2. JWT + 请求体双 `tenant_id` | **凭证是唯一信任源，`tenant_id` 字段从请求结构体里删掉** |
| 3. API Key 明文存库 | **只存 SHA256 哈希，明文创建时返回一次，强制 90 天轮换** |
| 4. 配额走 SQL `COUNT` | **高频累加走 Redis Lua 原子计数，低频精确计数才用 SQL** |
| 5. legacy `app_id` 没映射租户 | **legacy 必须映射到 system 租户，`tenant_id` 永远不能是 0** |
| 6. JWT 永不吊销 | **access TTL 缩短到 15 分钟，租户状态查库兜底实时下线** |
| 7. Milvus 漏写 `tenant_id` metadata | **chunk metadata 三件套（tenant_id/kb_id/document_id），expr 强制租户过滤** |

## 💡 面试时主动升华

> "我做完多租户这一整套后最大的感受是：**多租户隔离 80% 不是写代码的问题，是'让漏写变成不可能'的工程问题**。
>
> 写一遍 `Where tenant_id = ?` 谁都会，难的是保证 100 个 Repository、500 个 handler、3 套客户端、2 个 Phase 之后，**这道过滤永远不会被新人误删、被复制粘贴漏写、被 legacy 路径绕过**。
>
> 所以真正决定隔离强度的不是 `tenant_id` 这个字段加得多漂亮，而是：**Repository 类型签名能不能让漏传编译失败、CI 跑不跑租户 A/B 隔离回归、handler 入口能不能在 dev 环境对 `tenant_id=0` panic、向量库 expr 是不是写死系统保留字段**。
>
> 一句话总结：**好的多租户架构，是用工具把'人会犯错'这个变量从系统里消除掉**。"
