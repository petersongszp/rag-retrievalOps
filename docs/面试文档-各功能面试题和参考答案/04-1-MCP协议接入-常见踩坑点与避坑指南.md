# 04-1 MCP 协议接入 - 7 个最容易踩的坑与避坑指南

> 配套主文档：[04-MCP协议接入-面试题和参考答案.md](04-MCP协议接入-面试题和参考答案.md)

---

## 前言

MCP 协议接入这事看起来就是"封个 Server、定义个工具、转发到现有 API"三件套，但实际上 stdio / http 两套传输、Authorization 透传、Origin 校验、Stateless 会话、agent 维度灰度，每一个点都能踩出血。

下面这 7 个坑，按踩中概率从高到低排序。

---

## 🕳️ 坑 1：MCP Server 里把检索逻辑重写了一遍 → 治理体系直接分裂

### 问题描述
为了"性能更好""更灵活"，让 MCP Server 直接调 `internal/milvus`，结果检索日志、租户校验、灰度策略全失效，Web/SDK/MCP 三个通道行为漂移。

### 踩坑过程
最开始接 MCP 的普遍心态是："反正 RAG 代码就在隔壁包里，import 进来直接调多省事，还能少一跳网络。" 然后就有人开始在 MCP handler 里直接 `import "internal/milvus/retrieval"`，绕过 `/v1/retrieve`。

短期看一切都好：延迟少 30ms、不用维护 HTTP 客户端。但**第二周开始问题就来了**：

- 业务侧投诉某个租户的检索结果不一致——MCP 通道的租户校验是新写的一套，漏判了 `kb_permission`
- 检索日志 `kb_retrieve_log` 里 MCP 那条记录的 `request_id` 字段空着，因为 `request_id` 是 `/v1/retrieve` 这层生成的
- 灰度发布完全不生效，`release.Controller.Decide` 是绑在 RAG handler 里的，MCP 直连绕过了

发现是因为运营按 `app_id` 做检索质量周报时，看到 MCP 渠道的 `evidence_gate_result`、`refusal_reason` 全是空，根本统计不出来。

### 后果
- 治理体系分裂：同一个 query 走 SDK 是 Phase2 走 MCP 是 Phase1，行为不一致
- 检索日志缺失关键字段（占比 100%），无法做 agent 维度的质量分析
- 后续要补回来，等于把 RAG handler 的逻辑在 MCP 这边再写一遍，**代码重复工作量按月算**

### 避坑方案
1. **协议层和能力层物理分离**：MCP Server 只能通过 HTTP 调 `/v1/retrieve`，不允许 import 任何 `internal/milvus` 或 `internal/kb` 的包。我们项目里这条强约束写在 [mcp-agent-integration-design.md](../../backend/docs/rag/mcp-agent-integration-design.md) 第 3.2 节"非目标"里
2. **lint 卡死 import**：在 CI 加一条静态检查，扫描 `backend/internal/mcp/**` 里如果出现 `internal/milvus` 或 `internal/kb` 的 import path，直接 fail
3. **接口反向校验**：每周跑一次 e2e，对比同一个 query 走 SDK 和走 MCP 的 `request_id`、`strategy_version`、`evidence_gate_result` 是否一致
4. **代码 review 强制看 RetrieverFactory**：所有 MCP 新工具必须通过 [handler.RetrieverFactory](../../backend/internal/mcp/handler/retrieve.go#L30-L38) 接口拿 Retriever，禁止自己 `new` 一个 Milvus 客户端

> 详见主文档 [Q1：你们 MCP 接入这块整体是怎么设计的](04-MCP协议接入-面试题和参考答案.md#q1你们-mcp-接入这块整体是怎么设计的为什么这么分层)

### 📚 延伸知识点
- **Adapter Pattern（适配器模式）**：MCP Server 的本质就是协议适配器，不应该承担业务逻辑——经典 GoF 模式在协议层的体现
- **Sidecar 模式**：把协议适配独立成 Gateway 进程，是云原生里把"翻译职责"和"业务职责"解耦的标配做法
- **Bounded Context（领域驱动设计）**：MCP 是一个独立限界上下文，不应该跨越边界去触碰检索领域的内部实现
- **API Gateway 反模式**：网关里写业务逻辑，是最常见的"网关变巨石"的开端

### 面试时怎么说
> "在 MCP 接入这块我们最早其实差点踩一个大坑。当时讨论是不是让 MCP Server 直接调 `internal/milvus` 包，少一跳 HTTP 看起来更高效。
>
> 后来仔细想了一下发现不行——一旦绕过 `/v1/retrieve`，租户校验、`request_id` 生成、检索日志、灰度决策全是空的，等于把 RAG 的治理体系凿了个洞。而且 Web、SDK、MCP 三个通道会慢慢漂移，同一个 query 不同渠道结果不一样，排查成本极高。
>
> 所以我们最后定了一条死规矩：**MCP 只能通过 HTTP 调公开接口，绝对不准 import 内部检索包**。这件事让我意识到，**协议层最危险的地方就是它看起来'和业务很近'，但凡降低一点点门槛去碰业务，整个治理就崩了。协议层永远只做翻译，不做业务**。"

## 🕳️ 坑 2：stdio 模式被带到生产 → 一个 Token 全租户共享

### 问题描述
开发同学本地用 stdio 模式接 Claude Desktop 调通了，运维直接复制配置上生产，结果整个生产 MCP Server 共用一个 `RAG_ACCESS_TOKEN`，所有租户 API Key 隔离失效。

### 踩坑过程
最开始 MCP 接入是从开发本地起步的，普遍流程是："起 `rag-mcp-server --transport stdio`，把 `RAG_ACCESS_TOKEN=rag_dev_xxx` 写到环境变量，Claude Desktop config 里加一行命令，跑通 demo。" 很爽，10 分钟搞定。

后来要上预发，运维同学按惯例"开发怎么跑的我就怎么部署"，把 stdio 模式也带到了预发环境。预发环境就一个 token，所有内部测试用户共用。

**真正出问题是在准备上生产前的安全评审**：评审的同事问"你这个 token 是哪个租户的？"——发现整个 Server 进程绑死一个租户的 API Key，所有走 MCP 的请求落到 RAG 侧的 `tenant_id`、`user_id` 全是同一个。多租户隔离形同虚设。

我们后来在 [config.go#L96-L99](../../backend/internal/mcp/config.go#L96-L99) 的 `Validate()` 里加了硬约束：`prod` 环境用 stdio 直接 `return error`，让进程压根起不来。

### 后果
- 多租户隔离失效，**所有 MCP 请求 `tenant_id` 都是同一个**，审计完全错乱
- API Key 一旦泄漏，整个 MCP 通道全沦陷，没法按租户吊销
- 修复要回滚到 http 模式 + 重新发 API Key 给所有 Agent，**沟通成本按周算**

### 避坑方案
1. **Validate 硬卡死**：[config.go#L96-L103](../../backend/internal/mcp/config.go#L96-L103) 里 `APP_ENV=prod` 且 `Transport=stdio` 直接 return error，让进程压根起不来——**工具层封死，比文档强 100 倍**
2. **prod 强制 http + ALLOWED_ORIGINS**：同样写在 Validate 里，缺一不可
3. **部署模板分离**：开发用的 `docker-compose.dev.yml` 和生产 [Dockerfile.mcp](../../backend/Dockerfile.mcp) 严格分开，Dockerfile 默认 `MCP_TRANSPORT=http`
4. **API Key 反向校验**：上线前 grep 所有部署配置，看 `RAG_ACCESS_TOKEN` 是否存在——生产 http 模式根本不应该用这个变量

### 📚 延伸知识点
- **Fail-Fast 启动校验**：配置不合法宁可启动失败，也不要带病运行——Spring Boot、Kubernetes admission webhook 都是这个思路
- **Per-Request Authentication vs Service Account**：每个请求带租户身份 vs 进程绑死身份，前者才是 SaaS 标配
- **MCP Transport 规范**：stdio 是 MCP 协议设计给"单用户本地工具"的，不是为多租户云服务设计的，把 stdio 上生产是误用协议

### 面试时怎么说
> "stdio 这个坑挺典型的。最开始大家都是本地用 Claude Desktop 调 MCP，stdio + 环境变量配 Token 特别方便，10 分钟搞定。
>
> 然后预发环境就直接复用了开发的部署方式，没人觉得有问题。结果安全评审的时候被问到——你这个 token 对应哪个租户？大家才反应过来：**stdio 模式下整个进程绑死一个 Token，多租户隔离根本没生效**，所有 MCP 请求落到日志里 `tenant_id` 都是同一个。
>
> 现在我们在配置 Validate 里直接硬卡：prod 环境用 stdio 启动失败，prod + http 还要求必须配 ALLOWED_ORIGINS。这件事教会我一个道理：**便利的部署方式往往隐藏着危险的默认值，安全约束一定要写到代码里让进程起不来，写在文档里大家都会忘**。"

## 🕳️ 坑 3：Origin 校验默认放行空 Origin → DNS Rebinding 防护是空的

### 问题描述
配了 `MCP_ALLOWED_ORIGINS` 觉得安全了，结果攻击者构造的请求干脆不带 Origin 头，直接绕过白名单。

### 踩坑过程
最开始做 Origin 校验时的常见心态是"白名单写好了就行"。我们 [security/origin.go#L28-L37](../../backend/internal/mcp/security/origin.go#L28-L37) 早期逻辑就是：拿到 Origin，空就放行，非空就比对白名单。

看起来没毛病——浏览器一定会带 Origin，带了就校验。但**这是业内通病**：MCP 协议 SSE/Streamable 模式下，DNS Rebinding 攻击的核心手法就是构造一个"看起来像本地服务"的请求绕过同源策略。攻击者写的恶意页面用 `fetch` 调 `http://127.0.0.1:8898/mcp`，浏览器遇到 `mode: 'no-cors'` 就**不会带 Origin**，我们这里直接 `next.ServeHTTP` 放行。

发现是社区有人在 MCP SDK issue 里报这个问题，我们排查下来确认空 Origin 的请求也能直达 `tools/call`。

### 后果
- DNS Rebinding 类攻击的防护**形同虚设**，白名单白配
- 本地开发场景下任何浏览器页面都能调通本地 MCP Server，权限边界完全失控
- 修复涉及配置语义变更，要发 changelog 给所有内嵌部署用户

### 避坑方案
1. **生产强制 `MCP_REQUIRE_ORIGIN_HEADER=true`**：[config.go#L35](../../backend/internal/mcp/config.go#L35) 里这个开关默认 false，生产环境必须打开，没带 Origin 直接 403——见 [origin.go#L30-L34](../../backend/internal/mcp/security/origin.go#L30-L34)
2. **白名单 + 必填双闸**：白名单挡住已知恶意源，必填挡住"故意不带 Origin"的攻击
3. **本地开发也要带 Origin**：[transport/http_test.go#L66](../../backend/internal/mcp/transport/http_test.go#L66) 里测试用例已经这么做了——`req.Header.Set("Origin", "https://agent.example.com")`，用测试反推接入方
4. **CORS 永远不要 `*`**：[origin.go#L56-L58](../../backend/internal/mcp/security/origin.go#L56-L58) 里 `Access-Control-Allow-Origin` 永远回显具体的 Origin（前提是白名单内），不写 `*`

### 📚 延伸知识点
- **DNS Rebinding 攻击**：通过 DNS TTL 切换让浏览器认为一个外部域名是本地地址，绕过同源策略，专打监听 127.0.0.1 的本地服务，是 MCP/Electron 这类"本地运行 HTTP Server"应用的头号威胁
- **Sec-Fetch-Site / Sec-Fetch-Mode**：现代浏览器自动带的元数据头，比 Origin 更难伪造，未来可以作为 Origin 的补充校验
- **PNA (Private Network Access)**：Chrome 在推的标准，限制公网页面访问私网/本地服务，本质上就是为了堵 DNS Rebinding
- **mode: 'no-cors' 反模式**：fetch 这个选项让浏览器跳过同源策略和预检，是大量"本地服务被打"的导火索

### 面试时怎么说
> "Origin 校验这块我们踩过一个挺隐蔽的坑。最开始觉得，配个 ALLOWED_ORIGINS 白名单就 OK 了嘛，浏览器一定会带 Origin 头，带了我就校验。
>
> 后来发现 MCP SDK 那边有人提 issue，说 DNS Rebinding 攻击根本不会带 Origin——攻击者构造一个 `mode: 'no-cors'` 的 fetch，浏览器就把 Origin 头吃掉了，我们这边代码直接放行了。**白名单挡的是带头的请求，不带头的反而是绿色通道**。
>
> 所以我们后来加了 `MCP_REQUIRE_ORIGIN_HEADER` 这个开关，生产环境强制必须带 Origin，没带直接 403。这件事让我学到：**安全防护一定要假设攻击者会绕过你的'默认友好'路径，凡是空值、缺省值能进的入口，都得当作高危入口对待**。"

## 🕳️ 坑 4：MCP 层重复验 Token → 双重校验逻辑漂移

### 问题描述
为了"加固安全"在 MCP 层也校验了一遍 API Key 的 hash，结果和 RAG 侧的校验逻辑漂移，出现"MCP 放行但 RAG 拒"或"MCP 拒了但 RAG 其实能过"的灵异 bug。

### 踩坑过程
普遍心态是"多校验一道总没坏处"。最开始 MCP 的 `passThroughTokenVerifier` 只检查 Token 不为空，有人觉得这太弱，提议在 MCP 层也查一下 `rag_api_key` 表，验证 Key 是否吊销。

听起来很合理。问题在于：

- RAG 侧的 [middleware/auth.go#L138-L221](../../backend/internal/middleware/auth.go#L138-L221) 已经做了完整校验：格式、hash、状态、过期、租户状态。这是**业务真理**
- MCP 这边再做一遍意味着要 import RAG 的 repo 包或者复制一份代码
- 后来 RAG 侧加了"租户 quota 超额禁用"逻辑，MCP 这边没跟上，**线上出现 MCP 放行、RAG 返回 403** 的情况，错误码语义对不齐

更糟的是 MCP 这边校验通过后还会更新 `last_used_at`，RAG 那边也更新，**同一次调用更新了两次时间戳**，把 `last_used_at` 的语义搞乱了。

最后我们坚持只在 MCP 层做"非空校验"，真伪交给 RAG，见 [transport/http.go#L108-L118](../../backend/internal/mcp/transport/http.go#L108-L118) 的 `passThroughTokenVerifier`。

### 后果
- 双层校验逻辑漂移，**错误码不一致**，Agent 拿到 401 不知道该信谁
- `last_used_at` 重复更新，统计 API Key 活跃度数据失真
- 加新校验规则要改两处，**维护成本翻倍**

### 避坑方案
1. **认证语义单点**：API Key 真伪判断只在 RAG 侧做，MCP 层只做"协议要求的最小校验"（格式、不为空），见 [server.go#L47-L60](../../backend/internal/mcp/server.go#L47-L60) 透传逻辑
2. **错误码原样透传**：MCP 这边把 RAG 返回的 401/403 通过 [client/rag_client.go#L219-L237](../../backend/internal/mcp/client/rag_client.go#L219-L237) 的 `mapStatus` 映射成 MCP 语义码，原状态码不丢
3. **Token 指纹日志关联**：MCP 用 [security/redact.go](../../backend/internal/mcp/security/redact.go) 的 SHA256 指纹日志关联请求，不需要解析 Token 内容
4. **测试用 e2e 兜底**：[http_security_test.go#L21](../../backend/internal/mcp/transport/http_security_test.go#L21) 的 `TestHTTPTransportMapsUpstreamUnauthorizedAndForbidden` 专门验证错误码映射不丢

### 📚 延伸知识点
- **认证职责单一原则**：DDD 里的"业务真理只能有一处"，认证决策应该只在一个层做，其他层只做透传
- **错误码不透明 vs 透明**：MCP SDK 的 `CallToolResult.IsError + structured payload` 是透明错误模型，比 HTTP 状态码丢失语义要好
- **JWT vs Opaque Token**：JWT 自带 claim 可以本地校验，opaque token 必须查后端——我们的 API Key 是 opaque，注定单点校验

### 面试时怎么说
> "鉴权这块我们也讨论过要不要在 MCP 层加一道。当时有同学说'多验一道更安全'，听起来挺对。
>
> 但后来想清楚了：API Key 的真伪判断只能有一处，那就是 RAG 侧。MCP 再校验一遍意味着代码要复制、规则要同步，**RAG 那边新加一条 quota 超额禁用，MCP 这边没跟上，立马就出现两边判断不一致的灵异 bug**。
>
> 现在 MCP 层只做最小校验，Token 不为空就放过去，真伪让 RAG 判，错误码原样透传给客户端。这件事让我体会到：**'多一层防护'听起来很美，但如果两层防护逻辑不能保证完全同步，那就是制造分歧而不是加固安全**。"

## 🕳️ 坑 5：metadata_filter 没限大小和深度 → 攻击者一发请求打挂 Milvus

### 问题描述
工具 schema 里 `metadata_filter` 接的是 `map[string]interface{}`，最开始没限大小和嵌套深度，结果有人塞了几千行 OR 嵌套，整条检索链路被拖垮。

### 踩坑过程
最开始定 schema 时心态是"filter 要灵活，给用户最大自由"，于是 `metadata_filter` 就是个开放的 object，能传啥传啥。

正常用户最多 2-3 层 OR/AND，大家用得很爽。直到某天看到 P95 飙升告警，排查发现某个 Agent 的 `metadata_filter` 里写了**几千行的嵌套 OR**——可能是 LLM 生成 filter 时 hallucinate 了。

这种 filter 一路传到 Milvus，**embedding 阶段没事，filter 编译阶段直接消耗 50ms+ CPU，Milvus 单 shard 基本卡住**。更糟的是 Agent 的重试逻辑没退避，**每秒打 50 个相同请求**，单租户直接把 Milvus 整个集群压到不响应。

发现是因为 RAG 平台的 `mcp_tool_call_total{status="invalid_request"}` 这条线一直在涨——但当时还没拒，是 Milvus 拒。

后来在 [handler/retrieve.go#L17-L24](../../backend/internal/mcp/handler/retrieve.go#L17-L24) 加了 `maxMetadataFilterBytes = 16KB`、`maxMetadataFilterDepth = 8`，[L162-L177](../../backend/internal/mcp/handler/retrieve.go#L162-L177) 的 `validateMetadataFilter` 里序列化算字节、递归算深度，超就拒。

### 后果
- **单租户能打挂整个 Milvus 集群**，多租户隔离的边界被绕过了
- P95 飙升、其他正常租户被拖累，**故障半径远超预期**
- 修复需要紧急上线 schema 校验 + 通知 Agent 方修复重试逻辑

### 避坑方案
1. **schema 是第一道闸，handler 是第二道闸**：[tools/definition.go](../../backend/internal/mcp/tools/definition.go) 里写 maxLength/maxItems，但 schema 校验是客户端善意行为，**handler 必须重新校验** ——见 [handler/retrieve.go#L162-L177](../../backend/internal/mcp/handler/retrieve.go#L162-L177)
2. **字节数 + 嵌套深度双限**：JSON 序列化算字节挡 16KB，递归算深度挡 8 层，两个都要有，单一维度都能被绕
3. **错误码区分对待**：超限返回 `invalid_request, retryable=false`，Agent 重试就是死循环
4. **限流前置**：`mcp_tool_call_total{status="invalid_request"}` 单独配告警，超过阈值在网关层先限流，别让大量错误请求打到 RAG

### 📚 延伸知识点
- **Billion Laughs / XML Bomb**：经典的解析炸弹，递归深度无限的 XML/JSON 能把解析器打挂，所有协议层都要做深度限制
- **Cardinality / Complexity Bound**：API Gateway 里限制 query depth/breadth 是 GraphQL 标配（如 `graphql-depth-limit`），REST 这边经常被忽略
- **Backpressure（背压）**：Agent 重试不退避是反模式，正确做法是 exponential backoff + jitter
- **故障半径（Blast Radius）**：单租户/单 Agent 的请求不能打挂整个集群，是 SaaS 多租户设计的核心命题

### 面试时怎么说
> "metadata_filter 这块我们踩过一次特别痛的坑。最开始 schema 没限大小，觉得给用户最大自由就行。
>
> 结果某天 Milvus 被打到不响应，排查发现是某个 Agent 的 LLM 生成 filter 时 hallucinate 了，写了几千行的嵌套 OR。**单条请求消耗 50ms CPU，Agent 重试没退避每秒打 50 条，单租户直接把整个集群打瘫**。
>
> 现在我们在 schema 里写了 `maxLength: 2000`、`maxItems: 100` 这些上限，handler 里再用字节数和嵌套深度做二次校验，超 16KB 或超 8 层直接拒，错误码标 `retryable=false` 让客户端别再重试。这件事让我意识到，**协议层最大的责任是给下游系统挡刀，schema 不能只考虑友好的客户端，还要考虑出现 bug 或被恶意构造的客户端**。"

## 🕳️ 坑 6：Stateless 模式开了但忘了 SessionTimeout → SSE 长连接堆积 OOM

### 问题描述
为了横向扩展开了 `Stateless: true`，以为不需要管 session 了，结果 SSE 长连接没人清理，堆积到 OOM。

### 踩坑过程
最开始用 [transport/http.go#L56-L61](../../backend/internal/mcp/transport/http.go#L56-L61) 的 `StreamableHTTPHandler` 时，看到 `Stateless: true` 这个选项，普遍心态是"打开就能横扩，不用管 session 了"。

跑了两周一切正常。然后某天 MCP Server 内存涨到 4GB 触发告警。dump 了 heap 一看，**几千个 SSE 连接 hanging 在那**，每个连接占用大几百 KB。

排查下来发现：

- `Stateless: true` 只是说服务端不强依赖 session 做业务路由，不代表连接生命周期管理也不需要
- Claude Desktop 客户端断网/休眠时不会发 close，连接就 dangling
- 我们 `SessionTimeout` 用了默认值，但没在 ServerOptions 里显式传——结果默认很大，根本不超时

后来在 [config.go#L57-L64](../../backend/internal/mcp/config.go#L57-L64) 里默认 `5 * time.Minute`，并且必须在 [transport/http.go#L58-L61](../../backend/internal/mcp/transport/http.go#L58-L61) 里显式传给 `StreamableHTTPOptions`。

### 后果
- MCP Server 内存周期性涨到 OOM，需要每 N 小时重启
- 重启时正在调用的 Agent 全部失败，**用户感知到"Claude 工具不可用"**
- 排查走了不少弯路，因为"Stateless"字面意思容易误导

### 避坑方案
1. **Stateless ≠ 不管连接**：`Stateless: true` 是会话语义层面的，连接超时还是要显式配
2. **SessionTimeout 写到 Validate 里强校验**：[config.go#L129-L131](../../backend/internal/mcp/config.go#L129-L131) 里 `if c.SessionTimeout <= 0 { return error }`，不允许配 0 或负数
3. **HTTP Server 自身也要超时**：[transport/http.go#L27-L29](../../backend/internal/mcp/transport/http.go#L27-L29) 里 `ReadHeaderTimeout: 5s`、`IdleTimeout: 2min`，多层防护
4. **连接数监控**：用 `process_open_fds` 或自己埋一个 gauge，连接数超过阈值告警

### 📚 延伸知识点
- **Stateful vs Stateless 的真实含义**：协议无状态指业务无状态，不代表 TCP 连接、文件描述符、内存缓冲区也无需治理
- **Slowloris 攻击**：故意发慢请求/不发完连接的 DDoS 手法，所有 HTTP Server 必须配 ReadHeaderTimeout/IdleTimeout
- **SSE vs WebSocket**：SSE 是单向长连接，看起来轻量但同样要配超时；WebSocket 有 ping/pong 心跳更容易检测断连
- **K8s `terminationGracePeriodSeconds`**：滚动重启时给 SSE 长连接留出排空窗口，避免硬切

### 面试时怎么说
> "Stateless 这块我踩过一个挺隐蔽的坑。我们用的 MCP SDK 提供 `Stateless: true` 这个选项，最开始我们一打开觉得'好了 session 不用管了能横扩了'。
>
> 结果两周后 MCP Server 内存爆了，排查发现是 SSE 长连接堆积——客户端断网或休眠的时候不发 close，连接就 dangling，我们没配 SessionTimeout，连接死活不被清理。
>
> 后来才搞明白，`Stateless` 指的是**业务层面无状态**，不是说底层连接、文件描述符也不用治理。现在我们在 Validate 里强校验 SessionTimeout 必须大于 0，HTTP Server 自身也配了 ReadHeaderTimeout 和 IdleTimeout。这件事让我反思了一个观念：**框架/SDK 提供的"贴心默认值"，往往会让你忽略本来该自己负责的边界——配置越多越不能偷懒，每一项都得想清楚再开**。"

## 🕳️ 坑 7：agent 维度灰度直接复用 user_id 分桶 → Agent 全有或全无

### 问题描述
灰度发布想按 Agent 维度切流，但 `release.Controller` 的桶 key 是 `user_id`，而 API Key 对应固定 `user_id`，导致**同一个 Agent 要么全 Phase2 要么全 Phase1**，根本切不了百分比。

### 踩坑过程
最开始接 MCP 时复用 RAG 的灰度体系是顺理成章的——[release/controller.go#L233-L243](../../backend/internal/rag/release/controller.go#L233-L243) 的 `matchesStableBucket` 用 `userID` 做 FNV hash mod 100，分桶发 Phase2。

听起来无懈可击。直到产品提需求："我想让 Cursor 用户先用 10% 流量灰度新策略，Claude Desktop 用户暂时不动。"

我们就懵了：

- API Key 对应一个固定 `user_id`（API Key 创建时绑定的）
- 同一个 Agent（如 Cursor）通常用同一把 Key，所以**所有 Cursor 流量都是同一个 user_id**，FNV hash 出来要么在桶内、要么不在桶内
- 结果是 Cursor 全在 Phase2 或者全在 Phase1，**根本做不到 10% 灰度**

发现是产品看灰度报表数据时问"为啥 canary 桶里 Cursor 的 QPS 不是 10% 而是 0% 或 100%"。

短期我们的处置方式是：让 agent 维度灰度走 `runtime override`（[controller.go#L78-L96](../../backend/internal/rag/release/controller.go#L78-L96)）+ 单独发临时 API Key 给 canary 子集用户。**长期需要在 `evaluateStage` 里加 `app_id` 维度的分桶**，主文档 Q7 里也写了这是已知未做项。

### 后果
- 产品想做的"按 Agent 灰度 10%"实际变成"全切或全不切"，**灰度策略形同虚设**
- 临时绕过方案要发临时 API Key、改 `app_id` 白名单，**运维成本陡增**
- 数据报表里 canary 桶的 Agent 分布看起来很奇怪，沟通成本高

### 避坑方案
1. **承认现状，文档化限制**：在主文档 Q7 里明确写"agent 级灰度未做"，不要假装能做——见 [04-MCP协议接入-面试题和参考答案.md Q7](04-MCP协议接入-面试题和参考答案.md#q7mcp-这套现在还有什么没做后续要做什么为什么没一上来做)
2. **短期用 runtime override + 用户子集**：[release/controller.go#L78-L96](../../backend/internal/rag/release/controller.go#L78-L96) 的 `SetRuntimeOverride` 可以临时切，配合给 canary 子集发独立 API Key
3. **长期改桶 key**：在 `evaluateStage` 里增加 `app_id` 维度，桶 key 从 `user_id` 改成 `(user_id, app_id)` 组合，需要把 `app_id` 上下文从 MCP Header 传到 RAG
4. **请求级伪随机分桶（更激进方案）**：直接用 `request_id` hash 分桶，能做到精确 10% 但破坏"同一个用户体验一致"的原则，要慎用

### 📚 延伸知识点
- **Sticky Bucketing（粘性分桶）**：A/B 测试经典原则——同一用户应该始终在同一桶，避免体验不一致。`user_id` 分桶是粘性的，`request_id` 分桶不粘
- **Multi-Dimension Targeting**：成熟的 Feature Flag 系统（LaunchDarkly、Unleash）支持按 user/account/segment 多维定向
- **Canary Analysis**：灰度不只是分桶，还要自动对比 canary 和 baseline 的指标，Spinnaker 的 Kayenta 是这个领域代表
- **API Key 不应承载灰度身份**：业内最佳实践是把 user/account/agent 解耦，灰度按 segment 而不是按认证主体

### 面试时怎么说
> "灰度这块我们踩过一个挺尴尬的坑。最开始觉得 MCP 复用 RAG 的灰度逻辑就行——`release.Controller` 按 `user_id` FNV hash 分桶，发 10% canary。
>
> 后来产品说想让 Cursor 用户灰度 10%，结果发现做不到——**API Key 对应固定 `user_id`，所有 Cursor 流量都是同一个 hash，要么全切要么全不切**。我们当时挺懵的，灰度策略看着完美但根本切不动。
>
> 短期我们用 runtime override + 临时 API Key 兜了一下，长期方案是把分桶 key 从 `user_id` 改成 `(user_id, app_id)` 组合。这件事我反思下来：**复用现有灰度体系前一定要先想清楚'分桶 key 是什么'，灰度的本质是切流量，但流量的'人'和'代理'可能根本不是同一个维度**。"

## 📋 总结：7 个坑的避坑口诀

| 坑 | 避坑口诀 |
|---|---------|
| MCP 直接调内部检索包 | 协议层只做翻译，禁 import internal 业务包 |
| stdio 模式上生产 | Validate 硬卡死，prod + stdio 启动失败 |
| Origin 校验放行空头 | 生产强制 REQUIRE_ORIGIN_HEADER，白名单 + 必填双闸 |
| MCP 层重复验 Token | 认证语义单点，MCP 只做非空校验，真伪交 RAG |
| metadata_filter 不限大小 | 字节数 + 嵌套深度双限，schema 是第一闸，handler 是第二闸 |
| Stateless 模式忘配超时 | Stateless ≠ 不管连接，SessionTimeout 必须显式配 |
| Agent 灰度复用 user_id 桶 | 想清楚分桶 key，多维定向用 (user_id, app_id) 组合 |

## 💡 面试时主动升华

讲完某个具体的坑之后，可以顺势补一句，体现你的深度思考：

> "MCP 这一层踩过的坑回头看，其实都不是 MCP 协议本身的问题。**协议层最大的危险，就是它看起来'离业务很近'——很容易被'多做一点会更好'的诱惑带歪**。多校验一道？多做一层缓存？多 import 一个内部包？每一个'多做一点'都是在协议层和业务层之间打洞。
>
> 我现在的方法论很简单：**协议层永远只做三件事——翻译、校验、转发**。其他事再合理也不该这一层做。这个边界守住了，MCP 就是稳定的；守不住，再小的项目也会变成网关巨石。"
