## 1. 全链路可观测实现

**Q：你们项目的全链路可观测是怎么实现的？**

**我的回答：**

我们做了四层体系：指标、日志、追踪、告警。

最底层是 **Metrics 指标层**，用 Prometheus + Grafana，埋了二十多个核心指标，覆盖请求量、延迟、错误率、缓存命中率这些关键数据。每个指标都带了 strategy、release_stage、route 这些标签，方便下钻。

然后是 **Logs 结构化日志层**，这个我们没有用 ELK，而是直接存在 MySQL 里，有八十多个字段。因为我们每天也就十几万条日志，MySQL 完全够，而且团队都熟，运维成本低。日志里除了常规信息，还存了每个检索请求的 Debug Trace，就是检索各阶段的快照。

再往上是 **Traces 链路层**，做了两层：一层是通用的分布式追踪，用 OTel，跨服务串联；另一层是自研的 Debug Trace，专门存检索内部每个阶段的详情——路由命中了多少、融合去重前后的变化、重排的结果对比这些。这个对排查问题特别有用。

> "Debug Trace 是我们自研的**业务语义层追踪**，弥补 OTel 粒度太粗的问题。它通过 Context 透传一个结构化收集器，让检索链路上每个阶段（路由、召回、rerank）把自己的输入、输出、关键决策按统一格式记录下来，最后异步落到 MySQL。OTel 回答'**慢在哪**'，Debug Trace 回答'**为什么结果是这样**'，两者通过 TraceID 关联，互补使用。线上排查检索效果问题基本靠它，MTTR 从小时级降到分钟级。"

最顶层是 **Alerting 告警层**，也是两层：Prometheus 规则告警和代码级实时告警。告警做了分级，P1 是必须起来处理的，P2 是可以上班再看的。

整体效果就是 MTTR 从小时级降到了 30 分钟以内，而且大部分故障都是我们自己先发现的，不是用户先报的。

### 🔍 深挖追问兜底

**Q：跨服务的 TraceID 是怎么串联的？用了 OpenTelemetry 吗？**
> 没用 OTel，是自研的 TraceID 透传。HTTP 服务之间通过自定义请求头（`X-Trace-Id`）传，进程内通过 `context.Context` 传，写入消息队列时塞进消息体的 metadata，协程池任务提交时手动把 TraceID 从父 ctx 拷到子 ctx。**关键是所有跨边界调用都用封装好的公共工具类**，禁止业务直接用原生 client，否则一定会漏。

**Q：Prometheus 在 K8s 里怎么发现你的服务实例？**
> 通过 Kubernetes SD 配置（`kubernetes_sd_configs`），让 Prometheus 监听 K8s API server 的 service/pod 变更事件，自动把带特定 annotation（`prometheus.io/scrape: "true"`）的 pod 加进采集列表。这样新扩容的 pod 不用改任何配置，几秒内就被采集到。

**Q：日志放 MySQL 不会扛不住吗？为什么不用 ELK 或 ClickHouse？**
> 当前每天十几万条，MySQL 完全够用，团队都熟、运维成本低、故障时也能直接 SQL 查。技术选型看场景不是越新越好。我们做了**冷热分离**和**字段准入评审**控制存储增长（详见 [踩坑指南 坑 6](./10-1-全链路可观测-常见踩坑点与避坑指南.md#-坑-6结构化日志字段膨胀--写入性能拖垮)），到了真扛不住的那天再切 ClickHouse 也不晚。

## 2. 状态机与故障回滚

**Q：你们是怎么把线上故障平均恢复时间压缩到 30 分钟的？状态机和一键回滚是怎么设计的？**

**我的回答：**

核心就是两个东西：**灰度发布状态机** + **一键回滚安全闸**。

状态机分五个阶段：phase1 基线 → internal 内部验证 → small_flow 金丝雀 → batch 批量 → full 全量。每个阶段之间不能跳，必须一步一步来，而且每个阶段都有指标门禁——错误率、P95、空结果率这三个指标超过基线阈值就卡着不让往下走。

一键回滚做的是**内存级 runtime override**：值班同学调用 `POST /api/admin/kb/release/rollback` 接口，全局的 release stage 直接切回 phase1，整个过程不重启服务、毫秒级生效。状态切换用 `sync.RWMutex` 保护，保证不会出现"一半请求走新策略一半走旧策略"的中间态。

**这里我们其实做了一个比较克制的取舍：回滚链路是"告警→人工确认→调接口"，没有做全自动回滚。** Prometheus 单阈值告警（比如 P95 > 2s 持续 10 分钟、错误率 > 3% 持续 5 分钟）触发后，飞书机器人 @值班，值班看一眼监控确认是真故障，再点回滚。

之所以不做自动回滚，主要是两个考虑：一是回滚本身也是一次变更，深夜被自动回滚搞出二次事故的成本更高；二是我们的告警规则虽然窗口够长，但仍可能因为依赖抖动、流量突刺产生误报，让系统自动决策反而更危险。**回滚的目标是"30 分钟止损"，不是"30 秒止损"，留 1-2 分钟给人确认很值得。**

回滚完了不是就完事，会自动比对三个黄金指标有没有回到 phase1 的基线区间，确认真的恢复了再发"故障已恢复"通告。

> 相关代码：[release/controller.go](../../backend/internal/rag/release/controller.go)、告警规则 [rag-l8-alert-rules.yml](../../backend/deploy/monitoring/prometheus/rag-l8-alert-rules.yml)

### 🔍 深挖追问兜底

**Q：runtime override 不重启就能生效，是怎么实现的？**
> 全局变量 + `sync.RWMutex`。读路径（每个请求判断走哪个 stage）拿读锁，几乎无竞争；写路径（回滚接口）拿写锁，原子替换整个 override 结构体。配合 Go 的内存模型，写完锁释放后，所有后续请求看到的就是新值。

**Q：那进程重启 override 不就丢了吗？**
> 是的，所以 override 同时会落一份到配置中心/DB，进程启动时会先去拉一次最新 override。这块属于"持久化兜底"，纯内存只是为了快。

**Q：为什么不做全自动回滚？业内不是都在推自愈吗？**
> 我们评估过，自愈适合"明确可枚举的故障模式"，比如 pod OOM 自动重启。但灰度发布期间的指标异常成因太复杂——可能是策略真的差，可能是上游抖动，也可能是采样偏差。让程序替人做"要不要回滚"的决策风险太高。我们做的是**降低人决策成本**：告警里直接附 Grafana 链接和回滚命令，值班 30 秒内就能拍板。

## 3. Histogram 分桶与 SLA

**Q：Histogram 的分桶你们是怎么设计的？为什么 P95 是 2.5s 而不是其他值？**

**我的回答：**

2.5s 这个目标是**倒推**出来的——用户能接受的 RAG 端到端延迟大概是 5s，检索占一半，LLM 生成占一半，所以检索这边定 P95 在 2.5s 内。

分桶设计上，我们没用 Prometheus 默认分桶，而是做了自定义：

```
0.01, 0.025, 0.05, 0.1, 0.2, 0.35, 0.5, 0.75, 1, 1.5, 2, 3, 5, 8
```

关键是**在 SLA 阈值附近加密**——1-3s 这个区间放了 1、1.5、2、3 四个桶，把 P95 估算误差控制在 5% 以内。这个事我们之前踩过坑，**详见 [踩坑指南 坑 2](./10-1-全链路可观测-常见踩坑点与避坑指南.md#-坑-2histogram-分桶太粗--p95-严重失真)**。

分桶不是一劳永逸的，业务变化了就要调。比如加了稀疏检索之后，我们就把检索路由层的分桶也调细了。

### 🔍 深挖追问兜底

**Q：`histogram_quantile` 这个函数的估算原理是什么？为什么会有误差？**
> 它假设**每个 bucket 内部数据是均匀分布的**，然后做线性插值。比如 P95 落在 [1, 2.5] 这个桶里，桶里有 100 个样本，要找第 95 个样本的位置，就在 1 和 2.5 之间按比例插值。如果桶很宽（比如 1-2.5 之间没有中间桶），桶内分布又不均匀（比如实际都堆在 2.0 附近），插值出来的 P95 就会偏。所以解决办法是**在关注的区间加密分桶**。

**Q：Histogram 和 Summary 怎么选？**
> Summary 在客户端就算好分位数，准但**不能跨实例聚合**——每个 pod 算自己的 P95，没法合并成全局 P95。Histogram 是上报每个桶的计数，服务端聚合后再算分位数，**支持多实例聚合但有估算误差**。我们选 Histogram 主要因为多 pod 场景下需要全局视图。

**Q：你们的桶数量是 14 个，会不会指标基数太多？**
> 单个 metric 14 个桶不算多，每个桶是一个时间序列。真正的基数风险来自**标签**而不是桶（详见 [踩坑指南 坑 3](./10-1-全链路可观测-常见踩坑点与避坑指南.md#-坑-3标签基数爆炸--prometheus-直接-oom)）。我们的标签都是可枚举的，整体序列数是可控的。

## 4. 灰度发布与流量控制

**Q：灰度发布的流量控制是怎么做的？为什么用 userID 哈希？如何避免哈希偏斜？**

**我的回答：**

我们的实现其实挺朴素的，就是 **`FNV-1a(userID) % 100`** 算出一个 0-99 的桶号，再跟当前 stage 的放量比例（比如 small_flow 是 5、batch 是 25）做比较，小于阈值就走新策略。

用 userID 而不是 requestID，主要是为了保证**同一个用户的体验一致**——不会一会儿新策略一会儿旧策略，对用户来说体验是稳定的，对我们排查问题也方便（同一个 userID 的所有请求要么全在 phase1 要么全在 phase2，日志好对齐）。

内部用户单独走一条路：在哈希分桶之前先判断 `internal_role` 和 `user_allowlist`，命中的直接进 phase2，不走哈希。这样可以让自己人先踩坑，而且内部用户反馈快、能描述清楚问题。

**关于哈希偏斜，老实讲我们当前规模下还没碰到严重问题。** 每天检索请求十几万量级，活跃用户分布相对均匀，从历史数据看各个百分位桶的实际流量比例和理论值基本吻合。所以**目前没专门做偏斜监控和自动 rebalance**，遇到偏斜的处理方式是手动调整 `canary_percent` 和 `user_allowlist`。

但这是个已知的"未来要还的债"。如果业务量再涨一个数量级，或者出现明显的头部用户（比如某个大客户占了 30% 流量），现在的方案肯定扛不住，我们想过两个方向：

1. **分层抽样**：把活跃用户、沉睡用户分开做哈希，每层独立放量，避免活跃用户全堆到一个桶里
2. **按 tenant 维度分桶**：to B 场景下按租户分而不是按用户分，颗粒度更合适

引用具体代码：[release/controller.go#L233-243](../../backend/internal/rag/release/controller.go#L233-243)。

### 🔍 深挖追问兜底

**Q：为什么用 FNV-1a 不用 MurmurHash 或者 xxhash？**
> FNV-1a 在 Go 标准库里就有（`hash/fnv`），零依赖、计算快、对小输入（userID 是 uint）的分布质量足够。MurmurHash 和 xxhash 在大输入场景下质量更好，但对我们这个场景属于过度设计。

**Q：内部用户不进哈希桶，会不会导致内部用户多的时候 phase2 实际流量超出 canary_percent？**
> 会，所以我们的 `canary_percent` 是针对"外部用户"算的。内部用户走另一条统计口径，不计入金丝雀比例。监控面板上 phase2 的总流量 = 外部金丝雀流量 + 内部用户流量，分开看。

**Q：换 stage 的时候，原本被哈希到 phase2 的用户会不会突然被踢回 phase1？**
> 不会。因为哈希值只跟 userID 有关，是稳定的；切 stage 只是改"放量比例"这个阈值。比如从 small_flow（5%）升到 batch（25%），原本桶号 0-4 的用户继续在 phase2，新增 5-24 桶的用户加入。**只升不降**是这个设计的隐含保证。

## 5. 告警规则与信噪比

**Q：告警规则为什么用 5 分钟窗口而不是 1 分钟？怎么避免告警风暴？**

**我的回答：**

简单说就是——**告警的第一要务不是"早"，而是"准"**。1 分钟窗口我们踩过大坑，详细故事 [踩坑指南 坑 1](./10-1-全链路可观测-常见踩坑点与避坑指南.md#-坑-1告警太灵敏--狼来了效应) 里写了。

现在的规则是 **5 分钟窗口 + 5 分钟 `for` 持续时间**，异常持续 5 分钟才告警，把瞬时抖动都过滤掉。宁可比实际故障晚发现 3 分钟，也不能让团队对告警麻木。

避免告警风暴主要做了三件事：
1. **分级**：P1 才 @所有人电话呼叫，P2 普通群消息，P3 邮件即可
2. **聚合**：同类告警在 Alertmanager 里 group 起来，1 分钟内的同 group 告警合并成一条发
3. **抑制**：上游服务挂了直接抑制下游所有告警，避免几百条级联告警刷屏

每条告警必须写清楚**排查步骤**和 **Grafana 链接**，不然新人收到根本不知道怎么处理。每周例会复盘上周的告警，没人处理过的告警要么调阈值要么删掉，把信噪比作为核心 KPI 来运营。

### 🔍 深挖追问兜底

**Q：Alertmanager 的告警聚合（group）和抑制（inhibit）有什么区别？**
> **group** 是把"相似"的告警合并成一条（按 alertname、cluster 等维度），主要解决"刷屏"问题；**inhibit** 是当 A 告警在响时，自动屏蔽 B 告警（比如机器宕机告警在响时，屏蔽该机器上所有服务告警），主要解决"级联误报"问题。两个机制叠加才能把告警风暴压下去。

**Q：那静默（silence）又是什么？**
> silence 是**人工临时屏蔽**某条告警，比如计划内的发布、压测期间，运维提前点 silence 避免告警吵人。和 inhibit 的区别是：inhibit 由规则自动触发，silence 由人手动触发并且有时效。

**Q：5 分钟窗口意味着真故障要晚 5 分钟才告警，这不会拉长 MTTR 吗？**
> 会拉长"发现时间"，但**不会拉长 MTTR**。因为之前 1 分钟窗口的时代，告警来了大家本能性以为是误报，实际响应反而要 10-20 分钟。现在 5 分钟窗口看起来晚，但告警一响大家立刻就动，端到端反而更快。这就是"信噪比比绝对速度更重要"的核心逻辑。

## 6. 线上排障实战

**Q：线上 P95 突然飙升，你怎么排查？**

**我的回答：**

我有个固定的排查套路，核心是先定范围再找根因。

第一步先花 30 秒看全局：Grafana 总览面板，QPS 是不是突增了？错误率有没有同步上升吗？是只有 P95 高还是 P50 也高？最近 15 分钟有没有发布？——先搞清楚问题多大，影响了多少人。

第二步花 2 分钟下钻：如果 P50 也高，那就是整体问题，先看 Milvus 健康不健康，Redis 卡不卡；如果只有 P95 高，那就是长尾，按维度下钻——按 release_stage 看是不是灰度的问题，按 route 看是 dense 还是 sparse 的问题，按 strategy 看是不是某个策略的锅。

第三步花 5 分钟找具体根因：抓几个慢请求的 requestID，去查结构化日志里的 Debug Trace，看每个阶段的耗时，到底是 embedding 慢、向量检索慢、还是重排慢。

最后是止损优先，能回滚就先回滚，回滚完了再慢慢查原因。别死磕根因结果故障扩大了，那就得不偿失了。

**但回滚之前必须先保留现场**——抓几个慢请求的完整日志、dump 一份 Debug Trace 样本、记一下当时的 P95/QPS 截图。否则回滚之后服务恢复了，根因也跟着消失了，下次还会再踩。

### 🔍 深挖追问兜底

**Q：怎么定义"慢请求"去抓样本？**
> 我们的结构化日志里每条记录都打了总耗时，排障时直接 `SELECT * FROM rag_logs WHERE created_at > now() - 5min AND total_cost_ms > 2000 ORDER BY total_cost_ms DESC LIMIT 20`，捞出来 Top 20 慢请求，再用 requestID 去查它们的完整 Debug Trace 看哪个阶段慢。

**Q：如果是间歇性偶发慢，监控上看不出来怎么排？**
> 这种最难。我们的做法是**在 Debug Trace 里开"慢请求 100% 采样"**——正常请求不采样，但只要某个请求总耗时超过阈值（比如 1.5s），就强制把它的 Debug Trace 完整存下来。这样间歇性慢请求不会被采样漏掉。

**Q：回滚不能解决问题怎么办？**
> 那说明不是新版本引入的问题，是底层依赖（Milvus、Redis、嵌入服务）出了问题。这时候排查路径变成"按依赖分层查"：先看 Milvus 健康指标，再看 Redis 慢查询，再看嵌入服务的 P95，最快锁定是哪一层的问题，再针对性扩容或限流。
