# AI 智能面试平台 - 项目架构与目录结构说明

## 1. 架构设计理念

### 1.1 企业级 Go 标准布局 (Standard Go Project Layout)
本项目严格遵循 Go 社区主流的工程结构标准（[golang-standards/project-layout](https://github.com/golang-standards/project-layout)），摒弃了简单的 MVC 模式，采用了更适合中大型微服务项目的分层架构。这种结构在字节跳动、Uber 等大厂的 Go 项目中广泛应用，能够支撑项目从原型快速演进到大规模生产环境。

### 1.2 领域驱动设计 (DDD) 落地
我们将业务逻辑拆分为不同的领域（Domain），并严格区分了**接口层**、**应用服务层**、**领域层**和**基础设施层**，确保关注点分离（Separation of Concerns）。

*   **接口层 (`api`)**: 负责对外暴露 HTTP 接口，处理参数校验、协议解析和响应格式化。**它不包含核心业务逻辑**，仅作为外界进入系统的“门户”。
*   **应用/领域层 (`internal/service`, `internal/agents`)**: 系统的“大脑”。
    *   `service`: 承载传统的确定性业务逻辑（如用户管理、面试状态流转）。
    *   `agents`: 承载 AI 相关的概率性业务逻辑（如简历分析、智能问答编排）。
*   **基础设施层 (`internal/repository`, `internal/mq`, `internal/milvus`)**: 提供数据库、缓存、消息队列、向量检索等底层技术支持，为上层业务提供稳定的“地基”。

### 1.3 高内聚与安全性
通过大量使用 `internal` 目录，我们利用 Go 语言特性强制隔离了私有代码。这意味着 `backend/internal` 下的代码只能被本项目内部引用，无法被外部项目导入。这不仅防止了业务逻辑的意外泄露和耦合，也为未来可能的微服务拆分划定了清晰的边界。

## 2. 详细目录结构说明

```text
backend/
├── cmd/                        # 应用程序入口
│   └── server/
│       └── main.go             # 后端服务主入口，负责依赖注入、配置加载和服务启动
├── api/                        # 接口层 (Interface Layer)
│   ├── handler/                # HTTP 请求处理器 (Hertz Handler)
│   │   └── interview/          # 面试相关接口，仅负责“收发信”
│   ├── router/                 # 路由定义
│   └── idl/                    # 接口定义语言 (Thrift/Protobuf)
├── internal/                   # 私有应用代码 (核心业务逻辑)
│   ├── agents/                 # [核心] AI 智能体层 (AI Agents - UseCase)
│   │   ├── interview/          # 专项/综合面试智能体实现
│   │   ├── resume/             # 简历分析智能体
│   │   └── llm/                # 大模型交互封装 (OpenAI/Doubao)
│   ├── service/                # [核心] 领域服务层 (Domain Service)
│   │   ├── interview/engine/   # 面试引擎核心 (状态机、SSE 实时流、调度逻辑)
│   │   └── user/               # 用户服务
│   ├── repository/             # 基础设施层 - 数据持久化 (Repository Pattern)
│   ├── model/                  # 数据实体模型 (GORM Model)
│   ├── config/                 # 配置管理 (支持 YAML + 环境变量注入)
│   ├── milvus/                 # 向量检索模块 (RAG 核心组件)
│   └── mq/                     # 消息队列封装 (Redis/Kafka)
├── pkg/                        # 公共工具库 (Public Library)
├── scripts/                    # 运维与评估脚本 (原 tests 目录)
├── Dockerfile                  # 容器化构建文件
├── docker-compose.yml          # 本地开发环境编排 (MySQL, Redis, Milvus)
└── go.mod                      # 依赖管理 (Module: interview-agents)
```

## 3. 架构优势分析

### 3.1 拒绝“贫血模型”：业务逻辑纯粹化
在架构演进过程中，我们识别到原有的 `api/handler` 层承载了过多的业务逻辑（如状态机流转、SSE 循环），形成了典型的**“贫血模型”反模式 (Anemic Domain Model)** —— 即领域对象仅为数据容器，而业务逻辑被挤压在传输层。

为了解决这一 **Code Smell**，我们将 **面试引擎 (`InterviewEngine`)** 彻底下沉至 `internal/service/interview/engine`。
*   **职责单一**: Handler 层回归其“门户”本职，仅负责 HTTP 协议适配、参数绑定与响应格式化。
*   **逻辑闭环**: 复杂的面试状态管理、超时控制、SSE 推送逻辑在 Service 层内部闭环，不再依赖 HTTP 上下文。
*   **可测试性**: 核心引擎逻辑现在可以脱离 Web 框架进行独立的单元测试，大大提升了系统的健壮性。

### 3.2 消除“公共库”歧义：核心能力内聚化
原有的 `agents` 目录位于项目根路径，容易被误认为是可供外部调用的**公共库 (Public Library)**，这违背了模块化设计中**“默认隐藏”**的原则。

我们将 AI 相关的核心逻辑移入 `internal/agents` 目录：
*   **强制封装**: 利用 Go 语言的 `internal` 机制，从编译器层面禁止外部项目引用这些核心 AI 逻辑，确保了核心资产的私有性。
*   **物理隔离**: 将概率性的 AI 业务（Prompt Engineering、LLM Chain）与确定性的 CRUD 业务在物理目录上分离，使得 AI 工程师可以专注于智能体的迭代，而不必担心破坏核心交易链路。

### 3.3 极致的配置灵活性 (12-Factor App)
项目配置系统 (`config.yaml` + `config.go`) 经过改造，全面支持**环境变量注入**。
*   **优势**: 实现了 "Build Once, Run Anywhere"。在 Docker、K8s 或本地开发环境中，无需修改代码或配置文件，只需通过环境变量（如 `DB_HOST`, `OPENAI_API_KEY`）即可动态调整应用行为。这是云原生应用的最佳实践。

### 3.4 主流技术栈的深度整合
*   **Web 框架**: **CloudWeGo Hertz** —— 字节跳动内部主流的高性能 HTTP 框架，专为微服务设计。
*   **AI 框架**: **CloudWeGo Eino** —— 专为 LLM 应用开发设计的框架，提供了强大的编排和治理能力。
*   **工程化**: 完整的 Docker/Compose 支持，开箱即用的全栈开发环境（包含 Milvus, MinIO, Etcd 等复杂依赖的编排）。

## 4. 总结
当前的架构不仅仅是一个代码仓库的组织形式，更是**高并发 AI 应用**的最佳实践落地。它既保留了 Go 语言简单直接的特性，又引入了企业级开发所需的规范性、扩展性和安全性。无论是应对复杂的面试流程控制，还是灵活接入各种大模型，这套架构都能提供坚实的支撑，完全具备了走向 Production 的能力。
