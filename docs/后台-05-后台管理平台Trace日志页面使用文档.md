# 后台管理平台 Trace 日志页面使用文档

## 背景

这篇文档用于帮助用户和开发学习者快速上手后台管理平台里的“Trace 日志”功能。

这里的“Trace 日志页面”实际包含两层页面：

1. 检索日志页：`/trace-logs/retrieval`
2. 入库日志页：`/trace-logs/ingest`

另外，`/trace-logs` 会自动跳转到 `/trace-logs/retrieval`。

这两个页面共同组成了知识库链路里的日志与排障入口：

1. 检索日志页回答“这次检索请求发生了什么、为什么空结果、为什么慢、为什么报错”。
2. 入库日志页回答“这次入库任务走到哪一步、为什么失败、有没有被人工操作过”。

它们和知识库详情页形成互补关系。知识库详情页更偏“操作入口”，Trace 日志页更偏“排障入口”和“审计入口”。

## 这篇文档会做什么

看完这篇文档，你应该能理解下面几件事：

1. 检索日志页和入库日志页分别解决什么问题。
2. 两个页面的筛选区、列表区、详情抽屉应该怎么用。
3. 页面上的关键字段分别代表什么含义。
4. 这些页面依赖了哪些后端接口，查询参数和返回结构是什么。
5. 当前实现里有哪些限制，哪些行为需要提前对齐使用预期。

## 需要先理解的术语

### Trace 日志

这里的 Trace 日志可以理解成“系统把一次关键链路执行过程结构化记录下来”。  
它不是普通的文本日志，而是可以被页面筛选、列表展示、详情展开的结构化数据。

### 检索日志

检索日志记录的是一次知识库检索请求。  
它关心的问题包括：

1. 用户查了什么 `query`
2. 命中了哪些知识库 `kb_ids`
3. 最终返回了多少条结果 `final_count`
4. 这次请求是成功、无结果、被过滤、报错还是超时
5. 每个阶段耗时多少毫秒

### 入库日志

入库日志记录的是一次文档入库任务。  
它关心的问题包括：

1. 哪个知识库 `kb_id`
2. 哪个文档 `document_id`
3. 当前任务状态是什么
4. 最近一次错误码和错误详情是什么
5. 有没有发生过人工重试、取消等操作

### 结果状态

检索日志页里的 `result_status` 用来概括一次检索的最终结果。当前页面支持的状态有：

1. `success`：成功返回结果
2. `no_result`：没有检索到结果
3. `filtered_out`：候选结果被后处理过滤掉
4. `error`：请求执行失败
5. `timeout`：请求超时

### 任务状态

入库日志页里的 `status` 表示入库任务状态。当前页面支持的状态有：

1. `pending`：已创建，等待处理
2. `processing`：正在处理
3. `completed`：处理完成
4. `failed`：处理失败
5. `retrying`：正在重试或准备重试
6. `dead`：多次失败后进入不可自动恢复状态
7. `canceled`：被人工取消

### 操作审计

操作审计记录的是“谁在什么时候，把任务从什么状态改到了什么状态”。  
它主要服务两个场景：

1. 追踪人工干预，比如重试、取消
2. 回看状态机是否发生了符合预期的流转

### Contract gap

如果某个字段在前端预期里应该存在，但当前返回值是空，页面会显示 `Contract gap`。  
它更像“接口合同提醒”，不是业务值，也不一定代表系统出错。

### P3 摘要

检索详情抽屉里有一组和高级检索策略相关的补充字段，例如：

1. `parent_child_enabled`
2. `topk_policy_version`
3. `evidence_gate_result`
4. `citation_support_score`
5. `refusal_reason`

如果这些字段都没有返回，页面会提示当前请求暂时没有 P3 摘要字段。

## 整体流程

从一次请求或任务产生，到用户在后台里排查问题，主流程通常是这样的：

1. 用户在知识库页面上传文档，系统创建入库任务。
2. 入库任务持续更新状态，并可能产生人工操作审计记录。
3. 用户在业务侧或实验室发起检索请求，系统记录一条检索日志。
4. 后台管理页面按知识库、状态、时间范围等条件拉取日志列表。
5. 用户在列表里找到目标记录，打开详情抽屉查看完整字段。
6. 如果是检索问题，可以继续跳到调试视图查看更细的检索链路。
7. 如果是入库问题，可以通过任务详情和操作审计判断是系统失败还是人工干预导致。

这条链路的核心价值不是“看日志”本身，而是把检索链路和入库链路都做成了可筛选、可追踪、可回看的后台运维界面。

## 页面定位与项目亮点

Trace 日志页面在整个后台里主要承担三个角色：

1. 排障入口：快速定位慢请求、空结果、失败任务。
2. 审计入口：回看任务是否被人工重试、取消，以及状态怎样流转。
3. 关联入口：从日志进一步跳到检索调试视图，或者回到知识库上下文继续排查。

对用户来说，它回答的是“为什么这次没结果、为什么这次失败、是谁改了这个任务状态”。

对开发和运维来说，它回答的是“前端能看到哪些结构化字段、这些字段怎么和后端接口对齐、哪些数据隔离和合同能力还不完整”。

## 页面使用说明

## 检索日志页面

### 页面入口

检索日志页路由和组件文件是：

1. `admin/src/app/(admin)/trace-logs/retrieval/page.tsx`
2. `admin/src/components/admin/retrieval-logs-page.tsx`

页面地址是：`/trace-logs/retrieval`

### 页面作用

检索日志页主要做四件事：

1. 按知识库、结果状态、请求 ID、关键词、时间范围筛选检索日志。
2. 展示一次检索请求的核心摘要信息。
3. 打开详情抽屉查看阶段耗时、路由信息、错误信息和 P3 摘要。
4. 从列表跳到调试视图，继续看更细粒度的检索链路。

### 筛选区说明

筛选区支持下面几个条件：

| 字段 | 含义 | 使用建议 |
| --- | --- | --- |
| 知识库 | 只看某个知识库相关的检索日志 | 默认会优先带上当前选中的知识库 |
| 状态 | 只看某种 `result_status` | 排查空结果时优先看 `no_result` 或 `filtered_out` |
| Request ID | 精确定位单次请求 | 已知请求号时最有效 |
| Query 关键词 | 对原始 `query` 做模糊匹配 | 适合不知道请求号，只记得关键词的场景 |
| 时间范围 | 限定日志产生时间 | 适合缩小排查窗口 |

这里有两个实现细节需要注意：

1. 页面初次进入时，会优先读取 URL 里的 `request_id`、`kb_id`、`result_status`，并回填到表单。
2. 如果 URL 没有传 `kb_id`，页面会默认使用当前知识库上下文里的 `selectedBase`。

### 顶部按钮说明

检索日志页右上角有一个 `刷新` 按钮。

它的作用是：

1. 保持当前筛选条件不变
2. 重新请求当前页数据

### 列表区说明

检索日志表格按页展示数据，前端每页请求 `20` 条。当前主要列如下：

| 列名 | 含义 | 说明 |
| --- | --- | --- |
| Query | 原始查询文本 | 过长时省略显示 |
| Request ID | 请求唯一标识 | 详情和调试视图都依赖它 |
| KB | 命中的知识库 ID 集合 | 当前直接显示后端返回的 `kb_ids` 字符串 |
| Top K | 请求的目标召回数量 | 属于检索参数摘要 |
| Final | 最终返回条数 | 用于判断空结果或强过滤 |
| Duration | 总耗时 | 单位为毫秒 |
| Status | 本次请求结果状态 | 颜色标签区分成功、超时、错误等 |
| Created | 创建时间 | 用于定位时间窗口 |
| 操作 | 当前提供“调试视图”按钮 | 进入更细的检索调试页 |

#### 列表如何使用

建议按下面顺序排查：

1. 先看 `Status`，判断是成功、空结果、报错还是超时。
2. 再看 `Final` 和 `Duration`，判断是结果数量异常还是耗时异常。
3. 如果已经知道具体请求，直接按 `Request ID` 精确查找。
4. 如果只记得用户问了什么，可以先用 `Query 关键词` 缩小范围。
5. 找到目标行后，点击整行打开详情抽屉。

#### 调试视图按钮

表格最后一列提供 `调试视图` 按钮。

点击后会跳转到：

`/retrieval-lab/debug?request_id={request_id}`

这个入口适合在“列表摘要和详情抽屉还不够用”时继续深挖，例如：

1. 看具体命中的文档
2. 看融合前后结果
3. 看重排和过滤前后的变化

### 详情抽屉说明

点击列表任意一行，会打开检索详情抽屉。抽屉按四组信息展示。

#### 一，请求信息

这一组主要回答“这次请求到底是怎么发出去的”。字段包括：

1. `Request ID`
2. `KB IDs`
3. `Query`
4. `Final Query`
5. `Expr`
6. `Top K`
7. `Candidate Top K`
8. `Final Top K`

其中最值得优先看的三个字段是：

1. `Query`：原始用户输入
2. `Final Query`：最终真正参与检索的查询
3. `Expr`：后端拼出来的检索表达式

#### 二，阶段耗时

这一组主要回答“慢到底慢在哪一步”。字段包括：

1. `Embedding`
2. `Search`
3. `Postprocess`
4. `Rerank`
5. `Duration`

如果 `Duration` 很高，通常先对比：

1. 是向量化慢
2. 是检索慢
3. 还是重排和后处理慢

#### 三，结果与路由

这一组主要回答“系统是怎么命中结果的，以及为什么最后结果这么多或这么少”。字段包括：

1. `Routes`
2. `Collection`
3. `Retriever`
4. `Result Status`
5. `Final Count`
6. `Truncated Count`
7. `Dense Hits`
8. `Sparse Hits`
9. `Dense Contribution`
10. `Sparse Contribution`

这组字段很适合判断：

1. 是否命中了预期检索路由
2. 稠密召回和稀疏召回谁贡献更多
3. 是否因为截断或过滤导致最终结果偏少

#### 四，错误与补充信息

这一组主要回答“为什么失败、为什么拒答、为什么没有结果”。字段包括：

1. `P3 摘要`
2. `Error Code`
3. `Error Message`
4. `Strategy`
5. `Release Stage`
6. `Release Reason`
7. `Empty Reason`
8. `Created At`

如果抽屉顶部出现“该请求暂时没有 P3 摘要字段”的提示，说明当前仍可看基础 trace，但这次日志没有返回高级策略相关字段。

#### 检索详情的典型排查方法

1. 空结果先看 `Result Status`、`Empty Reason`、`Final Count`。
2. 慢请求先看阶段耗时，确认是 `Embedding`、`Search` 还是 `Rerank` 拉高了总耗时。
3. 命中异常先看 `Routes`、`Dense Hits`、`Sparse Hits` 和贡献度。
4. 高级策略问题再看 `P3 摘要` 里的 `evidence_gate_result`、`citation_support_score`、`refusal_reason`。

## 入库日志页面

### 页面入口

入库日志页路由和组件文件是：

1. `admin/src/app/(admin)/trace-logs/ingest/page.tsx`
2. `admin/src/components/admin/ingest-logs-page.tsx`

页面地址是：`/trace-logs/ingest`

### 页面作用

入库日志页主要做四件事：

1. 按知识库、任务状态、错误码、时间范围筛选入库任务。
2. 查看每个任务的最新状态摘要。
3. 打开详情抽屉查看完整任务信息。
4. 查看操作审计记录，判断是否有人工重试、取消等行为。

### 筛选区说明

筛选区支持下面几个条件：

| 字段 | 含义 | 使用建议 |
| --- | --- | --- |
| 知识库 | 只看某个知识库的任务 | 默认会优先带上当前选中的知识库 |
| 状态 | 只看某种任务状态 | 排查失败时先看 `failed`、`dead` |
| 错误类型 | 按 `error_code` 过滤 | 适合同类错误集中排查 |
| 时间范围 | 限定任务创建时间 | 适合缩小排查窗口 |

当前前端把“错误类型”下拉写死成了三个常见值：

1. `embedding_failed`
2. `milvus_error`
3. `canceled_by_operator`

这意味着页面支持的筛选值并不等于后端全部错误码集合，后面在“当前限制”里会再强调这一点。

### 顶部按钮说明

入库日志页右上角也有一个 `刷新` 按钮。

它的作用是：

1. 保持当前筛选条件不变
2. 重新请求当前页数据

### 列表区说明

入库日志表格同样按页展示数据，前端每页请求 `20` 条。当前主要列如下：

| 列名 | 含义 | 说明 |
| --- | --- | --- |
| Job ID | 任务主键 | 用于排障和接口详情查询 |
| KB | 任务所属知识库 ID | 用来确认知识库上下文 |
| Document | 任务所属文档 ID | 可和文档或知识库详情页联动排查 |
| Status | 当前任务状态 | 颜色标签区分处理中、失败、完成等 |
| Error Code | 最近一次错误码 | 空值显示 `-` |
| Operation | 最近一次操作 | 例如重试、取消 |
| Reason | 最近一次操作原因 | 过长时省略显示 |
| Created | 任务创建时间 | 用于定位时间窗口 |

#### 列表如何使用

建议按下面顺序排查：

1. 先按 `Status` 找到失败、重试中或已取消的任务。
2. 再看 `Error Code`，判断是系统失败还是人工取消。
3. 如果要确认有没有人动过这个任务，看 `Operation` 和 `Reason`。
4. 点击整行打开详情抽屉，查看完整任务信息和审计日志。

### 详情抽屉说明

点击列表任意一行，会打开入库详情抽屉。抽屉分两块内容。

#### 一，任务信息

这一组主要回答“任务现在是什么状态、最近发生了什么”。字段包括：

1. `Job ID`
2. `KB ID`
3. `Document ID`
4. `Status`
5. `Retry Count`
6. `Error Code`
7. `Error Detail`
8. `Operation`
9. `Operation Reason`
10. `Operated At`

这里的理解重点是：

1. `Error Code` 适合用来归类问题
2. `Error Detail` 适合看这一次的具体失败描述
3. `Operation` 和 `Operation Reason` 表示最近一次操作摘要
4. `Operated At` 表示最近一次操作时间，不等于任务创建时间

#### 二，操作审计记录

详情抽屉下方有一张“操作审计记录”表。

这张表不是只看当前状态，而是回看整条人工操作历史。当前字段包括：

1. 时间
2. 操作人
3. 操作
4. 状态流转
5. 原因

其中最关键的是 `状态流转`，格式是：

`from_status -> to_status`

它能直接告诉你：

1. 这次操作前任务处于什么状态
2. 操作后任务变成了什么状态

#### 入库详情的典型排查方法

1. 任务失败先看 `Status`、`Error Code`、`Error Detail`。
2. 怀疑有人手动改过任务时，看 `Operation`、`Operation Reason` 和操作审计记录。
3. 如果任务被取消，优先确认是否出现 `canceled_by_operator` 以及对应的操作人和操作时间。

### 入库日志字段

| 字段 | 所在位置 | 含义 |
| --- | --- | --- |
| `id` | 列表、详情 | 入库任务主键，也就是 Job ID |
| `kb_id` | 列表、详情 | 任务所属知识库 ID |
| `document_id` | 列表、详情 | 任务所属文档 ID |
| `status` | 列表、详情 | 当前任务状态 |
| `retry_count` | 详情 | 当前任务已重试次数 |
| `last_error_code` | 列表、详情 | 最近一次错误码 |
| `last_error_detail` | 详情 | 最近一次错误详情 |
| `operation` | 列表、详情 | 最近一次操作摘要 |
| `operation_reason` | 列表、详情 | 最近一次操作原因 |
| `operated_at` | 详情 | 最近一次操作发生时间 |
| `created_at` | 列表 | 任务创建时间 |
| `started_at` | 数据模型中存在 | 任务开始处理时间，当前列表页未展示 |
| `finished_at` | 数据模型中存在 | 任务结束时间，当前列表页未展示 |
| `operator_id` | 审计表 | 执行该次操作的用户 ID |
| `from_status` | 审计表 | 这次操作前的状态 |
| `to_status` | 审计表 | 这次操作后的状态 |

### 检索日志列表接口说明

接口：`GET /api/admin/kb/retrieve/audit`

支持的查询参数有：

| 参数 | 是否必填 | 含义 |
| --- | --- | --- |
| `page` | 否 | 页码，默认 `1` |
| `page_size` | 否 | 每页大小，后端默认 `10`，前端当前传 `20` |
| `kb_id` | 否 | 按知识库过滤 |
| `result_status` | 否 | 按结果状态过滤 |
| `request_id` | 否 | 按请求 ID 精确查找 |
| `query_keyword` | 否 | 按查询文本模糊匹配 |
| `start_time` | 否 | 起始时间，要求 RFC3339 格式 |
| `end_time` | 否 | 结束时间，要求 RFC3339 格式 |

返回结构是标准分页对象：

| 字段 | 含义 |
| --- | --- |
| `items` | 当前页日志数组 |
| `total` | 总数 |
| `page` | 当前页码 |
| `page_size` | 当前页大小 |

实现细节有两个值得注意：

1. 这个接口会校验登录态。
2. 列表查询会把当前登录用户的 `user_id` 作为过滤条件之一。

### 检索日志详情接口说明

接口：`GET /api/admin/kb/retrieve/audit/{request_id}`

这个接口直接按 `request_id` 返回单条检索日志详情，前端抽屉展示的字段基本都来自这里。

返回重点包括：

1. 请求摘要字段
2. 各阶段耗时
3. 路由和贡献度信息
4. 错误信息
5. P3 摘要字段

如果 `request_id` 为空，后端会返回 `400`。  
如果查不到记录，后端会返回 `404`。

### 检索调试视图接口说明

接口：`GET /api/admin/kb/retrieve/audit/{request_id}/debug`

这个接口不是当前页面主抽屉的一部分，但列表里的“调试视图”按钮会间接依赖它。  
它适合在下面这些场景继续深挖：

1. 想看具体命中的文档和 chunk
2. 想看重排、融合、去重、过滤前后的结果变化
3. 想看更多 `contract_gaps`

### 入库日志列表接口说明

接口：`GET /api/admin/kb/logs/ingest`

支持的查询参数有：

| 参数 | 是否必填 | 含义 |
| --- | --- | --- |
| `page` | 否 | 页码，默认 `1` |
| `page_size` | 否 | 每页大小，后端默认 `10`，前端当前传 `20` |
| `kb_id` | 否 | 按知识库过滤 |
| `status` | 否 | 按任务状态过滤 |
| `error_code` | 否 | 按最近一次错误码过滤 |
| `start_time` | 否 | 起始时间，要求 RFC3339 格式 |
| `end_time` | 否 | 结束时间，要求 RFC3339 格式 |

返回结构同样是标准分页对象：

| 字段 | 含义 |
| --- | --- |
| `items` | 当前页任务数组 |
| `total` | 总数 |
| `page` | 当前页码 |
| `page_size` | 当前页大小 |

实现细节有两个值得注意：

1. 这个接口会校验登录态。
2. 它当前没有像检索日志列表那样显式带上 `user_id` 过滤条件。

### 入库日志详情接口说明

接口：`GET /api/admin/kb/logs/ingest/{job_id}`

这个接口返回两部分：

1. `job`：当前任务的完整信息
2. `operation_logs`：这条任务的操作审计记录

其中 `operation_logs` 里的每条记录至少包含：

1. `operator_id`
2. `operation`
3. `from_status`
4. `to_status`
5. `operation_reason`
6. `created_at`

这也是为什么入库日志详情抽屉能同时展示“最新任务摘要”和“完整人工操作历史”。

### 参数校验和错误规则

这两类列表接口在后端都有一些共同校验规则：

1. 如果时间格式不是 RFC3339，会返回 `400`。
2. 如果 `start_time` 晚于 `end_time`，会返回 `400`。
3. 如果状态值不在允许集合内，会返回 `400`。
4. 如果没有登录态，会返回 `401`。

## 当前限制

这部分很重要，因为它直接关系到用户培训、排障预期和后续迭代方向。

### 限制一：检索日志页只把部分筛选条件同步到 URL

当前检索日志页只会把下面三个条件写回地址栏：

1. `request_id`
2. `kb_id`
3. `result_status`

这意味着下面两个条件不会被 URL 保留：

1. `query_keyword`
2. 时间范围

所以如果你刷新页面或复制链接给别人，这两个条件不会自动恢复。

### 限制二：入库日志页当前不做 URL 同步

入库日志页的筛选条件只保存在页面状态里，没有同步到地址栏。

这意味着：

1. 刷新页面后筛选会丢失
2. 不能直接分享一个“带筛选条件的入库日志链接”

### 限制三：入库日志页的错误码筛选选项不是完整枚举

前端错误类型下拉只内置了三个值：

1. `embedding_failed`
2. `milvus_error`
3. `canceled_by_operator`

但后端接口实际支持传任意 `error_code` 作为过滤条件。  
也就是说，页面当前暴露的是“常见错误码子集”，不是完整错误码全集。

### 限制四：两个日志页都是只读观察页，不直接提供任务操作按钮

当前这两个页面的职责是查看和审计，不是执行重试、取消等运维动作。

这意味着：

1. 检索日志页没有“重放请求”或“重新检索”按钮
2. 入库日志页没有“重试任务”或“取消任务”按钮

如果需要真正执行任务操作，当前仍然要回到知识库详情页或其他操作入口。

### 限制五：检索详情抽屉展示的是摘要，不是完整调试链路

检索日志详情抽屉已经能看很多字段，但它仍然是“摘要视图”。

如果要看下面这些更细节的内容：

1. 具体命中的文档和 chunk
2. 融合、去重、重排前后的结果集合
3. 更完整的调试 trace

还需要进一步跳到“调试视图”页面。

### 限制六：部分字段可能出现 Contract gap

如果后端没有返回某些扩展字段，前端会显示 `Contract gap` 或空提示。

这通常出现在：

1. 某些补充字段尚未接通
2. 某条旧日志记录生成时还没有这套字段
3. 当前请求或任务本身没有对应值

所以看到 `Contract gap` 时，先理解为“字段暂缺”，不要直接等同于“系统失败”。

### 限制七：当前接口的权限隔离粒度还不完全一致

从当前后端实现看，这组接口主要先校验登录态。

但具体到数据过滤：

1. 检索日志列表接口会带当前登录用户 `user_id` 过滤
2. 入库日志列表接口当前没有显式带 `user_id` 过滤
3. 两类详情接口也没有在 handler 层再做更细的用户范围校验

这说明日志页已经是可用的后台能力，但如果后续要强化多用户隔离和权限边界，这一组接口仍然值得继续收口。

### 限制八：入库日志页没有直接展示开始时间和完成时间

虽然任务数据模型里存在：

1. `started_at`
2. `finished_at`

但当前列表页和详情抽屉都没有把这两个时间完整展示出来。

这会带来一个小影响：

用户可以看到创建时间和最近操作时间，但不能直接在页面里精确判断“任务真正执行了多久、什么时候结束”。

## 如何验证

如果你要验证这篇文档对应的实现，可以按下面方式检查：

1. 打开 `/trace-logs`，确认页面自动跳到 `/trace-logs/retrieval`。
2. 在检索日志页切换知识库、状态、请求 ID、关键词和时间范围，确认列表会重新加载。
3. 点击检索日志任意一行，确认详情抽屉能展示请求信息、阶段耗时、结果与路由、错误与补充信息。
4. 点击检索日志的 `调试视图`，确认能带着 `request_id` 跳到调试页。
5. 打开 `/trace-logs/ingest`，确认默认会带上当前选中的知识库过滤。
6. 在入库日志页按状态、错误码和时间范围筛选，确认列表会重新加载。
7. 点击入库日志任意一行，确认详情抽屉同时展示任务信息和操作审计记录。

## 取舍与后续优化

当前这套 Trace 日志页面已经具备完整的“日志查询 + 详情查看 + 审计回看”主链路，但还有几个很值得继续优化的点：

1. 把检索日志页和入库日志页的筛选条件完整同步到 URL，方便分享和复现。
2. 补全入库日志页的错误码枚举，避免前端筛选项落后于后端真实值集合。
3. 在入库日志页补充 `started_at`、`finished_at` 等更直接的任务时序字段。
4. 进一步明确日志接口的数据隔离和权限边界。
5. 让详情抽屉和调试视图之间的分工更清晰，例如增加一键跳转或更多联动提示。

这篇文档的核心结论可以概括成一句话：

Trace 日志页面真正管理的不是“日志文本本身”，而是“检索请求和入库任务在后台里的可观测性、可追踪性和可审计性”。
