# 9.2.1 统一模型接入层：一套接口对接 OpenAI / DeepSeek / Doubao

在上一节中，我们构建了基于 Redis 滑动窗口的限流机制，解决了多租户场景下的"吵闹邻居"问题。但在限流之前，还有一个更基础的工程问题需要解决：**我们的系统到底应该怎样接入大语言模型？**

在真实的企业环境中，很少有团队只使用单一模型供应商。以我们的面试系统为例，它可能同时需要依赖多个不同的供应商：综合面试环节使用 DeepSeek V3 来追求高性价比，专项深度追问需要 GPT-4o 来保障推理质量，而面向内部团队的场景则可能接入火山引擎的豆包（Doubao）模型来降低延迟与成本。如果为每个供应商都写一套独立的接入代码，整个系统很快就会陷入维护的噩梦。

本节的目标，就是设计一个**统一的模型接入层**，让上层的所有 Agent（无论是 Go 专项面试官、Java 专项面试官还是综合面试官）都通过同一套接口调用底层模型，彻底屏蔽掉不同厂商 SDK 之间的差异。

## OpenAI 兼容协议：AI 行业的"USB 接口"

在深入代码之前，我们需要先理解一个关键的行业背景：**OpenAI 兼容协议已经成为大模型 API 的事实标准**。

当 OpenAI 发布 ChatGPT 并开放 API 时，它定义了一套以 `/v1/chat/completions` 为核心端点的 RESTful 接口规范。这套规范定义了请求体中 `messages`（对话消息列表）、`model`（模型标识）、`temperature`（温度参数）等字段的结构，也统一了响应体中 `choices`（回复列表）和 `usage`（Token 消耗统计）的格式。由于 OpenAI 的先发优势和生态影响力，后来的模型厂商——包括 DeepSeek、火山引擎（Doubao）、Moonshot（Kimi）、通义千问，乃至本地部署的 Ollama——纷纷选择**兼容这套协议**。

这意味着什么？只要一个 HTTP 客户端能够按照 OpenAI 的请求格式发送请求，那么只需**更换 Base URL 和 API Key**，它就可以无缝切换到其他任何兼容供应商。这为我们的统一接入层提供了天然的技术基础。

## Eino 框架的抽象：ToolCallingChatModel 接口

在代码层面，Eino 框架为我们提供了一个名为 `ToolCallingChatModel` 的核心接口（定义在 `github.com/cloudwego/eino/components/model` 包中）。这个接口是整个 Agent 系统的底座——所有的 Agent（不论是 `adk.NewChatModelAgent` 还是 `compose.NewGraph`）在需要调用 LLM 时，都只依赖这个接口，而不关心实际连接的是哪个供应商的服务。

同时，Eino 框架的扩展包 `eino-ext` 提供了 `openai.NewChatModel` 工厂函数，它能够创建一个实现了 `ToolCallingChatModel` 接口的模型实例。正因为各家供应商都兼容 OpenAI 协议，这个工厂函数可以在只改变配置参数（Base URL、API Key、Model 名称）的情况下，对接任何兼容供应商。

接下来，我们来看项目中是如何在这一抽象之上，构建出一套完整的"万能模型接入层"的。

## 用户级的模型配置：user_model 数据表

为了支持不同用户使用不同的模型，我们在数据库中设计了一张 `user_model` 表。每个用户可以配置多个模型（比如一个 DeepSeek 和一个 GPT-4o），并指定其中一个为默认模型。

代码清单 9-4 展示了 `UserModel` 的核心字段定义：

代码清单 9-4 用户模型配置数据结构
```go
// UserModel 用户模型配置
type UserModel struct {
    ID              uint64 `gorm:"primaryKey;autoIncrement"`
    UserID          int64  `gorm:"index;not null"`
    Name            string `gorm:"size:128;not null;comment:模型显示名称"`
    ModelKey        string `gorm:"size:128;not null;comment:模型标识"`
    Protocol        string `gorm:"size:64;not null;comment:协议类型"`
    BaseURL         string `gorm:"size:255;not null;comment:API 基础地址"`
    APIKeyEncrypted string `gorm:"type:text;not null;comment:加密后的 API 密钥"`
    ProviderName    string `gorm:"size:64;not null;comment:提供商名称"`
    IsDefault       int    `gorm:"not null;default:0;comment:是否为默认"`
    Status          int    `gorm:"not null;default:1;comment:状态"`
    // ... 其他字段省略
}
```

这张表的设计有几个值得注意的要点：

- **ModelKey**：存储模型的标识字符串，例如 `deepseek-ai/DeepSeek-V3.2`、`gpt-4o` 或火山引擎的端点 ID `ep-xxxxxxxx`。不同供应商的标识格式各异，但对于我们的接入层来说，它只是一个透传给 API 的字符串。

- **BaseURL**：这是实现"万能接入"的关键参数。OpenAI 使用 `https://api.openai.com/v1`，DeepSeek 使用 `https://api.deepseek.com/v1`，火山引擎使用 `https://ark.cn-beijing.volces.com/api/v3`。正是这个字段的不同，决定了请求最终发往哪个供应商。

- **APIKeyEncrypted**：API 密钥以加密形式存储在数据库中，使用时通过 `DecryptAPIKey` 函数解密。这是基本的安全实践——密钥明文落盘是生产环境的大忌。

- **Protocol**：虽然当前版本的实现统一使用 OpenAI 兼容协议，但保留了协议字段（如 `openai`、`ark`、`claude`），为未来对接不兼容协议的供应商预留了扩展空间。

## 核心工厂函数：CreatOpenAiChatModel

有了配置数据，接下来就是整个接入层最核心的代码——`CreatOpenAiChatModel` 工厂函数。它的职责是：根据用户 ID 从数据库中读取默认模型配置，解密 API Key，组装 HTTP 客户端，并最终返回一个 `ToolCallingChatModel` 接口实例。

代码清单 9-5 展示了这个工厂函数的完整实现：

代码清单 9-5 统一模型接入工厂函数
```go
func CreatOpenAiChatModel(ctx context.Context, userId uint) (model.ToolCallingChatModel, error) {
    // 第一步：从数据库获取用户的默认模型配置
    result, err := usermodel.UserModelDao.GetDefaultUserModel(int64(userId))
    if err != nil {
        return nil, errors.NewDBError("Failed to get user model", err)
    }

    // 第二步：解密 API Key
    apiKey, err := common.DecryptAPIKey(result.APIKeyEncrypted)
    if err != nil {
        return nil, errors.NewInternalError("Failed to decrypt API key", err)
    }
    key := strings.TrimSpace(apiKey)

    // 第三步：读取模型名称和 Base URL
    modelName := strings.TrimSpace(result.ModelKey)
    url := sanitizeURL(result.BaseURL) // 过滤不可见字符、去除尾部多余路径

    // 第四步：组装 HTTP 请求管线（详见下文）
    cb := circuitbreaker.NewCircuitBreaker(fmt.Sprintf("openai-%s", modelName))
    innerTransport := &loggingTransport{
        Transport:      getBaseTransport(),
        CircuitBreaker: cb,
    }
    var outerTransport http.RoundTripper = innerTransport
    if globalRateLimiter != nil {
        outerTransport = &rateLimitTransport{
            Transport:   innerTransport,
            RateLimiter: globalRateLimiter,
            APIKey:      key,
            ModelName:   modelName,
        }
    }
    httpClient := &http.Client{
        Timeout:   0,
        Transport: outerTransport,
    }

    // 第五步：调用 Eino 的 OpenAI 兼容工厂，创建模型实例
    chatModel, err := openai.NewChatModel(ctx, &openai.ChatModelConfig{
        APIKey:     key,
        Model:      modelName,
        BaseURL:    url,
        HTTPClient: httpClient,
    })
    if err != nil {
        return nil, handleModelError(err) // 统一错误分类处理
    }

    return chatModel, nil
}
```

这段代码的精妙之处在于**第五步**。注意 `openai.NewChatModel` 只接收四个参数：API Key、模型标识、Base URL 和 HTTP 客户端。它并不关心你传入的是 OpenAI 的地址还是 DeepSeek 的地址——因为它们说的都是同一种"语言"（OpenAI 兼容协议）。

举一个具体的例子：如果用户在前端的"模型管理"页面配置了一个 DeepSeek 模型，那么 `UserModel` 表中就会存储 `BaseURL = "https://api.deepseek.com/v1"` 和 `ModelKey = "deepseek-chat"`。工厂函数读取这些配置后，直接传入 `openai.NewChatModel`，Eino 框架会将 Chat Completions 请求发往 DeepSeek 的服务器端点——整个过程中没有任何 `if/else` 分支来判断"这是哪家供应商"。

## 装饰器模式：可插拔的请求管线

在代码清单 9-5 的第四步中，我们组装了一条 HTTP 请求管线。这条管线采用了经典的**装饰器模式（Decorator Pattern）**，通过嵌套实现 `http.RoundTripper` 接口的不同 Transport，将多个横切关注点（Cross-Cutting Concerns）以可插拔的方式层层叠加在基础传输层之上。

整条管线的结构如下：

```
http.Client
   └── rateLimitTransport    ← 限流拦截（9.1.3 节已讲）
          └── loggingTransport    ← 日志 + 熔断
                 └── baseTransport        ← 连接池复用
```

每一层都只负责一件事：

- **baseTransport**（最内层）：使用 `sync.Once` 确保全局单例，配置了连接池参数（`MaxIdleConns`、`IdleConnTimeout` 等），所有模型的 HTTP 请求都复用同一个连接池，避免频繁创建和销毁 TCP 连接带来的性能损耗。

- **loggingTransport**（中间层）：负责请求/响应的调试日志输出，同时集成了 `CircuitBreaker`（熔断器）。当某个模型连续返回 5xx 或 429 错误时，熔断器会自动触发，暂时阻断后续请求，避免对不可用的服务端持续发起无效请求。

- **rateLimitTransport**（最外层）：这一层就是 9.1.3 节中详细介绍的限流拦截器，负责 RPM/TPM 的预扣与补偿。

这种设计的最大好处是**可插拔**。你甚至可以通过配置来决定要不要启用某一层，以下是限流层的启用判断逻辑：

```go
var outerTransport http.RoundTripper = innerTransport
if globalRateLimiter != nil {
    outerTransport = &rateLimitTransport{
        Transport:   innerTransport,
        RateLimiter: globalRateLimiter,
        APIKey:      key,
        ModelName:   modelName,
    }
}
```

如果系统未初始化限流器（`globalRateLimiter == nil`），请求会直接跳过限流层，不会因为基础设施缺失而影响核心业务的可用性。

## 对上层完全透明的调用体验

统一模型接入层建好之后，上层的各类 Agent 的代码就变得极其简洁。不管是 Go 专项面试官还是 Java 专项面试官，它们的模型获取逻辑都是同一行代码。

代码清单 9-6 展示了 Go 专项面试官的创建过程：

代码清单 9-6 Go 专项面试官调用统一接入层
```go
func NewGoSpecializedAgent(userId uint, needResumeTool bool) (adk.Agent, error) {
    ctx := context.Background()

    // 所有 Agent 都通过同一个工厂函数获取模型
    // 无需关心用户配置的是 OpenAI、DeepSeek 还是 Doubao
    model, err := llm.CreatOpenAiChatModel(ctx, userId)
    if err != nil {
        return nil, fmt.Errorf("failed to create chat model: %w", err)
    }

    baseAgent, err := adk.NewChatModelAgent(ctx, &adk.ChatModelAgentConfig{
        Name:          "GoSpecializedAgent",
        Description:   "Go 专项面试官",
        Instruction:   GoSpecializedAgentInstruction,
        Model:         model,    // 传入统一接口
        MaxIterations: 15,
        // ... 工具配置省略
    })
    return baseAgent, nil
}
```

可以看到，`NewGoSpecializedAgent` 完全不需要知道底层用的是哪个供应商的模型。它只调用了 `llm.CreatOpenAiChatModel(ctx, userId)` 就拿到了一个 `ToolCallingChatModel` 接口实例，然后直接传给 Eino 的 Agent 构造函数。

Java 面试官、MQ 面试官、综合面试官，甚至简历解析 Agent 和评估 Agent，走的都是完全一样的路径。这就是统一接入层的价值——**一处对接，处处可用**。

## 火山引擎的特殊处理：端点 ID 兼容

值得一提的是，虽然绝大部分供应商完美兼容了 OpenAI 协议，但在实践中仍然存在一些细微的差异需要处理。以火山引擎为例，它要求 `model` 参数传入的不是通用的模型名称（如 `doubao-1.5-pro`），而是用户在平台上创建的**端点 ID**（形如 `ep-20240601xxxxx`）。

为了帮助用户排查这类配置错误，我们在工厂函数中加入了一段兼容性提示逻辑：

```go
if strings.Contains(url, "volces.com") && !strings.HasPrefix(modelName, "ep-") {
    // 记录警告日志，提示用户可能需要使用端点 ID
}
```

这种"防呆设计"虽然只有两行代码，却能在用户配置出错时快速定位问题，大大降低了运维排查成本。

## 本节小结

本节我们构建了一个统一的模型接入层，它由三个关键部件组成：`user_model` 数据表提供了用户级的多模型配置能力；`CreatOpenAiChatModel` 工厂函数利用 OpenAI 兼容协议的行业标准，实现了"一套代码对接所有供应商"的零分支切换逻辑；装饰器模式的 HTTP Transport 管线则以可插拔的方式，将限流、日志、熔断等横切关注点分层组织。

最终，上层的每一个 Agent 都只需要调用同一个工厂函数，就能拿到一个标准的 `ToolCallingChatModel` 接口。这种"对上透明、对下兼容"的设计，让我们的系统能够轻松应对供应商切换、多租户差异化配置等现实场景。

在下一节中，我们将进一步探讨：当某个供应商突然"罢工"（返回 5xx 或网络超时）时，系统如何在不影响用户体验的前提下，自动将请求切换到备用模型——也就是**模型故障自动切换（Failover）** 机制。
