# 7.2.2 动态追问机制：从线性 Chain 到图编排 Graph

在上一节打通了 RAG 知识外挂之后，我们的 AI 面试官已经具备了充实的领域理论基础。然而，在传统的“面试机器人”应用中，提问流程往往是预设好的固定列表或是单纯的顺序执行链（Chain），缺乏真人的“察言观色”能力。即便知识储备再丰富，如果一味地只是抛出独立的技术问题，整个交互依然像是在干瘪地“背题库”。真正的资深技术面试官在考察候选人时，势必会根据上一题的回答反馈，动态决定下一题的策略：是继续深挖底层源码、还是降低难度考察基础原理、亦或是平滑切换到另外一块技术栈。本节将详细解析，如何利用图架构替代线性结构，实现千人千面的动态追问机制。

### 基于图编排的动态路由架构

为了让面试拥有起承转合的节奏感，我们舍弃了传统的简单顺序链路，引入了基于状态与分支条件的图计算网络。

*   **Who**：在底层，该机制重度依赖 Eino 框架的组件级图编排特性（`compose.NewGraph`）。
*   **What**：它是一个支持环形循环、并在单次循环内包含了生成、等待回答、打分评估与动态重定向四大阶段的执行状态机。
*   **Features**：
    *   **独立评估节点**：在获得回答后，首先进入独立的 `EvaluateNode` 进行解耦打分，生成可量化的动作指令。
    *   **多维分支路由**：通过 `Branch` 节点，将流转策略拆分为 Deepen（拓深）、Continue（平铺）、Lower（降级）、Switch（切换）四条独立路径。
    *   **上下文提示词覆盖**：被路由命中的分支节点不直接生成最终对话，而是负责向状态引擎的数据结构中写入针对下一题的具体微调提示词（`NextActionHint`）。
*   **Value**：这种机制彻底打破了机械式的 Q&A 一问一答模式。系统不再被动地依赖大模型自身的发散思维去决定下一个问题，而是将面试难度的控制权 100% 掌握在后端引擎手中。

### 核心模块一：动作决策与条件分支

在工程中，整个系统的智商跃迁来自于一个名为 `NextAction` 的状态标量。当候选人返回了一段关于某技术点的回答后，旁路运行的评估器会结合当前主题的掌握度与连续答题分数，计算出一个策略动作，并将其存入全局状态总线 `InterviewState` 中。

在代码架构层面，我们需要基于这个状态，在引擎主干中利用 `branchCondition` 函数进行流转分发。在以下截取的引擎装载逻辑中，请重点关注 `evalBranch` 是如何被 `NewGraphBranch` 包装并注册到评估节点之后的，它决定了数据流接下来的去向。

```go
// 源码路径: backend/internal/service/interview/engine/graph_loop.go

// 1. 定义打分节点后的分支条件逻辑
func branchCondition(ctx context.Context, state *InterviewState) (string, error) {
	// 遇到终止指令或逾越题目阈值，走向终结节点
	if state.ShouldStop || state.QuestionIndex >= state.MaxQuestions {
		return NodeEnd, nil
	}
	
	// 根据量化评分所推断出的最佳策略，实施路由
	switch state.EvalResult.NextAction {
	case evaluator.ActionDeepen:
		return NodeDeepen, nil
	case evaluator.ActionLower:
		return NodeLower, nil
	case evaluator.ActionSwitch:
		return NodeSwitch, nil
	default:
		// 当得分中规中矩时，维持当前话题广度
		return NodeContinue, nil
	}
}

// 2. 将此条件器注册为 Graph 的路由枢纽
evalBranch := compose.NewGraphBranch(branchCondition, map[string]bool{
	NodeDeepen:   true,
	NodeContinue: true,
	NodeLower:    true,
	NodeSwitch:   true,
	NodeEnd:      true,
})
// 从评估节点拉取出一条多岔口边
_ = graph.AddBranch(NodeEvaluate, evalBranch)
```

### 核心模块二：上下文劫持与意图注入

当路由进入特定的策略节点（例如高分触发了 Deepen 拓深节点）后，我们并不会在这里调用大模型生成具体问题。相反，我们在这个安全的普通计算节点中，使用纯 Go 代码对大语言模型进行**意图控制注入**。

在这段控制逻辑中，我们向宿主状态装载了语气极度细微的推拉指令（`NextActionHint`）。仔细阅读下方的代码可以发现，我们不仅下达了追问方向的要求，甚至在 Prompt 中封杀了“让我们深入了解一下”此类极度暴露 AI 机械感的生硬语料，强制模型通过“既然你提到了...”的方式进行顺滑衔接。

```go
// 源码路径: backend/internal/service/interview/engine/graph_loop.go

// deepenNode 深入追问节点 (高分分支触发)
func deepenNode(ctx context.Context, state *InterviewState) (*InterviewState, error) {
	log.Printf("[Graph] Branch: DEEPEN - Q%d score=%.2f, going deeper", state.QuestionIndex, state.EvalResult.Overall)
	
	// 劫持状态机的上下文，注入具有策略性的强制提示词
	state.NextActionHint = `请基于候选人刚才的回答，自然地深入追问一个相关的技术细节或原理性问题。
语气要求：
- 像正常对话一样自然衔接，例如"刚才你提到了...，那么..."或"关于这个，我想再深入问一下..."
- 不要说"让我们深入一下"或"接下来我们深入探讨"这类生硬的过渡语
- 直接提出问题，保持对话流畅
追问方向（任选其一）：
- 刚才回答中提到的某个概念的底层实现
- 该方案在边界情况下的表现
- 相关的性能优化或最佳实践`

	state.QuestionIndex++
	return state, nil
}
```

而在最终的 `questionNode`（提问节点）启动前，这些带有极强约束力的 `NextActionHint` 会同之前的滑动窗口对话历史拼接在一起，共同作为大模型发散问题时的上下文锚点。

### Trade-off：控制与发散的博弈

在设计这套动态追问架构时，有一个工程界的经典抉择：为什么不把所有的工作（打分、判断下一步该干什么、同时生成下一题）都通过一次 `LLM Invoke` 让大模型自己处理掉？

*   **设计优势（Pros）**：图编排实现了极高的数据流防腐性与调试可见性。如果不切断动作，大模型的注意力会被冲散，并极其容易产生幻觉（例如明明上一题极其糟糕，模型却开始生拉硬扯地深挖源码）。通过 Eino Graph 截断并接管路由，使整场面试的节奏感 100% 被锁定在了强类型的 Go 代码逻辑中，做到了工程侧的绝对可控。
*   **设计劣势（Cons）**：状态机图的维护成本陡增。相比于一根极简的流处理管道，含有闭环的图（Loop Graph）不仅加重了状态对象 `InterviewState` 字段维护的复杂度，也迫使开发人员在新增任意环节时都要仔细梳理多出度的连线安全。

### 本节小结

本小节剖析了如何利用 Eino 框架的图编排能力，将简单的顺序提示词对话，升级为具备复杂决策意识的状态机引擎。在这个环形网络中，通过引入独立的评估与路由节点，程序接管了大语言模型难以自控的话题延展节奏。无论是拔高难度的主动追问，或是低分时的基础降级挽救，均由确定的代码逻辑进行“军师级”的意图注入。在架构迭代的演进中，将非确定性的模型生成能力关进确定性的逻辑代码笼子里，正是构建严肃型生产级不可或缺的第一步。
