# 7.1.2 难点：如何避免“尬聊”并保持话题连贯性

在上一节，我们成功地为系统打造了多个硬核的“技术专家”，使他们具备了极具压迫感的深度追问能力。然而，仅仅拥有聪明的单体智能是不够的。在真实的多轮模拟面试中，我们遇到了一个极其破坏用户体验的痛点——如果仅仅是将用户的对话机械地传递给大语言模型，随着交流轮次的增加，面试官会逐渐变“健忘”。它们可能会重复询问已经讨论过的内容，或者前言不搭后语，导致面试话题剧烈跳跃，最终演变成无视上下文的“尬聊”。本节将重点解析如何在工程链路中引入上下文记忆机制，使每一位参与协作的面试官都能完美承接对话，保证交流的平滑与深度。

### 多轮对话的记忆引擎：滑动窗口上下文

为了解决多轮面试中的“失忆”与逻辑跳跃问题，我们在面试执行引擎中引入了一种经典的记忆维护形态。在这套架构中，这套机制被称为**滑动窗口上下文（Sliding Window Context）**。

*   **这是谁的设计（Who）**：这是架构团队在构建大规模多轮对话系统时，为了兼顾 LLM（大语言模型）理解力与 Token 消耗成本，从服务端层面独立维护的记忆管理组件。
*   **这是什么（What）**：它是一个队列形的数据结构，专门负责临时存储并更新面试过程中候选人与面试官最近的若干次问答记录。
*   **有什么特点（Features）**：具有严格的容量限制（如固定保留最近五轮对话），并伴随面试的推进不断“向后滑动”，丢弃陈旧信息，将最鲜活的交流记录动态组装进下一次的请求提示词中。
*   **解决了什么问题（Value）**：从根本上避免了上下文丢失导致的重复提问与话题跳跃，且有效控制了每次调用大模型时的请求载荷，防止因 Token 溢出导致的请求失败或响应拖延。

### 引擎中的历史数据流转逻辑

在实际的业务编码中，如何将上述理论转化为顺滑执行的引擎逻辑？在 `engine.go` 核心模块内，我们脱离了纯依赖智能体框架内置记忆体的限制，而是从业务主循环层进行显式拦截与投递。

具体而言，我们创建了一个循环，在每一次生成新问题之前，系统都会扫描目前已发生过的问答对。如果当前并不是第一题，系统则会提取队列 `recentHistory` 中的问答记录，并将其编织到下发给智能体的系统提示词中。在这个提示词内部，我们不仅附带了近期对话文本，还进行了强规则挂载，例如要求“避免重复之前问过的问题”和“引导面试进入下一阶段”。在获取最新一道回答后，系统再次更新这个队列，并剔除超出长度阈值的旧元素。

以下是引擎中执行上下文记忆注入的关键代码。在阅读时，请重点关注 `recentHistory` 是如何随着 `historyContextSize` 动态更新的，以及这些历史文本如何被格式化进最终的 `prompt` 中。

```go
// 源码路径: backend/internal/service/interview/engine/engine.go

	const maxQuestions = 20      // 设定整场面试最多生成20道问题
	const historyContextSize = 5 // 基于 Token 成本与语境需求，只保留前5道题作为历史上下文

	// 1. 初始化一个结构体切片，用于存储最近的历史问答记录
	type HistoryItem struct {
		Question string
		Answer   string
	}
	var recentHistory []HistoryItem

	// 进入核心问答循环
	for questionIndex := 1; questionIndex <= maxQuestions; questionIndex++ {
		
        // ... (上下文监听容错逻辑)

		var prompt string
		if questionIndex == 1 {
            // 首个问题无需历史记录，直接根据简历背景提出
			prompt = fmt.Sprintf(`请作为面试官团队的负责人，根据简历和难度等级开始面试...（略）`)
		} else {
			// 2. 组装历史文本：遍历最近的五道题，逐字拼装出历史对话轴
			historyText := ""
			for i, h := range recentHistory {
				historyText += fmt.Sprintf("问题%d：%s\n回答%d：%s\n\n", i+1, h.Question, i+1, h.Answer)
			}

            // 3. 将装载完毕的历史轴，同约束纪律一起注入系统指令
			prompt = fmt.Sprintf(`根据简历ID、难度等级和最近的问答历史，推动面试进程。
如果你（主面试官）认为当前应该由副面试官或项目面试官进行提问，请通过工具调用由他们生成问题。

简历ID: %d
难度等级: %s

最近的问答历史（前%d道题）：
%s

要求：
1. 根据用户的回答情况，引导面试进入下一阶段或深化当前技术话题
2. 避免重复之前问过的问题
3. 逐步深化面试深度
4. 必须包含身份前缀（如"我是主面试官："或其他面试官前缀）
`, session.ResumeId, session.Difficulty, len(recentHistory), historyText)
		}

		// 4. 将包含了这段宏大上下文的指令传递给 Agent 生成新的一题
		// ... (调用智能体执行)
        
		// 5. 将当前轮次的最新提问与回答存入历史队列
		recentHistory = append(recentHistory, HistoryItem{
			Question: questionText,
			Answer:   answer,
		})
        
        // 6. 滑动窗口核心：若超出大小限制，则切除最老旧的记录
		if len(recentHistory) > historyContextSize {
			recentHistory = recentHistory[len(recentHistory)-historyContextSize:]
		}
	}
```

通过这套逻辑，我们赋予了 AI “短期记忆”。在每一次思考下个问题时，它都在复盘刚刚和候选人探讨了什么。如果候选人上一个回答已经完美阐述了 `HashMap` 的结构，注入了历史上下文的 AI 就绝对不会在下一秒钟问出“请说一下 Map 是怎么实现的”这种低级问题，而是会聪明地追问“既然你提到了红黑树，它在扩容期是如何保持平衡的？”

> **思考**：在庞大的架构中，我们往往倾向于引入高深的框架以解决问题。但在处理 AI 记忆时，回归本质的“手动显式上下文推入”虽然看起来原始，却赋予了业务侧 100% 的控制力。我们能精确决定 AI 该记住什么长度的内容，该遗忘什么信息，这种控制力远比黑盒化的内置记忆体更具工程价值。


### 本节小结

本小节探讨了 AI 模拟面试应用在深入交互时面临的话题连贯性挑战。我们剖析了滑动窗口上下文在此类企业级场景中的价值，并以 `engine.go` 源码为例，深入拆解了系统是如何在服务端主循环中通过截断、保存并重新组合并下发历史问答对，来实现精确的对话记忆控制的。这套轻量而具有掌控力的机制不仅解决了模型“失忆”和“尬聊”的问题，更是控制 Token 支出、增强底层流转可用性的关键保障。
