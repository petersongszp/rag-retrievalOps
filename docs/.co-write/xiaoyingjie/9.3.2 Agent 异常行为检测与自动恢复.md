# 9.3.2 Agent 异常行为检测与自动恢复

在上一节中，我们为 LLM 的输出建立了一道数据校验管线。然而，输出内容的正确性只是冰山一角。在生产环境中，更棘手的问题是：**Agent 的整体行为会不会失控？**

一个具体的场景：面试正在进行中，系统调用 LLM 生成第三道题，但模型因为某种原因陷入了"自我纠结"——它反复调用 RAG 工具检索知识库，每次检索后又觉得信息不够，继续检索……如此循环往复，最终耗尽了所有 Token 配额，用户在前端看到的只是一个永无止境的"思考中"加载动画。再或者，候选人在回答时临时离开了电脑，系统在等待回答的环节无限挂起，占用着服务器连接和内存资源。

这些都不是假想的场景，而是所有基于 LLM 构建的实时交互系统都必须面对的工程现实。本节将深入剖析系统中实际落地的多层异常防护机制。

## 第一层防线：Agent 级别的迭代上限（MaxIterations）

在 Eino 框架中，一个 Agent 在处理单次请求时可能会经历多轮"思考"——它先分析问题，决定调用某个工具，获取工具返回结果，再分析结果，可能还要再调用另一个工具……这个过程叫做**迭代（Iteration）**。正常情况下，Agent 会在几轮迭代内完成任务并返回结果。但当模型"犯迷糊"时（例如工具调用的返回不符合预期，Agent 反复尝试同一操作），迭代次数可能无限增长。

为此，我们在所有 Agent 的创建配置中都显式设置了 `MaxIterations` 参数：

代码清单 9-11 各类 Agent 的迭代上限配置
```go
// 单面试官 Agent（Go/Java/MySQL/Redis/MQ 专项）
baseAgent, err := adk.NewChatModelAgent(ctx, &adk.ChatModelAgentConfig{
    Name:          "GoSpecializedAgent",
    MaxIterations: 15,    // 单面试官最多 15 轮迭代
    // ...
})

// 多面试官协作的主面试官
hostAgent, err := adk.NewChatModelAgent(ctx, &adk.ChatModelAgentConfig{
    Name:          "MainInterviewer",
    MaxIterations: 30,    // 多 Agent 协作场景需要更多轮次
    // ...
})

// 简历解析 Agent
resumeAgent, err := adk.NewChatModelAgent(ctx, &adk.ChatModelAgentConfig{
    Name:          "ResumeParser",
    MaxIterations: 20,    // 简历解析可能需要多次工具调用
    // ...
})
```

这些数字并非随意设定，背后是基于实际运行观察的经验：单面试官在正常情况下通常在 3 到 5 轮迭代内就能生成一道好题，15 轮是一个足够宽裕的安全上限。多 Agent 协作中主面试官需要调用"技术面试官"和"项目面试官"两个子工具，每个子工具本身也有其迭代过程，因此上限提升到 30 轮。一旦迭代次数触达上限，Eino 框架会强制中断 Agent 的思考循环，返回当前已有的最佳结果——相当于给 Agent 装了一个"闹钟"，到点必须交卷。

## 第二层防线：Graph 编排的全局步数上限（MaxRunSteps）

`MaxIterations` 控制的是**单个 Agent 单次调用**的迭代次数。但在我们的面试系统中，整场面试是由一个 Eino Graph 编排驱动的循环——"提问、等待回答、评分、分支决策、再提问"——这个循环本身也需要有边界。

在 `RunInterviewLoopWithGraph` 函数中，我们在编译 Graph 时通过 `WithMaxRunSteps` 精确控制了整个图的最大执行步数：

代码清单 9-12 Graph 编排的全局步数限制
```go
const maxQuestions = 20

// 每个问题大约经过 6 个节点（question → waitAnswer → evaluate → branch → action → loop）
// 乘以安全系数，再加上首尾开销
maxRunSteps := maxQuestions*10 + 20

runnable, err := graph.Compile(ctx, compose.WithMaxRunSteps(maxRunSteps))
```

这段代码的计算逻辑值得细看：一轮完整的"提问到下一轮提问"需要经过大约 6 个图节点（`questionNode`、`waitAnswerNode`、`evaluateNode`、分支决策、动作节点、循环判断），20 道题就是 120 步。但考虑到某些节点可能发生重试或异常处理中的额外流转，我们将系数放大到 10 并额外预留了 20 步，最终上限设为 220 步。

如果因为某种意料之外的 Bug 导致 Graph 没有正常到达 `NodeEnd`，执行步数超过 220 后 Eino 框架会自动终止整个 Graph 的运行。这是一道系统级的"保险丝"，确保无论发生什么，面试流程都不会变成一个无限循环的失控进程。

## 第三层防线：ShouldStop 标志与多触发源的优雅终止

在面试循环的每一个关键节点，代码都会检查 `ShouldStop` 标志。这个布尔值本身并不复杂，但它的价值在于**统一了多种异常场景的终止逻辑**：

代码清单 9-13 多触发源汇聚到统一终止标志
```go
// 触发源一：Agent 生成问题失败
func questionNode(ctx context.Context, state *InterviewState) (*InterviewState, error) {
    // ...
    err := state.AgentSvc.RunInterviewWithCallback(ctx, ...)
    if err != nil {
        log.Printf("[Graph] Failed to generate question %d: %v", state.QuestionIndex, err)
        state.Error = err
        state.ShouldStop = true    // ← 记录错误并标记终止
        return state, nil          // ← 注意：返回 nil error，让 Graph 继续流转到 End 节点
    }

    // 触发源二：Agent 返回空结果
    if len(state.QuestionText) == 0 {
        state.Error = fmt.Errorf("agent returned empty result")
        state.ShouldStop = true
    }
    return state, nil
}

// 触发源三：等待回答超时
func waitAnswerNode(ctx context.Context, state *InterviewState) (*InterviewState, error) {
    answer, received := WaitForAnswerWithHeartbeat(ctx, ...)
    if !received {
        state.Error = fmt.Errorf("answer timeout")
        state.ShouldStop = true
        return state, nil
    }
    // ...
}

// 触发源四：达到最大问题数
func branchCondition(ctx context.Context, state *InterviewState) (string, error) {
    if state.ShouldStop || state.QuestionIndex >= state.MaxQuestions {
        return NodeEnd, nil    // ← 直接路由到结束节点
    }
    // ...
}
```

这里有一个非常精妙的设计决策：**各节点在检测到异常后，不会直接返回 error 将 Graph 炸毁，而是将 `ShouldStop` 设为 `true` 并返回 `nil error`**。这是为了让 Graph 能够正常流转到 `NodeEnd` 结束节点，执行必要的"善后工作"——比如保存已完成的对话记录、发送"面试结束"事件给前端。如果直接抛出 error，Graph 会立即中断，前端只会收到一个冰冷的错误提示，用户失去了之前所有对话的数据。

## 第四层防线：心跳保活与超时控制

在"等待用户回答"这个环节，系统面临两个挑战：一方面，SSE 长连接可能因为中间代理（如 Nginx、CDN）的空闲超时而被断开；另一方面，用户可能长时间不回复（离开了电脑、网络断线）。`WaitForAnswerWithHeartbeat` 用 Go 的 `select` 多路复用同时解决了这两个问题：

代码清单 9-14 心跳保活与超时等待
```go
func WaitForAnswerWithHeartbeat(ctx context.Context, sm *SessionManager, sessionID string,
    timeout time.Duration, heartbeatInterval time.Duration, writer io.Writer) (string, bool) {

    heartbeatTicker := time.NewTicker(heartbeatInterval)
    defer heartbeatTicker.Stop()

    timeoutTimer := time.NewTimer(timeout)
    defer timeoutTimer.Stop()

    session := sm.GetSession(sessionID)
    if session == nil {
        return "", false
    }

    for {
        select {
        case <-ctx.Done():         // 外部取消信号（如用户主动结束面试）
            return "", false

        case <-heartbeatTicker.C:   // 每 15 秒发送一次心跳
            err := SendHeartbeatEvent(writer)
            if err != nil {
                return "", false   // 心跳发送失败 = 连接已断
            }

        case answer := <-session.AnswerChan:  // 收到用户回答
            return answer, true

        case <-timeoutTimer.C:     // 30 分钟超时
            return "", false
        }
    }
}
```

这段代码中的 `select` 语句同时监听了四个信道，这是 Go 并发编程中非常典型的模式。每 15 秒触发一次心跳，向前端发送一个轻量级的 SSE 事件，确保长连接不被中间网络设备误杀。如果心跳发送失败（`err != nil`），说明连接已经断了，此时直接返回 `false` 让上层将 `ShouldStop` 设为 `true`，优雅终止面试。30 分钟的终极超时则是一道绝对的底线——即使心跳正常、连接活着，但用户已经半小时没说话，系统必须释放资源。

## 第五层防线：评分失败的优雅降级

在整场面试的循环中，评分节点 `evaluateNode` 调用 LLM 对候选人的回答进行打分。但评分本身也是一次 LLM 调用，它同样可能失败——模型返回了无法解析的内容、网络瞬断、Token 配额耗尽等等。如果评分失败就直接终止面试，这对候选人来说是非常糟糕的体验。

代码的处理方式是**降级而非中断**：

代码清单 9-15 评分失败的降级处理
```go
func evaluateNode(ctx context.Context, state *InterviewState) (*InterviewState, error) {
    result, err := state.Evaluator.EvaluateWithHistory(ctx, &evaluator.EvaluationRequest{...}, state.ScoreHistory)

    if err != nil {
        log.Printf("[Graph] Evaluation failed: %v", err)
        // 评分失败不影响主流程——使用默认的"继续"动作
        state.EvalResult = &evaluator.EvaluationResult{
            NextAction: evaluator.ActionContinue,
        }
    } else {
        state.EvalResult = result
        // ... 正常更新覆盖度和日志
    }

    return state, nil    // ← 无论评分成败，面试继续
}
```

当评分失败时，代码构造了一个最小化的 `EvaluationResult`，其中 `NextAction` 被设为 `ActionContinue`——即"继续当前话题"。这意味着面试会按照中性路径继续进行：不会因为评分缺失而深入追问（`ActionDeepen`），也不会错误地降低难度（`ActionLower`）。候选人不会感知到任何异常，只会觉得"面试官又问了一道同领域的题"。而在后台日志中，`log.Printf("[Graph] Evaluation failed: %v", err)` 则忠实记录了这次降级事件，供运维团队事后排查。

## 本节小结

本节系统梳理了面试系统中五层逐级递进的异常防护机制。`MaxIterations` 在单次 Agent 调用层面遏制了模型的"思考死循环"；`MaxRunSteps` 在 Graph 编排层面为整场面试设置了全局步数上限；`ShouldStop` 标志汇聚了多种异常触发源，统一导向优雅终止以保全已有数据；`WaitForAnswerWithHeartbeat` 通过心跳保活和超时控制解决了长连接场景下的资源泄漏风险；评分降级机制则确保了辅助系统的失败不会打断核心的面试流程。

这五层防线的设计遵循一个共同的原则：**异常是常态，恢复优先于中断**。在与 LLM 协作的系统中，"一切正常"反而是一种不能依赖的假设。如果用我们在 9.3.1 节中总结的话来说——面对输出结果我们保持"有罪推定"，那么面对系统运行，我们同样要保持"墨菲定律"式的警觉：凡是可能出错的，终将出错。而工程师的职责，就是让系统在出错时依然体面。
