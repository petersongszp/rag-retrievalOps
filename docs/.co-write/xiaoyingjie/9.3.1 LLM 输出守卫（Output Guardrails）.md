# 9.3.1 LLM 输出守卫（Output Guardrails）

在 7.2.3 节中，我们从"输入侧"构筑了双重防线——利用提示词约束（角色锚定）防御 Prompt 注入，用 `TopicTracker` 工程化管控话题偏移。然而，防住了"用户的嘴"，还不够。在企业级 Agent 系统中，另一个同样危险但常被忽视的攻击面潜伏在"输出侧"：**大语言模型返回的内容本身就可能是不可靠的。**

LLM 的输出并不像数据库查询那样具有确定性。它可能返回格式错误的 JSON（比如在 JSON 前后包裹了一层 Markdown 代码块标记），可能给出超出合法范围的评分（比如给出了 15 分或 -3 分），甚至可能在"下一步动作"字段中编造一个系统根本不识别的新值。如果这些"脏数据"不经校验直接流入下游的决策引擎，轻则面试流程错乱（该深追的题被跳过），重则系统级报错导致整场面试中断。

本节将聚焦于"输出守卫"（Output Guardrails）——在数据从 LLM 到达业务逻辑之间，建立一道严格的校验与修正管线。

## Prompt 端的格式约束："只返回 JSON，不要任何其他内容"

输出守卫的第一层，并不在 Go 代码中，而是在发给 LLM 的 Prompt 本身。在我们的评分系统中，`EvaluatorInstruction` 以非常强硬的语气约束了模型的输出行为：

代码清单 9-7 评分器系统提示词中的格式约束
```go
const EvaluatorInstruction = `你是一位资深的技术面试评估专家...

重要：
- 保持客观公正，不要因为回答简短就给低分
- 关注回答的质量而非长度
- 只返回 JSON 格式，不要有任何其他文字`
```

配合评分请求 Prompt 中明确的 JSON Schema 定义（`BuildEvaluationPrompt` 函数），模型被告知了返回值的精确结构：

```go
return fmt.Sprintf(`...
返回JSON格式（只返回JSON，不要任何其他内容）：
{
  "scores": {
    "correctness": <1-10>,
    "depth": <1-10>,
    "completeness": <1-10>,
    "practicality": <1-10>
  },
  "overall": <加权总分1-10>,
  "covered_topics": ["知识点1", "知识点2"],
  "next_action": "<deepen|continue|lower|switch>",
  "reason": "<简短的评分理由，20字以内>"
}`, ...)
```

这种在 Prompt 中内嵌 JSON Schema 的做法，相当于为 LLM 指定了一个"数据合同"。大部分情况下，模型会遵守这个合同。但"大部分情况"在生产环境中远远不够——一个十万分之一的格式异常在日调用十万次的系统里，意味着每天至少一次事故。所以我们还需要第二层和第三层防线。

## 代码端的 JSON 清洗：应对"Markdown 包裹"问题

LLM 有一个众所周知的"坏习惯"：即使你明确告诉它"只返回 JSON"，它仍然可能在 JSON 外面套一层 Markdown 的代码块标记（<code>```json</code> ... <code>```</code>）。如果直接将这种带标记的字符串传入 `json.Unmarshal`，解析必定失败。

`parseEvaluationResponse` 函数专门处理了这个问题：

代码清单 9-8 JSON 响应清洗与解析
```go
func parseEvaluationResponse(content string) (*EvaluationResult, error) {
    // 清理响应内容（移除可能的 Markdown 代码块标记）
    content = strings.TrimSpace(content)
    content = strings.TrimPrefix(content, "```json")
    content = strings.TrimPrefix(content, "```")
    content = strings.TrimSuffix(content, "```")
    content = strings.TrimSpace(content)

    var result EvaluationResult
    if err := json.Unmarshal([]byte(content), &result); err != nil {
        return nil, fmt.Errorf("json unmarshal failed: %w, content: %s", err, content)
    }

    return &result, nil
}
```

这段代码的处理策略是"先清洗，再解析"。它依次剥离了可能出现的 <code>```json</code> 前缀、通用的 <code>```</code> 前后缀，以及多余的空白字符，然后才将"干净"的 JSON 字符串交给 `json.Unmarshal`。值得注意的是，当解析仍然失败时，错误信息中会包含原始的 `content` 内容——这对于线上问题的排查至关重要，因为开发者可以直接在日志中看到 LLM 到底返回了什么"奇怪的东西"。

## 数值边界守卫：clampScore 与 validateAndFixResult

即使 JSON 成功解析了，里面的数值也不一定是合法的。LLM 可能给出 0 分（低于最低标准）、12 分（超出量程），甚至在加权总分字段中返回一个与各维度分数完全不匹配的离谱值。`validateAndFixResult` 是整个输出守卫体系中最关键的一环——它对评分结果进行**逐字段的校验与自动修正**：

代码清单 9-9 评分结果验证与修正
```go
func (e *Evaluator) validateAndFixResult(result *EvaluationResult) {
    // 第一层：将所有维度的原始分数强制钳位到 [1, 10] 区间
    result.Scores.Correctness = clampScore(result.Scores.Correctness)
    result.Scores.Depth = clampScore(result.Scores.Depth)
    result.Scores.Completeness = clampScore(result.Scores.Completeness)
    result.Scores.Practicality = clampScore(result.Scores.Practicality)

    // 第二层：如果加权总分不在合法范围，用各维度分数重新计算
    if result.Overall < 1 || result.Overall > 10 {
        result.Overall = result.Scores.CalculateOverall()
    }

    // 第三层：如果 NextAction 不是合法枚举值，根据分数自动推断
    switch result.NextAction {
    case ActionContinue, ActionDeepen, ActionSwitch, ActionLower:
        // 有效值，保持不变
    default:
        result.NextAction = e.inferNextAction(result.Overall)
    }

    // 第四层：防止空指针——确保切片字段不为 nil
    if result.CoveredTopics == nil {
        result.CoveredTopics = []string{}
    }
}
```

这段代码体现了一种"**永不信任，始终验证**"（Never Trust, Always Verify）的防御性编程哲学。我们来逐层拆解：

**第一层：分数钳位（Clamping）。** `clampScore` 函数将任何小于 1 的分数强制拉升到 1，大于 10 的强制压低到 10。这是一条硬性的数值边界，无论 LLM 给出多么离谱的数字，最终到达业务逻辑的一定是 [1, 10] 范围内的合法值。

```go
func clampScore(score float64) float64 {
    if score < 1 {
        return 1
    }
    if score > 10 {
        return 10
    }
    return score
}
```

**第二层：总分一致性校验。** LLM 有时会"编"一个和各维度分数不匹配的总分。代码不会去追究原因，而是直接用 `CalculateOverall` 按照预设权重（正确性 40%、深度 25%、完整性 20%、实践性 15%）重新计算，确保总分与各维度分数之间的数学关系始终是可解释的。

**第三层：枚举值兜底。** `NextAction` 字段应该是 `continue`、`deepen`、`switch`、`lower` 之一。但 LLM 可能返回 `"proceed"`、`"next"` 这类非法值。代码通过 `switch-default` 分支捕获所有不认识的值，并用 `inferNextAction` 根据总分自动推断出一个合理的动作。

**第四层：空值防护。** `CoveredTopics` 如果为 `nil`，下游的 `TopicTracker.UpdateCoverage` 在遍历时虽然不会报错（Go 的 range 对 nil slice 是安全的），但将其初始化为空切片是更明确的语义——"没有覆盖任何知识点"和"未知状态"是两个不同的含义。

## LLM API 错误的分类处理

输出守卫不仅要防范 LLM 返回的"内容问题"，还需要处理 LLM 返回的"通信问题"。在 `CreatOpenAiChatModel` 函数中，我们对 LLM API 的错误进行了分类识别：

代码清单 9-10 LLM API 错误分类
```go
errMsg := strings.ToLower(err.Error())
switch {
case strings.Contains(errMsg, "insufficient_quota") ||
     strings.Contains(errMsg, "billing_not_active"):
    return nil, errors.NewInsufficientTokensError("余额不足，请充值", err)

case strings.Contains(errMsg, "rate_limit_exceeded") ||
     strings.Contains(errMsg, "too_many_requests"):
    return nil, errors.NewRateLimitExceededError("请求过于频繁", err)

case strings.Contains(errMsg, "context_length_exceeded"):
    return nil, errors.NewContextLengthExceededError("上下文超长", err)

default:
    return nil, errors.NewOpenAIError("模型调用失败", err)
}
```

这段代码的价值在于将一个模糊的 `error` 转化为了**语义明确的错误类型**。上层的 API Handler 可以根据不同的错误类型返回对应的 HTTP 状态码和用户友好的提示信息：余额不足应该引导用户充值（而不是显示一个令人困惑的 500 错误），请求过频应该建议用户稍后重试。这种分类处理让整个错误链路从"黑箱"变成了"白箱"。

## 本节小结

本节构建了一条完整的 LLM 输出校验管线，它由四个层次组成：Prompt 中的 JSON Schema 合同约束模型的输出格式；`parseEvaluationResponse` 清洗响应中的 Markdown 污染；`validateAndFixResult` 对数值边界、总分一致性、枚举值合法性和空值进行逐字段的校验与自动修正；LLM API 错误分类则为上层提供了语义明确的异常处理能力。

这套守卫体系的核心理念可以归纳为一句话：**对 LLM 的输出，永远保持"有罪推定"**——先怀疑，再清洗，再校验，最后才放行。在与不确定性共舞的 AI 系统中，确定性的工程逻辑是系统稳定性的最后一道防线。
