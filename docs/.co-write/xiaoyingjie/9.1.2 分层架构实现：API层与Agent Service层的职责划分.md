# 9.1.2 分层架构实现：API 层与 Agent Service 层的职责划分

在 9.1.1 节中，我们从宏观视角勾勒了面试系统的全景定位——集面试、分析、推荐于一体的解决方案。但"定位"只是蓝图，真正把系统搭建起来的是**分层架构**。一个设计良好的分层架构，能让每一层各司其职、互不干扰，在系统复杂度持续膨胀的过程中保持可理解性和可维护性。

本节将从一次完整的"面试开始"请求出发，自上而下地拆解系统的四层架构，看看一个 HTTP 请求是如何逐层穿透，最终变成一场由 AI 驱动的实时面试对话的。

## 一次请求的完整旅程

当用户在前端点击"开始面试"按钮时，一个 POST 请求被发送到 `/api/interview/stream/start`。这个请求会依次穿过四个架构层，如下图所示：

```
┌─────────────────────────────────────────────────────────────────────┐
│  API Handler 层（interview_service.go）                              │
│  职责：请求校验、鉴权、SSE 连接建立、面试记录创建                       │
│  ↓ 创建 InterviewEngine，启动 goroutine                             │
├─────────────────────────────────────────────────────────────────────┤
│  面试引擎层（engine.go + graph_loop.go）                              │
│  职责：会话管理、Agent 类型选择、Graph 编排驱动面试循环                  │
│  ↓ 通过 InterviewAgentService 调用具体 Agent                        │
├─────────────────────────────────────────────────────────────────────┤
│  Agent Service 层（interview_agent_service.go）                      │
│  职责：Agent 工厂、流式执行、消息过滤                                  │
│  ↓ 创建并运行具体的 Agent 实例                                       │
├─────────────────────────────────────────────────────────────────────┤
│  Agent 实现层（specialized/*.go, comprehensive/*.go, multiagent/*.go）│
│  职责：Prompt 定义、工具绑定、LLM 交互                                │
└─────────────────────────────────────────────────────────────────────┘
```

接下来，我们逐层拆解。

## 第一层：API Handler——请求的入口与前端的桥梁

`StartInterviewStream` 是整个面试流程的起点。这个函数定义在 `api/handler/interview/interview_service.go` 中，它的职责非常明确：**只做 HTTP 协议层的事情**，不涉及任何 AI 逻辑。

代码清单 9-1 面试启动 API Handler
```go
func StartInterviewStream(ctx context.Context, c *app.RequestContext) {
    // 第一步：请求校验与鉴权
    var req mianshiapi.InterviewStartInterviewRequest
    if err := c.BindAndValidate(&req); err != nil {
        response.BadRequest(ctx, c, "Invalid request: "+err.Error())
        return
    }
    userID := middleware.GetUserID(c)
    if userID == 0 {
        response.Unauthorized(ctx, c, "Authorization token is required")
        return
    }

    // 第二步：创建业务记录（面试记录入库）
    interviewSvc := interviewservice.NewInterviewService()
    recordID, err := interviewSvc.CreateInterviewRecord(ctx, recordDTO)

    // 第三步：创建面试会话
    sm := core.GetGlobalSessionManager()
    session := sm.CreateSessionWithDetails(userID, recordID, ...)

    // 第四步：建立 SSE 长连接（关键！）
    cancelCtx, cancelFunc := context.WithCancel(ctx)
    session.CancelFunc = cancelFunc
    core.SetupSSEResponse(c)
    pipeReader, pipeWriter := io.Pipe()
    c.SetBodyStream(pipeReader, -1)

    // 第五步：启动异步面试引擎
    go func() {
        defer pipeWriter.Close()
        engine := core.NewInterviewEngine(sm, interviewSvc, pipeWriter)
        engine.RunInterviewLoopWithGraph(cancelCtx, session)
    }()
}
```

这段代码有几个值得注意的设计决策：

**SSE 长连接的建立方式**。面试是一个可能持续 30 分钟的实时对话过程，传统的"请求-响应"模式无法胜任。代码使用 `io.Pipe()` 创建了一对读写端，将写端（`pipeWriter`）传给面试引擎，让它可以随时向前端推送 SSE 事件（问题文本、心跳、进度等），而读端（`pipeReader`）则通过 `c.SetBodyStream` 交给 Hertz 框架持续向客户端输出。

**goroutine 异步启动**。面试引擎运行在一个独立的 goroutine 中，`StartInterviewStream` 函数在启动 goroutine 后立即返回，不会阻塞 Hertz 的工作线程。整场面试的生命周期完全由 `cancelCtx` 控制——当用户调用"结束面试"接口时，`EndInterview` Handler 会触发 `session.CancelFunc()`，通过 Context 取消信号优雅终止面试循环。

**Handler 不做任何 AI 决策**。注意 Handler 中没有任何与 Prompt、Agent 类型选择或评分逻辑相关的代码。它只负责"搭台"——校验请求、创建记录、建立连接——然后把"唱戏"的工作完全交给下一层。

## 第二层：面试引擎——编排者与决策者

`InterviewEngine` 是整个系统的"大脑"，定义在 `internal/service/interview/engine/` 目录下。它不直接与 LLM 交互，但掌控着面试的全局节奏。

代码清单 9-2 面试引擎的核心结构与职责
```go
type InterviewEngine struct {
    sessionManager *SessionManager
    interviewSvc   interviewservice.InterviewManager
    writer         io.Writer
}

func (e *InterviewEngine) RunInterviewLoopWithGraph(ctx context.Context, session *InterviewSession) {
    // 职责一：确定使用哪种 Agent
    agentSvc := interview.NewInterviewAgentService(session.UserID)
    agentType := e.selectAgentType(session)

    // 职责二：创建评分器和话题追踪器
    evaluatorInstance, _ := evaluator.NewEvaluator(ctx, session.UserID, nil)

    // 职责三：构建并编译 Graph（编排面试流程）
    graph := compose.NewGraph[*InterviewState, *InterviewState]()
    // ... 添加节点和边 ...
    runnable, _ := graph.Compile(ctx, compose.WithMaxRunSteps(maxRunSteps))

    // 职责四：运行 Graph，驱动整场面试
    finalState, _ := runnable.Invoke(ctx, state)

    // 职责五：保存对话记录到数据库
    e.saveAllDialogues(ctx, session, finalState.AllDialogues)
}
```

引擎层最关键的决策之一是 `selectAgentType`——根据用户选择的面试类型和领域，将请求路由到正确的 Agent：

代码清单 9-3 Agent 类型选择的路由逻辑
```go
func (e *InterviewEngine) selectAgentType(session *InterviewSession) interview.InterviewAgentType {
    // 多人模拟面试 → 多 Agent 协作
    if session.Type == "多人模拟面试" {
        return interview.GroupInterview
    }

    // 综合面试 → 按学历/经验分
    if session.Type == "综合面试" {
        switch session.Domain {
        case "校招简历面试":
            return interview.ComprehensiveSchool
        case "社招简历面试":
            return interview.ComprehensiveSocial
        }
    }

    // 专项面试 → 按技术领域分
    switch session.Domain {
    case "Java":  return interview.SpecializedJava
    case "MySQL": return interview.SpecializedMySQL
    case "Redis": return interview.SpecializedRedis
    case "MQ":    return interview.SpecializedMQ
    default:      return interview.SpecializedGo
    }
}
```

这个路由函数虽然只有几十行代码，但它体现了分层设计的核心理念：**决策逻辑集中在引擎层，而不是分散在各个 Agent 中**。Agent 不需要知道自己是"被谁选中的"，它只需要专注于"提好技术问题"这一件事。

## 第三层：Agent Service——Agent 的工厂与运行时

`InterviewAgentService` 定义在 `internal/agents/usecase/interview/` 目录下，它扮演了两个角色：**Agent 工厂**和**流式执行器**。

先看工厂部分。`GetInterviewAgent` 方法根据传入的 `agentType` 枚举值，调用对应的构造函数创建 Agent 实例：

```go
func (s *InterviewAgentService) GetInterviewAgent(agentType InterviewAgentType, needResumeTool bool) (adk.Agent, error) {
    switch agentType {
    case ComprehensiveSchool:
        return comprehensive.NewSchoolComprehensiveAgent(s.userId, needResumeTool)
    case SpecializedGo:
        return specialized.NewGoSpecializedAgent(s.userId, needResumeTool)
    case GroupInterview:
        return multiagent.NewInterviewHostAgent(ctx, s.userId, needResumeTool)
    // ... 其他类型
    }
}
```

再看执行器部分。`RunInterviewWithCallback` 方法封装了 Agent 的流式调用过程，它负责处理 Eino 框架的 `Runner` + `Iterator` 模式，并通过回调函数将每个文本片段实时推送给上层：

```go
func (s *InterviewAgentService) RunInterviewWithCallback(ctx context.Context,
    agentType InterviewAgentType, needResumeTool bool, prompt string,
    callback func(message string) error) error {

    agent, _ := s.GetInterviewAgent(agentType, needResumeTool)

    runner := adk.NewRunner(ctx, adk.RunnerConfig{
        Agent:           agent,
        EnableStreaming: true,
    })
    iter := runner.Run(ctx, []adk.Message{schema.UserMessage(prompt)})

    for {
        event, ok := iter.Next()
        if !ok { break }
        // 关键过滤：只将 Assistant 角色的消息输出给前端
        if msg.Role != schema.Assistant { continue }
        if msg.Content != "" {
            callback(msg.Content) // 实时推送文本片段
        }
    }
}
```

这一层有一个重要的细节：**消息角色过滤**。在 Agent 的内部迭代过程中，LLM 会产生多种角色的消息——`System`（系统提示词回显）、`Tool`（工具调用请求和返回结果）、`Assistant`（面试官的实际发言）。如果不加过滤，用户会在前端看到 RAG 检索的原始文档片段或工具调用的 JSON 结构体，这对候选人来说是非常困惑的体验。`RunInterviewWithCallback` 通过 `msg.Role != schema.Assistant` 这行代码，确保了只有"面试官真正想说的话"才能到达前端。

## 第四层：Agent 实现——每个面试官的"人格"

最底层是各个具体 Agent 的实现。以 Go 专项面试官为例（已在 9.2.1 节展示过），它的代码非常简洁：

```go
func NewGoSpecializedAgent(userId uint, needResumeTool bool) (adk.Agent, error) {
    model, _ := llm.CreatOpenAiChatModel(ctx, userId)  // 统一模型接入层

    baseAgent, _ := adk.NewChatModelAgent(ctx, &adk.ChatModelAgentConfig{
        Name:          "GoSpecializedAgent",
        Instruction:   GoSpecializedAgentInstruction,   // 人格 Prompt
        Model:         model,
        ToolsConfig:   toolsConfig,                     // RAG 工具等
        MaxIterations: 15,
    })
    return baseAgent, nil
}
```

每个 Agent 只关心三件事：用哪个模型（通过 9.2.1 节的统一接入层获取）、怎么提问（由 `Instruction` 定义的人格 Prompt 决定）、能使用哪些工具（如 RAG 知识库检索、简历信息查询）。它完全不知道自己是被 Graph 编排调用的、前面有一个 SSE 连接在等着、后面有一个评分器在打分——这些都不是它该操心的事。

## 分层的价值：一个真实的演进案例

这套分层架构并非凭空设计出来的"完美方案"，而是随着系统演进逐步长成的。回顾 `engine.go` 的代码，你会发现里面同时存在 `RunInterviewLoop`（线性循环版本）和 `RunInterviewLoopWithGraph`（Graph 编排版本）两个方法。`StartInterviewStream` Handler 中有一行被注释掉的代码：

```go
//engine.RunInterviewLoop(cancelCtx, session)
engine.RunInterviewLoopWithGraph(cancelCtx, session)
```

这正是分层架构带来的实际收益：当我们从"简单 for 循环"演进到"Graph 编排"时，API Handler 层的代码一行都不用改，Agent Service 层也丝毫不受影响——变化被完全封闭在了引擎层内部。上层只知道"调用引擎的某个方法就能跑一场面试"，至于引擎内部是用 for 循环驱动还是用 Graph 编排驱动，它完全无感。

这就是分层设计最核心的价值：**每一层的变化都不会波及其他层，系统可以在不断演进的同时保持整体稳定**。

## 本节小结

本节从一次"开始面试"请求的完整旅程出发，拆解了系统的四层架构。API Handler 层负责 HTTP 协议处理和 SSE 连接建立，面试引擎层掌控会话管理和流程编排，Agent Service 层提供 Agent 工厂和流式执行能力，Agent 实现层则专注于每个面试官的"人格"定义。四层之间通过接口和回调函数实现了清晰的解耦，使得系统能够在从 "for 循环" 到 "Graph 编排"的演进过程中，将变化封闭在单一层级，而不波及其他层。
