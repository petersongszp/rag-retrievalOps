# 11.1.2 协程模型优化：Netpoll 的配置与 GOMAXPROCS

## 概念描述

在高并发 HTTP 服务中，协程调度与 I/O 模型直接影响吞吐与延迟。本节涉及两方面的“协程模型优化”：

1. **Netpoll 与 Hertz**：Hertz 是字节开源的高性能 HTTP 框架，底层基于 Netpoll 网络库。Netpoll 采用 epoll（Linux）/ kqueue（macOS）等 I/O 多路复用，结合协程（goroutine）实现非阻塞网络 I/O，减少系统调用与上下文切换，适合高并发短连接与长连接场景。项目选用 Hertz 即默认获得 Netpoll 的协程与 I/O 模型，无需在应用层单独配置 Netpoll 本身。
2. **GOMAXPROCS**：Go 运行时中，`GOMAXPROCS` 决定同时执行用户态代码的 OS 线程数（可理解为“P”的数量）。默认等于 CPU 核数；在容器或虚拟化环境下可能未正确识别核数，或希望限制并发度以留出资源给其他进程时，可在进程启动时显式设置。设置合适的 GOMAXPROCS 有助于平衡 CPU 利用与调度开销，属于 11.1.2 中“协程模型优化”的可调项。

通过启动时根据配置设置 `runtime.GOMAXPROCS`，项目在保持 Hertz/Netpoll 默认协程模型的前提下，实现了对运行时可并行的 P 数量的可控调优。

## 项目实现概览

本项目在以下方面实现了 11.1.2 协程模型优化：

1. **Hertz 与 Netpoll**：直接使用 Hertz 作为 HTTP 网关，其底层 Netpoll 的 I/O 与协程模型由框架内置，无需额外配置。
2. **GOMAXPROCS 配置**：在 `config.yaml` 的 `hertz` 下提供 `gomaxprocs` 配置项（0 表示不修改，使用运行时默认）；在 `main.go` 启动流程中，若配置值大于 0 则调用 `runtime.GOMAXPROCS(cfg.Hertz.GOMAXPROCS)` 并打日志，便于运维确认实际生效的 P 数。

## 核心功能代码

### 1. 配置结构中的 GOMAXPROCS 字段

Hertz 配置结构中已包含 `gomaxprocs` 字段，用于 11.1.2 协程模型优化：控制进程启动时设置的 GOMAXPROCS 值。

**Go 语言代码片段 (`backend/internal/config/config.go`)**:

```go
// HertzConfig Hertz框架配置（含 11.1 高并发相关）
type HertzConfig struct {
	LogLevel     string          `yaml:"log_level"`
	LogPath      string          `yaml:"log_path"`
	ReadTimeout  string          `yaml:"read_timeout"`
	WriteTimeout string          `yaml:"write_timeout"`
	IdleTimeout  string          `yaml:"idle_timeout"`
	KeepAlive    bool            `yaml:"keep_alive"` // 11.1.1 连接池：是否开启 KeepAlive
	GOMAXPROCS   int             `yaml:"gomaxprocs"` // 11.1.2 协程模型：P 数量，0 表示不设置（使用默认）
	RateLimit    RateLimitConfig `yaml:"rate_limit"` // 11.1.3 限流：支持分布式 Redis 限流
}
```

*   **说明**：`GOMAXPROCS` 对应配置文件中的 `hertz.gomaxprocs`。设为 0 表示不修改运行时默认值（通常为 CPU 核数）；设为大于 0 的整数时，将在服务启动时调用 `runtime.GOMAXPROCS` 进行设置，实现 11.1.2 中的协程模型调优。

### 2. 启动时设置 GOMAXPROCS

在初始化 Hertz 服务器之前，根据配置设置 GOMAXPROCS，并输出日志便于确认生效，与 11.1.2 中“协程模型优化”的实践一致。

**Go 语言代码片段 (`backend/cmd/server/main.go`)**:

```go
	// 11.1.2 协程模型优化：启动时设置 GOMAXPROCS（0 表示不修改，使用默认）
	if cfg.Hertz.GOMAXPROCS > 0 {
		prev := runtime.GOMAXPROCS(cfg.Hertz.GOMAXPROCS)
		log.Printf("[11.1.2] GOMAXPROCS set to %d (was %d)", cfg.Hertz.GOMAXPROCS, prev)
	}
```

*   **说明**：仅当 `cfg.Hertz.GOMAXPROCS > 0` 时修改运行时的 GOMAXPROCS，并将修改前后的值写入日志。这样在容器或固定核数环境下可显式控制并行度，避免默认值过小或过大带来的性能问题，完成 11.1.2 协程模型优化中的“GOMAXPROCS 配置”部分。

### 3. 配置示例

通过 YAML 配置可灵活控制是否启用 GOMAXPROCS 调优及具体数值。

**配置示例 (`backend/config.yaml`)**:

```yaml
# Hertz框架配置（11.1 高并发：连接池、协程模型、限流）
hertz:
  log_level: "info"
  log_path: "./logs"
  read_timeout: "10s"
  write_timeout: "10s"
  idle_timeout: "60s"
  keep_alive: true                    # 11.1.1 连接池：KeepAlive
  gomaxprocs: 0                       # 11.1.2 协程模型：P 数量，0=不设置（使用默认）
  rate_limit:                         # 11.1.3 限流
    rps: 20
    burst: 50
    use_redis: false
    redis_key_prefix: "rl:"
```

*   **说明**：`gomaxprocs: 0` 表示不修改 GOMAXPROCS，使用运行时默认。若部署在 4 核容器且希望限制为 2 个 P，可设为 `gomaxprocs: 2`，重启后日志中会看到 `[11.1.2] GOMAXPROCS set to 2 (was 4)` 等输出，便于验证 11.1.2 的协程模型优化已生效。

## 结论

Hertz 基于 Netpoll 的 I/O 与协程模型为项目提供了高并发网关基础；在此基础上，通过配置项 `hertz.gomaxprocs` 与启动时对 `runtime.GOMAXPROCS` 的按需设置，项目实现了对运行时可并行 P 数量的可控调优，与书中 11.1.2“协程模型优化：Netpoll 的配置与 GOMAXPROCS”的实践一致，适用于容器与多核环境下的性能调优。
