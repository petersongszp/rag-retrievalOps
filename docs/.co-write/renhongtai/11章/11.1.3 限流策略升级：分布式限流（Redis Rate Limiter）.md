# 11.1.3 限流策略升级：分布式限流（Redis Rate Limiter）

## 概念描述

在高并发网关层，限流用于保护后端与下游服务不被突发流量压垮，并保证多租户或多用户场景下的公平性。本节涉及的“限流策略升级”主要包括：

1. **单机限流（内存）**：在单进程内按客户端 IP 维护限流状态（如 token bucket 或滑动窗口），实现简单、无外部依赖，但多实例部署时各实例独立计数，无法做到全局限流，且实例重启后状态丢失。
2. **分布式限流（Redis）**：将限流计数与窗口存储在 Redis 中，多实例共享同一套计数，从而在多实例、多副本部署时实现统一的“全局限流”；同时可配合 Redis 的过期机制实现固定窗口或滑动窗口。代价是依赖 Redis 可用性，通常需要在 Redis 异常时设计降级策略（如放行或返回 503），避免雪崩。

本项目在 Hertz 网关层实现了两种限流策略的**可配置切换**：通过配置 `rate_limit.use_redis` 选择使用内存版 IP 限流器（`golang.org/x/time/rate` 的 token bucket，按 IP 维度）或基于 Redis 的分布式限流器（固定窗口、按 IP+时间窗口维度），对应书中 11.1.3“限流策略升级：分布式限流（Redis Rate Limiter）”。

## 项目实现概览

本项目通过以下方式实现了 11.1.3 限流策略升级：

1. **配置驱动**：在 `hertz.rate_limit` 下配置 `rps`、`burst`、`use_redis`、`redis_key_prefix`。启动时根据 `use_redis` 决定挂载内存限流中间件或 Redis 限流中间件，并对 rps/burst 做默认值兜底。
2. **内存限流器（IPRateLimiter）**：使用 `golang.org/x/time/rate` 的 Limiter，按客户端 IP 维护 token bucket，支持每秒请求数（RPS）与突发容量（burst）；后台协程定期清理长时间未访问的 IP 对应 Limiter，避免内存泄漏。
3. **Redis 分布式限流器（RedisRateLimiter）**：使用 Redis + Lua 脚本实现“按 IP + 秒级时间窗口”的固定窗口计数，原子执行 INCR 与 EXPIRE，超出 burst 时返回 429；Redis 不可用时选择放行请求并依赖日志排查，避免因 Redis 故障导致网关整体不可用。

## 核心功能代码

### 1. 限流配置结构与启动时分支

限流相关配置集中在 `HertzConfig.RateLimit` 中，启动时根据 `UseRedis` 选择内存或 Redis 限流中间件，实现 11.1.3 的限流策略升级。

**配置结构 (`backend/internal/config/config.go`)**:

```go
// RateLimitConfig 限流配置
type RateLimitConfig struct {
	RPS            int    `yaml:"rps"`              // 每秒请求数
	Burst          int    `yaml:"burst"`            // 突发容量
	UseRedis       bool   `yaml:"use_redis"`        // 是否使用 Redis 分布式限流
	RedisKeyPrefix string `yaml:"redis_key_prefix"` // Redis 键前缀，空则用 "rl:"
}
```

*   **说明**：`rps`、`burst` 控制限流强度；`use_redis` 为 true 时启用 Redis 分布式限流，为 false 时使用内存限流；`redis_key_prefix` 用于 Redis 键前缀，多服务共享 Redis 时可区分不同应用。

**启动时应用 (`backend/cmd/server/main.go`)**:

```go
	// 11.1.3 限流中间件：支持单机（内存）或分布式（Redis）
	rps, burst := cfg.Hertz.RateLimit.RPS, cfg.Hertz.RateLimit.Burst
	if rps <= 0 {
		rps = 20
	}
	if burst <= 0 {
		burst = 50
	}
	if cfg.Hertz.RateLimit.UseRedis {
		log.Println("[11.1.3] Using Redis distributed rate limiter")
		prefix := cfg.Hertz.RateLimit.RedisKeyPrefix
		if prefix == "" {
			prefix = "rl:"
		}
		s.Use(appMiddleware.NewRedisRateLimiter(redisClient, prefix, burst).Handler())
	} else {
		s.Use(appMiddleware.NewIPRateLimiter(rate.Limit(rps), burst).Handler())
	}
```

*   **说明**：对 rps、burst 做默认值兜底后，根据 `UseRedis` 挂载 Redis 或内存限流中间件。启用 Redis 时打印 `[11.1.3] Using Redis distributed rate limiter`，便于运维确认当前使用的是 11.1.3 的分布式限流策略。

### 2. 内存限流器：IPRateLimiter（按 IP 的 token bucket）

单机场景下使用内存版限流器，按客户端 IP 维护 token bucket，支持 RPS 与突发容量，并定期清理长时间未访问的 IP 以控制内存占用。

**Go 语言代码片段 (`backend/internal/middleware/ratelimit.go`)**:

```go
// IPRateLimiter IP 限流器
type IPRateLimiter struct {
	ips   sync.Map
	rate  rate.Limit
	burst int
	mu    sync.Mutex
	lastSeen sync.Map
}

// NewIPRateLimiter 创建新的 IP 限流器
// r: 每秒允许的请求数 (RPS)
// b: 允许的突发请求数
func NewIPRateLimiter(r rate.Limit, b int) *IPRateLimiter {
	limiter := &IPRateLimiter{
		rate:  r,
		burst: b,
	}
	go limiter.cleanupLoop()
	return limiter
}

// getLimiter 获取指定 IP 的限流器
func (i *IPRateLimiter) getLimiter(ip string) *rate.Limiter {
	i.lastSeen.Store(ip, time.Now())
	if v, ok := i.ips.Load(ip); ok {
		return v.(*rate.Limiter)
	}
	i.mu.Lock()
	defer i.mu.Unlock()
	if v, ok := i.ips.Load(ip); ok {
		return v.(*rate.Limiter)
	}
	limiter := rate.NewLimiter(i.rate, i.burst)
	i.ips.Store(ip, limiter)
	return limiter
}

// Handler Hertz 中间件处理函数
func (i *IPRateLimiter) Handler() app.HandlerFunc {
	return func(c context.Context, ctx *app.RequestContext) {
		ip := ctx.ClientIP()
		limiter := i.getLimiter(ip)
		if !limiter.Allow() {
			ctx.AbortWithStatusJSON(http.StatusTooManyRequests, map[string]string{
				"error":   "Too Many Requests",
				"message": "您的请求过于频繁，请稍后再试",
			})
			return
		}
		ctx.Next(c)
	}
}
```

*   **说明**：每个 IP 对应一个 `rate.Limiter`（token bucket），通过 `sync.Map` 存储；`Allow()` 在未超限时放行并消费一个 token。超限时返回 429 与友好提示。`cleanupLoop`（未在片段中展开）会定期清理超过一定时间未访问的 IP，避免 11.1.3 单机限流场景下的内存泄漏。

### 3. Redis 分布式限流器：固定窗口 + Lua 原子化

多实例部署时使用 Redis 存储计数，按“IP + 秒级时间窗口”做固定窗口限流，Lua 脚本保证 INCR 与 EXPIRE 的原子性，实现 11.1.3 的分布式限流。

**Go 语言代码片段 (`backend/internal/middleware/redis_ratelimit.go`)**:

```go
// RedisRateLimiter 基于 Redis 的分布式 IP 限流器（固定窗口，原子 INCR+EXPIRE）
// 适用于多实例部署时统一限流（11.1.3 分布式限流）
type RedisRateLimiter struct {
	client *redis.Client
	prefix string
	burst  int
}

// redisFixedWindowLua 原子：INCR key，首次则 EXPIRE 2s，返回当前计数
const redisFixedWindowLua = `
local k = KEYS[1]
local c = redis.call('INCR', k)
if c == 1 then
  redis.call('EXPIRE', k, 2)
end
return c
`

// NewRedisRateLimiter 创建 Redis 分布式限流器
func NewRedisRateLimiter(client *redis.Client, prefix string, burst int) *RedisRateLimiter {
	if client == nil {
		panic("RedisRateLimiter: redis client is nil")
	}
	if prefix == "" {
		prefix = "rl:"
	}
	return &RedisRateLimiter{
		client: client,
		prefix: prefix,
		burst:  burst,
	}
}

// Handler 返回 Hertz 限流中间件
func (r *RedisRateLimiter) Handler() app.HandlerFunc {
	return func(c context.Context, ctx *app.RequestContext) {
		ip := ctx.ClientIP()
		windowKey := strconv.FormatInt(time.Now().Unix(), 10)
		key := r.prefix + ip + ":" + windowKey

		n, err := r.client.Eval(c, redisFixedWindowLua, []string{key}).Int()
		if err != nil {
			// Redis 不可用时放行并记录，避免雪崩
			ctx.Next(c)
			return
		}

		if n > r.burst {
			ctx.AbortWithStatusJSON(http.StatusTooManyRequests, map[string]string{
				"error":   "Too Many Requests",
				"message": "您的请求过于频繁，请稍后再试",
			})
			return
		}
		ctx.Next(c)
	}
}
```

*   **说明**：限流键为 `prefix + IP + 当前秒级时间戳`，实现按秒的固定窗口。Lua 脚本内 INCR 与 EXPIRE 原子执行，避免并发下窗口过期与计数不一致。计数超过 `burst` 时返回 429。Redis 调用失败时选择放行并继续执行 `Next`，避免因 Redis 故障导致所有请求被拒绝，符合 11.1.3 分布式限流实践中常见的降级策略。

### 4. 配置示例

通过 YAML 可切换单机与分布式限流，并调节 rps、burst 及 Redis 键前缀。

**配置示例 (`backend/config.yaml`)**:

```yaml
hertz:
  rate_limit:                         # 11.1.3 限流
    rps: 20
    burst: 50
    use_redis: false                  # 多实例部署时改为 true 启用分布式限流
    redis_key_prefix: "rl:"
```

*   **说明**：`use_redis: false` 时使用内存版 IP 限流器；多实例部署时改为 `use_redis: true` 即可启用 Redis 分布式限流，全局限流键以 `redis_key_prefix` 为前缀，便于与其他服务区分。

## 结论

通过配置项 `hertz.rate_limit` 与两种限流中间件（内存版 IPRateLimiter、Redis 版 RedisRateLimiter）的可选挂载，本项目在网关层实现了单机限流与分布式限流的策略升级。单实例时使用内存限流简单可靠；多实例部署时开启 `use_redis: true` 即可获得基于 Redis 的全局限流能力，并与书中 11.1.3“限流策略升级：分布式限流（Redis Rate Limiter）”的实践一致。
