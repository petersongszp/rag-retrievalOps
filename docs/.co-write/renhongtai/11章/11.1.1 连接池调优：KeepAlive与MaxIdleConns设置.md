# 11.1.1 连接池调优：KeepAlive 与 MaxIdleConns 设置

## 概念描述

在高并发场景下，连接池与长连接配置直接影响网关与下游服务的吞吐和延迟。本节涉及的“连接池调优”主要包括三方面：

1. **HTTP 网关（Hertz）的 KeepAlive**：是否对客户端维持 TCP 长连接。开启后，同一连接可复用处理多次请求，减少握手/挥手开销，降低延迟并提高 QPS。
2. **数据库连接池的 MaxIdleConns / MaxOpenConns**：控制与 MySQL 等数据库之间保持的空闲连接数、最大打开连接数，避免连接耗尽或过多空闲占用资源。
3. **LLM 调用侧 HTTP Transport 的 MaxIdleConns / KeepAlive**：请求第三方模型 API（如 OpenAI、豆包）时，通过 `http.Transport` 复用连接，减少每次请求建连成本，对高并发调用尤为重要。

通过统一从配置读取这些参数（或在代码中采用合理默认值），项目在网关层、数据层和模型调用层实现了可配置的连接池与 KeepAlive 调优，对应书中 11.1.1 连接池调优实践。

## 项目实现概览

本项目在以下三处实现了连接池与 KeepAlive 相关配置与代码：

1. **Hertz 网关**：在 `config.yaml` 的 `hertz` 下配置 `keep_alive`，启动时解析超时与 KeepAlive 并传入 `server.WithKeepAlive`、`WithReadTimeout`、`WithWriteTimeout`、`WithIdleTimeout`。
2. **数据库连接池**：在 `database` 配置中提供 `max_open_conns`、`max_idle_conns`、`conn_max_lifetime`，在 `InitDatabase` 中调用 `SetMaxIdleConns`、`SetMaxOpenConns`、`SetConnMaxLifetime`。
3. **LLM HTTP Client**：在调用 OpenAI 兼容 API 时使用单例 `getBaseTransport()`，内部设置 `MaxIdleConns`、`MaxIdleConnsPerHost`、`IdleConnTimeout`，并显式设置 `DisableKeepAlives: false` 以启用长连接复用。

## 核心功能代码

### 1. Hertz 配置与 KeepAlive 的读取与应用

配置结构中定义 `KeepAlive` 等字段，启动时解析超时与 KeepAlive，并传入 Hertz 服务器，实现 11.1.1 中“连接池/网关”的调优。

**配置结构 (`backend/internal/config/config.go`)**:

```go
// HertzConfig Hertz框架配置（含 11.1 高并发相关）
type HertzConfig struct {
	LogLevel     string          `yaml:"log_level"`
	LogPath      string          `yaml:"log_path"`
	ReadTimeout  string          `yaml:"read_timeout"`
	WriteTimeout string          `yaml:"write_timeout"`
	IdleTimeout  string          `yaml:"idle_timeout"`
	KeepAlive    bool            `yaml:"keep_alive"` // 11.1.1 连接池：是否开启 KeepAlive
	GOMAXPROCS   int             `yaml:"gomaxprocs"` // 11.1.2 协程模型：P 数量，0 表示不设置（使用默认）
	RateLimit    RateLimitConfig `yaml:"rate_limit"` // 11.1.3 限流：支持分布式 Redis 限流
}
```

*   **说明**：`KeepAlive` 对应配置文件中的 `hertz.keep_alive`，用于控制 HTTP 网关是否对客户端保持长连接。其余超时与限流配置为 11.1 高并发章节的其他小节所用。

**启动时应用 (`backend/cmd/server/main.go`)**:

```go
	// 11.1.1 Hertz 连接池/网关：从配置解析超时与 KeepAlive
	readTimeout := 3 * time.Second
	if d, err := time.ParseDuration(cfg.Hertz.ReadTimeout); err == nil && d > 0 {
		readTimeout = d
	}
	writeTimeout := 3 * time.Second
	if d, err := time.ParseDuration(cfg.Hertz.WriteTimeout); err == nil && d > 0 {
		writeTimeout = d
	}
	idleTimeout := 1 * time.Minute
	if d, err := time.ParseDuration(cfg.Hertz.IdleTimeout); err == nil && d > 0 {
		idleTimeout = d
	}
	keepAlive := cfg.Hertz.KeepAlive
	// 兼容旧配置：未配置 rate_limit 时视为旧配置，默认开启 KeepAlive。若需显式关闭，须同时配置 rate_limit（如 rps: 20）
	if !keepAlive && cfg.Hertz.RateLimit.RPS == 0 && cfg.Hertz.RateLimit.Burst == 0 {
		keepAlive = true
	}

	// 初始化 Hertz 服务器（11.1.1 高并发配置：KeepAlive、超时从 config 读取）
	s := server.Default(
		server.WithHostPorts(fmt.Sprintf("%s:%d", cfg.Host, cfg.Port)),
		server.WithReadTimeout(readTimeout),
		server.WithWriteTimeout(writeTimeout),
		server.WithIdleTimeout(idleTimeout),
		server.WithKeepAlive(keepAlive),
		server.WithMaxRequestBodySize(4*1024*1024), // 4MB Limit
	)
```

*   **说明**：从 `cfg.Hertz` 读取读/写/空闲超时与 `KeepAlive`，在未显式配置限流时为保证兼容默认开启 KeepAlive。最终通过 `server.WithKeepAlive(keepAlive)` 等传入 Hertz，完成 11.1.1 中网关侧连接池与 KeepAlive 的设置。

### 2. 数据库连接池：MaxIdleConns 与 MaxOpenConns

数据库连接池通过配置中的 `max_idle_conns`、`max_open_conns` 与 `conn_max_lifetime` 控制空闲连接数、最大打开连接数以及连接最大存活时间，避免连接泄漏与资源浪费。

**配置示例 (`backend/config.yaml`)**:

```yaml
database:
  driver: "mysql"
  dsn: "${DB_USER}:${DB_PASSWORD}@tcp(${DB_HOST}:${DB_PORT})/${DB_NAME}?charset=utf8mb4&parseTime=True&loc=Local"
  max_open_conns: 100
  max_idle_conns: 10
  conn_max_lifetime: "1h"
```

*   **说明**：`max_idle_conns` 对应连接池中保持的空闲连接数（MaxIdleConns），`max_open_conns` 为最大打开连接数（MaxOpenConns），`conn_max_lifetime` 为连接最大存活时间，三者共同实现 11.1.1 中数据库连接池的调优。

**Go 语言代码片段 (`backend/internal/repository/database.go`)**:

```go
	// 配置连接池
	sqlDB, err := db.DB()
	if err != nil {
		return err
	}

	sqlDB.SetMaxIdleConns(dbConfig.MaxIdleConns)
	sqlDB.SetMaxOpenConns(dbConfig.MaxOpenConns)
	if dbConfig.ConnMaxLifetime != "" {
		connMaxLifetime, err := time.ParseDuration(dbConfig.ConnMaxLifetime)
		if err == nil {
			sqlDB.SetConnMaxLifetime(connMaxLifetime)
		}
	}
```

*   **说明**：在 GORM 打开数据库后，通过底层 `*sql.DB` 设置空闲连接数、最大打开连接数以及连接最大存活时间，使配置中的 MaxIdleConns / MaxOpenConns 生效，符合 11.1.1 连接池调优的实践。

### 3. LLM 调用侧 HTTP Transport：MaxIdleConns 与 KeepAlive

请求外部模型 API 时，通过单例 `http.Transport` 设置全局与每 host 的空闲连接数、空闲超时，并显式开启 KeepAlive，实现连接复用，减少高并发下建连开销。

**Go 语言代码片段 (`backend/internal/agents/llm/openAi.go`)**:

```go
// getBaseTransport returns a singleton http.Transport with optimized connection pooling settings
func getBaseTransport() *http.Transport {
	transportOnce.Do(func() {
		baseTransport = &http.Transport{
			Proxy:                 http.ProxyFromEnvironment,
			MaxIdleConns:          100,              // Total max idle connections
			MaxIdleConnsPerHost:   20,               // Max idle connections per host
			IdleConnTimeout:       90 * time.Second, // Idle connection timeout
			TLSHandshakeTimeout:   10 * time.Second,
			ExpectContinueTimeout: 1 * time.Second,
			DisableKeepAlives:     false, // Enable KeepAlives for connection reuse
			ForceAttemptHTTP2:     false, // Avoid HTTP/2 framing errors
		}
	})
	return baseTransport
}
```

*   **说明**：`getBaseTransport` 以单例方式提供统一的 `http.Transport`，设置全局最大空闲连接数（MaxIdleConns）、单 host 最大空闲连接数（MaxIdleConnsPerHost）、空闲连接超时（IdleConnTimeout），并将 `DisableKeepAlives` 设为 `false` 以启用 TCP 长连接复用。该 Transport 被 11.2.1 中复用的 `http.Client` 使用，既满足连接池调优，又避免为每次请求新建连接，对应 11.1.1 中“连接池调优”在 LLM 调用侧的实现。

## 结论

通过 Hertz 的 KeepAlive 与超时配置、数据库的 MaxIdleConns / MaxOpenConns / ConnMaxLifetime，以及 LLM 调用侧 Transport 的 MaxIdleConns、MaxIdleConnsPerHost 与 KeepAlive 设置，本项目在网关、数据库和模型 API 三层实现了可配置或合理默认的连接池与长连接调优，与书中 11.1.1“连接池调优：KeepAlive 与 MaxIdleConns 设置”的实践一致，为高并发场景下的稳定与性能提供了基础。
