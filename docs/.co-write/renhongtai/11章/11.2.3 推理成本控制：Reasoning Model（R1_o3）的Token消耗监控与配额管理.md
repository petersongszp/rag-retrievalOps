# 11.2.3 推理成本控制：Reasoning Model（R1/o3）的 Token 消耗监控与配额管理

## 概念描述

在使用 Reasoning Model（如 OpenAI o3、豆包 R1、DeepSeek R1）或高单价模型时，单次请求的 Token 消耗往往远高于普通对话模型，若不加以监控与限制，容易造成成本失控或单用户占用过多资源。

本节涉及的“推理成本控制”主要包括：

1. **Token 消耗监控**：在每次模型调用结束（Eino 回调 OnEnd）时，从输出中解析出 prompt/completion/total token 数，并**按用户、按日**累计到 Redis 等存储中，便于统计、对账与后续的配额判断。
2. **配额管理**：在用户发起新一轮推理（如开始一场面试）前，先检查该用户**当日已消耗 Token 是否超过配置的上限**；若超过则拒绝并返回友好提示（如“当日 Token 配额已用尽，明日再试或联系管理员”），从而对 Reasoning Model 等高成本调用做每用户每日上限控制。
3. **与 Eino 监控的集成**：通过 `TokenRecorder` 接口与 `DefaultTokenRecorder` 全局注入，在监控回调 OnEnd 中自动调用 `Record` 记录消耗；在面试引擎 RunInterviewLoopWithGraph 入口处注入 UserID、调用 `CheckQuota`，实现“开场前检查、过程中记录”的闭环。

本项目通过配置项 `eino.token_quota_per_user_per_day`（0 表示不限制）与 Redis 实现的 `TokenRecorder`，在面试主流程中接入了 Token 监控与配额检查，对应书中 11.2.3“推理成本控制：Reasoning Model（R1/o3）的 Token 消耗监控与配额管理”。

## 项目实现概览

本项目在以下方面实现了 11.2.3 的推理成本控制：

1. **接口与全局注入**：在 `pkg/eino/callbacks` 中定义 `TokenRecorder` 接口（`Record`、`CheckQuota`）与 `DefaultTokenRecorder`；在 `main.go` 启动时，若配置的 `TokenQuotaPerUserPerDay > 0`，则用 Redis 与上限值创建 `llm.NewTokenRecorder` 并赋给 `DefaultTokenRecorder`。
2. **Redis 实现**：`internal/agents/llm/tokenquota.go` 中的 `tokenRecorder` 按“用户 ID + 日期”生成 Redis 键，`Record` 时 Pipeline 执行 INCRBY 与 EXPIRE，`CheckQuota` 时 GET 当前值并与 limit 比较，超限返回 error。
3. **监控侧记录**：`MonitoringHandler.OnEnd` 中若 `DefaultTokenRecorder != nil` 且 context 带 UserID，则从 CallbackOutput 解析 token 数并调用 `Record`，实现“每次组件结束自动累计”。
4. **面试侧检查与 UserID 注入**：在 `RunInterviewLoopWithGraph` 开头调用 `WithUserID(ctx, session.UserID)`，然后若 `DefaultTokenRecorder != nil` 则调用 `CheckQuota`，失败则打日志并通过 `SendErrorEvent` 返回错误给前端，不再进入面试流程。

## 核心功能代码

### 1. TokenRecorder 接口与 DefaultTokenRecorder

在 callbacks 包中定义 Token 记录与配额检查接口，并由应用在启动时注入具体实现，实现 11.2.3 的“监控 + 配额”扩展点。

**Go 语言代码片段 (`backend/pkg/eino/callbacks/monitoring.go`)**:

```go
	ctxKeyUserID    contextKey = "userID" // 11.2.3 用于 Token 监控与配额（可选注入）
)

// ...

// WithUserID 11.2.3 注入 UserID 到 context，供 Token 监控/配额使用（如面试引擎在 RunInterviewLoopWithGraph 前调用）
func WithUserID(ctx context.Context, userID uint) context.Context {
	return context.WithValue(ctx, ctxKeyUserID, userID)
}

// TokenRecorder 11.2.3 推理成本控制：Token 消耗记录与配额检查（可由 internal/agents/llm/tokenquota 实现）
type TokenRecorder interface {
	Record(ctx context.Context, userID uint, promptTokens, completionTokens, totalTokens int64)
	CheckQuota(ctx context.Context, userID uint) error

// DefaultTokenRecorder 应用启动时注入（如 main 或面试引擎初始化时），未设置则不记录/不检查配额
var DefaultTokenRecorder TokenRecorder
```

*   **说明**：`WithUserID` 将 userID 放入 context，供 OnEnd 中 Record 使用；`TokenRecorder` 定义记录与配额检查两个方法；`DefaultTokenRecorder` 由 main 在启动时按配置注入，未注入则监控与配额逻辑均不生效，实现 11.2.3 的可选推理成本控制。

### 2. OnEnd 中根据 UserID 与输出记录 Token

在监控回调 OnEnd 中，若注入了 TokenRecorder 且 context 带 UserID，则从 CallbackOutput 解析 token 数并调用 Record，实现“每次推理结束自动累计”。

**Go 语言代码片段 (`backend/pkg/eino/callbacks/monitoring.go`)**:

```go

	tokenInfo := extractTokenUsage(output)
	// 11.2.3 Token 监控：若有注入 Recorder 且 context 带 UserID，则记录本次消耗

		if uid, _ := ctx.Value(ctxKeyUserID).(uint); uid != 0 {
			if p, c, t, ok := extractTokenUsageValues(output); ok && t > 0 {

			}
		}
	}

	log.Printf("[Eino Monitor] [TraceID: %s] End Component: %s (%s), Latency: %dms%s",
		traceID, info.Name, info.Component, latencyMs, tokenInfo)
```

*   **说明**：OnEnd 中先格式化 token 日志（使用 11.2.2 的 bufferPool），再在存在 DefaultTokenRecorder 且 context 中有 UserID 时，用 `extractTokenUsageValues` 解析出 prompt/completion/total token，若 total > 0 则调用 `Record`，实现 11.2.3 的 Token 消耗监控与 Eino 回调的集成。

### 3. Redis 实现：按用户按日累计与配额检查

Token 记录与配额检查的 Redis 实现，键为“用户 ID + 日期”，Record 用 INCRBY 累计并设置过期，CheckQuota 读取当前值与上限比较。

**Go 语言代码片段 (`backend/internal/agents/llm/tokenquota.go`)**:

```go
const (
	tokenUsageKeyPrefix = "token_usage:user:"
	tokenUsageKeyTTL    = 48 * time.Hour // 保留 2 天便于统计
)

// tokenRecorder 11.2.3 推理成本控制：基于 Redis 的每用户每日 Token 消耗记录与配额检查（含 R1/o3 等 Reasoning Model）
type tokenRecorder struct {
	redis *redis.Client
	limit int // 每用户每日上限，0 表示不限制
}

// NewTokenRecorder 创建 Token 记录/配额器，limit 为每用户每日上限（0 表示不限制）
func NewTokenRecorder(redisClient *redis.Client, limit int) callbacks.TokenRecorder {
	if redisClient == nil {
		return nil
	}
	return &tokenRecorder{redis: redisClient, limit: limit}
}

func (r *tokenRecorder) key(userID uint) string {
	return tokenUsageKeyPrefix + fmt.Sprintf("%d", userID) + ":" + time.Now().Format("2006-01-02")
}

// Record 记录本次调用的 Token 消耗（OnEnd 时由 monitoring 回调）
func (r *tokenRecorder) Record(ctx context.Context, userID uint, promptTokens, completionTokens, totalTokens int64) {
	if r == nil || r.redis == nil || totalTokens <= 0 {
		return
	}
	k := r.key(userID)
	pipe := r.redis.Pipeline()
	pipe.IncrBy(ctx, k, totalTokens)
	pipe.Expire(ctx, k, tokenUsageKeyTTL)
	_, _ = pipe.Exec(ctx)
}

// CheckQuota 在发起推理前调用，若用户当日已超配额则返回 error（用于 Reasoning Model 等成本控制）
func (r *tokenRecorder) CheckQuota(ctx context.Context, userID uint) error {
	if r == nil || r.redis == nil || r.limit <= 0 {
		return nil
	}
	k := r.key(userID)
	n, err := r.redis.Get(ctx, k).Int64()
	if err == redis.Nil {
		return nil
	}
	if err != nil {
		return err
	}
	if n >= int64(r.limit) {
		return fmt.Errorf("当日 Token 配额已用尽（已用 %d，上限 %d），明日再试或联系管理员", n, r.limit)
	}
	return nil
}
```

*   **说明**：键格式为 `token_usage:user:{userID}:{yyyy-MM-dd}`，实现按用户按日统计。Record 用 Pipeline 执行 INCRBY 与 EXPIRE，保证累计与 TTL 一致；CheckQuota 读取该键，达到或超过 limit 时返回错误。这样实现 11.2.3 的 Token 消耗监控与每用户每日配额管理，适用于 Reasoning Model（R1/o3）等高成本模型的成本控制。

### 4. 启动时注入与配置

在 main 中根据配置决定是否启用 Token 配额，并注入 DefaultTokenRecorder；配置结构中提供每用户每日上限字段。

**Go 语言代码片段 (`backend/cmd/server/main.go`)**:

```go
	// 11.2.3 推理成本控制：Token 消耗监控与配额（Reasoning Model R1/o3 等），0 表示不限制
	if cfg.Eino.TokenQuotaPerUserPerDay > 0 {
		callbacks.DefaultTokenRecorder = llm.NewTokenRecorder(repository.GetRedis(), cfg.Eino.TokenQuotaPerUserPerDay)
		log.Printf("[11.2.3] Token quota enabled: %d per user per day", cfg.Eino.TokenQuotaPerUserPerDay)
	}
```

**配置结构 (`backend/internal/config/config.go`)**:

```go
// EinoConfig Eino框架配置
type EinoConfig struct {
	// ...
	// 11.2.3 推理成本控制：每用户每日 Token 配额（含 Reasoning Model R1/o3 等），0 表示不限制
	TokenQuotaPerUserPerDay int `yaml:"token_quota_per_user_per_day"`
}
```

*   **说明**：仅当 `TokenQuotaPerUserPerDay > 0` 时创建并注入 `DefaultTokenRecorder`，并打日志便于运维确认 11.2.3 已启用。配置为 0 时不注入，不记录、不检查配额，保持对现有部署的兼容。

### 5. 面试流程中的 UserID 注入与开场前配额检查

在面试图循环入口处注入 UserID 并在开场前检查配额，超限则直接返回错误事件，不再进入面试。

**Go 语言代码片段 (`backend/internal/service/interview/engine/graph_loop.go`)**:

```go
// RunInterviewLoopWithGraph 使用 Eino Graph 编排运行面试循环
func (e *InterviewEngine) RunInterviewLoopWithGraph(ctx context.Context, session *InterviewSession) {
	// 12.1.1 全链路监控：整场面试共享同一 TraceID，便于日志聚合与回溯
	ctx = mycallbacks.WithTraceID(ctx, session.SessionID)
	// 11.2.3 Token 监控与配额：注入 UserID 供 OnEnd 记录消耗；开场前检查当日配额
	ctx = mycallbacks.WithUserID(ctx, session.UserID)
	if mycallbacks.DefaultTokenRecorder != nil {
		if err := mycallbacks.DefaultTokenRecorder.CheckQuota(ctx, session.UserID); err != nil {
			log.Printf("[Graph] Token quota exceeded for user %d: %v", session.UserID, err)
			SendErrorEvent(e.writer, err.Error())
			return
		}
	}
	// ... 后续面试逻辑
```

*   **说明**：在面试开始前注入 UserID，确保后续 OnEnd 中能按用户记录；若启用了 TokenRecorder 且 CheckQuota 返回错误（当日已超配额），则打日志并通过 `SendErrorEvent` 将错误信息返回前端，不进入面试流程，实现 11.2.3 的“开场前检查、过程中记录”的推理成本控制闭环。

## 结论

通过 `TokenRecorder` 接口与 Redis 实现的按用户按日累计、启动时按配置注入 `DefaultTokenRecorder`、在 OnEnd 中自动 Record 以及在面试入口处 WithUserID 与 CheckQuota，本项目实现了 Reasoning Model（R1/o3）等模型的 Token 消耗监控与每用户每日配额管理，与书中 11.2.3“推理成本控制：Reasoning Model（R1/o3）的 Token 消耗监控与配额管理”的实践一致。配置 `eino.token_quota_per_user_per_day` 为大于 0 即可启用，为 0 则不限制、不记录。
