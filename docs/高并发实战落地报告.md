# 高并发企业级 AI 智能体实战：工程化落地报告

## 1. 核心治理架构升级

为了支撑企业级高并发场景，本项目在原有架构基础上进行了三层治理升级：

1.  **流量接入层（防护盾）**：引入 IP 级限流，防止恶意流量打穿服务。
2.  **异步处理层（蓄水池）**：优化 MQ 消费模型，从“无限并发”改为“协程池”模式，防止内存溢出。
3.  **外部调用层（保险丝）**：针对 AI 模型调用引入熔断机制，防止下游不稳定拖垮整个系统。

## 2. 关键代码实现

### 2.1 流量接入层：Hertz 限流中间件

我们使用 `golang.org/x/time/rate` 实现了基于令牌桶算法的 IP 限流中间件。

**代码位置**: `backend/internal/middleware/ratelimit.go`

```go
// 核心逻辑
func (i *IPRateLimiter) Handler() app.HandlerFunc {
    return func(c context.Context, ctx *app.RequestContext) {
        ip := ctx.ClientIP()
        limiter := i.getLimiter(ip)

        if !limiter.Allow() {
            ctx.AbortWithStatusJSON(http.StatusTooManyRequests, ...)
            return
        }
        ctx.Next(c)
    }
}
```

**配置**: 在 `main.go` 中配置为每秒 20 QPS (Burst 50)。

### 2.2 外部调用层：AI 服务熔断器

我们封装了 `github.com/sony/gobreaker`，并在 OpenAI HTTP Client 层进行了无侵入式集成。

**代码位置**:
- `backend/pkg/circuitbreaker/breaker.go`
- `backend/chatApp/chat/openAi.go`

**熔断策略**:
- 连续失败/超时 5 次 -> 触发熔断。
- 熔断后 30 秒内直接拒绝请求，快速失败。
- 30 秒后进入半开状态，尝试恢复。

### 2.3 异步处理层：MQ 协程池

针对 Redis Queue 的消费者，我们引入了 `ants` 协程池库，限制最大并发 Goroutine 数量为 1000。

## 3. 压测与验证方案

### 3.1 压测工具准备
推荐使用 `wrk` (HTTP 基准测试) 或 `JMeter`。

### 3.2 场景一：验证限流 (Rate Limiting)

**目标**: 验证系统在流量洪峰下的自我保护能力。

**命令**:
```bash
# 模拟 100 个并发连接，持续 30 秒，攻击不需要登录的接口
wrk -t4 -c100 -d30s http://localhost:8080/api/ping
```

**预期结果**:
- QPS 稳定在 20 左右（受限于限流配置）。
- 大量请求返回 `429 Too Many Requests`。
- 系统内存和 CPU 保持平稳，未出现崩溃。

### 3.3 场景二：验证熔断 (Circuit Breaker)

**目标**: 验证 AI 服务不可用时，系统的快速响应能力。

**步骤**:
1.  修改 `config.yaml`，将 OpenAI API Key 设为无效值，或断开网络。
2.  发起对话请求。
3.  观察日志：
    - 前 5 次请求：响应较慢（等待超时或 API 返回错误）。
    - 第 6 次起：响应极快，日志显示 `circuit breaker is open`。
4.  恢复配置，等待 30 秒，验证服务自动恢复。

### 3.4 场景三：验证协程池 (Worker Pool)

**目标**: 验证在高并发任务积压时，内存不会爆炸。

**步骤**:
1.  向 Redis 队列快速推入 10,000 条任务。
2.  观察 `pprof` 的 Goroutine 数量。
    - **预期**: Goroutine 数量稳定在 ~1000 个左右（Pool Size）。
    - **对比组**: 如果不使用 Pool，Goroutine 数量会飙升至 10,000+，可能导致 OOM。

## 4. 下一步建议

1.  **配置中心化**: 将限流阈值、熔断策略等参数移入 `config.yaml` 或配置中心 (Nacos/Consul)，支持动态调整。
2.  **监控大盘**: 接入 Prometheus + Grafana，可视化展示：
    - 实时 QPS / 拒绝率
    - 熔断器状态 (Closed/Open)
    - 协程池使用率
3.  **分布式限流**: 当前为单机限流，多实例部署时建议升级为 Redis Lua 分布式限流。
