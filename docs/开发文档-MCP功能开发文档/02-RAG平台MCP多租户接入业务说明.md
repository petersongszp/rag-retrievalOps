# RAG 平台 MCP 多租户接入业务说明

本文档面向产品、业务负责人、企业接入方、平台运营人员和交付同学，说明为什么要把当前 RAG 平台的接入方式从传统 HTTP/SDK 扩展为 MCP 接入，以及这次改造对接入模式、租户隔离、使用流程和协作方式会带来什么变化。

## 1. 文档目标

这份文档不讨论底层代码实现细节，重点回答四个业务问题：

1. 为什么要引入 MCP 接入方式
2. MCP 接入后，企业客户、业务 Agent、平台运营分别怎么使用
3. 多租户和权限边界怎么保证
4. 现有 HTTP 接入方如何兼容和迁移

## 2. 现状与问题

当前平台已经具备较完整的 RAG 能力：

- 知识库管理
- 文档上传与入库
- 检索召回
- 检索审计
- 引用溯源
- 管理后台运营能力

当前企业接入方式主要是：

- 管理侧通过后台或管理接口维护知识库
- 业务侧通过 `POST /v1/retrieve` 调用检索接口
- 接入方自己把检索结果组装到 Prompt，再调用自己的大模型生成回答

这种方式可以工作，但也存在几个明显问题：

### 2.1 接入协议不统一

不同 Agent 平台、不同语言栈、不同智能体框架，往往都要自己封装 HTTP Client 或 SDK。结果是：

- 接入成本重复
- 各家封装方式不一致
- 排障时难以统一定位问题

### 2.2 Agent 工具化接入不自然

越来越多的智能体平台不是直接让业务代码手写 HTTP，而是更偏向“工具调用”模式。当前平台虽然有检索接口，但它在智能体生态里还不是一个标准工具。

### 2.3 多语言接入成本偏高

如果只提供 Go 侧思路，其他语言团队仍然要重复理解接口、鉴权和错误处理，无法真正做到低门槛接入。

### 2.4 多租户能力有，但接入表达不够标准

当前平台已经具备：

- 租户
- API Key
- 租户与知识库授权
- 基于 `JWT/API Key -> tenant -> KB permission` 的访问控制

但这些能力目前主要暴露在 HTTP API 语义里，还没有通过 MCP 这种跨平台工具协议表达出来。

## 3. 为什么要引入 MCP

MCP 的核心价值，不是替代 RAG 检索本身，而是把“调用平台检索能力”标准化成智能体可理解、可发现、可调用的工具接口。

引入 MCP 后，平台的业务意义主要体现在以下几个方面。

### 3.1 统一 Agent 接入协议

企业侧不需要再围绕不同 Agent 框架分别封装 HTTP 调用逻辑，而是统一通过 MCP 工具方式接入平台检索能力。

这意味着：

- 智能体平台更容易接入
- 工具定义更一致
- 后续扩展更多工具能力更自然

### 3.2 降低接入门槛

对业务方来说，理解“有一个工具叫 `retrieve_knowledge`，输入 query 和 kb_ids，返回可引用证据”通常比理解一整套 HTTP API 更直接。

### 3.3 更适合多语言生态

MCP 的优势在于协议统一，而不是语言绑定。只要客户端支持 MCP，就可以用：

- TypeScript
- Python
- Java
- Go

等不同语言栈，按一致方式调用平台。

### 3.4 平台边界更清晰

引入 MCP 后，平台对外能力可以分成两类：

- 管理能力：继续由后台和管理接口负责
- 检索能力：通过 MCP 工具标准化提供给各类 Agent

这会让平台的“运营侧”和“调用侧”边界更加清楚。

## 4. 本次业务方案的范围

这次 MCP 改造是 V1，不是一次性把全部能力都搬到 MCP。

### 4.1 V1 纳入 MCP 的能力

V1 只纳入一项能力：

- 检索工具 `retrieve_knowledge`

它的业务作用是：

- 让企业 Agent 在生成答案前，从 RAG 平台召回知识证据
- 返回结构化检索结果，供 Agent 拼装回答或做引用展示

### 4.2 V1 不纳入 MCP 的能力

以下能力继续保持原方式，不进入本次 MCP 范围：

- 创建知识库
- 上传文档
- 查看入库任务
- 检索审计后台查询
- 评测与实验
- 策略治理
- 告警、报表、运维工具

原因很简单：

- 这些能力本质上属于运营后台能力
- 使用者通常不是在线业务 Agent，而是运营、算法、知识库管理员
- V1 先把“业务 Agent 的标准检索接入”解决掉，收益最大、风险最低

## 5. 改造后的业务接入模式

改造后，平台会同时保留两种对外调用方式：

1. HTTP 直连方式
2. MCP 工具方式

其中推荐关系如下：

- 新业务、Agent 平台、跨语言接入：优先走 MCP
- 现有系统、已跑通的服务端调用：可继续保留 HTTP

### 5.1 新的推荐链路

```text
企业 Agent / 智能体平台
        │
        │ 调用 MCP Tool: retrieve_knowledge
        ▼
RAG MCP Server
        │
        │ 透传 Authorization Bearer 凭证
        ▼
RAG Platform /v1/retrieve
        │
        ├─ tenant 校验
        ├─ API Key / JWT 校验
        ├─ KB 权限校验
        └─ 检索执行
        ▼
返回结构化证据结果
        │
        ▼
Agent 继续生成最终回答
```

### 5.2 业务含义

这个链路说明一件事：

- MCP Server 负责“协议适配”
- RAG 平台仍然负责“真正的业务鉴权与检索”

这样做的好处是，租户隔离、知识库授权和现有审计链路都不用重做。

需要特别说明的是，MCP Server 只负责把调用方的身份凭证带到 RAG 平台，不应该自己解释租户归属，也不应该让调用方在工具参数里直接传入 `tenant_id` 来覆盖身份。生产接入建议优先使用平台签发的 API Key；如果使用 JWT，需要确认该 JWT 能被 `/v1/retrieve` 当前鉴权链路识别。

## 6. 多租户业务设计

这是这次方案最重要的业务约束。

### 6.1 多租户复用现有平台能力

平台现有多租户逻辑继续保留并复用：

- 每个租户拥有自己的知识库范围
- 每个租户可创建独立 API Key
- API Key 可控制可访问的知识库范围
- JWT 也可映射到租户身份

MCP 不新增一套租户体系，不新建一套权限表，也不重复做知识库授权。

### 6.2 多租户的业务原则

MCP 只做一件事：

- 把调用方携带的 Bearer Token 原样带到现有 RAG 平台

RAG 平台继续负责：

- 识别这个 token 属于哪个租户
- 校验这个租户能访问哪些知识库
- 决定这次检索是否允许执行

补充约束：

- MCP Server 不保存、不打印明文 Token、API Key 或 JWT
- MCP Tool 入参不接受 `tenant_id`、`api_key_id` 这类身份覆盖字段
- 租户身份只能由 RAG 平台根据凭证解析得出
- legacy `app_id` 只作为旧链路兼容，不建议作为 MCP 生产接入方式
- API Key 过期、吊销、租户停用、知识库未授权时，必须由 RAG 平台返回明确拒绝结果

### 6.3 为什么不能把共享多租户压在 stdio 上

从业务角度讲，`stdio` 更像：

- 本地开发模式
- 单用户桌面客户端模式
- 本地调试模式

它不适合作为企业内共享、多租户统一接入入口，原因是：

- 一个本地 `stdio` 进程天然更像一个单会话工具
- 不容易表达每次请求的独立身份
- 不适合作为统一网关部署
- 很容易把租户凭证和工具运行环境耦合在一起

所以本次业务方案明确规定：

- 共享部署、多租户接入：走 HTTP MCP
- 本地开发、桌面工具接入：可走 stdio

## 7. 两种 MCP 使用场景

### 7.1 HTTP MCP

这是企业标准接入主路径。

适用场景：

- 企业内部统一部署
- 多个业务 Agent 共用一套 MCP 服务
- 多租户并发接入
- 多语言客户端接入

业务特点：

- 每个调用方自己携带 Bearer Token
- MCP Server 不持久保存每个租户的业务权限
- 统一通过现有 RAG 平台完成授权判断

### 7.2 stdio MCP

这是本地调试和单用户接入路径。

适用场景：

- 本地开发
- IDE/桌面智能体客户端调试
- 单人验证知识库检索效果

业务特点：

- 可以通过本地环境变量配置访问 token
- 更适合单租户、单应用场景
- 不作为企业共享接入主模式

## 8. 对不同角色的价值

### 8.1 对企业业务方

收益：

- 接入标准更统一
- 新 Agent 更容易接平台能力
- 多语言团队都能复用同一套方式
- 不需要了解向量库、Embedding、检索链路细节

### 8.2 对 Agent 开发团队

收益：

- 把平台能力作为标准工具使用
- 更容易在 Agent 编排框架中接入
- 可以减少自定义 SDK 和 HTTP 适配代码

### 8.3 对平台运营和交付团队

收益：

- 管理能力继续保留在后台，不影响现有流程
- 调用能力标准化后，更容易做客户交付
- 后续可以围绕 MCP 继续扩展更多标准工具

## 9. 工具能力说明

V1 统一提供一个 MCP 工具：

- `retrieve_knowledge`

它的业务语义是：

- 根据问题内容，在指定知识库中检索候选知识证据
- 返回可用于回答生成和引用展示的结构化结果

### 9.1 输入信息

接入方需要提供：

- `query`
- `kb_ids` 或 `kb_id`

可选提供：

- `top_k`
- `strategy_profile`
- `metadata_filter`

其中 `strategy_profile` 和 `metadata_filter` 在 V1 中建议作为预留或透传字段处理。只有当底层 `/v1/retrieve` 和检索链路已经明确支持对应策略选择或元数据过滤时，才承诺业务生效；否则 MCP 工具可以接收这些字段，但需要在接入文档中标注为“暂不保证生效”。

### 9.2 输出信息

平台会返回：

- `request_id`
- `items`
- `strategy_version`

其中 `items` 会包含：

- `content`
- `score`
- `citation`
- `source`

业务方可以直接把这些结果：

- 拼进 Prompt
- 用于答案引用展示
- 用于审计排查时回查 `request_id`

V1 对外建议把 `request_id`、`items[].content`、`items[].score`、`items[].citation`、`items[].source` 作为稳定字段。`strategy_version`、`request_cost`、`citation_check`、`refusal`、`evidence_gate_result` 等字段可以作为增强字段，是否出现取决于当前 RAG 检索链路能力。

### 9.3 错误语义

MCP Server 不应该吞掉 RAG 平台返回的关键错误语义。建议至少保持下面几类业务错误可被接入方识别：

- 未携带凭证或凭证无效：认证失败
- API Key 过期或吊销：认证失败
- 租户停用：禁止访问
- 知识库不存在：资源不存在
- 知识库未授权或跨租户访问：禁止访问
- 检索超时或后端不可用：服务异常或超时

这样 Agent 平台才能区分“应该提示配置问题”“应该换凭证”“应该降级回答”还是“稍后重试”。

## 10. 与现有 HTTP 接入的关系

这次改造不是推翻现有 HTTP 接入，而是增加一个新的标准入口。

### 10.1 保留兼容

现有能力继续有效：

- `POST /v1/retrieve` 继续保留
- 管理后台继续保留
- 管理接口继续保留

### 10.2 推荐迁移方向

建议分两类看：

- 已经稳定跑通的现网业务：先不强制迁移
- 新接入的 Agent 平台和新业务：优先采用 MCP

### 10.3 迁移收益

从业务角度，迁移到 MCP 的收益不是“功能变强”，而是：

- 接入标准更统一
- 复用成本更低
- 跨语言和跨 Agent 平台更自然
- 后续能力扩展更顺滑

## 11. 接入流程建议

建议企业接入时按下面顺序推进：

### 11.1 第一步：完成知识准备

- 创建知识库
- 上传业务资料
- 等待入库完成
- 在管理后台确认检索效果

### 11.2 第二步：申请接入凭证

- 为租户或应用创建 API Key
- 配置可访问的知识库范围
- 明确是测试环境还是生产环境凭证

### 11.3 第三步：接入 MCP

- 如果是企业共享服务，接 HTTP MCP
- 如果是本地调试，接 stdio MCP

### 11.4 第四步：业务联调

- Agent 调用 `retrieve_knowledge`
- 验证召回结果是否正确
- 验证是否能正确拼接到业务回答链路
- 验证错误权限下是否能正确拦截

### 11.5 第五步：上线与运营

- 观察检索效果
- 通过 `request_id` 做排障
- 继续用后台维护知识库和检索策略

### 11.6 上线验收建议

MCP 接入上线前，建议至少完成以下验收：

- 无凭证调用 `retrieve_knowledge` 必须失败
- 使用有效 API Key 调用已授权知识库必须成功
- 使用过期或吊销 API Key 必须失败
- 调用未授权知识库必须失败
- 跨租户知识库不能被召回
- 每次成功检索都能通过 `request_id` 在审计日志中回查
- 审计日志能记录 `tenant_id`、`app_id`、`api_key_id`、`auth_type`、`source_api`
- MCP Server 日志中不出现明文 Token、API Key、JWT
- `top_k` 超过平台上限时能被平台限制或拒绝
- RAG 平台超时或不可用时，MCP Server 能返回可识别错误

## 12. 业务边界与约束

### 12.1 MCP 不是后台替代品

MCP V1 的定位是“业务调用工具层”，不是“后台管理能力替代品”。

所以：

- 管理动作继续走后台
- 运营动作继续走后台
- 检索调用走 MCP

### 12.2 MCP 不负责最终回答

平台负责的是检索和证据提供，不负责替企业业务方决定：

- 最终 Prompt 怎么写
- 回答由哪个大模型生成
- 生成后怎么展示给用户

### 12.3 MCP 不改变租户权限模型

MCP 不会改变现有平台的：

- 租户归属
- API Key 归属
- 知识库授权模型

它只是让这些能力以更标准的工具协议被调用。

## 13. 常见业务问题

### 13.1 现有 HTTP 接入要不要马上下线

不用。

建议策略是：

- 存量业务保留
- 新业务优先 MCP
- 等 MCP 跑稳定后，再评估是否统一迁移

### 13.2 如果一个企业有多个租户怎么办

每个租户继续使用自己的：

- API Key
- JWT
- 知识库授权关系

HTTP MCP 共享部署即可，不需要为每个租户单独发一套 MCP 协议实现。

### 13.3 为什么本地 stdio 不建议做共享多租户

因为它更适合本地工具进程模型，不适合企业统一网关化接入。业务上如果强行这么做，会让：

- 凭证管理复杂
- 客户端兼容性变差
- 安全边界变模糊

### 13.4 为什么 V1 只做检索工具

因为检索是业务 Agent 最核心、最高频、最容易标准化的调用动作。先把这一步做稳，业务收益最大，推广阻力最小。

## 14. 建议的对外口径

如果后续要对企业客户、内部业务团队或交付团队说明这次改造，可以统一用下面这段话：

“RAG 平台在保留现有 HTTP 检索接口的基础上，新增了 MCP 标准接入方式。以后企业 Agent 可以把平台检索能力当作标准工具调用，底层仍然复用现有多租户、API Key、知识库权限和检索审计能力。共享部署场景推荐使用 HTTP MCP，本地调试场景可使用 stdio MCP。V1 先聚焦检索工具，不改变后台管理方式。”

## 15. 后续演进方向

在 V1 稳定后，可以再评估是否逐步扩展：

- 知识库查询类工具
- 检索日志查询类工具
- 简化版审计查询工具
- 业务友好的平台 SDK 封装

但这些都建议放在 V2 之后，不影响当前业务接入主线。

## 16. 结论

这次引入 MCP 的本质，不是改掉 RAG 平台原来的核心能力，而是把“平台检索能力”变成更适合智能体时代的标准工具。

最终形成的业务格局是：

- 后台继续做运营管理
- RAG 平台继续做检索和权限控制
- MCP 负责标准化接入
- 企业 Agent 更低成本地接入平台能力

对于多租户场景，核心原则非常明确：

- 权限不重做
- 租户模型不重做
- MCP 只做协议适配
- 真正的访问控制继续复用现有平台逻辑

这也是这次方案最重要的业务价值。
