# 后台管理平台知识库页面使用文档

## 背景

这篇文档用于帮助用户和开发学习者快速上手后台管理平台里的“知识库”功能。

这里的“知识库页面”实际上包含两层页面：

1. 知识库列表页：`/knowledge-bases`
2. 知识库详情页：`/knowledge-bases/[kbId]`

这两个页面共同组成了后台知识库管理的主流程。用户通常会先在列表页创建或选择知识库，再进入详情页完成文档上传、入库任务跟踪、失败重试、任务取消等操作。

## 这篇文档会做什么

看完这篇文档，你应该能理解下面几件事：

1. 知识库页面在整个后台里承担什么角色。
2. 列表页和详情页分别解决什么问题。
3. 页面上的每个核心区域、按钮、表格字段分别是什么意思。
4. 文档上传、入库任务、删除文档、重试任务这些动作的后端口径是什么。
5. 当前实现里有哪些使用限制，哪些地方后续值得优化。

## 需要先理解的术语

### 知识库

知识库可以理解成一组被系统统一管理的文档集合。后续检索、问答、实验评测，都是基于这些知识库里的内容展开的。

### 文档

文档是被上传进知识库的原始资料。当前后台允许的文件类型是：

1. `pdf`
2. `txt`
3. `md`
4. `markdown`

### 入库任务

文档上传后，系统不会立刻就能检索，而是要进入一条“入库任务”流程。这个流程通常会完成文件解析、切分、向量化、写入索引等动作。

### 任务状态

当前入库任务常见状态有：

1. `pending`：已创建，等待处理
2. `processing`：正在处理
3. `completed`：处理完成
4. `failed`：处理失败
5. `retrying`：准备重试或重试中
6. `dead`：多次失败后进入不可自动恢复状态
7. `canceled`：被人工取消

### Contract gap

知识库详情页里有些字段如果后端暂时没返回，会显示 `Contract gap`。

这不是业务值，而是在提示你：“前端页面预期这里应该有数据，但当前接口合同里没有给到，或者当前记录没有这个值”。

## 整体流程

从用户进入知识库页面到完成一次文档入库，主流程是这样的：

1. 打开知识库列表页。
2. 新建一个知识库，或者进入已有知识库。
3. 在知识库详情页上传文档。
4. 系统创建文档记录和入库任务记录。
5. 后端把任务投递到消息队列，异步执行入库。
6. 页面轮询任务列表，持续刷新处理中状态。
7. 如果任务成功，文档状态会进入 `completed`。
8. 如果任务失败，用户可以在任务表里重试或取消。

这条链路体现了这个项目后台知识库模块的亮点：它不是只做一个“上传文件”的静态后台，而是把知识库、任务状态和检索能力衔接成了完整的运维闭环。

## 页面定位与项目亮点

知识库页面在整个后台里主要承担三个角色：

1. 资源管理入口：创建和查看知识库。
2. 内容入库入口：上传文档并触发入库流程。
3. 运维排障入口：通过任务状态、错误信息和重试操作定位问题。

对用户来说，知识库页面回答的是“资料放到哪里、是否已经可用、失败后怎么办”。

对开发和运维来说，知识库页面回答的是“前端当前暴露了哪些能力、这些能力对应哪些后端接口、状态机怎么流转、哪里可能出现认知偏差”。

## 页面使用说明

## 列表页

### 页面入口

列表页路由是：

1. `admin/src/app/(admin)/knowledge-bases/page.tsx`
2. `admin/src/components/admin/knowledge-bases-page.tsx`

在后台左侧导航里，对应菜单是“知识库”。

### 页面作用

知识库列表页主要做三件事：

1. 展示当前可见的知识库列表。
2. 提供“新建知识库”入口。
3. 作为进入知识库详情页的跳板。

### 页面顶部按钮

列表页右上角有两个常用按钮：

1. `刷新`
   作用：重新请求知识库列表。
2. `新建`
   作用：打开“新建知识库”弹窗。

如果当前账号被前端判断为权限不足，`新建` 按钮会被禁用。

### 列表卡片说明

每个知识库会显示一张卡片，主要字段包括：

| 字段 | 含义 | 说明 |
| --- | --- | --- |
| 名称 | 知识库名称 | 列表中最主要的识别信息 |
| 状态 | 当前知识库状态 | 当前主要是 `active`，页面暂未提供停用操作 |
| 描述 | 对知识库用途的补充说明 | 可以为空 |
| 创建时间 | 该知识库的创建时间 | 便于区分新旧库 |

每张卡片都有两个入口：

1. `打开` 按钮
2. `查看详情` 链接

它们最终都会进入 `/knowledge-bases/{id}` 详情页。

### 新建知识库弹窗

新建弹窗文件在：

`admin/src/components/admin/create-knowledge-base-modal.tsx`

用户需要填写两个字段：

| 字段 | 是否必填 | 含义 |
| --- | --- | --- |
| 名称 | 是 | 知识库的唯一名称 |
| 描述 | 否 | 用于说明知识库用途 |

这里有两个很重要的实现细节：

1. 名称为空会被前后端同时拦截。
2. 当前后端按“全局名称唯一”校验，不是“同一用户下唯一”。

也就是说，不同用户也不能创建同名知识库。

### 空状态说明

如果当前没有任何知识库，页面会显示空状态提示，引导用户先新建一个知识库。

这个设计很适合首次接触系统的人，因为它把“从零开始的第一步”说得很明确。

## 详情页

### 页面入口

详情页路由是：

1. `admin/src/app/(admin)/knowledge-bases/[kbId]/page.tsx`
2. `admin/src/components/admin/knowledge-base-detail-page.tsx`

### 页面作用

详情页是知识库操作的核心页面，主要承担下面几件事：

1. 查看当前知识库的基本信息。
2. 上传文档。
3. 查看文档列表。
4. 查看入库任务列表。
5. 对失败任务进行重试。
6. 对未完成任务进行取消。
7. 删除文档。

### 页面顶部区域

详情页顶部通常包含四个动作：

1. `刷新`
   作用：重新拉取文档列表和任务列表。
2. `打开检索实验室`
   作用：跳到检索实验室，基于当前知识库继续做检索测试。
3. `上传文档`
   作用：打开上传弹窗。
4. 页面标题
   作用：显示当前知识库名称。

### 基本信息卡片

详情页中有一张基础信息卡，展示：

| 字段 | 含义 |
| --- | --- |
| 状态 | 当前知识库状态 |
| 描述 | 当前知识库说明 |
| 创建时间 | 当前知识库建立时间 |

这张卡的作用更像“当前上下文确认区”，让用户知道自己正在操作的是哪个知识库。

### 文档 Tab

文档 Tab 用来展示当前知识库里的文档记录。当前表格主要字段如下：

| 字段 | 含义 | 说明 |
| --- | --- | --- |
| 文件 | 文档名称 | 展示原始文件名 |
| 类型 | 文件类型 | 页面会转成大写标签显示 |
| 大小 | 文件大小 | 当前以前端换算成 KB 显示 |
| 分块数 | 文档被切分后的 chunk 数量 | 没值时会显示 `Contract gap` |
| 文件哈希 | 文件内容的 SHA-256 哈希 | 用于同库去重 |
| 状态 | 当前文档状态 | 常见是 `pending`、`processing`、`completed`、`failed` |
| 操作 | 删除按钮 | 用于删除当前文档 |

#### 文档状态怎么理解

文档状态和任务状态相关，但它们不是完全同一个概念。

你可以简单这样理解：

1. 文档状态表示“这个文档整体是否已经成功入库”。
2. 任务状态表示“最近一次围绕这个文档执行的入库任务处于什么状态”。

例如：

1. 文档刚上传时通常是 `pending`
2. 开始处理时会进入 `processing`
3. 成功入库后变成 `completed`
4. 失败后会变成 `failed`

### 入库任务 Tab

任务 Tab 展示当前知识库相关的入库任务记录。当前表格主要字段如下：

| 字段 | 含义 | 说明 |
| --- | --- | --- |
| 任务 ID | 当前任务主键 | 用于排查和日志关联 |
| 文档 ID | 任务所属文档 ID | 可和文档表联动排查 |
| 状态 | 当前任务状态 | 直接决定是否可重试、可取消 |
| 重试次数 | 当前任务已重试多少次 | 有助于判断问题是否持续存在 |
| 开始时间 | 任务开始处理时间 | 处理中和已完成任务常用 |
| 完成时间 | 任务结束时间 | 成功、失败、取消后通常会有值 |
| 错误信息 | 最近一次错误摘要 | 快速理解失败原因 |
| 错误码 | 最近一次错误类型 | 便于统一归类问题 |
| 最近操作 | 最近一次人工或系统操作 | 例如 `retry`、`cancel` |

### 任务操作按钮说明

详情页会根据任务状态动态显示不同操作按钮。

#### 重试

只有当任务状态是下面两种之一时，页面才会显示 `重试` 按钮：

1. `failed`
2. `dead`

点击重试后，系统会：

1. 把任务状态改成 `retrying`
2. 清空旧错误信息
3. 重新投递入库消息
4. 把对应文档状态重置为 `pending`

#### 取消

只要任务还没有进入下面这些终态之一，页面就会显示 `取消` 按钮：

1. `completed`
2. `canceled`
3. `dead`

点击取消后，系统会：

1. 把任务状态改成 `canceled`
2. 写入 `canceled_by_operator` 错误码
3. 尝试把文档状态更新为 `failed`

这里要注意一件事：

取消是状态层面的取消，不代表一定能中断一个已经在底层执行中的耗时步骤。它更像是给这次任务流转一个明确的人工终止结果。

### 自动轮询机制

详情页有一个很实用的功能：只要任务列表里存在下面这些活跃状态之一，页面就会每 3 秒自动刷新任务列表：

1. `pending`
2. `processing`
3. `retrying`

这意味着用户上传完文档后，不需要手动频繁点刷新，也能看到任务逐步推进。

### 上传文档弹窗

详情页上传弹窗支持的格式是：

1. `PDF`
2. `MD`
3. `TXT`
4. `MARKDOWN`

当前后端还有一个硬限制：

单文件大小不能超过 `20MB`。

上传成功后，页面会：

1. 关闭弹窗
2. 清空本地文件列表
3. 重新拉取文档和任务数据

### 删除文档

点击删除文档后，前端会弹出确认框。确认后会调用删除接口。

从业务上看，用户看到的是“文档已删除”。

从后端实现看，这一步实际上做了两件事：

1. 先对数据库记录做软删除。
2. 如果启用了 Milvus，再尽力删除对应向量。

这里有一个很重要的实现细节：

即使向量删除失败，后端当前也只是记录日志，接口仍然返回成功。

所以对开发同学来说，删除文档成功并不等于向量侧一定已经完全清干净。

## 开发实现说明

### 前端相关文件

如果你要修改知识库页面，建议优先看下面几个文件：

1. `admin/src/components/admin/knowledge-bases-page.tsx`
   作用：知识库列表页主组件。
2. `admin/src/components/admin/create-knowledge-base-modal.tsx`
   作用：新建知识库弹窗。
3. `admin/src/components/admin/knowledge-base-detail-page.tsx`
   作用：知识库详情页主组件。
4. `admin/src/components/admin/knowledge-base-provider.tsx`
   作用：知识库列表加载、当前知识库状态维护、本地缓存。
5. `admin/src/config/api.ts`
   作用：接口地址配置。
6. `admin/src/types/kb.ts`
   作用：知识库、文档、任务相关前端类型定义。

### 后端相关文件

如果你要查后端行为和数据口径，重点看：

1. `backend/api/router/custom_kb.go`
   作用：注册知识库相关路由。
2. `backend/api/handler/kb/handler.go`
   作用：创建知识库、上传文档、列出文档、列出任务、重试任务、取消任务、删除文档。
3. `backend/internal/model/kb_knowledge_base.go`
   作用：知识库模型和数据库访问。
4. `backend/internal/model/kb_document.go`
   作用：文档模型、软删除、按知识库查询、补充最新任务信息。
5. `backend/internal/model/kb_ingest_job.go`
   作用：任务状态机、任务列表查询、状态流转规则。

### 主要接口清单

知识库页面当前主要依赖这些接口：

| 接口 | 方法 | 作用 |
| --- | --- | --- |
| `/api/admin/kb/bases` | `GET` | 获取知识库列表 |
| `/api/admin/kb/bases` | `POST` | 新建知识库 |
| `/api/admin/kb/documents` | `GET` | 获取某个知识库下的文档列表 |
| `/api/admin/kb/documents/upload` | `POST` | 上传文档并触发入库 |
| `/api/admin/kb/documents/{document_id}` | `DELETE` | 删除文档 |
| `/api/admin/kb/jobs` | `GET` | 获取任务列表，可按 `kb_id` 过滤 |
| `/api/admin/kb/jobs/{job_id}` | `GET` | 获取单个任务详情 |
| `/api/admin/kb/jobs/{job_id}/retry` | `POST` | 重试失败任务 |
| `/api/admin/kb/jobs/{job_id}/cancel` | `POST` | 取消任务 |

### 创建知识库接口说明

请求体字段：

| 字段 | 是否必填 | 含义 |
| --- | --- | --- |
| `name` | 是 | 知识库名称 |
| `description` | 否 | 知识库描述 |

创建成功后，后端会自动把知识库状态设置成 `active`。

当前页面没有提供“编辑知识库”和“停用知识库”的入口，所以创建后主要就是进入详情页继续上传和管理文档。

### 上传文档接口说明

上传接口的关键规则如下：

| 规则 | 当前实现 |
| --- | --- |
| 表单字段 | `kb_id`、`file` |
| 文件大小限制 | 单文件不超过 `20MB` |
| 支持格式 | `pdf`、`txt`、`md`、`markdown` |
| 存储方式 | 本地 OSS，目录在 `uploads/knowledge` 下 |
| 对象命名 | `kb_{kbID}_{timestamp}_{safeName}` |

#### 重复上传的处理逻辑

后端会先读取文件内容并计算 SHA-256 哈希，然后按下面规则做去重：

1. 只在“同一个知识库内”检查重复。
2. 如果同库内已存在相同哈希的文档，就直接复用旧文档记录。
3. 接口会返回 `reused: true`。

这说明两件事：

1. 同一个文件上传到不同知识库，是允许的。
2. 当前前端页面没有把“这是一次复用上传”单独提示出来，用户看到的只是上传成功。

### 删除文档接口说明

删除文档接口的实际行为是：

1. 先校验文档是否存在。
2. 把 `deleted` 字段改成 `1`，也就是软删除。
3. 记录审计事件。
4. 如果启用了 Milvus，尝试删除对应向量。

对开发同学来说，这里最值得注意的是：

数据库侧删除是主流程，向量侧删除是“尽力而为”的补充流程。

### 任务状态机说明

任务状态不是随意切换的，后端有明确的状态转移约束。

可以先用一个简化理解：

1. `pending` 可以进入 `processing`、`failed`、`canceled`
2. `processing` 可以进入 `completed`、`failed`、`retrying`、`canceled`
3. `failed` 可以进入 `retrying`、`dead`、`canceled`
4. `retrying` 可以重新进入 `processing`、`failed`、`dead`、`canceled`
5. `dead` 可以重新被人工拉回 `retrying`

这套状态机的好处是：

它把“系统自动流转”和“人工干预”都纳入同一套规则里，避免任务状态被随意改乱。

### 页面和接口的数据映射

#### 知识库列表页

列表页使用 `KnowledgeBaseProvider` 拉取 `/bases` 接口，并维护：

1. `bases`
2. `selectedBase`
3. `isPermissionDenied`
4. `error`

这也是为什么后台顶部的“当前知识库”选择器，和知识库页面本身能共享当前选中状态。

#### 详情页

详情页会并行拉两类数据：

1. 文档列表：`GET /documents?kb_id=...`
2. 任务列表：`GET /jobs?kb_id=...`

其中任务列表还会在活跃任务存在时自动轮询。

## 字段含义与用户理解

### 为什么文档表里要展示文件哈希

对普通用户来说，文件哈希看起来不直观，但它在排查重复上传时很有用。

你可以把它理解成“文件内容指纹”。如果两个文件内容完全一致，它们的哈希通常也一致。

### 为什么任务表里要展示错误码和错误信息

这两个字段分工不一样：

1. 错误码更适合做归类，比如判断是解析失败、队列失败还是人为取消。
2. 错误信息更适合看当前这一次具体出了什么问题。

### 为什么有时候会看到 Contract gap

如果某条记录还没有最新入库耗时、最近任务信息或者某些扩展字段，前端会显示 `Contract gap`。

它更像一个“数据合同提醒”，而不是业务异常提示。

## 当前实现的限制和注意点

这部分很重要，因为它直接关系到用户培训和后续迭代预期。

### 限制一：列表页目前只拿默认第一页

知识库列表页调用 `/bases` 时没有主动传 `page` 和 `page_size`。

而后端默认分页大小是 `10`。

这意味着：

如果系统里知识库数量超过 10，当前页面默认只能看到第一页。

### 限制二：详情页的文档列表和任务列表也只拿默认第一页

详情页请求文档和任务数据时，同样没有主动传分页参数。

因此当前页面实际只加载：

1. 前 10 条文档
2. 前 10 条任务

页面里的表格分页更像“前端对已加载数据做本地分页”，并不是和后端总量联动的真正翻页。

### 限制三：上传弹窗前端允许选多个文件，但后端当前按单文件处理

详情页上传组件当前设置了：

1. `maxCount = 10`
2. 前端会循环把多个文件都 append 到 `file` 字段

但后端上传接口当前使用的是：

`c.FormFile("file")`

这表示它按单文件字段读取，不是严格意义上的多文件批量上传接口。

所以从真实能力上看：

当前更应该把它理解成“单文件上传接口”，而不是稳定的批量上传接口。

### 限制四：删除文档成功不等于向量一定删除成功

这一点前面提过，但值得再强调一次。

前端看到“删除成功”时，数据库记录通常已经删除成功；但如果 Milvus 向量删除失败，当前接口不会把这个失败直接反馈到页面。

### 限制五：当前页面没有知识库编辑能力

目前可以：

1. 创建知识库
2. 查看知识库
3. 使用知识库

但还不能直接在页面里：

1. 修改知识库名称
2. 修改描述
3. 禁用知识库
4. 删除知识库

## 权限与访问说明

从当前后端代码看，知识库页面相关接口主要校验的是“是否登录”：

1. `CreateKnowledgeBase`
2. `ListKnowledgeBases`
3. `UploadDocument`
4. `ListDocuments`
5. `ListJobs`
6. `RetryJob`
7. `CancelJob`
8. `DeleteDocument`

它们当前并没有显式调用 `requireAdmin`。

这说明：

1. 产品层面它属于后台能力。
2. 代码层面它更像“登录后可访问的知识库管理接口”。

如果后续要强化后台权限隔离，这一组接口是值得统一收口的地方。

## 常见使用场景

### 场景一：新项目初始化知识库

建议顺序：

1. 进入知识库列表页。
2. 点击“新建”。
3. 填写知识库名称和描述。
4. 创建完成后进入详情页。
5. 上传首批文档。
6. 观察任务是否顺利完成。

### 场景二：上传后一直没生效

建议顺序：

1. 进入知识库详情页。
2. 看文档 Tab 里的状态是否还停留在 `pending` 或 `processing`。
3. 切到任务 Tab 看任务状态和错误信息。
4. 如果失败，优先看 `error_msg` 和 `last_error_code`。
5. 需要时点击重试。

### 场景三：清理错误文档或历史废弃文档

建议顺序：

1. 在文档 Tab 找到目标文档。
2. 点击删除并确认。
3. 如果后续检索结果异常，再去日志或向量侧确认关联数据是否已同步清理。

## 如何验证

如果你要验证这篇文档对应的实现，可以按下面方式检查：

1. 打开 `/knowledge-bases`，确认列表页能正常展示知识库卡片。
2. 新建一个知识库，确认创建后自动跳到详情页。
3. 在详情页上传一个 `pdf`、`md` 或 `txt` 文件，确认页面出现文档记录和任务记录。
4. 等待任务轮询，确认活跃状态会自动刷新。
5. 人为制造失败任务后，确认 `重试` 按钮只在 `failed` 或 `dead` 状态下出现。
6. 确认 `取消` 按钮不会在 `completed`、`canceled`、`dead` 状态下出现。
7. 删除文档后，确认文档列表刷新。

## 取舍与后续优化

当前这套知识库页面已经具备完整主链路，但还有几个很值得继续优化的点：

1. 把列表页、文档列表、任务列表补成真正的后端分页，而不是只看默认第一页。
2. 统一前端和后端对“是否支持批量上传”的能力定义，避免界面和真实能力不一致。
3. 在上传成功时区分“新文档上传成功”和“重复文件已复用”。
4. 补充知识库编辑、禁用、删除等基础管理能力。
5. 对删除文档后的向量清理结果做更明确的可观测反馈。

这篇文档的核心结论可以概括成一句话：

知识库页面真正管理的不是“文件本身”，而是“文件进入可检索系统之前和之后的完整生命周期”。
