# 文本 Embedding 策略与向量维度选择建议

在构建基于 Milvus 的 RAG 知识库时，Embedding 模型的设计直接影响检索的精准度和系统成本。本指南对比了主流模型（OpenAI, Ark/豆包, BGE）的特性，并提供了维度选择建议。

## 1. 主流 Embedding 模型对比

| 特性 | OpenAI (v3-small) | Ark / 豆包 (doubao-embedding) | BAAI / BGE (BGE-M3) |
| :--- | :--- | :--- | :--- |
| **厂商** | OpenAI | 火山引擎 (字节跳动) | 北京人工智能研究院 |
| **标准维度** | 1536 / 512 (可根据参数调整) | 2560 (最新版支持 4096) | 1024 (固定) |
| **中英文支持** | 优秀 | **顶级 (专为中文优化)** | 优秀 |
| **最大输入长度** | 8191 tokens | 4096 tokens | 8192 tokens |
| **成本/价格** | 约 0.144 RMB / 1M tokens | **约 0.8 RMB / 1M tokens** | 硬件托管成本 (开源免费) |
| **部署方式** | SaaS API | SaaS API | 本地部署 / 云原生托管 |
| **适用场景** | 国际化项目、通用语义检索 | **国内技术面试、本土化业务** | 对数据隐私要求极高的私有化场景 |

## 2. 向量维度与性能调优

在 Milvus 中，向量维度越高，语义表达越细腻，但同时会带来计算开销和存储成本的增加。

### 2.1 性能数据参考
以下数据基于 Milvus HNSW 索引（M=16, efConstruction=200）在百万级数据集上的模拟表现：

| 向量维度 | 单次检索耗时 (ms) | 内存占用 (GB/1M docs) | 建议索引类型 |
| :--- | :--- | :--- | :--- |
| **384 (BGE-small)** | < 5ms | ~1.5 GB | FLAT / HNSW |
| **1024 (BGE-M3)** | ~10ms | ~4.0 GB | HNSW |
| **1536 (OpenAI)** | ~15ms | ~6.0 GB | HNSW / IVFFLAT |
| **2560 (Ark/豆包)** | ~25ms | ~10.0 GB | HNSW / SQ8 |

### 2.2 调优建议
1.  **权衡精度与速度**：对于面试 Agent 场景，1024-2560 维度是“甜点位”。如果追求极致速度，可以使用更小的模型或对高维向量进行 **PCA 降维**（虽然模型如 OpenAI v3 支持原生降维，但需测试精度损失）。
2.  **量化策略 (Quantization)**：若维度超过 1536 且内存有限，建议在 Milvus 中开启 `IVF_PQ` 或 `SQ8` 索引，通过牺牲 1-2% 的召回率来换取 4 倍的存储压缩和显著的检索加速。
3.  **Matryoshka 学习模型**：OpenAI v3 系列支持 Matryoshka 缩放，即你可以截断前 512 维使用。经测试，OpenAI v3-large 在 1024 维时的表现优于 ada-002 在 1536 维时的表现。

## 3. 本项目推荐策略

由于本项目（Go-Eino Interview Agent）主要面向中文技术面试场景：

1.  **首选模型**：`doubao-embedding` (Ark)。
    *   原因：字节跳动对中文技术名词（如“协程”、“切片”）的理解语义空间更贴合真实面试语境。
2.  **固定维度**：`1024` 或 `2560`（需与 `config.yaml` 中的 `Dimensions` 保持一致）。
    *   在我们的集成中，默认使用了 1024 维以获取最佳的性能平衡。
3.  **索引配置**：生产环境建议使用 `HNSW`，对应的 `MetricType` 推荐为 `COSINE`（余弦相似度），因为它对不同长度的文本片段更公平。
