# L1 - 混合检索召回链路（Dense + Sparse） 测试报告

## 测试目标
验证混合检索 API 返回 `routes=dense+sparse`，检查 `dense_hits` 和 `sparse_hits` 计数，验证单路失败时降级行为。

## 测试环境
- 测试时间：2026-05-26 01:30 CST
- API 地址：http://localhost:8899/api/admin/kb/retrieve
- 测试数据：知识库 id=1（Go/React 教程），id=2（L6 冒烟测试）

## 测试用例

### 用例1: 混合检索 routes=dense+sparse
- **测试方法**：POST `/api/admin/kb/retrieve` with `{"kb_id":1, "query":"Go语言并发编程", "top_k":5}`
- **预期结果**：返回结果中 routes 为 "dense+sparse"，retriever_version 为 "phase2-hybrid-v1"
- **实际结果**：
  - `routes: "dense+sparse"` ✅
  - `retriever_version: "phase2-hybrid-v1"` ✅
  - `strategy: "phase2"` ✅
  - `release_stage: "full"` ✅
  - `release_reason: "legacy_flags"` ✅
- **测试结论**：✅ 通过

### 用例2: Dense 和 Sparse 命中计数
- **测试方法**：检查日志中的 `dense_hits` 和 `sparse_hits` 字段
- **预期结果**：dense_hits > 0，sparse_hits >= 0
- **实际结果**：
  - 测试1（"Go语言并发编程"）：`dense_hits=2, sparse_hits=0` — Dense 有命中，Sparse 无匹配
  - 测试2（"Go"经 rewrite 后 "go golang"）：`dense_hits=2, sparse_hits=1` — Sparse 也有命中
  - 测试3（KB2 "测试"）：`dense_hits=0, sparse_hits=0` — KB2 无文档
- **测试结论**：✅ 通过（Sparse 命中取决于倒排索引匹配，非所有查询都能命中）

### 用例3: Retriever Version 标识
- **测试方法**：检查返回结果中 `source.retriever_version` 字段
- **预期结果**：为 "phase2-hybrid-v1"
- **实际结果**：所有返回结果的 `source.retriever_version` 均为 `"phase2-hybrid-v1"` ✅
- **测试结论**：✅ 通过

### 用例4: 空知识库降级行为
- **测试方法**：对无文档的知识库 id=2 执行检索
- **预期结果**：返回空结果，empty_reason 为 "Empty-After-Retrieve"
- **实际结果**：
  - `items_count: 0`
  - `empty_reason: "Empty-After-Retrieve"` ✅
  - `result_status: "no_result"` ✅
  - `routes: "dense+sparse"` — 双路都尝试了
- **测试结论**：✅ 通过

### 用例5: 单路降级验证（代码审查）
- **测试方法**：审查 `hybrid_search.go` 中的错误处理逻辑
- **预期结果**：单路失败时应记录错误但不中断整体检索
- **实际结果**：日志中 `dense_error` 和 `sparse_error` 字段存在，当前为空字符串（无错误）。代码中 sparse 搜索失败时会记录错误但仍返回 dense 结果。
- **测试结论**：✅ 通过（代码层面支持降级，当前环境无触发场景）

## 测试总结
- **通过率**：5/5 (100%)
- **发现的问题**：
  1. Sparse 检索在当前测试数据下命中率较低（仅 "Go" 的 rewrite 查询命中 1 条），可能需要更多包含关键词匹配的数据来充分测试
- **建议改进方向**：
  1. 增加包含更多中文关键词的测试文档，提升 Sparse 倒排索引的命中率
  2. 可增加 Sparse 单独降级的集成测试（mock sparse 失败场景）
