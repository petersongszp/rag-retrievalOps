### 用例4: ConfigurableReranker 降级机制（代码审查）
- **测试方法**：审查 `reranker.go` 中 `ConfigurableReranker.Rerank` 方法
- **预期结果**：primary 超时/失败时自动降级到 fallback
- **实际结果**：
```go
func (r *ConfigurableReranker) Rerank(ctx context.Context, query string, docs []*schema.Document) (*RerankResult, error) {
    // 1. primary 为 nil → 直接用 fallback
    // 2. 设置 timeout context
    // 3. primary.Rerank 成功 → 返回
    // 4. primary 失败 → fallback.Rerank
    // 5. fallback 也失败 → 返回错误
}
```
- 降级原因分类：`classifyRerankFallbackReason` 支持 "timeout"、"canceled"、"error"
- 日志中 `rerank_fallback: false` — 当前无触发降级的场景
- **测试结论**：✅ 通过（代码层面支持降级）

## 测试总结
- **通过率**：5/5 (100%)
- **发现的问题**：
  1. 当前 Jaccard reranker 在小数据集上 latency 为 0ms，无法充分验证延迟监控
  2. API 响应中未直接返回 `rerank_score`、`rerank_version`、`rerank_latency_ms` 字段（仅在日志和 metadata 中）
- **建议改进方向**：
  1. 增加大数据集测试，验证 rerank 延迟监控的准确性
  2. 在 API 响应的 `source` 对象中增加 `rerank_score` 等字段，便于前端展示
  3. 可增加 rerank 超时的集成测试（mock 慢 reranker）
