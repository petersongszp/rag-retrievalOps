# Semantic Cache L0-L6 开会讲稿

## 1. 这次会议想讲清楚什么

今天这次汇报，我建议就讲三句话：

1. Semantic Cache 不是单点优化，而是一条新的检索短路路径。
2. 我们按 `L0 -> L6` 分层推进，是为了先保证安全，再保证收益，最后保证可上线和可交付。
3. 现在这条链路已经从设计、实现、观测、Gate 到文档收口闭环了。

---

## 2. 一句话讲 Semantic Cache

Semantic Cache 的本质是：

对于“语义相近、上下文边界一致”的检索请求，不再重新跑完整检索链路，而是直接复用历史检索结果。

它带来的价值主要有三个：

1. 降低重复相似 query 的检索延迟。
2. 降低重复请求带来的 retrieval 和 rerank 成本。
3. 提高高频问题场景下的吞吐和稳定性。

---

## 3. 为什么一定要按 L0 到 L6 这个顺序做

这个顺序不是为了好看，而是为了避免两个大坑：

1. 先写缓存、后补边界，容易产生误命中和跨租户污染。
2. 先写功能、后补观测，出了问题就解释不清楚。

所以我们的顺序是：

1. `L0` 先冻结规则
2. `L1` 再定义存储协议
3. `L2` 先打通命中短路读路径
4. `L3` 再补未命中回填和失效
5. `L4` 再补日志、指标、成本、调试
6. `L5` 基于前面的证据做 Gate、灰度、回滚
7. `L6` 最后把所有证据收成正式交付物

可以把它理解成一句话：

先防错，再跑通，再观测，最后上线和收口。

---

## 4. 每一层做了什么

### L0：配置、边界和命中契约冻结

L0 解决的问题是“什么请求能命中，什么请求绝对不能命中”。

这一层主要冻结了：

1. 开关和阈值配置
2. `tenant_id + kb_ids + strategy_version + query_type + top_k` 这些边界
3. debug、空 query、高风险流量等绕过条件

要点是：
如果 L0 不清楚，后面所有层都会不安全。

### L1：缓存数据结构与 Redis 协议

L1 解决的问题是“缓存到底怎么存、怎么找、怎么删”。

这一层主要补了：

1. cache entry 结构
2. scope 和候选索引协议
3. payload、TTL 和按知识库删除能力

要点是：
L2 要读，L3 要写，所以必须先统一协议。

### L2：检索入口缓存查询与短路返回

L2 解决的问题是“请求进来后能不能先试一下缓存”。

这一层主要做了：

1. 检索入口判断是否允许查缓存
2. 生成 query embedding，拉候选，算相似度
3. 命中后直接短路返回结果
4. 对 scope、top_k、payload 做安全校验

要点是：
这是 Semantic Cache 第一次真正改变主链路行为。

### L3：未命中回填、失效和清理策略

L3 解决的问题是“缓存从哪里来，以及什么时候该失效”。

这一层主要做了：

1. 未命中后正常检索成功再回填
2. 只回填安全、成功、非空结果
3. 知识库变化时按 kb 失效
4. TTL 自动清理旧缓存

要点是：
L2 负责读，L3 负责写，这两层合起来缓存才完整。

### L4：日志、指标、成本与调试链路

L4 解决的问题是“这次命中到底发生了什么，我们能不能看懂”。

这一层主要补了：

1. retrieve log 的 semantic cache 字段
2. cost trace 的 saved retrieval/rerank cost
3. debug trace 的结构化缓存视图

要点是：
L4 决定了我们线上出了问题时，是不是只能猜。

### L5：测试、Gate、灰度与回滚

L5 解决的问题是“现在能不能上线，如果不能，卡在哪里”。

这一层主要补了：

1. `gate` 接口
2. `acceptance` 接口
3. 命中率、lookup P95、误命中、收益、观测完整性的判定
4. 灰度计划和回滚计划

要点是：
L5 把“能跑”变成“敢上线”。

### L6：文档收口与验收报告

L6 解决的问题是“团队怎么复盘、怎么验收、怎么拿这套能力继续往下走”。

这一层主要补了：

1. `report` 接口
2. L6 验收报告文档
3. 这份 L0-L6 会议讲稿

要点是：
L6 把零散成果收成统一交付物。

---

## 5. 现在怎么对外描述这条链路

如果会上只能讲 30 秒，可以直接这么说：

我们给检索主链路加了一条语义缓存短路路径。  
先用 L0 和 L1 固定边界与协议，确保缓存不会误命中；  
再用 L2 和 L3 打通命中短路与未命中回填；  
再用 L4 补齐日志、指标、成本和调试；  
最后用 L5 和 L6 完成 Gate、灰度、回滚和验收收口。

---

## 6. 当前验收口径

现在我们看 6 个问题：

1. 开关关闭后，主链路是不是完全回到原行为。
2. 命中是不是只发生在正确隔离边界。
3. 返回结果契约是不是稳定。
4. 知识库变更后旧缓存会不会污染新结果。
5. 日志、成本、调试链路能不能解释缓存行为。
6. 出现异常时能不能快速关闭和回滚。

## 8. 会上最后的结论建议

建议最后这样收：

Semantic Cache 目前已经不是单纯的实验代码，而是一套有边界、有协议、有主链路接入、有回填失效、有观测、有 Gate、有灰度回滚、也有文档收口的完整能力。  
下一步如果继续推进，可以在当前 L6 收口基础上，再考虑更深的收益优化，比如 Answer Cache 或多级缓存体系。
