# Semantic Cache L6 验收报告

## 1. 文档目的

这份文档不是重复讲代码细节，而是回答 4 个交付问题：

1. Semantic Cache 到底做到了什么。
2. 它为什么可以按 `L0 -> L6` 这个顺序推进。
3. 现在怎么验收它。
4. 如果线上有风险，怎么快速灰度和回滚。

## 3. 从 L0 到 L6 的验收链路

### L0：配置、边界和命中契约冻结

先定义规则，不让缓存跨租户、跨知识库、跨策略乱命中。

为什么必须先做：
如果一开始不冻结边界，后面所有命中和回填都可能建立在错误前提上。

### L1：缓存数据结构与 Redis 协议

先定义缓存 entry、scope、候选索引、TTL 和删除协议。

为什么必须第二个做：
L2 要读缓存，L3 要写缓存，读写双方必须先使用同一套协议。

### L2：检索入口缓存查询与短路返回

让请求进入检索主链路前，先尝试命中历史缓存。

为什么放在 L3 前：
要先确认“读路径”安全成立，才有必要开始写回缓存。

### L3：未命中回填、失效和清理策略

让未命中请求在正常检索成功后把结果存回缓存，并在知识库变化时及时清理旧缓存。

为什么在 L2 后：
如果没有稳定的命中消费路径，先大量写缓存没有意义，还容易把脏数据放大。

### L4：日志、指标、成本与调试链路

把缓存命中、原因、候选数、相似度、lookup 耗时、节省的 retrieval/rerank 成本全部记下来。

为什么在 L2/L3 后：
因为只有缓存先真实工作起来，日志和指标才有真实对象可以观察。

### L5：测试、Gate、灰度与回滚

把缓存能力变成“可上线”的能力，而不是“能跑”的能力。

为什么在 L4 后：
Gate、灰度和回滚判断都依赖前面的日志、指标和成本证据。

### L6：文档收口与验收报告

把前面零散的实现、测试、收益、风险、灰度和回滚材料统一收口。

为什么最后做：
因为 L6 要引用前面 L0-L5 已经存在的事实，不能空口写结论。

## 4. 当前验收关注点

Semantic Cache 当前的核心验收点有 6 个：

1. 关闭 `enable_semantic_cache` 后，行为必须回到原始检索链路。
2. 命中只能发生在正确的隔离边界内。
3. 命中后返回的 payload 契约稳定，不偷改结果结构。
4. 知识库变更后，旧缓存不会继续污染新结果。
5. retrieve log、cost trace、debug trace 都能解释缓存行为。
6. 出现异常时可以快速关闭开关并执行回滚。

---

## 5. 本次测试覆盖

已经覆盖的重点场景：

1. L2：
   - bypass reason
   - exact top_k 命中约束
   - scope 过滤后的命中短路返回
2. L3：
   - unsafe result 不回填
   - success result 正常回填
   - knowledge base 维度失效
3. L4：
   - cache saved retrieval/rerank cost 记账
   - debug trace 能展示结构化缓存信息
4. L5：
   - gate 接口
   - acceptance 接口
5. L6：
   - report 接口聚合实现摘要、收益、风险和下一步动作

推荐本地验收顺序：

1. 跑 semantic-cache 相关单测。
2. 跑 `go test ./... -run TestDoesNotExist` 做全量编译检查。
3. 用 admin 接口分别查看 `gate / acceptance / report` 三个响应。

---

## 6. 收益口径

L6 统一用下面 4 组收益口径说话：

1. 命中率：回答“缓存有没有被真正用起来”。
2. lookup P95：回答“命中前的缓存查找是不是足够便宜”。
3. saved retrieval cost：回答“省了多少检索成本”。
4. saved rerank cost：回答“省了多少重排成本”。

这也是为什么 L4 和 L5 必须先做完。
没有这些字段，L6 就只能写主观判断，不能写可验收的数据结论。

---

## 7. 灰度与回滚

### 灰度建议

1. 先在内部环境观察命中短路和未命中回填是否符合预期。
2. 再根据 release stage 小流量放量。
3. 每一步都盯住命中率、lookup P95、误命中样本和节省成本。

### 回滚建议

1. 先关闭 `enable_semantic_cache`。
2. 停止读取和回填，但先不删 Redis 历史数据。
3. 保留日志、成本和调试链路，确认回滚后行为恢复正常。
4. 如果仍有风险，再配合 release rollback 退回上一阶段。
