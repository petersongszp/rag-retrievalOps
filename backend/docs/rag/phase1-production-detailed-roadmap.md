# Phase 1 详细功能实现路线（生产可用）

## 1. 文档定位

本文档是 Phase 1 的执行手册，目标是把“RAG 生产可用”拆成可直接实施的细颗粒任务路线。
它有两个用途：

1. 作为团队推进 Phase 1 的统一执行文档。
2. 作为后续优化阶段（Phase 2）的稳定工程基线。

本文档风格与现有路线文档保持一致：
目标 -> 路线 -> 模块任务 -> 验收门禁 -> 下一步入口。

统一口径说明：

1. `统一检索结果契约` 固定指：`content/score/citation/source`。
2. `source` 在 Phase 1 最小包含：`route/collection/retriever_version`。
3. `Collection 一致性校验` 固定指：导入 Collection、查询 Collection、当前 active Collection 三者一致。
4. `结构化检索日志` 固定至少包含：`query/user_id/kb_id/expr/topk/rewrite/routes/final_count/duration_ms/request_id`。
5. `可重试错误` 固定指：临时网络失败、Embedding 超时、Milvus 写入超时；`不可重试错误` 固定指：文件解析失败、参数非法、鉴权失败。

---

## 2. Phase 1 范围边界

## 2.1 本阶段必须完成

1. 入库链路具备可观测重试与补偿能力（自动 + 人工）。
2. 检索链路具备生产级监控、告警与追踪字段。
3. 检索结果引用信息增强，支持稳定定位到文档与分块。
4. 权限隔离、限流、配额与关键安全回归压测可落地。
5. 灰度开关、回滚路径、运行手册（Runbook）可执行。

## 2.2 本阶段明确不做

1. 混合检索召回策略（向量 + BM25 排名融合）。
2. 动态 TopK 与学习型重排。
3. 多租户跨区域容灾（多活）架构改造。
4. 全量自动化成本优化（Embedding 缓存分层、冷热索引迁移）。
5. 高级策略引擎（如 AB 自动实验平台）。

---

## 3. 目标与通过标准（Gate）

Phase 1 通过标准（全满足）：

1. 入库任务失败后可自动重试，且最终状态可追踪。
2. 关键链路指标可在监控面板查看，并有有效告警。
3. 检索请求可通过 `request_id` 完整关联日志、耗时、结果数量。
4. 隔离策略在压测与越权测试中通过，不发生跨用户数据泄露。
5. 灰度发布后业务稳定，必要时可在 10 分钟内完成回滚。

---

## 4. 实现路线总览（L0 -> L7）

Phase 1 按 8 条路线推进，按门禁顺序合流：

1. L0：生产基线开关与配置分层
2. L1：重试与补偿机制
3. L2：任务状态机与人工运维入口
4. L3：监控指标与告警体系
5. L4：检索溯源增强与审计日志
6. L5：安全隔离、限流与配额
7. L6：压测、稳定性与发布回滚
8. L7：验收收口与运行手册

建议顺序：`L0 -> L1 + L2 -> L3 + L4 -> L5 -> L6 -> L7`

---

## 5. 详细路线拆解

## 5.1 L0 生产基线开关与配置分层

### 目标
让 RAG 能以“可控、可灰度、可回滚”方式进入生产运行。

### 功能任务

1. 新增 Feature Flag：
   - `RAG_ENABLE_PROD_GUARD`
   - `RAG_ENABLE_INGEST_RETRY`
   - `RAG_ENABLE_RETRIEVE_AUDIT`
2. 增加环境分层配置（dev/staging/prod），避免硬编码。
3. 对关键阈值参数化：
   - `max_retry_count`
   - `retry_backoff_ms`
   - `retrieve_timeout_ms`
   - `user_qps_limit`
4. 启动阶段校验生产必填配置，缺失即 fail-fast。
5. 补充配置版本日志，启动时打印配置快照摘要（脱敏）。

### 验收

1. 不同环境可加载不同策略参数。
2. 关闭开关时不影响 Phase 0 基线路径。
3. 关键配置缺失时服务拒绝启动并明确报错。

---

## 5.2 L1 重试与补偿机制

### 目标
降低临时故障导致的入库失败率，确保任务最终一致性。

### 功能任务

1. 在消费器引入重试策略：
   - 指数退避（建议带抖动）
   - 最大重试次数可配置
2. 增加错误分类器：
   - `retryable`
   - `non_retryable`
3. `kb_ingest_job` 增加字段：
   - `next_retry_at`
   - `last_error_code`
   - `last_error_detail`
4. 增加补偿任务扫描器：定时拉取“可重试且到期”的失败任务再投递。
5. 增加死信策略：超过最大重试进入 `dead` 状态，等待人工处理。

### 验收

1. 临时故障可自动恢复并最终 completed。
2. 不可重试错误不进入无效重试循环。
3. 超限任务可在后台明确看到 dead 状态与失败原因。

---

## 5.3 L2 任务状态机与人工运维入口

### 目标
让任务生命周期可管理、可干预、可审计。

### 功能任务

1. 明确状态机：
   - `pending -> processing -> completed`
   - `pending/processing -> failed -> retrying -> processing`
   - `failed -> dead`
2. 新增运维 API（内部或管理端）：
   - `POST /api/kb/jobs/:job_id/retry`
   - `POST /api/kb/jobs/:job_id/cancel`
   - `GET /api/kb/jobs?status=`
3. 增加状态流转合法性校验，禁止非法跳转。
4. 增加操作审计字段：
   - `operator_id`
   - `operation`
   - `operation_reason`
5. 增加运行手册中的人工补偿流程（标准操作步骤）。

### 验收

1. 人工重试仅对 `failed/dead` 状态生效。
2. 取消任务后不会继续执行入库动作。
3. 每次人工操作都有可追踪审计记录。

---

## 5.4 L3 监控指标与告警体系

### 目标
实现“出问题可发现、可定位、可响应”的最小生产监控闭环。

### 功能任务

1. 增加核心指标埋点：
   - 入库成功率
   - 入库平均耗时/P95
   - 检索请求量、错误率、超时率
   - 检索耗时 P50/P95/P99
2. 增加错误码维度统计（按 error_code 聚合）。
3. 增加消费者积压指标（队列 backlog）。
4. 配置基础告警规则：
   - 入库失败率超过阈值
   - 检索错误率超过阈值
   - P95 延迟超过阈值
   - 消费 backlog 持续上升
5. 告警通知分级：P1/P2，并定义值班升级路径。

### 验收

1. 面板可看到 24h 指标趋势。
2. 人工注入故障时告警可触发。
3. 告警信息能直接定位到服务、接口、错误码。

---

## 5.5 L4 检索溯源增强与审计日志

### 目标
提升检索结果可解释性与问题排查效率。

### 功能任务

1. 检索返回 `source` 增强字段：
   - `route`
   - `collection`
   - `retriever_version`
2. `citation` 增强字段：
   - `kb_id/document_id/chunk_id/file_name/chunk_index`
   - `snippet_offset`（可选，命中片段位置信息）
3. 为每次检索生成并透传 `request_id`。
4. 结构化日志补齐：
   - 请求参数摘要
   - 过滤表达式
   - 命中数与截断信息
   - 耗时拆分（embedding/search/postprocess）
5. 增加审计查询能力：按 `request_id` 查询完整链路日志。

### 验收

1. 任意检索请求均可通过 `request_id` 回查。
2. 返回契约稳定包含 `content/score/citation/source`。
3. 日志可区分“无结果”“过滤过严”“执行异常”三类情况。

---

## 5.6 L5 安全隔离、限流与配额

### 目标
确保生产流量下的安全性与资源公平性。

### 功能任务

1. 强化鉴权校验：请求 `user_id` 与 token 身份一致。
2. 检索表达式强制包含 `user_id + kb_id` 双过滤，不可绕过。
3. 增加用户级限流：
   - QPS 限制
   - 并发请求限制
4. 增加上传配额：
   - 单文件大小上限
   - 单用户总容量上限
   - 单知识库文档数上限
5. 增加越权测试用例与自动回归脚本。

### 验收

1. 越权请求全部被拒绝并返回明确错误码。
2. 限流生效且不影响合法低频请求。
3. 配额超限行为可预期、提示可读。

---

## 5.7 L6 压测、稳定性与发布回滚

### 目标
验证系统在生产负载下的稳定性，并具备快速处置能力。

### 功能任务

1. 制定压测场景：
   - 检索稳态流量
   - 上传突发流量
   - 混合读写流量
2. 建立基线指标：
   - 吞吐
   - 延迟
   - 错误率
   - 资源占用
3. 故障演练：
   - Milvus 抖动
   - Embedding 超时
   - MQ 积压
4. 灰度发布策略：按用户比例或环境分批放量。
5. 回滚预案演练：
   - 关闭 Feature Flag
   - 暂停 ingest 消费
   - 降级到 Phase 0 基线

### 验收

1. 压测结果满足预设 SLO。
2. 故障演练后恢复流程可执行。
3. 灰度与回滚在演练中通过。

---

## 5.8 L7 验收收口与运行手册

### 目标
确保 Phase 1 具备可交付、可运维、可交接的完整收口。

### 功能任务

1. 输出 Phase 1 验收报告（功能 + 指标 + 风险）。
2. 固化 Runbook：
   - 常见故障定位步骤
   - 重试/补偿操作步骤
   - 告警响应步骤
3. 补充 On-call 值班检查清单。
4. 补充发布检查清单（发布前/发布后）。

### 验收

1. 新同学可按 Runbook 独立完成一次故障处理演练。
2. 值班链路（告警 -> 响应 -> 恢复 -> 复盘）完整可执行。

---

## 6. 推荐实施节奏（无固定时长）

## 6.1 阶段推进建议

1. 先完成 `L0`，冻结配置、开关与生产参数口径。
2. 再完成 `L1 + L2`，确保失败任务可恢复、可人工干预。
3. 然后完成 `L3 + L4`，建立监控与排障基础设施。
4. 再完成 `L5`，把隔离、限流、配额作为上线前硬门禁。
5. 最后执行 `L6 + L7`，完成压测、演练与交付收口。

## 6.2 并行与合流规则

1. 可并行：`L1` 与 `L3`，`L2` 与 `L4`。
2. 必须串行：`L5` 依赖 `L4` 日志与契约稳定，`L6` 依赖 `L1~L5` 完成。
3. 统一合流：全部功能通过 `L7` 验收后再进入 Phase 2。

---

## 7. 角色分工（建议）

1. 后端A：L0 + L1（配置、重试、补偿）
2. 后端B：L2 + L4（状态机、运维 API、审计日志）
3. 后端C：L3 + L5（指标、告警、限流、隔离）
4. SRE/平台：L6（压测、演练、灰度与回滚）
5. QA/联调：L7（验收、回归、运行手册演练）

补充协作约束：

1. 后端与 SRE 先冻结指标命名和告警阈值口径，再接入面板。
2. 后端与 QA 先冻结错误码与状态机，再执行自动化回归。
3. 灰度前必须完成一次跨角色联合演练并记录结论。

---

## 8. 阶段验收模板（执行后填写）

1. 功能完成情况（按 L0~L7）
2. 监控与告警结果（触发/误报/漏报）
3. 压测结果（吞吐/延迟/错误率）
4. 指标快照：
   - 入库成功率
   - 入库 P95 耗时
   - 检索错误率
   - 检索 P95 耗时
   - backlog 峰值
5. 故障演练结果与恢复时长
6. 遗留问题与负责人
7. 是否进入 Phase 2（是/否）

---

## 9. Phase 1 完成后下一步（明确路线衔接）

下一阶段固定进入 Phase 2（召回与效果优化），按以下顺序：

1. 混合检索（Dense + BM25）
2. 动态 TopK 与查询改写策略
3. 重排模型接入与离线评测
4. 索引参数优化与成本评估

完成 Phase 2 门禁后，再进入 Phase 3 的策略自动化与多场景扩展。

---

## 10. 文档维护规则（作为后续实现参考基线）

1. 任何 Phase 1 范围变更，先改本文档再改代码。
2. 新增状态、错误码、告警规则必须同步更新 L1/L2/L3 对应章节。
3. 每次灰度与回滚演练后补充“阶段验收模板”记录。
4. 后续我按本文档逐项实现时，以本版本为唯一参考。
