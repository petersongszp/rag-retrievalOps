## 1. 文档用途

这份文档用于今晚团队分享，目标不是汇报路线图本身，而是围绕“我最近实际做出来了什么、前端怎么演示、后端支撑了什么能力”来做一次完整的成果展示。

## 2. 这次分享想传达的核心信息

如果只用一句话总结这次 P3 和 P4 的成果，可以这样讲：

> 我们最近不是只把 RAG 做成了“能回答问题”，而是进一步把它做成了“可调试、可管理、可治理”的系统。

如果展开成三层，可以这样讲：

1. `P3` 解决的是高级检索链路的可解释性和策略可控性。
2. `P4` 解决的是系统进入运营阶段之后的成本、审计、告警和周报治理能力。
3. 前端负责把这些复杂能力做成大家看得见、点得动、讲得清的页面；后端负责把原来分散在日志、配置和底层流程里的能力沉淀成结构化接口和治理闭环。

## 4. 正式演讲稿（完整版）

大家晚上好，今天我想和大家分享一下我最近在 RAG 管理台这块推进的成果。

这段时间我主要完成的是 `P3` 和 `P4` 两个阶段。  
如果简单概括一下，`P3` 主要解决的是高级检索链路的可解释性和策略可控性，`P4` 主要解决的是系统上线之后的治理能力，比如成本、审计、告警和周报。

我觉得这次工作的核心变化，不是单纯多了几个页面，而是我们把整个 RAG 系统从“能跑”推进到了“可观测、可调试、可运营”的阶段。

所以我今天不会按路线图去讲，而是会直接从前端效果给大家看。因为对大家来说，最容易感受到价值的方式，就是看现在这个管理台到底能做什么；然后我会在每个页面后面带一下，对应的后端我具体补了哪些能力。

### 4.1 先讲 P3：把高级检索从黑盒变成白盒

先看 `Retrieval Lab`。

这个页面原来就有，但现在它的角色已经不只是一个简单的检索测试页了。  
现在从这里发起一次查询之后，我们不仅能拿到检索结果，还能拿到这次请求对应的 `request_id`。这个 `request_id` 很关键，因为后面所有调试、追踪、审计相关的能力，都会围绕这个主键展开。

所以我通常会先在这里输入一个真实问题，发起一次查询。  
然后我会告诉大家，这里现在最重要的变化不是“答案显示出来了”，而是这次请求已经可以被完整追踪、完整拆解了。

接下来我会点进 `Retrieval Debug` 页面。

这个页面我觉得是 P3 最核心的成果之一。  
大家可以把它理解成：我们把一次检索请求从一个黑盒过程，拆成了一个可以逐阶段查看的白盒流程。

首先在页面顶栏，我们可以看到这次请求最基础的信息，比如 `request_id`、原始 query、改写后的 query、知识库 ID、创建时间，以及这条请求当前是否具备完整的 debug 数据。

这一步看起来像是一个普通详情页，但背后其实意味着一件事：  
后端现在已经不是只留一份零散日志了，而是把一次高级检索请求整理成了结构化的 debug trace，前端不需要再去手工拼日志、猜步骤，而是可以直接消费结构化接口。

然后我会往下讲 `Query Rewrite` 和 `Route Hits`。

这一块是非常适合给大家建立直觉的。  
以前大家看到的更多是“最后搜到了什么”，但现在我们能看到“原始问题是什么”“系统有没有改写”“改写成了什么”“dense route 和 sparse route 分别命中了什么内容”。

这件事的意义在于，我们不只是知道结果，而是开始知道系统为什么会拿到这样的结果。  
也就是说，检索不再只是一个最终输出，而变成了一个可解释的过程。

再往下是 `Fusion / Dedupe / Rerank / Filter`。

这一块我一般会重点讲一句：  
以前我们只能看到最终答案前面的少量引用，现在我们能看到候选结果在后端经历了哪些变化。

比如：

1. fusion 前后候选集发生了什么变化；
2. 哪些结果被 dedupe 去掉了；
3. rerank 之后顺序为什么变了；
4. filter 或 truncate 为什么删掉了一些内容。

前端上这些都是可视化的卡片和表格，但背后对应的是后端把整个高级检索链路里的关键中间态都结构化暴露出来了。

然后我会讲 `Parent-Child`。

这一块可以讲得稍微业务一点。  
我们在真实问答里，很多时候不是单纯找到一个 chunk 就结束了。一个子块可能命中了关键词，但真正让回答更完整的，是它的父块、相邻块或者同章节上下文。

所以现在在这个页面里，我们不仅能看到 child hits，也能看到 parent contexts 是怎么被补回来的。  
这说明我们现在的检索不只是“召回片段”，而是开始具备“补上下文”的能力。

接着我会重点讲三个高价值模块：`TopK Decision`、`Evidence Gate`、`Citation Consistency`。

这三个模块很重要，因为它们其实决定了系统答得稳不稳。

`TopK Decision` 解决的是：候选结果到底拿多少条最合适。  
不是拿得越多越好，因为会影响 token、成本和噪音；也不是拿得越少越好，因为会影响证据覆盖。

`Evidence Gate` 解决的是：当证据不足的时候，系统到底该不该答。  
这个能力非常关键，因为它直接影响“胡答”和“稳答”的边界。

`Citation Consistency` 解决的是：回答里的关键结论，是不是真的被引用片段支撑。  
也就是说，我们现在不只看“有没有 citation”，而是在看“citation 是否真正支持这段回答”。

这一页最重要的价值，就是把这些原来完全发生在后端内部的高风险决策，都变成了前端可见、可讲、可核对的过程。  
所以 P3 的第一件大事，其实就是让高级检索链路变得可解释了。

### 4.2 再讲 P3 的第二部分：策略中心

如果说刚才的调试页解决的是“看懂一次请求”，那 `Strategy Center` 解决的就是“管理整套高级检索策略”。

我会先带大家看页面顶部几个概览卡片，比如启用策略数、canary 策略数、error 策略数、最近回滚次数。  
这一层的作用，是让大家先快速知道现在系统整体的策略状态。

然后重点看中间的 `Feature Flags` 列表。  
这里可以直接看到每个策略当前是 enabled、disabled、shadow、canary 还是 rolling back，也能看到灰度比例、风险等级和当前版本。

这里我会强调一个点：  
我们做的不是一个简单的“配置开关页”，而是一个带灰度、带风险、带回滚能力的策略控制台。

比如现在修改一个策略时：

1. 前端要求填写变更原因；
2. 高风险策略会有风险提示；
3. 修改之后会刷新 impact、gate 和操作日志；
4. 出问题时还能执行回滚。

这意味着什么？  
意味着策略不再只是写在后端配置里的一串值，而是被纳入了一个正式的管理闭环。

接着我会点开右侧的几个区域：

1. `Impact 分析`
2. `Gate 摘要`
3. `版本列表`
4. `操作日志`

这里我会这样讲：

前端现在能看到的不只是“这个开关是开还是关”，而是还能看到这个策略到底带来了什么影响。  
比如它是否提升了 rewrite gain，是否影响了 citation support，是否带来了更高的 p95 延迟，样本量够不够，门禁有没有通过。

从后端角度看，这背后其实补齐了几件事：

1. 策略 flags 列表和修改接口；
2. 策略版本和版本详情接口；
3. 策略影响分析接口；
4. 策略门禁摘要接口；
5. 策略操作日志和回滚接口。

所以到这里，P3 其实形成了一个完整闭环：  
一次请求出了问题，我们可以进入调试视图定位链路；  
如果发现是策略问题，我们可以进入策略中心看状态、看收益、看风险、做灰度、做回滚。

我觉得这件事本身，就已经把 RAG 管理能力往前推进了一大步。

### 4.3 进入 P4：从调试能力走向治理能力

P3 解决的是“可解释、可控制”，P4 解决的是“可治理、可运营”。

先看 `成本看板`。

这个页面很好理解，因为它直接回答了一个很现实的问题：  
我们这套 RAG 系统到底把钱花在哪了。

现在这个页面上可以看到：

1. 总成本；
2. 每千次问答成本；
3. 平均上下文 tokens；
4. 高成本 query 数；
5. 时间趋势；
6. 高成本 query 列表。

这一页我会重点讲一点：  
以前如果我们想看成本，往往只能看到一个比较粗的整体数字；但现在我们已经能从请求级别去做成本归因了。

也就是说，我们不只是知道“贵了”，还开始知道“为什么贵”“贵在哪条请求上”“是不是某个策略版本带来的”“是不是上下文太长导致的”。

后端为了支撑这个页面，补的主要能力包括：

1. embedding、LLM、rerank、context token 等成本字段采集；
2. 请求级成本记录；
3. 成本汇总接口；
4. 成本时序接口；
5. 高成本 query 接口；
6. 和 request_id、strategy_version、kb_id 的下钻关联。

所以这一页并不只是一个 dashboard，而是让成本治理第一次具备了真正的抓手。

### 4.4 再看 Vector DB：把底层向量库运维显性化

接下来我会切到 `Vector DB` 页面。

这个页面对应的是 P4 的运维能力。  
现在前端可以直接看到 Collection 列表、active 状态、health 状态、index version，以及最近的操作记录。

这一页我建议讲得务实一点。  
可以直接说：以前很多底层向量库相关的状态，对于大部分人来说其实是不可见的；现在至少在管理台里，我们能先看到当前系统底层跑在哪个 collection 上、健康状态怎么样、最近做过什么操作。

如果你要顺带带一句后端做了什么，可以这么说：

后端这里主要补的是 Collection 列表、健康检查、容量与索引状态相关接口，并且把这类高风险能力往受控 API 的方向推进，而不是继续停留在临时命令式操作。

### 4.5 审计中心：开始具备可追踪能力

再往下我会看 `审计中心`。

这个页面比较能体现系统成熟度。  
因为当页面、策略、运维动作越来越多之后，系统不能只回答“现在是什么”，还要能回答“是谁改的”“为什么改”“改了什么”“有没有留下痕迹”。

现在这个页面上，我们已经能看到：

1. action；
2. resource；
3. resource id；
4. reason；
5. created time；
6. 详情里的 before / after 和 contract gaps。

我在这里会重点讲一句：  
这意味着我们的系统开始具备正式的治理追踪能力了。

从后端角度看，这部分对应的是：

1. 统一审计事件模型；
2. 审计列表接口；
3. 审计详情接口；
4. before / after 摘要；
5. 后续接入脱敏、导出、补偿和覆盖率统计的基础。

所以 P4 做的不是再加一个日志页，而是开始把系统行为沉淀为可查询、可解释的治理事件。

### 4.6 告警中心：让风险不再依赖人工发现

接下来是 `告警中心`。

这一页我一般不会讲太久，但一定会点出来它的意义。

现在页面里可以看到治理告警的标题、类别、级别、状态和 metric，并且支持确认和解决。  
这意味着系统已经开始把质量、成本、容量、审计这些风险统一收口到一个地方，而不是靠人去翻多个页面、或者等有人事后发现异常。

这里我建议你现场强调一句：  
告警不是简单把一堆红点摆出来，而是意味着后端已经开始把治理风险结构化了，前端只是把它做成可操作入口。

### 4.7 周报：从“排问题”进入“做复盘”

最后我会看 `周报` 页面。

这一页特别适合拿来做收束。  
如果说 P3 更偏“看懂单次请求”，P4 就更偏“按周期运营整个系统”。

周报页面现在可以看到：

1. 已生成的周报列表；
2. 时间窗口；
3. 风险数量；
4. 周报详情中的风险摘要；
5. 下一步动作；
6. 质量摘要。

这一页我会这么讲：

这说明我们已经不是只在做一个工程项目，而是在开始建设一套有周度复盘、有风险沉淀、有后续动作追踪能力的 RAG 运营机制。

从后端上看，这背后就是周报生成、列表、详情和后续导出能力的底座。

## 5. 你在现场怎么演示前端

这一节是给你现场操作用的，重点不是原理，而是你点击时怎么讲。

### 5.1 第一步：从 Retrieval Lab 开始

操作：

1. 打开 `/retrieval-lab`
2. 输入一个真实问题
3. 发起检索
4. 展示结果和 `request_id`

你可以这样讲：

“我先从检索实验室开始。这个页面原来就有，但现在它不只是一个测试问答的地方了。现在每一次查询都会拿到 request_id，这个 request_id 是后面调试、追踪、审计的统一入口。也就是说，一次检索请求从这里开始，后面已经能被完整串起来了。”

前端讲解重点：

1. 先让大家看到真实查询是怎么发起的；
2. 强调 `request_id` 是链路主键；
3. 不要在这个页面讲太久，目的是自然跳去 debug。

后端对应能力：

1. 检索请求结构化记录；
2. request_id 贯穿检索链路；
3. 与后续 audit / trace / debug 能力关联。

### 5.2 第二步：进入 Retrieval Debug

操作：

1. 点击“查看调试视图”
2. 打开 `/retrieval-lab/debug?request_id=xxx`
3. 从上往下讲

你可以这样讲：

“这个页面是我觉得 P3 最核心的成果之一。我们把一次检索请求从一个黑盒过程，拆成了一个可视化的白盒链路。”

#### 5.2.1 先讲请求顶栏

你可以讲：

“这里先看最基础的信息：原始 query、改写后的 query、知识库、创建时间，还有这次请求是否具备完整的 debug 数据。这个看起来是前端详情，但背后其实是后端已经把高级检索 trace 结构化了。”

#### 5.2.2 再讲 Query Rewrite 和 Route Hits

你可以讲：

“这里能看到原始 query 和改写后的 query，也能看到不同 route 分别命中了什么结果。以前我们只知道最后搜到了什么，现在我们能知道系统为什么会搜到这些内容。”

前端讲解重点：

1. 这是“看过程”，不是只看结果；
2. route hit 是解释检索行为的关键入口。

后端对应能力：

1. debug trace 接口；
2. route hits 结构化返回；
3. rewrite 字段与 route query 字段补齐。

#### 5.2.3 再讲 Fusion / Dedupe / Rerank / Filter

你可以讲：

“这里特别适合看系统中间过程。比如哪些候选被融合了，哪些被去重了，rerank 怎么改变了顺序，filter 又为什么删掉了一些结果。也就是说，现在我们不只是拿最终结果，而是能看到结果形成的路径。”

前端讲解重点：

1. 告诉大家“中间过程第一次可见了”；
2. 不要逐字段念，重点讲价值。

后端对应能力：

1. fusion 结果结构化；
2. dedupe removed 项输出；
3. rerank before/after 输出；
4. filter / truncate 原因输出。

#### 5.2.4 再讲 Parent-Child

你可以讲：

“这一块体现的是我们现在不仅能召回命中的子块，还能把父块或者相邻上下文补回来，所以回答会更完整。这意味着系统已经不只是‘找片段’，而是在‘补上下文’。”

后端对应能力：

1. child hits 输出；
2. parent contexts 输出；
3. parent fill strategy、tokens、fallback reason 输出。

#### 5.2.5 再讲 TopK / Evidence / Citation

你可以讲：

“这里是我觉得最能体现系统成熟度的地方。TopK 决定拿多少候选，Evidence Gate 决定证据不够时要不要拒答，Citation Consistency 决定回答是不是被引用真正支撑。以前这些关键决策都藏在后端里，现在前端可以直接看到。”

前端讲解重点：

1. 突出“高风险决策可见”；
2. 这是和普通检索结果页最不一样的部分。

后端对应能力：

1. topk decision 数据；
2. evidence gate 数据；
3. citation consistency 数据；
4. unsupported claims 输出。

### 5.3 第三步：进入 Strategy Center

操作：

1. 打开 `/strategy-center`
2. 先看顶部统计卡片
3. 再看 flags 列表
4. 再看 impact / gate / versions / operations

你可以这样讲：

“如果刚才的调试页解决的是‘看懂一次请求’，那策略中心解决的就是‘管理整套高级检索策略’。”

前端怎么讲：

1. 顶部统计卡片：讲当前整体策略状态。
2. flags 列表：讲 enabled、shadow、canary、rolling back 这些状态。
3. 修改弹窗：讲 reason、灰度、风险提示。
4. rollback：讲可回滚是为了安全上线，不是为了追求页面复杂。

你可以讲的完整一点：

“我们不是做了一个简单开关页，而是做了一个带灰度、带风险、带回滚能力的策略控制台。现在策略已经不只是后端配置项，而是进入了一个正式管理闭环。”

后端对应能力：

1. flags 列表和更新接口；
2. strategy version 列表与详情；
3. strategy impact 聚合接口；
4. gates 摘要接口；
5. rollback 接口；
6. operations 最小日志。

### 5.4 第四步：展示成本看板

操作：

1. 打开 `/cost-ops/cost`
