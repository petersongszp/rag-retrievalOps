## Go 语言

### goroutine 和线程的区别

goroutine 是 Go 运行时管理的轻量级协程，初始栈大小约 2KB，可动态增长到 GB 级别。操作系统线程栈通常固定为 1-8MB。

关键区别：
- **调度方式**：goroutine 由 Go 运行时的 GMP 调度器调度（M:N 模型），线程由 OS 内核调度（1:1 模型）
- **上下文切换成本**：goroutine 切换只需保存少量寄存器，约数百纳秒；线程切换需要陷入内核，约数微秒
- **创建成本**：创建 goroutine 只需 `go func()`，几乎无成本；线程创建涉及系统调用，成本高
- **通信方式**：goroutine 推荐通过 channel 通信（CSP 模型）；线程通常用共享内存 + 锁

### Go 的 GMP 调度模型

GMP 是 Go 调度器的核心模型：
- **G（Goroutine）**：待执行的协程，包含栈、PC 等上下文
- **M（Machine）**：操作系统线程，负责实际执行 G
- **P（Processor）**：逻辑处理器，持有本地 goroutine 队列，个数由 `GOMAXPROCS` 决定

工作流程：
1. 新建的 goroutine 优先放入当前 P 的本地队列（最多 256 个）
2. 队列满了则放入全局队列
3. M 从绑定的 P 的本地队列取 G 执行；本地队列为空时从全局队列或其他 P 偷取（work stealing）
4. G 发生系统调用时，M 和 G 绑定进入内核，P 会解绑并被其他 M 接管，防止 P 空转

### channel 的底层实现

channel 底层是 `hchan` 结构体，核心字段：
- `buf`：环形缓冲区（有缓冲 channel 专用）
- `sendq` / `recvq`：阻塞等待的发送/接收 goroutine 队列（`sudog` 链表）
- `mutex`：保护 hchan 内部操作的互斥锁

发送流程（`ch <- v`）：
1. 若 recvq 有等待的接收者，直接将数据复制过去并唤醒接收者（零拷贝）
2. 若缓冲区未满，将数据写入 buf
3. 否则当前 goroutine 阻塞，加入 sendq

关闭 channel 注意事项：
- 向已关闭的 channel 发送数据会 panic
- 从已关闭的 channel 接收会返回零值和 `false`
- 只有发送方应该关闭 channel

### Go 内存逃逸分析

逃逸分析决定变量分配在栈还是堆上：

常见逃逸场景：
- 返回局部变量的指针
- 变量被闭包引用
- 接口赋值（interface 装箱）
- 大小不确定的变量（如 `make([]int, n)`，n 是运行时变量）
- 调用 `fmt.Println` 等接收 `interface{}` 的函数

查看逃逸分析：`go build -gcflags="-m" ./...`

### Go 垃圾回收（GC）

Go 使用**三色标记清除**算法 + 混合写屏障：

三色标记：
- **白色**：未被访问，GC 结束后清除
- **灰色**：已被发现但子对象未扫描完
- **黑色**：本身及所有子对象均已扫描

GC 触发条件：
- 堆内存达到上次 GC 后的 2 倍（`GOGC=100`，默认）
- 手动调用 `runtime.GC()`
- 距上次 GC 超过 2 分钟

Go 1.14+ 采用混合写屏障，STW（Stop The World）时间通常在亚毫秒级。

## Java

### JVM 内存模型

JVM 运行时内存划分：
- **堆（Heap）**：存放对象实例，GC 主要区域，分为新生代（Eden + Survivor）和老年代
- **方法区（Method Area）**：存储类信息、常量池、静态变量（JDK 8 改为元空间 Metaspace，使用本地内存）
- **栈（JVM Stack）**：每个线程独有，存放栈帧（局部变量表、操作数栈、动态链接、返回地址）
- **程序计数器（PC Register）**：当前线程执行的字节码行号，线程私有
- **本地方法栈（Native Method Stack）**：为 native 方法服务

### Java 并发：synchronized vs ReentrantLock

| 特性 | synchronized | ReentrantLock |
|------|-------------|---------------|
| 实现层次 | JVM 内置关键字 | Java API（AQS） |
| 是否可中断 | 不可中断 | 可中断（`lockInterruptibly()`） |
| 超时尝试 | 不支持 | 支持（`tryLock(timeout)`） |
| 公平锁 | 不支持 | 支持（`new ReentrantLock(true)`） |
| 条件变量 | 单一（wait/notify） | 多个（`newCondition()`） |
| 自动释放 | 是（退出块自动释放） | 否（必须手动 `unlock()`） |

JDK 6 后 synchronized 引入锁升级机制（无锁 → 偏向锁 → 轻量级锁 → 重量级锁），性能接近 ReentrantLock。

### HashMap 的底层原理

Java 8 之后 HashMap 使用**数组 + 链表 + 红黑树**：

核心参数：
- 默认容量：16，负载因子：0.75
- 扩容阈值：`capacity * loadFactor`
- 链表转红黑树：链表长度 > 8 且数组长度 >= 64

`put` 流程：
1. 计算 key 的 hash（`hashCode() ^ (h >>> 16)`，高低位混合减少碰撞）
2. `(n-1) & hash` 定位桶位置
3. 桶为空直接插入；否则遍历链表/红黑树，key 相同则覆盖，否则追加
4. 插入后检查是否需要扩容或链表转树

线程不安全原因：多线程并发 put 可能触发并发扩容，导致数据丢失。线程安全场景用 `ConcurrentHashMap`。

## 数据结构与算法

### 二叉树的常见遍历

```
        1
       / \
      2   3
     / \
    4   5
```

- **前序**（根-左-右）：1 2 4 5 3
- **中序**（左-根-右）：4 2 5 1 3
- **后序**（左-右-根）：4 5 2 3 1
- **层序**（BFS）：1 2 3 4 5

迭代实现中序遍历（常考）：
```go
func inorderTraversal(root *TreeNode) []int {
    var res []int
    stack := []*TreeNode{}
    cur := root
    for cur != nil || len(stack) > 0 {
        for cur != nil {
            stack = append(stack, cur)
            cur = cur.Left
        }
        cur = stack[len(stack)-1]
        stack = stack[:len(stack)-1]
        res = append(res, cur.Val)
        cur = cur.Right
    }
    return res
}
```

### 常见排序算法复杂度对比

| 算法 | 时间复杂度（平均） | 时间复杂度（最坏） | 空间复杂度 | 稳定性 |
|------|-----------------|-----------------|----------|--------|
| 快速排序 | O(n log n) | O(n²) | O(log n) | 不稳定 |
| 归并排序 | O(n log n) | O(n log n) | O(n) | 稳定 |
| 堆排序 | O(n log n) | O(n log n) | O(1) | 不稳定 |
| 冒泡排序 | O(n²) | O(n²) | O(1) | 稳定 |
| 插入排序 | O(n²) | O(n²) | O(1) | 稳定 |
| 计数排序 | O(n+k) | O(n+k) | O(k) | 稳定 |

快排优化：三路快排（针对大量重复元素）、随机选基准（避免已排序数组退化 O(n²)）。

### 动态规划解题思路

DP 三要素：
1. **状态定义**：`dp[i]` 表示什么
2. **状态转移方程**：`dp[i]` 如何从子状态推导
3. **边界条件**：初始值是什么

经典例题 - 最长递增子序列（LIS）：
- `dp[i]` = 以 `nums[i]` 结尾的最长递增子序列长度
- `dp[i] = max(dp[j]+1)` for all `j < i` where `nums[j] < nums[i]`
- 朴素 O(n²)；结合二分查找可优化至 O(n log n)

## 数据库

### MySQL 索引的数据结构

MySQL InnoDB 使用 **B+ 树**作为索引结构，而非 B 树或哈希：

B+ 树特点：
- 所有数据存储在叶子节点，非叶节点只存储索引键
- 叶子节点之间通过双向链表连接，支持高效范围查询
- 树高通常为 3-4 层，每次查找只需 3-4 次磁盘 IO

对比 B 树：B 树非叶节点也存数据，导致每个节点能存的键更少，树更高，IO 次数更多。

聚簇索引 vs 二级索引：
- **聚簇索引**（主键索引）：叶子节点存完整行数据
- **二级索引**：叶子节点存主键值，查询数据需**回表**（再查一次聚簇索引）
- **覆盖索引**：查询字段全在索引中，避免回表

### MySQL 事务与 MVCC

事务四大特性 ACID：
- **原子性（Atomicity）**：事务要么全提交，要么全回滚，通过 undo log 实现
- **一致性（Consistency）**：事务前后数据满足约束
- **隔离性（Isolation）**：并发事务互不干扰，通过 MVCC + 锁实现
- **持久性（Durability）**：提交后数据永久保存，通过 redo log 实现

MVCC（多版本并发控制）核心：
- 每行数据有隐藏字段：`trx_id`（最后修改的事务 ID）、`roll_pointer`（指向 undo log）
- **Read View**：快照读时生成，包含当前活跃事务列表
- 读取时判断行的 `trx_id` 是否对当前事务可见，不可见则顺着 undo log 找历史版本

四种隔离级别及问题：

| 隔离级别 | 脏读 | 不可重复读 | 幻读 |
|---------|------|----------|------|
| 读未提交 | 有 | 有 | 有 |
| 读已提交 | 无 | 有 | 有 |
| 可重复读（默认） | 无 | 无 | 基本无（MVCC+间隙锁） |
| 串行化 | 无 | 无 | 无 |

### Redis 数据类型与使用场景

| 类型 | 底层结构 | 典型场景 |
|------|---------|---------|
| String | SDS（简单动态字符串）| 缓存、计数器、分布式锁 |
| Hash | ziplist / hashtable | 用户信息、购物车 |
| List | quicklist（ziplist 链表）| 消息队列、最新列表 |
| Set | intset / hashtable | 标签、去重、共同关注 |
| ZSet | ziplist / 跳表 | 排行榜、延时队列 |

Redis 分布式锁（SETNX）注意点：
- 设置过期时间（防死锁）：`SET key value EX 30 NX`
- value 用唯一 ID（防误删他人锁）
- 续期问题：业务超时时锁已过期，使用 Redisson 的 watchdog 机制自动续期

## 操作系统

### 进程、线程、协程的区别

- **进程**：资源分配的基本单位，有独立地址空间；进程间切换开销大，通过 IPC 通信
- **线程**：CPU 调度的基本单位，共享进程地址空间；切换比进程轻，但需注意同步
- **协程**：用户态的轻量级线程，由程序自身调度；无内核参与，切换成本极低

### 内存管理：虚拟内存与分页

虚拟内存的作用：
- 让每个进程拥有独立的逻辑地址空间，互不干扰
- 支持内存超额分配（物理内存不足时用磁盘 swap）
- 实现内存保护

分页机制：
- 虚拟地址 = 页号 + 页内偏移
- 通过**页表**将虚拟页号映射到物理页框号
- TLB（Translation Lookaside Buffer）是页表的高速缓存，减少地址翻译开销
- 多级页表（如 Linux x86-64 的四级页表）减少页表本身的内存占用

## 计算机网络

### TCP 三次握手与四次挥手

**三次握手（建立连接）：**
1. 客户端发 SYN（seq=x）→ 服务端
2. 服务端发 SYN+ACK（seq=y, ack=x+1）→ 客户端
3. 客户端发 ACK（ack=y+1）→ 服务端

为什么是三次而不是两次？两次握手服务端无法确认客户端能收到自己的消息，无法防止历史重复连接。

**四次挥手（断开连接）：**
1. 主动方发 FIN → 被动方（主动方进入 FIN_WAIT_1）
2. 被动方发 ACK → 主动方（主动方进入 FIN_WAIT_2，被动方进入 CLOSE_WAIT）
3. 被动方数据发完后发 FIN → 主动方（被动方进入 LAST_ACK）
4. 主动方发 ACK → 被动方，等待 2MSL 后关闭（TIME_WAIT 状态）

TIME_WAIT 存在原因：确保最后一个 ACK 能到达对端；防止旧连接的迷途报文影响新连接。

### HTTP/HTTPS 区别

- **HTTP**：明文传输，端口 80，无身份验证
- **HTTPS**：HTTP + TLS/SSL，端口 443，提供加密、完整性、身份认证

TLS 握手流程（TLS 1.3 简化）：
1. 客户端发 ClientHello（支持的加密套件、随机数）
2. 服务端发 ServerHello + 证书 + 公钥
3. 客户端验证证书，生成会话密钥（基于 ECDHE），发送加密的 Finished
4. 服务端验证后，双方用会话密钥对称加密通信

## 系统设计

### 如何设计一个高并发的短链接系统

核心需求：长链 → 短链，短链 → 302 重定向

短链生成方案：
- **哈希法**：对长链取 MD5/MurmurHash，取前 6-8 位字符（Base62），冲突时追加随机串重试
- **发号器**：全局自增 ID（可用数据库 AUTO_INCREMENT 或 Redis incr），转 Base62 编码

高并发优化：
- 短链到长链的映射缓存到 Redis（TTL 与业务一致）
- 数据库只做持久化，读请求 99% 走缓存
- 短链服务无状态，水平扩展；发号器单独部署，保证全局唯一

### 分布式系统中的 CAP 理论

CAP 理论：分布式系统无法同时满足以下三者：
- **C（Consistency）一致性**：所有节点同一时刻看到相同数据
- **A（Availability）可用性**：每个请求都能收到响应（不保证是最新数据）
- **P（Partition Tolerance）分区容错性**：网络分区时系统仍能运行

实际分布式系统网络分区不可避免，因此必须选 P，在 C 和 A 之间取舍：
- **CP 系统**（如 ZooKeeper、etcd）：网络分区时拒绝服务，保证强一致
- **AP 系统**（如 Cassandra、DNS）：网络分区时仍可用，但可能返回旧数据（最终一致性）
