
## 3. JVM、GC 与内存排查

### 3.1 JVM 内存区域概览

JVM 运行时通常讨论这些区域：

- Heap，堆，主要存放对象实例，是 GC 的核心区域
- Metaspace，元空间，存放类元数据，JDK 8 之后替代永久代
- JVM Stack，虚拟机栈，线程私有，存放栈帧、局部变量、操作数栈
- Program Counter Register，程序计数器，线程私有
- Native Method Stack，本地方法栈

如果线上服务出现内存问题，第一步不要只问“是不是 Full GC 太多”，而应先区分：

- 是堆内存持续上涨，还是元空间持续上涨
- 是对象存活时间变长，还是瞬时对象过多
- 是应用线程响应慢，还是 GC 日志显示 STW 时间长

### 3.2 GC、STW 与内存泄漏的关系

GC 是垃圾回收机制，STW 是回收过程中可能出现的应用暂停。GC 频繁不一定代表内存泄漏，内存泄漏也不一定第一时间表现为 Full GC。

常见误区：

- 误区一：只要 GC 频繁就是代码有泄漏
- 误区二：STW 很短就说明系统一定健康
- 误区三：Young GC 次数多一定比 Full GC 危险

更准确的判断方式：

- 观察堆使用量在 GC 之后是否能明显回落
- 观察老年代或大对象分配是否持续增长
- 观察对象年龄分布和晋升情况
- 结合业务流量判断问题是“自然增压”还是“异常堆积”

### 3.3 JVM 排查流程

一个实用的 JVM 排查顺序如下：

1. 看现象：P99 延迟升高、接口超时、CPU 高、容器内存接近上限
2. 看 GC 日志：Young GC、Mixed GC、Full GC 的频率和停顿时间
3. 看堆快照：对象分布、大对象、重复集合、缓存是否失控
4. 看线程状态：是否有大量线程等待锁、阻塞 IO、卡在 RPC
5. 看外部依赖：数据库慢查询、ES 查询慢、MQ 消费堆积是否反向拖累服务

### 3.4 JVM 故障案例

案例：某 Java 服务在高峰期出现“RT 抖动 + Full GC 频繁 + CPU 不算特别高”的问题。排查后发现：

- 请求高峰时有一批大型 JSON 反序列化对象进入缓存
- 缓存没有 TTL，也没有大小上限
- 老年代回收压力快速上升
- Full GC 后堆占用下降有限

最终结论：

- 根因不是 GC 算法本身，而是应用层缓存策略错误
- GC 只是把问题暴露出来
- 如果只调整 JVM 参数而不处理缓存逻辑，问题会反复出现

这里适合测试的问题包括：

- 什么情况下 GC 频繁不一定是内存泄漏
- JVM 排查第一步应该看什么
- Full GC 频繁但 CPU 不高可能说明什么
- 上述案例的根因是什么

## 4. Go 并发、goroutine 与性能优化

### 4.1 goroutine、线程与协程

goroutine 是 Go 运行时管理的轻量级执行单元。它和操作系统线程不是一一对应关系，而是通过 GMP 调度模型映射执行。

核心概念：

- G 是 goroutine
- M 是 machine，通常对应系统线程
- P 是 processor，调度上下文

常见面试式表述：

- goroutine 切换成本通常低于线程切换
- goroutine 适合处理大量高并发、短任务、IO 密集型场景
- goroutine 并不是“免费”的，失控创建一样会导致内存和调度开销上升

### 4.2 channel、锁与原子操作

Go 并发控制并不意味着“只用 channel，不用锁”。实际工程里，channel、`sync.Mutex`、`sync.RWMutex`、`atomic` 都有适合的场景。

大致建议：

- 任务编排、事件流转、worker pool 更适合 channel
- 共享 map、共享状态保护更适合锁
- 热点计数器、状态位更适合 atomic

常见误区：

- 误区一：channel 总是比 mutex 高级
- 误区二：RWMutex 在任何读多写少场景都一定更快
- 误区三：atomic 可以替代所有锁

### 4.3 Go 性能问题的排查顺序

Go 服务出现性能问题时，可以按这个顺序排：

1. 先看业务指标：QPS、错误率、P99、超时率
2. 再看资源指标：CPU、内存、goroutine 数、GC 次数
3. 再看 profile：CPU profile、heap profile、mutex profile、block profile
4. 最后看代码路径：热点函数、字符串拼接、JSON 编解码、无界 goroutine 创建

### 4.4 Go 并发案例

案例：某服务上线后出现 CPU 飙高、goroutine 数量不断上升、P99 延迟抖动。排查后发现：

- 为每个请求都起了多个 goroutine
- 下游超时时没有正确 cancel context
- 某些 goroutine 在等待 channel 读写时长期悬挂
- 结果聚合逻辑没有超时保护

结论：

- 根因是 goroutine 泄漏和上下文取消不完整
- 如果只扩容实例，问题只会被延后
- 需要补充 `context.WithTimeout`、统一 cancel、限制并发数、避免无界 fan-out

适合测试的问题包括：

- goroutine 和线程的区别
- Go 服务 CPU 高但不一定是纯计算问题，为什么
- goroutine 泄漏常见原因是什么
- context cancel 为什么重要

## 5. Kafka、MQ 与消息处理链路

### 5.1 Kafka 基础概念

Kafka 是一种分布式消息系统，也经常被泛称为 MQ。核心概念包括：

- Broker，服务节点
- Topic，主题
- Partition，分区
- Replica，副本
- ISR，同步副本集合
- Consumer Group，消费组

注意：

- Kafka 是 MQ 的一种，但 MQ 不等于 Kafka
- RabbitMQ 更偏传统消息队列模型
- RocketMQ、Pulsar 也属于常见消息系统

### 5.2 生产端关键参数

Kafka 生产端常见参数包括：

- `acks`
- `retries`
- `linger.ms`
- `batch.size`
- `compression.type`
- `enable.idempotence`

经验结论：

- `acks=all` 可靠性更高，但延迟可能更高
- 开启幂等可以减少重试带来的重复写入风险
- 合理的批量和压缩通常能提升吞吐
- 盲目把 `linger.ms` 调得很大，可能损伤低延迟场景

### 5.3 消费端常见问题

Kafka 消费端容易出现的问题包括：

- 消费堆积
- 分区倾斜
- rebalance 频繁
- 提交 offset 不合理
- 消费处理时间长于 poll 周期

一个常见错误是：业务处理很重，但消费者线程模型没有隔离，导致 poll 和业务执行互相影响，最后触发 rebalance，问题进一步放大。

### 5.4 Kafka 故障案例

案例：某业务出现“消息堆积 + 消费延迟升高 + 实例 CPU 偏高”的问题。排查结果如下：

- Topic 分区数不足，消费并行度不够
- 某一个 key 导致热点分区，分区倾斜明显
- 消费端每条消息都同步调用下游 RPC
- RPC 超时设置过长，失败重试没有熔断
- offset 提交策略过晚，导致 rebalance 后重复消费增多

最终建议：

- 先确认分区是否足够支撑消费并发
- 评估 key 设计是否导致热点
- 解耦 poll 线程与业务处理线程
- 缩短不合理超时，加入重试上限与熔断
- 评估是否需要 DLQ 来接住异常消息

适合测试的问题包括：

- Kafka 和 RabbitMQ 有什么区别
- 消费堆积常见原因有哪些
- rebalance 频繁通常会带来什么影响
- 上述案例里为什么“长 RPC 超时”会放大堆积问题

## 6. Redis 缓存、击穿、穿透、雪崩与分布式锁

### 6.1 Redis 常见使用场景

Redis 常被用于：

- 热点数据缓存
- 分布式锁
- 计数器
- 排行榜
- 会话存储
- 限流

### 6.2 缓存问题区分

缓存相关问题经常被混淆，本文给出简化定义：

- 缓存穿透：请求的数据根本不存在，缓存和数据库都查不到
- 缓存击穿：某个热点 key 过期瞬间，大量请求同时打到数据库
- 缓存雪崩：大量 key 同时失效，导致后端承压

建议：

- 对不存在的数据也可短期缓存空值，缓解穿透
- 对热点 key 使用互斥重建、逻辑过期或单飞机制，缓解击穿
- 给 TTL 加随机抖动，缓解雪崩

### 6.3 Redis 分布式锁

Redis 分布式锁常见实现思路：

- 使用 `SET key value EX 30 NX`
- value 使用唯一请求 ID
- 释放锁时先校验 value，再删除 key

常见问题：

- 业务执行时间超过锁过期时间
- 客户端异常退出，锁提前失效
- 只做加锁，不做续期与保护

如果场景要求更高，通常会引入成熟客户端能力，例如自动续期、看门狗或更完整的互斥语义。

### 6.4 Redis 故障案例

案例：某接口在大促时数据库被打满，应用团队怀疑 Redis 不稳定。最后发现：

- 热点商品详情 key 统一在整点过期
- 没有做空值缓存和热点重建保护
- 下游数据库索引本身也不理想

结论：

- 这不是单点 Redis 故障，而是“缓存击穿 + TTL 设计不合理 + DB 慢查询”的组合问题
- 单独扩 Redis 实例不能根治

适合测试的问题包括：

- 缓存穿透、击穿、雪崩的区别
- 为什么给 TTL 加随机值
- Redis 分布式锁为什么要校验 value
- 这个案例的根因是什么

## 7. MySQL 索引、事务、MVCC 与慢查询

### 7.1 B+ 树索引与回表

MySQL InnoDB 常见索引结构是 B+ 树。对工程实践来说，比记概念更重要的是理解下面几点：

- 主键索引叶子节点存完整行数据
- 二级索引叶子节点通常存主键值
- 通过二级索引找到主键再回主键索引取整行，这个过程叫回表
- 如果查询字段都在索引里，可以形成覆盖索引

### 7.2 慢查询常见原因

慢查询不一定是数据库“性能差”，常见根因包括：

- 没有合适索引
- 索引命中率低
- 过滤条件选择性差
- 返回行数太多
- 排序和分页方式不合理
- SQL 写法导致无法走索引
- 应用层连接池设置不当

### 7.3 MVCC 与事务隔离

MVCC 是多版本并发控制，用来提升读写并发能力。它并不等于“数据库完全没有锁”，而是在很多读场景下减少了读写冲突。

工程上可以这样理解：

- 快照读通常依赖 MVCC
- 当前读仍然会涉及锁
- 可重复读并不意味着不会出现所有并发现象

### 7.4 MySQL 故障案例

案例：某分页接口在数据量上涨后变慢。排查后发现：

- 使用了 `limit 100000, 20` 这种深分页
- 排序字段和过滤字段没有形成合适联合索引
- 应用侧还在每次查询后做额外 RPC enrich

最终建议：

- 避免深分页，改用基于游标或 last id 的翻页方式
- 按过滤字段和排序字段设计联合索引
- 评估 enrichment 是否能异步化或批量化

适合测试的问题包括：

- 什么是回表
- 覆盖索引有什么好处
- 深分页为什么慢
- 上面案例中为什么不是只加机器就能解决

## 8. RPC、超时、重试、熔断、幂等

### 8.1 超时、重试与熔断不是一回事

这三个概念经常被混用：

- 超时：请求等待多久算失败
- 重试：失败后是否再试一次或多次
- 熔断：当错误率持续过高时，暂时快速失败，防止雪崩

错误做法：

- 超时设置过长，导致资源占满
- 重试没有上限，导致放大流量
- 所有错误都重试，包括参数错误和不可恢复错误
- 没有区分读请求和写请求的幂等性

### 8.2 幂等设计

幂等的关键不是“请求只发一次”，而是“多次执行产生同样结果或可接受结果”。

常见实现手段：

- 幂等号
- 去重表
- 状态机约束
- 条件更新
- 消息消费去重

### 8.3 RPC 链路案例

案例：某推荐服务 RT 飙升，调用链路显示主要时间花在下游 RPC。问题包括：

- 超时设为 3 秒，远高于实际 SLA
- 每次失败默认重试 3 次
- 没有熔断
- 下游错误已经明显升高，但上游还在持续堆压

最终结论：

- 看起来是“下游慢”，其实上游重试策略也在放大故障
- 合理的短超时、有限重试、快速失败和降级策略比无限等待更可靠

适合测试的问题包括：

- 超时、重试、熔断的区别
- 为什么重试会放大故障
- 写请求为什么特别强调幂等
- 上述案例的放大器是什么

## 9. 可用性、限流、降级与容量设计

### 9.1 限流与降级

限流和降级都是保护系统的手段，但目的不同：

- 限流是限制进入系统的请求量，避免系统被打穿
- 降级是当资源不足或依赖异常时，主动关闭次要能力或返回简化结果

常见限流算法：

- 固定窗口
- 滑动窗口
- 令牌桶
- 漏桶

一般工程上更常提令牌桶，因为它更适合控制平均速率并允许一定突发。

### 9.2 容量评估

容量评估至少应回答这些问题：

- 峰值 QPS 是多少
- 平均响应时间和 P99 分别是多少
- 单实例承载上限是多少
- 下游依赖的瓶颈在哪里
- 是否有缓存、批量化、异步化空间

### 9.3 可用性案例

案例：某聚合接口依赖用户服务、商品服务、推荐服务和画像服务。一次故障中：

- 推荐服务 RT 抖动
- 商品服务偶发超时
- 聚合接口没有降级分支
- 上游网关还在高并发放量

结果：

- 聚合接口线程被占满
- 排队时间变长
- P99 快速恶化
- 局部故障放大成系统性故障

建议：

- 给关键依赖设置不同级别的超时
- 对非核心字段允许降级
- 对热点流量做限流和缓存保护
- 避免一个接口在高峰时串行依赖过多下游

适合测试的问题包括：

- 限流和降级有什么区别
- 为什么一个下游抖动会拖垮聚合接口
- 令牌桶适合什么场景
- 上述案例中有哪些保护手段缺失

## 10. 综合排查剧本

本节故意设计成“长上下文 + 多条件 + 多技术点交叉”，特别适合测试 parent-child retrieval、dynamic topk 和 strategic topk。

### 10.1 剧本一：消息堆积引发链路雪崩

现象：

- Kafka 消费堆积
- 消费延迟持续上升
- 消费实例 CPU 偏高但不是 100%
- 下游 RPC 错误率升高
- 聚合接口 P99 明显抖动

可能原因不止一个：

- 分区数不足，消费并发不够
- 热点 key 导致分区倾斜
- 消费逻辑同步调用下游，且 RPC 超时过长
- 重试策略没有上限
- 没有熔断和 DLQ

排查顺序建议：

1. 先看是否是生产速度突然升高
2. 再看分区和消费组并发是否匹配
3. 再看热点 key 是否导致某分区被打满
4. 再看消费端是否串行阻塞在 RPC
5. 最后看 offset 提交和 rebalance 是否进一步放大问题

这类问题的重点不是只找一个点，而是识别“拥塞链条”。

### 10.2 剧本二：缓存击穿叠加数据库慢查询

现象：

- 热点接口 RT 飙升
- Redis 命中率下降
- MySQL 连接数升高
- CPU 不是唯一瓶颈
- Full GC 频率也开始升高

可能的因果链：

- 热点 key 在同一时间过期
- 请求回源数据库
- 数据库索引不佳导致慢查询
- 线程堆积引发对象堆积
- GC 压力上升，RT 进一步恶化

核心结论：

- 这不是一个单点问题
- Redis、MySQL、应用线程池、JVM 内存都可能被串起来
- 只盯某一层通常会误判

### 10.3 剧本三：Go 服务 goroutine 泄漏

现象：

- goroutine 数持续增长
- 内存缓慢爬升
- P99 时好时坏
- CPU 高峰不稳定

可能原因：

- fan-out 后未正确汇总或未关闭 channel
- context 没有 cancel
- 某些下游阻塞时，等待协程长期残留
- 定时任务不断创建新 goroutine，但没有退出机制

建议排查：

- 先看 goroutine profile
- 再看是否存在固定调用路径的堆积
- 检查 context timeout 和 cancel 是否成对出现
- 检查 worker pool 是否有上限

## 11. 明确结论区

本节专门放一些可以被系统直接引用的短结论，适合测试 citation consistency。

- “GC 频繁不一定意味着内存泄漏，关键要看回收后堆是否回落以及对象是否持续存活。”
- “Kafka 是一种 MQ，但 MQ 不等于 Kafka。”
- “缓存穿透是查不到，缓存击穿是热点 key 失效瞬间被并发打穿，缓存雪崩是大量 key 同时失效。”
- “超时、重试、熔断不是一回事，错误配置重试会放大故障。”
- “goroutine 不是免费资源，失控创建会带来调度和内存开销。”
- “覆盖索引的价值之一是避免回表。”
- “限流是保护入口，降级是牺牲次要能力保护核心路径。”
