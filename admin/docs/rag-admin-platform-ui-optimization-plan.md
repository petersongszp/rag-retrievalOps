# RAG 管理台前端体验与视觉平台化优化方案

## 1. 文档定位

本文档用于指导当前 `admin` 前端从“功能验证型后台”升级为“可面向真实用户使用的平台型管理台”。

本次优化不以新增后端能力为主，而是围绕现有页面做四类改造：

1. 视觉升级：统一布局、颜色、间距、卡片、表格、图表和空状态，让页面看起来像正式产品。
2. 信息架构升级：把功能按用户任务重新分组，减少 Phase、Debug、Test 等工程推进痕迹。
3. 术语汉化和解释：保留专业能力，但用更低门槛的中文表达帮助用户理解。
4. 新手指引产品化：把过去用于测试功能的说明，改成自然的使用引导、状态提示和最佳实践。

目标不是把后台做成营销页，而是做成一个安静、清晰、可信的企业级工作台：用户能快速知道当前系统是否健康、该先做什么、出问题去哪查、风险动作如何确认。

## 2. 当前现状

### 2.1 技术与页面基础

当前前端位于 `admin/`，主要技术栈为：

1. `Next.js 14 + React 18 + TypeScript`。
2. `Ant Design 5` 作为主要组件库。
3. `Tailwind CSS` 用于局部样式和布局。
4. 已有多页面管理台骨架：`AdminShell`、侧边导航、顶部知识库选择器、面包屑、登录注册页。

当前已覆盖的主要页面：

1. `/dashboard`：概览、监控指标和关键入口。
2. `/knowledge-bases` 与 `/knowledge-bases/[kbId]`：知识库、文档、入库任务。
3. `/retrieval-lab` 与 `/retrieval-lab/debug`：检索测试、检索调试视图。
4. `/trace-logs/retrieval` 与 `/trace-logs/ingest`：检索日志和入库日志。
5. `/evaluation/*` 与 `/quality-monitor`：评测、报告和质量监控。
6. `/strategy-center`：策略开关、影响分析和回滚。
7. `/cost-ops/*`、`/audit`、`/alerts`、`/reports/weekly`：治理、成本、审计、告警和周报。
8. `/api-keys`、`/tenant/*`、`/docs/integration`、`/semantic-cache`、`/embedding-cache`。

### 2.2 主要体验问题

1. 平台定位不够明确：品牌仍是 `RAG Admin`，更像内部后台名，而不是用户可理解的平台名。
2. 工程阶段痕迹明显：页面文案中存在 `Phase 3`、`Phase 4`、`P3`、`P4`、`Phase2 Baseline` 等研发阶段表达。
3. 测试语气明显：`检索实验室`、`运行检索测试`、`检查契约字段`、`debug trace` 等词让用户感觉自己在使用测试工具。
4. 专业词汇门槛较高：`Feature Flags`、`Canary`、`Gate`、`Baseline`、`Candidate`、`Recall@K`、`nDCG`、`P95 Latency Delta` 等缺少面向业务用户的解释。
5. 视觉系统不统一：Ant Design 默认卡片较多，页面之间标题、说明、按钮、指标卡、表格密度和颜色表达不够一致。
6. 首页缺少平台总控感：当前概览更像指标和入口堆叠，缺少“今日状态、待处理事项、核心风险、推荐动作”的运营台心智。
7. 空状态偏技术：空数据、接口失败、权限不足、字段缺失等提示多以开发视角描述，缺少用户下一步行动。
8. 表格与详情页信息密度不稳定：有些页面英文指标较多，有些页面字段名直接展示接口字段，正式用户理解成本高。
9. 登录页也有研发阶段痕迹：例如 `Phase 4 Admin Access` 和“开发期默认入口”等表达应移出正式产品界面。

## 3. 优化目标与 Gate

### 3.1 核心目标

把前端升级为“知识库智能检索运营平台”的管理台：

1. 新用户能在 5 分钟内理解：怎么建知识库、怎么上传文档、怎么验证检索效果、怎么查看质量和风险。
2. 管理员能在首页直接看到：系统是否健康、是否有失败任务、是否有质量下降、是否有成本异常、是否有待处理告警。
3. 研发或高级运营人员仍能进入调试、日志、策略和评测页面，但入口文案是产品化的，不暴露内部测试口径。
4. 所有专业指标保留，但有中文名称、短解释和使用场景。
5. 页面视觉统一、可信、克制，适合长时间使用。

### 3.2 验收标准

1. 侧边导航和页面标题中不再出现研发阶段名：`Phase`、`P3`、`P4`、`Baseline` 等只可保留在开发文档或高级详情字段中。
2. 用户主路径不再出现“测试前端”的语气，例如“运行测试”“检查契约字段”“debug 数据”等。
3. 每个主页面都有统一结构：页面标题、业务说明、核心指标、主要操作、列表或详情、空状态。
4. 首页能回答三件事：今天是否正常、哪里需要处理、下一步建议做什么。
5. 关键专业词汇完成汉化和解释，英文缩写只作为辅助显示。
6. 所有空状态、错误状态、权限状态、字段缺失状态都有明确下一步。
7. 表格、指标卡、筛选区、详情抽屉和危险操作确认的样式统一。
8. 移动端或窄屏下不出现明显文字重叠、按钮挤压和布局错位。

## 4. 范围边界

### 4.1 必须做

1. 全局品牌、导航、页面标题和核心说明文案重写。
2. 建立平台级视觉规范：颜色、字体、间距、卡片、按钮、表格、标签、图表和状态。
3. 首页重构为平台总览，不只是指标堆叠。
4. 知识库、检索、质量、策略、成本、审计、告警等页面做术语汉化。
5. 将“测试指引”改为“使用引导”和“排障建议”。
6. 为高门槛功能增加说明气泡、帮助抽屉或字段解释。
7. 梳理危险操作确认文案，例如策略回滚、Collection 切换、删除文档、吊销密钥。

### 4.2 暂不做

1. 不重写后端 API，不把前端优化变成后端能力重构。
2. 不引入新的大型 UI 框架，优先复用 Ant Design 和 Tailwind。
3. 不做营销型首页，不用大面积装饰图、渐变球或过度动效。
4. 不隐藏专业能力；只是把专业能力翻译成用户可理解的表达。
5. 不用假数据把平台伪装成已上线能力，缺失字段仍要显示为“暂未返回”或“暂不支持”。

## 5. 产品命名与信息架构

### 5.1 推荐平台命名

当前：`RAG Admin`

建议改为以下其一：

1. `知识检索运营平台`
2. `智能知识库管理平台`
3. `RAG 知识运营平台`

推荐首版使用：`智能知识库管理平台`。

理由：

1. “智能知识库”比 `RAG` 更容易被非研发用户理解。
2. “管理平台”比 `Admin` 更正式。
3. 仍然能覆盖知识库、检索、质量、成本、审计和接入能力。

### 5.2 导航改造建议

当前导航基本按功能和研发阶段堆叠。建议按用户任务分组：

| 分组 | 当前页面 | 建议中文名称 | 用户心智 |
|---|---|---|---|
| 工作台 | `/dashboard` | 工作台 | 看整体状态和待办 |
| 知识资产 | `/knowledge-bases` | 知识库管理 | 管文档、入库、处理任务 |
| 检索体验 | `/retrieval-lab` | 检索调优 | 验证问答效果和查看引用 |
| 检索体验 | `/retrieval-lab/debug` | 检索链路分析 | 查看一次检索为什么这样返回 |
| 质量运营 | `/quality-monitor` | 质量看板 | 看最近质量变化 |
| 质量运营 | `/evaluation/datasets` | 评测样本 | 管标准问题和期望答案 |
| 质量运营 | `/evaluation/runs` | 评测任务 | 发起和查看质量评测 |
| 质量运营 | `/evaluation/reports/[runId]` | 评测报告 | 看优化前后对比 |
| 策略运营 | `/strategy-center` | 策略管理 | 管高级检索策略和回滚 |
| 运维治理 | `/trace-logs/*` | 链路追踪 | 查请求、查入库、定位问题 |
| 运维治理 | `/cost-ops/cost` | 成本分析 | 看成本趋势和高成本请求 |
| 运维治理 | `/cost-ops/vector-db` | 向量库运维 | 看 Collection 健康和容量 |
| 安全治理 | `/audit` | 操作审计 | 查谁做了什么 |
| 安全治理 | `/alerts` | 风险告警 | 处理质量、成本、容量风险 |
| 平台接入 | `/api-keys` | 接入密钥 | 管应用接入凭证 |
| 平台接入 | `/docs/integration` | 接入指南 | 给开发者看如何调用 |
| 租户与账号 | `/tenant/*` | 组织设置、用量统计 | 管组织、套餐、用量 |

### 5.3 首屏结构建议

`/dashboard` 建议从“指标陈列”改为“工作台”：

1. 顶部状态条：当前知识库、时间范围、系统健康、最近更新时间。
2. 今日概览：知识库数、文档数、入库成功率、检索请求量、空结果率、每千次问答成本。
3. 待处理事项：失败入库任务、质量下降、成本异常、未确认告警、即将超限资源。
4. 快捷操作：新建知识库、上传文档、发起检索调优、查看质量报告、创建接入密钥。
5. 趋势区：质量趋势、请求趋势、成本趋势、错误类型 TopN。
6. 最近活动：最近上传、最近策略变更、最近告警、最近评测任务。

## 6. 术语汉化规范

### 6.1 导航和页面级术语

| 当前词 | 建议展示 | 备注 |
|---|---|---|
| Dashboard / 概览 | 工作台 | 更像正式平台入口 |
| Retrieval Lab / 检索实验室 | 检索调优 | 减少“实验/测试”感 |
| Debug / 调试详情 | 链路分析 | 调试能力保留，入口更产品化 |
| Trace Logs / 链路日志 | 链路追踪 | 更符合排障场景 |
| Evaluation | 质量评测 | 直接表达价值 |
| Strategy Center | 策略管理 | 减少英文中心感 |
| Cost & Ops | 成本与运维 | 更清晰 |
| Vector DB | 向量库 | 面向中文用户 |
| API Keys | 接入密钥 | 可在详情里保留 API Key |
| Tenant | 组织 | 如果产品面向企业用户，比“租户”更自然 |
| Audit | 操作审计 | 明确用途 |
| Alerts | 风险告警 | 强调处理事项 |

### 6.2 指标和字段术语

| 当前词 | 建议展示 | 说明方式 |
|---|---|---|
| Recall@K | 召回率@K | 前 K 条结果中命中标准答案的比例 |
| MRR | 首个正确结果排名 | 正确结果越靠前越好 |
| nDCG | 排序质量 | 同时考虑命中结果和排序位置 |
| Citation Precision | 引用准确率 | 回答引用是否能支撑答案 |
| P95 Latency | P95 响应耗时 | 95% 请求能在该时间内完成 |
| Empty Rate | 空结果率 | 没有返回有效结果的请求比例 |
| Baseline | 对照版本 | 优化前或稳定参考版本 |
| Candidate | 候选版本 | 正在验证的新策略版本 |
| Gate | 发布门禁 | 是否允许上线或转正的检查项 |
| Feature Flags | 策略开关 | 控制策略是否启用 |
| Canary | 小流量试用 | 先让少量请求使用新策略 |
| Rollback | 回退 | 恢复到稳定策略或版本 |
| Request ID | 请求编号 | 用于排查单次请求 |
| Debug Trace | 链路明细 | 一次检索从改写到返回的全过程 |
| Collection | 向量集合 | 向量库中保存文档向量的集合 |
| Embedding | 向量化 | 把文本转换为可检索的向量 |
| Rerank | 重排 | 对候选结果重新排序 |
| TopK | 返回数量 | 本次最多取回的候选结果数 |
| Token | 模型用量 | 可在成本页保留 Token，但加解释 |

### 6.3 文案替换示例

1. `运行检索测试` -> `开始检索验证`
2. `检查 request_id 与契约字段` -> `查看本次检索的链路编号、相关度和引用来源`
3. `查看调试视图` -> `查看链路分析`
4. `P3 summary fields are not fully available yet` -> `高级链路信息暂未完整返回`
5. `回滚到 Phase2 Baseline` -> `回退到稳定检索策略`
6. `Feature Flags` -> `策略开关`
7. `Impact 分析` -> `策略影响分析`
8. `Gate Checks` -> `发布门禁检查`
9. `Dataset Size` -> `样本数量`
10. `Phase 4 暂不开放` -> `当前版本暂不支持`

## 7. 视觉设计规范

### 7.1 整体风格

关键词：清晰、可信、克制、专业、可扫描。

不建议：

1. 大面积渐变背景。
2. 过多圆角大卡片。
3. 页面里套页面、卡片里套卡片。
4. 所有模块都使用同一种蓝紫色。
5. 为了“酷”加入不服务任务的装饰元素。

建议：

1. 使用浅灰页面背景，白色内容区，边框比阴影更常用。
2. 卡片圆角控制在 `6px - 8px`，保持工具型产品气质。
3. 页面顶部使用清楚的信息层级，不做营销 hero。
4. 表格、筛选、指标区尽量对齐，减少视觉跳动。
5. 用颜色表达状态，不用颜色装饰页面。

### 7.2 颜色建议

当前 `tailwind.config.js` 里 `primary` 是绿色，页面中大量使用 Ant Design 默认蓝、紫、青。建议统一为：

1. 主色：深青蓝 `#0F766E` 或企业蓝 `#2563EB`，二选一。
2. 成功：`#16A34A`
3. 警告：`#D97706`
4. 危险：`#DC2626`
5. 信息：`#2563EB`
6. 中性色：`#0F172A`、`#475569`、`#94A3B8`、`#E2E8F0`、`#F8FAFC`

推荐首版选 `#2563EB` 作为主色，因为与 Ant Design 默认生态更接近，迁移成本低。

### 7.3 组件规则

1. 页面标题区：
   - 标题：一句话说明当前页面。
   - 副标题：说明用户能在这里完成什么，不写研发阶段。
   - 右侧：只放 1-3 个高频操作。
2. 指标卡：
   - 标题用中文。
   - 主数字突出。
   - 解释文案不超过一行。
   - 增长、下降、异常用统一颜色和图标。
3. 表格：
   - 默认密度适中。
   - 操作列固定在右侧。
   - 接口字段名不要直接作为表头。
   - 长 ID 默认截断，支持复制。
4. 筛选区：
   - 统一放在内容区顶部。
   - 高频筛选常驻，低频筛选收起到“更多筛选”。
5. 空状态：
   - 说明当前为什么为空。
   - 给出下一步按钮。
   - 避免“暂无数据”孤零零出现。
6. 错误状态：
   - 分清权限不足、接口失败、字段缺失、加载超时。
   - 提供重试、联系管理员、查看接入配置等下一步。
7. 危险操作：
   - 必须二次确认。
   - 明确影响范围。
   - 用业务语言说明后果。

## 8. 页面级优化路线

### L0 全局品牌与布局统一

目标：先让整个平台不再像内部测试后台。

任务：

1. `AdminShell` 品牌从 `RAG Admin` 改为 `智能知识库管理平台`。
2. 侧边底部移除 `Phase 4` 说明，改为平台状态或帮助入口。
3. 顶部知识库选择器改为“当前知识库”，选中后展示更简洁。
4. 统一刷新按钮为图标按钮，并增加 tooltip。
5. 页面内容最大宽度和间距统一，例如 `24px` 页面间距、`16px` 模块间距。
6. 登录页移除 `Phase 4 Admin Access` 等开发期表达。

验收：

1. 全局框架无 `Phase`、`P3`、`P4` 可见文案。
2. 页面外观统一，侧边栏、顶部栏和内容区没有明显割裂。

### L1 工作台重构

目标：让 `/dashboard` 成为用户每天进入平台后的总控台。

任务：

1. 页面标题从“概览”改为“工作台”。
2. 首屏增加“当前状态”和“待处理事项”。
3. 把知识库、文档、入库任务、失败任务保留为核心资产指标。
4. 把 P95、空结果率、每千次成本等指标改成中文解释。
5. 增加快捷入口：新建知识库、上传文档、开始检索验证、查看质量报告。
6. 将“P4 成本治理”“审计覆盖入口”“治理告警入口”改为“成本分析”“操作审计”“风险告警”。

验收：

1. 用户不用懂研发阶段，也能理解每个指标的意义。
2. 首页能自然引导用户处理失败任务和质量风险。

### L2 知识库管理产品化

目标：让知识库页面像资产管理工具，而不是文件上传测试页。

任务：

1. 新建知识库弹窗里的示例文案保留，但改成正式业务示例。
2. 知识库列表增加状态解释：可用、处理中、异常、停用。
3. 文档上传区域增加支持格式、大小限制、处理流程说明。
4. 入库任务状态改为用户能理解的阶段：解析中、切分中、向量化中、写入中、已完成、失败。
5. 失败任务提供“重试”“查看原因”“复制错误编号”。

验收：

1. 用户能知道文档从上传到可检索经历了哪些状态。
2. 失败时知道下一步该重试还是联系管理员。

### L3 检索调优替代检索实验室

目标：保留检索验证能力，但不让它看起来像测试工具。

任务：

## 9. 新手指引与测试说明改造

### 9.1 原则

过去为了测试功能写的指引，不应直接给最终用户看。改造原则：

1. 把“测试某功能是否可用”改为“完成某个业务目标”。
2. 把“检查字段是否返回”改为“确认结果是否可信”。
3. 把“debug / trace”改为“链路分析 / 排障详情”。
4. 把“Phase 能力”改为“当前版本支持的能力”。
5. 把“示例数据”改为“推荐样例”或“入门样例”。

### 9.2 指引形态

建议增加三类指引：

1. 首次进入工作台：
   - 创建知识库
   - 上传文档
   - 开始检索验证
   - 加入质量样本
   - 创建接入密钥
2. 页面内轻引导：
   - 空状态给下一步按钮。
   - 高级指标给 tooltip。
   - 危险操作给影响范围。
3. 排障指引：
   - 入库失败：查看失败原因 -> 重试 -> 联系管理员。
   - 检索无结果：检查知识库、关键词、入库状态、过滤条件。
   - 质量下降：查看评测报告 -> 查看失败样本 -> 进入链路分析。
   - 成本升高：查看高成本请求 -> 查看策略版本 -> 判断是否回退。

## 12. 维护规则

1. 用户界面不得出现研发阶段词：`Phase`、`P0-P4`、`contract freeze`、`debug trace`、`mock`、`test`，除非位于开发者接入文档或高级原始字段区。
2. 页面标题必须使用用户任务命名，不使用内部模块名。
3. 新增英文缩写指标时，必须同时提供中文名称和简短解释。
4. 空状态必须包含下一步动作。
5. 危险操作必须说明影响范围和回退方式。
6. 缺失字段不可伪装成 0，必须说明“暂未返回”或“当前版本暂不支持”。
7. 任何视觉优化都不能牺牲表格可读性和重复操作效率。
